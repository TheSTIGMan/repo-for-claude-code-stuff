## Lab 2.4: Configure and Manage Software {#lab-2-4}

::: labinfo
**Objective:** 2.4 Given a scenario, configure and manage software in a Linux environment.\
**Domain:** 2.0 Services and User Management (20% of the exam)\
**Time:** about 180 minutes (it is fine to split it over two or three sessions)\
**VM:** ubuntu-lab (most tasks) and rocky-lab (Task 4)\

Installing, updating, and removing software is the job a Linux administrator does most often. In this lab you will use `apt` and `dpkg` on Ubuntu, `dnf` and `rpm` on Rocky, add a signed third-party repository, build a program from source, try the language package managers `pip`, `cargo`, and `npm`, and run sandboxed apps. Then you will set up small but real DNS, NTP, DHCP, web (Apache and Nginx), SMTP, and IMAP4 services, because the exam expects you to recognize their basic configuration.

### What you'll practice

- Installation, update, and removal of software from a **repository**, from **source**, and from package files, including **package dependencies and conflicts**
- **Package managers**: `apt`, `dpkg`, `dnf`, `rpm`
- **Language-specific** package managers: **pip**, **cargo**, **npm**
- **Repository management**: **enabling/disabling** repositories, adding a **third-party** repository, checking **GPG signatures**
- **Package and repository exclusions** (`apt-mark hold`, `exclude=` in `dnf.conf`, `--exclude`)
- **Update alternatives** (`update-alternatives`)
- **Software configuration** (files in `/etc`, drop-in directories)
- **Sandboxed applications** (snap, Flatpak, AppImage)
- **Basic configs of common services**: **DNS** (BIND), **NTP/PTP** (chrony, linuxptp), **DHCP** (Kea), **HTTP** (**Apache httpd**, **Nginx**), **SMTP** (Postfix), **IMAP4** (Dovecot)

### How it works

**Packages.** A *package* is an archive that contains a program's files plus *metadata*: its name, version, a description, a list of the other packages it needs, and scripts to run during install and removal. Debian and Ubuntu use `.deb` packages. Red Hat, Rocky, Fedora, and SUSE use `.rpm` packages.

**Two layers of tools.** Each family has a low-level tool and a high-level tool:

```{.diagram}
                 Debian / Ubuntu          RHEL / Rocky
 High level      apt  (apt-get)           dnf  (yum)
   - talks to repositories, downloads, solves dependencies
                      |                        |
 Low level       dpkg                     rpm
   - installs ONE local package file, keeps the database
                      |                        |
 Database        /var/lib/dpkg/           /var/lib/rpm/
```

The low-level tool (`dpkg`, `rpm`) installs a single file you hand it and records what it installed. It does **not** download anything and does **not** fetch missing pieces. The high-level tool (`apt`, `dnf`) is the *package manager* you use day to day: it reads repository indexes, works out everything that must be installed, downloads it, and then calls the low-level tool.

**Repositories.** A *repository* (repo) is a web server or folder holding packages plus an index file that lists them. Your system has a list of repos it trusts. `apt update` (or `dnf makecache`) downloads fresh copies of the indexes so the package manager knows what versions exist. A *third-party* repository is one not run by your distribution, for example a vendor such as nginx.org or Docker.

**Dependencies and conflicts.** A *dependency* is another package that must be present for a package to work, such as a shared library. A *conflict* is a package that cannot be installed at the same time, often because both provide the same service or file. For example, only one NTP daemon or one mail server should own a port. Package managers read these rules from the metadata and either solve them for you or refuse with an error.

**GPG signatures.** Anyone could put a fake package on a mirror. To prevent that, the repository owner signs the index (apt) or each package (rpm) with a private **GPG** key. Your system holds the matching public key. Before installing, the package manager checks the signature with the public key. If the check fails, it refuses. That is why adding a third-party repo always has two steps: install its public key, then add the repo line.

**Source code.** Sometimes software is not packaged at all. Then you download the *source code* (usually a `.tar.gz` "tarball") and compile it yourself. The classic three steps are `./configure` (check the system and write a Makefile), `make` (compile), and `sudo make install` (copy files, usually under `/usr/local`). The package manager does not track these files, so you are responsible for updates and removal.

**Language package managers.** Programming languages have their own package managers: `pip` for Python, `npm` for JavaScript (Node.js), and `cargo` for Rust. They pull libraries from their own online registries (PyPI, the npm registry, crates.io). They can install packages *locally* (inside one project folder or virtual environment) or *globally* (for the whole system). Local is safer because it cannot break programs that the OS itself depends on.

**Sandboxed applications.** A *sandbox* is a restricted environment that limits what a program can see and change. Snap (Canonical), Flatpak (common on desktops), and AppImage (a single portable file) bundle an app with its libraries. Snap and Flatpak also confine the app, so it cannot read your whole home directory or write anywhere it likes.

**Configuration.** Almost all software is configured with text files under `/etc`. Modern packages use *drop-in directories* such as `/etc/nginx/conf.d/` or `/etc/chrony/conf.d/`. You add your own small file there instead of editing the big main file. Package updates then replace the main file safely while your file stays untouched.

**Services you will meet.** DNS turns names into IP addresses (BIND's daemon is `named`). NTP keeps clocks in sync (chrony); PTP is a more precise time protocol for local networks (linuxptp). DHCP hands out IP addresses automatically (Kea). HTTP serves web pages (Apache, called `apache2` on Ubuntu and `httpd` on Rocky, and Nginx). SMTP moves email between servers (Postfix). IMAP4 lets mail clients read mailboxes stored on a server (Dovecot).

### Tasks

#### Task 1: Use apt to search, install, inspect, and remove packages

1. Make the lab folder and refresh the package indexes.

    ```bash
    mkdir -p ~/labs/2.4 && cd ~/labs/2.4
    sudo apt update
    ```

    ```{.output}
    Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease
    Get:2 http://archive.ubuntu.com/ubuntu noble-updates InRelease [126 kB]
    Hit:3 http://security.ubuntu.com/ubuntu noble-security InRelease
    ...
    Reading package lists... Done
    12 packages can be upgraded. Run 'apt list --upgradable' to see them.
    ```

    ::: explain
    **What just happened:** `apt update` downloads the latest package *indexes* from every enabled repository. It installs nothing. `Hit` means the index had not changed; `Get` means a new one was downloaded. `noble` is the code name of Ubuntu 24.04, and `noble-updates` and `noble-security` are separate repos for fixes. Always run `apt update` before installing, or apt may try to fetch versions that no longer exist on the mirror.
    :::

2. See what could be upgraded, then search for a package.

    ```bash
    apt list --upgradable
    apt search --names-only '^tree$'
    ```

    ::: explain
    **What just happened:** `apt list --upgradable` shows installed packages that have a newer version available. `apt search` searches names and descriptions; `--names-only` limits it to names, and `'^tree$'` is a regular expression meaning "exactly tree". The single quotes stop the shell from changing the special characters.
    :::

3. Look at a package's details before you install it.

    ```bash
    apt show tree
    apt-cache policy tree
    ```

    ```{.output}
    Package: tree
    Version: 2.1.1-2ubuntu3
    Priority: optional
    Section: universe/utils
    ...
    Depends: libc6 (>= 2.34)
    ...
    tree:
      Installed: (none)
      Candidate: 2.1.1-2ubuntu3
      Version table:
         2.1.1-2ubuntu3 500
            500 http://archive.ubuntu.com/ubuntu noble/universe amd64 Packages
    ```

    ::: explain
    **What just happened:** `apt show` prints the metadata, including `Depends:` (the dependencies). `apt-cache policy` shows the installed version, the *candidate* (the version apt would install), and which repository offers each version. The number `500` is the *priority*; when several repos offer a package, apt picks the highest priority, then the highest version. Your version numbers may differ.
    :::

4. Install the package and use it.

    ```bash
    sudo apt install -y tree
    tree -L 1 /etc/apt
    ```

    ::: explain
    **What just happened:** `apt install` resolved dependencies, downloaded the `.deb`, and called `dpkg` to install it. `-y` answers "yes" to the confirmation question. `tree -L 1` shows one level of the `/etc/apt` folder, where apt keeps its configuration.
    :::

5. Look at dependencies in both directions.

    ```bash
    apt-cache depends tree
    apt-cache rdepends --installed libc6 | head
    ```

    ::: explain
    **What just happened:** `apt-cache depends` lists what a package *needs*. `apt-cache rdepends` ("reverse depends") lists what needs *it*; `--installed` limits the list to installed packages. Almost everything depends on `libc6`, the C library, which is why you must never remove it. (`apt depends` and `apt rdepends` work too.)
    :::

6. Remove, purge, and clean up.

    ```bash
    sudo apt remove -y tree
    dpkg -l tree
    sudo apt purge -y tree
    sudo apt autoremove -y
    ```

    ```{.output}
    ||/ Name           Version        Architecture Description
    +++-==============-==============-============-=================
    rc  tree           2.1.1-2ubuntu3 amd64        displays an indented directory tree
    ```

    ::: explain
    **What just happened:** `apt remove` deletes the program but keeps its configuration files. `dpkg -l` shows the state as two letters: `rc` means "removed, config files remain" (`ii` means fully installed). `apt purge` removes the configuration files too. `apt autoremove` removes packages that were installed only as dependencies and are no longer needed by anything.
    :::

You do not need to run a full upgrade in this lab, but you must know the upgrade commands.

::: explain
**Upgrades in brief:** `sudo apt upgrade` installs newer versions of installed packages but never removes a package. `sudo apt full-upgrade` (the old `apt-get dist-upgrade`) may also remove packages if that is needed to solve new dependencies. `sudo apt install --only-upgrade <pkg>` upgrades just one package. On a real server, read the list apt prints before you type `y`.
:::

::: checkpoint
**Checkpoint:** `dpkg -l tree` should now print `dpkg-query: no packages found matching tree`, because the package was purged.
:::

#### Task 2: Package files, dependency failures, conflicts, and holds

1. Download a `.deb` file without installing it. `fortune-mod` prints random quotes and needs packages that a server does not have.

    ```bash
    cd ~/labs/2.4
    apt download fortune-mod
    ls *.deb
    dpkg -I fortune-mod_*.deb | grep -E 'Package|Version|Depends'
    ```

    ::: explain
    **What just happened:** `apt download` fetches a package file into the current folder. `dpkg -I` (capital i, "info") reads the metadata inside the file. The `Depends:` line lists packages that must be installed first. The `*` is a shell wildcard so you do not need to type the long version number.
    :::

2. Install the file with the low-level tool and watch it fail.

    ```bash
    sudo dpkg -i fortune-mod_*.deb
    ```

    ```{.output}
    Selecting previously unselected package fortune-mod.
    Preparing to unpack fortune-mod_1%3a1.99.1-7.1build1_amd64.deb ...
    Unpacking fortune-mod (1:1.99.1-7.1build1) ...
    dpkg: dependency problems prevent configuration of fortune-mod:
     fortune-mod depends on fortunes-min | fortunes | fortune-cookie-db; however:
      Package fortunes-min is not installed.
      ...
     fortune-mod depends on librecode0 (>= 3.6); however:
      Package librecode0 is not installed.

    dpkg: error processing package fortune-mod (--install):
     dependency problems - leaving unconfigured
    Errors were encountered while processing:
     fortune-mod_1%3a1.99.1-7.1build1_amd64.deb
    ```

    ::: explain
    **What just happened:** `dpkg -i` (install) unpacked the files but could not *configure* the package, because `dpkg` never downloads dependencies. The package is now in a "broken" half-installed state. Until you fix it, apt will refuse most other installs and tell you to run `apt --fix-broken install`. The `|` in `fortunes-min | fortunes` means "any one of these".
    :::

3. Let apt fix the broken dependency, then run the program.

    ```bash
    sudo apt -f install -y
    dpkg -l fortune-mod
    fortune
    ```

    ::: explain
    **What just happened:** `apt -f install` (long form `apt --fix-broken install`) finds the missing dependencies, downloads them, and finishes configuring `fortune-mod`. `dpkg -l` now shows `ii`. On Ubuntu the program lives in `/usr/games`, which is already in your `PATH`.
    :::

    ::: tip
    The easy way to install a local `.deb` is `sudo apt install ./file.deb`. The `./` tells apt it is a file, and apt resolves dependencies automatically. You may see a note that the download was "performed unsandboxed as root" because apt's `_apt` user cannot read your home folder; that is harmless.
    :::

4. Ask `dpkg` questions about installed packages.

    ```bash
    dpkg -L fortune-mod | head
    dpkg -S /usr/games/fortune
    ```

    ::: explain
    **What just happened:** `dpkg -L` lists every file a package installed. `dpkg -S` does the reverse: it searches for which package owns a file. These two are the Debian equivalents of `rpm -ql` and `rpm -qf` that you will use on Rocky.
    :::

5. See a real package conflict. Ubuntu may ship the small `systemd-timesyncd` time client, and `chrony` is a full NTP daemon. Only one time daemon may run, so the packages conflict. Simulate the install with `-s`.

    ```bash
    apt-cache show chrony | grep -E '^(Conflicts|Provides|Replaces)'
    apt install -s chrony | grep -E 'REMOVED|NEW|^Remv|^Inst'
    ```

    ```{.output}
    Conflicts: ntp, time-daemon, timekeeper
    Provides: time-daemon
    The following packages will be REMOVED:
    The following NEW packages will be installed:
    Remv systemd-timesyncd [255.4-1ubuntu8]
    Inst chrony (4.5-1ubuntu4 Ubuntu:24.04/noble [amd64])
    ```

    ::: explain
    **What just happened:** `-s` (simulate) makes apt print its plan without changing anything, so you do not need `sudo`. Both packages *provide* the virtual package `time-daemon`, and chrony *conflicts* with any other `time-daemon`, so apt plans to remove `systemd-timesyncd`. If chrony is already installed on your VM, apt instead says it is already the newest version; the `Conflicts:` line still shows the rule. Whenever apt says "will be REMOVED", stop and read the list.
    :::

6. Exclude a package from upgrades with a hold.

    ```bash
    sudo apt-mark hold fortune-mod
    apt-mark showhold
    sudo apt-mark unhold fortune-mod
    ```

    ::: explain
    **What just happened:** `apt-mark hold` freezes a package at its current version: `apt upgrade` skips it and lists it as "kept back". This is how you *exclude* a package from updates on Debian/Ubuntu (for example, to keep a database at a tested version). `showhold` lists held packages, and `unhold` releases the hold.
    :::

::: checkpoint
**Checkpoint:** `fortune` prints a quote, `dpkg -l fortune-mod` begins with `ii`, and `apt-mark showhold` prints nothing.
:::

#### Task 3: Manage Ubuntu repositories and add a signed third-party repo

1. Look at where Ubuntu 24.04 keeps its repository list.

    ```bash
    ls /etc/apt/sources.list /etc/apt/sources.list.d/
    cat /etc/apt/sources.list.d/ubuntu.sources
    ```

    ```{.output}
    Types: deb
    URIs: http://archive.ubuntu.com/ubuntu/
    Suites: noble noble-updates noble-backports
    Components: main restricted universe multiverse
    Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg

    Types: deb
    URIs: http://security.ubuntu.com/ubuntu/
    Suites: noble-security
    Components: main restricted universe multiverse
    Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
    ```

    ::: explain
    **What just happened:** Ubuntu 24.04 uses the newer *deb822* format (named after the email-header style of RFC 822). Each block, separated by a blank line, is one source. `Types: deb` means binary packages (`deb-src` would mean source packages). `URIs` is the server, `Suites` are the release names, and `Components` are sections: `main` (supported free software), `restricted` (supported non-free drivers), `universe` (community-maintained), and `multiverse` (non-free). `Signed-By` names the public key file that must have signed this repo. The old one-line format in `/etc/apt/sources.list` still works, but on 24.04 that file usually only holds a comment.
    :::

2. Install the tools needed to add a third-party repository and create the folder for its key.

    ```bash
    sudo apt install -y curl gnupg ca-certificates
    sudo install -m 0755 -d /etc/apt/keyrings
    ```

    ::: explain
    **What just happened:** `curl` downloads the key, `gnupg` converts it, and `ca-certificates` lets curl trust HTTPS sites. `install -m 0755 -d` creates the directory `/etc/apt/keyrings` with permissions `0755` if it does not exist. That folder is the recommended place for keys you add by hand.
    :::

3. Download nginx.org's public signing key and store it in binary form.

    ```bash
    curl -fsSL https://nginx.org/keys/nginx_signing.key \
      | sudo gpg --dearmor -o /etc/apt/keyrings/nginx-archive-keyring.gpg
    gpg --show-keys /etc/apt/keyrings/nginx-archive-keyring.gpg
    ```

    ```{.output}
    pub   rsa2048 2011-08-19 [SC] [expires: 2027-05-24]
          573BFD6B3D8FBC641079A6ABABF5BD827BD9BF62
    uid                      nginx signing key <signing-key@nginx.com>
    ...
    ```

    ::: explain
    **What just happened:** `curl -fsSL` downloads quietly (`-s`), follows redirects (`-L`), shows errors (`-S`), and fails on HTTP errors (`-f`). The key arrives as text ("ASCII armored"). `gpg --dearmor` converts it to the binary format apt reads, and `-o` writes it to the file. `gpg --show-keys` prints the key's fingerprint without importing it anywhere. On a real system, compare the fingerprint with the one published on the vendor's website before trusting it. You may see more than one key; vendors rotate keys over time.
    :::

4. Add the repository in deb822 format. This uses a *heredoc*: everything between `<<'EOF'` and the line `EOF` is sent as input to `sudo tee`, which writes it to the file. The quotes around `EOF` stop the shell from changing anything inside.

    ```bash
    cat <<'EOF' | sudo tee /etc/apt/sources.list.d/nginx.sources
    Types: deb
    URIs: http://nginx.org/packages/ubuntu
    Suites: noble
    Components: nginx
    Signed-By: /etc/apt/keyrings/nginx-archive-keyring.gpg
    EOF
    sudo apt update
    ```

    ::: explain
    **What just happened:** You created a new source file. `apt update` now also downloads `nginx.org`'s index and checks its signature with only the key named in `Signed-By`. Limiting a key to one repo with `Signed-By` is important: an old, deprecated method (`apt-key add`) trusted every key for every repo. The URL uses plain `http`, which is fine because the GPG signature, not the transport, protects the packages from tampering.
    :::

5. Compare the versions offered by the two repositories.

    ```bash
    apt-cache policy nginx
    ```

    ```{.output}
    nginx:
      Installed: (none)
      Candidate: 1.28.0-1~noble
      Version table:
         1.28.0-1~noble 500
            500 http://nginx.org/packages/ubuntu noble/nginx amd64 Packages
         ...
         1.24.0-2ubuntu7 500
            500 http://archive.ubuntu.com/ubuntu noble/main amd64 Packages
    ```

    ::: explain
    **What just happened:** Both repos have priority 500, so apt chooses the higher version, which comes from nginx.org. This is the power and the risk of third-party repos: they can replace distribution packages. You could raise or lower a repo's priority with a *pin* file in `/etc/apt/preferences.d/`. You will not install from nginx.org in this lab; later tasks use Ubuntu's own `nginx`.
    :::

6. Disable the third-party repository without deleting it, and confirm.

    ```bash
    echo 'Enabled: no' | sudo tee -a /etc/apt/sources.list.d/nginx.sources
    sudo apt update
    apt-cache policy nginx | head -4
    ```

    ::: explain
    **What just happened:** In deb822 format, adding `Enabled: no` to a block disables that source. `tee -a` *appends* to the file instead of overwriting it. After `apt update`, the candidate version comes from Ubuntu again. To re-enable it, delete that line (or change it to `yes`). With the old one-line format, you disable a repo by putting `#` at the start of its line.
    :::

    ::: tip
    `add-apt-repository ppa:<user>/<name>` adds a Launchpad PPA (Personal Package Archive), which is another kind of third-party repo. It downloads the key and writes the source file for you. `add-apt-repository --remove` undoes it.
    :::

::: checkpoint
**Checkpoint:** `apt-cache policy nginx` shows a candidate version from `archive.ubuntu.com`, and `grep Enabled /etc/apt/sources.list.d/nginx.sources` prints `Enabled: no`.
:::

#### Task 4: Use dnf and rpm on Rocky Linux

Run every command in this task on rocky-lab.

1. Install a package, read its information, and find which package provides a file.

    ```bash
    # on rocky-lab
    sudo dnf install -y tree
    dnf info tree
    dnf provides /usr/bin/dig
    ```

    ```{.output}
    Name         : tree
    Version      : 1.8.0
    Release      : 10.el9
    Architecture : x86_64
    Size         : 56 k
    Source       : tree-1.8.0-10.el9.src.rpm
    Repository   : @System
    From repo    : baseos
    ...
    bind-utils-32:9.16.23-24.el9_5.x86_64 : Utilities for querying DNS name servers
    Repo        : appstream
    Matched from:
    Filename    : /usr/bin/dig
    ```

    ::: explain
    **What just happened:** `dnf install` works like `apt install`: it resolves dependencies and downloads from repos. There is no separate "update the index" step, because dnf refreshes its cached metadata automatically when it is old (you can force it with `sudo dnf makecache`). `dnf info` shows metadata; `@System` means installed. `dnf provides` searches all repos for a file path, so you can find which package to install when a command is missing. `yum` still exists on Rocky 9 as a link to `dnf`.
    :::

2. Query the RPM database directly.

    ```bash
    # on rocky-lab
    rpm -qi tree | head -5
    rpm -ql tree
    rpm -qf /usr/bin/tree
    rpm -qa | grep -c .
    ```

    ::: explain
    **What just happened:** `rpm -q` means query. `-qi` shows info, `-ql` lists the files in a package, `-qf` finds which package owns a file, and `-qa` lists all installed packages (`grep -c .` counts the lines). These read the local database only, so they work offline.
    :::

3. Use the history to undo a transaction.

    ```bash
    # on rocky-lab
    sudo dnf history
    ```

    ```{.output}
    ID     | Command line             | Date and time    | Action(s)      | Altered
    --------------------------------------------------------------------------------
         4 | install -y tree          | 2026-10-10 14:02 | Install        |    1
         3 | ...
    ```

    Replace `4` below with the ID of your `install -y tree` line.

    ```bash
    # on rocky-lab
    sudo dnf history info 4
    sudo dnf history undo -y 4
    rpm -q tree
    ```

    ::: explain
    **What just happened:** dnf records every transaction. `history info` shows exactly what changed, and `history undo` reverses it (here, it removes `tree`). This is a quick way to back out a bad install. `rpm -q tree` now prints `package tree is not installed`. The normal way to remove a package is `sudo dnf remove tree`.
    :::

4. List repositories, then disable and enable one.

    ```bash
    # on rocky-lab
    dnf repolist
    dnf repolist all
    sudo dnf install -y dnf-plugins-core
    sudo dnf config-manager --set-disabled extras
    dnf repolist
    sudo dnf config-manager --set-enabled extras
    ```

    ```{.output}
    repo id                         repo name
    appstream                       Rocky Linux 9 - AppStream
    baseos                          Rocky Linux 9 - BaseOS
    extras                          Rocky Linux 9 - Extras
    ```

    ::: explain
    **What just happened:** `dnf repolist` shows enabled repos; `repolist all` also shows disabled ones such as `crb`. Repos are defined in `.repo` files in `/etc/yum.repos.d/`. `config-manager` (from `dnf-plugins-core`) edits those files for you: `--set-disabled` writes `enabled=0` and `--set-enabled` writes `enabled=1`. For a single command only, use `--enablerepo=<id>` or `--disablerepo=<id>`.
    :::

5. Add a popular third-party repo: EPEL (Extra Packages for Enterprise Linux). The EPEL documentation tells you to enable the `crb` repo first because some EPEL packages need it.

    ```bash
    # on rocky-lab
    sudo dnf config-manager --set-enabled crb
    sudo dnf install -y epel-release
    dnf repolist
    sudo dnf install -y htop
    ```

    ```{.output}
    Importing GPG key 0x3228467C:
     Userid     : "Fedora (epel9) <epel@fedoraproject.org>"
     Fingerprint: FF8A D134 4597 106E CE81 3B91 8A38 72BF 3228 467C
     From       : /etc/pki/rpm-gpg/RPM-GPG-KEY-EPEL-9
    Key imported successfully
    ```

    ::: explain
    **What just happened:** `epel-release` is a tiny package from Rocky's `extras` repo that drops `/etc/yum.repos.d/epel.repo` and the EPEL public key into place. The first time you install from EPEL, dnf imports that key (`-y` accepted it for you). `htop` is not in Rocky's own repos; it comes from EPEL.
    :::

6. Inspect GPG checking and verify a package file yourself.

    ```bash
    # on rocky-lab
    grep -E '^\[|gpgcheck|gpgkey' /etc/yum.repos.d/rocky.repo | head -6
    rpm -q gpg-pubkey --qf '%{NAME}-%{VERSION}-%{RELEASE}  %{SUMMARY}\n'
    cd /tmp && dnf download tree
    rpm -K tree-*.rpm
    ```

    ```{.output}
    [baseos]
    gpgcheck=1
    gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-Rocky-9
    ...
    gpg-pubkey-350d275d-6279464b  Rocky Enterprise Software Foundation - Release key 2022 ...
    gpg-pubkey-3228467c-613798eb  Fedora (epel9) <epel@fedoraproject.org> public key
    tree-1.8.0-10.el9.x86_64.rpm: digests signatures OK
    ```

    ::: explain
    **What just happened:** `gpgcheck=1` tells dnf to verify every package's signature against the key in `gpgkey=`. 4. **PTP.** The Precision Time Protocol syncs clocks to under a microsecond on a local network using hardware timestamps in the network card. Virtual NICs usually do not have that hardware.

    ::: tip
    **Explore/simulate:** Install the tools and check what your NIC supports (replace `enp0s3` with your interface from `ip -br link`):

    ```bash
    sudo apt install -y linuxptp ethtool
    ethtool -T enp0s3
    sudo timeout 10 ptp4l -i enp0s3 -S -m
    ```

    `ethtool -T` lists timestamping capabilities; a VM usually shows only `software-*` modes and `PTP Hardware Clock: none`. `ptp4l` is the PTP daemon: `-S` uses software timestamps, `-m` prints messages to the screen, and `timeout 10` stops it after 10 seconds. With no other PTP clock on the network it announces itself and ends up as the grandmaster (`assuming the grand master role`). On real hardware, `phc2sys` then copies the NIC's clock to the system clock. Config lives in `/etc/linuxptp/ptp4l.conf`.

5. **DNS with BIND.** Install the BIND server and look at its main file.

    ```bash
    sudo apt install -y bind9 bind9-dnsutils
    cat /etc/bind/named.conf
    ```

    ::: explain
    **What just happened:** The package is `bind9`; the daemon is `named` (name daemon). `named.conf` just includes three files: `named.conf.options` (global settings), `named.conf.local` (your zones), and `named.conf.default-zones`. 6. Declare an authoritative zone for the made-up domain `lab.test` (`.test` is reserved for testing). Open the zones file with `sudo nano /etc/bind/named.conf.local` and add:

    ```text
    zone "lab.test" {
        type primary;
        file "/etc/bind/db.lab.test";
    };
    ```

7. Create the zone file with the records. Replace the IPs with yours.

    ```bash
    cat <<'EOF' | sudo tee /etc/bind/db.lab.test
    $TTL 300
    @       IN  SOA ns1.lab.test. admin.lab.test. (
                    2026101001 ; serial
                    3600       ; refresh
                    900        ; retry
                    604800     ; expire
                    300 )      ; negative-cache TTL
            IN  NS    ns1.lab.test.
    ns1     IN  A     192.168.100.10
    web     IN  A     192.168.100.10
    rocky   IN  A     192.168.100.20
    www     IN  CNAME web
    EOF
    ```

    ::: explain
    **What just happened:** A *zone file* lists a domain's records. `$TTL 300` means resolvers may cache answers for 300 seconds. `@` stands for the zone name itself. The `SOA` (Start of Authority) record names the primary server and the admin email (`admin.lab.test.` means `admin@lab.test`), plus timers; increase the *serial* every time you edit the file. `NS` names the zone's name server, `A` maps a name to an IPv4 address, and `CNAME` makes one name an alias for another. The trailing dot in `ns1.lab.test.` means "fully qualified"; without it BIND appends the zone name.

10. Back up the default Kea config and write a small one. Kea uses JSON: curly braces hold named settings, square brackets hold lists, and every comma matters.

    ```bash
    sudo cp /etc/kea/kea-dhcp4.conf /etc/kea/kea-dhcp4.conf.orig
    cat <<'EOF' | sudo tee /etc/kea/kea-dhcp4.conf
    {
      "Dhcp4": {
        "interfaces-config": { "interfaces": [ "lab-dhcp0" ] },
        "lease-database": { "type": "memfile", "persist": true },
        "valid-lifetime": 3600,
        "subnet4": [
          {
            "id": 1,
            "subnet": "10.99.0.0/24",
            "pools": [ { "pool": "10.99.0.100 - 10.99.0.200" } ],
            "option-data": [
              { "name": "routers", "data": "10.99.0.1" },
              { "name": "domain-name-servers", "data": "10.99.0.1" },
              { "name": "domain-name", "data": "lab.test" }
            ]
          }
        ]
      }
    }
    EOF
    sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf
    ```

    ::: explain
    **What just happened:** `interfaces` limits Kea to `lab-dhcp0`. `memfile` stores leases in a CSV file under `/var/lib/kea/`. `valid-lifetime` is the lease time in seconds. The `subnet4` entry defines the network, the *pool* of addresses to hand out, and *options* sent to clients: default gateway (`routers`), DNS servers, and domain name. `kea-dhcp4 -t` tests the file and exits; it reports the error and line if anything is wrong. Because `tee` overwrites an existing file, the file keeps its original owner and permissions, so the `_kea` service user can still read it.

    ::: explain
    **What just happened:** On Ubuntu, Nginx reads every file linked into `/etc/nginx/sites-enabled/`; `sites-available/` is just storage. A `server` block is Nginx's *virtual host*: `listen` sets the port, `server_name` the host name it answers to, and `root` the folder of web files. Removing the `default` link (the file itself stays in `sites-available`) frees port 80. `nginx -t` tests the config. `reload` applies it without dropping current connections. Nginx packages from nginx.org and on Rocky use `/etc/nginx/conf.d/*.conf` instead of `sites-enabled`.
    :::

2. Install Apache and add a name-based virtual host on port 80.

    ```bash
    sudo apt install -y apache2
    sudo mkdir -p /var/www/apache-lab
    echo '<h1>Hello from Apache site1</h1>' | sudo tee /var/www/apache-lab/index.html
    cat <<'EOF' | sudo tee /etc/apache2/sites-available/site1.conf
    <VirtualHost *:80>
        ServerName site1.lab.test
        DocumentRoot /var/www/apache-lab
        ErrorLog ${APACHE_LOG_DIR}/site1-error.log
        CustomLog ${APACHE_LOG_DIR}/site1-access.log combined
    </VirtualHost>
    EOF
    sudo a2ensite site1
    sudo apachectl configtest
    sudo systemctl reload apache2
    ```

    ::: explain
    **What just happened:** A `<VirtualHost>` block is Apache's virtual host. `ServerName` is the host name it answers to, so many sites can share one IP and port (*name-based* virtual hosting). `DocumentRoot` is the folder of web files. `a2ensite` creates the link in `sites-enabled` (`a2dissite` removes it); `a2enmod`/`a2dismod` do the same for modules. `apachectl configtest` prints `Syntax OK` when the file is valid.
    :::

3. Test both web servers and see which process owns which port.

    ```bash
    curl -H 'Host: site1.lab.test' http://localhost/
    curl -s http://localhost/ | grep -o '<title>.*</title>'
    sudo ss -tlnp | grep -E ':(80|8080) '
    ```

    ```{.output}
    <h1>Hello from Apache site1</h1>
    <title>Apache2 Ubuntu Default Page: It works</title>
    LISTEN 0  511   0.0.0.0:8080   0.0.0.0:*  users:(("nginx",pid=5120,fd=6),...)
    LISTEN 0  511         *:80           *:*  users:(("apache2",pid=6011,fd=4),...)
    ```

    ::: explain
    **What just happened:** `-H 'Host: site1.lab.test'` sends the host name a browser would send, so Apache picks your virtual host. Without it, Apache uses the first (default) site. `ss -tlnp` shows TCP listeners: Nginx owns 8080 and Apache owns 80. Two daemons can never listen on the same address and port.
    :::

    ::: tip
    On Rocky the Apache package and service are both called **httpd**: `sudo dnf install -y httpd`, `sudo systemctl enable --now httpd`. The main file is `/etc/httpd/conf/httpd.conf`, extra files go in `/etc/httpd/conf.d/*.conf`, there is no `a2ensite`, and firewalld blocks it until you run `sudo firewall-cmd --permanent --add-service=http` and `sudo firewall-cmd --reload`.
    :::

4. **SMTP with Postfix.** Postfix normally asks setup questions during install. Pre-answer them with `debconf-set-selections` so that it only delivers mail locally.

    ```bash
    echo 'postfix postfix/main_mailer_type select Local only' | sudo debconf-set-selections
    echo 'postfix postfix/mailname string ubuntu-lab' | sudo debconf-set-selections
    sudo apt install -y postfix mailutils
    postconf -n | grep -E 'inet_interfaces|mydestination|default_transport'
    ```

    ```{.output}
    default_transport = error
    inet_interfaces = loopback-only
    mydestination = $myhostname, ubuntu-lab, localhost.localdomain, localhost
    ```

    ::: explain
    **What just happened:** `debconf-set-selections` stores answers before the package asks. *Local only* configures Postfix so it listens only on loopback (`inet_interfaces`), accepts mail for the names in `mydestination`, and refuses to send anywhere else (`default_transport = error`). That is safe for a lab. `postconf -n` shows settings that differ from the defaults in `/etc/postfix/main.cf`. `mailutils` provides the `mail` command. Postfix is an MTA (Mail Transfer Agent); it speaks SMTP on TCP port 25.
    :::

5. Send two messages to yourself, one with `mail` and one with the classic `sendmail` interface, then read the mailbox file.

    ```bash
    echo 'This is the body.' | mail -s 'Test 1 from mail' student
    printf 'Subject: Test 2 from sendmail\n\nSecond body.\n' | /usr/sbin/sendmail student
    sleep 2
    mailq
    grep '^Subject:' /var/mail/student
    ```

    ```{.output}
    Mail queue is empty
    Subject: Test 1 from mail
    Subject: Test 2 from sendmail
    ```

    ::: explain
    **What just happened:** `mail -s` sets the subject and reads the body from standard input. `/usr/sbin/sendmail` is a command every MTA provides for compatibility; it reads a full message (headers, a blank line, then the body). `mailq` shows mail waiting to be delivered; empty means it was delivered. Postfix stored the messages in *mbox* format in `/var/mail/student` (one file per user). Delivery logs are in `journalctl -u postfix@-` or `/var/log/mail.log`.
    :::

6. **IMAP4 with Dovecot.** Install the IMAP server and check its mail location and ports.

    ```bash
    sudo apt install -y dovecot-imapd
    sudo doveconf mail_location
    sudo ss -tlnp | grep dovecot
    ```

    ```{.output}
    mail_location = mbox:~/mail:INBOX=/var/mail/%u
    LISTEN 0 100  0.0.0.0:143  0.0.0.0:*  users:(("dovecot",pid=7001,fd=36))
    LISTEN 0 100  0.0.0.0:993  0.0.0.0:*  users:(("dovecot",pid=7001,fd=38))
    ```

    ::: explain
    **What just happened:** Dovecot is an IMAP (and POP3) server: it lets mail clients read mail the MTA delivered. `mail_location` says the INBOX is `/var/mail/<user>` (`%u` is the user name), which is where Postfix put your messages. IMAP4 uses TCP port 143 (upgradable to TLS with STARTTLS) and IMAPS uses 993 (TLS from the start). Config files are in `/etc/dovecot/conf.d/`. Ubuntu creates a self-signed certificate for testing.
    :::

7. List your mailbox and read a message with `curl`, which speaks IMAP. Type your `student` password when asked.

    ```bash
    curl -u student imap://localhost/
    curl -u student 'imap://localhost/INBOX;UID=1'
    ```

    ```{.output}
    * LIST (\HasNoChildren) "/" INBOX
    ...
    Subject: Test 1 from mail
    To: student@ubuntu-lab
    ...
    This is the body.
    ```

    ::: explain
    **What just happened:** `curl -u student` logs in as `student`. The first command lists folders; the second fetches message UID 1 from INBOX. Dovecot normally refuses plain-text passwords on unencrypted connections, but it treats connections from the same machine (localhost) as secure, so this works locally.
    :::

8. Talk raw IMAP over TLS on port 993, the way a mail client does. Type each line that starts with `a` and press Enter; replace `YOURPASSWORD`.

    ```bash
    openssl s_client -connect localhost:993 -quiet
    ```

    ```text
    a1 LOGIN student YOURPASSWORD
    a2 LIST "" "*"
    a3 SELECT INBOX
    a4 FETCH 1:* (BODY[HEADER.FIELDS (SUBJECT)])
    a5 LOGOUT
    ```

    ::: explain
    **What just happened:** `openssl s_client` opens a TLS connection and then lets you type. You will see certificate warnings because the certificate is self-signed; that is expected in a lab. Each IMAP command starts with a *tag* (`a1`, `a2`...) so the server's reply can say `a1 OK`. `SELECT` opens a folder and reports how many messages exist; `FETCH 1:*` gets the subject of every message.

### Exam corner

- Low-level tools install one local file and do not resolve dependencies: `dpkg -i`, `rpm -ivh`. High-level package managers resolve dependencies from repositories: `apt`, `dnf` (`yum`), `zypper` (SUSE).
- Fix a broken `dpkg -i` with `apt -f install` (`--fix-broken`). `apt install ./file.deb` and `dnf install ./file.rpm` resolve dependencies for local files.
- `apt remove` keeps config files (`rc` state); `apt purge` deletes them; `apt autoremove` removes unneeded dependencies. `apt update` refreshes indexes; `apt upgrade` installs newer versions.
- Query commands: `dpkg -l`, `dpkg -L` (files in package), `dpkg -S` (owner of file); `rpm -qa`, `rpm -qi`, `rpm -ql`, `rpm -qf`; `dnf provides` finds a package by file name even if it is not installed.
- Ubuntu 24.04 repos are in `/etc/apt/sources.list.d/ubuntu.sources` (deb822); disable a block with `Enabled: no`. RHEL repos are `.repo` files in `/etc/yum.repos.d/` with `enabled=` and `gpgcheck=`; toggle with `dnf config-manager --set-enabled/--set-disabled`.
- Third-party repos need a GPG public key: on Ubuntu a keyring in `/etc/apt/keyrings/` referenced by `signed-by`; on RHEL `rpm --import` or `gpgkey=`. `rpm -K file.rpm` checks a package signature. EPEL is enabled with `dnf install epel-release`.
- Exclusions: `apt-mark hold`; `exclude=` in `/etc/dnf/dnf.conf` or a `.repo` section; `dnf --exclude=pkg` for one command; `--disableexcludes` overrides.
- `dnf history` and `dnf history undo <ID>` roll back a transaction.
- Building from source: `./configure`, `make`, `sudo make install` (into `/usr/local`); needs `build-essential` (Ubuntu) or "Development Tools" (`dnf groupinstall`) on RHEL. Not tracked by the package manager.
- `pip` (PyPI, use a venv; PEP 668 blocks system installs on new distros), `npm` (`node_modules` local, `-g` global), `cargo` (crates.io, `Cargo.toml`).
- `update-alternatives --config|--set|--auto|--display` manages `/etc/alternatives` symlinks; RHEL calls it `alternatives`.
- Sandboxed apps: snap (`snap install`, strict confinement), Flatpak (`flatpak install flathub ...`), AppImage (single executable, `chmod +x`).
- Services: BIND `named` (`named-checkconf`, `named-checkzone`, `dig @server`), chrony (`chronyc sources`, `allow`), PTP (`ptp4l`, `phc2sys`), DHCP (Kea `kea-dhcp4 -t`, old `dhcpd.conf`), Apache (`apache2`/`httpd`, `apachectl configtest`), Nginx (`nginx -t`), Postfix (SMTP port 25, `postconf`, `mailq`), Dovecot (IMAP 143, IMAPS 993).
