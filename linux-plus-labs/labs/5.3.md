## Lab 5.3: Troubleshoot Networking Issues {#lab-5-3}

::: labinfo
**Objective:** 5.3 Given a scenario, analyze and troubleshoot networking issues on a Linux system.\
**Domain:** 5.0 Troubleshooting (22% of the exam)\
**Time:** about 3 hours\
**VM:** ubuntu-lab (most scenarios) and rocky-lab (firewall and dual stack scenarios)\
**Snapshot first:** Recommended. Most scenarios run inside isolated network namespaces and cannot cut off your SSH session, but the last two change real interfaces and firewall rules.
:::

Network problems are the most common "it's broken" tickets, and they are easy to misdiagnose if you jump straight to the application. In this lab you build a private practice network inside ubuntu-lab using network namespaces, then break it in all the ways the exam lists: links that go down, MTU mismatches, wrong subnet masks, bad gateways, broken routing, DNS failures, IP conflicts, DHCP failures, bond failover, and MAC spoofing protection. You finish with a firewall problem and a dual stack (IPv4 and IPv6) problem between your two real VMs.

### What you'll practice

- A bottom-up (OSI layer by layer) troubleshooting flow, starting with "cannot ping server"
- Link down and link negotiation issues (`ip link`, `ethtool`, NO-CARRIER)
- Interface misconfiguration: MTU mismatch, bonding, MAC spoofing, subnet, cannot ping server
- Routing issues: wrong or missing gateway, missing return routes, IP forwarding (`ip route`, `tracepath`, `traceroute`, `tcpdump`)
- Server unreachable: telling "refused", "timed out", and "no route to host" apart
- DNS issues (`resolvectl`, `dig`, `getent`, `/etc/hosts`, `/etc/resolv.conf`)
- IP conflicts (`arping -D`, `ip neigh`, `ip monitor neigh`)
- DHCP issues (DHCP server logs, client leases, APIPA 169.254.x.x addresses)
- Misconfigured firewalls (`firewall-cmd`, logging denied packets)
- Dual stack issues (IPv4 and IPv6): link-local addresses, address selection, `curl -4`/`-6`, `/etc/gai.conf`

### How it works

**Troubleshoot from the bottom up.** Networking is built in layers. Each layer depends on the one below it, so if you check them in order you never waste time on DNS when the cable is unplugged.

| Layer | Question | Commands |
|---|---|---|
| 1 Physical / link | Is the link up? Speed and duplex right? | `ip -br link`, `ethtool IF`, `networkctl` |
| 2 Data link | Right MAC? Can I resolve neighbors (ARP)? Same MTU? Bond healthy? | `ip neigh`, `arping`, `ip link` (mtu), `/proc/net/bonding/*` |
| 3 Network | Right IP and mask? Route and gateway? Can packets get there and back? | `ip -br addr`, `ip route`, `ip route get`, `ping`, `tracepath` |
| 4 Transport | Is the port open and listening? Is a firewall in the way? | `ss -tulnp`, `nc -zv`, `firewall-cmd`, `nft list ruleset` |
| 7 Application | Does the name resolve? Does the service answer? | `dig`, `getent hosts`, `resolvectl`, `curl -v` |

**The "cannot ping server" ladder.** When a host cannot reach a server, ping in this order and stop at the first failure. That failure tells you which layer is broken:

1. `ping 127.0.0.1` (the TCP/IP stack works)
2. `ping <my own IP>` (the interface has the address)
3. `ping <default gateway>` (the local network, cable, and ARP work)
4. `ping <remote server IP>` (routing works in both directions)
5. `ping <remote server name>` (DNS works)

Remember that some hosts and firewalls block ping on purpose, so a failed ping is a clue, not proof. Test the actual service port too (`nc -zv host port`).

**Error messages are clues:**

- `Network is unreachable`: your own host has no route to that network (often no default gateway).
- `Destination Host Unreachable`: ARP for the next hop failed; nobody answered on the local network.
- `Connection refused`: the target host answered but nothing listens on that port.
- `Connection timed out`: no answer at all (firewall silently dropping, host down, routing black hole).
- `No route to host` (for TCP): often a firewall *rejecting* the connection with an ICMP message.
- `Temporary failure in name resolution`: DNS failed.

**Your practice network.** A **network namespace** is a separate copy of the Linux network stack (its own interfaces, addresses, routes, and firewall), like a tiny virtual computer that shares the kernel. A **veth pair** is a virtual cable: two interfaces where whatever goes in one end comes out the other. A **bridge** is a virtual switch. You will build this inside ubuntu-lab:

```{.diagram}
  client ns                router ns                          server ns
 +------------+        +--------------------------+        +-------------+
 | veth-c     |--------| veth-rc                  |        |             |
 | 10.10.1.10 |  LAN 1 |   \_ br0 (switch)        |  LAN 2 |  veth-s     |
 +------------+        |      10.10.1.1/24        |--------|  10.10.2.20 |
                       |   veth-rs 10.10.2.1/24   |        +-------------+
 (later scenarios plug |   ip_forward=1 (router)  |
  more hosts into br0) +--------------------------+
```

Your real `enp0s3` (or similar) interface is never touched by these scenarios, so you cannot lose your SSH session. Every command that changes a namespace needs root: `sudo ip -n client ...` runs an `ip` command inside the `client` namespace, and `sudo ip netns exec client <command>` runs any command there.

3. Write the script that builds the practice network. Open `~/labs/5.3/labnet-up.sh` with `nano`, or use the heredoc below (a heredoc sends every line up to `EOF` into the file; quoting `'EOF'` stops the shell from changing `$` signs).

    ```bash
    cat <<'EOF' > ~/labs/5.3/labnet-up.sh
    #!/bin/bash
    # labnet-up.sh: build an isolated practice network with namespaces
    set -e
    for ns in client router server; do ip netns add "$ns"; done
    # cables (veth pairs): client<->router and router<->server
    ip link add veth-c type veth peer name veth-rc
    ip link add veth-s type veth peer name veth-rs
    ip link set veth-c netns client
    ip link set veth-rc netns router
    ip link set veth-rs netns router
    ip link set veth-s netns server
    # a switch (bridge) for LAN 1 inside the router namespace
    ip -n router link add br0 type bridge
    ip -n router link set br0 address 02:00:00:00:01:01
    ip -n router link set veth-rc master br0
    # addresses
    ip -n client addr add 10.10.1.10/24 dev veth-c
    ip -n router addr add 10.10.1.1/24 dev br0
    ip -n router addr add 10.10.2.1/24 dev veth-rs
    ip -n server addr add 10.10.2.20/24 dev veth-s
    # bring everything up
    for ns in client router server; do ip -n "$ns" link set lo up; done
    ip -n client link set veth-c up
    ip -n router link set br0 up
    ip -n router link set veth-rc up
    ip -n router link set veth-rs up
    ip -n server link set veth-s up
    # routing
    ip -n client route add default via 10.10.1.1
    ip -n server route add default via 10.10.2.1
    ip netns exec router sysctl -qw net.ipv4.ip_forward=1
    echo "lab network is up"
    EOF
    ```

    ::: explain
    **What just happened:** `ip netns add` creates the three namespaces. `ip link add ... type veth peer name ...` creates a cable with two ends, and `ip link set ... netns` moves each end into a namespace. The bridge `br0` acts as a switch for LAN 1 so you can plug more hosts in later. It gets a fixed MAC address because a Linux bridge otherwise copies the lowest MAC of its ports, so its address (the client's gateway MAC) would change every time you plug in or remove a host, leaving the client with a stale ARP entry. `net.ipv4.ip_forward=1` lets the router namespace pass packets between its interfaces; it is set only inside that namespace. `set -e` stops the script at the first error.
    :::

#### Task 2: Scenario 1: "The network is dead" (link down and link negotiation)

1. **Break it.** Unplug the client's "cable" at the switch end by shutting down the router-side port.

    ```bash
    sudo ip -n router link set veth-rc down
    ```

2. **Symptom.** The client cannot reach even its gateway.

    ```bash
    sudo ip netns exec client ping -c 2 -W 1 10.10.1.1
    ```

    ```{.output}
    2 packets transmitted, 0 received, 100% packet loss, time 1012ms
    ```

3. **Investigate layer 1 on the client.**

    ```bash
    sudo ip -n client -br link show veth-c
    sudo ip netns exec client ethtool veth-c | grep -E "Speed|Duplex|Link detected"
    sudo ip -n client route
    ```

    ```{.output}
    veth-c@if5       DOWN           0a:00:0c:29:b1:ae <NO-CARRIER,BROADCAST,MULTICAST,UP>
            Speed: 10000Mb/s
            Duplex: Full
            Link detected: no
    default via 10.10.1.1 dev veth-c linkdown
    10.10.1.0/24 dev veth-c proto kernel scope link src 10.10.1.10 linkdown
    ```

    ::: explain
    **What just happened:** The flags contain `UP` (the admin turned the interface on) but also `NO-CARRIER`, and the state is `DOWN`. That combination means "configured on, but no signal from the other end": an unplugged cable, a dead switch port, or a shut-down port on the other side. `ethtool` agrees (`Link detected: no`), and the kernel marks routes through that interface `linkdown`. If the flags had **no** `UP`, the interface itself would be administratively down on this host (`ip link set dev X up` fixes that).
    :::

4. **Root cause and fix.** The other end of the link is down. Bring it up (on real hardware: reseat or replace the cable, enable the switch port, check the switch for errors).

    ```bash
    sudo ip -n router link set veth-rc up
    sudo ip netns exec client ping -c 2 10.10.1.1
    ```

5. **Real systems.** On ubuntu-lab, link changes are logged by systemd-networkd; on Rocky, by NetworkManager. Look at what a healthy link logged at boot:

    ```bash
    journalctl -u systemd-networkd -b | grep -i -E "carrier|link" | tail -n 5
    ```

    ```{.output}
    systemd-networkd[612]: enp0s3: Link UP
    systemd-networkd[612]: enp0s3: Gained carrier
    ```

    A flapping link shows repeated `Lost carrier` / `Gained carrier` pairs, which points to a bad cable, transceiver, or switch port. `ip monitor link` shows the changes live.

6. **Link negotiation (explore/simulate).** Ethernet devices *auto-negotiate* speed and duplex. If one side is forced (for example `100 Mb/s full duplex`) and the other auto-negotiates, the auto side often falls back to **half duplex**. The link is "up" but slow, with collisions and CRC errors. This is a **duplex mismatch**.

    ::: tip
    **Explore/simulate:** Virtual NICs do not negotiate, so you inspect the real NIC, try the change on a veth to see the error a virtual device gives, and read a realistic sample from physical hardware.
    :::

    ```bash
    sudo ethtool $(ip route show default | awk '{print $5; exit}')
    sudo ip netns exec client ethtool -s veth-c speed 100 duplex half autoneg off
    ```

    ```{.output}
    Settings for enp0s3:
            Supported link modes:   10baseT/Half 10baseT/Full
                                    100baseT/Half 100baseT/Full
                                    1000baseT/Full
            Advertised auto-negotiation: Yes
            Speed: 1000Mb/s
            Duplex: Full
            Auto-negotiation: on
            Link detected: yes
    netlink error: Operation not supported
    ```

    ::: explain
    **What just happened:** `$(ip route show default | awk '{print $5; exit}')` finds your main interface name (the fifth word of the default route). `ethtool IF` shows supported modes, speed, duplex, and whether auto-negotiation is on. An emulated e1000 NIC shows values like those above; a virtio NIC may show `Speed: Unknown!`. The veth refuses `ethtool -s` because it has no physical layer. On a physical server with a duplex mismatch you would see something like this:

    ```{.output}
    Speed: 100Mb/s
    Duplex: Half
    Auto-negotiation: on
    ```

    plus rising error counters in `ip -s link show eth0` (`errors`, `collsns`) and `ethtool -S eth0` (`rx_crc_errors`, `tx_late_collisions`). The fix is to set **both** ends the same way, normally auto-negotiation on both: `sudo ethtool -s eth0 autoneg on`. To make it permanent use a systemd `.link` file (`AutoNegotiation=`, `BitsPerSecond=`, `Duplex=`) on Ubuntu or `nmcli connection modify eth0 802-3-ethernet.auto-negotiate yes` on Rocky.
    :::

::: checkpoint
**Checkpoint:** You can explain the difference between `NO-CARRIER` with `UP` (other end or cable) and missing `UP` (admin down here), and you know the symptoms of a duplex mismatch (link up, slow, collisions, CRC errors).
:::

#### Task 3: Scenario 2: "Small requests work, big transfers hang" (MTU mismatch)

The **MTU** (maximum transmission unit) is the largest packet an interface sends, normally 1500 bytes on Ethernet. Both ends of a link must agree. If one side sends 1500-byte packets and the other side (or a device in between) only handles 1400, small packets pass but big ones are dropped.

1. **Break it.** Lower the MTU on the router side of LAN 1, and turn off *segmentation offload* on the client so the virtual cable behaves like a physical one (offload lets virtual devices hand around oversized "super packets", which would hide the problem).

    ```bash
    sudo ip -n router link set veth-rc mtu 1400
    sudo ip netns exec client ethtool -K veth-c tso off gso off
    ```

2. **Symptom.** Ping works and a TCP connection opens, but a 2 MB upload never finishes. Start a listener on the server, then send a file from the client.

    ```bash
    sudo -v
    sudo ip netns exec server timeout 15 nc -l 8000 > /dev/null &
    head -c 2000000 /dev/zero > ~/labs/5.3/big.bin
    sudo ip netns exec client ping -c 1 10.10.2.20 | sed -n 2p
    sudo ip netns exec client timeout 5 nc -N 10.10.2.20 8000 < ~/labs/5.3/big.bin
    echo "exit code: $?"
    ```

    ```{.output}
    64 bytes from 10.10.2.20: icmp_seq=1 ttl=63 time=0.061 ms
    exit code: 124
    ```

    ::: explain
    **What just happened:** `nc -l 8000` listens on TCP port 8000 and `timeout 15` ends it after 15 seconds. On the client, `nc -N` connects, sends the file, and closes the connection at the end. Exit code `124` means `timeout` had to kill it after 5 seconds: the transfer hung. Ping used small 84-byte packets and worked. "Connects, then hangs on big data" (an SSH session that freezes on `ls -l`, a web page that loads halfway) is the classic MTU symptom.
    :::

3. **Investigate.** Compare the MTU on both ends, then probe with pings of exact sizes. `-M do` sets the "don't fragment" flag, and `-s` sets the ICMP payload size. Payload + 8 bytes ICMP header + 20 bytes IP header = packet size, so `-s 1472` makes a 1500-byte packet.

    ```bash
    sudo ip -n client link show veth-c | grep -o 'mtu [0-9]*'
    sudo ip -n router link show veth-rc | grep -o 'mtu [0-9]*'
    sudo ip netns exec client ping -c 1 -W 1 -M do -s 1472 10.10.1.1
    sudo ip netns exec client ping -c 1 -W 1 -M do -s 1372 10.10.1.1
    sudo ip -s -n client link show veth-c | grep -A1 TX
    ```

    ```{.output}
    mtu 1500
    mtu 1400
    PING 10.10.1.1 (10.10.1.1) 1472(1500) bytes of data.
    ping: sendmsg: No buffer space available
    PING 10.10.1.1 (10.10.1.1) 1372(1400) bytes of data.
    1380 bytes from 10.10.1.1: icmp_seq=1 ttl=64 time=0.043 ms
        TX:  bytes packets errors dropped carrier collsns
             10177      78      0       5       0       0
    ```

    ::: explain
    **What just happened:** The two ends disagree (1500 versus 1400). A 1400-byte packet passes, a 1500-byte packet does not, and the `dropped` counter on the client rises. On a veth pair the kernel refuses the oversized packet locally ("No buffer space available"); on a real network it usually just disappears (100% loss with no error). Either way, the largest size that works tells you the real path MTU. `tracepath` also reports the path MTU when routers send back "fragmentation needed" messages.
    :::

4. **Root cause.** MTU mismatch on LAN 1: the client sends 1500-byte frames the other side cannot accept.

5. **Fix.** Make both sides match, then restore offload.

    ```bash
    sudo ip -n router link set veth-rc mtu 1500
    sudo ip netns exec client ethtool -K veth-c tso on gso on
    ```

6. **Verify.** Wait until the first listener has exited (about 15 seconds after you started it), then repeat the `nc -l` and `nc -N` commands from step 2. The transfer now finishes in well under a second with `exit code: 0`.

7. **Prevent.** Set MTU deliberately and the same everywhere on a segment: netplan `mtu: 1500` (or `9000` for jumbo frames on a storage network, only if *every* switch and host supports it), `nmcli connection modify eth0 802-3-ethernet.mtu 9000` on Rocky. Remember that VPNs and tunnels add headers and need a smaller MTU, and never block all ICMP on firewalls: path MTU discovery depends on "fragmentation needed" messages.

::: checkpoint
**Checkpoint:** You found the working packet size with `ping -M do -s`, and the 2 MB transfer completes after the fix.
:::

#### Task 4: Scenario 3: "I can ping the gateway but not the server" (subnet mask)

A **subnet mask** (or prefix length, like `/24`) tells a host which addresses are on its own local network (reach directly with ARP) and which are remote (send to the gateway). A wrong mask makes the host make the wrong choice.

1. **Break it.** Give the client a `/16` mask instead of `/24`.

    ```bash
    sudo ip -n client addr flush dev veth-c
    sudo ip -n client addr add 10.10.1.10/16 dev veth-c
    sudo ip -n client route add default via 10.10.1.1
    ```

    ::: explain
    **What just happened:** `addr flush` removes all addresses from the interface (and with them the routes that used it). You add the address back with the wrong prefix and restore the default route.
    :::

2. **Symptom.**

    ```bash
    sudo ip netns exec client ping -c 1 10.10.1.1 | sed -n 2p
    sudo ip netns exec client ping -c 4 10.10.2.20
    ```

    ```{.output}
    64 bytes from 10.10.1.1: icmp_seq=1 ttl=64 time=0.062 ms
    PING 10.10.2.20 (10.10.2.20) 56(84) bytes of data.
    From 10.10.1.10 icmp_seq=1 Destination Host Unreachable
    From 10.10.1.10 icmp_seq=2 Destination Host Unreachable
    From 10.10.1.10 icmp_seq=3 Destination Host Unreachable
    ```

3. **Investigate.**

    ```bash
    sudo ip -n client -br addr show veth-c
    sudo ip -n client route get 10.10.2.20
    sudo ip -n client neigh
    ipcalc 10.10.1.10/16 | grep -E "Network|HostMin|HostMax"
    ```

    ```{.output}
    veth-c@if5       UP             10.10.1.10/16
    10.10.2.20 dev veth-c src 10.10.1.10 uid 0
        cache
    10.10.2.20 dev veth-c FAILED
    10.10.1.1 dev veth-c lladdr 02:00:00:00:01:01 REACHABLE
    Network:   10.10.0.0/16         00001010.00001010. 00000000.00000000
    HostMin:   10.10.0.1            00001010.00001010. 00000000.00000001
    HostMax:   10.10.255.254        00001010.00001010. 11111111.11111110
    ```

    ::: explain
    **What just happened:** `ip route get` asks the kernel which route it would use for an address. The answer has **no** `via 10.10.1.1`: the client thinks `10.10.2.20` is on its own LAN, because `/16` covers `10.10.0.0` to `10.10.255.255` (as `ipcalc` shows). So it sends ARP requests for `10.10.2.20` directly; nobody on LAN 1 has that address, the neighbor entry stays `INCOMPLETE` while it is trying and becomes `FAILED` when it gives up, and ping reports `Destination Host Unreachable` from the client's own address.
    :::

4. **The opposite mistake.** A mask that is too *small* can put the gateway outside the subnet:

    ```bash
    sudo ip -n client addr flush dev veth-c
    sudo ip -n client addr add 10.10.1.10/29 dev veth-c
    sudo ip -n client route add default via 10.10.1.1
    ```

    ```{.output}
    Error: Nexthop has invalid gateway.
    ```

    ::: explain
    **What just happened:** `/29` covers only `10.10.1.8` to `10.10.1.15`, so the gateway `10.10.1.1` is not on the local network and the kernel refuses the route. In netplan or NetworkManager the same mistake produces a host with no default route ("Network is unreachable" for everything remote).
    :::

5. **Root cause and fix.** Wrong prefix length. Put back the correct `/24`.

    ```bash
    sudo ip -n client addr flush dev veth-c
    sudo ip -n client addr add 10.10.1.10/24 dev veth-c
    sudo ip -n client route add default via 10.10.1.1
    ```

6. **Verify.** `sudo ip netns exec client ping -c 2 10.10.2.20` succeeds and `sudo ip -n client route get 10.10.2.20` shows `via 10.10.1.1`.

7. **Prevent.** Copy the prefix from the network documentation, check new configs with `ip route get <remote>` (it must say `via <gateway>`), and on Ubuntu run `sudo netplan try`, which rolls back automatically after 120 seconds if you lose access.

::: checkpoint
**Checkpoint:** You can explain why `/16` caused `Destination Host Unreachable` and why `/29` caused `Nexthop has invalid gateway`.
:::

#### Task 5: Scenario 4: "Local network works, nothing remote does" (gateway issues)

1. **Break it.** Point the client's default route at an address where no router exists.

    ```bash
    sudo ip -n client route replace default via 10.10.1.254
    ```

2. **Symptom.**

    ```bash
    sudo ip netns exec client ping -c 4 10.10.2.20
    ```

    ```{.output}
    From 10.10.1.10 icmp_seq=1 Destination Host Unreachable
    From 10.10.1.10 icmp_seq=2 Destination Host Unreachable
    ...
    4 packets transmitted, 0 received, +4 errors, 100% packet loss, time 3059ms
    ```

3. **Investigate.**

    ```bash
    sudo ip -n client route show default
    sudo ip -n client neigh
    sudo ip netns exec client ping -c 1 -W 1 10.10.1.254
    ```

    ```{.output}
    default via 10.10.1.254 dev veth-c
    10.10.1.254 dev veth-c FAILED
    10.10.1.1 dev veth-c lladdr 02:00:00:00:01:01 STALE
    1 packets transmitted, 0 received, 100% packet loss, time 0ms
    ```

    ::: explain
    **What just happened:** The default route uses `10.10.1.254`, but ARP for that address never completes (`INCOMPLETE` while trying, then `FAILED`) and it does not answer ping. The real router (`10.10.1.1`) is reachable, which proves the link and subnet are fine. Hypothesis: wrong gateway address.
    :::

4. **Break it a second way: no default route at all.**

    ```bash
    sudo ip -n client route del default
    sudo ip netns exec client ping -c 1 10.10.2.20
    ```

    ```{.output}
    ping: connect: Network is unreachable
    ```

    ::: explain
    **What just happened:** With no route for `10.10.2.20`, the kernel fails immediately with `Network is unreachable` without sending anything. Compare: a *wrong* gateway gives `Destination Host Unreachable` after a few seconds of ARP attempts; a *missing* gateway gives `Network is unreachable` instantly.
    :::

5. **Fix.**

    ```bash
    sudo ip -n client route replace default via 10.10.1.1
    sudo ip netns exec client ping -c 2 10.10.2.20
    ```

    ::: explain
    **What just happened:** `ip route replace` adds the route, or overwrites it if one exists, so it is safe either way. Changes made with `ip` are temporary. On a real Ubuntu server you fix the gateway permanently in netplan (`routes: - to: default via: 192.168.100.1`, then `sudo netplan apply`); on Rocky with `sudo nmcli connection modify eth0 ipv4.gateway 192.168.100.1` and `sudo nmcli connection up eth0`.
    :::

6. **Check your real gateway the same way.**

    ```bash
    ip route show default
    ping -c 2 $(ip route show default | awk '{print $3; exit}')
    ```

::: checkpoint
**Checkpoint:** The client can ping `10.10.2.20` again, and you can tell a wrong gateway (`Destination Host Unreachable`) from a missing one (`Network is unreachable`).
:::

#### Task 6: Scenario 5: "The server is unreachable" (routing beyond the gateway)

When the local side is fine, the problem is further along the path, and you must remember that packets need a route **there and back**.

1. **Break it (part 1).** Turn off forwarding on the router.

    ```bash
    sudo ip netns exec router sysctl -w net.ipv4.ip_forward=0
    ```

2. **Symptom and investigation.** Walk the path hop by hop.

    ```bash
    sudo ip netns exec client ping -c 1 -W 1 10.10.1.1 | sed -n 2p
    sudo ip netns exec client ping -c 1 -W 1 10.10.2.1 | sed -n 2p
    sudo ip netns exec client ping -c 2 -W 1 10.10.2.20 | tail -n 2
    sudo ip netns exec client traceroute -n -w 1 -q 1 -m 4 10.10.2.20
    ```

    ```{.output}
    64 bytes from 10.10.1.1: icmp_seq=1 ttl=64 time=0.104 ms
    64 bytes from 10.10.2.1: icmp_seq=1 ttl=64 time=0.261 ms
    2 packets transmitted, 0 received, 100% packet loss, time 1014ms
    traceroute to 10.10.2.20 (10.10.2.20), 4 hops max, 60 byte packets
     1  *
     2  *
     3  *
     4  *
    ```

    ::: explain
    **What just happened:** The client can ping both router addresses (a host answers for all of its own addresses, even when not forwarding), but nothing beyond. `traceroute` sends probes with increasing TTL (time to live) and lists who answers at each hop; `-n` skips name lookups, `-w 1` waits one second, `-q 1` sends one probe per hop, and `-m 4` stops after 4 hops. Even hop 1 shows `*` because the router drops the packets instead of forwarding them. Check the router:
    :::

    ```bash
    sudo ip netns exec router sysctl net.ipv4.ip_forward
    ```

    ```{.output}
    net.ipv4.ip_forward = 0
    ```

3. **Fix part 1.** Turn forwarding back on. (On a real Linux router, make it permanent with a file such as `/etc/sysctl.d/90-router.conf` containing `net.ipv4.ip_forward = 1`, then `sudo sysctl --system`.)

    ```bash
    sudo ip netns exec router sysctl -w net.ipv4.ip_forward=1
    ```

4. **Break it (part 2).** Remove the server's default route, so it does not know how to send replies back to LAN 1.

    ```bash
    sudo ip -n server route del default
    ```

5. **Symptom and investigation.** The client still gets no replies. Watch the server's interface with `tcpdump` while the client pings.

    ```bash
    sudo -v
    sudo ip netns exec server timeout 4 tcpdump -lni veth-s icmp &
    sleep 1; sudo ip netns exec client ping -c 2 -W 1 10.10.2.20 > /dev/null; wait
    sudo ip netns exec server ip route get 10.10.1.10
    ```

    ```{.output}
    10:13:39.494603 IP 10.10.1.10 > 10.10.2.20: ICMP echo request, id 11946, seq 1, length 64
    10:13:40.515955 IP 10.10.1.10 > 10.10.2.20: ICMP echo request, id 11946, seq 2, length 64
    RTNETLINK answers: Network is unreachable
    ```

    ::: explain
    **What just happened:** `tcpdump -lni veth-s icmp` captures ICMP packets on the server's interface (`-n` no name lookups, `-l` line-buffered output, `-i` interface). Requests **arrive**, but no replies are sent. `ip route get 10.10.1.10` on the server explains why: it has no route back. This one-way pattern ("requests in, no replies out") is the signature of a missing return route or asymmetric routing.
    :::

6. **Fix part 2.**

    ```bash
    sudo ip -n server route add default via 10.10.2.1
    sudo ip netns exec client tracepath -n 10.10.2.20
    ```

7. **Verify.** `tracepath` reaches `10.10.2.20` in 2 hops.

8. **Prevent.** Document routes on every host and router, persist them in netplan/NetworkManager (not just `ip route`), and use `tcpdump` on both ends to prove where packets stop instead of guessing.

::: checkpoint
**Checkpoint:** You saw requests arrive at the server without replies, and fixed both forwarding and the return route. `sudo ip netns exec client ping -c 1 10.10.2.20` succeeds.
:::

#### Task 7: Scenario 6: "The website is down" but it is really DNS

**DNS** turns names into IP addresses. On Ubuntu, programs ask `/etc/resolv.conf`, which points to the local systemd-resolved stub at `127.0.0.53`; systemd-resolved forwards to the real DNS servers. Before DNS, the system checks `/etc/hosts`, because `/etc/nsswitch.conf` says `hosts: files dns`.

1. **Investigate the real VM first** (read-only).

    ```bash
    ls -l /etc/resolv.conf
    grep nameserver /etc/resolv.conf
    resolvectl dns
    resolvectl query ubuntu.com
    grep ^hosts: /etc/nsswitch.conf
    ```

    ```{.output}
    lrwxrwxrwx 1 root root 39 Apr 23 10:02 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
    nameserver 127.0.0.53
    Global:
    Link 2 (enp0s3): 192.168.100.1
    ubuntu.com: 185.125.190.20                     -- link: enp0s3
    hosts:          files dns
    ```

    ::: explain
    **What just happened:** `/etc/resolv.conf` is a symlink to the stub file, so it always says `127.0.0.53`; the *real* upstream servers are shown by `resolvectl dns` (here `192.168.100.1` on `enp0s3`, learned from DHCP or netplan). `resolvectl query` resolves through systemd-resolved and shows which link answered. On Rocky, `/etc/resolv.conf` lists the real servers directly (written by NetworkManager).
    :::

2. **Break it.** In the practice network, run a DNS server for the `lab` domain in the server namespace and point the client at it. `ip netns exec` uses files in `/etc/netns/<name>/` instead of the same files in `/etc`, so the client gets its own `resolv.conf`. Then misconfigure the client's DNS server address.

    ```bash
    sudo -v
    sudo ip netns exec server dnsmasq --no-daemon --no-resolv --no-hosts \
        --listen-address=10.10.2.20 --bind-interfaces \
        --address=/web.lab/10.10.2.20 --log-queries > ~/labs/5.3/dns.log 2>&1 &
    sudo mkdir -p /etc/netns/client
    echo "nameserver 10.10.2.20" | sudo tee /etc/netns/client/resolv.conf
    sudo ip netns exec client getent hosts web.lab
    echo "nameserver 10.10.2.99" | sudo tee /etc/netns/client/resolv.conf
    ```

    ```{.output}
    nameserver 10.10.2.20
    10.10.2.20      web.lab
    nameserver 10.10.2.99
    ```

    ::: explain
    **What just happened:** `dnsmasq` answers DNS queries on `10.10.2.20`; `--address=/web.lab/10.10.2.20` creates a record, `--no-resolv` and `--no-hosts` stop it from reading the host's own files, and `--log-queries` logs every question. The first `getent` proves it works. Then you changed the client to a DNS server address that does not exist, a typical typo.
    :::

3. **Symptom.**

    ```bash
    sudo ip netns exec client ping -c 1 web.lab
    sudo ip netns exec client ping -c 1 10.10.2.20 | sed -n 2p
    ```

    ```{.output}
    ping: web.lab: Temporary failure in name resolution
    64 bytes from 10.10.2.20: icmp_seq=1 ttl=63 time=0.051 ms
    ```

4. **Investigate.** The name fails but the IP works: that alone points to DNS. Now test the configured server and a known-good server directly.

    ```bash
    sudo ip netns exec client cat /etc/resolv.conf
    sudo ip netns exec client dig web.lab | grep -E 'timed out|reached'
    sudo ip netns exec client dig @10.10.2.20 +short web.lab
    ```

    ```{.output}
    nameserver 10.10.2.99
    ;; communications error to 10.10.2.99#53: timed out
    ;; communications error to 10.10.2.99#53: timed out
    ;; communications error to 10.10.2.99#53: timed out
    ;; no servers could be reached
    10.10.2.20
    ```

    ::: explain
    **What just happened:** `dig` sends a DNS query and shows the full answer. With no `@server`, it uses `/etc/resolv.conf`, tries three times, and gives up (after about 15 seconds; be patient). The `grep` keeps just the error lines. `dig @10.10.2.20` asks a specific server, and it answers, so the DNS service is fine and the client's configuration is wrong. On the real Ubuntu VM you would run `dig @192.168.100.1 ubuntu.com` (or another known server) the same way.
    :::

5. **Fix.**

    ```bash
    echo "nameserver 10.10.2.20" | sudo tee /etc/netns/client/resolv.conf
    sudo ip netns exec client ping -c 1 web.lab | head -n 1
    ```

6. **Break it a second way: a stale `/etc/hosts` entry.** Give the client its own hosts file with an old address for `web.lab`.

    ```bash
    { cat /etc/hosts; echo "10.10.2.99 web.lab"; } | sudo tee /etc/netns/client/hosts > /dev/null
    sudo ip netns exec client getent hosts web.lab
    sudo ip netns exec client dig +short web.lab
    sudo ip netns exec client grep -n web.lab /etc/hosts
    ```

    ```{.output}
    10.10.2.99      web.lab
    10.10.2.20
    12:10.10.2.99 web.lab
    ```

    ::: explain
    **What just happened:** `getent hosts` resolves the way applications do (files first, then DNS) and returns the wrong `10.10.2.99`. `dig` only talks DNS and returns the right `10.10.2.20`. `grep -n` shows the stale line at the end of the file (your line number will differ). **When `getent` and `dig` disagree, look in `/etc/hosts`.** This is a very common cause of "it works for me but not on that server".
    :::

7. **Fix and verify.**

    ```bash
    sudo rm /etc/netns/client/hosts
    sudo ip netns exec client getent hosts web.lab
    tail -n 2 ~/labs/5.3/dns.log
    sudo pkill -f '^dnsmasq --no-daemon'
    ```

    ::: tip
    The `^` in the `pkill -f` pattern matters. `-f` matches against the whole command line, and the `sudo pkill -f ...` process has the pattern in its own command line, so without `^` (start of line) pkill can kill its own `sudo` parent. With `^`, only a command line that *starts* with `dnsmasq --no-daemon` matches.
    :::

8. **Prevent.** Configure DNS servers in netplan (`nameservers: addresses: [...]`) or NetworkManager rather than editing `/etc/resolv.conf` by hand (it is regenerated), keep `/etc/hosts` small and documented, and after DNS changes flush caches with `resolvectl flush-caches`.

::: checkpoint
**Checkpoint:** You can name the tool that bypasses `/etc/hosts` (`dig`) and the one that uses it (`getent hosts`), and `web.lab` resolves to `10.10.2.20` in the client namespace.
:::

#### Task 8: Scenario 7: "The connection keeps dropping" (IP conflict)

Two hosts with the same IP address on one network fight over it. Other devices keep updating their ARP table to whichever host spoke last, so traffic goes to one, then the other: intermittent failures that are maddening to debug.

::: warning
Never create an IP conflict on a real network: you can knock someone else's server offline. Here it happens only inside your private namespaces.
:::

1. **Break it.** Plug a new host, `intruder`, into the LAN 1 switch and give it the client's address.

    ```bash
    sudo ip netns add intruder
    sudo ip link add veth-i type veth peer name veth-ri
    sudo ip link set veth-i netns intruder
    sudo ip link set veth-ri netns router
    sudo ip -n router link set veth-ri master br0
    sudo ip -n router link set veth-ri up
    sudo ip -n intruder link set veth-i up
    sudo ip -n intruder addr add 10.10.1.10/24 dev veth-i
    sudo ip netns exec intruder ping -c 1 -W 1 10.10.1.1 > /dev/null
    ```

    ::: explain
    **What just happened:** You built another cable, attached one end to the bridge (`master br0`), and configured `10.10.1.10` on the new host. Its ping to the router makes the router learn the intruder's MAC address for `10.10.1.10`.
    :::

2. **Symptom.** The client, which did nothing wrong, loses connectivity. (If the first try works, wait a few seconds and try again: failing *sometimes* is exactly how IP conflicts behave.)

    ```bash
    sudo ip netns exec client ping -c 3 -W 1 10.10.2.20 | tail -n 2
    ```

    ```{.output}
    3 packets transmitted, 0 received, 100% packet loss, time 2025ms
    ```

3. **Investigate.** Look at the router's ARP (neighbor) table and compare MAC addresses.

    ```bash
    sudo ip -n router neigh show 10.10.1.10
    sudo ip -n client -br link show veth-c
    sudo ip -n intruder -br link show veth-i
    ```

    ```{.output}
    10.10.1.10 dev br0 lladdr fa:cb:e3:f0:00:d2 REACHABLE
    veth-c@if5       UP             0a:00:0c:29:b1:ae <BROADCAST,MULTICAST,UP,LOWER_UP>
    veth-i@if13      UP             fa:cb:e3:f0:00:d2 <BROADCAST,MULTICAST,UP,LOWER_UP>
    ```

    ::: explain
    **What just happened:** The router maps `10.10.1.10` to `fa:cb:...`, which is the intruder's MAC, not the client's. So the router sends the client's replies to the intruder. On a real network you would see the MAC change when you check repeatedly.
    :::

4. **Test the hypothesis** with duplicate address detection: `arping -D` asks "is anyone using this address?" without claiming it.

    ```bash
    sudo ip netns exec client arping -D -I veth-c -c 2 10.10.1.10
    echo "exit code: $?"
    ```

    ```{.output}
    ARPING 10.10.1.10 from 0.0.0.0 veth-c
    Unicast reply from 10.10.1.10 [FA:CB:E3:F0:00:D2]  0.594ms
    Sent 1 probes (1 broadcast(s))
    Received 1 response(s)
    exit code: 1
    ```

    ::: explain
    **What just happened:** `-D` is duplicate address detection mode, `-I` the interface, `-c 2` the probe count. Another MAC answered for "our" address, so there is a conflict (exit code `1`; `0` would mean the address is free). Running this *before* assigning a static address prevents conflicts.
    :::

5. **Watch the flapping live.** Each host announcing itself (a *gratuitous ARP*) steals the address back.

    ```bash
    sudo -v
    sudo ip netns exec router ip monitor neigh &
    sleep 1
    sudo ip netns exec intruder arping -U -I veth-i -c 1 10.10.1.10 > /dev/null
    sudo ip netns exec client arping -U -I veth-c -c 1 10.10.1.10 > /dev/null
    sleep 1; sudo pkill -f '^ip monitor neigh'
    ```

    ```{.output}
    10.10.1.10 dev br0 lladdr fa:cb:e3:f0:00:d2 STALE
    10.10.1.10 dev br0 lladdr 0a:00:0c:29:b1:ae STALE
    ```

6. **Root cause and fix.** Two hosts share one IP. Remove the duplicate (on a real network: find the device by its MAC in the switch's MAC table, then readdress it).

    ```bash
    sudo ip netns del intruder
    sudo ip netns exec client arping -U -I veth-c -c 1 10.10.1.10 > /dev/null
    sudo ip netns exec client ping -c 2 10.10.2.20 | tail -n 2
    ```

    ::: explain
    **What just happened:** Deleting the namespace deletes its veth pair too. The client's gratuitous ARP (`-U`, unsolicited) updates the router immediately instead of waiting for the old entry to expire.
    :::

7. **Prevent.** Use DHCP with reservations instead of hand-picked static addresses, keep an IP address management (IPAM) list, exclude static ranges from DHCP pools, and probe with `arping -D` before assigning an address. NetworkManager can check automatically (`ipv4.dad-timeout`).

::: checkpoint
**Checkpoint:** `arping -D` found the duplicate before the fix, and the client pings the server reliably after it.
:::

#### Task 9: Scenario 8: "The new machine gets no IP address" (DHCP issues)

**DHCP** hands out addresses in four messages: the client broadcasts **Discover**, servers send an **Offer**, the client sends a **Request**, and the server confirms with an **ACK** (remember DORA). If no server answers, many clients give themselves an **APIPA** (automatic private IP addressing) link-local address in `169.254.0.0/16`, which works only with other machines on the same link. Seeing `169.254.x.x` almost always means "DHCP failed".

1. **Look at the real DHCP client first.** On ubuntu-lab, systemd-networkd is the DHCP client (if your VM uses DHCP).

    ```bash
    networkctl status $(ip route show default | awk '{print $5; exit}') | grep -i -E "address|gateway|dhcp"
    journalctl -u systemd-networkd -b | grep -i dhcp | tail -n 3
    ```

    ```{.output}
             Address: 192.168.100.10 (DHCPv4 via 192.168.100.1)
             Gateway: 192.168.100.1
    systemd-networkd[612]: enp0s3: DHCPv4 address 192.168.100.10/24, gateway 192.168.100.1 acquired from 192.168.100.1
    ```

    ::: explain
    **What just happened:** `networkctl status IF` shows where each address came from (`DHCPv4 via` the DHCP server). The journal shows each lease. If your VM uses a static address, these lines are absent; that is fine. On Rocky, use `nmcli device show eth0` and `journalctl -u NetworkManager | grep -i dhcp`.
    :::

2. **Break it.** Plug a new `laptop` namespace into LAN 1 and run a DHCP server on the router with a pool from the **wrong subnet** (`10.10.9.x` instead of `10.10.1.x`), a common copy-paste mistake.

    ```bash
    sudo ip netns add laptop
    sudo ip link add veth-l type veth peer name veth-rl
    sudo ip link set veth-l netns laptop
    sudo ip link set veth-rl netns router
    sudo ip -n router link set veth-rl master br0
    sudo ip -n router link set veth-rl up
    sudo ip -n laptop link set lo up
    sudo ip -n laptop link set veth-l up
    sudo -v
    sudo ip netns exec router dnsmasq --no-daemon --port=0 --interface=br0 --bind-interfaces \
        --dhcp-range=10.10.9.100,10.10.9.150,255.255.255.0,1h \
        --dhcp-option=option:router,10.10.1.1 --dhcp-leasefile=/tmp/labnet-leases \
        > ~/labs/5.3/dhcp.log 2>&1 &
    ```

    ::: explain
    **What just happened:** `--port=0` turns off dnsmasq's DNS function so it is only a DHCP server. `--interface=br0 --bind-interfaces` makes it listen only on LAN 1. `--dhcp-range` is the pool to hand out (start, end, netmask, lease time), `--dhcp-option=option:router` is the gateway given to clients, and `--dhcp-leasefile` is where it records leases.
    :::

3. **Write a tiny DHCP client hook.** BusyBox's `udhcpc` gets the lease, then runs a script to apply it, passing the details in variables.

    ```bash
    cat <<'EOF' > ~/labs/5.3/dhcp-apply.sh
    #!/bin/sh
    # Called by udhcpc. $1 is the event; lease details arrive in variables.
    [ "$1" = "bound" ] || exit 0
    ip addr add "$ip/$mask" dev "$interface"
    [ -n "$router" ] && ip route add default via "$router"
    echo "configured $interface with $ip/$mask, gateway $router"
    EOF
    chmod 755 ~/labs/5.3/dhcp-apply.sh
    ```

4. **Symptom.**

    ```bash
    sudo ip netns exec laptop busybox udhcpc -i veth-l -n -q -f -s ~/labs/5.3/dhcp-apply.sh
    sudo ip -n laptop -br addr show veth-l
    ```

    ```{.output}
    udhcpc: started, v1.36.1
    udhcpc: broadcasting discover
    udhcpc: broadcasting discover
    udhcpc: broadcasting discover
    udhcpc: no lease, failing
    veth-l@if19      UP
    ```

    ::: explain
    **What just happened:** `-i` is the interface, `-n` exits if no lease is obtained, `-q` exits after getting one, `-f` stays in the foreground, and `-s` names the hook script. The client broadcast Discover three times and got no Offer, so the interface has no address.
    :::

5. **Investigate the server side.**

    ```bash
    cat ~/labs/5.3/dhcp.log
    ```

    ```{.output}
    dnsmasq: started, version 2.90 DNS disabled
    dnsmasq-dhcp: DHCP, IP range 10.10.9.100 -- 10.10.9.150, lease time 1h
    dnsmasq-dhcp: DHCP, sockets bound exclusively to interface br0
    dnsmasq-dhcp: no address range available for DHCP request via br0
    dnsmasq-dhcp: no address range available for DHCP request via br0
    ```

    ::: explain
    **What just happened:** The server *did* hear the requests (so the network path and the client are fine), but its pool `10.10.9.x` does not belong to the subnet of the interface the request arrived on (`br0` is `10.10.1.1/24`). A DHCP server only hands out addresses that match the receiving network (or the relay's network). Other common DHCP failures: the server is down, the pool is exhausted (log says `no address available`), a firewall blocks UDP ports 67/68, or a different VLAN has no DHCP relay (`ip helper-address` on the router).
    :::

6. **Fix.** Restart the server with the correct pool.

    ```bash
    sudo pkill -f '^dnsmasq --no-daemon'
    sudo -v
    sudo ip netns exec router dnsmasq --no-daemon --port=0 --interface=br0 --bind-interfaces \
        --dhcp-range=10.10.1.100,10.10.1.150,255.255.255.0,1h \
        --dhcp-option=option:router,10.10.1.1 --dhcp-leasefile=/tmp/labnet-leases \
        > ~/labs/5.3/dhcp.log 2>&1 &
    ```

7. **Verify.**

    ```bash
    sudo ip netns exec laptop busybox udhcpc -i veth-l -n -q -f -s ~/labs/5.3/dhcp-apply.sh
    sudo ip netns exec laptop ping -c 1 10.10.2.20 | sed -n 2p
    grep -E "DHCP(DISCOVER|OFFER|REQUEST|ACK)" ~/labs/5.3/dhcp.log
    cat /tmp/labnet-leases
    ```

    ```{.output}
    udhcpc: started, v1.36.1
    udhcpc: broadcasting discover
    udhcpc: broadcasting select for 10.10.1.138, server 10.10.1.1
    udhcpc: lease of 10.10.1.138 obtained from 10.10.1.1, lease time 3600
    configured veth-l with 10.10.1.138/24, gateway 10.10.1.1
    64 bytes from 10.10.2.20: icmp_seq=1 ttl=63 time=0.304 ms
    dnsmasq-dhcp: DHCPDISCOVER(br0) 42:a4:2b:22:cb:48
    dnsmasq-dhcp: DHCPOFFER(br0) 10.10.1.138 42:a4:2b:22:cb:48
    dnsmasq-dhcp: DHCPREQUEST(br0) 10.10.1.138 42:a4:2b:22:cb:48
    dnsmasq-dhcp: DHCPACK(br0) 10.10.1.138 42:a4:2b:22:cb:48
    1791630729 42:a4:2b:22:cb:48 10.10.1.138 * 01:42:a4:2b:22:cb:48
    ```

    ::: explain
    **What just happened:** You can see all four DORA steps in the log. The lease file records expiry time (in seconds since 1970), MAC, IP, and client ID. dnsmasq waits a few seconds before its first offer while it pings the address to make sure nobody already uses it, which is why the client may broadcast Discover twice.
    :::

8. **Prevent.** Monitor DHCP pool usage, keep static addresses outside the pool, and document relay agents. Stop the DHCP server now:


#### Task 10: Scenario 9: "One cable failed and the server stayed up" (bonding)

**Bonding** (also called teaming or link aggregation) combines several network interfaces into one logical interface, `bond0`. Common modes: `active-backup` (mode 1: one link carries traffic, the other takes over if it fails; works with any switch), `802.3ad` (mode 4, LACP: all links carry traffic; the switch must be configured for LACP), and `balance-rr`, `balance-alb`, and others.

1. **Build it.** Create a `bondhost` namespace with two "NICs" both plugged into the LAN 1 switch, and bond them in active-backup mode.

    ```bash
    sudo ip netns add bondhost
    sudo ip link add eth0b type veth peer name veth-rb0
    sudo ip link add eth1b type veth peer name veth-rb1
    sudo ip link set eth0b netns bondhost
    sudo ip link set eth1b netns bondhost
    sudo ip link set veth-rb0 netns router
    sudo ip link set veth-rb1 netns router
    sudo ip -n router link set veth-rb0 master br0
    sudo ip -n router link set veth-rb1 master br0
    sudo ip -n router link set veth-rb0 up
    sudo ip -n router link set veth-rb1 up
    sudo ip -n bondhost link add bond0 type bond mode active-backup miimon 100
    sudo ip -n bondhost link set eth0b master bond0
    sudo ip -n bondhost link set eth1b master bond0
    sudo ip -n bondhost link set lo up
    sudo ip -n bondhost link set bond0 up
    sudo ip -n bondhost addr add 10.10.1.30/24 dev bond0
    sudo ip -n bondhost route add default via 10.10.1.1
    ```

    ::: explain
    **What just happened:** `type bond mode active-backup miimon 100` creates the bond and checks each member link's carrier every 100 ms (MII monitoring). `master bond0` enslaves each interface; the IP address goes on `bond0`, never on the members. If `ip link add ... type bond` says `Unknown device type`, the `bonding` module could not load: check `modinfo bonding` and `/etc/modprobe.d/` for a blacklist (see Lab 5.2, missing drivers).
    :::

2. **Check its health.** The kernel reports bond status in `/proc/net/bonding/`.

    ```bash
    sudo ip netns exec bondhost cat /proc/net/bonding/bond0
    sudo ip netns exec bondhost ping -c 2 10.10.2.20 | tail -n 2
    ```

    ```{.output}
    Ethernet Channel Bonding Driver: v6.8.0-45-generic

    Bonding Mode: fault-tolerance (active-backup)
    Primary Slave: None
    Currently Active Slave: eth0b
    MII Status: up
    MII Polling Interval (ms): 100

    Slave Interface: eth0b
    MII Status: up
    Speed: 10000 Mbps
    Duplex: full
    Link Failure Count: 0

    Slave Interface: eth1b
    MII Status: up
    Speed: 10000 Mbps
    Duplex: full
    Link Failure Count: 0
    ```

3. **Break it.** Fail the active link by shutting the switch port it is plugged into.

    ```bash
    sudo ip -n router link set veth-rb0 down
    sleep 1
    sudo ip netns exec bondhost grep -E "Currently Active|Slave Interface|MII Status|Link Failure" \
        /proc/net/bonding/bond0
    sudo ip netns exec bondhost ping -c 2 10.10.2.20 | tail -n 2
    ```

    ```{.output}
    Currently Active Slave: eth1b
    MII Status: up
    Slave Interface: eth0b
    MII Status: down
    Link Failure Count: 1
    Slave Interface: eth1b
    MII Status: up
    Link Failure Count: 0
    2 packets transmitted, 2 received, 0% packet loss, time 1001ms
    ```

    ::: explain
    **What just happened:** The bond detected the lost carrier on `eth0b` within 100 ms, switched the active member to `eth1b`, and traffic kept flowing. The bond's overall `MII Status` is still `up`. This is why a degraded bond is dangerous: nothing visibly breaks, so monitor `/proc/net/bonding/*` or `Link Failure Count`, or the second failure takes the server down.
    :::

4. **Fix and verify.** Restore the failed link and confirm both members are up again.

    ```bash
    sudo ip -n router link set veth-rb0 up
    sleep 1
    sudo ip netns exec bondhost grep -A1 "Slave Interface" /proc/net/bonding/bond0
    ```

5. **Common bonding misconfigurations.** In `802.3ad` mode with a switch that is *not* configured for LACP, `/proc/net/bonding/bond0` shows `Partner Mac Address: 00:00:00:00:00:00` and members in different aggregators, and only one link (or none) passes traffic: configure LACP on the switch ports or use `active-backup`. Members plugged into different, unconnected switches cause one-way traffic in load-balancing modes. A permanent Ubuntu bond is defined in netplan; save it as a file under `/etc/netplan/` and run `sudo netplan try`:

    ```yaml
    network:
      version: 2
      ethernets:
        enp0s8: {}
        enp0s9: {}
      bonds:
        bond0:
          interfaces: [enp0s8, enp0s9]
          addresses: [192.168.50.10/24]
          parameters:
            mode: active-backup
            mii-monitor-interval: 100
    ```

    On Rocky: `nmcli connection add type bond ifname bond0 bond.options "mode=active-backup,miimon=100"` plus one `type ethernet ... master bond0` connection per member.

6. **Undo.** `sudo ip netns del bondhost`

::: checkpoint
**Checkpoint:** You saw `Currently Active Slave` change from `eth0b` to `eth1b` with zero ping loss, and `Link Failure Count: 1` recorded the failure.
:::

#### Task 11: Scenario 10: "I changed the MAC address and lost the network" (MAC spoofing)

Every NIC has a burned-in MAC address, but Linux can set any MAC with `ip link set dev IF address XX:...`. **MAC spoofing** is using a MAC address that is not the one assigned. Attackers use it to bypass MAC filters or impersonate devices, so hypervisors and switches often block it: VirtualBox and Hyper-V have a "MAC address spoofing" setting, VMware has "MAC address changes" and "Forged transmits" (set to Reject), libvirt uses network filters, and physical switches use *port security*. With protection on, frames with any other source MAC are dropped.

1. **Break it (part 1: the protection).** Simulate a hypervisor's anti-spoofing rule on the router's switch port: an nftables bridge rule that drops frames from `veth-rc` unless they carry the client's assigned MAC.

    ```bash
    MAC=$(sudo ip -n client -br link show veth-c | awk '{print $3}'); echo "assigned MAC: $MAC"
    sudo ip netns exec router nft -f - <<EOF
    table bridge portsec {
        chain pre {
            type filter hook prerouting priority 0; policy accept;
            iifname "veth-rc" ether saddr != $MAC counter drop
        }
    }
    EOF
    sudo ip netns exec client ping -c 1 10.10.2.20 | sed -n 2p
    ```

    ::: explain
    **What just happened:** The `bridge` family of nftables filters Ethernet frames as they enter the switch (`hook prerouting`). The rule drops any frame arriving on port `veth-rc` whose source MAC is not the assigned one, and counts them. This heredoc has no quotes around `EOF`, so the shell fills in `$MAC`. The client still works because it uses its assigned MAC.
    :::

2. **Break it (part 2: the change).** Inside the "VM", an admin sets a different MAC (perhaps copied from an old server's config).

    ```bash
    sudo ip -n client link set dev veth-c down
    sudo ip -n client link set dev veth-c address 02:11:22:33:44:55
    sudo ip -n client link set dev veth-c up
    sudo ip -n client route add default via 10.10.1.1
    ```

    ::: explain
    **What just happened:** Many NICs only accept a MAC change while down, so you take the interface down, set the address, and bring it up. Bringing it down removed the default route, so you add it back. `02:` at the start marks a *locally administered* address, the correct kind to invent.
    :::

3. **Symptom.**

    ```bash
    sudo ip netns exec client ping -c 2 -W 1 10.10.2.20 | tail -n 2
    ```

    ```{.output}
    2 packets transmitted, 0 received, 100% packet loss, time 1027ms
    ```

4. **Investigate.** Layer 1 is fine (link `UP`, `LOWER_UP`), so check layer 2: compare the current MAC with the assigned one, and look for drops at the "switch".

    ```bash
    sudo ip -n client -br link show veth-c
    echo "assigned: $MAC"
    sudo ip netns exec router nft list table bridge portsec | grep counter
    ```

    ```{.output}
    veth-c@if5       UP             02:11:22:33:44:55 <BROADCAST,MULTICAST,UP,LOWER_UP>
    assigned: 0a:00:0c:29:b1:ae
    iifname "veth-rc" ether saddr != 0a:00:0c:29:b1:ae counter packets 2 bytes 56 drop
    ```

    ::: explain
    **What just happened:** The interface uses a MAC that differs from the one the "hypervisor" assigned, and the drop counter is rising (these first packets are ARP requests, 28 bytes each). On a real VM, compare `ip link` with the MAC shown in the hypervisor's VM settings; on physical NICs, `ip link` shows a `permaddr` field when the MAC was changed from the burned-in one.
    :::

5. **Root cause and fix.** The MAC was changed, and anti-spoofing protection drops the frames. Either restore the assigned MAC (usual fix) or, if the change is legitimate (for example a cluster virtual MAC), allow it in the hypervisor or switch.

    ```bash
    sudo ip -n client link set dev veth-c down
    sudo ip -n client link set dev veth-c address "$MAC"
    sudo ip -n client link set dev veth-c up
    sudo ip -n client route add default via 10.10.1.1
    sudo ip netns exec client ping -c 1 10.10.2.20 | sed -n 2p
    ```

6. **Prevent.** Find where a MAC is set permanently: netplan `macaddress:` under an interface, NetworkManager `ethernet.cloned-mac-address` (`nmcli -f 802-3-ethernet connection show eth0`). Leave spoofing protection **on** for normal VMs and enable it only for workloads that need it (nested virtualization, some clusters and load balancers). Tools such as `arpwatch` alert when a known IP suddenly appears with a new MAC.

7. **Undo.** `sudo ip netns exec router nft delete table bridge portsec`

::: checkpoint
**Checkpoint:** The drop counter showed the spoofed frames, and after restoring the assigned MAC the client reaches the server again.
:::

#### Task 12: Scenario 11: "The web server works locally but not from other hosts" (misconfigured firewall)

Now use your two real VMs. Rocky runs firewalld, which blocks incoming connections except for allowed services.

1. **Break it.** Install and start Apache on rocky-lab, but do not open the firewall (a very common oversight).

    ```bash
    # on rocky-lab
    sudo dnf install -y httpd
    echo "hello from rocky-lab" | sudo tee /var/www/html/index.html
    sudo systemctl enable --now httpd
    ```

2. **Symptom.** From ubuntu-lab:

    ```bash
    curl -v --max-time 5 http://rocky-lab/ 2>&1 | grep -E "Trying|connect|Failed"
    nc -zv -w 3 rocky-lab 80
    ```

    ```{.output}
    *   Trying 192.168.100.20:80...
    * connect to 192.168.100.20 port 80 from 192.168.100.10 port 51514 failed: No route to host
    curl: (7) Failed to connect to rocky-lab port 80 after 3 ms: Couldn't connect to server
    nc: connect to rocky-lab (192.168.100.20) port 80 (tcp) failed: No route to host
    ```

    ::: explain
    **What just happened:** `curl -v` shows each step of the connection. "No route to host" returned within milliseconds is typical of a firewall that **rejects** (sends back an ICMP "administratively prohibited" message), which is firewalld's default. A firewall that silently **drops** would give "Connection timed out" instead. Either way, ping can still work, because firewalld allows ICMP by default.

3. **Investigate on rocky-lab**, bottom up: is the service listening, does it work locally, and what does the firewall allow?

    ```bash
    # on rocky-lab
    sudo ss -tlnp | grep ':80 '
    curl -s http://localhost/
    sudo firewall-cmd --get-active-zones
    sudo firewall-cmd --list-all
    ```

    ```{.output}
    LISTEN 0  511   *:80   *:*   users:(("httpd",pid=2211,fd=4),...)
    hello from rocky-lab
    public
      interfaces: ens18
    public (active)
      target: default
      interfaces: ens18
      services: cockpit dhcpv6-client ssh
      ports:
      ...
    ```

    ::: explain
    **What just happened:** httpd listens on all addresses (`*:80`) and answers locally, so the application is fine. The active zone `public` allows only `cockpit`, `dhcpv6-client`, and `ssh`; `http` is missing. Hypothesis confirmed: the firewall blocks port 80.
    :::

4. **Prove it with firewall logging** (very useful when the rules are complicated).

    ```bash
    # on rocky-lab
    sudo firewall-cmd --set-log-denied=all
    ```

    Run the `curl` from ubuntu-lab again, then on rocky-lab:

    ```bash
    # on rocky-lab
    sudo journalctl -k --since "2 minutes ago" | grep -i reject | tail -n 1
    sudo firewall-cmd --set-log-denied=off
    ```

    ```{.output}
    kernel: filter_IN_public_REJECT: IN=ens18 OUT= MAC=... SRC=192.168.100.10 DST=192.168.100.20 LEN=60 ... PROTO=TCP SPT=51514 DPT=80 WINDOW=64240 SYN URGP=0
    ```

    ::: explain
    **What just happened:** `--set-log-denied=all` makes firewalld log every rejected or dropped packet to the kernel log. The entry shows the zone (`public`), the source, and the destination port (`DPT=80`) of the blocked SYN. Turn logging off afterwards; it is noisy.

5. **Fix.** Allow the service permanently, then reload.


    ::: explain
    **What just happened:** `--permanent` writes the rule to the saved configuration, and `--reload` applies the saved configuration to the running firewall. A rule added **without** `--permanent` works immediately but disappears at the next reload or reboot: a classic "it worked yesterday" firewall problem. (`--runtime-to-permanent` saves current runtime rules.)

6. **Verify.** On ubuntu-lab, `curl http://rocky-lab/` prints `hello from rocky-lab`.

7. **Ubuntu side.** ufw is inactive by default on Ubuntu. If it is active, the same investigation is `sudo ufw status verbose`, the fix is `sudo ufw allow 80/tcp`, and denied packets are logged as `[UFW BLOCK]` in `journalctl -k`. Under both tools, `sudo nft list ruleset` shows the real nftables rules.

Leave httpd running for the next scenario.

#### Task 13: Scenario 12: "SSH to rocky-lab takes several seconds to connect" (dual stack issues)

**Dual stack** means a host runs IPv4 and IPv6 at the same time. Every IPv6 interface has a **link-local** address (`fe80::/10`), usable only on its own link. When a name has both an IPv4 (`A`) and IPv6 (`AAAA`) address, the system chooses an order (address selection rules from RFC 6724, tuned in `/etc/gai.conf`). IPv6 usually wins. If the IPv6 path is broken, programs try IPv6 first, wait, and then fall back to IPv4.

1. **Explore IPv6 between the VMs.** Find rocky-lab's link-local address and ping it from ubuntu-lab. A link-local address needs the outgoing interface after `%`.

    ```bash
    # on rocky-lab
    ip -6 addr show scope link
    ```

    ```{.output}
    2: ens18: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP qlen 1000
        inet6 fe80::7c1e:52ff:fe4a:9b20/64 scope link noprefixroute
    ```

    ```bash
    IF=$(ip route show default | awk '{print $5; exit}'); echo "$IF"
    ping -6 -c 2 fe80::7c1e:52ff:fe4a:9b20%$IF
    ```

    ```{.output}
    PING fe80::7c1e:52ff:fe4a:9b20%enp0s3(fe80::7c1e:52ff:fe4a:9b20%enp0s3) 56 data bytes
    64 bytes from fe80::7c1e:52ff:fe4a:9b20%enp0s3: icmp_seq=1 ttl=64 time=0.402 ms
    ```

    ::: explain
    **What just happened:** Use *your* rocky-lab address from the first command. `%enp0s3` (the **zone index**) tells ping which link to use, because every interface has its own `fe80::` network. IPv6 on the link works.
    :::

2. **Break it.** Give ubuntu-lab a global IPv6 address and add an IPv6 address for `rocky-lab` to `/etc/hosts`, but do **not** configure it on rocky-lab. (This is like a DNS `AAAA` record that points to an address the server does not really have.) `2001:db8::/32` is reserved for documentation and labs.

    ```bash
    sudo cp /etc/hosts /etc/hosts.lab-orig
    sudo ip -6 addr add 2001:db8:100::10/64 dev "$IF"
    echo "2001:db8:100::20 rocky-lab" | sudo tee -a /etc/hosts
    ```

3. **Symptom.**

    ```bash
    time ssh -v -o BatchMode=yes student@rocky-lab true 2>&1 | grep -E "Connecting to|connect to address|Connection established"
    ```

    ```{.output}
    debug1: Connecting to rocky-lab [2001:db8:100::20] port 22.
    debug1: connect to address 2001:db8:100::20 port 22: No route to host
    debug1: Connecting to rocky-lab [192.168.100.20] port 22.
    debug1: Connection established.

    real    0m3.112s
    ```

    ::: explain
    **What just happened:** `ssh -v` prints debug messages, `-o BatchMode=yes` stops it from asking for a password (it will fail authentication, which does not matter here), and `true` is the remote command. SSH tried the IPv6 address first, waited about 3 seconds while IPv6 neighbor discovery failed, then fell back to IPv4. Users just see "SSH is slow". Some programs with short timeouts fail completely instead.
    :::

4. **Investigate.**

    ```bash
    getent ahosts rocky-lab | grep STREAM
    curl -4 -s --max-time 3 http://rocky-lab/; echo "IPv4 exit: $?"
    curl -6 -s --max-time 6 http://rocky-lab/; echo "IPv6 exit: $?"
    ip -6 neigh show 2001:db8:100::20
    ```

    ```{.output}
    2001:db8:100::20 STREAM rocky-lab
    192.168.100.20  STREAM
    hello from rocky-lab
    IPv4 exit: 0
    IPv6 exit: 7
    2001:db8:100::20 dev enp0s3 FAILED
    ```

    ::: explain
    **What just happened:** `getent ahosts` shows every address for a name **in the order programs will try them**: IPv6 first. `curl -4` and `curl -6` force one protocol, which isolates the broken one: IPv4 works, IPv6 fails (exit 7, cannot connect; the longer `--max-time` lets the roughly 3-second neighbor discovery give up first, otherwise you would see exit 28, timeout). `ip -6 neigh` shows IPv6 neighbor discovery (the IPv6 version of ARP) `FAILED` for that address: nobody on the link has it. (`curl` without `-4`/`-6` uses "Happy Eyeballs", trying both almost at once, so browsers and curl hide this problem while SSH shows it.)
    :::

5. **Root cause.** The name has an IPv6 address that the server does not actually answer on: broken dual stack.

6. **Fix option A: make dual stack really work.** Configure the address on rocky-lab. The commands below use `ens18`; replace it with rocky-lab's interface name from step 1.

    ```bash
    # on rocky-lab
    sudo ip -6 addr add 2001:db8:100::20/64 dev ens18
    ```

    Then on ubuntu-lab:

    ```bash
    curl -6 -s http://rocky-lab/
    time ssh -o BatchMode=yes student@rocky-lab true 2>/dev/null
    ```

    ::: explain
    **What just happened:** Now IPv6 works end to end: `curl -6` gets the page and SSH connects instantly. firewalld rules apply to IPv4 and IPv6 alike, so `http` is already allowed. With plain `nftables`/`iptables`, remember IPv6 needs its own rules (`ip6tables`, or the `inet` family in nftables): a classic dual stack mistake is opening a port for IPv4 only.
    :::

7. **Fix option B: prefer IPv4** (a workaround when you cannot fix IPv6 right away). Remove the rocky-lab IPv6 address again, then tell the resolver library to sort IPv4 first. In `/etc/gai.conf`, this line is present but commented out:

    ```bash
    # on rocky-lab
    sudo ip -6 addr del 2001:db8:100::20/64 dev ens18
    ```

    ```bash
    sudo cp /etc/gai.conf /etc/gai.conf.lab-orig
    sudo sed -i 's/^#precedence ::ffff:0:0\/96  100/precedence ::ffff:0:0\/96  100/' /etc/gai.conf
    grep '^precedence' /etc/gai.conf
    getent ahosts rocky-lab | grep STREAM
    ```

    ```{.output}
    precedence ::ffff:0:0/96  100
    192.168.100.20  STREAM rocky-lab
    2001:db8:100::20 STREAM
    ```

    ::: explain
    **What just happened:** `::ffff:0:0/96` is how the address selection table represents all IPv4 addresses; giving it precedence `100` puts IPv4 ahead of IPv6. `getent ahosts` now lists IPv4 first, so SSH connects instantly. This hides the real problem, so treat it as temporary.
    :::

8. **Undo.**

    ```bash
    sudo cp /etc/gai.conf.lab-orig /etc/gai.conf && sudo rm /etc/gai.conf.lab-orig
    sudo cp /etc/hosts.lab-orig /etc/hosts && sudo rm /etc/hosts.lab-orig
    sudo ip -6 addr del 2001:db8:100::10/64 dev "$IF"
    ```

9. **Prevent.** Only publish `AAAA` records for services that really listen on IPv6, test both protocols explicitly (`curl -4`, `curl -6`, `ping -4`, `ping -6`), and keep IPv4 and IPv6 firewall rules in sync.

::: checkpoint
**Checkpoint:** You saw SSH try IPv6 first and fall back after about 3 seconds, used `getent ahosts` to see the order, and isolated the broken protocol with `curl -4` and `curl -6`.

### Exam corner

- Troubleshoot bottom up: link (`ip link`, `ethtool`), MAC/ARP/MTU (`ip neigh`, `arping`), IP/routing (`ip addr`, `ip route`, `ping`, `traceroute`/`tracepath`), ports/firewall (`ss`, `nc`, `firewall-cmd`), then DNS/app (`dig`, `curl`).
- `NO-CARRIER` with `UP` = cable, switch port, or far end down (**link down**). Duplex mismatch (**link negotiation**) = link up but slow with collisions/CRC errors; fix with auto-negotiation on both sides (`ethtool -s IF autoneg on`).
- **MTU mismatch**: small packets work, large transfers hang. Test with `ping -M do -s 1472` (1472 + 28 = 1500).
- Wrong **subnet** mask: too wide makes remote hosts look local (`Destination Host Unreachable`, ARP `INCOMPLETE`); too narrow puts the gateway off-net. `ip route get <ip>` shows the decision.
- **Gateway**: wrong = `Destination Host Unreachable`; missing = `Network is unreachable`. Fix with `ip route replace default via X`, persist in netplan/nmcli.
- **Routing**: packets need a route back. `tcpdump` showing requests with no replies means a missing return route; a Linux router needs `net.ipv4.ip_forward=1`.
- Server **unreachable**: "Connection refused" = nothing listening; "timed out" = dropped (firewall/routing/host down); TCP "No route to host" = often a firewall reject.
- **DNS**: "Temporary failure in name resolution". `dig` bypasses `/etc/hosts`; `getent hosts` follows `nsswitch.conf`. Ubuntu: `resolvectl status`, stub `127.0.0.53`.
- **IP conflict**: intermittent connectivity, ARP entry flapping between MACs; detect with `arping -D -I IF IP` (exit 1 = conflict).
- **DHCP**: DORA (Discover, Offer, Request, ACK), UDP 67/68; `169.254.x.x` (APIPA) means no DHCP server answered. Check server logs and `journalctl -u systemd-networkd` / `NetworkManager`.
- **Bonding**: status in `/proc/net/bonding/bond0`; `active-backup` = mode 1, `802.3ad` (LACP) = mode 4 and needs switch support.
- **MAC spoofing**: `ip link set dev IF address ...`; hypervisors/switches may block non-assigned MACs.
- **Dual stack**: test with `ping -4/-6`, `curl -4/-6`; `getent ahosts` shows the order; `precedence ::ffff:0:0/96 100` in `/etc/gai.conf` prefers IPv4; link-local `fe80::` needs `%interface`.
- **Firewall**: `firewall-cmd --list-all`, `--permanent` + `--reload`, `--set-log-denied=all`; Ubuntu `ufw status verbose`.

**Review questions**

1. A host can ping its gateway but not a server on another subnet. `ip route get <server>` returns a route with no `via`. What is the most likely cause?
    A. DNS failure  B. Subnet mask too wide  C. Link down  D. MTU mismatch
2. Users can SSH to a server, but the session freezes whenever a command produces a lot of output. Which test best confirms the suspected cause?
3. `ip link` shows `<NO-CARRIER,BROADCAST,MULTICAST,UP>` for `eth0`. What does this mean and what should you check?
4. `getent hosts app01` returns `10.0.0.5` but `dig +short app01` returns `10.0.0.50`. Where should you look first?
5. A new workstation shows the address `169.254.33.7`. What failed?
    A. DNS  B. DHCP  C. The default gateway  D. Bonding
6. From a client, `nc -zv web01 443` fails instantly with "No route to host", but `ping web01` works. What is the most likely cause?

::: answers
1. **B.** No `via` means the host thinks the server is on its own subnet, which happens when the mask is too wide (for example `/16` instead of `/24`).
2. `ping -M do -s 1472 <server>` (and smaller sizes): if large packets with "don't fragment" fail while small ones pass, it is an MTU mismatch.
3. The interface is administratively up but has no carrier: the cable, switch port, or other end is down (layer 1). Check cabling, the switch port, and `ethtool eth0` (`Link detected: no`).
4. `/etc/hosts`: `getent` checks local files before DNS, while `dig` queries DNS only, so a stale hosts entry is the likely cause.
5. **B.** A `169.254.0.0/16` (APIPA) address means the client got no answer from a DHCP server.
6. A host firewall on web01 rejecting TCP 443 (for example firewalld without the `https` service); ping works because ICMP is allowed.
:::
