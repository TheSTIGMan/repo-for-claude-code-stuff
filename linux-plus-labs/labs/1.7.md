## Lab 1.7: Run Virtual Machines with QEMU, KVM, and libvirt {#lab-1-7}

::: labinfo
**Objective:** 1.7 Summarize virtualization on Linux systems.\
**Domain:** 1.0 System Management (23% of the exam)\
**Time:** about 120 minutes (longer without hardware acceleration)\
**VM:** ubuntu-lab\
**Snapshot first:** Yes. This lab installs the virtualization stack and creates virtual networks.
:::

ubuntu-lab is itself a virtual machine, and in this lab it becomes a virtualization *host* too: you will run tiny CirrOS virtual machines inside it. Along the way you will inspect, convert, and resize disk images, build a baseline template with linked clones, drive VMs through their states with `virsh`, change their CPU, RAM, storage, and network, take and revert snapshots, clone a VM, practise the steps of a migration, and build a private virtual network. Almost every Linux server today runs on a hypervisor or hosts VMs, so these are core skills, and the exam expects you to know the vocabulary.

### What you'll practice

- Hypervisors: QEMU, KVM
- VMs: paravirtualized drivers, VirtIO; disk image operations (convert, resize, image properties); VM states; nested virtualization
- VM operations: resources (storage, RAM, CPU, network); baseline image templates; cloning; migrations; snapshots
- Bare metal vs. virtual machines
- Network types: bridged, NAT, host-only/isolated, routed, open
- Tools: libvirt, `virsh`, `virt-manager`

### How it works

**Bare metal versus virtual machines.** A *bare metal* server runs one operating system directly on the hardware. A *virtual machine* (VM) is a complete computer made of software: virtual CPUs, RAM, disks, and network cards. A program called a **hypervisor** shares one physical machine between many VMs and keeps them isolated from each other. A *type 1* hypervisor runs directly on the hardware (VMware ESXi, Microsoft Hyper-V, Xen, and Linux with KVM). A *type 2* hypervisor runs as an application on a normal desktop OS (VirtualBox, VMware Workstation). The physical machine is the *host*; each VM is a *guest*.

**The Linux virtualization stack.** Linux splits the job into layers, and the exam expects you to know each name:

```{.diagram}
  virt-manager (GUI)   virsh (CLI)   virt-install / virt-clone
          \                 |                /
           +---------- libvirt API ---------+      management layer
                            |                      (libvirtd daemon, XML configs)
               +------------------------+
               | QEMU process (one/VM)  |          emulates the machine:
               |  VirtIO disk, VirtIO   |          disks, NICs, BIOS, display
               |  net, serial console   |
               +------------------------+
                            |  /dev/kvm
               +------------------------+
               | KVM kernel module      |          runs guest code directly on
               | (kvm_intel / kvm_amd)  |          the CPU with Intel VT-x / AMD-V
               +------------------------+
                      Linux kernel  ->  hardware
```

- **KVM** (Kernel-based Virtual Machine) is a Linux kernel module. It uses the CPU's virtualization extensions (Intel VT-x, flag `vmx`; AMD-V, flag `svm`) so guest code runs on the real CPU at near-native speed.
- **QEMU** is a user-space program that emulates a whole computer: firmware, disk controllers, network cards, display. With KVM it is fast. Without KVM it can still run guests using **TCG** (Tiny Code Generator), which translates every guest instruction in software. TCG always works but is roughly 5 to 20 times slower.
- **libvirt** is a management layer (the `libvirtd` daemon plus an API) that stores each VM's configuration as XML and talks to QEMU for you. **virsh** is its command-line tool, **virt-install** creates VMs, **virt-clone** copies them, and **virt-manager** is the graphical tool.

**Nested virtualization.** Running a hypervisor inside a VM is *nested virtualization*. For KVM to work inside ubuntu-lab, the outer hypervisor (VirtualBox, VMware, Hyper-V, or KVM on your PC) must pass the CPU virtualization extensions through to ubuntu-lab. If it does not, this lab falls back to TCG automatically and everything still works, only slower.

**Paravirtualized drivers and VirtIO.** QEMU can pretend to be real, well-known hardware, such as an Intel e1000 network card or an IDE disk. That is *full emulation*: any OS has drivers for it, but every disk or network operation is translated, which is slow. With *paravirtualization*, the guest knows it is virtual and uses special drivers designed for a hypervisor. On KVM those drivers are **VirtIO**: `virtio-blk`/`virtio-scsi` for disks (they appear as `/dev/vda`), `virtio-net` for networking, `virtio-balloon` for returning memory, and `virtio-rng` for randomness. Linux has VirtIO drivers built in; Windows guests need the `virtio-win` driver ISO.

**Disk images.** A VM's disk is usually a file. A **raw** image is a byte-for-byte disk. **qcow2** (QEMU copy-on-write version 2) is QEMU's native format: it grows as data is written (thin provisioning), supports compression, internal snapshots, and *backing files*. A backing file is the key to templates: you keep one read-only **baseline image** and create small qcow2 *overlay* files on top of it. Each overlay stores only the blocks that VM changes. That is a *linked clone*. A *full clone* is an independent copy of the whole disk.

```{.diagram}
   cirros-base.qcow2  (baseline template, never booted directly)
          ^                 ^
          |  backing file   |
   cirros1.qcow2      (other overlays...)
   (only cirros1's changes)
```

**VM states.** libvirt reports a state for every VM: *running*, *idle* (running but waiting), *paused* (suspended in RAM, CPU stopped), *in shutdown*, *shut off*, *crashed*, and *pmsuspended* (the guest suspended itself to RAM). A *snapshot* records a VM's disk (and optionally memory) at a moment so you can return to it. *Migration* moves a VM to another host: *cold/offline* migration moves a stopped VM, *live* migration moves a running VM with only a brief pause.

**Virtual network types.**

| Type | Guests can reach outside? | Outside can reach guests? | Typical use |
|---|---|---|---|
| NAT | Yes, through the host's IP | No (unless you forward ports) | Default; laptops and labs |
| Bridged | Yes, directly | Yes, guests are on the LAN with their own IPs | Servers that need real LAN addresses |
| Host-only / isolated | No | Only the host and other guests | Test networks, security labs |
| Routed | Yes, routed by the host without NAT | Yes, if the LAN router has a route back | Data centers, public subnets |
| Open | Whatever you configure | Whatever you configure | libvirt adds no firewall rules at all |

### Tasks

#### Task 1: Check for hardware virtualization and nested support

1. Look for the CPU virtualization flags.

    ```bash
    grep -cE 'vmx|svm' /proc/cpuinfo
    lscpu | grep -i virtualization
    ```

    ```{.output}
    2
    Virtualization:                       VT-x
    ```

    ::: explain
    **What just happened:** `/proc/cpuinfo` lists every CPU core with its feature flags. `grep -c` counts the lines that contain `vmx` (Intel VT-x) or `svm` (AMD-V); `-E` allows the `|` ("or"). A number greater than 0 (usually your vCPU count) means the extensions are visible inside ubuntu-lab. `0` means your outer hypervisor is not passing them through. `lscpu` shows the same information in a friendlier form; with no extensions it prints nothing, or shows a `Hypervisor vendor:` line only.
    :::

2. Install `cpu-checker` and ask `kvm-ok` for a verdict.

    ```bash
    sudo apt update
    sudo apt install -y cpu-checker
    sudo kvm-ok
    ```

    With nested virtualization working:

    ```{.output}
    INFO: /dev/kvm exists
    KVM acceleration can be used
    ```

    Without it:

    ```{.output}
    INFO: Your CPU does not support KVM extensions
    KVM acceleration can NOT be used
    ```

    ::: explain
    **What just happened:** `kvm-ok` (an Ubuntu tool from the `cpu-checker` package) checks the CPU flags and whether `/dev/kvm`, the device QEMU uses to talk to the KVM module, exists. Either result is fine for this lab. If KVM is available you will create VMs with `--virt-type kvm`; if not, with `--virt-type qemu` (TCG software emulation).
    :::

3. If you want KVM acceleration and `kvm-ok` said no, shut down ubuntu-lab and enable nested virtualization in the program that runs it, then boot and re-run `sudo kvm-ok`:

    - **VirtualBox:** VM Settings > System > Processor > tick **Enable Nested VT-x/AMD-V**. If it is greyed out, run `VBoxManage modifyvm "ubuntu-lab" --nested-hw-virt on` on your PC while the VM is off.
    - **VMware Workstation / Fusion:** VM Settings > Processors > tick **Virtualize Intel VT-x/EPT or AMD-V/RVI**. (ESXi: "Expose hardware assisted virtualization to the guest OS".)
    - **Hyper-V:** in an elevated PowerShell on the host, with the VM off: `Set-VMProcessor -VMName ubuntu-lab -ExposeVirtualizationExtensions $true`.
    - **KVM/libvirt or Proxmox on Linux:** give the VM the CPU model `host-passthrough` (Proxmox: CPU type `host`), and check `cat /sys/module/kvm_intel/parameters/nested` (or `kvm_amd`) on the physical host shows `Y` or `1`.

    ::: tip
    On Windows PCs with Hyper-V, WSL2, or "Core isolation / Memory integrity" turned on, VirtualBox and VMware run on top of Hyper-V and often cannot offer nested VT-x. You do not need to change your PC: this lab works without KVM, just more slowly.
    :::

4. Save the right virtualization type in a shell variable so later commands work either way.

    ```bash
    if [ -e /dev/kvm ]; then VTYPE=kvm; else VTYPE=qemu; fi
    echo "This lab will use --virt-type $VTYPE"
    ```

    ::: explain
    **What just happened:** `[ -e /dev/kvm ]` tests whether the KVM device file exists. The `if` sets `VTYPE` to `kvm` or `qemu`. Shell variables vanish when you log out, so if you log out later in the lab, run this line again.
    :::

::: checkpoint
**Checkpoint:** You know whether your ubuntu-lab can use KVM (`sudo kvm-ok`), and `echo $VTYPE` prints `kvm` or `qemu`.
:::

#### Task 2: Install QEMU, KVM, and libvirt

1. Install the virtualization stack.

    ```bash
    sudo apt install -y qemu-system-x86 qemu-utils libvirt-daemon-system \
        libvirt-clients virtinst
    ```

    ::: explain
    **What just happened:** `qemu-system-x86` is the QEMU emulator for x86 guests (it also provides the virtual package name `qemu-kvm`, which is what the package is called on Rocky/RHEL). `qemu-utils` provides `qemu-img`, the disk image tool. `libvirt-daemon-system` installs and starts the libvirt daemon and creates the default NAT network. `libvirt-clients` provides `virsh`. `virtinst` provides `virt-install` and `virt-clone`. The KVM kernel modules are already part of Ubuntu's kernel.
    :::

2. Check that the daemon is running and the KVM modules are loaded.

    ```bash
    systemctl status libvirtd --no-pager | head -n 3
    lsmod | grep kvm
    ```

    ```{.output}
    ● libvirtd.service - libvirt legacy monolithic daemon
         Loaded: loaded (/usr/lib/systemd/system/libvirtd.service; enabled; preset: enabled)
         Active: active (running) since Sat 2026-10-10 11:02:13 UTC; 1min ago
    kvm_intel             487424  0
    kvm                  1409024  1 kvm_intel
    ```

    ::: explain
    **What just happened:** `libvirtd` is running. `lsmod` lists loaded kernel modules: `kvm` is the core module and `kvm_intel` (or `kvm_amd`) is the CPU-specific part. If ubuntu-lab has no virtualization extensions, the modules may be missing; that is expected with TCG.
    :::

3. Let `student` manage system VMs, and point `virsh` at the system instance.

    ```bash
    sudo usermod -aG libvirt student
    echo 'export LIBVIRT_DEFAULT_URI=qemu:///system  # lab 1.7' >> ~/.bashrc
    ```

    Log out and log back in (group changes only apply to new logins), then:

    ```bash
    if [ -e /dev/kvm ]; then VTYPE=kvm; else VTYPE=qemu; fi
    id | grep -o libvirt
    echo "$LIBVIRT_DEFAULT_URI"
    virsh list --all
    ```

    ```{.output}
    libvirt
    qemu:///system
     Id   Name   State
    --------------------
    ```

    ::: explain
    **What just happened:** Members of the `libvirt` group may control the system-wide libvirt daemon without `sudo`. libvirt has two *connection URIs*: `qemu:///system` (VMs managed by the system daemon, with access to system networks such as the default NAT network) and `qemu:///session` (per-user VMs with limited networking). A normal user's `virsh` uses `qemu:///session` unless told otherwise, so you set the `LIBVIRT_DEFAULT_URI` environment variable in `~/.bashrc`. (`virsh -c qemu:///system ...` does the same for one command.) The empty table means you have no VMs yet.
    :::

4. Run libvirt's own host check.

    ```bash
    virt-host-validate qemu
    ```

    ```{.output}
      QEMU: Checking for hardware virtualization                 : PASS
      QEMU: Checking if device '/dev/kvm' exists                 : PASS
      QEMU: Checking if device '/dev/kvm' is accessible          : PASS
      QEMU: Checking if device '/dev/vhost-net' exists           : PASS
      ...
    ```

    Without nested virtualization the first lines show `FAIL` or `WARN`; with TCG you can ignore them. Lines about IOMMU or secure guest support are also fine to ignore in this lab.

::: explain
**What just happened:** `virt-host-validate` (from `libvirt-clients`) runs a list of checks a virtualization host should pass: CPU extensions, the `/dev/kvm` device and its permissions, `/dev/vhost-net` (a kernel accelerator for VirtIO networking), cgroup controllers used to limit VM resources, and IOMMU support (needed only for passing physical PCI devices such as GPUs to VMs). It is a handy first step when VMs refuse to start on a new host.
:::

::: checkpoint
**Checkpoint:** `virsh uri` prints `qemu:///system`, and `virsh list --all` runs without `sudo` and without errors.
:::

#### Task 3: Download a cloud image and inspect, convert, and resize it

CirrOS is a tiny Linux distribution (about 20 MB) built for testing clouds. It boots in a few seconds with KVM, needs very little RAM, and comes as a ready-made disk image, so you do not need to run an installer.

1. Download the image into the lab directory.

    ```bash
    mkdir -p ~/labs/1.7 && cd ~/labs/1.7
    wget https://download.cirros-cloud.net/0.6.2/cirros-0.6.2-x86_64-disk.img
    du -h cirros-0.6.2-x86_64-disk.img
    ```

    ```{.output}
    21M     cirros-0.6.2-x86_64-disk.img
    ```

    ::: explain
    **What just happened:** `wget` downloaded the file over HTTPS into the current directory. `du -h` shows how much disk space it uses in human-readable units. The whole operating system fits in about 20 MB.
    :::

2. Look at the image properties with `qemu-img info`.

    ```bash
    qemu-img info cirros-0.6.2-x86_64-disk.img
    ```

    ```{.output}
    image: cirros-0.6.2-x86_64-disk.img
    file format: qcow2
    virtual size: 112 MiB (117440512 bytes)
    disk size: 20.4 MiB
    cluster_size: 65536
    Format specific information:
        compat: 1.1
        compression type: zlib
        lazy refcounts: false
        refcount bits: 16
        corrupt: false
        extended l2: false
    ...
    ```

    ::: explain
    **What just happened:** Even though the file ends in `.img`, `qemu-img` read its header and found it is **qcow2**; never trust the extension. The **virtual size** (112 MiB) is how big the disk looks to the guest. The **disk size** (about 20 MiB) is how much space the file really uses on the host, because qcow2 only stores blocks that contain data. `cluster_size` is qcow2's allocation unit, `compat: 1.1` is the qcow2 version, and `corrupt: false` is a quick health indicator. `qemu-img check FILE` performs a full consistency check. Your exact numbers may differ slightly.
    :::

3. Convert the image from qcow2 to raw, and compare the two.

    ```bash
    qemu-img convert -p -f qcow2 -O raw cirros-0.6.2-x86_64-disk.img cirros.raw
    qemu-img info cirros.raw
    ls -lhs cirros-0.6.2-x86_64-disk.img cirros.raw
    ```

    ```{.output}
        (100.00/100%)
    image: cirros.raw
    file format: raw
    virtual size: 112 MiB (117440512 bytes)
    disk size: 41.2 MiB
    ...
     21M -rw-rw-r-- 1 student student  21M Oct 10 11:08 cirros-0.6.2-x86_64-disk.img
     42M -rw-r--r-- 1 student student 112M Oct 10 11:10 cirros.raw
    ```

    ::: explain
    **What just happened:** `qemu-img convert` copies an image from one format to another: `-f` is the input format, `-O` (capital O) the output format, and `-p` shows progress. The raw file's *apparent* size (112M in the `ls -l` column) equals the virtual size, because raw is a plain byte-for-byte disk. `ls -s` (the first column) shows the blocks really used: `qemu-img` wrote a *sparse* file, skipping the empty areas, so it uses less than 112 MiB, but more than the qcow2 file, which is also compressed. Raw images are simple and slightly faster; qcow2 images add snapshots, backing files, and compression. Other formats `qemu-img` can convert to include `vmdk` (VMware), `vdi` (VirtualBox), and `vhdx` (Hyper-V), which is how you move VMs between hypervisors.
    :::

4. Convert back to qcow2 with compression, then resize a copy.

    ```bash
    qemu-img convert -c -f raw -O qcow2 cirros.raw cirros-compressed.qcow2
    cp cirros-compressed.qcow2 cirros-big.qcow2
    qemu-img resize cirros-big.qcow2 1G
    qemu-img info cirros-big.qcow2 | head -n 4
    ```

    ```{.output}
    Image resized.
    image: cirros-big.qcow2
    file format: qcow2
    virtual size: 1 GiB (1073741824 bytes)
    disk size: 20.6 MiB
    ```

    ::: explain
    **What just happened:** `-c` compresses the qcow2 output. `qemu-img resize` changed the *virtual* size to 1 GiB, but the file stayed small because the new space is empty. Growing the virtual disk is only step one: the guest must also grow its partition and file system (with `growpart` and `resize2fs` or `xfs_growfs`; CirrOS and most cloud images do this automatically at boot). Shrinking needs `--shrink` and destroys data unless the guest's partitions were shrunk first, so always back up before shrinking. Never resize an image that a running VM is using.
    :::

::: checkpoint
**Checkpoint:** `qemu-img info cirros.raw | grep format` prints `file format: raw`, and `qemu-img info cirros-big.qcow2 | grep virtual` shows `1 GiB`.
:::

#### Task 4: Build a baseline template and create a VM with VirtIO devices

1. Install the baseline image into libvirt's image directory, sized to 1 GiB.

    ```bash
    sudo cp ~/labs/1.7/cirros-big.qcow2 /var/lib/libvirt/images/cirros-base.qcow2
    sudo ls -l /var/lib/libvirt/images
    ```

    ::: explain
    **What just happened:** `/var/lib/libvirt/images` is libvirt's standard location for disk images. Using it avoids permission problems: QEMU runs as the user `libvirt-qemu`, which cannot read files inside your home directory (on Ubuntu 24.04, home directories are mode `750`), and the AppArmor profile for VMs expects images here. `cirros-base.qcow2` is now your **baseline image template**. You will never boot it directly; you build VMs on top of it. In production, a template is a fully patched, configured "golden image", cleaned of machine-specific data (SSH host keys, machine ID, logs) with a tool such as `virt-sysprep` from the `libguestfs-tools` package.
    :::

2. Create a linked clone: a small overlay disk that uses the template as its backing file.

    ```bash
    sudo qemu-img create -f qcow2 -F qcow2 \
        -b /var/lib/libvirt/images/cirros-base.qcow2 \
        /var/lib/libvirt/images/cirros1.qcow2
    sudo qemu-img info --backing-chain /var/lib/libvirt/images/cirros1.qcow2 | \
        grep -E '^image|backing file:|disk size'
    ```

    ```{.output}
    Formatting '/var/lib/libvirt/images/cirros1.qcow2', fmt=qcow2 cluster_size=65536 ...
    image: /var/lib/libvirt/images/cirros1.qcow2
    disk size: 196 KiB
    backing file: /var/lib/libvirt/images/cirros-base.qcow2
    image: /var/lib/libvirt/images/cirros-base.qcow2
    disk size: 20.6 MiB
    ```

    ::: explain
    **What just happened:** `qemu-img create -f qcow2` makes a new qcow2 file. `-b` names the backing file, and `-F` states its format (QEMU 8 refuses to guess it, for security). No size was given, so the overlay inherits the template's 1 GiB. The overlay is only 196 KiB: every read of an unchanged block comes from the template, and every write goes into the overlay. Ten VMs built this way cost ten tiny files instead of ten full copies. The catch: the template must never change or move, or every overlay built on it breaks. Use an absolute path for `-b`.
    :::

3. Create the VM with `virt-install`, using VirtIO for both disk and network.

    ```bash
    virt-install \
        --name cirros1 \
        --virt-type "$VTYPE" \
        --memory 256 \
        --vcpus 1 \
        --disk path=/var/lib/libvirt/images/cirros1.qcow2,format=qcow2,bus=virtio \
        --network network=default,model=virtio \
        --osinfo cirros0.5.2 \
        --import \
        --graphics none \
        --noautoconsole
    ```

    ```{.output}
    Starting install...
    Creating domain...
    Domain creation completed.
    ```

    ::: explain
    **What just happened:** `virt-install` wrote a libvirt XML definition and started the VM (libvirt calls a VM a *domain*). `--virt-type` chooses KVM or TCG. `--memory 256` gives 256 MiB of RAM and `--vcpus 1` one virtual CPU. `--disk ...,bus=virtio` attaches your overlay as a paravirtualized VirtIO disk, and `--network network=default,model=virtio` connects a VirtIO network card to libvirt's default NAT network. `--osinfo cirros0.5.2` tells libvirt which OS to tune defaults for (the newest CirrOS entry in Ubuntu 24.04's OS database; `--osinfo detect=on,require=off` would let it guess instead). `--import` means "the disk already has an OS, skip the installer". `--graphics none` gives the VM a serial console instead of a graphical display, and `--noautoconsole` returns your prompt instead of attaching to it.
    :::

4. Connect to the VM's console and log in.

    ```bash
    virsh console cirros1
    ```

    Press Enter if the screen is quiet. With KVM the login prompt appears within seconds; with TCG, boot can take 1 to 3 minutes (CirrOS waits for a cloud metadata service that does not exist, then continues). Log in as `cirros` with password `gocubsgo` (CirrOS prints these on the console).

    ```{.output}
    Connected to domain 'cirros1'
    Escape character is ^] (Ctrl + ])

    login as 'cirros' user. default password: 'gocubsgo'. use 'sudo' for root.
    cirros login: cirros
    Password:
    $
    ```

5. Inside the guest, confirm the VirtIO devices and the network.

    ```bash
    ls /sys/bus/virtio/drivers
    cat /proc/partitions
    ip -4 addr show eth0
    ping -c 2 192.168.122.1
    ```

    ```{.output}
    ...  virtio_blk  ...  virtio_net  ...
    major minor  #blocks  name
     252        0    1048576 vda
     252        1    1035247 vda1
     ...
        inet 192.168.122.57/24 brd 192.168.122.255 scope global eth0
    2 packets transmitted, 2 packets received, 0% packet loss
    ```

    ::: explain
    **What just happened:** You ran these commands *inside the guest*. The `virtio_blk` and `virtio_net` drivers are registered on the VirtIO bus (the exact list of drivers varies), and the disk appears as `vda` (`vd` = VirtIO disk; an emulated SATA disk would be `sda`). The guest grew its root partition to fill the 1 GiB disk at boot. It received a `192.168.122.x` address by DHCP from libvirt's NAT network and can reach the host side, `192.168.122.1`. Your address will differ.
    :::

6. Leave the console with **Ctrl+]** (hold Ctrl and press the closing square bracket). On some non-US keyboards use Ctrl+5. The VM keeps running.

7. Back on ubuntu-lab, look at the VM from the host side.

    ```bash
    virsh list --all
    virsh domifaddr cirros1
    virsh dumpxml cirros1 | grep -E "bus='virtio'|model type="
    ```

    ```{.output}
     Id   Name      State
    -------------------------
     1    cirros1   running
     Name       MAC address          Protocol     Address
    -------------------------------------------------------------------------------
     vnet0      52:54:00:3a:91:c2    ipv4         192.168.122.57/24
          <target dev='vda' bus='virtio'/>
          <model type='virtio'/>
    ```

    ::: explain
    **What just happened:** `virsh list --all` shows running *and* stopped VMs (without `--all`, only running ones). `domifaddr` shows the guest's IP address from the DHCP lease. `dumpxml` prints the full XML definition that libvirt stores in `/etc/libvirt/qemu/cirros1.xml`; the lines you filtered confirm VirtIO for disk and NIC. Edit a definition safely with `virsh edit cirros1`, which validates the XML when you save.
    :::

::: tip
If `virt-install` fails with "Network not found: no network with matching name 'default'" or the network is inactive, run `virsh net-start default` and `virsh net-autostart default`. If starting it fails with "Network is already in use by interface", ubuntu-lab's own network uses `192.168.122.0/24` (common when your PC also runs libvirt). Run `virsh net-edit default`, change every `192.168.122` to `192.168.123`, save, and start the network again.
:::

::: checkpoint
**Checkpoint:** `virsh list --all` shows `cirros1` as `running`, and from ubuntu-lab `ping -c 2` to the address from `virsh domifaddr cirros1` succeeds.

1. Check the current state and details.

    ```bash
    virsh domstate cirros1
    virsh dominfo cirros1
    ```

    ```{.output}

    Id:             1
    Name:           cirros1
    UUID:           6f1d3c2a-...
    OS Type:        hvm
    State:          running
    CPU(s):         1

    Max memory:     262144 KiB
    Used memory:    262144 KiB
    Persistent:     yes
    ```

#### Task 8: Explore virtual network types and build an isolated network

1. List libvirt's networks and read the default NAT network's definition.

    ```bash
    virsh net-list --all
    virsh net-dumpxml default
    ```

    ```{.output}
     Name      State    Autostart   Persistent
    --------------------------------------------
     default   active   yes         yes

    <network>
      <name>default</name>
      <uuid>...</uuid>
      <forward mode='nat'>
    ```

    ::: explain
    **What just happened:** libvirt networks are defined in XML. `<forward mode='nat'>` makes this a **NAT** network: guest traffic leaving the host is rewritten to use the host's own IP address, like a home router, so guests can reach the internet but outside machines cannot start connections to them. `<bridge name='virbr0'>` is a virtual switch on the host that the guests' `vnet` interfaces plug into. The `<ip>` element gives the host the address `192.168.122.1` on that switch, and `<dhcp>` runs a DHCP server (dnsmasq) for guests.


    ```{.output}

    ...masquerade...
    ```

    ::: explain
    **What just happened:** `virbr0` is the bridge with the host's address on the NAT network. libvirt also added firewall rules that *masquerade* guest traffic, which is the NAT. libvirt 10.0 on Ubuntu 24.04 writes these rules with `iptables`, which on Ubuntu is the nftables-based `iptables-nft`, so they also appear in the nftables rule set.     **What just happened:** `net-define` saved a persistent network definition, and `net-start` created the bridge `virbr10` and started DHCP on it. `Autostart: no` means it will not start at boot unless you run `virsh net-autostart isolated-lab`. 5. Learn the other network types by writing (not applying) their configurations.

    ::: tip
    **Explore/simulate:** A **routed** network looks like NAT but with `<forward mode='route'/>`: the host forwards guest traffic without rewriting addresses, so your LAN router needs a route to the guest subnet (for example "10.20.0.0/24 via 192.168.100.10"). An **open** network uses `<forward mode='open'/>`: libvirt creates the bridge and routes, but adds **no** firewall rules at all, leaving filtering entirely to you. 4. Compare bare metal and virtual machines.

    | | Bare metal | Virtual machine |
    |---|---|---|
    | Performance | Full hardware speed, no overhead | Near-native with KVM and VirtIO; slower with emulation |
    | Density | One OS per server | Many VMs per host; better hardware use |

### Exam corner

- **KVM** is the Linux kernel module that uses Intel VT-x (`vmx`) or AMD-V (`svm`) for hardware-accelerated VMs; **QEMU** emulates the machine and devices and can run without KVM using slow software emulation (TCG). Check support with `grep -E 'vmx|svm' /proc/cpuinfo` or `kvm-ok`.
- **libvirt** is the management layer (daemon `libvirtd`, XML definitions in `/etc/libvirt/qemu/`); **virsh** is its CLI, **virt-install** creates VMs, **virt-clone** clones them, **virt-manager** is the GUI.
- **Nested virtualization** means running a hypervisor inside a VM; the outer hypervisor must expose VT-x/AMD-V to the guest.
- **Paravirtualized drivers** (VirtIO: `virtio-blk`, `virtio-net`, `virtio-balloon`) are faster than emulated hardware; VirtIO disks appear as `/dev/vda`.
- `qemu-img info` shows image properties (format, virtual size, disk size, backing file); `qemu-img convert -f qcow2 -O raw` changes format; `qemu-img resize img +10G` grows the virtual disk (then grow the partition and file system in the guest).
- qcow2 supports thin provisioning, compression, internal snapshots, and backing files; a baseline template plus qcow2 overlays (`qemu-img create -b base -F qcow2`) gives linked clones; `virt-clone` makes full clones with a new UUID and MAC.
- VM states: running, idle, paused (`virsh suspend`/`resume`), in shutdown, shut off, crashed, pmsuspended. `virsh shutdown` is graceful, `virsh destroy` is a forced power-off, `virsh undefine` deletes the definition.
- Resources: `virsh setmem`/`setmaxmem`, `virsh setvcpus`, `virsh attach-disk`/`detach-disk`, `virsh attach-interface`; `--config` (persistent), `--live` (running VM), `--persistent` (both, for attach/detach).
- Snapshots: `virsh snapshot-create-as`, `snapshot-list`, `snapshot-revert`, `snapshot-delete`. Snapshots are not backups.
- Migration: cold/offline (stopped VM: copy disk, `dumpxml`/`define`) versus live (`virsh migrate --live VM qemu+ssh://host2/system`, needs shared or copied storage and compatible CPUs).
- Networks: **NAT** (libvirt `default`, `virbr0`, 192.168.122.0/24), **bridged** (guests on the physical LAN), **host-only/isolated** (no `<forward>`), **routed** (`forward mode='route'`, no NAT), **open** (`forward mode='open'`, no firewall rules added).
- Bare metal: best performance and isolation, direct hardware. VMs: density, templates, snapshots, cloning, and migration.

**Review questions**

1. A technician runs `grep -cE 'vmx|svm' /proc/cpuinfo` inside a VM and gets `0`. What does this mean for running KVM guests inside that VM, and how can it be fixed?
2. Which command shows the format, virtual size, actual disk usage, and backing file of a VM disk image?
    - A. `virsh dominfo disk.qcow2`
    - B. `qemu-img info disk.qcow2`
    - C. `qemu-img check disk.qcow2 --format`
    - D. `lsblk disk.qcow2`
3. An administrator wants twenty test VMs that share one read-only baseline image and store only their own changes. Which approach does this?
    - A. `virt-clone` twenty times
    - B. `qemu-img convert` the image twenty times
    - C. Create qcow2 overlay images with `qemu-img create -b base.qcow2 -F qcow2`
    - D. Take twenty snapshots of one VM
4. What is the difference between `virsh shutdown web01` and `virsh destroy web01`?
5. A VM must be reachable from other computers on the office LAN at its own IP address, as if it were a physical server. Which virtual network type should be used?
    - A. NAT
    - B. Isolated
    - C. Bridged
    - D. Host-only
6. Why do VirtIO devices give better disk and network performance than emulated devices such as an IDE disk or e1000 NIC?

::: answers
1. The CPU virtualization extensions are not exposed to the VM, so KVM acceleration is unavailable (guests would run only with slow QEMU TCG emulation); enable nested virtualization in the outer hypervisor (for example VirtualBox "Enable Nested VT-x/AMD-V", VMware "Virtualize Intel VT-x/EPT", or Hyper-V `Set-VMProcessor -ExposeVirtualizationExtensions $true`).
2. **B.** `qemu-img info` reports image properties including file format, virtual size, disk size, and any backing file.
3. **C.** qcow2 overlays with a backing file are linked clones that store only each VM's changed blocks; `virt-clone` makes full copies.
4. `shutdown` asks the guest OS to shut down cleanly via an ACPI event, while `destroy` immediately powers the VM off like pulling the plug; neither deletes the VM.
5. **C.** A bridged network connects the VM directly to the physical LAN so it gets its own LAN address; NAT hides guests behind the host, and isolated/host-only networks do not reach the LAN.
6. VirtIO drivers are paravirtualized: the guest knows it is virtual and exchanges data with the hypervisor through efficient shared-memory queues instead of having QEMU emulate every register access of real hardware.
:::
