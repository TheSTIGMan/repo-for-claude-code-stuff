## Lab 3.3: Operating System Hardening {#lab-3-3}

::: labinfo
**Objective:** 3.3 Given a scenario, apply operating system (OS) hardening techniques on a Linux system.\
**Domain:** 3.0 Security (18% of the exam)\
**Time:** about 180 minutes\
**VM:** ubuntu-lab and rocky-lab (both)\
**Snapshot first:** Yes, on both VMs. This lab edits `sudoers`, `sshd`, PAM, SELinux, and kernel module settings. A mistake can lock you out.
:::

Hardening means closing the doors you are not using and putting good locks on the ones you need. This is the biggest objective in the Security domain, so this lab is long. You will tighten privilege escalation with `sudo`, protect files with attributes and permissions, add fine-grained ACLs, configure SELinux on rocky-lab, lock down SSH, run `fail2ban`, remove insecure services, block unused filesystems, and inspect Secure Boot. Every change here is something a real auditor or benchmark (such as the CIS Benchmarks) will ask you to prove.

### What you'll practice

- Privilege escalation: `sudo`, `/etc/sudoers`, `/etc/sudoers.d`, `visudo`, `NOPASSWD`, `NOEXEC`, `sudo -i`, `su -`, the `wheel` and `sudo` groups
- File attributes: `chattr`, `lsattr` (immutable, append only)
- Permissions: `chown`, `chgrp`, `chmod` (octal and symbolic), special permissions (setuid, setgid, sticky bit), `umask`
- Access control: ACLs (`setfacl`, `getfacl`, default ACLs, mask)
- SELinux: states (enforcing, permissive, disabled), `getenforce`, `setenforce`, `ls -Z`, `restorecon`, `chcon`, `semanage`, `getsebool`, `setsebool`, `audit2allow`, `sealert`
- Secure remote access: SSHD (`PermitRootLogin`, `X11Forwarding`, `AllowUsers`, `AllowGroups`, key vs password auth), `ssh-agent`, `ssh-add`, SSH tunneling, SFTP chroot, `fail2ban`
- Avoiding insecure services (Telnet, FTP, TFTP), disabling unused filesystems, removing unnecessary SUID bits, Secure Boot (UEFI)

### How it works

Hardening works on layers. If one layer fails, the next still protects you.

**Privilege escalation.** Nobody should log in as `root` for daily work. Instead, a trusted user runs a command with `sudo`, which checks `/etc/sudoers` (and drop-in files in `/etc/sudoers.d/`) and logs what happened. You edit sudoers only with `visudo`, which checks the syntax before saving so a typo cannot lock out every administrator. On Ubuntu the admin group is `sudo`; on Rocky it is `wheel`. Important options: `NOPASSWD` lets a rule run without a password (convenient but risky), and `NOEXEC` stops a command from spawning a shell. `sudo -i` starts a root login shell through sudo (logged, uses your password); `su -` switches to another user with a full login shell (needs that user's password).

**File attributes** are set on the filesystem itself, below permissions. `chattr +i` makes a file **immutable**: even root cannot change or delete it until the bit is removed. `chattr +a` makes it **append only**: you can add to it but not rewrite it, which is perfect for log files.

**Permissions.** Every file has an owner, a group, and three permission sets (user, group, other), each with read (4), write (2), execute (1). Octal mode `750` means owner `rwx` (7), group `r-x` (5), other none (0). Three **special** bits sit above them:

- **setuid** (4000) on an executable: it runs as the file's owner, not you. `passwd` is setuid root so you can change your own password in `/etc/shadow`.
- **setgid** (2000) on a directory: new files inside inherit the directory's group, great for shared folders.
- **sticky bit** (1000) on a directory: only a file's owner may delete it, which is why anyone can write in `/tmp` but cannot delete others' files.

`umask` is the mask subtracted from default permissions when a file is created.

**ACLs** (Access Control Lists) go beyond owner/group/other: `setfacl` grants a specific user or group its own permissions on a file. A **default ACL** on a directory is inherited by new files inside it. The **mask** is a ceiling on what named users and groups may get.

**SELinux** (on RHEL/Rocky; Ubuntu uses AppArmor) adds **mandatory access control**: every process and file has a security **context** (label), and a policy decides which process types may touch which file types, regardless of ordinary permissions. Its three states are **enforcing** (block and log), **permissive** (allow but log), and **disabled**. Most SELinux problems are a file with the wrong label; `restorecon` fixes the label back to policy.

**Secure remote access.** SSH keys are far stronger than passwords. You harden the SSH server by turning off password login and root login, limiting who may connect, and disabling features you do not use (like X11 forwarding). `fail2ban` watches logs and temporarily blocks IPs that fail to log in repeatedly.

**Reducing attack surface.** Remove cleartext services (Telnet, FTP, TFTP), block kernel modules for filesystems you never use, strip setuid bits that are not needed, and verify the UEFI **Secure Boot** chain that stops unsigned code from running at boot.

#### Task 1: Controlled sudo with a drop-in file

Take a snapshot now. Keep a second terminal logged in as `student` the whole time you edit sudoers. If sudo breaks, fix it from a root shell you still have, or from the VM console: `pkexec visudo` or boot to recovery.

1. See which group grants admin rights and how, then set up a working directory.

    ```bash
    mkdir -p ~/labs/3.3 && cd ~/labs/3.3
    groups student
    sudo grep -vE '^#|^$' /etc/sudoers | head
    ```

    ```{.output}
    student : student sudo
    Defaults	env_reset
    Defaults	mail_badpass
    Defaults	secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
    %sudo	ALL=(ALL:ALL) ALL
    root	ALL=(ALL:ALL) ALL
    @includedir /etc/sudoers.d
    ```

    ::: explain
    **What just happened:** `student` is in the `sudo` group. The line `%sudo ALL=(ALL:ALL) ALL` reads "members of group `sudo` (`%` means group) may run, on ALL hosts, as (ALL users:ALL groups), ALL commands". `@includedir /etc/sudoers.d` pulls in every file from that directory, which is where you add your own rules without touching the main file. On Rocky the equivalent line is `%wheel ALL=(ALL) ALL`.
    :::

2. Create a limited helpdesk user and a group for it.

    ```bash
    sudo useradd -m -s /bin/bash helpdesk
    sudo passwd helpdesk
    ```

3. Write a sudoers drop-in with `visudo -f` so it is syntax-checked before saving. This lets `helpdesk` restart one service and read logs, nothing else.

    ```bash
    sudo visudo -f /etc/sudoers.d/helpdesk
    ```

    In the editor, type these lines, then save:

    ```text
    # Command alias: the exact commands helpdesk may run
    Cmnd_Alias HELPDESK = /usr/bin/systemctl restart chrony, \
                          /usr/bin/journalctl -u chrony*
    helpdesk ALL=(root) HELPDESK
    ```

    ::: explain
    **What just happened:** `visudo -f FILE` edits that specific file and refuses to save if the syntax is wrong (it would say "What now?" and let you fix it). A `Cmnd_Alias` names a list of allowed commands. The rule `helpdesk ALL=(root) HELPDESK` lets `helpdesk` run exactly those commands as root. Listing full paths matters: if you wrote just `systemctl`, the user could restart any service. The backslash continues a long line.
    :::

4. Test as the helpdesk user.

    ```bash
    su - helpdesk
    sudo -l
    sudo systemctl restart chrony && echo "restarted ok"
    sudo systemctl restart ssh
    ```

    ```{.output}
    User helpdesk may run the following commands on ubuntu-lab:
        (root) /usr/bin/systemctl restart chrony, /usr/bin/journalctl -u chrony*
    restarted ok
    Sorry, user helpdesk is not allowed to execute '/usr/bin/systemctl restart ssh'
    as root on ubuntu-lab.
    ```

    ::: explain
    **What just happened:** `sudo -l` lists what the current user is allowed to run. The allowed `systemctl restart chrony` worked; restarting `ssh` was refused because it is not in the alias. This is **least privilege**: give exactly what the job needs and nothing more. Stay logged in as `helpdesk` for the next step.
    :::

5. See the `NOPASSWD` and `NOEXEC` options and why they matter. Still as `helpdesk`, run:

    ```bash
    exit
    sudo tee /etc/sudoers.d/helpdesk-extra <<'EOF'
    # NOPASSWD: no password needed (convenient, but a stolen session = instant root
    # for these commands). Use only for safe, specific commands.
    helpdesk ALL=(root) NOPASSWD: /usr/bin/systemctl restart chrony
    # NOEXEC: block any attempt by the command to launch another program (a shell).
    helpdesk ALL=(root) NOEXEC: /usr/bin/less /var/log/syslog
    EOF
    sudo visudo -c
    ```

    ```{.output}
    /etc/sudoers: parsed OK
    /etc/sudoers.d/helpdesk: parsed OK
    /etc/sudoers.d/helpdesk-extra: parsed OK
    ```

    ::: explain
    **What just happened:** `visudo -c` checks every sudoers file and reports whether each parses. The first rule adds `NOPASSWD` so the chrony restart needs no password. The second uses `NOEXEC`: `less` (and `vi`, `more`, `man`) can normally launch a shell from inside with `!sh`, which would hand the user a **root shell**, defeating the whole limit. `NOEXEC` uses a library preload to stop the command from executing any other program, so that escape is blocked.
    :::

6. Demonstrate the NOEXEC protection.

    ```bash
    su - helpdesk
    sudo systemctl restart chrony
    sudo less /var/log/syslog
    ```

    Inside `less`, type `!sh` and press Enter. You will see:

    ```{.output}
    Cannot fork: Operation not permitted
    ```

    Press `q` to quit `less`, then `exit` to leave the helpdesk shell.

    ::: explain
    **What just happened:** the chrony restart did not ask for a password (`NOPASSWD`). Inside `less`, the shell-escape `!sh` was blocked by `NOEXEC`: `less` was not allowed to fork a new process. Without `NOEXEC`, you would have landed in a `#` root prompt. This is a classic hardening win and a common exam point.
    :::

7. Compare `sudo -i` and `su -`.

    ```bash
    sudo -i whoami
    sudo -i pwd
    ```

    ```{.output}
    root
    /root
    ```

    ::: explain
    **What just happened:** `sudo -i` starts a root **login** shell (reads root's profile, lands in `/root`) but authenticates with **your** password and is logged by sudo. `su -` (which you have been using) switches users with a full login shell but needs the **target** user's password. `sudo -i` is preferred on servers because root's password can stay unset and every action is attributed to you in the logs. `sudo su -` and `sudo -s` are other variants (`-s` keeps your environment).
    :::

::: checkpoint
**Checkpoint:** `sudo -u helpdesk -l` shows only the chrony and journalctl commands, and the `!sh` escape inside `sudo less` was refused.

#### Task 2: File attributes with chattr and lsattr

1. Protect a config-style file by making it immutable.

    ```bash
    echo "important = yes" > ~/labs/3.3/critical.conf
    sudo chattr +i ~/labs/3.3/critical.conf
    lsattr ~/labs/3.3/critical.conf
    ```

    ```{.output}
    ----i---------e------- /home/student/labs/3.3/critical.conf
    ```

    ::: explain
    **What just happened:** `chattr +i` sets the **immutable** attribute (the `i` in the `lsattr` output). The `e` (extent format) is normal on ext4. Attributes need root, so `chattr` runs under `sudo`.
    :::

2. Try to change or delete it, even as root.

    ```bash
    echo "hacked" | sudo tee -a ~/labs/3.3/critical.conf
    sudo rm -f ~/labs/3.3/critical.conf
    sudo mv ~/labs/3.3/critical.conf /tmp/
    ```

    ```{.output}
    tee: /home/student/labs/3.3/critical.conf: Operation not permitted
    rm: cannot remove '.../critical.conf': Operation not permitted
    mv: cannot move '.../critical.conf': Operation not permitted
    ```

    ::: explain
    **What just happened:** even root cannot write, delete, rename, or link an immutable file. Admins use this on files that must never change, such as `/etc/resolv.conf` on some setups. The downside: you must remember the bit is there, or updates will mysteriously fail.
    :::

3. Remove the immutable bit and set **append only** instead, which suits logs.

    ```bash
    sudo chattr -i ~/labs/3.3/critical.conf
    sudo chattr +a ~/labs/3.3/applog.txt
    echo "line 1 - allowed" | sudo tee -a ~/labs/3.3/applog.txt
    echo "overwrite attempt" | sudo tee ~/labs/3.3/applog.txt
    lsattr ~/labs/3.3/applog.txt
    ```

    ```{.output}
    line 1 - allowed
    tee: /home/student/labs/3.3/applog.txt: Operation not permitted
    -----a--------e------- /home/student/labs/3.3/applog.txt
    ```

    ::: explain
    **What just happened:** `+a` is **append only** (the `a` flag). `tee -a` (append) worked; plain `tee` (which truncates the file first) failed. An attacker who breaks in cannot erase an append-only audit log to hide their tracks. Remove the bit afterward with `sudo chattr -a`.
    :::

::: checkpoint
**Checkpoint:** `lsattr ~/labs/3.3/applog.txt` shows the `a` flag, and appending works while overwriting fails.
:::

#### Task 3: Permissions workshop: ownership, special bits, and umask

1. Build a shared project directory for a team, using a group with setgid and the sticky bit.

    ```bash
    sudo groupadd project
    sudo useradd -m -s /bin/bash -G project alice
    sudo useradd -m -s /bin/bash -G project bob
    sudo mkdir -p /srv/project
    sudo chgrp project /srv/project
    sudo chmod 2770 /srv/project
    ls -ld /srv/project
    ```

    ```{.output}
    drwxrws--- 2 root project 4096 Oct 10 11:10 /srv/project
    ```

    ::: explain
    **What just happened:** `chgrp project` set the directory's group. `chmod 2770` means setgid (`2`) + `rwx` for owner + `rwx` for group + nothing for other. The `s` in `drwxrws---` is the **setgid** bit on the group's execute position. Now any file created inside inherits group `project`, so teammates can read each other's work without fiddling with groups each time.
    :::

2. Prove group inheritance works.

    ```bash
    sudo -u alice bash -c 'umask 0007; echo hi > /srv/project/alice.txt'
    sudo -u bob   bash -c 'umask 0007; echo yo > /srv/project/bob.txt'
    ls -l /srv/project
    ```

    ```{.output}
    -rw-rw---- 1 alice project 3 Oct 10 11:12 alice.txt
    -rw-rw---- 1 bob   project 3 Oct 10 11:12 bob.txt
    ```

    ::: explain
    **What just happened:** both files got group `project` automatically because of the setgid directory, and group members can read and write them (`rw-` for group) thanks to the `0007` umask. Alice and bob can now collaborate.
    :::

3. Add the sticky bit so teammates cannot delete each other's files.

    ```bash
    sudo chmod +t /srv/project
    ls -ld /srv/project
    sudo -u bob rm -f /srv/project/alice.txt
    ```

    ```{.output}
    drwxrws--T 2 root project 4096 Oct 10 11:12 /srv/project
    rm: cannot remove '/srv/project/alice.txt': Operation not permitted
    ```

    ::: explain
    **What just happened:** the trailing `T` is the **sticky bit** (capital `T` because "other" has no execute). With it, only a file's owner (or root) may delete or rename files in the directory, even though the whole group can write there. This is exactly how `/tmp` (mode `1777`) works. `+t` is the symbolic way; `chmod 3770` sets setgid + sticky in octal.
    :::

4. Understand setuid using `passwd`, then practice symbolic vs octal.

    ```bash
    ls -l /usr/bin/passwd
    ls -l /usr/bin/sudo
    chmod u=rwx,g=rx,o=r ~/labs/3.3/critical.conf
    ls -l ~/labs/3.3/critical.conf
    chmod 640 ~/labs/3.3/critical.conf
    ls -l ~/labs/3.3/critical.conf
    ```

    ```{.output}
    -rwsr-xr-x 1 root root 68208 ... /usr/bin/passwd
    -rwsr-xr-x 1 root root 277936 ... /usr/bin/sudo
    -rwxr-xr-- 1 student student 16 ... critical.conf
    -rw-r----- 1 student student 16 ... critical.conf
    ```

    ::: explain
    **What just happened:** the `s` in `-rwsr-xr-x` on `passwd` is **setuid root**: when you run `passwd`, it runs as root so it can edit `/etc/shadow`, even though you are not root. `sudo` is setuid for the same reason. The symbolic form `u=rwx,g=rx,o=r` sets each class explicitly; `chmod 640` is the octal equivalent of `rw-r-----`. Both forms are testable on the exam.
    :::

5. See how `umask` decides default permissions. The math: files start from `666`, directories from `777`, and the umask bits are removed.

    ```bash
    umask
    touch ~/labs/3.3/defaultfile
    mkdir ~/labs/3.3/defaultdir
    ls -ld ~/labs/3.3/defaultfile ~/labs/3.3/defaultdir
    ( umask 077; touch ~/labs/3.3/privatefile; ls -l ~/labs/3.3/privatefile )
    ```

    ```{.output}
    0022
    -rw-r--r-- 1 student student 0 ... defaultfile
    drwxr-xr-x 2 student student ... defaultdir
    -rw------- 1 student student 0 ... privatefile
    ```

    ::: explain
    **What just happened:** with umask `022`, a new file is `666 - 022 = 644` (`rw-r--r--`) and a new directory is `777 - 022 = 755`. In the parentheses (a subshell, so the change is temporary) umask `077` removes all group and other permissions, giving `600` files and `700` directories. Set a user's umask in `~/.bashrc` or system-wide in `/etc/profile` or `/etc/login.defs` (`UMASK`).
    :::

::: checkpoint
**Checkpoint:** `ls -ld /srv/project` shows `drwxrws--T`, new files there get group `project`, and bob cannot delete alice's file.
:::

#### Task 4: Fine-grained permissions with ACLs

1. Grant one extra user access to a file without changing its group.

    ```bash
    echo "team report" > /srv/project/report.txt
    sudo chown alice:project /srv/project/report.txt
    sudo chmod 640 /srv/project/report.txt
    getfacl /srv/project/report.txt
    ```

    ```{.output}
    # file: srv/project/report.txt
    # owner: alice
    # group: project
    user::rw-
    group::r--
    other::---
    ```

    ::: explain
    **What just happened:** `getfacl` shows the ACL. With no extra entries it just mirrors the normal permissions. Right now only alice (owner) and the `project` group can read it.
    :::

2. Give user `bob` read-write and a non-member user read-only, with `setfacl`.

    ```bash
    sudo useradd -m contractor
    sudo setfacl -m u:bob:rw,u:contractor:r /srv/project/report.txt
    getfacl /srv/project/report.txt
    ls -l /srv/project/report.txt
    ```

    ```{.output}
    # file: srv/project/report.txt
    # owner: alice
    # group: project
    user::rw-
    user:bob:rw-
    user:contractor:r--
    group::r--
    mask::rw-
    other::---
    -rw-rw----+ alice project ... report.txt
    ```

    ::: explain
    **What just happened:** `setfacl -m` modifies (adds) ACL entries: `u:bob:rw` and `u:contractor:r`. The `+` after the permissions in `ls -l` signals an ACL is present. A new line, `mask::rw-`, appeared: the **mask** is the maximum any named user or group may have. If the mask were `r--`, bob would be read-only no matter what his entry says. `ls -l` shows the mask in the group position, which is why you check real permissions with `getfacl`.
    :::

3. Set a **default ACL** on a directory so new files inherit it.

    ```bash
    sudo mkdir /srv/project/shared
    sudo setfacl -d -m u:contractor:rwX /srv/project/shared
    getfacl /srv/project/shared | grep default
    sudo -u alice bash -c 'echo new > /srv/project/shared/newfile.txt'
    getfacl /srv/project/shared/newfile.txt | grep contractor
    ```

    ```{.output}
    default:user:contractor:rwx
    default:group::r-x
    default:mask::rwx
    default:other::---
    user:contractor:rw-
    ```

    ::: explain
    **What just happened:** `-d` sets a **default** ACL on the directory; new files and subdirectories automatically get these entries. The `X` (capital) means "execute only if it is a directory or already executable", so data files do not become needlessly executable (the new file got `rw-`, not `rwx`). Remove an ACL with `setfacl -x u:bob FILE`, or wipe all ACLs with `setfacl -b FILE`.
    :::

::: checkpoint
**Checkpoint:** `getfacl /srv/project/report.txt` lists `user:bob:rw-` and `user:contractor:r--`, and files created in `/srv/project/shared` give contractor access automatically.
:::

#### Task 5: SELinux on rocky-lab

SELinux is RHEL's mandatory access control. Ubuntu uses AppArmor, so this task is on rocky-lab.

1. Check the state and config.

    ```bash
    # on rocky-lab
    getenforce
    sestatus | head -5
    cat /etc/selinux/config | grep -vE '^#|^$'
    ```

    ```{.output}
    Enforcing
    SELinux status:                 enabled
    SELinuxfs mount:                /sys/fs/selinux
    SELinux root directory:         /etc/selinux
    Loaded policy name:             targeted
    SELINUX=enforcing
    SELINUXTYPE=targeted
    ```

    ::: explain
    **What just happened:** `getenforce` prints the current mode. The three states are **enforcing** (deny and log violations), **permissive** (allow but log, great for troubleshooting), and **disabled** (off entirely, not recommended). `/etc/selinux/config` sets the mode at boot via `SELINUX=`. Changing it to `disabled` and rebooting fully turns SELinux off; switching between enforcing and permissive does not need a reboot.
    :::

2. Switch modes at runtime (no reboot) and back.

    ```bash
    # on rocky-lab
    sudo setenforce 0
    getenforce
    sudo setenforce 1
    getenforce
    ```

    ```{.output}
    Permissive
    Enforcing
    ```

    ::: explain
    **What just happened:** `setenforce 0` = permissive, `setenforce 1` = enforcing. This is temporary and ignored at reboot. Use permissive to see whether SELinux is the cause of a problem without turning it off permanently: if the problem continues in permissive mode, SELinux is not to blame.
    :::

3. Look at security contexts.

    ```bash
    # on rocky-lab
    ls -Z /etc/passwd
    ps -Zp 1
    id -Z
    ```

    ```{.output}
    system_u:object_r:passwd_file_t:s0 /etc/passwd
    system_u:system_r:init_t:s0 ... /usr/lib/systemd/systemd
    unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
    ```

    ::: explain
    **What just happened:** `-Z` shows the SELinux context, written `user:role:type:level`. The **type** is what matters most in the targeted policy: files have types like `passwd_file_t`, processes run in **domains** like `init_t`. The policy says, for example, that only certain domains may write `passwd_file_t`. Your login shell is `unconfined_t`, meaning the policy does not restrict it.
    :::

4. Install a web server and trigger a classic "wrong context" denial.

    ```bash
    # on rocky-lab
    sudo dnf install -y httpd setroubleshoot-server policycoreutils-python-utils
    sudo systemctl enable --now httpd
    sudo firewall-cmd --add-service=http
    echo "Default web root" | sudo tee /var/www/html/index.html
    echo "from home dir" > ~/mypage.html
    sudo mv ~/mypage.html /var/www/html/mypage.html
    curl -s http://localhost/mypage.html | head -1
    ```

    ```{.output}
    <!DOCTYPE HTML PUBLIC ...>
    ... 403 Forbidden ...
    ```

    ::: explain
    **What just happened:** the page from the default root works, but `mypage.html` gives **403 Forbidden**. The file came from your home directory, so it kept the context `user_home_t`. Apache (domain `httpd_t`) is only allowed to read `httpd_sys_content_t`, so SELinux blocked it, even though the Unix permissions are fine. This is the single most common SELinux surprise.
    :::

5. Diagnose with the audit log and `sealert`, then fix with `restorecon`.

    ```bash
    # on rocky-lab
    ls -Z /var/www/html/
    sudo ausearch -m avc -ts recent 2>/dev/null | tail -4
    sudo sealert -a /var/log/audit/audit.log 2>/dev/null | grep -A3 'mypage' | head
    sudo restorecon -v /var/www/html/mypage.html
    curl -s http://localhost/mypage.html
    ```

    ```{.output}
    unconfined_u:object_r:user_home_t:s0 mypage.html
    unconfined_u:object_r:httpd_sys_content_t:s0 index.html
    type=AVC ... avc:  denied  { read } ... comm="httpd"
      name="mypage.html" ... tcontext=...:user_home_t ...
    Changing SELinux context ...user_home_t:s0->...httpd_sys_content_t:s0
    from home dir
    ```

    ::: explain
    **What just happened:** `ls -Z` shows the bad file is `user_home_t` while its neighbor is `httpd_sys_content_t`. An **AVC** (Access Vector Cache) denial in the audit log records exactly what was blocked. `sealert` turns raw AVCs into plain-English advice (it is part of `setroubleshoot-server`). `restorecon` resets the file's context to what the policy says that path should be, and the page now loads. `restorecon -Rv /path` fixes a whole tree.
    :::

6. Serve content from a non-standard directory using `semanage fcontext` (the permanent way) and `chcon` (the temporary way).

    ```bash
    # on rocky-lab
    sudo mkdir -p /webdata
    echo "custom location" | sudo tee /webdata/index.html
    sudo chcon -t httpd_sys_content_t /webdata/index.html
    ls -Z /webdata/index.html
    sudo semanage fcontext -a -t httpd_sys_content_t '/webdata(/.*)?'
    sudo restorecon -Rv /webdata
    ```

    ::: explain
    **What just happened:** `chcon -t` changes a context right now, but it is **temporary**: a filesystem relabel or `restorecon` would revert it, because `chcon` does not update the policy's rules. `semanage fcontext -a` **adds a rule** that says "anything matching `/webdata(/.*)?` should be `httpd_sys_content_t`", and `restorecon` then applies it. The `semanage` way survives relabels and is what you use in production. (You would also point Apache at `/webdata` with a config change to actually serve it.)
    :::

#### Task 6: Secure SSH with keys and a hardened config

1. On ubuntu-lab, generate an ed25519 key pair and copy the public key to rocky-lab.

    ```bash
    ssh-keygen -t ed25519 -C "student@ubuntu-lab lab3.3" -f ~/.ssh/id_ed25519 -N ""
    ssh-copy-id -i ~/.ssh/id_ed25519.pub student@rocky-lab
    ssh student@rocky-lab hostname
    ```

    ```{.output}
    Your identification has been saved in /home/student/.ssh/id_ed25519
    Number of key(s) added: 1
    rocky-lab
    ```

    ::: explain
    **What just happened:** `ssh-keygen -t ed25519` makes a modern, small, strong key pair. `-f` sets the file name, `-N ""` makes an empty passphrase (for the lab; in real life use a passphrase). `ssh-copy-id` appends the **public** key to `~/.ssh/authorized_keys` on rocky-lab, so from now on you log in with the key instead of a password. The private key never leaves ubuntu-lab.
    :::

2. Use `ssh-agent` and `ssh-add` so a passphrase is typed only once per session. (The effect is clearer with a passphrase, but the commands are the same.)

    ```bash
    eval "$(ssh-agent -s)"
    ssh-add ~/.ssh/id_ed25519
    ssh-add -l
    ssh student@rocky-lab uptime
    ```

    ```{.output}
    Agent pid 5123
    Identity added: /home/student/.ssh/id_ed25519 (student@ubuntu-lab lab3.3)
    256 SHA256:abc... student@ubuntu-lab lab3.3 (ED25519)
    ```

    ::: explain
    **What just happened:** `ssh-agent` is a background process that holds your unlocked private keys in memory. `eval "$(ssh-agent -s)"` starts it and sets the environment variables that let `ssh` find it. `ssh-add` loads a key into the agent (asking for the passphrase once); `ssh-add -l` lists loaded keys. With an agent, you authenticate many times without retyping the passphrase, and agent forwarding (`ssh -A`) can carry it to further hops.
    :::

3. Harden the SSH **server** on rocky-lab with a drop-in file.

    ::: warning
    This changes how you log in to rocky-lab. Keep your current rocky-lab SSH session open, and confirm key login works (step 1) before you turn off passwords. If you get locked out, fix the file from the VM console. Snapshot first.
    :::

    ```bash
    # on rocky-lab
    sudo groupadd sshusers
    sudo usermod -aG sshusers student
    sudo tee /etc/ssh/sshd_config.d/50-hardening.conf <<'EOF'
    PermitRootLogin no
    PasswordAuthentication no
    KbdInteractiveAuthentication no
    X11Forwarding no
    AllowGroups sshusers
    EOF
    sudo sshd -t && echo "config OK"
    ```

    ::: explain
    **What just happened:** files in `/etc/ssh/sshd_config.d/` are included by the main config and override it; using a drop-in keeps your changes separate. The settings: **`PermitRootLogin no`** stops direct root login (attackers must first get a user account); **`PasswordAuthentication no`** forces key login, defeating password guessing; **`X11Forwarding no`** disables forwarding graphical apps (an attack surface you rarely need on a server); **`AllowGroups sshusers`** lets only members of that group connect (`AllowUsers student@192.168.100.0/24` would limit by user and source). `sshd -t` tests the config; never restart until it says OK.
    :::

4. Apply and test from a **new** terminal while the old one stays open.

    ```bash

    ```


    ```{.output}

    student@rocky-lab: Permission denied (publickey).
    ```

    ::: explain
    **What just happened:** `reload` re-reads the config without dropping existing connections (safer than `restart`). Key login still works; forcing password-only authentication is now refused, proving passwords are off. Only after you confirm this should you trust the lockdown.
    :::

5. Create an SSH **tunnel** (local port forwarding). Apache on rocky-lab serves port 80; you will reach it from ubuntu-lab as `localhost:8080`.

    **What just happened:** `-L 8080:localhost:80` means "listen on **my** port 8080 and forward through the SSH connection to `localhost:80` **as seen from rocky-lab**". #### Task 7: An SFTP-only chroot group

Give file-transfer users SFTP access locked into their own directory, with no shell and no view of the rest of the system.

1. On rocky-lab, create the group, user, and a correctly owned chroot directory.

    ```bash
    # on rocky-lab
    sudo groupadd sftponly
    sudo useradd -g sftponly -s /sbin/nologin -d /home/sftproot/upload sftpuser
    sudo passwd sftpuser
    sudo mkdir -p /home/sftproot/upload
    sudo chown root:root /home/sftproot
    sudo chmod 755 /home/sftproot
    sudo chown sftpuser:sftponly /home/sftproot/upload
    ```

    ::: explain
    **What just happened:** `-s /sbin/nologin` means no interactive shell. The **chroot** directory (`/home/sftproot`) and every directory above it **must be owned by root and not writable by others**, or sshd refuses the chroot for security. The writable `upload` subdirectory inside is where the user actually puts files.
    :::

2. Add an SSH server rule that chroots this group to the internal SFTP server.

    ```bash
    # on rocky-lab
    sudo usermod -aG sshusers sftpuser
    sudo tee /etc/ssh/sshd_config.d/60-sftp.conf <<'EOF'
    Match Group sftponly
        ChrootDirectory /home/sftproot
        ForceCommand internal-sftp
        AllowTcpForwarding no
        X11Forwarding no
    EOF
    sudo sshd -t && sudo systemctl reload sshd
    ```

    ::: explain
    **What just happened:** a `Match` block applies settings only to connections that match (here, group `sftponly`). `ChrootDirectory` jails them so `/` looks like `/home/sftproot`. `ForceCommand internal-sftp` runs SSH's built-in SFTP server instead of a shell, so these users can only transfer files. We re-added sftpuser to `sshusers` because the Task 6 `AllowGroups` rule would otherwise block them.
    :::

3. Test from ubuntu-lab: SFTP works and is jailed, but shell login is refused.

    ```bash
    sftp sftpuser@rocky-lab
    ```

    At the `sftp>` prompt type `pwd`, then `ls`, then `put ~/.ssh/id_ed25519.pub test.pub`, then `exit`.

    ```{.output}
    sftp> pwd
    Remote working directory: /upload
    sftp> put ~/.ssh/id_ed25519.pub test.pub
    Uploading ... to /upload/test.pub
    ```

    ```bash
    ssh sftpuser@rocky-lab
    ```

    ```{.output}
    This service allows sftp connections only.
    Connection to rocky-lab closed.
    ```

    ::: explain
    **What just happened:** inside SFTP, the working directory shows as `/upload`, not the real path, proving the chroot jail works. A normal `ssh` login is refused because `internal-sftp` replaces the shell. This is the standard way to hand someone a drop-box without giving them the server.
    :::

#### Task 9: Remove insecure services and reduce attack surface

1. Confirm no cleartext services are listening, and check for their packages.

    ```bash
    ss -tulpn | grep -E ':23 |:21 |:69 ' || echo "no telnet/ftp/tftp listening"
    dpkg -l | grep -E 'telnetd|vsftpd|tftpd|inetutils-telnetd' || echo "none installed"
    ```

    ```{.output}
    no telnet/ftp/tftp listening
    none installed
    ```

    ::: explain
    **What just happened:** `ss -tulpn` lists listening TCP (`t`) and UDP (`u`) sockets with ports (`n`) and the owning program (`p`). Ports 23 (Telnet), 21 (FTP), and 69 (TFTP) send credentials and data in **cleartext**, so a hardened host must not run them. SSH (22) replaces Telnet, and SFTP/SCP replace FTP. If any were installed you would remove them: `sudo apt purge telnetd vsftpd tftpd-hpa`.
    :::

    ::: tip
    **Explore/simulate:** to see why Telnet is unsafe without exposing a real service, you can watch traffic on the loopback. In one terminal run `sudo tcpdump -i lo -A port 2323` and in another `nc -l 2323` plus a client `nc localhost 2323`; whatever you type appears in `tcpdump` as plain readable text. The same capture on an SSH session shows only encrypted bytes. This is the core reason to avoid Telnet/FTP/TFTP.
    :::

2. Disable unused file system kernel modules so they cannot be loaded (a CIS Benchmark item).

    ```bash
    sudo tee /etc/modprobe.d/lab-hardening.conf <<'EOF'
    install cramfs /bin/false
    install freevxfs /bin/false
    install udf /bin/false
    blacklist cramfs
    blacklist freevxfs
    EOF
    sudo modprobe -n -v cramfs
    sudo modprobe cramfs; echo "exit=$?"
    lsmod | grep cramfs || echo "cramfs not loaded"
    ```

    ```{.output}
    install /bin/false
    modprobe: ERROR: could not insert 'cramfs': ...
    exit=1
    cramfs not loaded
    ```

    ::: explain
    **What just happened:** `install cramfs /bin/false` tells modprobe to run `/bin/false` (which does nothing and returns failure) instead of loading the module, so an attacker cannot mount an exotic filesystem to smuggle in a setuid binary. `blacklist` stops automatic loading. `modprobe -n -v` shows what **would** happen (a dry run); the real `modprobe` then fails with exit code 1. These are filesystems a normal server never needs. (On an already-loaded module you would also `rmmod` it.)
    :::

3. Find setuid binaries and remove an unnecessary one from a **copy** (never strip the real `passwd` or `sudo`).

    ```bash
    sudo find /usr/bin /usr/sbin -perm -4000 -type f 2>/dev/null | head
    cp /bin/ping ~/labs/3.3/myping
    sudo chown root:root ~/labs/3.3/myping

    ls -l ~/labs/3.3/myping
    ```

    ```{.output}
    /usr/bin/sudo
    /usr/bin/passwd
    /usr/bin/chsh

    ...
    -rwsr-xr-x 1 root root ... myping
    -rwxr-xr-x 1 root root ... myping
    ```

    ::: explain
    **What just happened:** `find -perm -4000` finds files with the setuid bit set (`-perm -4000` means "at least these bits"). Every setuid-root program is a potential path to full control if it has a bug, so you audit the list and remove the bit from anything that does not need it. `chmod 4755` added setuid to the copy (the `s` appears); `chmod u-s` removed it. In the real world you compare this list against a baseline and investigate anything new. `-perm -2000` finds setgid files.
    :::

4. Explore Secure Boot. VMs are often BIOS, so this is an explore/simulate step.

    ```bash
    mokutil --sb-state 2>/dev/null || echo "mokutil not present or not UEFI"
    [ -d /sys/firmware/efi ] && echo "booted in UEFI mode" \
      || echo "booted in BIOS/legacy mode"
    ```

    ```{.output}
    mokutil: This system doesn't support Secure Boot
    booted in BIOS/legacy mode
    ```

    ::: tip
    **Explore/simulate:** **Secure Boot** is a UEFI feature that only lets **signed** boot code run, so malware cannot replace your bootloader or kernel (a "bootkit"). The chain is: UEFI firmware verifies **shim** (signed by Microsoft), shim verifies **GRUB**, GRUB verifies the **signed kernel**, and the kernel only loads signed modules. The presence of `/sys/firmware/efi` means the machine booted via UEFI (needed for Secure Boot); your lab VM is likely BIOS, so `mokutil --sb-state` reports it is unsupported. On real hardware that command prints `SecureBoot enabled` or `disabled`, and `mokutil --list-enrolled` shows the trusted keys. You enroll your own keys with `mokutil --import` when signing custom modules.

### Exam corner

- Edit sudoers only with `visudo`; drop-ins go in `/etc/sudoers.d/`; `visudo -c` checks syntax, `sudo -l` lists a user's rights.
- `NOPASSWD` runs without a password (convenience vs risk); `NOEXEC` blocks shell escapes from commands like `less`/`vi`. Admin group: `sudo` on Ubuntu, `wheel` on Rocky.
- `sudo -i` = root login shell via your password (logged); `su -` = switch user with a login shell via the target's password.
- `chattr +i` immutable (even root cannot change/delete), `chattr +a` append only; view with `lsattr`.
- Permissions: octal `4000` setuid, `2000` setgid, `1000` sticky; `chmod 2770`, `chmod +t`, symbolic `u=rwx,g=rx,o=`. setuid on files, setgid+sticky mainly on directories.
- `umask`: files `666 - umask`, directories `777 - umask`; `022` gives 644/755.
- ACLs: `setfacl -m u:name:rw file`, `-d` default ACL on a directory, `-x` remove, `-b` wipe; `getfacl` to view; the **mask** caps named entries; `+` in `ls -l` means an ACL exists.
- SELinux states: enforcing, permissive, disabled (`getenforce`, `setenforce 0/1`, `/etc/selinux/config`). Context = `user:role:type:level`; view with `ls -Z`, `ps -Z`.
- Fix SELinux labels with `restorecon` (applies policy) or `chcon` (temporary); add path rules with `semanage fcontext -a` then `restorecon`; ports with `semanage port -a`; switches with `setsebool -P`; diagnose with `ausearch -m avc`, `sealert`, and `audit2allow`.
- SSH hardening (`sshd_config` / `sshd_config.d/`): `PermitRootLogin no`, `PasswordAuthentication no`, `X11Forwarding no`, `AllowUsers`/`AllowGroups`; always `sshd -t` before reload. Keys: `ssh-keygen`, `ssh-copy-id`, `ssh-agent`+`ssh-add`. Tunnels: `-L` local, `-R` remote, `-D` SOCKS.
- SFTP chroot: `Match Group`, `ChrootDirectory` (owned by root, not writable), `ForceCommand internal-sftp`.
- `fail2ban`: jails in `jail.d/*.local`, `fail2ban-client status <jail>`, `set <jail> unbanip <ip>`.
- Avoid cleartext Telnet (23), FTP (21), TFTP (69); check with `ss -tulpn`. Block filesystems in `/etc/modprobe.d/` with `install <fs> /bin/false` + `blacklist`. Remove unneeded SUID with `chmod u-s` (find with `find / -perm -4000`). Secure Boot: UEFI-only, checked with `mokutil --sb-state`.
