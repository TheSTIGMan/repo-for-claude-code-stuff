## Lab 3.3: Apply OS Hardening Techniques {#lab-3-3}

::: labinfo
**Objective:** 3.3 Given a scenario, apply operating system (OS) hardening techniques on a Linux system.\
**Domain:** 3.0 Security (18% of the exam)\
**Time:** about 180 minutes (split it over two sittings if you like)\
**VM:** ubuntu-lab and rocky-lab (both)\
**Snapshot first:** Yes, on **both** VMs. This lab edits sudoers, SSH server settings, SELinux, and kernel module rules.

Hardening means reducing what can go wrong: fewer privileges, fewer open doors, tighter defaults. In this lab you will lock down sudo, file permissions, ACLs, SELinux, and SSH, then remove insecure services and unused kernel features. Most security incidents start with a weak default someone forgot to change, so this is one of the most practical labs in the book and one of the heaviest objectives on the exam.

### What you'll practice

- Privilege escalation controls: **sudo**, **/etc/sudoers** (**NOEXEC**, **NOPASSWD** implications), **/etc/sudoers.d**, **visudo**, **sudo -i**, **wheel** group, **sudo group**, **su -**
- File attributes: **chattr**, **lsattr** (**immutable**, **append only**)
- Permissions: **chgrp**, **chmod** (**octal**, **symbolic**), **chown**; special permissions (**sticky bit**, **setuid**, **setgid**); **umask**
- Access control: **ACL**s (**setfacl**, **getfacl**); **SELinux** (**restorecon**, **semanage**, **chcon**, **ls -Z**, **getenforce**, **setenforce**, **getsebool**, **setsebool**, **audit2allow**, **sealert**; states **Enforcing**, **Permissive**, **Disabled**)
- Secure remote access: **sshd** (**key** vs password auth, SSH **tunnel**ing, **PermitRootLogin**, **X11Forwarding**, **AllowUsers**, **AllowGroups**), **ssh-agent** and `ssh-add`, **SFTP** with **chroot**, **fail2ban**
- Avoiding unsecure services: **Telnet**, **FTP**, **TFTP**
- Disabling an **unused file system** module
- Removal of unnecessary **SUID** permissions
- **Secure Boot** (**UEFI**)

### How it works

Hardening follows a few simple principles:

- **Least privilege:** give each user and program only the rights it needs, and nothing more. A helpdesk user who restarts one service does not need a root shell.
- **Defense in depth:** stack several independent layers. Even if one fails (a weak password), another (key-only SSH, fail2ban, SELinux) still stops the attacker.
- **Minimize attack surface:** every running service, open port, SUID program, and loadable kernel module is something that could have a bug. Remove what you do not use.
- **Secure defaults and verification:** check every change (`visudo -c`, `sshd -t`, `restorecon -n`) before it goes live, and keep a way back in.

The layers you will work with, from the inside out:

```{.diagram}
  +---------------------------------------------------------------+
  | Boot:       UEFI Secure Boot -> shim -> GRUB -> signed kernel |
  |  +---------------------------------------------------------+  |
  |  | Kernel:  modules (block unused file systems), SELinux    |  |
  |  |  +---------------------------------------------------+  |  |
  |  |  | Files: owner/group/mode, special bits, ACLs, attrs |  |  |
  |  |  |  +---------------------------------------------+  |  |  |
  |  |  |  | Users: sudo rules, su, wheel/sudo groups     |  |  |  |
  |  |  |  +---------------------------------------------+  |  |  |
  |  |  +---------------------------------------------------+  |  |
  |  +---------------------------------------------------------+  |
  |  Network edge: sshd settings, fail2ban, no Telnet/FTP/TFTP    |
  +---------------------------------------------------------------+
```

**Standard permissions** give three sets of rights (read `r`=4, write `w`=2, execute `x`=1) to three classes (user/owner, group, others). `chmod 640 file` means owner `rw-` (6), group `r--` (4), others `---` (0). **Special bits** add a fourth digit in front: **setuid** (4) runs a program as its owner, **setgid** (2) runs as the group or, on a directory, makes new files inherit the directory's group, and the **sticky bit** (1) on a directory means only a file's owner may delete it (that is why everyone can write `/tmp` but cannot delete each other's files).

**ACLs** (Access Control Lists) extend permissions to extra named users and groups ("bob may also read this file"). **File attributes** set with `chattr` work below permissions: an **immutable** file cannot be changed or deleted even by root until the attribute is removed.

**SELinux** (Security-Enhanced Linux, on by default on Rocky) is **Mandatory Access Control**. Every process and file has a **label** (context) such as `httpd_t` or `httpd_sys_content_t`, and a policy says which process labels may touch which file labels. Even if Apache runs as root and the file is mode 777, SELinux denies access if the labels do not match. Ubuntu uses **AppArmor**, a path-based MAC system, instead.
