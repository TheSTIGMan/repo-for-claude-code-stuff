## Lab 5.2: Troubleshoot Hardware, Storage, and OS Issues {#lab-5-2}

::: labinfo
**Objective:** 5.2 Given a scenario, analyze and troubleshoot hardware, storage, and Linux OS issues.\
**Domain:** 5.0 Troubleshooting (22% of the exam)\
**Time:** about 4 hours (do it over two or three sittings; each scenario stands alone)\
**VM:** ubuntu-lab (rocky-lab only for one SSH test)\
**Snapshot first:** Yes. Take a snapshot now. Several scenarios deliberately break booting, and you need console access to the VM (the hypervisor's window, not SSH) for those.
:::

This is a break-and-fix lab. In each scenario you deliberately cause a real problem, look at it the way you would on a production server, find the root cause with the right tools, fix it, and prove the fix worked. Exam questions for this objective describe a symptom ("users report No space left on device but df shows 40% free") and ask for the cause or the next command, so the goal is to connect symptoms to causes quickly.

### What you'll practice

- A repeatable troubleshooting method: identify symptoms, gather data, form a hypothesis, test, fix, verify, document
- OS filesystem full (including deleted-but-open files) and inode exhaustion
- Partition not writable (read-only mount, immutable attribute, permissions) and quota issues
- Filesystem will not mount and data corruption issues (`e2fsck`, backup superblocks, checksums)
- GRUB misconfiguration, filesystem will not mount at boot (`/etc/fstab`, emergency mode)
- Kernel panic and kernel corruption issues (`sysrq`, `kdump`, `dpkg -V`, reinstalling kernel packages)
- Missing or disabled drivers (`lsmod`, `modprobe`, `modinfo`, `/etc/modprobe.d`)
- Package dependency issues (`dpkg`, `apt --fix-broken install`, `rpm`/`dnf` equivalents)
- Segmentation fault (`dmesg`, `coredumpctl`, `gdb`)
- Killed processes (OOM killer) and memory leaks (`ps`, `pmap`, `smem`)
- PATH misconfiguration issues
- Systemd unit failures (`systemctl status`, `journalctl -xeu`, `daemon-reload`)
- Unresponsive process (process states, `strace`, signals)
- Device failure (`dmsetup` error target, `badblocks`, `mdadm` degraded array, `smartctl`)
- Server inaccessible and server not turning on (console, BMC/IPMI, boot logs)

### How it works

**The troubleshooting method.** Experienced admins do not guess randomly. They follow a loop. CompTIA's own methodology is very close to this:

```{.diagram}
 1. Identify the symptoms   -> What exactly fails? Exact error text? Since when?
          |                    What changed recently? Who/what is affected?
 2. Gather data             -> logs (journalctl, dmesg), status (systemctl),
          |                    resources (df, free, ps), config files
 3. Form a hypothesis       -> "I think the disk is out of inodes"
          |
 4. Test the hypothesis     -> run the one command that proves or disproves it
          |  (wrong? go back to 2 or 3)
 5. Fix                     -> smallest safe change; back up first
          |
 6. Verify                  -> repeat the original failing action; it works now
          |
 7. Document                -> what happened, cause, fix, how to prevent it
```

Three habits make this loop fast:

- **Read the exact error message.** "No space left on device", "Read-only file system", "Permission denied", "Operation not permitted", and "Disk quota exceeded" are five different problems. The kernel chooses the message carefully.
- **Ask "what changed?"** Most outages follow a change: an update, a config edit, a full disk after a log storm.
- **Change one thing at a time** and keep a copy of every file before you edit it (`sudo cp file file.bak`), so you can always undo.

**Where the evidence lives.**

| Evidence | Command |
|---|---|
| Kernel messages (hardware, drivers, filesystems, OOM, segfaults) | `dmesg -T`, `journalctl -k` |
| Everything systemd logged this boot / last boot | `journalctl -b`, `journalctl -b -1` |
| One service | `systemctl status unit`, `journalctl -xeu unit` |
| Disk space and inodes | `df -h`, `df -i`, `du`, `lsof +L1` |
| Mounts and their options | `findmnt`, `mount` |
| Memory and processes | `free -h`, `ps`, `top`, `/proc/PID/status` |
| Packages | `dpkg -l`, `dpkg -V`, `apt`, `rpm -V`, `dnf` |

**Practice safely with loop devices.** Most storage scenarios use *loop devices*: a regular file that the kernel presents as a disk (`/dev/loop0`). `mount -o loop file.img /mnt/x` sets one up automatically. You can corrupt, fill, and break these files as much as you like without touching your real disks; deleting the file removes the "disk".

**Documenting.** Keep a simple incident log while you work. For every scenario, write one line per method step. You will create the log file in Task 1. In real jobs this becomes the ticket notes or post-incident review.

#### Task 2: Scenario 1: "No space left on device" (filesystem full and inode exhaustion)

The same error message has two very different causes. You will create both.

**Part A: the filesystem is full**

1. **Break it.** Create a small 64 MB filesystem, fill it with a log file, hide 20 MB in a deleted file that a process still holds open, then fill the rest.

    ```bash
    cd ~/labs/5.2
    truncate -s 64M small.img
    mkfs.ext4 -q small.img
    sudo mkdir -p /mnt/small
    sudo mount -o loop small.img /mnt/small
    sudo chown student: /mnt/small
    fallocate -l 25M /mnt/small/app.log
    fallocate -l 20M /mnt/small/huge.tmp
    sleep infinity < /mnt/small/huge.tmp &
    rm /mnt/small/huge.tmp
    dd if=/dev/zero of=/mnt/small/filler bs=1M status=none
    ```

    ::: explain
    **What just happened:** `truncate -s 64M` creates an empty 64 MB file, `mkfs.ext4 -q` formats it quietly, and `mount -o loop` attaches it to a free loop device and mounts it. `fallocate -l` reserves space for a file instantly. `sleep infinity < huge.tmp &` starts a background process whose standard input is `huge.tmp`, so the file stays open. Then `rm` deletes the *name*, but the space is not freed while a process holds the file open. Finally `dd` writes zeros until the disk is full and stops with an error, which is expected.
    :::

2. **Symptom.** Try to save a file, as a user or application would.

    ```bash
    echo "hello" > /mnt/small/test.txt
    ```

    ```{.output}
    -bash: echo: write error: No space left on device
    ```

3. **Investigate.** Start with `df` (disk free) for the whole filesystem, then `du` (disk usage) for the files you can see.

    ```bash
    df -h /mnt/small
    du -sh /mnt/small/* 2>/dev/null
    du -sh /mnt/small
    ```

    ```{.output}
    Filesystem      Size  Used Avail Use% Mounted on
    /dev/loop3       55M   51M     0 100% /mnt/small
    25M     /mnt/small/app.log
    6.6M    /mnt/small/filler
    32M     /mnt/small
    ```

    ::: explain
    **What just happened:** `df` says 51 MB used, but `du` can only find about 32 MB of files. When `df` and `du` disagree, the usual hypothesis is a **deleted file that is still open**. Also notice `Avail 0` while `Used` is less than `Size`: ext4 reserves 5% of blocks for root, so ordinary users run out first. Root can still write, which keeps the system alive.
    :::

4. **Test the hypothesis** with `lsof +L1`, which lists open files whose link count is less than 1 (deleted but still open).

    ```bash
    lsof +L1 /mnt/small
    ```

    ```{.output}
    COMMAND  PID    USER FD  TYPE DEVICE SIZE/OFF NLINK NODE NAME
    sleep   4120 student 0r  REG    7,3 20971520     0   13 /mnt/small/huge.tmp (deleted)
    ```

5. **Root cause.** Two things: a large log and filler data used the space, and 20 MB is held by a deleted file that process `4120` (`sleep`) still has open. This is extremely common in real life: someone deletes a huge log file, but the service still has it open, so the space never comes back.

6. **Fix.** Remove the junk, empty the log without deleting it, and release the deleted file by stopping the process that holds it.

    ```bash
    rm /mnt/small/filler
    truncate -s 0 /mnt/small/app.log
    kill %1
    df -h /mnt/small
    ```

    ::: explain
    **What just happened:** `truncate -s 0` empties a file in place. Use it (or `: > file`) on logs that a service is writing; `rm` would leave the space held. `kill %1` stops background job 1 (the `sleep`), which closes the deleted file and frees its 20 MB. On a real server you would restart the service instead (for example `sudo systemctl restart nginx`). If you cannot restart it, you can empty the deleted file through `/proc`: `: > /proc/PID/fd/FD`.
    :::

7. **Verify.** `echo "hello" > /mnt/small/test.txt && cat /mnt/small/test.txt` now succeeds and `df -h` shows space available.

8. **Prevent.** Rotate logs with `logrotate` (using `copytruncate` or a reload), alert on disk usage above a threshold (Lab 5.1), put `/var` and `/home` on separate filesystems so a log storm cannot fill `/`, and find big items quickly with `sudo du -xh / --max-depth=2 | sort -h | tail`.

**Part B: out of inodes**

9. **Break it.** An **inode** is the small record that stores a file's metadata (owner, permissions, where its data blocks are). Every file and directory uses exactly one, and ext4 creates a fixed number when you format. Create a filesystem with only about 2,000 inodes and fill them with tiny "session" files.

    ```bash
    cd ~/labs/5.2
    truncate -s 64M inodes.img
    mkfs.ext4 -q -N 2048 inodes.img
    sudo mkdir -p /mnt/inodes
    sudo mount -o loop inodes.img /mnt/inodes
    sudo chown student: /mnt/inodes
    mkdir /mnt/inodes/sessions
    for i in $(seq 1 3000); do : > /mnt/inodes/sessions/sess_$i; done 2>/dev/null
    ```

    ::: explain
    **What just happened:** `-N 2048` asks `mkfs.ext4` for about 2,048 inodes instead of the normal several thousand. The `for` loop tries to create 3,000 empty files (`: > file` creates an empty file). It runs out partway through; `2>/dev/null` hides the error messages.
    :::

10. **Symptom.**

    ```bash
    touch /mnt/inodes/report.txt
    ```

    ```{.output}
    touch: cannot touch '/mnt/inodes/report.txt': No space left on device
    ```

11. **Investigate.** Check space, then inodes.

    ```bash
    df -h /mnt/inodes
    df -i /mnt/inodes
    du --inodes -s /mnt/inodes/* 2>/dev/null | sort -n | tail -n 3
    ```

    ```{.output}
    Filesystem      Size  Used Avail Use% Mounted on
    /dev/loop4       55M   24K   51M   1% /mnt/inodes
    Filesystem     Inodes IUsed IFree IUse% Mounted on
    /dev/loop4       2048  2048     0  100% /mnt/inodes
    1       /mnt/inodes/lost+found
    2038    /mnt/inodes/sessions
    ```

    ::: explain
    **What just happened:** `df -h` shows 1% used, so space is not the problem. `df -i` shows inodes (`IUse%` 100%). `du --inodes -s` counts inodes per directory, so the `sessions` directory is the culprit. On a real server, look at mail queues, PHP session directories, cache directories, and `/tmp`.
    :::

12. **Root cause.** Inode exhaustion: millions of tiny files (here 2,038) used every inode while most of the space is free.

13. **Fix.** Delete the unneeded files. `find ... -delete` handles any number of files; `rm sessions/*` would fail with "Argument list too long" on a real directory with millions of files.

    ```bash
    find /mnt/inodes/sessions -name 'sess_*' -delete
    df -i /mnt/inodes
    touch /mnt/inodes/report.txt && ls /mnt/inodes
    ```

14. **Prevent.** Clean old files automatically (`systemd-tmpfiles` or a cron job with `find -mtime +7 -delete`), monitor `df -i` as well as `df -h`, and format filesystems for many small files with more inodes (`mkfs.ext4 -i 4096` gives one inode per 4 KB). XFS and Btrfs allocate inodes dynamically, so they rarely hit this.

15. **Undo.**

    ```bash
    sudo umount /mnt/small /mnt/inodes
    rm -f ~/labs/5.2/small.img ~/labs/5.2/inodes.img
    ```

::: checkpoint
**Checkpoint:** You can explain why `df -h` and `du` disagreed in Part A (deleted-but-open file found with `lsof +L1`) and why `df -h` showed 1% in Part B (inodes, found with `df -i`). `findmnt /mnt/small /mnt/inodes` prints nothing.
:::

#### Task 3: Scenario 2: "I can't save my file" (partition not writable)

A partition can be not writable for several reasons, and each gives a different error. You will create three at once and use the messages to tell them apart.

1. **Break it.**

    ```bash
    cd ~/labs/5.2
    truncate -s 64M rw.img
    mkfs.ext4 -q rw.img
    sudo mkdir -p /mnt/rw /mnt/rw2
    sudo mount -o loop rw.img /mnt/rw
    sudo mkdir /mnt/rw/locked /mnt/rw/reports
    sudo chown student: /mnt/rw/reports
    echo "Q3 numbers" > /mnt/rw/reports/q3.txt
    sudo chattr +i /mnt/rw/reports/q3.txt
    truncate -s 64M ro.img && mkfs.ext4 -q ro.img
    sudo mount -o loop,ro ro.img /mnt/rw2
    ```

2. **Symptom.** Try three writes as student.

    ```bash
    touch /mnt/rw/locked/new.txt
    echo "more" >> /mnt/rw/reports/q3.txt
    sudo touch /mnt/rw2/new.txt
    ```

    ```{.output}
    touch: cannot touch '/mnt/rw/locked/new.txt': Permission denied
    -bash: /mnt/rw/reports/q3.txt: Operation not permitted
    touch: cannot touch '/mnt/rw2/new.txt': Read-only file system
    ```

    ::: explain
    **What just happened:** Three different messages for three different causes. "Permission denied" (`EACCES`) means the normal permission check failed. "Operation not permitted" (`EPERM`) on a file you own often means a file **attribute** blocks it. "Read-only file system" (`EROFS`) means the whole mount is read-only, so even root fails.
    :::

3. **Investigate cause 1: permissions.**

    ```bash
    ls -ld /mnt/rw/locked
    namei -l /mnt/rw/locked/new.txt
    id
    ```

    ```{.output}
    drwxr-xr-x 2 root root 1024 Oct 10 12:01 /mnt/rw/locked
    f: /mnt/rw/locked/new.txt
    drwxr-xr-x root root /
    drwxr-xr-x root root mnt
    drwxr-xr-x root root rw
    drwxr-xr-x root root locked
                         new.txt - No such file or directory
    ```

    ::: explain
    **What just happened:** Creating a file needs **write** and **execute** permission on the *directory*. `locked` is owned by root with mode `755`, so others (student) have only `r-x`. `namei -l` shows permissions for every directory along a path, which quickly finds a blocking parent directory. `id` confirms which user and groups you are.
    :::

4. **Investigate cause 2: attributes.**

    ```bash
    ls -l /mnt/rw/reports/q3.txt
    lsattr /mnt/rw/reports/q3.txt
    ```

    ```{.output}
    -rw-rw-r-- 1 student student 11 Oct 10 12:01 /mnt/rw/reports/q3.txt
    ----i---------e------- /mnt/rw/reports/q3.txt
    ```

    ::: explain
    **What just happened:** The normal permissions allow student to write, yet the write failed. `lsattr` shows extended filesystem attributes: `i` is **immutable** (nobody, not even root, can modify, rename, or delete the file) and `e` just means the file uses extents (normal on ext4). Another attribute you may meet is `a`, append-only, often used on logs.
    :::

5. **Investigate cause 3: read-only mount.**

    ```bash
    findmnt -o TARGET,SOURCE,OPTIONS /mnt/rw2
    sudo dmesg -T | grep -i -E "remount|read-only|EXT4-fs error" | tail -n 5
    ```

    ```{.output}
    TARGET   SOURCE     OPTIONS
    /mnt/rw2 /dev/loop6 ro,relatime
    ```

    ::: explain
    **What just happened:** `findmnt` shows the mount options; `ro` means read-only. Here you mounted it read-only on purpose, so `dmesg` shows nothing interesting. On a real server, a filesystem that *suddenly* becomes read-only was usually remounted by the kernel after it detected errors. Then `dmesg` shows lines like the ones below, and the right response is to find the disk problem, not just remount:

    ```{.output}
    EXT4-fs error (device sdb1): ext4_lookup:1855: inode #2: comm ls: deleted inode referenced: 12
    EXT4-fs (sdb1): Remounting filesystem read-only
    ```

    The behavior is set per filesystem with the `errors=` mount option (`continue`, `remount-ro`, or `panic`); `sudo tune2fs -l /dev/sdb1 | grep -i behavior` shows the default stored in the superblock.
    :::

6. **Root cause.** Cause 1: directory permissions. Cause 2: immutable attribute. Cause 3: read-only mount. (A fourth cause, a full filesystem, gives "No space left on device", which you saw in Scenario 1.)

7. **Fix** each one with the matching tool.

    ```bash
    sudo chown student: /mnt/rw/locked
    sudo chattr -i /mnt/rw/reports/q3.txt
    sudo mount -o remount,rw /mnt/rw2
    ```

    ::: explain
    **What just happened:** `chown` gives student ownership of the directory (you could also use `chmod` or an ACL with `setfacl -m u:student:rwx`). `chattr -i` removes the immutable attribute. `mount -o remount,rw` changes a mounted filesystem to read-write without unmounting it. If the kernel had forced it read-only after errors, you would instead unmount it, run `e2fsck`, then mount it again.
    :::

8. **Verify.** Repeat the three writes from step 2; all succeed.

    ```bash
    touch /mnt/rw/locked/new.txt
    echo "more" >> /mnt/rw/reports/q3.txt
    sudo touch /mnt/rw2/new.txt
    ```

9. **Prevent.** Document why a file is immutable when you set it (it confuses the next admin), check `findmnt` and `dmesg` first when writes fail for everyone, and use `namei -l` before changing permissions so you change the right directory.

10. **Undo.**

    ```bash
    sudo umount /mnt/rw /mnt/rw2
    rm -f ~/labs/5.2/rw.img ~/labs/5.2/ro.img
    ```

::: checkpoint
**Checkpoint:** Without looking back, match each message to its cause: "Permission denied", "Operation not permitted", "Read-only file system", "No space left on device".
:::

#### Task 4: Scenario 3: "Disk quota exceeded"

A **disk quota** limits how much space (blocks) or how many files (inodes) a user or group may use on a filesystem. The **soft limit** can be exceeded for a **grace period** (7 days by default); the **hard limit** can never be exceeded.

1. **Break it.** Create a filesystem with user quotas turned on and give student a 5 MB soft and 6 MB hard limit.

    ```bash
    cd ~/labs/5.2
    truncate -s 128M quota.img
    mkfs.ext4 -q quota.img
    sudo mkdir -p /mnt/quota
    sudo mount -o loop,usrquota quota.img /mnt/quota
    sudo quotacheck -cum /mnt/quota
    sudo quotaon -v /mnt/quota
    sudo chmod 1777 /mnt/quota
    sudo setquota -u student 5000 6000 0 0 /mnt/quota
    ```

    ```{.output}
    /dev/loop3 [/mnt/quota]: user quotas turned on
    ```

    ::: explain
    **What just happened:** The `usrquota` mount option enables user quota accounting. `quotacheck -cum` scans the filesystem and **c**reates the quota file `aquota.user` for **u**sers, without trying to re**m**ount read-only first. `quotaon` starts enforcing limits. `chmod 1777` makes the directory writable by everyone (with the sticky bit, like `/tmp`). `setquota -u student 5000 6000 0 0` sets block soft 5000 KB, block hard 6000 KB, and no inode limits (`0` means unlimited). Quota block numbers are in 1 KB units.
    :::

    ::: tip
    If `quotaon` reports that the quota format is not supported by the kernel, install the extra kernel modules with `sudo apt install -y linux-modules-extra-$(uname -r)` and run `quotaon` again.
    :::

2. **Symptom.** Student tries to save a 10 MB file.

    ```bash
    dd if=/dev/zero of=/mnt/quota/video.raw bs=1M count=10
    ```

    ```{.output}
    dd: error writing '/mnt/quota/video.raw': Disk quota exceeded
    6+0 records in
    5+0 records out
    5996544 bytes (6.0 MB, 5.7 MiB) copied, 0.0201 s, 298 MB/s
    ```

3. **Investigate.** The filesystem has plenty of space, so check quotas.

    ```bash
    df -h /mnt/quota
    quota -u student
    sudo repquota /mnt/quota
    ```

    ```{.output}
    Filesystem      Size  Used Avail Use% Mounted on
    /dev/loop3      115M  6.0M  100M   6% /mnt/quota
    Disk quotas for user student (uid 1000):
         Filesystem  blocks   quota   limit   grace   files   quota   limit   grace
         /dev/loop3   6000*    5000    6000   6days       1       0       0
    *** Report for user quotas on device /dev/loop3
    Block grace time: 7days; Inode grace time: 7days
                            Block limits                File limits
    User            used    soft    hard  grace    used  soft  hard  grace
    ----------------------------------------------------------------------
    root      --      20       0       0              2     0     0
    student   +-    6000    5000    6000  6days       1     0     0
    ```

    ::: explain
    **What just happened:** `quota -u student` shows one user's usage; the `*` after `6000` marks a limit that is exceeded, and `grace` shows time left before the soft limit is enforced like a hard limit. `repquota` reports every user; in the `+-` column, the first character is blocks and the second is files, and `+` means over the soft limit. student has hit the hard limit (6000), so writes fail even though the disk is 94% free.
    :::

4. **Root cause.** The user hit their hard block quota.

5. **Fix.** Either the user deletes files, or an admin raises the limit if it is justified. Raise it to 20 MB soft, 25 MB hard. (`sudo edquota -u student` does the same in an editor; `sudo edquota -t` changes grace periods.)

    ```bash
    rm /mnt/quota/video.raw
    sudo setquota -u student 20000 25000 0 0 /mnt/quota
    ```

6. **Verify.**

    ```bash
    dd if=/dev/zero of=/mnt/quota/video.raw bs=1M count=10 status=none && quota -u student
    ```

7. **Prevent.** Tell users their limits, use `warnquota` to email users who pass their soft limit, and review `repquota -a` regularly. When quotas are enabled permanently, add `usrquota`/`grpquota` to the options in `/etc/fstab`.

8. **Undo.**

    ```bash
    sudo quotaoff /mnt/quota
    sudo umount /mnt/quota
    rm -f ~/labs/5.2/quota.img
    ```

::: checkpoint
**Checkpoint:** You saw `Disk quota exceeded` with `df` showing lots of free space, and `sudo repquota` showed student with `+-` before your fix.
:::

#### Task 5: Scenario 4: Filesystem will not mount, and data corruption

**Data corruption** comes in two flavors: damaged *metadata* (the filesystem's own structures, which `fsck` can repair) and damaged *file contents* (which `fsck` cannot see at all). You will create both.

1. **Prepare** a 256 MB ext4 filesystem with an important file, a checksum, and a backup copy.

    ```bash
    cd ~/labs/5.2
    truncate -s 256M data.img
    mkfs.ext4 -q -b 4096 data.img
    sudo mkdir -p /mnt/data
    sudo mount -o loop data.img /mnt/data
    seq 1 200000 | sudo tee /mnt/data/important.txt > /dev/null
    (cd /mnt/data && sha256sum important.txt) > important.sha256
    cp /mnt/data/important.txt important.bak
    sudo umount /mnt/data
    ```

    ::: explain
    **What just happened:** `-b 4096` fixes the block size at 4 KB so the numbers below are predictable. `seq 1 200000` writes 200,000 numbered lines (about 1.2 MB). `sha256sum` records a fingerprint of the file; any change to even one byte changes the fingerprint. The parentheses run `cd` in a subshell, so your own shell stays in `~/labs/5.2`.
    :::

2. **Break it (metadata).** The **superblock** is the master record of an ext filesystem (size, block counts, features). It starts at byte 1024. Overwrite it with zeros.

    ```bash
    dd if=/dev/zero of=data.img bs=1024 seek=1 count=1 conv=notrunc
    ```

    ::: explain
    **What just happened:** `bs=1024 seek=1 count=1` writes one 1 KB block of zeros starting at offset 1024. `conv=notrunc` tells `dd` not to shorten the image file. This imitates a bad write, a failing disk, or someone running a tool against the wrong device.
    :::

3. **Symptom.**

    ```bash
    sudo mount -o loop data.img /mnt/data
    ```

    ```{.output}
    mount: /mnt/data: wrong fs type, bad option, bad superblock on /dev/loop3,
           missing codepage or helper program, or other error.
           dmesg(1) may have more information after failed mount system call.
    ```

4. **Investigate.**

    ```bash
    sudo dmesg | tail -n 2
    sudo blkid data.img; echo "blkid exit code: $?"
    dumpe2fs -h data.img
    ```

    ```{.output}
    [ 9231.441021] EXT4-fs (loop3): VFS: Can't find ext4 filesystem
    blkid exit code: 2
    dumpe2fs 1.47.0 (5-Feb-2023)
    dumpe2fs: Bad magic number in super-block while trying to open data.img
    ```

    ::: explain
    **What just happened:** The kernel cannot find an ext4 filesystem, `blkid` cannot identify any filesystem type (exit code `2` means nothing found), and `dumpe2fs -h` (print the superblock header) reports a bad **magic number**, the signature bytes that identify an ext superblock. Hypothesis: the primary superblock is damaged. ext filesystems keep **backup superblocks**, so it is fixable.
    :::

5. **Test the hypothesis:** find where the backups are. `mke2fs -n` is a dry run: it prints what it *would* do (including backup locations) without writing anything. You must give it the same block size you used originally.

    ```bash
    mke2fs -n -b 4096 data.img | grep -A1 -i backup
    ```

    ```{.output}
    Superblock backups stored on blocks:
            32768
    ```

    ::: warning
    Never forget the `-n`. Without it, `mke2fs` creates a new, empty filesystem and destroys whatever was there.
    :::

6. **Fix the metadata.** Run `e2fsck` using the backup superblock.

    ```bash
    e2fsck -f -y -b 32768 -B 4096 data.img
    ```

    ```{.output}
    e2fsck 1.47.0 (5-Feb-2023)
    Superblock has an invalid journal (inode 8).
    Clear? yes
    ...
    Pass 1: Checking inodes, blocks, and sizes
    Pass 2: Checking directory structure
    Pass 3: Checking directory connectivity
    Pass 4: Checking reference counts
    Pass 5: Checking group summary information
    ...
    data.img: ***** FILE SYSTEM WAS MODIFIED *****
    data.img: 12/65536 files (0.0% non-contiguous), 9054/65536 blocks
    ```

    ::: explain
    **What just happened:** `-b 32768` reads the superblock from the backup, `-B 4096` gives the block size, `-f` forces a full check, and `-y` answers yes to every repair question. When it finishes, it writes a good primary superblock. Your exact messages may differ (for example about the journal); what matters is that it finishes. On a real disk you run `e2fsck` (or `fsck`) on the device, for example `sudo e2fsck -f /dev/sdb1`, and **only when it is unmounted**. XFS uses `xfs_repair` instead.
    :::

7. **Verify** the mount works and the file is intact.

    ```bash
    sudo mount -o loop data.img /mnt/data
    (cd /mnt/data && sha256sum -c ~/labs/5.2/important.sha256)
    sudo umount /mnt/data
    ```

    ```{.output}
    important.txt: OK
    ```

8. **Break it (file contents).** Now damage the file's data instead. `debugfs` can tell you which disk blocks hold the file.

    ```bash
    BLK=$(debugfs -R "blocks /important.txt" data.img 2>/dev/null | awk '{print $1}')
    echo "first data block of important.txt: $BLK"
    dd if=/dev/urandom of=data.img bs=4096 seek="$BLK" count=1 conv=notrunc status=none
    ```

    ::: explain
    **What just happened:** `debugfs -R "blocks /important.txt"` prints the block numbers that store the file; `awk '{print $1}'` keeps the first one. `dd` then overwrites that 4 KB block with random bytes. This is what a failing disk, bad RAM, or a buggy controller does silently.
    :::

9. **Symptom and investigation.**

    ```bash
    e2fsck -f -n data.img | tail -n 1
    sudo mount -o loop data.img /mnt/data
    head -c 120 /mnt/data/important.txt | cat -v | head -n 3
    (cd /mnt/data && sha256sum -c ~/labs/5.2/important.sha256)
    ```

    ```{.output}
    data.img: 12/65536 files (0.0% non-contiguous), 9054/65536 blocks
    M-^Z^Q^GM-2kM-^@M-?^]x...
    important.txt: FAILED
    sha256sum: WARNING: 1 computed checksum did NOT match
    ```

    ::: explain
    **What just happened:** `e2fsck -n` (check only, change nothing) reports the filesystem as healthy, because all metadata is fine. Yet the file starts with garbage (`cat -v` shows unprintable bytes safely) and the checksum fails. **`fsck` does not protect file contents.** Only checksums, backups, and checksumming filesystems (Btrfs, ZFS) detect this kind of corruption.
    :::

10. **Root cause.** One data block of the file was overwritten (silent data corruption).

11. **Fix.** Restore the file from backup.

    ```bash
    sudo cp ~/labs/5.2/important.bak /mnt/data/important.txt
    ```

12. **Verify.** `(cd /mnt/data && sha256sum -c ~/labs/5.2/important.sha256)` prints `important.txt: OK`.

13. **Prevent.** Keep tested backups, store checksums for critical data, use ECC memory on servers, monitor disks with SMART (Task 16), and check `dmesg` for I/O errors. Never run `fsck` on a mounted filesystem.

14. **Undo.**

    ```bash
    sudo umount /mnt/data
    rm -f ~/labs/5.2/data.img ~/labs/5.2/important.bak ~/labs/5.2/important.sha256
    ```

::: checkpoint
**Checkpoint:** You repaired a "bad superblock" mount failure with `e2fsck -b 32768`, and you saw `fsck` report a clean filesystem while `sha256sum -c` caught corrupted file data.
:::

#### Task 6: Scenario 5: The server boots to a BusyBox prompt (GRUB misconfiguration)

**GRUB** is the bootloader: it loads the kernel and initramfs and passes the kernel its command line (for example `root=` to say where the root filesystem is). On Ubuntu you edit `/etc/default/grub` and run `update-grub`, which regenerates `/boot/grub/grub.cfg`. You never edit `grub.cfg` directly; it is overwritten on every kernel update.

::: warning
This scenario stops the VM from booting until you fix it. Use the VM console (hypervisor window), not SSH, and make sure you have a snapshot.
:::

1. **Prepare: make the GRUB menu visible.** Ubuntu hides the menu on single-OS systems, which makes recovery hard. Showing it for 10 seconds is a correct and common server change.

    ```bash
    sudo cp /etc/default/grub /etc/default/grub.lab-orig
    sudo sed -i 's/^GRUB_TIMEOUT_STYLE=.*/GRUB_TIMEOUT_STYLE=menu/; s/^GRUB_TIMEOUT=.*/GRUB_TIMEOUT=10/' \
        /etc/default/grub
    grep -E '^GRUB_(TIMEOUT|TIMEOUT_STYLE|CMDLINE_LINUX_DEFAULT)=' /etc/default/grub
    sudo update-grub
    ```

    ```{.output}
    GRUB_TIMEOUT_STYLE=menu
    GRUB_TIMEOUT=10
    GRUB_CMDLINE_LINUX_DEFAULT=""
    Sourcing file `/etc/default/grub'
    Generating grub configuration file ...
    Found linux image: /boot/vmlinuz-6.8.0-45-generic
    Found initrd image: /boot/initrd.img-6.8.0-45-generic
    done
    ```

    ::: explain
    **What just happened:** `sed -i` edits the file in place with two substitutions separated by `;`. `GRUB_TIMEOUT_STYLE=menu` always shows the menu, and `GRUB_TIMEOUT=10` waits 10 seconds before booting the default entry. `update-grub` (a wrapper for `grub-mkconfig -o /boot/grub/grub.cfg`) rebuilds the real configuration. On Rocky the equivalent is `sudo grub2-mkconfig -o /boot/grub2/grub.cfg`, or `grubby` for kernel arguments.
    :::

2. **Break it.** Add a bad `root=` kernel parameter. Because `/etc/default/grub` is a shell script, a line at the end can redefine a variable; `$GRUB_CMDLINE_LINUX_DEFAULT` keeps whatever was there before.

    ```bash
    echo 'GRUB_CMDLINE_LINUX_DEFAULT="$GRUB_CMDLINE_LINUX_DEFAULT root=/dev/sdz9"' | \
        sudo tee -a /etc/default/grub
    sudo update-grub
    grep -m1 -o 'root=/dev/sdz9' /boot/grub/grub.cfg
    sudo reboot
    ```

3. **Symptom.** Watch the console. The GRUB menu appears and boots normally, then after about 30 seconds:

    ```{.output}
    Gave up waiting for root file system device.  Common problems:
     - Boot args (cat /proc/cmdline)
       - Check rootdelay= (did the system wait long enough?)
     - Missing modules (cat /proc/modules; ls /dev)
    ALERT!  /dev/sdz9 does not exist.  Dropping to a shell!

    BusyBox v1.36.1 (Ubuntu 1:1.36.1-6ubuntu3.1) built-in shell (ash)
    Enter 'help' for a list of built-in commands.

    (initramfs)
    ```

4. **Investigate** from the `(initramfs)` prompt. This tiny shell runs from the initramfs, before the real root filesystem is mounted.

    ```bash
    cat /proc/cmdline
    ```

    ```{.output}
    BOOT_IMAGE=/vmlinuz-6.8.0-45-generic root=/dev/mapper/ubuntu--vg-ubuntu--lv ro root=/dev/sdz9
    ```

    ::: explain
    **What just happened:** `/proc/cmdline` shows the exact kernel command line GRUB passed. There are two `root=` parameters and the last one wins. `/dev/sdz9` does not exist, so the initramfs cannot mount the root filesystem and drops to a rescue shell.
    :::

5. **Root cause.** A bad kernel parameter in `/etc/default/grub` was written into `grub.cfg` by `update-grub`.

6. **Fix for this boot: edit the entry in the GRUB menu.** Press `Ctrl+Alt+Del` (or reset the VM from the hypervisor). When the GRUB menu appears, press an arrow key to stop the countdown, highlight **Ubuntu**, and press `e`. Find the line that starts with `linux` and delete ` root=/dev/sdz9` from its end (use the arrow keys and Backspace). Press `Ctrl+X` or `F10` to boot.

    ::: explain
    **What just happened:** Pressing `e` edits a menu entry **for this boot only**; nothing is saved. This is how you fix a bad kernel parameter, add `single` or `systemd.unit=rescue.target` to boot into rescue mode, or add `init=/bin/bash` to get a root shell without a password (useful when the root account is locked; remount `/` with `mount -o remount,rw /` before editing files, then run `exec /sbin/init` or reset). The **Advanced options for Ubuntu** submenu lists every installed kernel plus a **recovery mode** entry for each.
    :::

7. **Fix permanently.** Log in and remove the bad line, then regenerate the configuration.

    ```bash
    sudo sed -i '/root=\/dev\/sdz9/d' /etc/default/grub
    sudo update-grub
    grep -c 'sdz9' /boot/grub/grub.cfg
    ```

    ```{.output}
    0
    ```

8. **Verify.** `sudo reboot`; the VM boots normally without any editing, and `cat /proc/cmdline` shows a single `root=`.

9. **Prevent.** Keep a copy of `/etc/default/grub` before editing, check the generated file with `grep` before rebooting, keep the menu visible (or know that holding `Shift` on BIOS or pressing `Esc` on UEFI shows a hidden menu), and keep at least one older kernel installed.

    ::: tip
    If GRUB itself cannot find its files (for example after a disk change), you see a `grub rescue>` prompt instead. There you use `ls` to find partitions, `set prefix=(hd0,gpt2)/boot/grub` and `set root=(hd0,gpt2)`, then `insmod normal` and `normal`; afterwards boot the system and run `sudo grub-install /dev/sda` (Rocky: `grub2-install`) to fix it for good.
    :::

Leave the GRUB menu visible for the next two scenarios; the Clean up section restores the original file.

::: checkpoint
**Checkpoint:** The VM boots normally, `grep -c sdz9 /boot/grub/grub.cfg` prints `0`, and you know how to edit a boot entry with `e` and boot it with `Ctrl+X`.
:::

#### Task 7: Scenario 6: Boot stops in emergency mode (filesystem will not mount)

At boot, systemd mounts everything listed in `/etc/fstab`. If a required filesystem will not mount, `local-fs.target` fails and systemd drops into **emergency mode**: a minimal root shell for repairs.

::: warning
This scenario stops normal booting. Use the VM console and have a snapshot.
:::

1. **Prepare: give root a password.** Ubuntu locks the root account, and emergency mode then refuses to give you a shell ("Cannot open access to console, the root account is locked"). Many servers set a root password for exactly this reason. You will lock it again in Clean up.

    ```bash
    sudo passwd root
    ```

    ::: tip
    If you skip this step, you can still recover: edit the boot entry with `e` (Task 6), add `init=/bin/bash` to the `linux` line, boot, run `mount -o remount,rw /`, fix `/etc/fstab`, run `sync`, and reset the VM.
    :::

2. **Break it.** Back up `fstab` and add a filesystem whose UUID does not exist, as happens when a disk is replaced or a UUID is mistyped.

    ```bash
    sudo cp /etc/fstab /etc/fstab.lab-orig
    echo 'UUID=11111111-2222-3333-4444-555555555555 /srv/data ext4 defaults 0 2' | \
        sudo tee -a /etc/fstab
    sudo systemctl daemon-reload
    ```

3. **Investigate before rebooting** (the step people forget). Two commands catch fstab mistakes safely:

    ```bash
    sudo findmnt --verify
    sudo mount -a
    ```

    ```{.output}
    /srv/data
       [E] unreachable source: UUID=11111111-2222-3333-4444-555555555555: No such file or directory
       [W] target does not exist
    0 parse errors, 1 error, 1 warning
    mount: /srv/data: can't find UUID=11111111-2222-3333-4444-555555555555.
    ```

    ::: explain
    **What just happened:** `findmnt --verify` checks every fstab line (syntax, devices, mount points, filesystem types) without mounting anything. `mount -a` tries to mount everything in fstab that is not yet mounted, which is what boot will do. Both report the problem. In real life you would stop here and fix it; for practice, reboot anyway.
    :::

4. **Symptom.** `sudo reboot` and watch the console. After about 90 seconds:

    ```{.output}
    [ TIME ] Timed out waiting for device dev-disk-by\x2duuid-11111111...device
    [DEPEND] Dependency failed for srv-data.mount - /srv/data.
    [DEPEND] Dependency failed for local-fs.target - Local File Systems.
    You are in emergency mode. After logging in, type "journalctl -xb" to view
    system logs, "systemctl reboot" to reboot, "systemctl default" or "exit"
    to boot into default mode.
    Give root password for maintenance
    (or press Control-D to continue):
    ```

5. **Investigate** in emergency mode. Type the root password, then:

    ```bash
    systemctl --failed
    journalctl -xb -p err | tail -n 20
    ```

    ::: explain
    **What just happened:** `systemctl --failed` lists failed units (you will see `srv-data.mount`). systemd turns each fstab line into a `.mount` unit named after its path (`/srv/data` becomes `srv-data.mount`). `journalctl -xb -p err` shows errors from this boot with explanations (`-x`). The 90-second wait is systemd's default device timeout.
    :::

6. **Root cause.** A required fstab entry points to a device that does not exist.

7. **Fix** in emergency mode. The root filesystem may be read-only here, so remount it read-write first, then remove the bad line (or restore the backup).

    ```bash
    mount -o remount,rw /
    cp /etc/fstab.lab-orig /etc/fstab
    systemctl daemon-reload
    mount -a
    systemctl default
    ```

    ::: explain
    **What just happened:** `mount -o remount,rw /` makes `/` writable. You restore the saved fstab, `daemon-reload` makes systemd regenerate the mount units from the fixed file, `mount -a` proves every entry now mounts, and `systemctl default` continues booting to the normal target (you could also `reboot`).
    :::

8. **Verify.** You reach the normal login prompt. Log in and run `systemctl --failed`; it shows `0 loaded units listed`.

9. **Prevent.** Always run `sudo findmnt --verify` and `sudo mount -a` after editing fstab. Use UUIDs from `blkid`, not `/dev/sdX` names. For disks that are not needed to boot (USB, extra data, network shares), add `nofail` (boot continues if missing) and optionally `x-systemd.device-timeout=10s`; network filesystems also get `_netdev`.

::: checkpoint
**Checkpoint:** You saw "You are in emergency mode", repaired `/etc/fstab` from the emergency shell, and `systemctl --failed` is now empty.
:::

#### Task 8: Scenario 7: Kernel panic and kernel corruption

A **kernel panic** is a fatal kernel error: the kernel stops because it cannot safely continue. The console shows `Kernel panic - not syncing:` and a reason. Common causes: the root filesystem cannot be mounted (`VFS: Unable to mount root fs on unknown-block(0,0)`, usually a missing or broken initramfs), `Attempted to kill init!` (PID 1 died), faulty RAM or CPU, and buggy drivers.

**Part A: simulate a kernel panic (explore/simulate)**

::: tip
**Explore/simulate:** You cannot make a real hardware fault, but the kernel's magic SysRq interface can deliberately crash it. This is completely safe on a VM with a snapshot, but it is an instant power-cut for the OS: save your work and close other sessions first.
:::

1. Look at the panic-related settings, then make the kernel reboot automatically 10 seconds after a panic (the default `0` means hang forever, waiting for a human).

    ```bash
    sysctl kernel.panic kernel.panic_on_oops kernel.sysrq
    sudo sysctl -w kernel.panic=10
    ```

    ```{.output}
    kernel.panic = 0
    kernel.panic_on_oops = 0
    kernel.sysrq = 176
    kernel.panic = 10
    ```

    ::: explain
    **What just happened:** `kernel.panic` is the number of seconds before automatic reboot after a panic. `kernel.panic_on_oops=0` means a less serious kernel error (an **oops**) kills only the offending task instead of panicking. `kernel.sysrq` controls which SysRq key combinations work from the keyboard; root can always use `/proc/sysrq-trigger`. `sysctl -w` changes a value until the next reboot.
    :::

2. **Break it.** From the VM console:

    ```bash
    sync
    echo c | sudo tee /proc/sysrq-trigger
    ```

3. **Symptom.** The console fills with a trace and ends like this, then the VM reboots after 10 seconds:

    ```{.output}
    sysrq: Trigger a crash
    Kernel panic - not syncing: sysrq triggered crash
    CPU: 1 PID: 2112 Comm: tee Not tainted 6.8.0-45-generic #45-Ubuntu
    Call Trace:
     <TASK>
     dump_stack_lvl+0x48/0x70
     panic+0x33c/0x370
     sysrq_handle_crash+0x1a/0x20
    ...
    Kernel Offset: 0x2a600000 from 0xffffffff81000000
    Rebooting in 10 seconds..
    ```

4. **Investigate after the reboot.** The panic itself is rarely in the journal, because the kernel stopped before anything could be written to disk. What you *can* see is that the previous boot ended abruptly.

    ```bash
    journalctl --list-boots | tail -n 3
    journalctl -b -1 -n 5 --no-pager
    last -x | head -n 5
    ```

    ::: explain
    **What just happened:** `journalctl --list-boots` lists boots (index `0` is the current one, `-1` the previous). `journalctl -b -1 -n 5` shows the last five lines of the previous boot: they stop suddenly, with no shutdown messages. `last -x` reads the login records; a session that ended with `crash` instead of a normal shutdown confirms an unclean stop. To keep the actual panic text, you need a crash dump.
    :::

5. **Learn crash dumps (kdump).** **kdump** reserves memory for a second, small "capture" kernel. When the main kernel panics, the capture kernel boots and saves the crashed kernel's memory to `/var/crash`, where it can be analyzed with the `crash` tool or sent to a vendor. On Ubuntu you install `linux-crashdump` (which brings `kdump-tools`; check it with `kdump-config show`); on Rocky, `kexec-tools` and `kdump.service`. Both add a `crashkernel=` parameter to the kernel command line and need a reboot. You do not need to install it for this lab, but know the names.

**Part B: kernel corruption**

Kernel corruption means the kernel image (`/boot/vmlinuz-*`), the initramfs (`/boot/initrd.img-*`), or kernel modules (`/lib/modules/<version>/`) on disk are damaged or incomplete, often after a full `/boot`, an interrupted update, or a disk problem. You will corrupt one unimportant module.

6. **Break it.** Find the file for the `dummy` network module (a fake network interface driver), note which package owns it, keep a copy, and overwrite part of it.

    ```bash
    sudo modprobe -r dummy 2>/dev/null
    MOD=$(modinfo -n dummy); echo "$MOD"
    PKG=$(dpkg -S "$MOD" | cut -d: -f1); echo "$PKG"
    cp "$MOD" ~/labs/5.2/dummy-module.bak
    sudo dd if=/dev/urandom of="$MOD" bs=1 count=64 seek=200 conv=notrunc status=none
    ```

    ```{.output}
    /lib/modules/6.8.0-45-generic/kernel/drivers/net/dummy.ko.zst
    linux-modules-6.8.0-45-generic
    ```

    ::: explain
    **What just happened:** `modinfo -n` prints the file name of a module. `dpkg -S` searches the package database for the package that installed a file; `cut -d: -f1` keeps the package name. Ubuntu compresses modules with zstd (`.ko.zst`). `dd` overwrites 64 bytes in the middle of the file with random data. (If `modinfo` cannot find `dummy`, your kernel is missing the extra modules package; see Task 9.)
    :::

7. **Symptom.**

    ```bash
    sudo modprobe dummy
    ```

    ```{.output}
    modprobe: ERROR: could not insert 'dummy': Invalid argument
    ```

    The exact text can differ (for example `Exec format error`); any error loading a module that used to load is the symptom. Also check `sudo dmesg | tail -n 3` for a decompression or module format error.

8. **Investigate.** Ask the package manager to verify the files of the kernel packages against their recorded checksums.

    ```bash
    dpkg -V "$PKG"
    dpkg -V "linux-image-$(uname -r)"
    ```

    ```{.output}
    ??5??????   /lib/modules/6.8.0-45-generic/kernel/drivers/net/dummy.ko.zst
    ```

    ::: explain
    **What just happened:** `dpkg -V` (verify) prints only files that differ from the package. The `5` in the third column means the MD5 checksum does not match: the file content changed. No output for `linux-image` means the kernel image itself is fine. On Rocky, `rpm -V kernel-core` does the same (`S.5....T.` means size, checksum, and time differ).
    :::

9. **Root cause.** A kernel module file on disk is corrupted.

10. **Fix.** Reinstall the package that owns the file; this rewrites all its files from a fresh download.

    ```bash
    sudo apt install --reinstall -y "$PKG"
    dpkg -V "$PKG"
    ```

11. **Verify.**

    ```bash
    sudo modprobe dummy && lsmod | grep dummy
    sudo modprobe -r dummy
    rm ~/labs/5.2/dummy-module.bak
    ```

12. **Know the other kernel corruption fixes:**
    - Broken initramfs: `sudo update-initramfs -u -k $(uname -r)` (Rocky: `sudo dracut -f`).
    - Broken or unbootable new kernel: at the GRUB menu choose **Advanced options for Ubuntu**, boot the previous kernel, then `sudo apt install --reinstall linux-image-<version>` or remove the bad one. List installed kernels with `ls /boot/vmlinuz-*` or `dpkg -l 'linux-image-*'`.
    - `/boot` full during an update: clean old kernels with `sudo apt autoremove --purge`, then `sudo dpkg --configure -a`.

13. **Prevent.** Keep at least two kernels installed, monitor free space on `/boot`, never interrupt package updates, and verify packages with `dpkg -V` / `rpm -Va` after disk problems.

::: checkpoint
**Checkpoint:** `journalctl --list-boots` shows the crashed boot, `dpkg -V "$PKG"` prints nothing, and `sudo modprobe dummy` works again.
:::

#### Task 9: Scenario 8: The network card does not work (missing or disabled driver)

A **driver** is kernel code, usually a loadable **kernel module**, that controls a device. A device without a driver is visible on the bus (`lspci`, `lsusb`) but does not work. Drivers can be missing (not installed), disabled (blacklisted), or failing (firmware missing).

1. **Explore** how drivers attach to devices on your VM.

    ```bash
    lspci -k | grep -A3 -i -E "ethernet|network"
    lsmod | head -n 5
    ```

    ```{.output}
    00:03.0 Ethernet controller: Red Hat, Inc. Virtio network device
            Subsystem: Red Hat, Inc. Virtio network device
            Kernel driver in use: virtio-pci
    Module                  Size  Used by
    ...
    ```

    ::: explain
    **What just happened:** `lspci -k` shows each PCI device and the **Kernel driver in use** plus the **Kernel modules** that could drive it. A device with no `Kernel driver in use` line has no working driver: that is the first clue for a missing driver. `lsmod` lists loaded modules. Your device names depend on the hypervisor (virtio, e1000, vmxnet3, hv_netvsc).
    :::

2. **Break it.** Disable the `dummy` driver the way an admin (or a hardening script) might.

    ```bash
    cat <<'EOF' | sudo tee /etc/modprobe.d/lab-disable-dummy.conf
    # Lab 5.2: disable the dummy driver
    blacklist dummy
    install dummy /bin/false
    EOF
    ```

3. **Symptom.** Try to create a dummy network interface (Lab 5.3 uses these).

    ```bash
    sudo ip link add lab0 type dummy
    sudo modprobe dummy
    ```

    ```{.output}
    Error: Unknown device type.
    modprobe: ERROR: ../libkmod/libkmod-module.c:1088 command_do() Error running install command '/bin/false' for module dummy: retcode 1
    modprobe: ERROR: could not insert 'dummy': Invalid argument
    ```

4. **Investigate.**

    ```bash
    lsmod | grep -w dummy; echo "loaded? exit=$?"
    modinfo dummy | head -n 4
    grep -rn dummy /etc/modprobe.d/ /lib/modprobe.d/ 2>/dev/null
    ```

    ```{.output}
    loaded? exit=1
    filename:       /lib/modules/6.8.0-45-generic/kernel/drivers/net/dummy.ko.zst
    alias:          rtnl-link-dummy
    description:    Dummy netdevice driver
    license:        GPL
    /etc/modprobe.d/lab-disable-dummy.conf:2:blacklist dummy
    /etc/modprobe.d/lab-disable-dummy.conf:3:install dummy /bin/false
    ```

    ::: explain
    **What just happened:** The module is not loaded, but `modinfo` proves it is installed, so it is **disabled**, not missing. The `grep` finds the configuration. `blacklist dummy` only stops *automatic* loading by alias (for example when `ip link` asks for `rtnl-link-dummy`); an explicit `modprobe dummy` would still work. `install dummy /bin/false` replaces loading with running `/bin/false`, which always fails, so the driver cannot load at all. If `modinfo` itself said `Module dummy not found`, the driver would be **missing** instead.
    :::

5. **Root cause.** A modprobe configuration file disables the driver.

6. **Fix.** Remove the file. If the driver is needed early at boot (storage, some network cards), also rebuild the initramfs, because it contains a copy of the modprobe configuration.

    ```bash
    sudo rm /etc/modprobe.d/lab-disable-dummy.conf
    sudo update-initramfs -u
    ```

7. **Verify.**

    ```bash
    sudo ip link add lab0 type dummy && ip -br link show lab0
    sudo ip link del lab0
    sudo modprobe -r dummy
    ```

8. **Missing drivers in real life.** If `modinfo` says the module is not found: on Ubuntu, many drivers live in `linux-modules-extra-$(uname -r)`; vendor drivers often come as DKMS packages that rebuild for each kernel (`dkms status`). If the driver loads but the device still fails, look for firmware errors: `sudo dmesg | grep -i firmware` (for example `failed to load ... firmware`), fixed by installing `linux-firmware`. After installing, load it with `sudo modprobe <name>`.

9. **Prevent.** Comment every blacklist with the reason, keep `linux-modules-extra` installed on hardware servers, and check `lspci -k` after kernel updates.

#### Task 10: Scenario 9: apt refuses to install anything (package dependency issues)

A **dependency** is another package a package needs to work. `apt` and `dnf` resolve dependencies automatically; the low-level tools `dpkg` and `rpm` do not. Installing a downloaded `.deb` with `dpkg -i` is the classic way to break this.

1. **Break it.** Build a small local package that depends on `sl` (a harmless joke program), make sure `sl` is not installed, then install the package with `dpkg`.

    ```bash
    cd ~/labs/5.2
    sudo apt purge -y sl 2>/dev/null
    mkdir -p labtool/DEBIAN labtool/usr/local/bin
    cat <<'EOF' > labtool/DEBIAN/control
    Package: labtool
    Version: 1.0
    Architecture: all
    Maintainer: Student <student@ubuntu-lab>
    Depends: sl
    Description: Lab 5.2 demo tool that needs the sl package
    EOF
    printf '#!/bin/sh\nexec /usr/games/sl "$@"\n' > labtool/usr/local/bin/labtool
    chmod 755 labtool/usr/local/bin/labtool
    dpkg-deb --build --root-owner-group labtool labtool_1.0_all.deb
    sudo dpkg -i labtool_1.0_all.deb
    ```

    ```{.output}
    dpkg-deb: building package 'labtool' in 'labtool_1.0_all.deb'.
    Selecting previously unselected package labtool.
    (Reading database ... 112233 files and directories currently installed.)
    Preparing to unpack labtool_1.0_all.deb ...
    Unpacking labtool (1.0) ...
    dpkg: dependency problems prevent configuration of labtool:
     labtool depends on sl; however:
      Package sl is not installed.

    dpkg: error processing package labtool (--install):
     dependency problems - leaving unconfigured
    Errors were encountered while processing:
     labtool
    ```

    ::: explain
    **What just happened:** A `.deb` is an archive of files plus a `DEBIAN/control` file with metadata such as `Depends:`. `dpkg-deb --build` packs the directory; `--root-owner-group` makes the files owned by root inside the package. `dpkg -i` unpacked the files but refused to **configure** the package because `sl` is missing, and `dpkg` never downloads dependencies itself.
    :::

2. **Symptom.** Now try to install anything else.

    ```bash
    sudo apt install -y tree
    ```

    ```{.output}
    You might want to run 'apt --fix-broken install' to correct these.
    The following packages have unmet dependencies:
     labtool : Depends: sl but it is not going to be installed
    E: Unmet dependencies. Try 'apt --fix-broken install' with no packages (or specify a solution).
    ```

3. **Investigate.**

    ```bash
    dpkg -l labtool | tail -n 1
    sudo dpkg --audit
    dpkg -I labtool_1.0_all.deb | grep Depends
    apt-cache policy sl
    ```

    ```{.output}
    iU  labtool        1.0          all          Lab 5.2 demo tool that needs the sl package
    The following packages have been unpacked but not yet configured.
    ...
     labtool              Lab 5.2 demo tool that needs the sl package
     Depends: sl
    sl:
      Installed: (none)
      Candidate: 5.02-1
    ```

    ::: explain
    **What just happened:** In `dpkg -l`, the first letter is the desired state (`i` = install) and the second is the actual state (`U` = unpacked, not configured); a healthy package shows `ii`. `dpkg --audit` lists half-installed packages. `dpkg -I` shows a package file's control data, and `apt-cache policy sl` shows that `sl` is available from the repositories (`Candidate: 5.02-1`), so apt can fix this.
    :::

4. **Root cause.** A package installed with `dpkg -i` has an unmet dependency, which blocks apt.

5. **Fix.**

    ```bash
    sudo apt --fix-broken install -y
    ```

    ```{.output}
    Correcting dependencies... Done
    The following NEW packages will be installed:
      sl
    ...
    Setting up sl (5.02-1) ...
    Setting up labtool (1.0) ...
    ```

    ::: explain
    **What just happened:** `apt --fix-broken install` (short form `apt -f install`) works out what is needed to satisfy all dependencies: here it installs `sl` and then configures `labtool`. Always read its plan before confirming: if a dependency does not exist in any repository, its "fix" is to **remove** the broken package instead. A related command, `sudo dpkg --configure -a`, finishes configuring packages left half-done by an interrupted install (power loss, closed SSH session).
    :::

6. **Verify.** `dpkg -l labtool | tail -n 1` starts with `ii`, and `sudo apt install -y tree` now works.

7. **Prevent.** Install local packages with apt, which resolves dependencies: `sudo apt install ./labtool_1.0_all.deb`. Do not mix repositories from different releases, and do not interrupt updates.

    ::: tip

Use `sudo dnf install ./pkg.rpm` to pull dependencies from repositories, `rpm -qpR pkg.rpm` to list what a package file requires, `dnf repoquery --requires <name>` for repository packages, and `sudo dnf check` to find broken dependencies on the system.
    :::

8. **Undo.**

    ```bash
    sudo apt purge -y labtool sl tree
    rm -rf ~/labs/5.2/labtool ~/labs/5.2/labtool_1.0_all.deb
    ```

#### Task 11: Scenario 10: A program crashes with "Segmentation fault"

A **segmentation fault** (segfault, signal `SIGSEGV`, number 11) happens when a program touches memory it is not allowed to: a NULL pointer, freed memory, or past the end of a buffer. The kernel kills the program and can save a **core dump**, a snapshot of its memory, for debugging.

1. **Prepare core dump collection.** `systemd-coredump` stores core dumps and adds the `coredumpctl` command.

    ```bash
    sudo apt install -y systemd-coredump
    cat /proc/sys/kernel/core_pattern
    ```

    ```{.output}
    |/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h ...
    ```

    ::: explain
    **What just happened:** `core_pattern` tells the kernel what to do with a crashing program's memory. A value starting with `|` means "pipe it to this program". If yours still shows `/usr/share/apport/apport`, Ubuntu's crash reporter has the hook: run `sudo systemctl stop apport` and `sudo sysctl -p /usr/lib/sysctl.d/50-coredump.conf`, then check again.
    :::

2. **Break it.** Write and compile a tiny C program with a bug.

    ```bash
    cd ~/labs/5.2
    cat <<'EOF' > crashme.c
    #include <stdio.h>
    int main(void) {
        int *p = NULL;                 /* pointer to address 0 */
        printf("writing through a NULL pointer...\n");
        *p = 42;                       /* invalid memory write */
        return 0;
    }
    EOF
    gcc -g -o crashme crashme.c
    ```

    ::: explain
    **What just happened:** `gcc -g` compiles with debugging symbols, so the debugger can show source line numbers. Line 5 writes to address 0, which is never mapped in a Linux process.
    :::

3. **Symptom.**

    ```bash
    ulimit -c unlimited
    ./crashme
    echo "exit code: $?"
    ```

    ```{.output}
    writing through a NULL pointer...
    Segmentation fault (core dumped)
    exit code: 139
    ```

    ::: explain
    **What just happened:** `ulimit -c unlimited` allows core dumps in this shell (the default limit of `0` tells systemd-coredump to log the crash but not keep the memory). The exit code `139` is 128 + 11: a process killed by a signal exits with 128 plus the signal number.
    :::

4. **Investigate.** First the kernel log, then the saved core dump.

    ```bash
    sudo dmesg | grep crashme | tail -n 1
    coredumpctl list crashme
    coredumpctl info crashme | grep -E "Signal|Executable|#0"
    ```

    ```{.output}
    crashme[5512]: segfault at 0 ip 00005616c4a2a16d sp 00007ffd2b1c0e40 error 6 in crashme[5616c4a2a000+1000] likely on CPU 0
    TIME                         PID  UID  GID SIG     COREFILE EXE
    Sat 2026-10-10 14:10:22 UTC 5512 1000 1000 SIGSEGV present  /home/student/labs/5.2/crashme
          Signal: 11 (SEGV)
      Executable: /home/student/labs/5.2/crashme
                    #0  0x00005616c4a2a16d main (crashme + 0x116d)
    ```

    ::: explain
    **What just happened:** The kernel line says `segfault at 0`: the bad address was 0, a NULL pointer. `ip` is the instruction pointer and `error 6` means a user-mode *write* to a page that is not present. `coredumpctl list` shows the stored dump (`COREFILE present`), and `coredumpctl info` shows the signal and a stack trace pointing at `main`.
    :::

5. **Test the hypothesis** in the debugger to find the exact line.

    ```bash
    coredumpctl debug crashme
    ```

    At the `(gdb)` prompt type `bt` (backtrace), then `quit`:

    ```{.output}
    Program terminated with signal SIGSEGV, Segmentation fault.
    #0  main () at crashme.c:5
    5           *p = 42;                       /* invalid memory write */
    (gdb) bt
    #0  main () at crashme.c:5
    ```

6. **Root cause.** A NULL pointer dereference on line 5 of the program.

7. **Fix** the code so the pointer points at real memory, then rebuild.

    ```bash
    sed -i 's|int \*p = NULL;.*|int value = 0; int *p = \&value;|' crashme.c
    gcc -g -o crashme crashme.c
    ```

8. **Verify.** `./crashme; echo "exit code: $?"` prints the message and `exit code: 0`.

9. **Prevent / real-world advice.** You usually cannot fix the code of a packaged program. If a packaged program segfaults: update it (`apt list --upgradable`), check its files with `dpkg -V package` (a corrupted library also causes segfaults), and send the core dump to the developer. If *many unrelated* programs segfault randomly, suspect hardware (RAM): check `journalctl -k` for machine check errors and run a memory test.

::: checkpoint
**Checkpoint:** `coredumpctl list crashme` shows a SIGSEGV entry, and the fixed program exits with code `0`.

#### Task 12: Scenario 11: Processes are "Killed" (OOM killer and memory leaks)

When Linux runs out of memory, the **OOM (out-of-memory) killer** picks a process (the one with the highest `oom_score`, usually the biggest) and kills it with `SIGKILL` to save the system. The victim prints just `Killed` and exits with code 137 (128 + 9). A **memory leak** is a program that keeps allocating memory and never frees it; given time, it triggers the OOM killer.

1. **Prepare** a small program that leaks memory on purpose.

    ```bash
    cat <<'EOF' > ~/labs/5.2/leak.py
    #!/usr/bin/env python3
    # Leaks STEP MB every DELAY seconds and never frees it.
    import sys, time
    step = int(sys.argv[1]) if len(sys.argv) > 1 else 5
    delay = float(sys.argv[2]) if len(sys.argv) > 2 else 1
    cache = []
    while True:
        cache.append(b"x" * (step * 1024 * 1024))   # kept forever: the leak
        print(f"holding {len(cache) * step} MB", flush=True)
        time.sleep(delay)
    EOF
    ```

2. **Break it (killed process).** Run the leak quickly inside a **cgroup** limited to 200 MB, so only this program is affected, never your whole VM.

    ```bash
    sudo systemd-run --scope -p MemoryMax=200M -p MemorySwapMax=0 \
        python3 ~/labs/5.2/leak.py 20 0.2
    echo "exit code: $?"
    ```

    ```{.output}
    Running as unit: run-r3c1e1a2b9f6d4c4f8d8b0b8f0f3e2a1d.scope; invocation ID: ...
    holding 20 MB
    holding 40 MB
    ...
    holding 180 MB
    Killed
    exit code: 137
    ```

    ::: explain
    **What just happened:** `systemd-run --scope` runs a command in a new transient cgroup. `-p MemoryMax=200M` caps its memory, and `-p MemorySwapMax=0` forbids swapping so the limit is hit quickly. When the program passed 200 MB, the kernel's OOM killer killed it inside that cgroup. Without the limit, it would eat all RAM and swap first, slowing the whole VM down before something (maybe something important) is killed.
    :::

3. **Investigate the kill.** The kernel always logs OOM kills.

    ```bash
    journalctl -k --since "10 minutes ago" | grep -i -E "out of memory|oom-kill|killed process"
    ```

    ```{.output}
    kernel: python3 invoked oom-killer: gfp_mask=0xcc0(GFP_KERNEL), order=0, oom_score_adj=0
    kernel: oom-kill:constraint=CONSTRAINT_MEMCG,nodemask=(null),cpuset=/,mems_allowed=0,oom_memcg=/system.slice/run-r3c1....scope,...
    kernel: Memory cgroup out of memory: Killed process 6120 (python3) total-vm:221464kB, anon-rss:203520kB, file-rss:2304kB, shmem-rss:0kB, UID:0 pgtables:480kB oom_score_adj:0
    ```

    ::: explain
    **What just happened:** `constraint=CONSTRAINT_MEMCG` says a cgroup limit was hit (a system-wide shortage would say `CONSTRAINT_NONE` and `Out of memory: Killed process ...`). `anon-rss` is the program's private memory at the moment it died. For a service, `systemctl status` would also show `Failed with result 'oom-kill'`. You can see any process's current score in `/proc/PID/oom_score` and bias it with `/proc/PID/oom_score_adj` (-1000 = never kill, 1000 = kill first).
    :::

4. **Break it (memory leak).** Now run the leak slowly in the background, as a real leaking service would, 2 MB per second.

    ```bash
    python3 ~/labs/5.2/leak.py 2 1 > /dev/null &
    LEAKPID=$!
    ```

5. **Symptom.** Nothing fails yet. Free memory just keeps shrinking. Watch the process's memory over time.

    ```bash
    for i in 1 2 3 4; do ps -o pid,rss,vsz,etime,cmd -p "$LEAKPID" | tail -n 1; sleep 5; done
    ```

    ```{.output}
     6301 13420 25100       00:04 python3 /home/student/labs/5.2/leak.py 2 1
     6301 23664 35344       00:09 python3 /home/student/labs/5.2/leak.py 2 1
     6301 33908 45588       00:14 python3 /home/student/labs/5.2/leak.py 2 1
     6301 44152 55832       00:19 python3 /home/student/labs/5.2/leak.py 2 1
    ```

    ::: explain
    **What just happened:** `ps -o` picks columns: `rss` (resident set size, the physical RAM in KB actually used), `vsz` (virtual size, everything mapped), and `etime` (elapsed time). RSS climbs by about 10 MB every 5 seconds and never levels off. A healthy program grows at start-up and then stays roughly flat; steady growth over hours or days is the signature of a leak.
    :::

6. **Investigate** with more memory tools.

    ```bash
    grep -E "VmRSS|VmHWM" /proc/$LEAKPID/status
    pmap -x $LEAKPID | tail -n 1
    smem -k -P leak.py
    free -h
    ```

    ::: explain
    **What just happened:** `/proc/PID/status` shows `VmRSS` (current RAM) and `VmHWM` (high-water mark, the peak). `pmap -x` lists every memory mapping; the last line totals them, and a growing `[ anon ]` (heap) region points to a leak. `smem` adds **PSS** (proportional set size), which splits shared memory fairly between processes, a better "real cost" number. `free -h` shows the system view; watch the `available` column fall.
    :::

7. **Root cause.** The program appends data to a list it never clears: a memory leak.

8. **Fix.** Short term: restart the leaking process (memory is returned instantly). Long term: fix the code, and protect the system with a memory limit and automatic restart so a leak cannot take the server down.

    ```bash
    kill $LEAKPID
    free -h
    ```

    ::: explain
    **What just happened:** All of the process's memory is freed when it exits. For a real service, add `MemoryMax=500M` and `Restart=on-failure` with `sudo systemctl edit <service>`; the service is then killed and restarted cleanly at the limit instead of exhausting the whole machine.
    :::

9. **Verify.** `pgrep -f leak.py` prints nothing and `free -h` shows `available` back where it started.

10. **Prevent.** Monitor memory trends per process (not just totals), set cgroup limits on services, and report leaks to the developer with the data you collected.

::: checkpoint
**Checkpoint:** `journalctl -k | grep -i "killed process"` shows the OOM kill of `python3`, and you watched RSS grow steadily with `ps -o rss`.
:::

#### Task 13: Scenario 12: "command not found" (PATH misconfiguration)

The **PATH** variable is a colon-separated list of directories the shell searches, in order, when you type a command name without a `/`. A broken PATH makes ordinary commands "disappear"; a PATH in the wrong order can run the wrong program.

1. **Break it.** Simulate a careless edit of `~/.bashrc` (for example, someone tried to add a directory and overwrote PATH instead of appending to it).

    ```bash
    cp ~/.bashrc ~/labs/5.2/bashrc.bak
    cat <<'EOF' >> ~/.bashrc
    # lab 5.2 break: PATH overwritten instead of appended
    export PATH=/usr/local/sbin:/usr/locall/bin:/home/student/bin
    EOF
    source ~/.bashrc
    ```

2. **Symptom.**

    ```bash
    ls
    ```

    ```{.output}
    Command 'ls' is available in the following places
     * /bin/ls
     * /usr/bin/ls
    The command could not be located because '/bin:/usr/bin' is not included in the PATH environment variable.
    ls: command not found
    ```

3. **Investigate.** Shell built-ins like `echo` and `type` still work because they are part of bash itself.

    ```bash
    echo "$PATH"
    type ls
    /usr/bin/grep -n PATH ~/.bashrc ~/.profile /etc/environment
    ```

    ```{.output}
    /usr/local/sbin:/usr/locall/bin:/home/student/bin
    -bash: type: ls: not found
    /home/student/.bashrc:118:export PATH=/usr/local/sbin:/usr/locall/bin:/home/student/bin
    /home/student/.profile:22:    PATH="$HOME/bin:$PATH"
    /etc/environment:1:PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin"
    ```

    ::: explain
    **What just happened:** `echo $PATH` shows that `/usr/bin` and `/bin` are missing and that `/usr/locall/bin` is a typo. Running a program by its **absolute path** (`/usr/bin/grep`) always works, because the shell does not search PATH when the name contains `/`. `grep -n` shows where PATH is set: the system default in `/etc/environment`, additions in `~/.profile`, and the bad line in `~/.bashrc`.
    :::

4. **Root cause.** `~/.bashrc` replaces PATH with a short, misspelled list instead of appending to it.

5. **Fix.** Repair the current shell first, then the file.

    ```bash
    export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
    cp ~/labs/5.2/bashrc.bak ~/.bashrc
    ```

    ::: explain
    **What just happened:** The first line restores a working PATH for this shell only. Restoring the backup fixes all future shells. The correct way to *add* a directory is to keep the old value: `export PATH="$PATH:/opt/tool/bin"`.
    :::

6. **Verify.** Open a fresh login shell and check: `bash -l -c 'echo $PATH; type ls'` shows the full PATH and `ls is aliased to ...` or `/usr/bin/ls`.

7. **The other PATH problem: wrong order.** Directories earlier in PATH win. Create a fake `top` in `~/bin` and put `~/bin` first:

    ```bash
    mkdir -p ~/bin
    printf '#!/bin/sh\necho "this is NOT the real top"\n' > ~/bin/top
    chmod 755 ~/bin/top
    export PATH="$HOME/bin:$PATH"
    hash -r
    top
    type -a top
    ```

    ```{.output}
    this is NOT the real top
    top is /home/student/bin/top
    top is /usr/bin/top
    ```

    ::: explain
    **What just happened:** `type -a` lists every match in PATH order, so you can see which one runs. `hash -r` clears bash's memory of where it found commands earlier. This is also an attack technique: a writable directory early in PATH lets someone plant a fake command. That is why `sudo` ignores your PATH and uses `secure_path` from `/etc/sudoers`, and why you should never put `.` (the current directory) in PATH.
    :::

8. **Undo.**

    ```bash
    rm -f ~/bin/top ~/labs/5.2/bashrc.bak
    rmdir ~/bin 2>/dev/null
    export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
    hash -r
    ```

9. **Prevent.** Always append (`PATH="$PATH:/new"`), test edits with `bash -l -c 'echo $PATH'` before logging out, and keep a second SSH session open while editing login files.

::: checkpoint
**Checkpoint:** `type -a top` shows only `/usr/bin/top`, and `tail -n 2 ~/.bashrc` no longer contains the `lab 5.2 break` line.

#### Task 14: Scenario 13: A service will not start (systemd unit failure)

1. **Break it.** Create a small app and a unit file with a typo in `ExecStart`.

    ```bash
    cat <<'EOF' | sudo tee /usr/local/bin/labapp > /dev/null
    #!/bin/bash
    echo "labapp started with options: $*"
    exec sleep infinity
    EOF
    sudo chmod 755 /usr/local/bin/labapp
    cat <<'EOF' | sudo tee /etc/systemd/system/labapp.service
    [Unit]
    Description=Lab 5.2 demo application

    [Service]
    ExecStart=/usr/local/bin/labap --port 8080
    Restart=on-failure

    [Install]
    WantedBy=multi-user.target
    EOF
    sudo systemctl daemon-reload
    sudo systemctl enable --now labapp
    ```

2. **Symptom.** The command returns without error, but the app is not running.

    ```bash
    systemctl status labapp --no-pager
    systemctl --failed
    ```

    ```{.output}
    x labapp.service - Lab 5.2 demo application
         Loaded: loaded (/etc/systemd/system/labapp.service; enabled; preset: enabled)
         Active: failed (Result: exit-code) since Sat 2026-10-10 14:40:02 UTC; 3s ago
        Process: 7012 ExecStart=/usr/local/bin/labap --port 8080 (code=exited, status=203/EXEC)
    ```

    ::: explain
    **What just happened:** `Active: failed` and `status=203/EXEC` mean systemd could not execute the program at all. 3. **Investigate.**

    ```bash
    journalctl -xeu labapp --no-pager | grep -i -E "exec|locate" | head -n 3
    systemctl cat labapp
    systemd-analyze verify /etc/systemd/system/labapp.service
    ```

    ```{.output}
    labapp.service: Unable to locate executable '/usr/local/bin/labap': No such file or directory
    labapp.service: Failed at step EXEC spawning /usr/local/bin/labap: No such file or directory
    ...
    labapp.service: Command /usr/local/bin/labap is not executable: No such file or directory
    ```

    ::: explain
    **What just happened:** `journalctl -u labapp` shows the unit's logs; `-x` adds explanations and `-e` jumps to the end. The message names the missing file. `systemctl cat` prints the unit file systemd is actually using (including any drop-in overrides), and `systemd-analyze verify` checks a unit file for errors without starting it, which is worth doing before every `enable --now`.
    :::

4. **Root cause.** A typo in `ExecStart` (`labap` instead of `labapp`).

5. **Fix.** Correct the file, reload systemd's copy of it, clear the failed state, and start it.

    ```bash
    sudo sed -i 's|/usr/local/bin/labap |/usr/local/bin/labapp |' /etc/systemd/system/labapp.service
    sudo systemctl daemon-reload
    sudo systemctl reset-failed labapp
    sudo systemctl restart labapp
    ```

    ::: explain
    **What just happened:** systemd keeps unit files in memory; after editing one on disk you **must** run `daemon-reload` or systemd keeps using the old version (`systemctl status` warns "unit file changed on disk"). `reset-failed` clears the failed state and the start-limit counter so the unit can start again.
    :::

6. **Verify.**

    ```bash
    systemctl is-active labapp
    journalctl -u labapp -n 1 --no-pager
    ```

    ```{.output}
    active
    Oct 10 14:45:10 ubuntu-lab labapp[7101]: labapp started with options: --port 8080
    ```

7. **Prevent.** Run `systemd-analyze verify` after writing unit files, use `sudo systemctl edit name` (it creates drop-in overrides and reloads automatically), and check `systemctl --failed` after every change and every boot.

8. **Undo.**

    ```bash
    sudo systemctl disable --now labapp
    sudo rm -f /etc/systemd/system/labapp.service /usr/local/bin/labapp
    sudo systemctl daemon-reload
    ```

::: checkpoint
**Checkpoint:** You saw `status=203/EXEC`, found the typo with `journalctl -xeu`, and the service reached `active` after `daemon-reload`.

#### Task 15: Scenario 14: A program stops responding (unresponsive process)

A process can look "hung" for different reasons, and the fix depends on its **state**, shown in the `STAT` column of `ps`: `R` running, `S` sleeping (waiting for something, interruptible), `D` uninterruptible sleep (waiting on disk or network I/O, cannot be killed until the I/O finishes), `T` stopped, `Z` zombie (finished, waiting for its parent to collect it).

1. **Break it.** Start a "ticker" that writes the time every second, a reader that waits on a named pipe, and then stop the ticker.

    ```bash
    cd ~/labs/5.2
    bash -c 'while true; do date >> ~/labs/5.2/ticker.log; sleep 1; done' &
    TPID=$!
    mkfifo ~/labs/5.2/jobqueue
    cat ~/labs/5.2/jobqueue &
    RPID=$!
    sleep 3; kill -STOP $TPID
    ```

    ::: explain
    **What just happened:** The ticker appends a line every second. `mkfifo` creates a **named pipe**: a reader blocks until a writer opens the other end, like an application waiting for a job that never arrives. `kill -STOP` sends `SIGSTOP`, which freezes a process; it cannot be caught or ignored (pressing `Ctrl+Z` in a terminal sends the similar `SIGTSTP`).
    :::

2. **Symptom.** Neither process does anything: `ticker.log` stopped growing, and the reader never prints.

    ```bash
    tail -n 1 ticker.log; sleep 3; tail -n 1 ticker.log
    ```

3. **Investigate the states.**

    ```bash
    ps -o pid,stat,wchan:20,etime,cmd -p $TPID,$RPID
    grep State /proc/$TPID/status
    ```

    ```{.output}
        PID STAT WCHAN                    ELAPSED CMD
       7310 T    do_signal_stop             00:15 bash -c while true; do date >> ...
       7313 S    fifo_open                  00:12 cat /home/student/labs/5.2/jobqueue
    State:  T (stopped)
    ```

    ::: explain
    **What just happened:** `STAT T` means the ticker is stopped. `WCHAN` (wait channel) is the kernel function a sleeping process is waiting in: the reader is in a FIFO function (`fifo_open` here; some kernels show `wait_for_partner`), waiting for someone to open the pipe for writing. `/proc/PID/status` shows the same state in words.
    :::

4. **Test the hypothesis with strace.** `strace -p` attaches to a running process and shows the system call it is stuck in. Ubuntu restricts attaching to other processes, so use `sudo`. Press `Ctrl+C` to detach.

    ```bash
    sudo strace -p $RPID
    ```

    ```{.output}
    strace: Process 7313 attached
    openat(AT_FDCWD, "/home/student/labs/5.2/jobqueue", O_RDONLY
    ```

    ::: explain
    **What just happened:** The unfinished `openat(... O_RDONLY` line shows the process is waiting to open the pipe for reading. On real servers the same technique shows a process stuck in `read()` on a network socket, `futex()` (waiting on a lock), or `connect()` to a server that does not answer, which tells you where to look next.
    :::

5. **Root cause.** The ticker was stopped by a signal; the reader is waiting for input that never comes.

6. **Fix.**

    ```bash
    kill -CONT $TPID
    echo "job 1" > ~/labs/5.2/jobqueue
    ```

    ```{.output}
    job 1
    ```

    ::: explain
    **What just happened:** `SIGCONT` resumes a stopped process. Writing to the pipe gives the reader its input, so `cat` prints `job 1` and exits. If a process is truly stuck and must go, send `SIGTERM` first (`kill PID`, lets it clean up), and only if that fails `SIGKILL` (`kill -9 PID`). A process in `D` state ignores even `SIGKILL` until its I/O completes; fix the storage or NFS server it is waiting for (Lab 5.5 shows this).
    :::

7. **Verify.** `tail -n 1 ticker.log` shows the current time again, and `ps -p $RPID` shows the reader is gone.

8. **Undo.**

    ```bash
    kill $TPID
    rm -f ~/labs/5.2/ticker.log ~/labs/5.2/jobqueue
    ```

9. **Prevent.** Use timeouts in scripts and applications (`timeout 30 command`), monitor that work is actually progressing (a health check, Lab 5.1), and do not leave jobs suspended with `Ctrl+Z`.

::: checkpoint
**Checkpoint:** You saw `STAT T` and `STAT S` with `fifo_open`, used `strace -p` to see the blocked system call, and resumed the stopped process with `kill -CONT`.
:::

#### Task 16: Scenario 15: Disk errors (device failure)

Real disks fail by returning read errors, dropping off the bus, or slowly accumulating bad sectors. You will simulate each safely.

**Part A: a disk with bad sectors (device-mapper error target)**

1. **Break it.** **Device-mapper** builds virtual block devices from a table. Make a 100 MB device where a small range of sectors always returns an I/O error.

    ```bash
    cd ~/labs/5.2
    truncate -s 100M dev.img
    LOOP=$(sudo losetup --find --show dev.img); echo "$LOOP"
    SECTORS=$(sudo blockdev --getsz "$LOOP"); echo "$SECTORS sectors"
    cat <<EOF | sudo dmsetup create flaky
    0 100000 linear $LOOP 0
    100000 8 error
    100008 $((SECTORS - 100008)) linear $LOOP 100008
    EOF
    ```

    ::: explain
    **What just happened:** `losetup --find --show` attaches the file to a free loop device and prints its name. `blockdev --getsz` prints the size in 512-byte sectors (204800). This heredoc has **no quotes** around `EOF`, so the shell fills in `$LOOP` and the arithmetic. Each table line is *start length target*: sectors 0 to 99999 map straight to the loop device, sectors 100000 to 100007 use the `error` target (every access fails), and the rest map normally. The new device is `/dev/mapper/flaky`.
    :::

2. **Symptom.**

    ```bash
    sudo dd if=/dev/mapper/flaky of=/dev/null bs=4k status=none; echo "exit: $?"
    ```

    ```{.output}
    dd: error reading '/dev/mapper/flaky': Input/output error
    exit: 1
    ```

3. **Investigate.**

    ```bash
    sudo dmesg -T | grep -i -E "i/o error|dm-" | tail -n 3
    sudo badblocks -sv /dev/mapper/flaky
    ```

    ```{.output}
    [Sat Oct 10 15:02:11 2026] Buffer I/O error on dev dm-0, logical block 12500, async page read
    Checking blocks 0 to 102399
    Checking for bad blocks (read-only test): 50000
    50001
    50002
    50003
    done
    Pass completed, 4 bad blocks found. (4/0/0 errors)
    ```

    ::: explain
    **What just happened:** The kernel logged a buffer I/O error on `dm-0` (your flaky device). `badblocks -sv` reads every block (read-only test by default) with **s**how-progress and **v**erbose output. It uses 1 KB blocks, so 8 bad 512-byte sectors starting at sector 100000 are 1 KB blocks 50000 to 50003. On a real disk you would also see the device name (`sdb`) and SCSI or ATA error lines.
    :::

4. **Root cause and fix.** Bad sectors on the "disk". A disk that has started returning read errors is failing: copy the data off (`ddrescue` copies around bad areas) and replace it. Remove the simulation:

    ```bash
    sudo dmsetup remove flaky
    sudo losetup -d "$LOOP"
    rm -f dev.img
    ```

**Part B: a failed disk in a RAID 1 mirror (mdadm)**

5. **Break it.** Build a RAID 1 array from two loop devices, then mark one as failed.

    ```bash
    cd ~/labs/5.2
    truncate -s 200M r1.img r2.img r3.img
    L1=$(sudo losetup --find --show r1.img)
    L2=$(sudo losetup --find --show r2.img)
    L3=$(sudo losetup --find --show r3.img)
    yes | sudo mdadm --create /dev/md0 --level=1 --raid-devices=2 "$L1" "$L2"
    sudo mdadm --wait /dev/md0
    sudo mdadm --manage /dev/md0 --fail "$L2"
    ```

    ::: explain
    **What just happened:** `mdadm --create` builds `/dev/md0` as a mirror (`--level=1`) of two devices; `yes |` answers its "Continue creating array?" question. `--wait` waits until the initial sync finishes. `--fail` marks a member as failed, exactly what the kernel does on its own when a member disk returns errors.
    :::

6. **Symptom and investigation.**

    ```bash
    cat /proc/mdstat
    sudo mdadm --detail /dev/md0 | grep -E "State :|Failed Devices|faulty"
    journalctl -k -n 5 --no-pager | grep md
    ```

    ```{.output}
    md0 : active raid1 loop9[1](F) loop8[0]
          203776 blocks super 1.2 [2/1] [U_]
            State : clean, degraded
       Failed Devices : 1
           1       7        9        -      faulty   /dev/loop9
    kernel: md/raid1:md0: Disk failure on loop9, disabling device.
                          md/raid1:md0: Operation continuing on 1 devices.
    ```

    ::: explain
    **What just happened:** In `/proc/mdstat`, `(F)` marks the failed member, `[2/1]` means 2 devices expected and 1 working, and `[U_]` shows one up (`U`) and one missing (`_`). `mdadm --detail` says `degraded`: the data is still available, but one more failure would lose it. The `mdadm` monitor service can email these events if `MAILADDR` is set in `/etc/mdadm/mdadm.conf`.
    :::

7. **Fix.** Remove the failed member, add the replacement, and watch it rebuild.

    ```bash
    sudo mdadm --manage /dev/md0 --remove "$L2"
    sudo mdadm --manage /dev/md0 --add "$L3"
    sudo mdadm --wait /dev/md0; cat /proc/mdstat
    ```

    ```{.output}
    md0 : active raid1 loop10[2] loop8[0]
          203776 blocks super 1.2 [2/2] [UU]
    ```

8. **Undo.**

    ```bash
    sudo mdadm --stop /dev/md0
    sudo mdadm --zero-superblock "$L1" "$L2" "$L3"
    sudo losetup -d "$L1" "$L2" "$L3"
    rm -f ~/labs/5.2/r1.img ~/labs/5.2/r2.img ~/labs/5.2/r3.img
    ```

**Part C: a disk disappears, and SMART health (explore/simulate)**

::: tip
**Explore/simulate:** Removing a disk from the SCSI layer imitates a disk dropping off the bus. It only works if your extra disks are SCSI/SATA (`sdX`); skip it for `vdX` or NVMe disks. SMART data is usually not available on virtual disks, so you read the tool's output and a realistic sample instead.
:::

9. Confirm the transport type and pick an unused extra disk (here `/dev/sde`; substitute yours, and make sure it is not mounted).

    ```bash
    lsblk -S -o NAME,HCTL,TRAN,MODEL
    findmnt -S /dev/sde
    ```

10. Make it vanish, look at the evidence, and bring it back with a rescan.

    ```bash
    echo 1 | sudo tee /sys/block/sde/device/delete
    lsblk | grep sde; sudo dmesg | tail -n 2
    for h in /sys/class/scsi_host/host*/scan; do echo '- - -' | sudo tee "$h" > /dev/null; done
    lsblk | grep sd
    ```

    ::: explain
    **What just happened:** Writing `1` to `device/delete` removes the disk from the kernel, as if it failed or was unplugged; `lsblk` no longer shows it and `dmesg` logs `Synchronizing SCSI cache`. Writing `- - -` (all channels, targets, LUNs) to each SCSI host's `scan` file asks the controller to look for disks again, so it comes back (possibly with a different name). Admins use the rescan after hot-adding disks.
    :::

11. Check SMART. On a VM it usually reports no SMART support, which is itself useful to recognize.

    ```bash
    sudo smartctl -i -H /dev/sda
    ```

    ```{.output}
    SMART support is: Unavailable - device lacks SMART capability.
    ```

    On a physical failing disk, `sudo smartctl -a /dev/sda` shows lines like these. The attributes to watch are reallocated, pending, and uncorrectable sectors; any non-zero and rising value means "replace soon".

    ```{.output}
    SMART overall-health self-assessment test result: FAILED!
    ID# ATTRIBUTE_NAME          FLAG     VALUE WORST THRESH TYPE      RAW_VALUE
      5 Reallocated_Sector_Ct   0x0033   010   010   036    Pre-fail  1984
    197 Current_Pending_Sector  0x0012   100   100   000    Old_age   312
    198 Offline_Uncorrectable   0x0010   100   100   000    Old_age   87
    ```

12. **Prevent.** Use RAID or replication for important data, run the `smartd` service to alert on SMART changes, watch `dmesg` and `/proc/mdstat`, and keep spare disks.

**Checkpoint:** `badblocks` found 4 bad blocks on the flaky device, `/proc/mdstat` showed `[U_]` and then `[UU]` after the rebuild, and `cat /proc/mdstat` now lists no `md0`.

### Exam corner

- Method: identify symptoms, gather data, hypothesize, test, fix, verify, document. Ask "what changed?"
- "No space left on device" with free space in `df -h` means **inode exhaustion** (`df -i`). `df` larger than `du` means a **deleted-but-open file** (`lsof +L1`); restart the process or truncate instead of `rm`.
- Error messages: "Permission denied" = permissions/ACL; "Operation not permitted" = immutable attribute (`lsattr`, `chattr -i`); "Read-only file system" = `ro` mount or kernel remount after errors (`dmesg`); "Disk quota exceeded" = `quota`, `repquota`, `setquota`, `edquota`.
- "Bad superblock": `e2fsck -b 32768 /dev/sdX1` (find backups with `mke2fs -n` or `dumpe2fs`); never `fsck` a mounted filesystem; XFS uses `xfs_repair`. `fsck` cannot detect corrupted file contents.
- Bad `/etc/fstab` = emergency mode. Fix: `mount -o remount,rw /`, edit fstab, `systemctl daemon-reload`, `mount -a`. Prevent with `findmnt --verify`, `mount -a`, and `nofail`.
- GRUB: edit `/etc/default/grub`, then `update-grub` (Ubuntu) or `grub2-mkconfig -o /boot/grub2/grub.cfg` (Rocky). Press `e` at the menu for one-time edits; `Ctrl+X` boots. `(initramfs)` prompt = root device not found; `grub rescue>` = GRUB cannot find its files.
- Kernel panic: read the console; `kernel.panic` sets auto-reboot seconds; kdump saves crash dumps to `/var/crash`; `journalctl -b -1` shows the previous boot. Kernel corruption: boot an older kernel from **Advanced options**, `dpkg -V`/`rpm -V`, reinstall the kernel package, `update-initramfs -u` / `dracut -f`.
- Drivers: `lspci -k`, `lsmod`, `modinfo`, `modprobe`; disabled via `blacklist` or `install <mod> /bin/false` in `/etc/modprobe.d/`; missing ones in `linux-modules-extra`, DKMS, or `linux-firmware`.
- Dependencies: `dpkg -i` does not resolve them (`iU` state); fix with `apt --fix-broken install` / `apt -f install`, `dpkg --configure -a`; Rocky: `dnf install ./file.rpm`, `rpm -qpR`.
- Segfault = signal 11, exit code 139; `dmesg` shows `segfault at`; `coredumpctl list/info/debug`. OOM kill = `SIGKILL` (9), exit code 137, `journalctl -k | grep -i "killed process"`; limit with `MemoryMax=`.
- Memory leak = RSS growing steadily (`ps -o rss`, `pmap -x`, `smem`, `/proc/PID/status`).
- Unit failure: `systemctl status`, `journalctl -xeu unit`, `status=203/EXEC` = bad `ExecStart` path; always `daemon-reload` after edits; `reset-failed` after start-limit hits.
- Process states: `R`, `S`, `D` (uninterruptible, unkillable), `T` (stopped, `kill -CONT`), `Z` (zombie). `strace -p PID` shows where it waits.

2. A process still has the deleted file open, so the space is not freed; `lsof +L1` lists it, and restarting that process (or truncating the file through `/proc/PID/fd`) releases the space.
3. `sudo findmnt --verify` and `sudo mount -a`; both report bad UUIDs, devices, or mount points without rebooting.
4. **B.** Exit code 139 is 128 + signal 11 (SIGSEGV), and `segfault at 0` means it accessed address 0, a NULL pointer.
5. The `ExecStart=` path: 203/EXEC means systemd could not execute the program (missing file, typo, or not executable). Confirm with `journalctl -xeu app`.
6. `D` is uninterruptible sleep: the process is waiting inside the kernel for I/O and cannot handle signals until it completes. Check the storage or NFS server it is waiting on (`dmesg`, `iostat`, mount status).
