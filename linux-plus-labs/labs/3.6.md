## Lab 3.6: Compliance, Auditing, and Detection {#lab-3-6}

::: labinfo
**Objective:** 3.6 Explain the importance of compliance and audit procedures.\
**Domain:** 3.0 Security (18% of the exam)\
**Time:** about 180 minutes (several scans run for a few minutes each)\
**VM:** ubuntu-lab and rocky-lab\
**Snapshot first:** Yes. This lab destroys data on an extra disk, plants fake "attacker" artifacts, and changes login banners.
:::

Hardening a system once is not enough. You must keep checking it: scan for malware, hunt for signs of an intruder, find known vulnerabilities, compare the system with a security standard, detect changed files, and prove that the software you install is genuine. When hardware leaves your hands, you must destroy the data on it. This lab walks through each of these audit and compliance jobs with the real tools, so you can explain on the exam what each one is for and when you would use it.

### What you'll practice

- Detection and response: Anti-malware (ClamAV with the EICAR test file), Indicators of compromise (IoC)
- Vulnerability scanning: CVEs, CVSS, Backporting patches, Service misconfigurations; Tools: Port scanners (`nmap`), Protocol analyzer (`tcpdump`, `tshark`)
- Standards and audit: OpenSCAP, CIS Benchmarks
- File integrity: AIDE, rkhunter, Signed package verification, Installed file verification (`debsums`, `dpkg --verify`, `rpm -V`)
- Secure data destruction: `shred`, `badblocks -w`, `dd if=/dev/urandom`, Cryptographic destruction
- Software supply chain (the xz backdoor, verifying downloads, pinning, SBOMs)
- Security banners: `/etc/issue`, `/etc/issue.net`, `/etc/motd`

### How it works

**Why compliance and audit matter.** Many organizations must follow rules: PCI DSS for card payments, HIPAA for health data, government baselines like DISA STIGs. Auditors ask you to *prove* that systems are configured correctly and watched. Even without a law, regular audits catch mistakes and intruders early. Think of it like a building: locks (hardening) are not enough without cameras (detection), inspections (audits), and a way to shred old documents (data destruction).

**Detection and response.**

- **Anti-malware** software compares files against signatures of known malware. On Linux the free standard is **ClamAV**. Linux servers are often scanned because they store or pass on files (mail servers, file shares) that Windows clients will open.
- **Indicators of compromise (IoCs)** are clues that an attacker has been on a system: unknown listening ports, new user accounts, strange cron jobs, unexpected SUID programs, logins from odd places at odd times, outbound connections to unknown addresses, processes using 100% CPU (crypto miners), and changed system binaries.

**Vulnerability scanning.**

- A **CVE** (Common Vulnerabilities and Exposures) is a unique ID for one publicly known vulnerability, for example `CVE-2024-6387` (the "regreSSHion" bug in OpenSSH).
- **CVSS** (Common Vulnerability Scoring System) rates severity from 0.0 to 10.0. Bands: None 0.0, Low 0.1 to 3.9, Medium 4.0 to 6.9, High 7.0 to 8.9, Critical 9.0 to 10.0. The score comes from a *vector* such as `AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H`: attack vector Network, attack complexity High, no privileges or user interaction needed, high impact on confidentiality, integrity, and availability. That vector scores 8.1 (High).
- **Backporting** means the distribution takes only the security fix from a newer upstream version and applies it to the older version it ships. The version number stays "old", but the bug is fixed. This confuses scanners that only compare version numbers, so you must check the distribution's changelog or security notices.
- **Service misconfigurations** are mistakes in settings rather than bugs in code: a database listening on all interfaces with no password, directory listing turned on, debug servers left running, root SSH logins allowed.
- A **port scanner** (`nmap`) finds which ports are open and which software versions answer. A **protocol analyzer** (`tcpdump`, Wireshark, `tshark`) captures and decodes network traffic, so you can see whether passwords travel in cleartext. Full vulnerability scanners such as OpenVAS/Greenbone, Nessus, or Trivy (for containers) combine these ideas with a CVE database.

**Standards and audit.** The **CIS Benchmarks** from the Center for Internet Security are free, detailed hardening guides for each OS ("Ensure /tmp is a separate partition", "Ensure SSH root login is disabled"). Level 1 is a practical baseline; Level 2 is stricter. **OpenSCAP** is a scanner that reads machine-readable security content (SCAP, the Security Content Automation Protocol) and checks a system against a profile such as CIS Level 1, then produces an HTML report.

**File integrity.** An attacker who gets root often replaces programs like `ls` or `ps` with versions that hide their files (a *rootkit*). File integrity tools catch this:

```{.diagram}
 Day 0 (known good)            Later
 +------------------+         +------------------+
 | file -> SHA-256  |  compare| file -> SHA-256  |
 | /etc/hosts  a1b2 | ------> | /etc/hosts  9f3c |  <-- CHANGED
 | /bin/ls     77de |         | /bin/ls     77de |
 +------------------+         +------------------+
   baseline database            current system
```

- **AIDE** (Advanced Intrusion Detection Environment) builds a database of file hashes and attributes, then reports differences.
- **rkhunter** (Rootkit Hunter) looks for known rootkit files, suspicious settings, and changed system binaries.
- The **package manager** already knows the correct hash of every file it installed. `debsums` and `dpkg --verify` (Debian/Ubuntu) and `rpm -V` (RHEL/Rocky) compare installed files with those hashes. **Signed packages** prove that packages came from the distribution: `apt` checks a GPG-signed repository index, and `dnf`/`rpm` check a GPG signature on every package.

**Secure data destruction.** Deleting a file only removes its name; the data stays on the disk. Overwriting tools (`shred`, `dd`, `badblocks -w`) write over the data. On SSDs and copy-on-write filesystems overwriting is not reliable, because the drive may write new data to a different physical place. That is why **cryptographic destruction** (also called crypto-erase) matters: if data was always encrypted, destroying the key makes it unreadable instantly.

**Software supply chain.** You run code written by thousands of people. An attacker who sneaks malicious code into a library, a build server, or a download site can reach every user downstream. Defenses: install only from trusted, signed sources, verify checksums and signatures of downloads, pin versions, and keep a software bill of materials (SBOM).

**Security banners** are legal and informational messages: `/etc/issue` is shown before a local console login, `/etc/issue.net` before a network login (when SSH is configured to show it), and `/etc/motd` (message of the day) after a successful login.

### Tasks

#### Task 1: Scan for malware with ClamAV

1. Create the working directory and install ClamAV:

    ```bash
    mkdir -p ~/labs/3.6 && cd ~/labs/3.6
    sudo apt update
    sudo apt install -y clamav clamav-freshclam
    ```

    ::: explain
    **What just happened:** `clamav` provides the scanner `clamscan`. `clamav-freshclam` provides `freshclam`, the signature updater, plus a service that runs it automatically. Right after installation the service starts downloading the signature databases (a few hundred MB).
    :::

2. Make sure the signature databases have downloaded:

    ```bash
    systemctl status clamav-freshclam --no-pager | head -5
    ls -lh /var/lib/clamav/
    ```

    ```{.output}
    -rw-r--r-- 1 clamav clamav 276K Oct 10 16:02 bytecode.cvd
    -rw-r--r-- 1 clamav clamav  60M Oct 10 16:02 daily.cvd
    -rw-r--r-- 1 clamav clamav 163M Oct 10 16:03 main.cvd
    ```

    ::: explain
    **What just happened:** The `.cvd` (or `.cld`) files are the signature databases: `main` (the big base set), `daily` (new signatures, updated several times a day), and `bytecode` (detection programs). If the folder is still empty after a few minutes, run the updater by hand. It cannot run while the service holds its lock, so stop the service first: `sudo systemctl stop clamav-freshclam && sudo freshclam && sudo systemctl start clamav-freshclam`.
    :::

3. Create the EICAR test file. EICAR is a harmless 68-byte string that every anti-malware product agrees to detect as if it were a virus, so you can test scanners safely:

    ```bash
    printf '%s' 'X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*' > eicar.com
    echo "just a normal file" > normal.txt
    wc -c eicar.com
    ```

    ```{.output}
    68 eicar.com
    ```

    ::: explain
    **What just happened:** `printf '%s' '...'` prints the string exactly, with no newline, and the single quotes stop the shell from interpreting `!`, `$`, and `\`. The file is not malware; it is a test pattern.
    :::

4. Scan the folder:

    ```bash
    clamscan -r -i ~/labs/3.6
    ```

    ```{.output}
    /home/student/labs/3.6/eicar.com: Win.Test.EICAR_HDB-1 FOUND

    ----------- SCAN SUMMARY -----------
    Known viruses: 8712345
    Engine version: 1.0.7
    Scanned directories: 1
    Scanned files: 2
    Infected files: 1
    Data scanned: 0.00 MB
    Time: 18.512 sec (0 m 18 s)
    ```

    ::: explain
    **What just happened:** `-r` scans folders recursively and `-i` prints only infected files. ClamAV loaded millions of signatures (that is why it takes a few seconds and about 1 GB of RAM) and matched the EICAR signature. In a real incident you would quarantine the file rather than delete it, so it can be analyzed.
    :::

5. Quarantine infected files automatically:

    ```bash
    mkdir -p ~/labs/3.6/quarantine
    clamscan -r -i --move="$HOME/labs/3.6/quarantine" ~/labs/3.6
    ls ~/labs/3.6/quarantine
    ```

    ::: explain
    **What just happened:** `--move=DIR` moves each infected file into the quarantine folder. Other options: `--remove` (delete) and `--log=FILE`. For continuous protection, `clamav-daemon` provides `clamd` (a scanner that stays loaded in memory) and `clamonacc` for on-access scanning. Schedule `clamscan` with cron or a systemd timer for regular scans.
    :::

::: checkpoint
**Checkpoint:** `eicar.com` is now in `~/labs/3.6/quarantine`, and the scan summary showed `Infected files: 1`.
:::

#### Task 2: Plant and hunt indicators of compromise

You will play both roles: first the "attacker" plants four harmless IoCs, then the "defender" finds them with a standard checklist.

::: warning
Everything planted here is harmless (`/usr/bin/true` does nothing, and the listener only accepts connections). Still, remove every item at the end of the task, as shown.
:::

1. **Attacker:** plant the IoCs.

    ```bash
    sudo useradd -m -s /bin/bash sysupdate
    echo '*/5 * * * * root /usr/bin/true # system updater' | sudo tee /etc/cron.d/sys-updater
    sudo cp /usr/bin/true /usr/local/bin/sys-helper
    sudo chmod 4755 /usr/local/bin/sys-helper
    nohup nc -lk 4444 >/dev/null 2>&1 &
    ```

    ::: explain
    **What just happened:** You created a backdoor-looking user, a cron job that runs as root every 5 minutes, a program with the **SUID** bit (mode `4755`: it runs as its owner, root, no matter who starts it), and a process listening on TCP port 4444 (`nc -l` listen, `-k` keep listening). Real attackers use the same tricks for persistence and remote access. `nohup ... &` keeps the listener running in the background.
    :::

2. **Defender:** look for unexpected listening ports.

    ```bash
    sudo ss -tulpn
    ```

    ```{.output}
    Netid State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
    udp   UNCONN 0      0      127.0.0.54:53       0.0.0.0:*     users:(("systemd-resolve",pid=612,fd=16))
    tcp   LISTEN 0      1      0.0.0.0:4444        0.0.0.0:*     users:(("nc",pid=4120,fd=3))
    tcp   LISTEN 0      4096   *:22                *:*           users:(("sshd",pid=1,fd=3),("systemd",pid=1,fd=86))
    ```

    ::: explain
    **What just happened:** `ss` shows sockets: `-t` TCP, `-u` UDP, `-l` listening only, `-p` the owning process, `-n` numbers instead of names. You know why port 22 (SSH) and 53 on 127.0.0.54 (the local DNS resolver) are open. Port 4444 owned by `nc` is not part of any service you installed. That is an IoC. Follow up with `ls -l /proc/4120/exe` to see which program it is (use the PID from your output).
    :::

3. Look for new accounts and the log line that created them:

    ```bash
    awk -F: '$3 >= 1000 && $3 < 65534 {print $1, $3, $7}' /etc/passwd
    sudo grep 'new user' /var/log/auth.log | tail -3
    ```

    ```{.output}
    student 1000 /bin/bash
    sysupdate 1001 /bin/bash
    2026-10-10T16:20:11.402 ubuntu-lab useradd[4101]: new user: name=sysupdate, UID=1001, GID=1001, home=/home/sysupdate, shell=/bin/bash, from=/dev/pts/0
    ```

    ::: explain
    **What just happened:** `awk -F:` splits `/etc/passwd` on colons; `$3` is the UID, so this lists normal (human) accounts. `sysupdate` is not one of your users. The auth log shows exactly when it was created and from which terminal. Also check for a second UID 0 account: `awk -F: '$3 == 0' /etc/passwd` should print only `root`.
    :::

4. Look for persistence in scheduled jobs:

    ```bash
    ls -la /etc/cron.d/
    sudo find /etc/cron* /var/spool/cron -type f -mtime -1
    systemctl list-timers --all --no-pager | head
    ```

    ::: explain
    **What just happened:** `find -mtime -1` lists files changed in the last day. `/etc/cron.d/sys-updater` stands out: a new root job with a reassuring name. Attackers also hide in user crontabs (`/var/spool/cron/crontabs/`), systemd timers and services, and shell startup files like `~/.bashrc`.
    :::

5. Look for SUID programs that no package installed:

    ```bash
    for f in $(sudo find / -xdev -perm -4000 -type f 2>/dev/null); do
      dpkg -S "$f" >/dev/null 2>&1 || dpkg -S "${f#/usr}" >/dev/null 2>&1 \
        || echo "NOT FROM A PACKAGE: $f"
    done
    ```

    ```{.output}
    NOT FROM A PACKAGE: /usr/local/bin/sys-helper
    ```

    ::: explain
    **What just happened:** `find / -xdev -perm -4000 -type f` lists every regular file with the SUID bit on the root filesystem (`-xdev` stays on one filesystem). For each one, `dpkg -S` asks "which package owns this file?". The second `dpkg -S "${f#/usr}"` retries without the leading `/usr`, because some packages still register files under `/bin`. Legitimate SUID programs (`sudo`, `passwd`, `su`, `mount`) belong to packages. Your planted file does not. On Rocky use `rpm -qf FILE` instead of `dpkg -S`.
    :::

6. Check logins and connections:

    ```bash
    last -n 5
    sudo lastb -n 5
    sudo ss -tnp state established
    ps aux --sort=-%cpu | head -5
    ```

    ::: explain
    **What just happened:** `last` reads `/var/log/wtmp` (successful logins), and `lastb` reads `/var/log/btmp` (failed logins; many failures from one address means password guessing). `ss ... state established` lists active connections; an unknown outbound connection could be malware calling home. `ps aux --sort=-%cpu` shows the busiest processes, which would expose a crypto miner.
    :::

7. **Respond:** document what you found, then remove the IoCs.

    ```bash
    pkill -f 'nc -lk 4444'
    sudo rm -f /etc/cron.d/sys-updater /usr/local/bin/sys-helper
    sudo userdel -r sysupdate
    sudo ss -tlpn | grep 4444 || echo "port 4444 closed"
    ```

    ::: explain
    **What just happened:** `pkill -f` kills processes whose full command line matches. In a real incident you would first preserve evidence (copy logs, take a VM snapshot or memory image), then contain the system (isolate it from the network), and only then clean up. Because an attacker with root can hide things you did not find, the safest recovery is often to rebuild from a known-good image.
    :::

::: checkpoint
**Checkpoint:** You found all four IoCs (port 4444, user `sysupdate`, `/etc/cron.d/sys-updater`, and the SUID `sys-helper`), and the final command prints `port 4444 closed`.
:::

#### Task 3: Look up CVEs, CVSS scores, and backported fixes

1. On ubuntu-lab, check a specific CVE with the Ubuntu Pro client (installed by default; no subscription is needed for packages in `main`):

    ```bash
    pro fix CVE-2024-6387
    ```

    ```{.output}
    CVE-2024-6387: OpenSSH vulnerability
     - https://ubuntu.com/security/CVE-2024-6387

    1 affected source package is installed: openssh
    (1/1) openssh:
    A fix is available in Ubuntu standard updates.
    The update is already installed.

    CVE-2024-6387 is resolved.
    ```

    ::: explain
    **What just happened:** `pro fix` looked up the CVE in Ubuntu's security database, found which installed package it affects, and checked whether the fixed version is installed. If it were not, `pro fix` would offer to install it (use `--dry-run` to only look). `pro security-status` summarizes the support status of all installed packages.
    :::

2. See the version and the backported fix:

    ```bash
    dpkg -l openssh-server | tail -1
    ssh -V
    apt changelog openssh-server 2>/dev/null | grep -m3 'CVE-2024-6387'
    ```

    ```{.output}
    ii  openssh-server 1:9.6p1-3ubuntu13.5 amd64        secure shell (SSH) server, for secure access from remote machines
    OpenSSH_9.6p1 Ubuntu-3ubuntu13.5, OpenSSL 3.0.13 30 Jan 2024
        - debian/patches/CVE-2024-6387.patch: don't log in sshsigdie() as
        - CVE-2024-6387
    ```

    ::: explain
    **What just happened:** Upstream OpenSSH fixed regreSSHion in version 9.8p1. Ubuntu still ships **9.6p1**, yet the bug is fixed: Ubuntu **backported** the patch and raised only the Ubuntu part of the version (`-3ubuntu13.x`). Read the version string as: `1:` epoch, `9.6p1` upstream version, `3ubuntu13.5` Debian/Ubuntu revision. A naive scanner that says "OpenSSH older than 9.8 is vulnerable" would raise a false positive here. `apt changelog` downloads the package changelog, where every security fix lists its CVE.
    :::

3. Get the CVSS score from the US National Vulnerability Database (NVD) API:

    ```bash
    curl -s "https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2024-6387" \
      | grep -oE '"(baseScore|baseSeverity|vectorString)":"?[^,"]*' | head -3
    ```

    ```{.output}
    "vectorString":"CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H
    "baseScore":8.1
    "baseSeverity":"HIGH
    ```

    ::: explain
    **What just happened:** The API returns JSON about the CVE; `grep -o` pulls out three fields. The vector explains the score: reachable over the **N**etwork, but attack **C**omplexity **H**igh (the attacker must win a timing race), no privileges or user interaction needed, and full impact on confidentiality, integrity, and availability. Score 8.1 is **High**. The NVD API is rate-limited; if you get nothing, wait a minute or look the CVE up at `nvd.nist.gov` in a browser.
    :::

4. On rocky-lab, list pending security updates and check the same CVE:

    ```bash
    # on rocky-lab
    sudo dnf updateinfo list --security
    rpm -q openssh
    rpm -q --changelog openssh | grep -m2 'CVE-2024-6387'
    ```

    ```{.output}
    openssh-8.7p1-43.el9.x86_64
    - Possible remote code execution due to a race condition (CVE-2024-6387)
    ```

    ::: explain
    **What just happened:** `dnf updateinfo list --security` shows security advisories (named `RLSA-...` on Rocky) for packages that have updates waiting; empty output means you are up to date. Rocky 9 ships OpenSSH **8.7p1** from 2021, yet the changelog shows the 2024 fix was backported. Enterprise distributions do this for the whole 10-year life of a release, so the software stays stable but secure.
    :::

::: checkpoint
**Checkpoint:** You can state the CVSS score and severity of CVE-2024-6387 (8.1, High) and show from the changelogs that both VMs have the fix even though neither runs OpenSSH 9.8.

#### Task 4: Find misconfigurations with a port scanner and a protocol analyzer

1. On ubuntu-lab, install nmap and scan rocky-lab:

    ```bash
    sudo apt install -y nmap
    nmap -sV rocky-lab
    ```

    ```{.output}
    Nmap scan report for rocky-lab (192.168.100.20)
    Not shown: 998 filtered tcp ports (no-response)
    PORT     STATE  SERVICE VERSION
    22/tcp   open   ssh     OpenSSH 8.7 (protocol 2.0)
    9090/tcp closed zeus-admin
    ```

    ::: explain
    **What just happened:** `nmap` probed the 1000 most common TCP ports. `-sV` connects to open ports and identifies the software and version. "filtered" means firewalld dropped the probes (good); "closed" means the firewall allowed it but nothing is listening (9090 is the Cockpit port that Rocky's firewall allows by default). Only SSH is open. Scan only systems you own or have written permission to scan.
    :::

2. Now create a typical misconfiguration on rocky-lab: a developer starts a quick web server in a folder that contains a backup of a config file with a password, and opens the firewall for it.

    ```bash
    # on rocky-lab
    mkdir -p ~/labs/3.6/share && cd ~/labs/3.6/share
    echo "db_password=Winter2026" > config.bak
    sudo firewall-cmd --add-port=8080/tcp
    python3 -m http.server 8080
    ```

    ::: explain
    **What just happened:** `python3 -m http.server 8080` serves the current folder over plain HTTP, with directory listing, to anyone who can reach port 8080. The firewall rule is runtime-only. Leave the server running in this terminal.
    :::

3. On ubuntu-lab, scan again and look at what is exposed:

    ```bash
    nmap -sV -p 22,8080 rocky-lab
    curl -s http://rocky-lab:8080/ | grep href
    ```

    ```{.output}
    PORT     STATE SERVICE VERSION
    22/tcp   open  ssh     OpenSSH 8.7 (protocol 2.0)
    8080/tcp open  http    SimpleHTTPServer 0.6 (Python 3.9.18)
    <li><a href="config.bak">config.bak</a></li>
    ```

    ::: explain
    **What just happened:** The scan found a new service and identified it as Python's built-in test server, which should never face a network. `curl` showed the directory listing including `config.bak`. This is a service **misconfiguration**: no bug in Python, just an unsafe way of using it. Vulnerability scanners flag exactly this kind of finding.
    :::

4. Capture the traffic with a **protocol analyzer**. Open a second terminal on ubuntu-lab and start `tcpdump`:

    ```bash
    sudo tcpdump -i any -w /tmp/http.pcap host rocky-lab and tcp port 8080
    ```

    In the first terminal, fetch the file using a (fake) user name and password:

    ```bash
    curl -s -u admin:SuperSecret http://rocky-lab:8080/config.bak
    ```

    Then press `Ctrl+C` in the `tcpdump` terminal.

    ::: explain
    **What just happened:** `tcpdump -i any` captures on all interfaces, `-w /tmp/http.pcap` writes raw packets to a file (the standard pcap format that Wireshark opens), and the filter `host rocky-lab and tcp port 8080` keeps only this conversation. The file goes to `/tmp` because `tcpdump` drops root privileges to a `tcpdump` user before writing. `curl -u` sends HTTP Basic authentication.
    :::

5. Read the capture:

    ```bash
    tcpdump -A -r /tmp/http.pcap | grep -E 'Authorization|db_password'
    echo 'YWRtaW46U3VwZXJTZWNyZXQ=' | base64 -d; echo
    ```

    ```{.output}
    reading from file /tmp/http.pcap, link-type LINUX_SLL2 (Linux cooked v2)
    Authorization: Basic YWRtaW46U3VwZXJTZWNyZXQ=
    db_password=Winter2026
    admin:SuperSecret
    ```

    ::: explain
    **What just happened:** `-r` reads the file and `-A` prints packet contents as ASCII text. The password inside the file **and** the login credentials crossed the network in cleartext. "Basic" authentication is only Base64 encoding, which `base64 -d` reverses instantly; it is not encryption. Anyone on the path could read both. The fix is TLS (Lab 3.5) and never exposing such files at all.
    :::

6. Decode the same capture with `tshark`, the command-line version of Wireshark:

    ```bash
    sudo DEBIAN_FRONTEND=noninteractive apt install -y tshark
    tshark -r /tmp/http.pcap -Y http.request \
      -T fields -e ip.src -e http.request.uri -e http.authorization
    ```

    ```{.output}
    192.168.100.10	/config.bak	Basic YWRtaW46U3VwZXJTZWNyZXQ=
    ```

    ::: explain
    **What just happened:** `DEBIAN_FRONTEND=noninteractive` skips the installer question about letting normal users capture packets (the answer defaults to "no"). `tshark -r` reads the file, `-Y http.request` is a *display filter* that keeps only HTTP requests, and `-T fields -e ...` prints chosen fields. Unlike `tcpdump`, Wireshark/tshark understands hundreds of protocols and names every field. Run `tshark -r /tmp/http.pcap -Y http.request -V | grep -i credentials` to see tshark decode the password for you.
    :::

7. Fix the misconfiguration: on rocky-lab press `Ctrl+C` to stop the Python server, then remove the firewall opening:

    ```bash
    # on rocky-lab
    sudo firewall-cmd --reload
    sudo firewall-cmd --list-ports
    ```

    ::: explain
    **What just happened:** `--reload` throws away runtime-only changes and reloads the saved configuration, so port 8080 is closed again. An empty `--list-ports` output confirms it.
    :::

::: checkpoint
**Checkpoint:** `nmap -sV -p 8080 rocky-lab` now shows `filtered`, and you saw the cleartext credentials in both `tcpdump -A` and `tshark` output.
:::

#### Task 5: Audit rocky-lab against the CIS Benchmark with OpenSCAP

1. Install the scanner and the security content:

    ```bash
    # on rocky-lab
    sudo dnf install -y openscap-scanner scap-security-guide
    ls /usr/share/xml/scap/ssg/content/
    ```

    ```{.output}
    ssg-rl9-ds.xml
    ```

    ::: explain
    **What just happened:** `openscap-scanner` provides the `oscap` command. `scap-security-guide` (SSG, from the ComplianceAsCode project) provides the content: a *data stream* file (`-ds.xml`) that bundles the rules, checks, and profiles for this OS. Use the file name your system shows (it may be `ssg-rhel9-ds.xml`) in the next step.
    :::

2. List the profiles and find the CIS ones:

    ```bash
    # on rocky-lab
    ```

#### Task 6: Detect changed files with AIDE and rkhunter

1. On ubuntu-lab, install AIDE without extra recommended packages (which would pull in a mail server):

    ```bash
    sudo apt install -y --no-install-recommends aide
    ls /etc/aide/
    ```

    ```{.output}
    aide.conf  aide.conf.d
    ```

    ::: explain
    **What just happened:** On Ubuntu the AIDE configuration is `/etc/aide/aide.conf` plus many small rule files in `/etc/aide/aide.conf.d/`. The rules say which folders to watch and which attributes to record (hashes, permissions, owner, size, timestamps). `--no-install-recommends` skips optional packages such as a mail transfer agent, which AIDE would use to email daily reports.
    :::

2. Build the baseline database. This scans most of the filesystem and takes several minutes:

    ```bash
    sudo aideinit -y -f
    ls -lh /var/lib/aide/
    ```

    ```{.output}
    Running aide --init...
    Start timestamp: 2026-10-10 16:45:02 +0000 (AIDE 0.18.6)
    AIDE initialized database at /var/lib/aide/aide.db.new
    ...
    -rw------- 1 root root 21M Oct 10 16:51 aide.db
    -rw------- 1 root root 21M Oct 10 16:51 aide.db.new
    ```

    ::: explain
    **What just happened:** `aideinit` is Ubuntu's wrapper around `aide --config /etc/aide/aide.conf --init`. It writes the new database `aide.db.new` and then copies it to `aide.db`, the file AIDE compares against. `-y` answers yes to overwriting an existing database and `-f` forces it. In production, copy `aide.db` to read-only or offline storage, because an attacker with root could otherwise update it to hide changes.
    :::

3. Simulate an attacker: change a watched file and add a new one:

    ```bash
    sudo cp /etc/hosts /etc/hosts.lab-backup
    echo "203.0.113.66 updates.example.com" | sudo tee -a /etc/hosts
    echo "evil=1" | sudo tee /etc/lab-aide-test.conf
    ```

    ::: explain
    **What just happened:** Changing `/etc/hosts` is a classic attacker trick: it silently redirects a name (here an update server) to an attacker's address. `203.0.113.0/24` is a documentation-only address range, so nothing real is affected.
    :::

4. Run the check:

    ```bash
    sudo aide -c /etc/aide/aide.conf --check
    echo "exit code: $?"
    ```

    ```{.output}
    Start timestamp: 2026-10-10 16:58:40 +0000 (AIDE 0.18.6)
    AIDE found differences between database and filesystem!!

    Summary:
      Total number of entries:	104321
      Added entries:		2
      Removed entries:		0
      Changed entries:		1

    ---------------------------------------------------
    Added entries:
    ---------------------------------------------------

    f++++++++++++++++: /etc/hosts.lab-backup

    ---------------------------------------------------
    Changed entries:
    ---------------------------------------------------

    f   ...    .C... : /etc/hosts
    ...
    exit code: 5
    ```

    ::: explain
    **What just happened:** `-c` (same as `--config`) points to the Ubuntu config file, and `--check` compares the filesystem with `aide.db`. AIDE lists added files (`+` in every column), and changed files with a letter per changed attribute (`C` means the checksum changed; `s` size, `m` modification time, `p` permissions, `u` owner). Further down it shows old and new hash values. The exit code is a bitmask: 1 = added, 2 = removed, 4 = changed, so 1 + 4 = 5. Scripts and monitoring tools use this code. 5. After an approved change you accept it into the baseline with `--update`. Here you will instead undo the change and confirm:

    ```bash
    sudo mv /etc/hosts.lab-backup /etc/hosts
    sudo rm /etc/lab-aide-test.conf
    systemctl list-timers --all --no-pager | grep -i aide
    ```

    ::: explain
    **What just happened:** The files are back to their original state. To accept real changes you would run `sudo aide -c /etc/aide/aide.conf --update` and then `sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db`. Ubuntu runs a daily check automatically through `dailyaidecheck.timer` (older releases used `/etc/cron.daily/aide`). On Rocky, AIDE's config is `/etc/aide.conf` and you run `aide --init` then `aide --check` directly.
    :::

6. Now run **rkhunter**:

    ```bash
    sudo apt install -y --no-install-recommends rkhunter
    sudo rkhunter --update
    sudo rkhunter --propupd
    sudo rkhunter --check --sk --rwo
    ```

    ```{.output}
    [ Rootkit Hunter version 1.4.6 ]
    File updated: searched for 180 files, found 146
    Warning: The file properties have changed: ...
    ```

    ::: explain
    **What just happened:**

    - `--update` downloads new rootkit signature data. On Ubuntu it may print an error about `WEB_CMD`, because Ubuntu disables rkhunter's own downloads (`WEB_CMD="/bin/false"` in `/etc/rkhunter.conf`) and ships updates through apt instead. That error is expected.
    - `--propupd` records the current properties (hashes, sizes, permissions) of important system binaries as the known-good baseline. Run it right after installation and after every system update.
    - `--check` runs all tests: known rootkit files, changed binaries, hidden files, suspicious startup files, SSH settings, and more. `--sk` skips the "press Enter" pauses, and `--rwo` reports warnings only.

    Warnings are not proof of compromise. Each one needs a look; common false positives are scripts that replaced binaries in newer packages and hidden files that packages create. The full details are in `/var/log/rkhunter.log`.
    :::

**Checkpoint:** `sudo aide -c /etc/aide/aide.conf --check` listed `/etc/hosts` as changed (before you restored it), and `sudo grep -c Warning /var/log/rkhunter.log` returns a number you can explain.

#### Task 7: Verify installed files, signed packages, and the supply chain

1. On ubuntu-lab, install `debsums`, then tamper with a harmless file from the `nano` package:

    ```bash
    sudo apt install -y debsums nano
    sudo debsums -s nano && echo "nano: all files OK"
    echo "# tampered" | sudo tee -a /usr/share/nano/sh.nanorc
    sudo debsums -s nano
    dpkg --verify nano
    ```

    ```{.output}
    nano: all files OK
    debsums: changed file /usr/share/nano/sh.nanorc (from nano package)
    ??5?????? /usr/share/nano/sh.nanorc
    ```

    ::: explain
    **What just happened:** Every `.deb` package ships an MD5 list of its files in `/var/lib/dpkg/info/PACKAGE.md5sums`. `debsums` compares installed files with that list; `-s` (silent) prints only problems. `dpkg --verify` does the same and prints an `rpm -V`-style line where `5` means the checksum differs and `?` means "not checked". Run `sudo debsums -s` with no package name to check the whole system (it takes a few minutes); add `-a` to include configuration files, which admins are expected to change.
    :::

2. Repair the file by reinstalling the package:

    ```bash
    sudo apt install --reinstall -y nano
    sudo debsums -s nano && echo "nano: all files OK"
    ```

3. Do the same on rocky-lab with `rpm -V`:

    ```bash
    # on rocky-lab
    sudo dnf install -y nano
    echo "# tampered" | sudo tee -a /usr/share/nano/sh.nanorc
    rpm -V nano
    sudo rpm -Va 2>/dev/null | head -5
    sudo dnf reinstall -y nano
    rpm -V nano && echo "nano: all files OK"
    ```

    ```{.output}
    S.5....T.    /usr/share/nano/sh.nanorc
    S.5....T.  c /etc/sysconfig/...
    ...
    nano: all files OK
    ```

    ::: explain
    **What just happened:** `rpm -V PACKAGE` verifies one package; `rpm -Va` verifies all installed packages (it takes a while). Each letter is a failed test: `S` size, `M` mode (permissions), `5` digest (checksum), `D` device, `L` symlink, `U` user, `G` group, `T` modification time, `P` capabilities. A dot means the test passed. `c` marks a configuration file, where changes are often legitimate. A `5` on a binary in `/usr/bin` with no update to explain it is a serious warning sign. Note: an attacker with root can also change the RPM database, so the most trustworthy check boots from clean media or compares with AIDE data stored offline.
    :::

4. On rocky-lab, check package **signatures**:

    ```bash
    # on rocky-lab
    grep -m1 gpgcheck /etc/yum.repos.d/rocky.repo
    rpm -q gpg-pubkey --qf '%{NAME}-%{VERSION}  %{SUMMARY}\n'

    rpm -K nano-*.rpm
    ```

    ```{.output}
    gpgcheck=1
    gpg-pubkey-350d275d  Rocky Enterprise Software Foundation - Release key 2022 <releng@rockylinux.org> public key
    Signature   : RSA/SHA256, Mon 13 May 2024 10:21:16 PM UTC, Key ID 702d426d350d275d
    nano-5.6.1-6.el9.x86_64.rpm: digests signatures OK
    ```

    ::: explain
    **What just happened:** `gpgcheck=1` makes `dnf` refuse any package whose signature does not verify. The imported public keys appear as fake `gpg-pubkey` packages. Every installed package records which key signed it. `rpm -K` (also `rpm --checksig`) checks a package file before you install it: "digests signatures OK" means the file is intact and was signed by a trusted key. A package from an unknown source would say `NOKEY` or `NOT OK`.

5. On ubuntu-lab, see how **apt** verifies signed packages. Apt signs the repository index, not each `.deb`:

    ```bash
    grep -E '^(URIs|Suites|Signed-By)' /etc/apt/sources.list.d/ubuntu.sources | head -3
    ls /var/lib/apt/lists/ | grep InRelease | head -3
    cd ~/labs/3.6 && apt-get download nano
    sha256sum nano_*.deb
    apt-cache show nano | grep -m1 SHA256
    ```

    ```{.output}
    URIs: http://archive.ubuntu.com/ubuntu/
    Suites: noble noble-updates noble-backports
    Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
    archive.ubuntu.com_ubuntu_dists_noble-backports_InRelease
    archive.ubuntu.com_ubuntu_dists_noble-updates_InRelease
    archive.ubuntu.com_ubuntu_dists_noble_InRelease
    7d2f...e41a  nano_7.2-2ubuntu0.1_amd64.deb
    SHA256: 7d2f...e41a
    ```

    ::: explain
    **What just happened:** This is apt's chain of trust:

    ```{.diagram}
    ubuntu-archive-keyring.gpg --verifies--> InRelease (GPG-signed, was Release + Release.gpg)
    InRelease  --lists SHA256 of-->  Packages index
    Packages   --lists SHA256 of-->  every .deb file
    ```

    `Signed-By` names the only key allowed to sign this repository. During `apt update`, apt checks the signature on `InRelease`; during install, it checks each `.deb` against the hash in the signed index. You just did the last step by hand: the hash of the downloaded `.deb` matches the index. If any link fails, apt refuses with an error like "The following signatures couldn't be verified". Avoid adding random third-party repositories or running `curl ... | sudo bash` installers; each one is a new link in your supply chain.
    :::

6. **Supply chain case study: the xz backdoor (CVE-2024-3094, CVSS 10.0).** In March 2024, Microsoft engineer Andres Freund noticed SSH logins on Debian testing using 500 ms more CPU than expected. He found that versions 5.6.0 and 5.6.1 of `xz`/`liblzma` contained a backdoor, hidden in test files by a contributor who had spent about two years earning the trust of the project. Because some distributions link `sshd` to `libsystemd`, which loads `liblzma`, the backdoor could let the attacker take over `sshd`. It was caught before reaching stable releases. Check what your VMs run:

    ```bash
    xz --version
    dpkg -l xz-utils | tail -1
    ```

    ```bash
    # on rocky-lab
    rpm -q xz
    ```

    ```{.output}
    xz (XZ Utils) 5.4.5
    liblzma 5.4.5
    ii  xz-utils  5.6.1+really5.4.5-1ubuntu0.2  amd64  XZ-format compression utilities
    xz-5.2.5-8.el9_0.x86_64
    ```

    ::: explain
    **What just happened:** Ubuntu 24.04 was about to ship 5.6.1, so Ubuntu rebuilt the safe 5.4.5 code under the version name `5.6.1+really5.4.5`, which is how Debian-family distributions say "the version number is higher, but the content is really the older release". Rocky 9 uses 5.2.5 and was never affected. Lessons: trust is a supply chain attack surface, reproducible builds and code review matter, and odd performance changes deserve investigation.
    :::

8. Two more supply chain controls: **pinning** and an **SBOM**:

#### Task 8: Destroy data securely

::: warning
This task destroys all data on an extra disk. Take a snapshot now. Run `lsblk` and confirm `/dev/sdc` is an empty 5 GB lab disk with no mount points. If your second extra disk has another name, use it everywhere. Writing to the wrong device (like `/dev/sda`) destroys your VM.
:::

1. Start with a file. `shred` overwrites a file's contents before deleting it:

    ```bash
    cd ~/labs/3.6
    echo "customer card numbers" > secret.txt
    shred -v -n 1 -z -u secret.txt
    ```

    ```{.output}
    shred: secret.txt: pass 1/2 (random)...
    shred: secret.txt: pass 2/2 (000000)...
    shred: secret.txt: removing
    shred: secret.txt: renamed to 0000000000
    ...
    shred: secret.txt: removed
    ```

    ::: explain
    **What just happened:** `-n 1` overwrites once with random data, `-z` adds a final pass of zeros to hide that shredding happened, `-u` deletes the file afterwards (after renaming it several times to hide the name), and `-v` shows progress. One random pass is enough for modern hard disks. **Caveat:** on journaling or copy-on-write filesystems (ext4 with data journaling, Btrfs, ZFS), on SSDs, and when backups or snapshots exist, old copies may survive elsewhere. For files, shred is best effort; for whole devices it is reliable on hard disks.
    :::

2. Write a recognizable "secret" to the raw disk so you can prove each method destroys it:

    ```bash
    lsblk /dev/sdc
    echo "TOP-SECRET-LAB-DATA" | sudo dd of=/dev/sdc conv=fsync status=none
    sudo head -c 1M /dev/sdc | grep -a -c TOP-SECRET
    ```

    ```{.output}
    1
    ```

    ::: explain
    **What just happened:** `dd of=/dev/sdc` writes its input straight to the start of the disk; `conv=fsync` makes sure it reaches the disk. `head -c 1M` reads the first megabyte and `grep -a -c` counts lines containing the secret: 1, so it is there. You will repeat this "plant and check" pattern for each method.
    :::

3. **Method 1: `shred` on a whole device.**

    ```bash
    sudo shred -v -n 1 /dev/sdc
    sudo head -c 1M /dev/sdc | grep -a -c TOP-SECRET
    ```

    ```{.output}
    shred: /dev/sdc: pass 1/1 (random)...
    shred: /dev/sdc: pass 1/1 (random)...1.1GiB/5.0GiB 22%
    ...
    shred: /dev/sdc: pass 1/1 (random)...5.0GiB/5.0GiB 100%
    0
    ```

    ::: explain
    **What just happened:** `shred` overwrote all 5 GiB with random data (about a minute on a virtual disk). The count is now 0. On a hard disk this is a proper "clear" of the whole device.
    :::

4. **Method 2: `badblocks -w`.** Plant the secret again, then run a destructive write test over the first 100 MiB:

    ```bash
    echo "TOP-SECRET-LAB-DATA" | sudo dd of=/dev/sdc conv=fsync status=none
    sudo badblocks -wsv -b 4096 /dev/sdc 25599 0
    sudo hexdump -C -n 64 /dev/sdc
    ```

    ```{.output}
    Checking for bad blocks in read-write mode
    From block 0 to 25599
    Testing with pattern 0xaa: done
    Reading and comparing: done
    Testing with pattern 0x55: done
    Reading and comparing: done
    Testing with pattern 0xff: done
    Reading and comparing: done
    Testing with pattern 0x00: done
    Reading and comparing: done
    Pass completed, 0 bad blocks found. (0/0/0 errors)
    00000000  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
    *
    00000040
    ```

    ::: explain
    **What just happened:** `badblocks` is really a disk-testing tool. `-w` is the **destructive** write mode: it writes four patterns (`0xaa`, `0x55`, `0xff`, `0x00`) to every block and reads each back to find bad sectors, destroying all data as a side effect. `-s` shows progress, `-v` is verbose, and `-b 4096` uses 4 KiB blocks. The two numbers are the *last* block and the *first* block to test: blocks 0 to 25599 are 100 MiB, which keeps the lab fast; without them it tests the whole disk. `hexdump -C` shows the last pattern, all zeros, where the secret used to be. Never use `-w` on a disk with data you want; `-n` is the non-destructive read-write mode.
    :::

5. **Method 3: `dd if=/dev/urandom`.**

    ```bash
    echo "TOP-SECRET-LAB-DATA" | sudo dd of=/dev/sdc conv=fsync status=none
    sudo dd if=/dev/urandom of=/dev/sdc bs=1M count=100 status=progress
    sudo hexdump -C -n 64 /dev/sdc
    ```

    ```{.output}
    104857600 bytes (105 MB, 100 MiB) copied, 0.4 s, 262 MB/s
    100+0 records in
    100+0 records out
    00000000  9c 4e 1a f7 30 d2 88 5b  e1 07 c4 39 ae 52 6d 13  |.N..0..[...9.Rm.|
    ...
    ```

    ::: explain
    **What just happened:** `if=` is the input file (`/dev/urandom` produces endless random bytes) and `of=` the output (the disk). `bs=1M` writes in 1 MiB blocks and `count=100` stops after 100 blocks (100 MiB); leave out `count` to wipe the whole disk (dd then ends with a harmless "No space left on device"). `status=progress` shows live progress. `dd if=/dev/zero` is faster and is just as good on modern hard disks; random data hides which parts were ever used.
    :::

6. **Method 4: cryptographic destruction.** Encrypt the disk, store data, then destroy only the keys:

    ```bash
    sudo cryptsetup luksFormat --type luks2 /dev/sdc
    sudo cryptsetup open /dev/sdc wipetest
    sudo mkfs.ext4 -q /dev/mapper/wipetest
    sudo mkdir -p /mnt/wipetest && sudo mount /dev/mapper/wipetest /mnt/wipetest
    echo "TOP-SECRET-LAB-DATA" | sudo tee /mnt/wipetest/secret.txt
    sudo umount /mnt/wipetest && sudo cryptsetup close wipetest
    sudo cryptsetup luksErase /dev/sdc
    sudo cryptsetup luksDump /dev/sdc | sed -n '/^Keyslots:/,/^Tokens:/p'
    ```

    Type `YES` and a passphrase (for example `Wipe-Lab-1`) for `luksFormat`, the same passphrase for `open`, and `YES` again for `luksErase`.

    ```{.output}
    Keyslots:
    Tokens:
    ```

    ::: explain
    **What just happened:** All data on the disk was encrypted with a random master key. `luksErase` overwrote every key slot, so no passphrase can ever recover that master key, and the 5 GB of ciphertext is now permanently meaningless. It took less than a second, which is why crypto-erase is the preferred method for SSDs, cloud volumes, and large arrays: you do not have to reach every physical copy of the data. Try `sudo cryptsetup open /dev/sdc wipetest`; no passphrase works. Many SSDs and NVMe drives do the same internally ("self-encrypting drives"; `nvme format --ses=2` or the ATA secure erase command).
    :::

::: tip
Standards such as NIST SP 800-88 describe three levels: **clear** (overwrite with normal commands, like the methods above), **purge** (stronger, such as crypto-erase or the drive's built-in sanitize command), and **destroy** (shred, crush, or incinerate the physical media). Always record what was destroyed, how, by whom, and when (a certificate of destruction).
:::

::: checkpoint
**Checkpoint:** `sudo cryptsetup luksDump /dev/sdc` shows an empty `Keyslots:` section, and you saw the secret count drop to 0 or zeros after each method.
:::

### Exam corner

- **Anti-malware** on Linux: ClamAV (`freshclam` updates signatures, `clamscan -r -i` scans, `--move` quarantines). Test safely with the EICAR string.
- **Indicators of compromise**: unknown listening ports (`ss -tulpn`), new or UID 0 accounts, new cron jobs/timers, SUID files not owned by a package (`find / -perm -4000`), odd logins (`last`, `lastb`), unknown outbound connections, high CPU processes, changed binaries.
- **CVE** = unique ID for a public vulnerability; **CVSS** = 0.0 to 10.0 severity score (Low under 4, Medium 4 to 6.9, High 7 to 8.9, Critical 9 to 10) built from a vector.
- **Backporting**: distributions apply security fixes to older versions; check changelogs (`apt changelog`, `rpm -q --changelog`), `pro fix CVE-...`, or `dnf updateinfo`, not just upstream version numbers.
- **Port scanner**: `nmap -sV` finds open ports and versions; `nmap --script` adds checks. **Protocol analyzer**: `tcpdump -w`/`-r`/`-A`, Wireshark, `tshark`. Service **misconfiguration** = unsafe settings, not a code bug.
- **OpenSCAP**: `oscap xccdf eval --profile <id> --results r.xml --report r.html <datastream>` with content from `scap-security-guide`. **CIS** Benchmarks: Level 1 (baseline) and Level 2 (strict); Ubuntu's tool is `usg` (Ubuntu Pro).
- **AIDE**: `aide --init` (Ubuntu `aideinit`), `aide --check`, `aide --update`; config `/etc/aide/aide.conf` (Ubuntu) or `/etc/aide.conf` (RHEL). **rkhunter**: `--propupd` baseline, `--check --sk`.
- Installed file verification: `debsums -s`, `dpkg --verify` (Debian/Ubuntu), `rpm -V pkg` / `rpm -Va` (codes S, M, 5, D, L, U, G, T). **Signed package** checks: `rpm -K`, `gpgcheck=1`, apt `InRelease` + `Signed-By`.
- Destruction: `shred -v -n 1 -z -u file`, `badblocks -w` (destructive write test), `dd if=/dev/urandom of=/dev/sdX bs=1M`, and **cryptographic** erase (`cryptsetup luksErase`), best for SSDs.
- **Supply chain**: xz backdoor (CVE-2024-3094); verify downloads with checksums **and** GPG signatures; pin versions; keep an SBOM (SPDX, CycloneDX).
- Banners: `/etc/issue` (local, before login), `/etc/issue.net` (network, needs `Banner /etc/issue.net` in `sshd_config`), `/etc/motd` (after login; Ubuntu adds dynamic `/etc/update-motd.d/`).
