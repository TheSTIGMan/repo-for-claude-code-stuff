## Lab 3.5: Use Cryptography on Linux {#lab-3-5}

::: labinfo
**Objective:** 3.5 Explain cryptographic concepts and technologies in a Linux environment.\
**Domain:** 3.0 Security (18% of the exam)\
**Time:** about 150 minutes\
**VM:** ubuntu-lab and rocky-lab\
**Snapshot first:** Yes. This lab encrypts an extra disk, changes SSH algorithms, and changes the system crypto policy on rocky-lab.
:::

Cryptography protects data in two situations: when it sits on a disk (**data at rest**) and when it travels over a network (**data in transit**). In this lab you will hash and sign files, encrypt files with GPG, encrypt a whole disk with LUKS2, build your own small certificate authority, serve a website over TLS, build a WireGuard VPN between your two VMs, and remove weak algorithms. By the end, terms like "Argon2", "trusted root", and "TLS 1.3" will be things you have touched, not just words to memorize.

### What you'll practice

- Data at rest: File encryption (GPG); Filesystem encryption (LUKS2, Argon2)
- Data in transit: OpenSSL, WireGuard, LibreSSL, TLS protocol versions
- Hashing: SHA-256, HMAC
- Removal of weak algorithms (SSH algorithm lists, Rocky crypto policies, old TLS versions)
- Certificate management: Trusted root certificates (no-cost, commercial); Avoiding self-signed certificates

### How it works

**Three tools in the crypto toolbox.**

1. **Hashing** turns any amount of data into a short, fixed-length fingerprint. SHA-256 always produces 256 bits (64 hex characters). Change one byte of input and the hash changes completely. You cannot turn a hash back into the data. Hashes prove **integrity** ("this file has not changed"). Old hashes like MD5 and SHA-1 are broken: researchers can create two different files with the same hash, so they are considered weak algorithms.
2. **Symmetric encryption** uses one secret key to lock and unlock, like a house key. It is fast, so it is used for bulk data. AES (Advanced Encryption Standard) and ChaCha20 are the common modern ciphers.
3. **Asymmetric (public-key) encryption** uses a key *pair*. The **public key** can be shared with anyone; the **private key** stays secret. Data encrypted with the public key can only be decrypted with the private key. The private key can also create a **digital signature** that anyone with the public key can check. RSA, ECDSA, and Ed25519 are common examples. Asymmetric crypto is slow, so real systems use it to agree on a symmetric key, then switch to symmetric encryption.

**HMAC** (Hash-based Message Authentication Code) mixes a secret key into a hash. A plain hash proves a file did not change *by accident*, but an attacker who changes the file can just compute a new hash. With HMAC, only someone who knows the key can compute the correct value, so it proves integrity **and** that the sender knew the key.

**Data at rest.**

- **GPG** (GNU Privacy Guard) encrypts and signs individual files. It can use a passphrase (symmetric) or public keys (asymmetric).
- **LUKS2** (Linux Unified Key Setup, version 2) encrypts a whole block device. The data is encrypted with one random *master key*. That master key is stored in the LUKS header, locked in up to 32 *key slots*. Each slot is protected by a passphrase or key file. To turn your passphrase into a key, LUKS2 uses **Argon2id**, a *key derivation function* designed to need lots of memory and time, which makes guessing passphrases with GPUs very expensive. (LUKS1 used PBKDF2, which needs almost no memory.)

```{.diagram}
 passphrase "blue..."  --Argon2id-->  slot key  --unlocks-->  master key
 passphrase #2         --Argon2id-->  slot key  --unlocks-->  (same master key)
                                                                  |
                                       AES-XTS encrypts every sector on /dev/sdb
```

Because every slot unlocks the same master key, you can add or remove passphrases without re-encrypting the disk. If you destroy all key slots, the master key is gone and the data is unreadable forever. That is **cryptographic erase**.

**Data in transit.**

- **TLS** (Transport Layer Security) protects HTTPS, secure email, and much more. SSL 2.0, SSL 3.0, TLS 1.0, and TLS 1.1 are obsolete and must be disabled (TLS 1.0/1.1 were formally deprecated by RFC 8996 in 2021). Use **TLS 1.2** and **TLS 1.3**. TLS 1.3 is faster (one round trip) and removed all old, weak cipher options.
- **OpenSSL** is the TLS library and command-line toolkit on almost every Linux system. **LibreSSL** is a fork of OpenSSL created by the OpenBSD project in 2014, after the Heartbleed bug, to clean up and simplify the code. It is the default on OpenBSD and is used by macOS, but Ubuntu and Rocky ship OpenSSL. Its `openssl` command works almost the same way.
- **WireGuard** is a modern VPN built into the Linux kernel since version 5.6. It uses a small fixed set of modern algorithms (Curve25519, ChaCha20-Poly1305, BLAKE2s) and a configuration much simpler than IPsec or OpenVPN. Each peer has a key pair, a bit like SSH keys.

**Certificates and trust.** A TLS certificate binds a public key to a name (like `www.example.com`) and is signed by a **certificate authority (CA)**. Your system has a list of **trusted root certificates** (on Ubuntu in `/etc/ssl/certs`, from the `ca-certificates` package). A browser trusts a site's certificate if it can follow the chain of signatures up to one of those roots.

```{.diagram}
 Trusted root CA (in /etc/ssl/certs)      e.g. ISRG Root X1, DigiCert Global Root
        | signs
 Intermediate CA                          e.g. Let's Encrypt R11
        | signs
 Server (leaf) certificate                CN/SAN = www.example.com
```

- **No-cost** CAs: Let's Encrypt issues free certificates automatically using the **ACME** protocol (the `certbot` tool). The certificates are trusted everywhere and live 90 days, so renewal is automated.
- **Commercial** CAs (DigiCert, Sectigo, GlobalSign, and others) charge money. They offer organization-validated (OV) and extended-validation (EV) certificates, longer support, warranties, and help with special cases. The encryption is exactly the same strength.
- A **self-signed** certificate is signed by its own key. No one vouches for it, so clients show errors, and users learn to click "accept anyway", which makes man-in-the-middle attacks easy. Avoid self-signed certificates in production. For internal systems, run a private CA and install its root on your machines, as you will do in this lab.

### Tasks

#### Task 1: Prove integrity with SHA-256 and HMAC

1. Create the working directory and two sample files:

    ```bash
    mkdir -p ~/labs/3.5 && cd ~/labs/3.5
    echo "Quarterly report: revenue up 4%" > report.txt
    echo "Server inventory: web01 web02 db01" > inventory.txt
    ```

2. Compute SHA-256 hashes and save them to a checksum file:

    ```bash
    sha256sum report.txt inventory.txt | tee SHA256SUMS
    ```

    ```{.output}
    e4a693b44e226f2b9024b5427e19af895bedeceb02af483580bb1b15ccb9d826  report.txt
    71b30de0ef10362245837072ad5b724c2961dfc0a7a97e3f8706065b57a24aa9  inventory.txt
    ```

    ::: explain
    **What just happened:** `sha256sum` prints the hash and the file name for each file. `tee` shows the output and also writes it to `SHA256SUMS`. Because you used the exact same text, your hashes should match these exactly. That is the point of a hash: same input, same output, on any computer.
    :::

3. Verify the files, then tamper with one and verify again:

    ```bash
    sha256sum -c SHA256SUMS
    echo "Quarterly report: revenue up 40%" > report.txt
    sha256sum -c SHA256SUMS
    ```

    ```{.output}
    report.txt: OK
    inventory.txt: OK
    report.txt: FAILED
    inventory.txt: OK
    sha256sum: WARNING: 1 computed checksum did NOT match
    ```

    ::: explain
    **What just happened:** `-c` (check) reads the checksum file, recomputes each hash, and compares. A single added character changed the hash, so the check failed. Linux distributions publish `SHA256SUMS` files next to their ISO images for exactly this reason.
    :::

4. Now the weakness: an attacker who can change `report.txt` can also regenerate `SHA256SUMS`. An HMAC fixes this, because it needs a secret key. Put the original text back and compute an HMAC:

    ```bash
    echo "Quarterly report: revenue up 4%" > report.txt
    openssl dgst -sha256 -hmac "lab-shared-key" report.txt
    ```

    ```{.output}
    HMAC-SHA2-256(report.txt)= abfca3db36d0e38b4e4127178cf2623c5e6b7e5edbf6a6121ae7f481c34b49e2
    ```

    ::: explain
    **What just happened:** `openssl dgst` computes digests (hashes). `-sha256` picks the algorithm and `-hmac "lab-shared-key"` mixes in the secret key. Without the key, nobody can produce this value for a modified file. Run it again with a different key and the result is completely different. HMAC is used inside TLS, SSH (the "MAC" algorithms like `hmac-sha2-256`), JWT tokens, and API request signing.
    :::

5. Compare with the weak hashes, just to see them:

    ```bash
    md5sum report.txt
    sha1sum report.txt
    ```

    ::: explain
    **What just happened:** MD5 (128 bits) and SHA-1 (160 bits) still run, but collisions have been demonstrated for both (SHA-1 publicly in 2017). Use them only for non-security jobs like spotting accidental corruption. For security, use SHA-256 or stronger (SHA-384, SHA-512, SHA-3).
    :::

::: checkpoint
**Checkpoint:** `sha256sum -c SHA256SUMS` shows `OK` for both files again (you restored the original text), and `openssl dgst -sha256 -hmac "lab-shared-key" report.txt` prints the same HMAC as above.
:::

#### Task 2: Encrypt and sign files with GPG

You will use both VMs: ubuntu-lab encrypts a file so that only rocky-lab can read it, and signs it so rocky-lab can prove who sent it.

1. On ubuntu-lab, install GnuPG and tell it which terminal to use for passphrase prompts (needed over SSH):

    ```bash
    sudo apt install -y gnupg
    export GPG_TTY=$(tty)
    cd ~/labs/3.5
    echo "Door code for the server room: 4417" > notes.txt
    ```

    ::: explain
    **What just happened:** GnuPG asks for passphrases through a helper program called *pinentry*. On a text-only server it draws a box in your terminal, and `GPG_TTY` tells it which terminal that is. Without it you may see "Inappropriate ioctl for device". Run the `export` line again in every new terminal you use for GPG.
    :::

2. **Symmetric** encryption with a passphrase:

    ```bash
    gpg -c --cipher-algo AES256 notes.txt
    ls notes.txt*
    file notes.txt.gpg
    ```

    Type a passphrase twice (for example `Lab-Gpg-Sym-2026`).

    ```{.output}
    notes.txt  notes.txt.gpg
    notes.txt.gpg: PGP symmetric key encrypted data - AES with 256-bit key salted & iterated - SHA512 .
    ```

    ::: explain
    **What just happened:** `-c` means "symmetric" (conventional) encryption with a passphrase only, no keys. `--cipher-algo AES256` chooses AES with a 256-bit key. GPG wrote `notes.txt.gpg`; the original is not deleted. `file` identifies the result as encrypted data. Anyone with the passphrase can decrypt it, so this is good for backups or sending a file to someone you can give a passphrase to by another channel.
    :::

3. Decrypt it. First clear the passphrase cache so GPG really asks:

    ```bash
    gpgconf --kill gpg-agent
    gpg -o notes-decrypted.txt -d notes.txt.gpg
    cat notes-decrypted.txt
    ```

    ::: explain
    **What just happened:** `gpg-agent` remembers passphrases for a few minutes; `gpgconf --kill gpg-agent` stops it, emptying the cache. `-d` decrypts and `-o` names the output file. You see the original text.
    :::

4. Create a key pair on ubuntu-lab. Use any passphrase you will remember, for example `Ubuntu-Gpg-Key-2026`:

    ```bash
    gpg --quick-generate-key "Student Ubuntu <student@ubuntu-lab.example>" default default 1y
    gpg --list-keys
    ```

    ```{.output}
    pub   ed25519 2026-10-10 [SC] [expires: 2027-10-10]
          3F1A9C0E7B2D4E5F6A7B8C9D0E1F2A3B4C5D6E7F
    uid           [ultimate] Student Ubuntu <student@ubuntu-lab.example>
    sub   cv25519 2026-10-10 [E] [expires: 2027-10-10]
    ```

    ::: explain
    **What just happened:** `--quick-generate-key` takes a user ID (name and email), the algorithm (`default`), the usage (`default`), and an expiry (`1y`). GnuPG made a primary key for signing (`[S]`) and certifying other keys (`[C]`), plus a subkey for encryption (`[E]`). The long hex string is the **fingerprint**, the unique ID of the key. `[ultimate]` means you trust it completely, because it is yours. Some builds use RSA 3072 instead of Ed25519; either is fine.
    :::

5. On **rocky-lab**, do the same and export the public key:

    ```bash
    # on rocky-lab
    sudo dnf install -y gnupg2
    export GPG_TTY=$(tty)
    mkdir -p ~/labs/3.5 && cd ~/labs/3.5
    gpg --quick-generate-key "Student Rocky <student@rocky-lab.example>" default default 1y
    gpg --armor --export student@rocky-lab.example > rocky-pub.asc
    head -1 rocky-pub.asc
    scp rocky-pub.asc student@ubuntu-lab:labs/3.5/
    ```

    ```{.output}
    -----BEGIN PGP PUBLIC KEY BLOCK-----
    ```

    ::: explain
    **What just happened:** `--export` writes the public key; `--armor` makes it plain text (ASCII "armor") instead of binary, so it can be emailed or pasted. Only the **public** key left the machine. `scp` copied it to ubuntu-lab over SSH.
    :::

6. On ubuntu-lab, import Rocky's public key, export your own, and send it to rocky-lab:

    ```bash
    gpg --import rocky-pub.asc
    gpg --fingerprint student@rocky-lab.example
    gpg --armor --export student@ubuntu-lab.example > ubuntu-pub.asc
    scp ubuntu-pub.asc student@rocky-lab:labs/3.5/
    ```

    ::: explain
    **What just happened:** `--import` adds the key to your keyring. Before you trust an imported key, compare its fingerprint with the owner by a separate channel (in person, by phone). Here, compare it with `gpg --fingerprint` on rocky-lab. This check is what stops an attacker from slipping you a fake key.
    :::

7. Mark the key as verified by signing it locally, then encrypt a file **to** rocky-lab and sign a copy:

    ```bash
    gpg --quick-lsign-key "$(gpg --with-colons --fingerprint student@rocky-lab.example \
      | awk -F: '/^fpr/{print $10; exit}')"
    echo "Migration starts Friday at 22:00" > plans.txt
    gpg --armor -o plans.enc.asc -e -r student@rocky-lab.example plans.txt
    gpg --armor -o plans.txt.sig --detach-sign plans.txt
    scp plans.enc.asc plans.txt.sig student@rocky-lab:labs/3.5/
    ```

    ::: explain
    **What just happened:**

    - `--quick-lsign-key FINGERPRINT` signs Rocky's key with your key as "locally verified". The `awk` part pulls the fingerprint out of GPG's machine-readable (`--with-colons`) output. Without this, GPG warns "There is no assurance this key belongs to the named user".
    - `-e -r student@rocky-lab.example` **encrypts** to that recipient's public key. Only Rocky's private key can decrypt it. Even you cannot decrypt `plans.enc.asc` now.
    - `--detach-sign` creates a **signature** in a separate file, made with your private key (GPG asks for your key passphrase).
    :::

8. On rocky-lab, decrypt, import Ubuntu's key, and verify the signature:

    ```bash
    # on rocky-lab
    cd ~/labs/3.5
    gpg -o plans.txt -d plans.enc.asc
    cat plans.txt
    gpg --import ubuntu-pub.asc
    gpg --verify plans.txt.sig plans.txt
    ```

    ```{.output}
    gpg: Signature made Sat 10 Oct 2026 03:12:44 PM UTC
    gpg:                using EDDSA key 3F1A9C0E7B2D4E5F6A7B8C9D0E1F2A3B4C5D6E7F
    gpg: Good signature from "Student Ubuntu <student@ubuntu-lab.example>" [unknown]
    gpg: WARNING: This key is not certified with a trusted signature!
    ```

    ::: explain
    **What just happened:** Rocky's private key decrypted the file (you typed Rocky's key passphrase). `--verify` checked the signature with Ubuntu's public key: "Good signature" means the file is exactly what Ubuntu signed. The warning only means rocky-lab has not yet verified the fingerprint of Ubuntu's key, like you did in step 7.
    :::

9. Tamper with the file and verify again:

    ```bash
    # on rocky-lab
    echo "Migration starts Saturday" > plans.txt
    gpg --verify plans.txt.sig plans.txt
    ```

    ```{.output}
    gpg: BAD signature from "Student Ubuntu <student@ubuntu-lab.example>" [unknown]
    ```

::: checkpoint
**Checkpoint:** rocky-lab decrypted `plans.enc.asc`, `gpg --verify` said "Good signature" on the original file, and "BAD signature" after you changed it.
:::

#### Task 3: Encrypt a disk with LUKS2

::: warning
This erases an extra disk. Take a snapshot of ubuntu-lab now. Run `lsblk` and make sure `/dev/sdb` is an empty 5 GB disk with no partitions or mount points. If your disk has a different name (`vdb`, `nvme0n2`), use that name in every command.
:::

1. Confirm the disk and install the tools:

    ```bash
    lsblk
    sudo apt install -y cryptsetup
    ```

2. Format the disk as LUKS2:

    ```bash
    sudo cryptsetup luksFormat --type luks2 /dev/sdb
    ```

    ```{.output}
    WARNING!
    ========
    This will overwrite data on /dev/sdb irrevocably.

    Are you sure? (Type 'yes' in capital letters): YES
    Enter passphrase for /dev/sdb:
    Verify passphrase:
    ```

    Type `YES` in capitals, then a passphrase such as `Luks-Lab-Pass-1`.

    ::: explain
    **What just happened:** `luksFormat` wrote a LUKS header to the start of the disk, generated a random master key, and locked it in key slot 0 with your passphrase. `--type luks2` asks for version 2 explicitly (it is already the default on Ubuntu 24.04 and Rocky 9). It took a couple of seconds because Argon2id deliberately works hard on each passphrase.
    :::

3. Look at the header:

    ```bash
    sudo cryptsetup luksDump /dev/sdb
    ```

    ```{.output}
    LUKS header information
    Version:       	2
    ...
    Data segments:
      0: crypt
    	offset: 16777216 [bytes]
    	length: (whole device)
    	cipher: aes-xts-plain64
    	sector: 512 [bytes]

    Keyslots:
      0: luks2
    	Key:        512 bits
    	Priority:   normal
    	Cipher:     aes-xts-plain64
    	Cipher key: 512 bits
    	PBKDF:      argon2id
    	Time cost:  4
    	Memory:     1048576
    	Threads:    2
    ...
    ```

    ::: explain
    **What just happened:** `Version: 2` confirms LUKS2. The data is encrypted with `aes-xts-plain64` (AES in XTS mode, the standard mode for disk encryption) with a 512-bit key (XTS splits it into two 256-bit keys). Key slot 0 uses `PBKDF: argon2id` with `Memory: 1048576` KiB, meaning every passphrase guess needs about 1 GiB of RAM. That is what makes brute-force attacks so slow and expensive. Your time and memory numbers may differ; `cryptsetup` benchmarks your machine.
    :::

4. Open (unlock) the disk, create a filesystem, and mount it:

    ```bash
    sudo cryptsetup open /dev/sdb labcrypt
    ls -l /dev/mapper/labcrypt
    sudo mkfs.ext4 -q /dev/mapper/labcrypt
    sudo mkdir -p /mnt/secure
    sudo mount /dev/mapper/labcrypt /mnt/secure
    echo "TOPSECRET payroll data" | sudo tee /mnt/secure/payroll.txt
    lsblk /dev/sdb
    ```

    ```{.output}
    NAME         MAJ:MIN RM SIZE RO TYPE  MOUNTPOINTS
    sdb            8:16   0   5G  0 disk
    └─labcrypt   252:0    0   5G  0 crypt /mnt/secure
    ```

    ::: explain
    **What just happened:** `cryptsetup open` asked for the passphrase and created a *mapped* device, `/dev/mapper/labcrypt`. Everything written to it is encrypted before it reaches `/dev/sdb`, and decrypted when read back. You put a normal ext4 filesystem **on top of** the encrypted layer. `lsblk` shows the `crypt` layer between the disk and the mount point.
    :::

5. Prove the raw disk holds only ciphertext:

    ```bash
    sync
    sudo grep -a -c TOPSECRET /dev/sdb
    sudo blkid /dev/sdb
    ```

    ```{.output}
    0
    /dev/sdb: UUID="5b1e2c3d-..." TYPE="crypto_LUKS"
    ```

    ::: explain
    **What just happened:** `sync` flushes data to disk. `grep -a` treats the binary disk as text and `-c` counts matching lines. The word appears 0 times on the raw disk, because only encrypted bytes are stored there. If someone steals the disk or a backup image of it, they get nothing without a passphrase. `blkid` shows the type `crypto_LUKS` and the LUKS UUID.
    :::

6. Add a second passphrase (for example, a recovery passphrase kept in a safe) and test it:

    ```bash
    sudo cryptsetup luksAddKey /dev/sdb
    sudo cryptsetup luksDump /dev/sdb | grep -E '^ +[0-9]+: luks2'
    sudo cryptsetup open --test-passphrase /dev/sdb && echo "passphrase OK"
    ```

    ```{.output}
      0: luks2
      1: luks2
    passphrase OK
    ```

    ::: explain
    **What just happened:** `luksAddKey` first asks for an **existing** passphrase (to unlock the master key), then for the new one (try `Luks-Recovery-2`), and stores the master key in slot 1. For the test, type the new passphrase: `--test-passphrase` checks it without creating a mapping. To remove a slot later: `sudo cryptsetup luksKillSlot /dev/sdb 1`. Back up the header with `cryptsetup luksHeaderBackup`; if the header is damaged, all slots are lost.
    :::

7. Lock the disk again:

    ```bash
    sudo umount /mnt/secure
    sudo cryptsetup close labcrypt
    ls /dev/mapper/
    ```

    ::: explain
    **What just happened:** Unmount first, then `close` removes the mapping and wipes the master key from memory. Now the disk is just ciphertext until someone types a passphrase.
    :::

::: tip
To unlock a LUKS disk automatically at boot you add a line to **`/etc/crypttab`** and a normal line to `/etc/fstab`. In `/etc/crypttab` the fields are: mapped name, device, key file (`none` = ask for the passphrase at boot), options:

```text
labcrypt  UUID=5b1e2c3d-...  none  luks
```

and in `/etc/fstab`: `/dev/mapper/labcrypt  /mnt/secure  ext4  defaults,nofail  0  2`. You do not need to add these for this lab. Ubuntu's installer uses the same mechanism (with LVM on top) for full-disk encryption.
:::

::: checkpoint
**Checkpoint:** `sudo cryptsetup luksDump /dev/sdb` shows `Version: 2`, `PBKDF: argon2id`, and two key slots, and `/dev/mapper/labcrypt` no longer exists.
:::

#### Task 4: Build a small CA and see why self-signed certificates fail

You will first serve a **self-signed** certificate and watch clients reject it. Then you will create your own CA, sign a server certificate with it, and add the CA to the trust store.

1. Make a folder for keys and certificates, and create a self-signed certificate:

    ```bash
    mkdir -p ~/labs/3.5/pki && cd ~/labs/3.5/pki
    openssl req -x509 -newkey rsa:2048 -nodes -keyout selfsigned.key \
      -out selfsigned.crt -days 30 -subj "/CN=localhost"
    openssl x509 -in selfsigned.crt -noout -subject -issuer
    ```

    ```{.output}
    subject=CN = localhost
    issuer=CN = localhost
    ```

    ::: explain
    **What just happened:** `openssl req` normally creates a certificate *request*; `-x509` makes it create a finished certificate instead. `-newkey rsa:2048` generates a new RSA key, `-nodes` ("no DES") leaves the private key unencrypted so a server can read it, and `-subj` sets the name without questions. The subject and issuer are the same: the certificate vouches for itself. That is what self-signed means.
    :::

2. Serve it with OpenSSL's test server. Open a **second terminal**, and run:

    ```bash
    cd ~/labs/3.5/pki
    openssl s_server -accept 8443 -cert selfsigned.crt -key selfsigned.key -www
    ```

    ::: explain
    **What just happened:** `openssl s_server` is a tiny TLS server for testing. `-accept 8443` listens on port 8443, and `-www` answers web requests with a status page. Leave it running.
    :::

3. In your first terminal, connect as a client:

    ```bash
    curl https://localhost:8443/
    openssl s_client -connect localhost:8443 </dev/null 2>/dev/null | grep -E 'Verify return'
    ```

    ```{.output}
    curl: (60) SSL certificate problem: self-signed certificate
    More details here: https://curl.se/docs/sslcerts.html
    ...
    Verify return code: 18 (self-signed certificate)
    ```

    ::: explain
    **What just happened:** `curl` refused to connect because nothing it trusts signed this certificate. `openssl s_client` is the client-side test tool; `-connect host:port` opens a TLS connection, and `</dev/null` closes it right away. Error 18 means self-signed. You *could* use `curl -k` (ignore errors), but then curl would also accept an attacker's certificate. This is why self-signed leaf certificates are dangerous: they train people to bypass the warning.
    :::

    Stop the server with `Ctrl+C` in the second terminal.

4. Create your own CA: a private key and a self-signed **root** certificate that is allowed to sign other certificates:

    ```bash
    openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out ca.key
    openssl req -x509 -new -key ca.key -sha256 -days 3650 \
      -subj "/O=Lab/CN=Lab Root CA" -out ca.crt
    openssl x509 -in ca.crt -noout -text | grep -A1 'Basic Constraints'
    ```

    ```{.output}
                X509v3 Basic Constraints: critical
                    CA:TRUE
    ```

    ::: explain
    **What just happened:** `genpkey` generated a 4096-bit RSA private key for the CA. `req -x509` made a 10-year (`-days 3650`) root certificate signed with SHA-256. `CA:TRUE` means this certificate may sign other certificates. A root CA is always self-signed; that is fine, because it is not used directly by a server. It is trusted only because you choose to install it, the same way Ubuntu installs the public roots for you. Protect `ca.key`: anyone who has it can create certificates your machines will trust.
    :::

5. Create a server key and a certificate signing request (CSR), then sign it with the CA:

    ```bash
    openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key
    openssl req -new -key server.key -subj "/CN=ubuntu-lab" -out server.csr
    cat <<'EOF' > server.ext
    basicConstraints = CA:FALSE
    keyUsage = critical, digitalSignature, keyEncipherment
    extendedKeyUsage = serverAuth
    subjectAltName = DNS:ubuntu-lab, DNS:localhost, IP:127.0.0.1
    EOF
    openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
      -days 397 -sha256 -extfile server.ext -out server.crt
    openssl verify -CAfile ca.crt server.crt
    ```

    ```{.output}
    Certificate request self-signature ok
    subject=CN = ubuntu-lab
    server.crt: OK
    ```

    ::: explain
    **What just happened:**

    - The server got its own key (an elliptic-curve P-256 key, smaller and faster than RSA).
    - The **CSR** contains the server's public key and name. In real life you send the CSR (never the key) to a CA.
    - `server.ext` lists *extensions*. The most important is `subjectAltName` (SAN): modern clients check the name you connect to against the SAN list, not the CN. `extendedKeyUsage = serverAuth` limits the certificate to TLS servers. (The heredoc `<<'EOF'` writes the lines up to `EOF` into the file.)
    - `openssl x509 -req` signed the CSR with the CA key. `-CAcreateserial` creates `ca.srl` to give each certificate a unique serial number. 397 days is the maximum lifetime public CAs may issue today.
    - `openssl verify` confirms the chain: `server.crt` was signed by `ca.crt`.
    :::

#### Task 6: Build a WireGuard tunnel between the VMs

You will create a private network `10.200.0.0/24` inside an encrypted tunnel: ubuntu-lab will be `10.200.0.1` and rocky-lab `10.200.0.2`.

```{.diagram}
 ubuntu-lab  wg0 10.200.0.1  ===== encrypted UDP 51820 =====  wg0 10.200.0.2  rocky-lab
   192.168.100.10                  (over the lab network)          192.168.100.20
```

1. Install the tools and generate a key pair on **each** VM:

    ```bash
    sudo apt install -y wireguard-tools
    sudo mkdir -p /etc/wireguard
    sudo sh -c 'umask 077; wg genkey | tee /etc/wireguard/wg.key | wg pubkey > /etc/wireguard/wg.pub'
    sudo cat /etc/wireguard/wg.pub
    ```

    ```bash
    # on rocky-lab
    sudo dnf install -y wireguard-tools
    sudo modprobe wireguard && lsmod | grep wireguard
    sudo mkdir -p /etc/wireguard
    sudo sh -c 'umask 077; wg genkey | tee /etc/wireguard/wg.key | wg pubkey > /etc/wireguard/wg.pub'
    sudo cat /etc/wireguard/wg.pub
    ```

    ::: explain
    **What just happened:** `wg genkey` creates a random private key; `wg pubkey` derives the public key from it. `umask 077` makes the new files readable only by root. `sh -c '...'` runs the whole pipeline as root, so the redirection `>` also happens as root. On Rocky, `modprobe` loads the WireGuard kernel module, which is part of the Rocky 9 kernel. Write down both **public** keys; each side needs the other's.
    :::

2. On ubuntu-lab, create `/etc/wireguard/wg0.conf`. Show your private key with `sudo cat /etc/wireguard/wg.key`, then open the file with `sudo nano /etc/wireguard/wg0.conf` and enter:

    ```ini
    [Interface]
    Address = 10.200.0.1/24
    ListenPort = 51820
    PrivateKey = <ubuntu-lab private key from /etc/wireguard/wg.key>

    [Peer]
    PublicKey = <rocky-lab public key>
    Endpoint = rocky-lab:51820
    AllowedIPs = 10.200.0.2/32
    ```

    ::: explain
    **What just happened:** `[Interface]` describes this side: its tunnel address, its UDP port, and its private key. `[Peer]` describes the other side: its public key, where to reach it (`Endpoint`), and `AllowedIPs`, which means "packets for these addresses go to this peer, and packets from this peer may only use these source addresses". This is WireGuard's "cryptokey routing".
    :::

3. On rocky-lab, create the mirror image in `/etc/wireguard/wg0.conf` (`sudo vi` or `sudo nano` after `sudo dnf install -y nano`):

    ```ini
    PrivateKey = <rocky-lab private key from /etc/wireguard/wg.key>

    [Peer]
    PublicKey = <ubuntu-lab public key>
    Endpoint = ubuntu-lab:51820
    AllowedIPs = 10.200.0.1/32
    ```

    ::: explain
    **What just happened:** `firewall-cmd --add-port=51820/udp` allows WireGuard packets into rocky-lab (Ubuntu's `ufw` is inactive by default, so no rule is needed there). `wg-quick up wg0` reads `wg0.conf` and prints each step: create a `wireguard` interface, load the keys and peer, add the address, and bring the link up. #### Task 7: Remove weak algorithms

1. On ubuntu-lab, list the algorithms SSH supports and the ones the server actually offers:

    ```bash
    ssh -Q cipher
    ssh -Q mac
    sudo sshd -T | grep -E '^(ciphers|macs|kexalgorithms) '
    ```

    ```{.output}
    ciphers chacha20-poly1305@openssh.com,aes128-ctr,aes192-ctr,aes256-ctr,aes128-gcm@openssh.com,aes256-gcm@openssh.com
    macs umac-64-etm@openssh.com,umac-128-etm@openssh.com,hmac-sha2-256-etm@openssh.com,hmac-sha2-512-etm@openssh.com,hmac-sha1-etm@openssh.com,umac-64@openssh.com,umac-128@openssh.com,hmac-sha2-256,hmac-sha2-512,hmac-sha1
    kexalgorithms sntrup761x25519-sha512@openssh.com,curve25519-sha256,...
    ```

    ::: explain
    **What just happened:** `ssh -Q` lists everything the SSH program *can* use, including old algorithms like `3des-cbc` kept for compatibility. `sshd -T` prints the server's *effective* settings. The server still offers MACs based on SHA-1 (`hmac-sha1`) and 64-bit tags (`umac-64`). They are not broken in practice inside SSH, but security baselines (CIS, STIG) require removing them.
    :::

2. First prove the server accepts `hmac-sha1`. `BatchMode=yes` stops at the password prompt, so you only test the negotiation:

    ```bash
    ssh -o MACs=hmac-sha1 -o BatchMode=yes student@localhost true
    ```

    ```{.output}
    student@localhost: Permission denied (publickey,password).
    ```

    ::: explain
    **What just happened:** "Permission denied" sounds bad, but it means the algorithm negotiation **succeeded** and SSH reached the login step (which BatchMode refuses to do interactively). If you set up SSH keys in Lab 3.3, the command simply logs in, runs `true`, and prints nothing; that also means it was accepted.
    :::

3. Remove the weak MACs with a drop-in file and test again:

    ```bash
    cat <<'EOF' | sudo tee /etc/ssh/sshd_config.d/40-crypto.conf
    MACs -hmac-sha1,hmac-sha1-etm@openssh.com,umac-64@openssh.com,umac-64-etm@openssh.com
    EOF
    sudo sshd -t && sudo systemctl reload ssh
    sudo sshd -T | grep '^macs '
    ssh -o MACs=hmac-sha1 -o BatchMode=yes student@localhost true
    ```

    ```{.output}
    macs umac-128-etm@openssh.com,hmac-sha2-256-etm@openssh.com,hmac-sha2-512-etm@openssh.com,umac-128@openssh.com,hmac-sha2-256,hmac-sha2-512
    Unable to negotiate with 127.0.0.1 port 22: no matching MAC found. Their offer: umac-128-etm@openssh.com,hmac-sha2-256-etm@openssh.com,...
    ```

    ::: explain
    **What just happened:** A list that starts with `-` removes those entries from the built-in default list (a `+` would add, `^` would move to the front). Removing is safer than writing a full list, because you keep future good defaults. The drop-in is read before the main file and `sshd` uses the first value it finds, so it wins. Now a client that insists on `hmac-sha1` cannot connect. Old SSH ciphers like `3des-cbc` and the SHA-1 `ssh-rsa` signature are already disabled by default in OpenSSH 9.x.
    :::

4. On rocky-lab, weak algorithms are managed system-wide by **crypto policies**. See the current policy and what it means for SSH:

    ```bash
    # on rocky-lab

    grep -E '^(Ciphers|MACs)' /etc/crypto-policies/back-ends/opensshserver.config
    ```

    ```{.output}

    Ciphers aes256-gcm@openssh.com,chacha20-poly1305@openssh.com,aes256-ctr,aes128-gcm@openssh.com,aes128-ctr
    ```

    ::: explain
    **What just happened:** One setting controls OpenSSL, GnuTLS, NSS, OpenSSH, Kerberos, Java, and more. `update-crypto-policies` writes a file for each library in `/etc/crypto-policies/back-ends/`. The policies are: `LEGACY` (allows old algorithms for compatibility), `DEFAULT` (sensible today; SHA-1 signatures and TLS 1.0/1.1 already off), `FUTURE` (stricter: RSA keys at least 3072 bits, no SHA-1 at all, 128-bit AES ciphers removed), and `FIPS` (only FIPS 140 approved algorithms).
    :::

### Clean up

1. Stop WireGuard on both VMs and remove the configs:

    ```bash

    sudo rm -rf /etc/wireguard/wg0.conf /etc/wireguard/wg.key /etc/wireguard/wg.pub
    sudo firewall-cmd --reload
    ```

    (`firewall-cmd --reload` drops runtime-only rules like the 51820/udp opening.)

2. Remove the nginx site, nginx, certbot, and the lab CA from the trust store:

    ```bash
    sudo rm -f /etc/nginx/sites-enabled/lab-tls /etc/nginx/sites-available/lab-tls
    sudo rm -rf /etc/nginx/lab-tls
    sudo apt purge -y nginx nginx-common certbot python3-certbot-nginx
    sudo apt autoremove -y
    sudo rm -f /usr/local/share/ca-certificates/lab-root-ca.crt
    sudo update-ca-certificates --fresh
    ```

3. Remove the SSH drop-in:

    ```bash
    sudo rm -f /etc/ssh/sshd_config.d/40-crypto.conf
    sudo sshd -t && sudo systemctl reload ssh
    ```

4. Cryptographically erase and wipe the LUKS disk (make sure it is closed first):

    ```bash
    sudo cryptsetup luksErase /dev/sdb
    sudo wipefs -a /dev/sdb
    sudo rmdir /mnt/secure
    ```

    `luksErase` destroys every key slot (type `YES`), so the master key, and with it the data, is gone forever. `wipefs -a` then removes the LUKS signature.

5. Delete the GPG keys and lab files on both VMs. Use the fingerprints shown by `gpg --list-secret-keys`:

    ```bash
    gpg --list-secret-keys --with-colons | awk -F: '/^fpr/{print $10}'
    gpg --batch --yes --delete-secret-and-public-key <FINGERPRINT>
    gpg --batch --yes --delete-key student@rocky-lab.example
    rm -rf ~/labs/3.5
    ```

    ```bash
    # on rocky-lab
    gpg --list-secret-keys --with-colons | awk -F: '/^fpr/{print $10}'
    gpg --batch --yes --delete-secret-and-public-key <FINGERPRINT>
    gpg --batch --yes --delete-key student@ubuntu-lab.example
    rm -rf ~/labs/3.5
    ```

    (Use the first fingerprint printed; that is the primary key. Deleting a secret key in batch mode requires the full fingerprint.)

### Exam corner

- **Data at rest**: GPG for files (`gpg -c` symmetric; `gpg -e -r` to a recipient; `--detach-sign` and `--verify`), LUKS2 for block devices (`cryptsetup luksFormat --type luks2`, `open`, `close`, `luksAddKey`, `luksDump`, `luksErase`), and `/etc/crypttab` for unlocking at boot.
- LUKS2 uses **Argon2id** (memory-hard) as its default PBKDF; LUKS1 used PBKDF2. Up to 32 key slots unlock one master key.
- **Data in transit**: TLS (via OpenSSL or LibreSSL), SSH, and VPNs such as WireGuard (UDP 51820, `wg`, `wg-quick`, `[Interface]`/`[Peer]`, `AllowedIPs`).
- Allowed **TLS** versions: 1.2 and 1.3. SSLv2, SSLv3, TLS 1.0 and 1.1 are deprecated. Test with `openssl s_client -connect host:443 -tls1_2` and `nmap --script ssl-enum-ciphers`.
- **LibreSSL** is OpenBSD's 2014 fork of OpenSSL; `openssl version` tells you which you have.
- **SHA-256**: `sha256sum file`, `sha256sum -c SHA256SUMS`. **HMAC** adds a secret key: `openssl dgst -sha256 -hmac KEY file`.
- **Weak algorithms** to remove: MD5, SHA-1, DES/3DES, RC4, short RSA keys. Use `sshd_config` (`Ciphers`, `MACs`, `KexAlgorithms`) and `update-crypto-policies --set DEFAULT|FUTURE|LEGACY|FIPS` on RHEL.
- **Trusted root** stores: Ubuntu `/usr/local/share/ca-certificates/` + `update-ca-certificates` (bundle in `/etc/ssl/certs/`); RHEL `/etc/pki/ca-trust/source/anchors/` + `update-ca-trust`.
- **No-cost** CA: Let's Encrypt via ACME/`certbot`, 90-day automated certificates. **Commercial** CA: paid, OV/EV validation, support and warranties.
- Avoid **self-signed** leaf certificates; they cannot be verified and teach users to ignore warnings. Use a public CA or a private internal CA whose root you distribute.

**Review questions**

1. Which key derivation function does LUKS2 use by default to protect key slots? A. PBKDF2 B. bcrypt C. Argon2id D. scrypt
2. What is the difference between `sha256sum report.txt` and `openssl dgst -sha256 -hmac secret report.txt`?
3. You copied `corp-ca.crt` into `/usr/local/share/ca-certificates/` on Ubuntu, but curl still does not trust the internal site. What command did you forget?
4. Which nginx directive removes TLS 1.0 and TLS 1.1? A. `ssl_ciphers HIGH` B. `ssl_protocols TLSv1.2 TLSv1.3` C. `ssl_prefer_server_ciphers on` D. `ssl_version 1.2`
5. On Rocky Linux, which command makes the whole system reject SHA-1 and RSA keys shorter than 3072 bits?
6. In a WireGuard config, what does `AllowedIPs = 10.200.0.2/32` in a `[Peer]` section do?

::: answers
1. **C.** LUKS2 defaults to Argon2id, a memory-hard function that makes passphrase guessing expensive; LUKS1 used PBKDF2.
2. `sha256sum` is a plain hash anyone can recompute after changing the file; the HMAC mixes in a secret key, so only someone with the key can produce a valid value, proving integrity and authenticity.
3. `sudo update-ca-certificates`, which links the new CA into `/etc/ssl/certs` and rebuilds the CA bundle.
4. **B.** `ssl_protocols TLSv1.2 TLSv1.3` allows only those two versions.
5. `sudo update-crypto-policies --set FUTURE` (then restart services or reboot).
6. It routes traffic for `10.200.0.2` to that peer and only accepts packets from that peer whose source address is `10.200.0.2` (cryptokey routing).
:::
