### What you'll practice

- Kernel modules: `depmod`, `insmod`, `lsmod`, `modinfo`, `modprobe`, `rmmod`
- Device management: `dmesg`, `dmidecode`, `ipmitool`, `lm_sensors`, `lscpu`, `lshw`, `lsmem`, `lspci`, `lsusb`

### How it works

**Kernel modules.** The Linux kernel needs a driver for every piece of hardware and many features (filesystems, firewalls, virtual network devices). Building all of them into the kernel would make it huge. Instead, most drivers are **kernel modules**: separate files that the kernel can load into memory when needed and unload when not. Think of the kernel as a game console and modules as cartridges you plug in.

Modules for each kernel version live in `/lib/modules/<version>/`. On Ubuntu 24.04 they end in `.ko.zst` (a kernel object compressed with zstd); on Rocky 9 they end in `.ko.xz`. Many modules need other modules first. For example, a filesystem module may need a checksum module. The file `modules.dep` in the same folder lists these dependencies.

```{.diagram}
 /lib/modules/6.8.0-45-generic/
   kernel/drivers/net/dummy.ko.zst     <- module files
   modules.dep                         <- "who needs whom", built by depmod
   modules.alias                       <- hardware IDs -> module names

 modprobe dummy  --> reads modules.dep + /etc/modprobe.d/*.conf
                 --> loads dependencies first, then dummy (with options)
 insmod FILE     --> loads exactly one file, no dependencies, no config
 rmmod dummy     --> unloads one module
 modprobe -r     --> unloads a module and its unused dependencies
```

The commands:

| Command | Job |
|---|---|
| `lsmod` | List loaded modules, their size, and which modules use them. |
| `modinfo` | Show a module's file, description, license, dependencies, and options (parameters). |
| `modprobe` | The smart way to load (`modprobe NAME`) or unload (`modprobe -r NAME`) a module. Handles dependencies and reads configuration from `/etc/modprobe.d/`. |
| `insmod` | The low-level way to load one module **file** by its full path. No dependency handling. |
| `rmmod` | The low-level way to unload one module. |
| `depmod` | Rebuilds `modules.dep` and the other index files. Run it after adding a module file by hand. Package installs run it for you. |

Most of the time you never load modules yourself: when the kernel or `udev` (the device manager) sees new hardware, it looks up the hardware ID in `modules.alias` and runs `modprobe` automatically. Files in `/etc/modprobe.d/` can set options (`options NAME key=value`), stop automatic loading (`blacklist NAME`), or stop all loading (`install NAME /bin/false`). Files in `/etc/modules-load.d/` list modules to load at every boot.

**Device inspection tools.** Linux gives you a tool for each kind of hardware question:

| Tool | Answers |
|---|---|
| `lscpu` | What CPU, how many cores, which architecture? |
| `lsmem` | How is memory laid out, how much is online? |
| `lspci` | What is on the PCI bus (disk controllers, network and graphics cards)? `-k` shows the driver in use. |
| `lsusb` | What USB devices are attached? |
| `lshw` | Everything, as a tree (package `lshw`). |
| `dmidecode` | What does the firmware (DMI/SMBIOS table) say: vendor, model, serial number, memory slots? |
| `dmesg` | What did the kernel say while detecting hardware? |
| `lm_sensors` (`sensors`) | What are the temperatures, voltages, and fan speeds? |
| `ipmitool` | Talk to the server's BMC (Baseboard Management Controller) over IPMI: power on/off remotely, read hardware sensors and logs. |
| `nvtop` | How busy are the GPUs (like `top` for graphics cards)? |

**The initrd.** As you saw in Lab 1.1, the initrd (initramfs) is a small archive loaded with the kernel. It carries the modules needed to reach the root filesystem (disk controller, LVM, RAID, encryption drivers). If you change hardware or need a new driver early in boot, you must rebuild it. Ubuntu uses **initramfs-tools** and the command `update-initramfs`. Red Hat-family systems use **dracut**. **mkinitrd** is the old Red Hat tool that dracut replaced; where it still exists it is a thin wrapper that calls dracut.

**Custom hardware.** An **embedded system** is a computer built into a device to do one job: a router, a smart TV, a car dashboard, an industrial controller. They often use ARM or RISC-V CPUs, little memory, flash storage, and a stripped-down Linux built with tools like Yocto or Buildroot, often with BusyBox instead of the full GNU tools. Hardware on ARM boards is described by a **device tree** file instead of being discovered over PCI. A **GPU** (graphics processing unit) has thousands of small cores and is used on servers for AI and machine learning training and inference, video transcoding, scientific computing (HPC), and virtual desktops. GPUs need a driver (often a proprietary kernel module such as `nvidia`) and monitoring tools such as `nvtop` or `nvidia-smi`.

### Tasks

#### Task 1: List and inspect kernel modules

1. Create the lab directory on ubuntu-lab.

    ```bash
    mkdir -p ~/labs/1.2 && cd ~/labs/1.2
    ```

2. List the loaded modules. There are many, so look at the first few lines and count them.

    ```bash
    lsmod | head -6
    lsmod | wc -l
    ```

    ```{.output}
    Module                  Size  Used by
    tls                   155648  0
    isofs                  61440  0
    binfmt_misc            28672  1
    intel_rapl_msr         20480  0
    ext4                 1064960  1
    84
    ```

    ::: explain
    **What just happened:** `lsmod` reads `/proc/modules` and prints it as a table. **Module** is the module name, **Size** is the memory it uses in bytes, and **Used by** is a count followed by the names of modules that depend on it. A module with a count above 0 cannot be unloaded until its users are gone. Your list will differ depending on your virtualization software.
    :::

3. Inspect the `dummy` module. It creates fake network interfaces, so it is safe to experiment with.

    ```bash
    modinfo dummy
    ```

    ```{.output}
    filename:       /lib/modules/6.8.0-45-generic/kernel/drivers/net/dummy.ko.zst
    alias:          rtnl-link-dummy
    description:    Dummy netdevice driver which discards all packets sent to it
    license:        GPL
    srcversion:     6D4E8F1A0B2C3D4E5F6A7B8
    depends:
    retpoline:      Y
    intree:         Y
    name:           dummy
    vermagic:       6.8.0-45-generic SMP preempt mod_unload modversions
    parm:           numdummies:Number of dummy pseudo devices (int)
    ```

    ::: explain
    **What just happened:** `modinfo` reads information stored inside the module file. The key fields are: **filename** (where the file is), **alias** (other names that trigger it; `rtnl-link-dummy` means "load me when someone asks for a dummy link"), **license**, **depends** (empty: no other modules needed), **vermagic** (the kernel version it was built for; it must match the running kernel), and **parm** (options you can set, here `numdummies`, an integer).
    :::

    ::: tip
    If `modinfo dummy` says `Module dummy not found`, your kernel package does not include the extra drivers. Install them with `sudo apt install -y linux-modules-extra-$(uname -r)` and try again.
    :::

4. Ask for single fields. `-F` prints one field, and `-n` prints only the file name.

    ```bash
    modinfo -F license dummy
    modinfo -n dummy
    modinfo -F depends ext4
    ```

    ```{.output}
    GPL
    /lib/modules/6.8.0-45-generic/kernel/drivers/net/dummy.ko.zst
    mbcache,jbd2
    ```

    ::: explain
    **What just happened:** The `ext4` filesystem module depends on `mbcache` and `jbd2` (the journaling layer). That is why `modprobe` exists: it loads those two first. If the depends line for `ext4` is empty, `ext4` is built into your kernel; try `modinfo -F depends btrfs` instead.
    :::

::: checkpoint
**Checkpoint:** `lsmod | grep -c dummy` prints `0` (not loaded yet), and `modinfo -F parm dummy` prints the `numdummies` option.
:::

#### Task 2: Load and unload modules with modprobe, insmod, and rmmod

1. Load `dummy` with `modprobe` and check that it worked.

    ```bash
    sudo modprobe dummy
    lsmod | grep dummy
    ip -br link show type dummy
    ```

    ```{.output}
    dummy                  12288  0
    dummy0           DOWN           3a:9f:21:c4:07:5e <BROADCAST,NOARP>
    ```

    ::: explain
    **What just happened:** `modprobe dummy` found the module through `modules.dep` and loaded it. `modprobe` prints nothing when it succeeds. The module created one fake interface, `dummy0`. `ip -br link show type dummy` lists network links (`-br` means brief output) of type dummy.
    :::

2. Unload it with `modprobe -r`, then load it again with an option.

    ```bash
    sudo modprobe -r dummy
    sudo modprobe dummy numdummies=3
    ip -br link show type dummy
    ```

    ```{.output}
    dummy0           DOWN           3a:9f:21:c4:07:5e <BROADCAST,NOARP>
    dummy1           DOWN           d2:41:8c:5b:e0:13 <BROADCAST,NOARP>
    dummy2           DOWN           7e:02:9a:61:3f:c8 <BROADCAST,NOARP>
    ```

    ::: explain
    **What just happened:** Options (module parameters) are written as `name=value` after the module name. `numdummies=3` told the driver to create three interfaces. Options only take effect when a module is loaded, which is why you had to unload it first.
    :::

3. Unload it with the low-level `rmmod`, then load it with the low-level `insmod`. `insmod` needs the full path to the file, which `modinfo -n` gives you.

    ```bash
    sudo rmmod dummy
    sudo insmod $(modinfo -n dummy)
    lsmod | grep dummy
    sudo rmmod dummy
    ```

    ::: explain
    **What just happened:** `rmmod dummy` unloaded the module by name. `$(modinfo -n dummy)` expanded to the full path, for example `/lib/modules/6.8.0-45-generic/kernel/drivers/net/dummy.ko.zst`, and `insmod` loaded that exact file. `insmod` does not look up dependencies and does not read `/etc/modprobe.d/`. For a module with dependencies, such as `ext4`, `insmod` would fail with `Unknown symbol in module` unless you loaded every dependency first by hand. That is why administrators use `modprobe` and only use `insmod` for testing a module file that is not installed in `/lib/modules`.
    :::

4. See what `modprobe` would do for a module with dependencies, without loading anything.

    ```bash
    modprobe --show-depends vxlan
    ```

    ```{.output}
    insmod /lib/modules/6.8.0-45-generic/kernel/net/ipv4/udp_tunnel.ko.zst
    insmod /lib/modules/6.8.0-45-generic/kernel/net/ipv6/ip6_udp_tunnel.ko.zst
    insmod /lib/modules/6.8.0-45-generic/kernel/drivers/net/vxlan/vxlan.ko.zst
    ```

    ::: explain
    **What just happened:** `--show-depends` prints the `insmod` commands `modprobe` would run, in order: dependencies first, then the module. This is literally what `modprobe` does for you. Lines starting with `builtin` mean that piece is compiled into the kernel and needs no loading.
    :::

::: checkpoint
**Checkpoint:** `lsmod | grep -c dummy` prints `0` again, and you can explain why `modprobe` is preferred over `insmod` (dependencies and configuration).
:::

#### Task 3: Configure modules with /etc/modprobe.d and depmod

1. Make an option permanent. Files in `/etc/modprobe.d/` must end in `.conf`. This lab uses a **heredoc** with `sudo tee`: everything between `<<'EOF'` and the line `EOF` is sent to `tee`, which writes it to the file. You need `tee` because a plain `>` redirect would run without root rights.

    ```bash
    cat <<'EOF' | sudo tee /etc/modprobe.d/lab-dummy.conf
    # Lab 1.2: always create two dummy interfaces
    options dummy numdummies=2
    EOF
    sudo modprobe dummy
    ip -br link show type dummy
    sudo modprobe -r dummy
    ```

    ```{.output}
    # Lab 1.2: always create two dummy interfaces
    options dummy numdummies=2
    dummy0           DOWN           3a:9f:21:c4:07:5e <BROADCAST,NOARP>
    dummy1           DOWN           d2:41:8c:5b:e0:13 <BROADCAST,NOARP>
    ```

    ::: explain
    **What just happened:** `tee` echoed the file contents to the screen as it wrote them. When `modprobe` loaded `dummy`, it read the `options` line and passed `numdummies=2` automatically. This is how you tune drivers permanently, for example `options kvm_intel nested=1`.
    :::

2. Watch automatic loading happen. Asking for a dummy-type interface makes the kernel load the module by its alias.

    ```bash
    sudo ip link add lab0 type dummy
    lsmod | grep dummy
    sudo ip link delete lab0
    sudo modprobe -r dummy
    ```

    ::: explain
    **What just happened:** You never ran `modprobe`, yet `dummy` appears in `lsmod`. The kernel saw a request for link type `dummy`, asked `modprobe` for `rtnl-link-dummy` (the alias you saw in `modinfo`), and the module was loaded. Hardware drivers load the same way when `udev` sees a new device's ID.
    :::

3. Blacklist the module and try the same thing again.

    ```bash
    echo "blacklist dummy" | sudo tee /etc/modprobe.d/lab-blacklist.conf
    sudo ip link add lab0 type dummy
    ```

    ```{.output}
    blacklist dummy
    Error: Unknown device type.
    ```

    ::: explain
    **What just happened:** `blacklist dummy` tells `modprobe` to ignore the module's aliases, so automatic loading no longer works and `ip` cannot create the interface. Administrators blacklist drivers that misbehave or conflict, for example blacklisting `nouveau` before installing the proprietary NVIDIA driver.
    :::

4. A blacklist does **not** stop someone from loading the module by its real name. Prove it, then block it completely.

    ```bash
    sudo modprobe dummy && lsmod | grep dummy
    sudo modprobe -r dummy
    echo "install dummy /bin/false" | sudo tee -a /etc/modprobe.d/lab-blacklist.conf
    sudo modprobe dummy
    ```

    ```{.output}
    dummy                  12288  0
    install dummy /bin/false
    modprobe: ERROR: ../libkmod/libkmod-module.c:1047 command_do() Error running install
    command '/bin/false' for module dummy: retcode 1
    modprobe: ERROR: could not insert 'dummy': Invalid argument
    ```

    ::: explain
    **What just happened:** The explicit `modprobe dummy` still worked with only a blacklist. `tee -a` appends (`-a`) a second line. An `install` line replaces the loading step with a command of your choice; `/bin/false` always fails, so the module can never be loaded through `modprobe`. Security guides use this to disable unneeded filesystems and protocols (for example `install usb-storage /bin/false` to block USB disks).
    :::

5. Remove the blacklist so the module works again.

    ```bash
    sudo rm /etc/modprobe.d/lab-blacklist.conf
    sudo modprobe dummy && sudo modprobe -r dummy && echo "dummy loads again"
    ```

6. Look at the dependency database and rebuild it with `depmod`.

    ```bash
    ls -l /lib/modules/$(uname -r)/modules.dep
    grep -E '/ext4\.ko' /lib/modules/$(uname -r)/modules.dep
    sudo depmod -a
    ls -l /lib/modules/$(uname -r)/modules.dep
    ```

    ```{.output}
    -rw-r--r-- 1 root root 412345 Oct 10 09:11 /lib/modules/6.8.0-45-generic/modules.dep
    kernel/fs/ext4/ext4.ko.zst: kernel/lib/crc16.ko.zst kernel/fs/mbcache.ko.zst ...
    -rw-r--r-- 1 root root 412345 Oct 10 10:02 /lib/modules/6.8.0-45-generic/modules.dep
    ```

    ::: explain
    **What just happened:** Each line of `modules.dep` is `module: dependencies`. `depmod -a` scanned every module under `/lib/modules/$(uname -r)` and rewrote this file and the related index files (`modules.alias`, `modules.symbols`, and binary `.bin` versions). The timestamp changed, the content did not, because nothing was added. You run `depmod` after copying a module into `/lib/modules/<version>/` yourself (for example a vendor driver in the `updates/` or `extra/` folder); otherwise `modprobe` cannot find it. On Rocky, all these commands work exactly the same way.
    :::

::: checkpoint
**Checkpoint:** `ls /etc/modprobe.d/lab-*` shows only `lab-dummy.conf`, and `sudo modprobe dummy && ip -br link show type dummy` shows two interfaces. Unload it again with `sudo modprobe -r dummy`.
:::

Start by checking which inventory tools are already installed. `command -v` prints the path of each command it finds and stays silent for the ones it does not.

```bash
command -v lscpu lsmem lspci lsusb lshw dmidecode
```

    ```bash
    sudo dmidecode -s system-product-name
    sudo dmidecode -t memory | grep -E '^\s*(Size|Type|Speed):' | head -6
    ```

    ```{.output}
    H/W path        Device     Class          Description
    ===================================================
                               system         VirtualBox
    /0                         bus            VirtualBox
    /0/0                       memory         128KiB BIOS
    /0/1                       memory         4GiB System memory
    ```

    ::: explain
    **What just happened:** `lshw -short` prints one line per device in a hardware tree; `-class` filters by type (disk, network, memory, processor, display). In a VM the "hardware" is the hypervisor's virtual hardware, so you see VirtualBox, VMware, or QEMU.

    ```bash
    sudo dmesg -T | grep -E 'sd[a-e]\]|e1000|virtio' | head -8

    ```

    ```{.output}

    [Fri Oct 10 09:20:03 2026] sd 3:0:0:0: [sdb] 10485760 512-byte logical blocks: (5.37 GB/5.00 GiB)
    ```

    **What just happened:** `dmesg` prints the kernel ring buffer, a memory log of kernel messages since boot. `-T` converts the "seconds since boot" stamps into readable times. `--level=err,warn` shows only errors and warnings, a fast first step when a device misbehaves. You can see each disk being detected with its size, and the network driver naming the card `eth0` before `udev` renamed it to a predictable name (`enp0s3`). Run `sudo dmesg -w` to watch new messages live (for example, while plugging in a USB device), and press **Ctrl+C** to stop.

#### Task 5: Try the server and GPU hardware tools

::: tip
**Explore/simulate:** Virtual machines have no temperature sensors, no BMC for IPMI, and no GPU. You will install each tool, run it, and read the error, which is exactly what you would see on a real server with a missing driver or device. Then you will see the commands you would use on real hardware.
:::

1. Install the three tools. On Ubuntu the sensor package is called `lm-sensors`; on Rocky it is `lm_sensors`.

    ```bash
    sudo apt install -y lm-sensors ipmitool nvtop
    ```

2. Detect sensors and read them.

    ```bash
    sudo sensors-detect --auto | tail -4
    sensors
    ```

    ```{.output}
    No sensors were found.  Try loading the drivers manually,
    or check your BIOS/firmware.
    No sensors found!
    Make sure you loaded all the kernel drivers you need.
    Try sensors-detect at /usr/sbin/sensors-detect.
    ```

    ::: explain
    **What just happened:** `lm_sensors` (the project behind the `sensors` command) reads hardware monitoring chips. `sensors-detect --auto` probes for those chips, accepts all the default answers, and tells you which kernel modules to load (for example `coretemp` for Intel CPU temperatures). A VM has no such chips, so nothing is found. If you do see an entry such as `acpitz-acpi-0`, your hypervisor exposes a virtual sensor; that is fine. On a physical server, `sensors` prints lines such as `Core 0: +45.0°C (high = +80.0°C, crit = +100.0°C)` and fan speeds in RPM.
    :::

3. Try to talk to a BMC with `ipmitool`.

    ```bash
    sudo ipmitool sdr list
    ```

    ```{.output}
    Could not open device at /dev/ipmi0 or /dev/ipmi/0 or /dev/ipmidev/0: No such file or directory
    ```

    ::: explain
    **What just happened:** IPMI (Intelligent Platform Management Interface) is a standard for the BMC, a tiny separate computer on server motherboards (sold as Dell iDRAC, HPE iLO, Lenovo XClarity). It works even when the server is powered off or the OS has crashed. Locally, `ipmitool` talks to it through the device file `/dev/ipmi0`, which the `ipmi_si` and `ipmi_devintf` modules create when a BMC exists. No BMC means no device file.
    :::

4. Write down the commands you would use on a real server. Save them as a reference file. This does not run them.

    ```bash
    cat <<'EOF' > ~/labs/1.2/ipmi-cheatsheet.txt
    # Local BMC (needs: sudo modprobe ipmi_si ipmi_devintf)
    sudo ipmitool sdr list                 # all sensors: temps, fans, voltages
    sudo ipmitool sel list                 # System Event Log (hardware errors)
    sudo ipmitool lan print 1              # BMC network settings
    # Remote BMC over the network (IPMI v2.0 = lanplus interface)
    ipmitool -I lanplus -H 10.0.0.50 -U admin -P 'secret' chassis power status
    ipmitool -I lanplus -H 10.0.0.50 -U admin -P 'secret' chassis power cycle
    ipmitool -I lanplus -H 10.0.0.50 -U admin -P 'secret' sol activate   # serial console
    EOF
    cat ~/labs/1.2/ipmi-cheatsheet.txt
    ```

    ::: explain
    **What just happened:** `-I lanplus` selects the IPMI 2.0 network interface, `-H` is the BMC's IP address, and `-U`/`-P` are its user name and password. `chassis power` turns a server on, off, or power-cycles it remotely. `sol activate` (Serial over LAN) gives you the server's text console over the network, so you can watch it boot from home.
    :::

5. Look for a GPU and try `nvtop`.

    ```bash
    lspci | grep -i -E 'vga|3d|display'
    nvtop
    ```

    ```{.output}
    00:02.0 VGA compatible controller: VMware SVGA II Adapter
    No GPU to monitor.
    ```

    ::: explain
    **What just happened:** The VM has only a basic virtual display adapter, not a compute GPU. `nvtop` ("Neat Videocard TOP") monitors NVIDIA, AMD, and Intel GPUs: on a real GPU server it shows a live graph of GPU utilization, GPU memory use, temperature, power, and which processes use the GPU. A data center GPU shows up in `lspci` as `3D controller: NVIDIA Corporation ...`, and `lspci -k` would show the driver module (`nvidia` or the open-source `nouveau` or `amdgpu`).
    :::

**Checkpoint:** `command -v sensors ipmitool nvtop` prints three paths, and you can explain why each one reports "nothing found" in a VM.

#### Task 6: Rebuild the initrd on Ubuntu with update-initramfs

1. Check that `dummy` is not currently in the initrd. `lsinitramfs` lists the files inside.

    ```bash
    sudo lsinitramfs /boot/initrd.img-$(uname -r) | grep -c 'dummy.ko'
    ```

    ```{.output}
    0
    ```

2. Back up the current initrd, ask initramfs-tools to include the module, and rebuild. `/etc/initramfs-tools/modules` lists extra modules, one per line.

    ```bash
    sudo cp /boot/initrd.img-$(uname -r) /boot/initrd.img-$(uname -r).lab-backup
    echo "dummy" | sudo tee -a /etc/initramfs-tools/modules
    sudo update-initramfs -u -k $(uname -r)
    ```

    ```{.output}
    dummy
    update-initramfs: Generating /boot/initrd.img-6.8.0-45-generic
    ```

    ::: explain
    **What just happened:** `update-initramfs -u` updates (`-u`) an existing initrd, and `-k $(uname -r)` picks the running kernel's one (without `-k`, it updates the newest installed kernel, which may not be the one you booted). It works by re-running all the scripts in `/etc/initramfs-tools/` and `/usr/share/initramfs-tools/`. Other options: `-k all` rebuilds for every installed kernel, and `-c` creates a new one (used when a kernel is first installed). The package manager runs this automatically after installing a kernel or a driver package, which is why you rarely run it by hand.
    :::

3. Verify the module is now inside.

    ```bash
    sudo lsinitramfs /boot/initrd.img-$(uname -r) | grep 'dummy.ko'
    ```

    ```{.output}
    usr/lib/modules/6.8.0-45-generic/kernel/drivers/net/dummy.ko.zst
    ```

4. Remove the line you added and rebuild so the initrd is back to normal. `sed -i '/^dummy$/d'` deletes lines that contain exactly `dummy`.

    ```bash
    sudo sed -i '/^dummy$/d' /etc/initramfs-tools/modules
    sudo update-initramfs -u -k $(uname -r)
    sudo lsinitramfs /boot/initrd.img-$(uname -r) | grep -c 'dummy.ko'
    ```

    ::: explain
    **What just happened:** After the rebuild the count is `0` again. The backup copy you made is your safety net: if a rebuilt initrd ever stops a system from booting, you can pick an older kernel in the GRUB menu or boot rescue media and copy the backup back.
    :::

::: checkpoint
**Checkpoint:** `grep -c '^dummy$' /etc/initramfs-tools/modules` prints `0`, and `ls /boot/*.lab-backup` shows your backup.
:::

#### Task 7: Rebuild the initrd on Rocky with dracut (and meet mkinitrd)

1. On rocky-lab, back up the current initramfs and list the dracut modules it contains.

    ```bash
    # on rocky-lab
    sudo cp /boot/initramfs-$(uname -r).img /boot/initramfs-$(uname -r).img.lab-backup
    sudo lsinitrd -m | head -12
    sudo lsinitrd | grep -c 'dummy.ko'
    ```

    ::: explain
    **What just happened:** dracut builds an initramfs from **dracut modules** (not the same as kernel modules): small script bundles such as `lvm`, `crypt`, `nfs`, `systemd`, and `kernel-modules`. By default dracut runs in "host-only" mode and includes only what this machine needs to boot, so the image is small. The count of `dummy.ko` is `0`.
    :::

2. Tell dracut to add the `dummy` kernel driver, then rebuild. Configuration goes in `/etc/dracut.conf.d/` in files ending with `.conf`. The spaces inside the quotes matter: dracut joins lists, and the spaces stop names from running together.

    ```bash
    # on rocky-lab
    echo 'add_drivers+=" dummy "' | sudo tee /etc/dracut.conf.d/lab.conf
    sudo dracut -f
    sudo lsinitrd | grep 'dummy.ko'
    ```

    ```{.output}
    add_drivers+=" dummy "
    -rw-r--r--   1 root  root  2412 Apr 30 12:00 usr/lib/modules/5.14.0-427.13.1.el9_4.x86_64/
    kernel/drivers/net/dummy.ko.xz
    ```

    ::: explain
    **What just happened:** `dracut` with no file name rebuilds `/boot/initramfs-$(uname -r).img`. `-f` (force) allows it to overwrite the existing file; without `-f` it refuses. You could also build an image for another kernel with `sudo dracut -f /boot/initramfs-VERSION.img VERSION`, add `-v` for verbose output, or add a driver just once with `--add-drivers dummy`. `lsinitrd` confirms the driver is inside.
    :::

3. Check for `mkinitrd`, the legacy tool.

    ```bash
    # on rocky-lab
    command -v mkinitrd && rpm -qf "$(command -v mkinitrd)" || echo "mkinitrd is not installed"
    ```

    ::: explain
    **What just happened:** `mkinitrd` was the Red Hat initrd builder before RHEL 6. Today, where it exists, it is a compatibility script shipped with dracut that translates the old syntax `mkinitrd /boot/initramfs-VERSION.img VERSION` into a `dracut` command. Depending on your Rocky release you will see either a path owned by the `dracut` package or the message that it is not installed. Either way, on the exam remember: **dracut** is the modern RHEL tool, **mkinitrd** is the legacy one, and Debian/Ubuntu use `update-initramfs` (mkinitramfs underneath).
    :::

4. Remove the lab configuration and rebuild to return to normal.

    ```bash
    # on rocky-lab
    sudo rm /etc/dracut.conf.d/lab.conf
    sudo dracut -f
    sudo lsinitrd | grep -c 'dummy.ko'
    ```

::: checkpoint
**Checkpoint:** On rocky-lab, `ls /etc/dracut.conf.d/` does not show `lab.conf`, `sudo lsinitrd | grep -c dummy.ko` prints `0`, and the backup file exists in `/boot`.
:::

#### Task 8: Explore embedded-system traits

::: tip
**Explore/simulate:** You do not need a Raspberry Pi for this task. You will look for the things that make embedded Linux different and see that your x86 VM lacks them, and you will use BusyBox, the toolbox most embedded systems are built on.
:::

1. Look for a device tree. ARM and RISC-V boards describe their hardware in a device tree that the bootloader passes to the kernel; PCs discover hardware with ACPI and PCI instead.

    ```bash
    ls /proc/device-tree 2>/dev/null || echo "No device tree: ACPI/PCI (PC-style) system"
    ls /sys/class/gpio 2>/dev/null || echo "No GPIO pins exposed"
    ```

    ::: explain
    **What just happened:** On a Raspberry Pi, `/proc/device-tree/model` would print something like `Raspberry Pi 4 Model B`, and `/sys/class/gpio` (or the newer `gpiod` tools) would let you control the GPIO (general-purpose input/output) pins that switch LEDs, relays, and sensors. Your VM has neither.
    :::

2. Use BusyBox. Ubuntu ships it for the initrd, and embedded systems use it as their whole command set.

    ```bash
    command -v busybox || sudo apt install -y busybox-static
    busybox | head -2
    busybox --list | wc -l
    busybox uptime
    ```

    ```{.output}
    BusyBox v1.36.1 (Ubuntu 1:1.36.1-6ubuntu3.1) multi-call binary.
    BusyBox is copyrighted by many authors between 1998-2015.
    401
    10:15:22 up  1:02,  1 users,  load average: 0.00, 0.01, 0.00
    ```

    ::: explain
    **What just happened:** The first line installs BusyBox only if no `busybox` command exists yet (`||` runs the install only when `command -v` fails). Ubuntu Server normally already has it. BusyBox is one small program that contains simplified versions of hundreds of commands (`ls`, `cp`, `sh`, `ip`, `vi`). On an embedded device, `/bin/ls` and friends are just links to `/bin/busybox`, which saves a lot of flash storage. Embedded devices are also usually built for ARM or RISC-V, run from read-only flash with a small writable area, and are updated by replacing the whole image rather than with `apt`.
    :::

::: checkpoint
**Checkpoint:** You can list three ways an embedded Linux system differs from your server VM (CPU architecture, device tree instead of PCI discovery, BusyBox and flash storage).
:::

### Exam corner

- `lsmod` lists loaded modules (from `/proc/modules`). `modinfo` shows a module's file, license, dependencies, and parameters.
- `modprobe NAME` loads a module plus its dependencies and reads `/etc/modprobe.d/*.conf`; `modprobe -r NAME` unloads it.
- `insmod /full/path/file.ko` loads one file without dependencies; `rmmod NAME` unloads one module.
- `depmod -a` rebuilds `modules.dep` in `/lib/modules/$(uname -r)/`; run it after adding a module file by hand.
- In `/etc/modprobe.d/`: `options NAME key=value` sets parameters, `blacklist NAME` stops automatic (alias) loading, `install NAME /bin/false` stops all loading. `/etc/modules-load.d/` loads modules at boot.
- `lspci -k` shows which kernel driver each PCI device uses; `lsusb` lists USB devices; `lscpu` CPU; `lsmem` memory blocks; `lshw` everything (`-short`, `-class`).
- `dmidecode` reads the firmware DMI/SMBIOS table: manufacturer, model, serial number, memory slots. `dmesg` shows kernel (hardware detection) messages.
- `lm_sensors`: run `sensors-detect`, then `sensors` for temperatures, voltages, and fans. `ipmitool` talks to the BMC locally (`/dev/ipmi0`) or remotely (`-I lanplus -H host`).
- Ubuntu rebuilds the initrd with `update-initramfs -u` (`-k all` for all kernels). RHEL/Rocky uses `dracut -f`; `mkinitrd` is the legacy tool (now a dracut wrapper). `lsinitrd` and `lsinitramfs` list contents.
- Embedded systems: single-purpose devices, often ARM/RISC-V, BusyBox, device tree, flash storage. GPUs are used for AI/ML, HPC, video transcoding, and VDI; monitor them with `nvtop`.
