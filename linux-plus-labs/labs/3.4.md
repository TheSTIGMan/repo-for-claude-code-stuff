## Lab 3.4: Harden User Accounts {#lab-3-4}

::: labinfo
**Objective:** 3.4 Explain account hardening techniques and best practices.\
**Domain:** 3.0 Security (18% of the exam)\
**Time:** about 120 minutes\
**VM:** ubuntu-lab (most tasks) and rocky-lab (account lockout)\
**Snapshot first:** Yes. This lab edits PAM and SSH settings. A mistake in PAM can stop everyone from logging in.
:::

Most real break-ins do not start with clever exploits. They start with a weak password, a reused password, or a forgotten account that still has a login shell. In this lab you will make passwords stronger, stop password reuse, set password expiration, lock accounts after failed guesses, add a second factor to SSH, check a password against a breach list, give accounts restricted shells, and stop using root directly. These are exactly the account hardening techniques the exam asks you to explain.

### What you'll practice

- Passwords: Complexity, Length, Expiration, Reuse, History (`pam_pwquality`, `pwquality.conf`, `pam_pwhistory`, `chage`, `/etc/login.defs`)
- Account lockout with `pam_faillock` and `faillock`, and how `pam_tally2` (the old tool) did the same job
- MFA: time-based one-time passwords (TOTP) for SSH with `libpam-google-authenticator`, tested with `oathtool`
- Checking existing breach lists: the Have I Been Pwned (HIBP) range API and k-anonymity
- Restricted shells: `/sbin/nologin` (on Ubuntu, `/usr/sbin/nologin`) and `/bin/rbash`
- Avoid running as root: lock root, block root SSH logins, use `sudo`, and audit `sudo` use in the logs

### How it works

**PAM is the gatekeeper.** PAM stands for *Pluggable Authentication Modules*. Programs like `login`, `sshd`, `su`, `sudo`, and `passwd` do not check passwords themselves. They ask PAM. PAM reads a small text file for that program in `/etc/pam.d/` and runs a list of modules, one after another, like a line of security guards. Each guard can say "pass", "fail", or "not my business".

Each line in a PAM file has this shape:

```text
type     control      module            options
password requisite    pam_pwquality.so  retry=3
```

- **type** is the job: `auth` (prove who you are), `account` (are you allowed in right now, for example is the account expired), `password` (changing a password), `session` (set things up after login).
- **control** says what a result means. `required` means "must pass, but keep running the other modules". `requisite` means "must pass, and stop right now if it fails". `sufficient` means "if this passes, that is enough". Ubuntu also uses the bracket form `[success=1 default=ignore]`, which means "on success, skip the next 1 line".
- **module** is the shared library that does the work, for example `pam_unix.so` (checks `/etc/shadow`).

On Ubuntu, the main services include four shared files: `common-auth`, `common-account`, `common-password`, and `common-session`. Ubuntu builds these files with a tool named **`pam-auth-update`** from small "profile" files in `/usr/share/pam-configs/`. If you edit `common-*` files by hand, a later package install may run `pam-auth-update` and either refuse to touch your file or replace it. So on Ubuntu the safe way is to add a profile and let `pam-auth-update` write the file. Rocky Linux has a similar tool named **`authselect`**, which builds `/etc/pam.d/system-auth` and `password-auth` from profiles and "features".

```{.diagram}
  user runs passwd
        |
        v
  /etc/pam.d/passwd  --@include-->  /etc/pam.d/common-password
                                           |
     password requisite pam_pwquality.so   |  1. complex enough? long enough?
     password requisite pam_pwhistory.so   |  2. used in the last 5 changes?
     password [...]     pam_unix.so        |  3. hash it, save it in /etc/shadow
                                           v
                                   new password accepted
```

**Password policy has five parts on the exam:**

- **Complexity**: the mix of character classes (lowercase, uppercase, digits, symbols). `pam_pwquality` enforces it.
- **Length**: the minimum number of characters. Length matters more than complexity. A 16-character passphrase is much harder to guess than an 8-character jumble.
- **Expiration**: how long a password lives before it must change (`chage`, `/etc/login.defs`). Modern guidance (NIST SP 800-63B) says forced regular changes cause weak, predictable passwords, so many organizations now expire passwords only after a suspected compromise. The exam still expects you to know how to set expiration.
- **Reuse** and **History**: the system remembers old password hashes (in `/etc/security/opasswd`) and refuses a new password that matches one of the last N. `pam_pwhistory` does this.

**Account lockout** stops password guessing. After a few failed logins the account is locked for a while. The current module is `pam_faillock`. The older module, `pam_tally2`, was removed from Linux-PAM in version 1.5.0 (2020), so you will not find it on Ubuntu 24.04 or Rocky 9, but it still appears on the exam and in old documentation.

**MFA** (multi-factor authentication) means proving identity with two or more different *kinds* of factor: something you know (password), something you have (phone, hardware key), something you are (fingerprint). A TOTP app on a phone is "something you have". It computes a six-digit code from a shared secret and the current time, so the code changes every 30 seconds.

**Breach lists** are databases of passwords leaked in past data breaches. Attackers try these first. Good practice (and NIST guidance) is to reject any password that appears in such a list.

**Restricted shells** limit what an account can do. A service account that runs a program but never logs in should have the shell `/sbin/nologin`. A user who needs only a few commands can get `rbash`, a restricted Bash.

**Avoid running as root.** Root can do anything, so a typo or a malicious script running as root can destroy the system. Log in as a normal user and use `sudo` for single commands. `sudo` also writes a log line every time, so you know who did what.

#### Task 2: Enforce password length and complexity with pam_pwquality

1. Install the module. On Ubuntu it is in the `libpam-pwquality` package.

    ```bash
    sudo apt update
    sudo apt install -y libpam-pwquality
    grep pwquality /etc/pam.d/common-password
    ```

    ```{.output}
    password	requisite			pam_pwquality.so retry=3
    ```

    ::: explain
    **What just happened:** The package ships a profile in `/usr/share/pam-configs/pwquality`. During install it ran `pam-auth-update`, which added the `pam_pwquality.so` line to `common-password`. `requisite` means "if the new password is weak, stop right away". `retry=3` gives the user three tries before `passwd` gives up.
    :::

2. Look at the profile that produced that line, so you understand how Ubuntu's system works:

    ```bash
    cat /usr/share/pam-configs/pwquality
    ```

    ```{.output}
    Name: Pwquality password strength checking
    Default: yes
    Priority: 1024
    Conflicts: cracklib
    Password-Type: Primary
    Password:
    	requisite			pam_pwquality.so retry=3
    Password-Initial:
    	requisite			pam_pwquality.so retry=3
    ```

    ::: explain
    **What just happened:** A profile has a name, a priority (higher numbers go earlier in the stack), and the lines to insert for each PAM type. `pam_unix` has priority 256, so `pam_pwquality` (1024) runs first and can reject a weak password before it is saved.
    :::

3. Set the rules in `/etc/security/pwquality.conf`. Back it up, then open it:

    ```bash
    sudo cp /etc/security/pwquality.conf /etc/security/pwquality.conf.orig
    sudo nano /etc/security/pwquality.conf
    ```

    Every line in the file is a comment. Add these lines at the bottom, save (`Ctrl+O`, `Enter`) and exit (`Ctrl+X`):

    ```ini
    minlen = 12
    minclass = 3
    dcredit = -1
    ucredit = -1
    lcredit = -1
    ocredit = 0
    maxrepeat = 3
    dictcheck = 1
    usercheck = 1
    ```

    ::: explain
    **What just happened:** You set the policy:

    - `minlen = 12` sets the minimum **length**. (pwquality can give "credit" for character classes, so read the next point.)
    - `minclass = 3` means the password must use at least 3 of the 4 classes: digits, uppercase, lowercase, other (symbols). This is **complexity**.
    - The `*credit` options work in two ways. A **negative** number means "require at least this many": `dcredit = -1` requires one digit, `ucredit = -1` one uppercase letter, `lcredit = -1` one lowercase letter. A **positive** number means "each such character counts as extra length", which lets a short password pass `minlen`. `ocredit = 0` means symbols are neither required nor given bonus length. Using negative credits keeps `minlen` an honest length.
    - `maxrepeat = 3` rejects more than 3 identical characters in a row (`aaaa`).
    - `dictcheck = 1` rejects passwords based on dictionary words (it uses the cracklib word list).
    - `usercheck = 1` rejects passwords that contain the user name.

    Changes take effect immediately. PAM reads this file every time someone changes a password.
    :::

4. Test the rules as the test user. A normal user must type the old password first, then a new one. Switch to `pwtest`:

    ```bash
    su - pwtest
    passwd
    ```

    Enter the current password `Orbit-Cactus-71!`. Then try these new passwords one at a time and read each message:

    | Try this | Why it fails |
    |---|---|
    | `Sh0rt!` | too short |
    | `alllowercaseletters` | no digit (and too few classes) |
    | `Basketball12` | dictionary word |
    | `Pwtest-Cactus-99` | contains the user name |

    ```{.output}
    Changing password for pwtest.
    Current password:
    New password:
    BAD PASSWORD: The password is shorter than 12 characters
    New password:
    BAD PASSWORD: The password contains less than 1 digits
    New password:
    BAD PASSWORD: The password fails the dictionary check - it is based on a dictionary word
    passwd: Have exhausted maximum number of retries for service
    passwd: password unchanged
    ```

    ::: explain
    **What just happened:** Each `BAD PASSWORD:` line is `pam_pwquality` explaining the **first** rule that failed (the "at least one digit" rule from `dcredit = -1` is checked before `minclass`). After three failures (`retry=3`) `passwd` stops. Run `passwd` again to try the fourth example. The exact wording of the messages can differ a little between versions, but each one names the rule.
    :::

5. Still as `pwtest`, change the password to a good one, then return to `student`:

    ```bash
    passwd
    exit
    ```

    Current password: `Orbit-Cactus-71!`. New password (twice): `Velvet-Harbor-38#`.

    ```{.output}
    passwd: password updated successfully
    ```

::: tip
When **root** runs `passwd someuser`, pwquality only prints a warning and lets root set a weak password anyway. Add `enforce_for_root` to `pwquality.conf` if you want the rules to apply to root too. This is why you always test password rules as a normal user.
:::

::: checkpoint
**Checkpoint:** `sudo grep -v '^#' /etc/security/pwquality.conf | grep .` shows your nine settings, and `pwtest` was able to change to `Velvet-Harbor-38#` but not to the weak examples.
:::

#### Task 3: Block password reuse with pam_pwhistory

`pam_pwquality` stops weak passwords, but a user could still switch back and forth between two strong passwords forever. `pam_pwhistory` keeps a **history** of old password hashes in `/etc/security/opasswd` and blocks **reuse**.

1. Ubuntu has no ready-made profile for `pam_pwhistory`, so you will write one. This uses a *heredoc*: everything between `<<'EOF'` and the line `EOF` is sent as input to `sudo tee`, which writes it to the file. The quotes around `'EOF'` stop the shell from changing anything inside. Note the line under `Password:` must start with a tab or spaces.

    ```bash
    cat <<'EOF' | sudo tee /usr/share/pam-configs/pwhistory
    Name: Remember the last 5 passwords (Lab 3.4)
    Default: yes
    Priority: 1000
    Password-Type: Primary
    Password:
        requisite pam_pwhistory.so remember=5 use_authtok
    EOF
    ```

    ::: explain
    **What just happened:** You created a profile. Priority 1000 places it after `pam_pwquality` (1024) and before `pam_unix` (256). The options:

    - `remember=5` keeps the last 5 passwords per user and rejects any of them.
    - `use_authtok` means "do not ask for the new password again; use the one the earlier module already collected". Without it the user would be asked twice.
    :::

2. Apply the profile. `pam-auth-update` normally shows a menu; `--package` makes it apply enabled profiles without asking.

    ```bash
    sudo pam-auth-update --package
    grep -v '^#' /etc/pam.d/common-password | grep .
    ```

    ```{.output}
    password	requisite			pam_pwquality.so retry=3
    password	requisite pam_pwhistory.so remember=5 use_authtok
    password	[success=1 default=ignore]	pam_unix.so obscure use_authtok try_first_pass yescrypt
    password	requisite			pam_deny.so
    password	required			pam_permit.so
    ```

    ::: explain
    **What just happened:** The order is exactly what you want: quality check, then history check, then `pam_unix` saves the new hash (with the `yescrypt` algorithm) in `/etc/shadow`. `pam-auth-update` also adjusted the `[success=1 ...]` jump for you, which is the main reason to let the tool write the file. If your output shows `pam_pwhistory` after `pam_unix`, stop and use `sudo pam-auth-update` (menu mode) to check which profiles are enabled.
    :::

3. Test it. As `pwtest`, change the password twice, then try to go back to an old one:

    ```bash
    su - pwtest
    passwd
    ```

    - Change `Velvet-Harbor-38#` to `Quiet-Lantern-52$` (works).
    - Run `passwd` again and try to change `Quiet-Lantern-52$` back to `Velvet-Harbor-38#`:

    ```{.output}
    Current password:
    New password:
    Password has been already used. Choose another.
    passwd: Authentication token manipulation error
    passwd: password unchanged
    ```

    Type `exit` to return to `student`.

    ::: explain
    **What just happened:** When `pwtest` changed away from `Velvet-Harbor-38#`, `pam_pwhistory` stored that old password's hash in `/etc/security/opasswd`. The second attempt matched a stored hash, so the module refused. Note: only *previous* passwords are stored; that is why the very first change in Task 2 had nothing to compare with.
    :::

4. Look at the history file (as root, it is readable only by root):

    ```bash
    sudo cat /etc/security/opasswd
    ```

    ```{.output}
    pwtest:1001:1:$y$j9T$...
    ```

    ::: explain
    **What just happened:** Each line holds the user name, UID, the number of stored entries, and the old hashes (separated by commas once there is more than one). Only one is stored so far: `Velvet-Harbor-38#`, the password `pwtest` changed away from after the module was enabled. The passwords themselves are never stored, only hashes (`$y$` means yescrypt).
    :::

::: exam
On the exam, password history can also be done with `pam_unix.so remember=N` (older systems). Both store hashes in `/etc/security/opasswd`. On Rocky/RHEL the history settings can go in `/etc/security/pwhistory.conf`, and the feature is turned on with `authselect enable-feature with-pwhistory`.
:::

::: checkpoint
**Checkpoint:** `grep pwhistory /etc/pam.d/common-password` shows the line, and reusing `Velvet-Harbor-38#` was rejected.
:::

#### Task 4: Set password expiration with chage and login.defs

1. See the current aging settings for `pwtest`:

    ```bash
    sudo chage -l pwtest
    ```

    ```{.output}
    Last password change					: Oct 10, 2026
    Password expires					: never
    Password inactive					: never
    Account expires						: never
    Minimum number of days between password change		: 0
    Maximum number of days between password change		: 99999
    Number of days of warning before password expires	: 7
    ```

    ::: explain
    **What just happened:** `chage` ("change age") reads the aging fields from `/etc/shadow`. A maximum of 99999 days means the password effectively never expires.
    :::

2. Set an **expiration** policy for this user:

    ```bash
    sudo chage -M 90 -m 1 -W 14 -I 7 -E 2027-12-31 pwtest
    sudo chage -l pwtest
    ```

    ```{.output}
    Last password change					: Oct 10, 2026
    Password expires					: Jan 08, 2027
    Password inactive					: Jan 15, 2027
    Account expires						: Dec 31, 2027
    Minimum number of days between password change		: 1
    Maximum number of days between password change		: 90
    Number of days of warning before password expires	: 14
    ```

    ::: explain
    **What just happened:**

    - `-M 90` maximum password age: it must change every 90 days.
    - `-m 1` minimum age: the user must wait 1 day between changes. Without this, a user could change the password 5 times in a row to flush the history and get the old one back.
    - `-W 14` warn the user 14 days before expiry.
    - `-I 7` inactive days: after the password expires the user has 7 days to log in and change it; after that the account is locked.
    - `-E 2027-12-31` the whole *account* expires on that date (good for contractors).
    :::

3. Force a password change at the next login. This is what you do after creating an account with a temporary password:

    ```bash
    sudo chage -d 0 pwtest
    sudo chage -l pwtest | head -2
    ```

    ```{.output}
    Last password change					: password must be changed
    Password expires					: password must be changed
    ```

    ::: explain
    **What just happened:** `-d 0` sets the "last change" date to day 0 (1 January 1970), so the password is already expired. `sudo passwd -e pwtest` does the same thing. At the next login the user is forced to choose a new password, and that new password must still pass pwquality and pwhistory.
    :::

4. Defaults for **new** accounts come from `/etc/login.defs`. Look at them:

    ```bash
    grep -E '^PASS_(MAX|MIN|WARN)' /etc/login.defs
    ```

    ```{.output}
    PASS_MAX_DAYS	99999
    PASS_MIN_DAYS	0
    PASS_WARN_AGE	7
    ```

    Change the defaults with `sed` (stream editor), which edits the file in place (`-i`):

    ```bash
    sudo sed -i 's/^PASS_MAX_DAYS.*/PASS_MAX_DAYS\t90/' /etc/login.defs
    sudo sed -i 's/^PASS_MIN_DAYS.*/PASS_MIN_DAYS\t1/' /etc/login.defs
    sudo useradd -m agetest
    sudo chage -l agetest | tail -3
    ```

    ```{.output}
    Minimum number of days between password change		: 1
    Maximum number of days between password change		: 90
    Number of days of warning before password expires	: 7
    ```

    ::: explain
    **What just happened:** `s/old/new/` replaces text; `^PASS_MAX_DAYS.*` matches the whole line that starts with `PASS_MAX_DAYS`; `\t` writes a tab. The new user `agetest` picked up the new defaults. Existing users like `pwtest` and `student` are **not** changed by `login.defs`; you must use `chage` on them.
    :::

::: checkpoint
**Checkpoint:** `sudo chage -l pwtest` says "password must be changed", and `sudo chage -l agetest` shows a maximum of 90 days.
:::

#### Task 5: Lock accounts after failed logins with pam_faillock (rocky-lab)

On Ubuntu 24.04 `pam_faillock` is installed but not turned on, and enabling it means hand-editing `common-auth` with careful jump counts. On Rocky Linux it is one safe command with `authselect`, so you will do this task on rocky-lab.

1. On rocky-lab, open a second terminal with `sudo -i` and leave it open, just like in Task 1. Then check which authselect profile is active:

    ```bash
    # on rocky-lab
    sudo authselect current
    ```

    ```{.output}
    Profile ID: sssd
    Enabled features:
    - with-silent-lastlog
    - with-mdns4
    ```

    ::: explain
    **What just happened:** `authselect` manages the PAM files on Rocky. Your profile may be `sssd`, `minimal`, or `local`; all support faillock. If it says "No existing configuration detected", run `sudo authselect select sssd --force` first (you took a snapshot).
    :::

2. Create a test user and enable the faillock feature:

    ```bash
    # on rocky-lab
    sudo useradd -m locktest
    echo 'locktest:Rocky-Lock-2026!' | sudo chpasswd
    sudo authselect enable-feature with-faillock
    grep faillock /etc/pam.d/system-auth
    ```

    ```{.output}
    auth        required                                     pam_faillock.so preauth silent
    auth        required                                     pam_faillock.so authfail
    account     required                                     pam_faillock.so
    ```

    ::: explain
    **What just happened:** `chpasswd` reads `user:password` lines from standard input, which is handy in scripts. `enable-feature with-faillock` rewrote `system-auth` and `password-auth` (used by `sshd`) to add three faillock lines. `preauth` checks "is this account locked?" before asking for the password, `authfail` records a failure after a wrong password, and the `account` line blocks a locked user even if the password is right.
    :::

3. Set the lockout policy in `/etc/security/faillock.conf`. Back it up and append two settings:

    ```bash
    # on rocky-lab
    sudo cp /etc/security/faillock.conf /etc/security/faillock.conf.orig
    printf 'deny = 3\nunlock_time = 120\n' | sudo tee -a /etc/security/faillock.conf
    ```

    ::: explain
    **What just happened:** `deny = 3` locks the account after 3 failures in a row; `unlock_time = 120` unlocks it automatically after 120 seconds. `unlock_time = 0` would mean "locked until an admin unlocks it". By default root is never locked (`even_deny_root` turns that on), which keeps you from locking out the only admin.
    :::

4. Trigger the lockout. SSH to `locktest` on the same machine and type a **wrong** password three times:

    ```bash
    # on rocky-lab
    ssh locktest@localhost
    ```

    Type `yes` if asked about the host key. After three wrong passwords, try once more with the **correct** password `Rocky-Lock-2026!`. It is still refused.

5. Look at the failure records and reset them:

    ```bash
    # on rocky-lab
    sudo faillock --user locktest
    ```

    ```{.output}
    locktest:
    When                Type  Source                                           Valid
    2026-10-10 14:02:11 RHOST ::1                                                  V
    2026-10-10 14:02:15 RHOST ::1                                                  V
    2026-10-10 14:02:19 RHOST ::1                                                  V
    ```

    ```bash
    # on rocky-lab
    sudo faillock --user locktest --reset
    ssh locktest@localhost
    ```

    ::: explain
    **What just happened:** `faillock --user` lists recorded failures (stored in `/var/run/faillock/`). `V` means the record still counts. `--reset` clears them, so the correct password now works. Type `exit` to leave the `locktest` session. Failed attempts also show in `sudo journalctl -u sshd`.
    :::

::: exam
**pam_tally2** is the deprecated predecessor of pam_faillock. You may see this syntax on the exam:

- PAM line: `auth required pam_tally2.so deny=3 unlock_time=600 onerr=fail`
- Show failures: `pam_tally2 --user bob`
- Reset: `pam_tally2 --user bob --reset`

The modern equivalents are `pam_faillock.so` with `/etc/security/faillock.conf`, `faillock --user bob`, and `faillock --user bob --reset`. Older still: `pam_tally` and `faillog`.
:::

::: tip
On Ubuntu, faillock is enabled by adding `pam_faillock.so preauth` before `pam_unix` and `pam_faillock.so authfail` after it in `/etc/pam.d/common-auth`, plus `account required pam_faillock.so` in `common-account`, adjusting the `[success=N]` jump numbers. It works, but one wrong number locks everyone out, which is why this lab uses Rocky.
:::

::: checkpoint
**Checkpoint:** `sudo faillock --user locktest` showed three failures before the reset and none after it, and `locktest` could log in again.
:::

#### Task 6: Add MFA (TOTP) to SSH

You will require a password **and** a six-digit TOTP code for one test user. Instead of a phone, you will use `oathtool`, which calculates the same codes from the secret. (An authenticator app works too if you want to try it.)

::: warning
This changes `sshd` and its PAM file. Keep your root shell open. Do not close your current SSH session until you have tested a **new** login. Apply MFA only to the test user, as shown.
:::

1. Install the PAM module and `oathtool`, and create the MFA test user:

    ```bash
    sudo apt install -y libpam-google-authenticator oathtool
    sudo useradd -m -s /bin/bash mfauser
    echo 'mfauser:Mfa-Lab-Pass-42!' | sudo chpasswd
    ```

2. Become `mfauser` and create the TOTP secret:

    ```bash
    sudo -iu mfauser
    google-authenticator -t -d -f -r 3 -R 30 -w 3 -Q NONE
    ```

    ```{.output}
    Your new secret key is: JBSWY3DPEHPK3PXPLABS7Q2RMA
    Enter code from app (-1 to skip): -1
    Code confirmation skipped
    Your emergency scratch codes are:
      40812236
      ...
    ```

    Type `-1` to skip the confirmation. Write down the secret key.

    ::: explain
    **What just happened:** The tool wrote `~/.google_authenticator` (mode 0400, readable only by `mfauser`). Options: `-t` time-based codes (TOTP); `-d` disallow reusing the same code; `-f` write the file without asking; `-r 3 -R 30` allow at most 3 logins every 30 seconds; `-w 3` accept the code before and after the current one to allow small clock differences; `-Q NONE` do not draw a QR code. Normally you would scan the QR code with a phone app. The scratch codes are one-time backup codes if the phone is lost.
    :::

3. Still as `mfauser`, generate the current code from the secret, then go back to `student`:

    ```bash
    oathtool --totp -b "$(head -1 ~/.google_authenticator)"
    exit
    ```

    ```{.output}
    492039
    ```

    ::: explain
    **What just happened:** The first line of `~/.google_authenticator` is the Base32 secret. `oathtool --totp -b` decodes the Base32 secret (`-b`) and computes the TOTP code for the current 30-second window. Your phone app does exactly the same calculation. That is why both clocks must be correct; on Ubuntu 24.04 `systemd-timesyncd` keeps the VM clock in sync (check with `timedatectl`).
    :::

4. Tell PAM to ask for the code during SSH logins. Open `/etc/pam.d/sshd`:

    ```bash
    sudo nano /etc/pam.d/sshd
    ```

    Find the line `@include common-auth` near the top and add this line directly **below** it:

    ```text
    auth required pam_google_authenticator.so nullok
    ```

    ::: explain
    **What just happened:** After the normal password check (`common-auth`), PAM now runs the Google Authenticator module. `nullok` means "users without a `~/.google_authenticator` file can skip this step", so `student` and other users are not affected. In production you remove `nullok` once every user is enrolled.
    :::

5. Tell `sshd` to use keyboard-interactive login (the method that can ask several questions) and require it for `mfauser`. Create a drop-in file, and add a `Match` block at the very end of the main config:

    ```bash
    echo 'KbdInteractiveAuthentication yes' | sudo tee /etc/ssh/sshd_config.d/10-mfa.conf
    printf '\nMatch User mfauser\n    AuthenticationMethods keyboard-interactive\n' \
      | sudo tee -a /etc/ssh/sshd_config
    sudo sshd -t && sudo systemctl reload ssh
    ```

    ::: explain
    **What just happened:** Ubuntu's `sshd_config` sets `KbdInteractiveAuthentication no`. The `Include /etc/ssh/sshd_config.d/*.conf` line sits at the top of that file, and `sshd` keeps the **first** value it reads, so your drop-in wins. The `Match User mfauser` block must be at the end of the file because every line after a `Match` belongs to it. `AuthenticationMethods keyboard-interactive` makes `mfauser` go through the full PAM conversation (password, then code); a plain password or key alone is not enough. `sshd -t` tests the config for errors; `reload` applies it only if the test passed.
    :::

6. Confirm the settings, then test a **new** login:

    ```bash
    sudo sshd -T -C user=mfauser,host=localhost,addr=127.0.0.1 | grep -i authenticationmethods
    ssh mfauser@localhost
    ```

    ```{.output}
    authenticationmethods keyboard-interactive
    (mfauser@localhost) Password:
    (mfauser@localhost) Verification code:
    ```

    Type the password `Mfa-Lab-Pass-42!`. For the code, run `oathtool --totp -b "$(sudo head -1 /home/mfauser/.google_authenticator)"` in another terminal and type the result. You are logged in. Type `exit`. Then try again with a wrong code, and see the login refused.

    ::: explain
    **What just happened:** `sshd -T` prints the effective configuration; `-C` tells it which connection to simulate, so you can test `Match` blocks safely. The login now needs two factors: something you know (password) and something you have (the device holding the secret). Note that `-d` stops you reusing the same code in the same 30 seconds, so wait for a fresh code before a second login.
    :::

::: tip
A stronger production setup is `AuthenticationMethods publickey,keyboard-interactive`: an SSH key first, then the TOTP code (with the password line removed from the PAM stack). Hardware security keys (FIDO2, `ssh-keygen -t ed25519-sk`) are another strong MFA option.
:::

::: checkpoint
**Checkpoint:** `ssh mfauser@localhost` asks for both a password and a verification code, and `ssh student@localhost` still works with just a password (or key).
:::

#### Task 7: Check a password against a breach list

Have I Been Pwned (HIBP) keeps a list of over 900 million passwords seen in real breaches. You can check a password against it **without sending the password**, thanks to a trick called *k-anonymity*.

::: warning
Only use obviously bad test passwords like `password123` in this task. Never type a real password into a command line, because it is saved in your shell history.
:::

1. Compute the SHA-1 hash of the test password:

    ```bash
    echo -n 'password123' | sha1sum
    ```

    ```{.output}
    cbfdac6008f9cab4083784cbd1874f76618d2a97  -
    ```

    ::: explain
    **What just happened:** `echo -n` prints the text without a newline (a newline would change the hash). `sha1sum` computes the SHA-1 hash, a 40-character hex fingerprint. The same input always gives the same hash.
    :::

2. Send only the first 5 characters (`CBFDA`) to the range API and search the answer locally for the remaining 35 characters:

    ```bash
    curl -s https://api.pwnedpasswords.com/range/CBFDA | grep -i 'C6008F9CAB4083784CBD1874F76618D2A97'
    ```

    ```{.output}
    C6008F9CAB4083784CBD1874F76618D2A97:251682
    ```

    ::: explain
    **What just happened:** The server returned every hash suffix that starts with `CBFDA` (several hundred lines) and how often each one was seen. `grep -i` (case-insensitive) found yours locally. The number after the colon is how many times this password appeared in breaches; yours will be different and probably larger. The server never learned your full hash, so it cannot know which password you checked. That is k-anonymity: your request hides among many possible answers.
    :::

3. Wrap it in a small reusable script that reads the password without showing it:

    ```bash
    cat <<'EOF' > pwcheck.sh
    #!/bin/bash
    read -rsp "Password to check: " pw; echo
    hash=$(printf '%s' "$pw" | sha1sum | awk '{print toupper($1)}')
    prefix=${hash:0:5}; suffix=${hash:5}
    count=$(curl -s "https://api.pwnedpasswords.com/range/$prefix" \
      | grep "^$suffix:" | cut -d: -f2 | tr -d '\r')
    echo "Seen in breaches: ${count:-0} times"
    EOF
    chmod +x pwcheck.sh
    ./pwcheck.sh
    ```

    Type `password123` (nothing appears as you type), then try a random string like `Xq7-unlikely-Plinth-9204`.

    ::: explain
    **What just happened:** `read -s` hides input, so the password never lands in shell history. `${hash:0:5}` takes the first 5 characters and `${hash:5}` the rest. `tr -d '\r'` removes the Windows-style line endings the API returns. A result of 0 means "not in a known breach", not "strong", so you still need length and complexity rules.
    :::

::: tip
Some organizations plug this check directly into password changes, for example with a PAM module or a password manager feature. `pam_pwquality`'s `dictcheck` is a much smaller local version of the same idea.
:::

::: checkpoint
**Checkpoint:** `./pwcheck.sh` reports a large number for `password123` and 0 for your random string.
:::

#### Task 8: Use restricted shells (nologin and rbash)

1. First, look at where `nologin` lives on Ubuntu:

    ```bash
    ls -ld /sbin /bin
    ls -l /usr/sbin/nologin
    grep -E 'nologin|rbash' /etc/shells
    ```

    ```{.output}
    lrwxrwxrwx 1 root root 8 Apr 22  2024 /sbin -> usr/sbin
    lrwxrwxrwx 1 root root 7 Apr 22  2024 /bin -> usr/bin
    -rwxr-xr-x 1 root root 14640 Apr  5  2024 /usr/sbin/nologin
    /bin/rbash
    /usr/bin/rbash
    ```

    ::: explain
    **What just happened:** Ubuntu uses "merged /usr": `/sbin` is a symbolic link to `/usr/sbin` and `/bin` to `/usr/bin`. So `/sbin/nologin` (the path the exam uses, and the normal path on Rocky) and `/usr/sbin/nologin` are the same file. `/etc/shells` lists valid login shells; `nologin` is deliberately not in it.
    :::

2. Create a service account with no login shell:

    ```bash
    sudo useradd -r -M -s /usr/sbin/nologin svcapp
    getent passwd svcapp
    sudo su - svcapp
    ```

    ```{.output}
    svcapp:x:998:998::/home/svcapp:/usr/sbin/nologin
    This account is currently not available.
    ```

    ::: explain
    **What just happened:** `-r` makes a system account (UID below 1000), `-M` skips the home folder, and `-s /usr/sbin/nologin` sets the shell. When anyone tries to log in, `nologin` prints a message and exits with a failure code. A program can still run *as* `svcapp` (for example from a systemd unit with `User=svcapp`), but no one gets an interactive shell. This is the standard for service accounts. `/bin/false` does the same job silently.
    :::

3. Customize the refusal message. This works on **rocky-lab**: its `nologin` comes from the `util-linux` package and prints the contents of `/etc/nologin.txt` if that file exists. (Ubuntu's `nologin` comes from the `login` package and always prints the fixed message you just saw.)

    ```bash
    # on rocky-lab
    sudo useradd -r -M -s /sbin/nologin svcapp
    echo 'Service accounts cannot log in. Contact the admin team.' \
      | sudo tee /etc/nologin.txt
    sudo su - svcapp
    ```

    ```{.output}
    Service accounts cannot log in. Contact the admin team.
    Service accounts cannot log in. Contact the admin team.
    ```

    ::: explain
    **What just happened:** you created the same kind of service account on rocky-lab, where the path is `/sbin/nologin`. The first line of output is `tee` echoing what it wrote; the second is `nologin` refusing the login with your custom text.
    :::

    ::: warning
    Do not confuse `/etc/nologin.txt` with `/etc/nologin`. If the file `/etc/nologin` exists, **all non-root users** are blocked from logging in (used during maintenance).
    :::

4. Now create a user with a restricted Bash shell, `rbash`, who can run only `ls`, `date`, and `whoami`:

    ```bash
    sudo useradd -m -s /bin/rbash rbuser
    echo 'rbuser:Rbash-Lab-Pass-7!' | sudo chpasswd
    sudo mkdir /home/rbuser/bin
    sudo ln -s /usr/bin/ls /usr/bin/date /usr/bin/whoami /home/rbuser/bin/
    echo 'export PATH=$HOME/bin' | sudo tee /home/rbuser/.bash_profile
    sudo chown root:root /home/rbuser/.bash_profile /home/rbuser/bin
    sudo chmod 644 /home/rbuser/.bash_profile
    ```

    ::: explain
    **What just happened:** `rbash` is Bash in restricted mode (`/bin/rbash` is a link to `bash`; Bash restricts itself when started under that name). The startup file `.bash_profile` runs *before* the restrictions start, so it can set `PATH` to a folder with only three symbolic links. The file and folder are owned by root, so `rbuser` cannot change them.
    :::

5. Log in as `rbuser` and see what is blocked:

    ```bash
    ssh rbuser@localhost
    ```

    Inside that session, try each line:

    ```bash
    whoami
    ls /home
    cd /tmp
    /usr/bin/id
    export PATH=/usr/bin
    echo hello > test.txt
    vim
    ```

    ```{.output}
    rbuser
    agetest  mfauser  pwtest  rbuser  student
    -rbash: cd: restricted
    -rbash: /usr/bin/id: restricted: cannot specify `/' in command names
    -rbash: PATH: readonly variable
    -rbash: test.txt: restricted: cannot redirect output
    -rbash: vim: command not found
    ```

    Type `exit`.

    ::: explain
    **What just happened:** In restricted mode Bash refuses to: change directory, run a command whose name contains `/`, change `PATH` (and `SHELL`, `ENV`, `BASH_ENV`), or redirect output with `>`. Since `PATH` contains only `~/bin`, the user can run only the three linked commands.
    :::

::: warning
`rbash` is a speed bump, not a wall. If you link any program that can start another program (`vi`, `less`, `python3`, `awk`, `find`), the user can escape to a full shell. Also, because `rbuser` owns the home folder, file transfer with `sftp`/`scp` could still change files. For real isolation use containers, chroot jails, or SSH `ForceCommand`.
:::

::: checkpoint
**Checkpoint:** on rocky-lab, `sudo su - svcapp` prints your custom message, and on ubuntu-lab `rbuser` can run `whoami` but gets "restricted" errors for `cd` and `/usr/bin/id`.
:::

#### Task 9: Avoid running as root

1. Check the root account's password status:

    ```bash
    sudo passwd -S root
    ```

    ```{.output}
    root L 2024-04-22 0 99999 7 -1
    ```

    ::: explain
    **What just happened:** `passwd -S` shows status: user, state, date of the last password change, then the minimum, maximum, warning, and inactive days. `L` means the root password is **locked** (Ubuntu does this at install). No one can log in as root with a password; admins use `sudo` instead. `P` would mean a usable password and `NP` no password at all (dangerous). On Rocky, if root has a password you can lock it with `sudo passwd -l root` after confirming `student` can use `sudo`.
    :::

2. Block root logins over SSH completely:

    ```bash
    sudo sshd -T | grep -i permitrootlogin
    echo 'PermitRootLogin no' | sudo tee /etc/ssh/sshd_config.d/10-noroot.conf
    sudo sshd -t && sudo systemctl reload ssh
    sudo sshd -T | grep -i permitrootlogin
    ```

    ```{.output}
    permitrootlogin without-password
    PermitRootLogin no
    permitrootlogin no
    ```

    ::: explain
    **What just happened:** The default `prohibit-password` (shown as `without-password`) allows root to log in with an SSH key. `no` blocks root completely, so attackers cannot even try. Admins log in as themselves, which means every action is tied to a real person.
    :::

3. Use `sudo` for single commands instead of a root shell, and see what you are allowed to do:

    ```bash
    sudo -l
    getent group sudo
    ```

    ```{.output}
    User student may run the following commands on ubuntu-lab:
        (ALL : ALL) ALL
    sudo:x:27:student
    ```

    ::: explain
    **What just happened:** `sudo -l` lists your sudo rights. Members of the `sudo` group (on Rocky: `wheel`) may run any command as any user. Good practice: give people only the commands they need with files in `/etc/sudoers.d/` (always edited with `visudo`), and prefer `sudo command` over long-lived `sudo -i` shells like the emergency one you opened in Task 1.
    :::

4. Audit sudo usage. Every `sudo` call is logged:

    ```bash
    sudo grep 'sudo:' /var/log/auth.log | grep COMMAND | tail -5
    sudo journalctl _COMM=sudo --since today | grep COMMAND | tail -5
    ```

    ```{.output}
    2026-10-10T14:31:02 ubuntu-lab sudo:  student : TTY=pts/0 ; PWD=/home/student/labs/3.4 ; USER=root ; COMMAND=/usr/bin/passwd -S root
    ```

    ::: explain
    **What just happened:** Each line records who ran `sudo` (`student`), from which terminal, in which folder, as which user (`USER=root`), and the exact command. Failed attempts show as `authentication failure` or `user NOT in sudoers`. On Rocky the same lines go to `/var/log/secure` and the journal. A shared root password would give you none of this accountability.
    :::

::: checkpoint
**Checkpoint:** `sudo sshd -T | grep permitrootlogin` prints `no`, and `journalctl _COMM=sudo` shows your own recent commands.
:::

### Exam corner

- `pam_pwquality` (config `/etc/security/pwquality.conf`) enforces **length** (`minlen`) and **complexity** (`minclass`, `dcredit`, `ucredit`, `lcredit`, `ocredit`). Negative credit = required count; positive credit = bonus length.
- `pam_pwhistory remember=N` (or `pam_unix remember=N`) blocks password **reuse**; the **history** of hashes is in `/etc/security/opasswd`.
- `chage -M` max days, `-m` min days, `-W` warn days, `-I` inactive days, `-E` account expiry date, `-d 0` force change at next login, `-l` list. `passwd -e` also forces a change.
- `/etc/login.defs` (`PASS_MAX_DAYS`, `PASS_MIN_DAYS`, `PASS_WARN_AGE`) sets defaults for **new** accounts only.
- Account lockout: `pam_faillock` with `/etc/security/faillock.conf` (`deny`, `unlock_time`); view/reset with `faillock --user NAME [--reset]`. **pam_tally2** (`pam_tally2 --user NAME --reset`) is the removed predecessor.
- Ubuntu manages PAM with `pam-auth-update`; Rocky/RHEL with `authselect` (`enable-feature with-faillock`).
- **MFA** = two or more different factor types. TOTP via `pam_google_authenticator.so` plus `KbdInteractiveAuthentication yes` and `AuthenticationMethods` in `sshd_config`.
- **Breach** checking: HIBP range API uses k-anonymity: only the first 5 hex characters of the SHA-1 hash leave your machine.
- **Restricted shell**: `/sbin/nologin` (or `/bin/false`) for service accounts; `/bin/rbash` blocks `cd`, `/` in commands, changing `PATH`, and output redirection.
- Avoid running as **root**: locked root password, `PermitRootLogin no`, least-privilege `sudo` rules, and `sudo` logs in `/var/log/auth.log` (Ubuntu) or `/var/log/secure` (RHEL).
