systemd is the first program the Linux kernel starts, and it starts, stops, watches, and logs almost everything else. In this lab you will write your own service, drive it through every state the exam lists, add a timer and a mount unit, work with targets, and use the systemd tools that manage the hostname, time, DNS resolution, kernel parameters, and boot speed. These are daily tasks on any modern Linux server, Ubuntu and Rocky alike.

### How it works

**systemd and PID 1.** When the kernel finishes booting, it starts one program as process ID 1. On Ubuntu and Rocky that program is systemd. Its job is to bring the system to a working state and keep it there: start services in the right order, restart them if they crash, mount filesystems, run scheduled jobs, and shut everything down cleanly.

**Units.** systemd manages *units*. A unit is anything systemd can start or stop, described by a small text file in INI style (sections in `[brackets]`, `Key=value` lines). The file's extension tells you the unit type:

| Type | Extension | What it manages |
|---|---|---|
| Service | `.service` | A program or daemon (for example `ssh.service`) |
| Timer | `.timer` | Starts another unit on a schedule (a modern cron) |
| Mount | `.mount` | A mounted filesystem |
| Target | `.target` | A group of units, used as a synchronization point (like old runlevels) |
| Socket, path, device, swap, slice, scope | ... | Other types you will meet later |

**Where unit files live.** systemd reads three folders. When the same file name appears in more than one, the higher one wins:

```{.diagram}
 /etc/systemd/system/       <- YOUR files and overrides (highest priority)
 /run/systemd/system/       <- runtime units, gone after reboot
 /usr/lib/systemd/system/   <- files installed by packages (do not edit)
```

Never edit files under `/usr/lib/systemd/system/`; a package update would overwrite your change. Instead, create a *drop-in* override with `systemctl edit`, or copy the file to `/etc/systemd/system/`.

**Start versus enable.** These two words confuse beginners, so learn them now:

- `start` / `stop` act **now**. They do not affect the next boot.
- `enable` / `disable` act **at boot**. `enable` creates a symlink from a target's `.wants/` folder to the unit, so the unit starts when that target is reached. It does not start the unit now (unless you add `--now`).

**Mask.** `mask` is a stronger "disable". It links the unit name to `/dev/null`, so nothing can start it, not even another unit that depends on it, until you `unmask` it.

**Reload versus restart.** `restart` stops the process and starts a new one: connections drop and the process ID changes. `reload` asks the running process to re-read its configuration without stopping (usually by sending it the `SIGHUP` signal), so connections stay up. Not every service supports reload. `systemctl daemon-reload` is different again: it tells **systemd itself** to re-read unit files after you edit them. It does not restart any service.

**Targets.** A target is a named group of units. `multi-user.target` means "a full text-mode system with networking", `graphical.target` adds a graphical login, and `rescue.target` and `emergency.target` are repair modes. The *default target* is the one systemd boots into. They replace the old SysV *runlevels* (3 = multi-user, 5 = graphical, 1 = rescue).

**Dependencies and ordering.** In a unit file, `Wants=` and `Requires=` say which other units must also be started (weak and strong). `After=` and `Before=` only set the **order**. In `[Install]`, `WantedBy=multi-user.target` is what `enable` uses to decide where to place the symlink.

**The systemd tool family.** systemd also includes small helpers that replace the old way of editing files by hand: `hostnamectl` (hostname), `timedatectl` (clock, time zone, NTP), `resolvectl` (DNS, through the `systemd-resolved` service), `journalctl` (logs), and `systemd-analyze` (boot performance). `sysctl` is not part of systemd, but systemd applies your `sysctl` settings at boot through `systemd-sysctl.service`.

#### Task 2: Write your own service and use start, stop, enable, disable, and status

1. Create a system user for the service. Running services as a dedicated, unprivileged user limits the damage if the program is ever compromised.

    ```bash
    sudo useradd --system --no-create-home --shell /usr/sbin/nologin labsvc
    id labsvc
    ```

    ::: explain
    **What just happened:** `--system` creates a *system account* with a low UID and no password aging. `--no-create-home` skips the home folder, and the `nologin` shell means nobody can log in as this user.
    :::

2. Write the program the service will run. This uses a *heredoc*: everything between `<<'EOF'` and the line `EOF` is sent to `sudo tee`, which writes it to the file. The quotes around `EOF` stop the shell from expanding `$` signs inside, so the script is written exactly as shown.

    ```bash
    cat <<'EOF' | sudo tee /usr/local/bin/labheartbeat.sh
    #!/bin/bash
    # Lab 2.5 demo: print a heartbeat line forever
    INTERVAL="${INTERVAL:-5}"
    count=0
    while true; do
        count=$((count + 1))
        echo "heartbeat #$count from $(whoami), every ${INTERVAL}s"
        sleep "$INTERVAL"
    done
    EOF
    sudo chmod 755 /usr/local/bin/labheartbeat.sh
    ```

    ::: explain
    **What just happened:** The script loops forever, printing one line every `INTERVAL` seconds (5 by default; `${INTERVAL:-5}` means "use `$INTERVAL` if set, otherwise 5"). Anything a service prints to standard output goes into the systemd journal, so you do not need a log file. `chmod 755` makes it executable.
    :::

3. Write the unit file. Open it with `sudo nano /etc/systemd/system/labheartbeat.service` and type the following, or use the heredoc below.

    ```bash
    cat <<'EOF' | sudo tee /etc/systemd/system/labheartbeat.service
    [Unit]
    Description=Lab 2.5 heartbeat demo service
    After=network.target

    [Service]
    Type=simple
    User=labsvc
    ExecStart=/usr/local/bin/labheartbeat.sh
    Restart=on-failure
    RestartSec=3

    [Install]
    WantedBy=multi-user.target
    EOF
    ```

    ::: explain
    **What just happened:** `[Unit]` holds a description and ordering: `After=network.target` means start after basic networking is up. `[Service]` says how to run it. `Type=simple` means the program in `ExecStart` *is* the service and stays in the foreground (other types: `forking` for old daemons that background themselves, `oneshot` for a command that runs and exits, `notify` for programs that tell systemd when they are ready). `User=` runs it as `labsvc` instead of root. `ExecStart` must be an absolute path. `Restart=on-failure` restarts it if it crashes or exits with an error, after `RestartSec=3` seconds. `[Install]` is used only by `enable`: `WantedBy=multi-user.target` means "start me when the normal multi-user system starts".
    :::

4. Tell systemd about the new file, check it, and look at its state before starting.

    ```bash
    sudo systemctl daemon-reload
    systemd-analyze verify /etc/systemd/system/labheartbeat.service
    systemctl status labheartbeat --no-pager
    ```

    ```{.output}
    ○ labheartbeat.service - Lab 2.5 heartbeat demo service
         Loaded: loaded (/etc/systemd/system/labheartbeat.service; disabled; preset: enabled)
         Active: inactive (dead)
    ```

    ::: explain
    **What just happened:** `daemon-reload` makes systemd re-read all unit files from disk; run it every time you create or change one by hand. `systemd-analyze verify` checks a unit file for mistakes and prints nothing if it is fine. The empty circle `○` and `inactive (dead)` mean "not running"; `disabled` means it will not start at boot.
    :::

5. Start the service and observe it.

    ```bash
    sudo systemctl start labheartbeat
    systemctl is-active labheartbeat
    systemctl is-enabled labheartbeat
    systemctl status labheartbeat --no-pager
    ```

    ```{.output}
    active
    disabled
    ● labheartbeat.service - Lab 2.5 heartbeat demo service
         Loaded: loaded (/etc/systemd/system/labheartbeat.service; disabled; preset: enabled)
         Active: active (running) since Sat 2026-10-10 12:20:01 UTC; 6s ago
       Main PID: 3141 (labheartbeat.sh)
          Tasks: 2 (limit: 4613)
         CGroup: /system.slice/labheartbeat.service
                 ├─3141 /bin/bash /usr/local/bin/labheartbeat.sh
                 └─3150 sleep 5

    Oct 10 12:20:01 ubuntu-lab labheartbeat.sh[3141]: heartbeat #1 from labsvc, every 5s
    Oct 10 12:20:06 ubuntu-lab labheartbeat.sh[3141]: heartbeat #2 from labsvc, every 5s
    ```

    ::: explain
    **What just happened:** It is now `active` but still `disabled`: started now, not at boot. The filled dot `●` means running. The `CGroup` tree shows every process belonging to the service. systemd puts each service in its own *control group*, so it can track and kill all its processes, even children. The log lines prove it runs as `labsvc`.
    :::

6. Enable it for boot and see what `enable` really does.

    ```bash
    sudo systemctl enable labheartbeat
    ls -l /etc/systemd/system/multi-user.target.wants/ | grep labheartbeat
    systemctl is-enabled labheartbeat
    ```

    ```{.output}
    Created symlink /etc/systemd/system/multi-user.target.wants/labheartbeat.service → /etc/systemd/system/labheartbeat.service.
    lrwxrwxrwx 1 root root 40 Oct 10 12:21 labheartbeat.service -> /etc/systemd/system/labheartbeat.service
    enabled
    ```

    ::: explain
    **What just happened:** `enable` read `WantedBy=multi-user.target` and created a symbolic link in `multi-user.target.wants/`. At boot, when systemd reaches `multi-user.target`, it starts everything linked there. That is all "enabled" means.
    :::

7. Stop it and disable it, then use the shortcut that does both steps at once.

    ```bash
    sudo systemctl stop labheartbeat
    sudo systemctl disable labheartbeat
    systemctl is-active labheartbeat; systemctl is-enabled labheartbeat
    sudo systemctl enable --now labheartbeat
    systemctl is-active labheartbeat; systemctl is-enabled labheartbeat
    ```

    ::: explain
    **What just happened:** `stop` ended the process now; `disable` removed the symlink. `enable --now` enables **and** starts in one command (`disable --now` disables and stops). The `;` runs two commands on one line.
    :::

::: checkpoint
**Checkpoint:** `systemctl is-active labheartbeat` prints `active` and `systemctl is-enabled labheartbeat` prints `enabled`.
:::

#### Task 3: Restart on failure, read the logs, and daemon-reload after edits

1. Follow the service's log live. Open a **second terminal** (or SSH session) and run:

    ```bash
    journalctl -u labheartbeat -f
    ```

    ::: explain
    **What just happened:** `journalctl` reads the systemd journal. `-u labheartbeat` shows only this unit, and `-f` (follow) keeps printing new lines, like `tail -f`. Leave it running and return to the first terminal. Other useful options: `-n 20` (last 20 lines), `--since "10 min ago"`, `-b` (this boot only), `-p err` (errors and worse).
    :::

2. Simulate a crash by killing the main process with `SIGKILL`, then watch systemd bring it back.

    ```bash
    systemctl show -p MainPID --value labheartbeat
    sudo kill -9 $(systemctl show -p MainPID --value labheartbeat)
    sleep 5
    systemctl show -p MainPID --value labheartbeat
    systemctl show -p NRestarts --value labheartbeat
    ```

    In the journal terminal you see:

    ```{.output}
    labheartbeat.service: Main process exited, code=killed, status=9/KILL
    labheartbeat.service: Failed with result 'signal'.
    labheartbeat.service: Scheduled restart job, restart counter is at 1.
    Started labheartbeat.service - Lab 2.5 heartbeat demo service.
    labheartbeat.sh[3420]: heartbeat #1 from labsvc, every 5s
    ```

    ::: explain
    **What just happened:** `systemctl show -p MainPID --value` prints just the main PID. `$( ... )` inserts that number into the `kill` command. `kill -9` sends `SIGKILL`, which cannot be caught, so it looks like a crash. Because of `Restart=on-failure`, systemd waited `RestartSec=3` seconds and started a new process with a new PID. `NRestarts` counts automatic restarts. A normal `systemctl stop` is not a failure, so it never triggers a restart.
    :::

3. Edit the unit file directly and see why `daemon-reload` matters. Change the description with `sed`:

    ```bash
    sudo sed -i 's/^Description=.*/Description=Lab 2.5 heartbeat (edited)/' \
      /etc/systemd/system/labheartbeat.service
    systemctl status labheartbeat --no-pager | head -3
    ```

    ```{.output}
    Warning: The unit file, source configuration file or drop-ins of labheartbeat.service
    changed on disk. Run 'systemctl daemon-reload' to reload units.
    ● labheartbeat.service - Lab 2.5 heartbeat demo service
    ```

    ::: explain
    **What just happened:** `sed -i` edited the file in place, replacing the whole `Description=` line. systemd still has the **old** version in memory and warns you. Until you run `daemon-reload`, `start` and `restart` would use the old settings.
    :::

4. Reload systemd's view of unit files and confirm the change.

    ```bash
    sudo systemctl daemon-reload
    systemctl status labheartbeat --no-pager | head -3
    systemctl is-active labheartbeat
    ```

    ::: explain
    **What just happened:** The new description appears and the warning is gone. Note that the service kept running with the same PID: `daemon-reload` reloads *systemd's configuration*, not the service. If you change `ExecStart=` or `User=`, you must also run `sudo systemctl restart labheartbeat` for the running process to pick it up.
    :::

5. Press `Ctrl+C` in the second terminal to stop following the journal.

::: checkpoint
**Checkpoint:** `systemctl show -p NRestarts --value labheartbeat` prints `1` (or more), and `journalctl -u labheartbeat -n 5 --no-pager` shows recent heartbeats.
:::

#### Task 4: Override settings with systemctl edit

1. Create a drop-in override that changes the heartbeat interval.

    ```bash
    sudo systemctl edit labheartbeat
    ```

    An editor opens (nano on Ubuntu by default) showing the current unit file as comments. Type these two lines in the empty area between the two comment markers near the top, then save and exit (in nano: `Ctrl+O`, `Enter`, `Ctrl+X`):

    ```ini
    [Service]
    Environment=INTERVAL=2
    ```

    ::: explain
    **What just happened:** `systemctl edit` created `/etc/systemd/system/labheartbeat.service.d/override.conf` containing only your lines, and ran `daemon-reload` for you. A *drop-in* adds to or overrides individual settings of the main unit without touching it. This is the correct way to customize units installed by packages. You must repeat the section header (`[Service]`). `Environment=` sets an *environment variable* for the process. If you save an empty file, nothing is created.
    :::

2. Look at the merged result and apply it.

    ```bash
    systemctl cat labheartbeat
    sudo systemctl restart labheartbeat
    sleep 5
    journalctl -u labheartbeat -n 3 --no-pager
    ```

    ```{.output}
    # /etc/systemd/system/labheartbeat.service
    [Unit]
    Description=Lab 2.5 heartbeat (edited)
    ...
    # /etc/systemd/system/labheartbeat.service.d/override.conf
    [Service]
    Environment=INTERVAL=2

    Oct 10 12:31:02 ubuntu-lab labheartbeat.sh[3511]: heartbeat #2 from labsvc, every 2s
    Oct 10 12:31:04 ubuntu-lab labheartbeat.sh[3511]: heartbeat #3 from labsvc, every 2s
    ```

    ::: explain
    **What just happened:** `systemctl cat` shows the main file followed by each drop-in, with the file path as a comment. `restart` started a new process, which saw `INTERVAL=2`. To reset some settings, a drop-in can also *clear* a list setting first, for example `ExecStart=` on its own line, followed by a new `ExecStart=...`.
    :::

3. Know the other forms of `edit`.

    ```bash
    systemd-delta --type=extended
    ```

    ::: explain
    **What just happened:** `systemd-delta` lists units that are overridden or extended by drop-ins, a quick audit of local changes. Other forms: `sudo systemctl edit --full <unit>` copies the whole unit to `/etc/systemd/system/` for editing; `sudo systemctl revert <unit>` deletes your drop-ins and overrides and returns to the vendor version.
    :::

::: checkpoint
**Checkpoint:** `cat /etc/systemd/system/labheartbeat.service.d/override.conf` shows the `Environment=INTERVAL=2` line, and new journal lines say `every 2s`.

#### Task 5: Reload versus restart, and mask versus unmask (with Nginx)

1. Install Nginx, a web server that supports reload, and look at how its unit defines reload.

    ```bash
    sudo apt install -y nginx
    systemctl cat nginx | grep -E '^Exec'
    ```

    ```{.output}
    ExecStartPre=/usr/sbin/nginx -t -q -g 'daemon on; master_process on;'
    ExecStart=/usr/sbin/nginx -g 'daemon on; master_process on;'
    ExecReload=/usr/sbin/nginx -g 'daemon on; master_process on;' -s reload
    ExecStop=-/sbin/start-stop-daemon --quiet --stop --retry QUIT/5 --pidfile /run/nginx.pid
    ```

    ::: explain
    **What just happened:** `ExecReload=` is the command systemd runs on `systemctl reload`. A unit without `ExecReload=` cannot be reloaded, and `reload` fails with "Job type reload is not applicable". `ExecStartPre=` runs a config test before every start.
    :::

2. Reload, and watch which processes change.

    ```bash
    pgrep -a nginx
    sudo systemctl reload nginx
    pgrep -a nginx
    ```

    ```{.output}
    4210 nginx: master process /usr/sbin/nginx -g daemon on; master_process on;
    4211 nginx: worker process
    4212 nginx: worker process
    4210 nginx: master process /usr/sbin/nginx -g daemon on; master_process on;
    4290 nginx: worker process
    4291 nginx: worker process
    ```

    ::: explain
    **What just happened:** `pgrep -a` lists matching processes with their command lines. After `reload`, the **master** process kept its PID (4210); it re-read the configuration and started new worker processes, letting the old ones finish their current requests. No connection was dropped.
    :::

3. Now restart and compare.

    ```bash
    sudo systemctl restart nginx
    pgrep -a nginx
    sudo systemctl reload-or-restart nginx
    ```

    ::: explain
    **What just happened:** After `restart`, even the master has a new PID: everything was stopped and started again, which drops open connections. Use `reload` after configuration changes when the service supports it, and `restart` after upgrades or changes that need a fresh process. `reload-or-restart` reloads if possible and otherwise restarts.
    :::

4. Mask the service so nothing can start it.

    ```bash
    sudo systemctl stop nginx
    sudo systemctl mask nginx
    ls -l /etc/systemd/system/nginx.service
    sudo systemctl start nginx
    systemctl is-enabled nginx
    ```

    ```{.output}
    Created symlink /etc/systemd/system/nginx.service → /dev/null.
    lrwxrwxrwx 1 root root 9 Oct 10 12:40 /etc/systemd/system/nginx.service -> /dev/null
    Failed to start nginx.service: Unit nginx.service is masked.
    masked
    ```

    ::: explain
    **What just happened:** `mask` created a link named `nginx.service` in `/etc/systemd/system/`, which has priority over the real file in `/usr/lib/systemd/system/`, and pointed it at `/dev/null` (an empty file). systemd now sees an empty unit and refuses to start it, manually or as a dependency. Admins mask services that must never run, such as a conflicting firewall service. Because mask needs that name in `/etc/systemd/system/`, you cannot mask a unit whose real file lives there, like your `labheartbeat.service`; systemd would refuse because the file already exists.
    :::

5. Unmask and start it again.

    ```bash
    sudo systemctl unmask nginx
    sudo systemctl start nginx
    systemctl is-active nginx
    ```

::: checkpoint
**Checkpoint:** `systemctl is-enabled nginx` prints `enabled` (not `masked`) and `curl -s localhost | grep -o 'Welcome to nginx'` prints `Welcome to nginx`.
:::

#### Task 6: Schedule a job with a timer unit

A timer needs two units with the same base name: a `.service` that does the work and a `.timer` that says when.

1. Write a small report script and a `oneshot` service for it.

    ```bash
    cat <<'EOF' | sudo tee /usr/local/bin/labreport.sh
    #!/bin/bash
    echo "$(date '+%F %T') load: $(cut -d' ' -f1-3 /proc/loadavg)" >> /var/log/labreport.log
    EOF
    sudo chmod 755 /usr/local/bin/labreport.sh
    cat <<'EOF' | sudo tee /etc/systemd/system/labreport.service
    [Unit]
    Description=Lab 2.5 write a load report

    [Service]
    Type=oneshot
    ExecStart=/usr/local/bin/labreport.sh
    EOF
    ```

    ::: explain
    **What just happened:** The script appends the date and load averages to `/var/log/labreport.log`. `Type=oneshot` means the command runs, finishes, and the service goes back to inactive; systemd waits for it to finish. There is no `[Install]` section because the timer, not the boot process, will start this service.
    :::

2. Check the schedule syntax before you use it.

    ```bash
    systemd-analyze calendar 'minutely'
    systemd-analyze calendar 'Mon..Fri *-*-* 02:30:00'
    ```

    ```{.output}
      Original form: minutely
    Normalized form: *-*-* *:*:00
        Next elapse: Sat 2026-10-10 12:46:00 UTC
           From now: 31s left
    ```

    ::: explain
    **What just happened:** `OnCalendar=` uses the format `DayOfWeek Year-Month-Day Hour:Minute:Second`, where `*` means "any". `minutely`, `hourly`, `daily`, and `weekly` are shortcuts. `systemd-analyze calendar` shows the normalized form and the next time it would fire, so you can test expressions safely. The second example means 02:30 on weekdays.
    :::

3. Write the timer unit.

    ```bash
    cat <<'EOF' | sudo tee /etc/systemd/system/labreport.timer
    [Unit]
    Description=Run labreport every minute

    [Timer]
    OnCalendar=minutely
    AccuracySec=1s
    Persistent=true

    [Install]
    WantedBy=timers.target
    EOF
    sudo systemctl daemon-reload
    sudo systemctl enable --now labreport.timer
    ```

    ::: explain
    **What just happened:** By default a timer starts the service with the same name (`labreport.service`); `Unit=` could name another one. `OnCalendar=` is a wall-clock schedule. `AccuracySec=1s` makes it fire close to the exact second (the default allows up to one minute of delay to save power). `Persistent=true` means that if the machine was off at the scheduled time, the job runs once soon after boot, like `anacron`. Other timer types are relative: `OnBootSec=5min` (5 minutes after boot) and `OnUnitActiveSec=1h` (one hour after it last ran). You enable the **timer**, not the service.
    :::

4. List timers and wait for a run.

    ```bash
    systemctl list-timers --all | grep -E 'NEXT|labreport'
    sleep 65
    cat /var/log/labreport.log
    journalctl -u labreport.service -n 4 --no-pager
    ```

    ```{.output}
    NEXT                        LEFT LAST                        PASSED UNIT            ACTIVATES
    ```

#### Task 7: Mount a filesystem with a mount unit

1. Find the required unit name for the mount point `/mnt/lab`.

    ```bash
    systemd-escape -p --suffix=mount /mnt/lab
    ```

    ```{.output}
    mnt-lab.mount
    ```

    ::: explain
    **What just happened:** A mount unit's file name **must** match its mount point: remove the leading `/`, turn every other `/` into `-`, and add `.mount`. So `/mnt/lab` becomes `mnt-lab.mount` and `/var/lib/data` would be `var-lib-data.mount`. `systemd-escape -p` (path mode) does the conversion, including escaping special characters. If the name does not match `Where=`, systemd refuses to load the unit.
    :::

2. Write the mount unit for a 64 MB `tmpfs` (a filesystem that lives in RAM).

    ```bash
    cat <<'EOF' | sudo tee /etc/systemd/system/mnt-lab.mount
    [Unit]
    Description=Lab 2.5 tmpfs at /mnt/lab

    [Mount]
    What=tmpfs
    Where=/mnt/lab
    Type=tmpfs
    Options=size=64M,mode=1777

    [Install]
    WantedBy=multi-user.target
    EOF
    sudo systemctl daemon-reload
    sudo systemctl start mnt-lab.mount
    ```

    ::: explain
    **What just happened:** The `[Mount]` section holds the same four facts as an `/etc/fstab` line: `What=` (device; for tmpfs any name works), `Where=` (mount point, created automatically if missing), `Type=` (filesystem type), and `Options=` (mount options; `size=64M` caps its size and `mode=1777` makes it writable by everyone with the sticky bit, like `/tmp`). Starting the unit performs the mount.
    :::

3. Check the mount and stop it.

    ```bash
    findmnt /mnt/lab
    systemctl status mnt-lab.mount --no-pager | head -4
    sudo systemctl stop mnt-lab.mount
    findmnt /mnt/lab || echo "not mounted"
    ```

    ```{.output}
    TARGET   SOURCE FSTYPE OPTIONS
    /mnt/lab tmpfs  tmpfs  rw,relatime,size=65536k,inode64
    ```

    ::: explain
    **What just happened:** `findmnt` shows the mounted filesystem with your options (`mode=1777` is missing only because it is already the default for `tmpfs`, and the kernel lists only non-default modes). `stop` unmounts it, just like `umount /mnt/lab`. To mount it at every boot, you would run `sudo systemctl enable mnt-lab.mount`.
    :::

4. See how your `/etc/fstab` lines become mount units.

    ```bash
    systemctl list-units --type=mount --no-pager | head
    ls /run/systemd/generator/
    systemctl cat -- -.mount
    ```

    ```{.output}
    # /run/systemd/generator/-.mount
    # Automatically generated by systemd-fstab-generator

    [Unit]
    Documentation=man:fstab(5) man:systemd-fstab-generator(8)
    SourcePath=/etc/fstab
    ...
    [Mount]
    What=/dev/disk/by-uuid/0b3f...
    Where=/
    Type=ext4
    ```

    ::: explain
    **What just happened:** At boot and on every `daemon-reload`, `systemd-fstab-generator` reads `/etc/fstab` and writes a mount unit for each line into `/run/systemd/generator/`. The root filesystem's unit is named `-.mount`. The `--` tells `systemctl` that `-.mount` is a name, not an option. That is why you must run `sudo systemctl daemon-reload` after editing `/etc/fstab`. For most mounts fstab is simpler; mount units are useful when you need systemd dependencies (for example, "start this service only after this mount is ready", with `RequiresMountsFor=`). A matching `.automount` unit mounts on first access.
    :::

::: checkpoint
**Checkpoint:** `systemctl is-active mnt-lab.mount` prints `inactive` after the stop, and `sudo systemctl start mnt-lab.mount && findmnt /mnt/lab` mounts it again. Stop it once more afterwards.
:::

1. Look at the default target and the active targets.

    ```bash
    systemctl get-default
    systemctl list-units --type=target --no-pager
    systemctl list-dependencies multi-user.target --no-pager | head -15
    ```

    ```{.output}
    graphical.target
      UNIT                   LOAD   ACTIVE SUB    DESCRIPTION
      basic.target           loaded active active Basic System
      graphical.target       loaded active active Graphical Interface
      multi-user.target      loaded active active Multi-User System
      network-online.target  loaded active active Network is Online

    ```

    ::: explain
    **What just happened:** `get-default` shows the target systemd boots into; it is the symlink `/etc/systemd/system/default.target`. Ubuntu Server often reports `graphical.target` even without a desktop installed; with no display manager it behaves the same as `multi-user.target`. Rocky minimal reports `multi-user.target`. `list-dependencies` shows the tree of units a target pulls in.

2. Change the default target, check it, and change it back. Save the original first.

    ```bash
    ORIG_TARGET=$(systemctl get-default)
    echo "$ORIG_TARGET"
    sudo systemctl set-default multi-user.target
    ls -l /etc/systemd/system/default.target
    sudo systemctl set-default "$ORIG_TARGET"
    systemctl get-default
    ```

    ::: explain
    **What just happened:** `ORIG_TARGET=$(...)` stores the current default in a shell variable so you can restore it. `set-default` simply re-points the `default.target` symlink. It changes the **next** boot only. Old runlevel names still exist as aliases: `runlevel3.target` is `multi-user.target` and `runlevel5.target` is `graphical.target`.
    :::

3. Understand `isolate` (read, do not run it over SSH).

    ::: warning
    `sudo systemctl isolate rescue.target` switches **right now** to that target and stops every unit it does not need, including networking and SSH. Over SSH you would lock yourself out. Only use it at the VM console. To return, run `sudo systemctl isolate multi-user.target` (or `default`) at the console.
    :::

    ::: explain
    **What just happened:** `isolate` is like the old `init 1` or `telinit 3`: it changes the current state instead of the boot default. Only targets with `AllowIsolate=yes` can be isolated. To boot once into a target, add `systemd.unit=rescue.target` to the kernel command line in the GRUB menu (press `e` at the menu).
    :::

    ```bash
    systemd-analyze critical-chain
    ```

    ```{.output}
          6.021s systemd-networkd-wait-online.service
    ```

    ::: explain
    **What just happened:** `systemd-analyze` prints total boot time split into kernel and userspace. `blame` (what the exam calls "systemd-blame") lists units sorted by how long they took to start. #### Task 9: hostnamectl, timedatectl, resolvectl, and sysctl

1. **hostnamectl.** View and temporarily change the hostname.

    ```bash
    hostnamectl
    sudo hostnamectl set-hostname lab-temp
    hostname; cat /etc/hostname
    sudo hostnamectl set-hostname ubuntu-lab
    hostnamectl --static
    ```

    ::: explain
    **What just happened:** `hostnamectl` shows the hostname plus OS, kernel, and virtualization details. `set-hostname` changes it immediately **and** writes `/etc/hostname`, so it survives reboot. While the name was `lab-temp`, `sudo` may warn `unable to resolve host lab-temp`, because `/etc/hosts` has no line for it; that shows why `/etc/hosts` must match the hostname. 2. **timedatectl.** View the clock settings, then change and restore the time zone.

    ```{.output}
                   Local time: Sat 2026-10-10 12:58:20 UTC
               Universal time: Sat 2026-10-10 12:58:20 UTC

    System clock synchronized: yes
    ```

    ::: explain
    **What just happened:** `timedatectl` shows local time, UTC, the hardware clock (RTC), the time zone, and whether NTP sync is working. `show -p Timezone --value` prints just the zone name so you can save it. `set-timezone` changes the link `/etc/localtime`. `sudo timedatectl set-ntp true` turns automatic sync on, and `set-time "2026-10-10 13:00:00"` sets the clock by hand, but only when NTP is off. 3. **systemd-resolved and resolvectl.** See how name resolution works on Ubuntu.

    ```bash
    ls -l /etc/resolv.conf
    grep -v '^#' /etc/resolv.conf
    resolvectl status
    ```

    ```{.output}
    lrwxrwxrwx 1 root root 39 Apr 23  2024 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
    nameserver 127.0.0.53
    ```

    ::: explain
    **What just happened:** `systemd-resolved` is a local DNS service. Programs read `/etc/resolv.conf`, which is a symlink to a *stub* file that lists only `127.0.0.53`, an address where `systemd-resolved` listens. 4. Query a name and look at the cache.

    ```bash
    resolvectl query ubuntu.com
    resolvectl statistics
    sudo resolvectl flush-caches
    ```

    ```{.output}

                185.125.190.21                     -- link: enp0s3

    -- Information acquired via protocol DNS in 31.8ms.
    -- Data is authenticated: no; Data was acquired via local or encrypted transport: no
    -- Data from: network
    ```

    ::: explain
    **What just happened:** `resolvectl query` resolves a name through `systemd-resolved` and says which link and protocol answered. 5. **sysctl.** Read kernel parameters at runtime.

    ```bash
    sysctl -a 2>/dev/null | wc -l
    sysctl vm.swappiness
    cat /proc/sys/vm/swappiness
    ```

    ::: explain
    **What just happened:** `sysctl` reads and writes kernel parameters. `-a` lists all of them (more than a thousand; `2>/dev/null` hides permission warnings). Each parameter is also a file under `/proc/sys/`, with dots turned into slashes. `vm.swappiness` (default 60) controls how eagerly the kernel swaps memory to disk.
    :::

6. Change a parameter for now, then make it persistent.

    ```bash
    sudo sysctl -w vm.swappiness=30
    sysctl vm.swappiness
    echo 'vm.swappiness = 30' | sudo tee /etc/sysctl.d/99-lab.conf
    sudo sysctl --system | grep -E '99-lab|swappiness'
    ```

    ```{.output}
    vm.swappiness = 30
    vm.swappiness = 30
    vm.swappiness = 30
    * Applying /etc/sysctl.d/99-lab.conf ...
    vm.swappiness = 30
    ```

    ::: explain
    **What just happened:** The first three lines come from `sysctl -w` (it echoes the new value), `sysctl vm.swappiness`, and `tee` (which echoes what it writes). `sysctl -w` changes the value in the running kernel immediately, but it is lost at reboot. To make it permanent, put it in a file in `/etc/sysctl.d/` ending in `.conf` (files are applied in name order, so `99-` wins over lower numbers). `/etc/sysctl.conf` also works. `sysctl --system` applies all files now (it first lists every file it reads, then prints every value it sets, so `grep` picks out the two lines you care about), the same way `systemd-sysctl.service` does at boot. `sysctl -p <file>` applies one file.
    :::

### Exam corner

- `start`/`stop`/`restart` act now; `enable`/`disable` act at boot (symlinks in `<target>.wants/`); `enable --now` does both.
- `reload` re-reads the service's config without stopping it (needs `ExecReload=`); `restart` stops and starts (new PID); `daemon-reload` makes **systemd** re-read unit files after you edit them.
- `mask` links the unit to `/dev/null` so nothing can start it; `unmask` removes the link.
- `systemctl edit <unit>` creates a drop-in `/etc/systemd/system/<unit>.d/override.conf`; `--full` edits a full copy; `systemctl cat` shows the merged result; `systemctl revert` undoes it.
- Unit file priority: `/etc/systemd/system/` beats `/run/systemd/system/` beats `/usr/lib/systemd/system/`.
- Service essentials: `Type=simple|forking|oneshot|notify`, `ExecStart=`, `User=`, `Restart=on-failure`, `WantedBy=multi-user.target`.
- Timers: a `.timer` starts the `.service` of the same name; `OnCalendar=` (wall clock), `OnBootSec=`/`OnUnitActiveSec=` (relative), `Persistent=true`; list with `systemctl list-timers`.
- Mount unit names must match the path: `/mnt/lab` is `mnt-lab.mount` (`systemd-escape -p --suffix=mount`); fstab lines become mount units via `systemd-fstab-generator`.
- Targets: `systemctl get-default`, `set-default`, `isolate`; `multi-user.target` = runlevel 3, `graphical.target` = 5, `rescue.target` = 1.
- `systemd-analyze` (boot time), `systemd-analyze blame` (slowest units), `systemd-analyze critical-chain`, `systemd-analyze verify`, `systemd-analyze calendar`.
- `hostnamectl set-hostname`, `timedatectl set-timezone`/`set-ntp`, `resolvectl status`/`query`/`flush-caches`; `/etc/resolv.conf` points to the `systemd-resolved` stub at `127.0.0.53`.
- `sysctl -w key=value` is runtime only; persist in `/etc/sysctl.d/*.conf` and apply with `sysctl --system` or `sysctl -p`.
