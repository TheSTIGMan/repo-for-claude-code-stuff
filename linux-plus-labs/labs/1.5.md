The shell is where a Linux administrator spends most of the day. In this lab you build a small practice dataset (a fake web server log and a server inventory in CSV format) and then use it to practise the everyday shell skills: moving around the file system, working with environment variables, customizing your prompt and `PATH`, redirecting input and output, slicing text with classic tools like `grep`, `awk`, and `sed`, reusing your command history, and editing files in `vim` and `nano`. The exam tests these skills with "which command would..." scenarios, so the goal is that each tool feels familiar.

### What you'll practice

- Environment variables: `DISPLAY`, `HOME`, `PATH`, `PS1`, `SHELL`, `USER`
- Paths: absolute (`~`, `/`) and relative (`.`, `..`, `-`)
- Shell environment configs: `.bashrc`, `.bash_profile`, `.profile` (login and non-login shells)
- Redirection: `<`, `>`, `<<`, `>>`, `|`; standard output, standard error, standard input; here docs; here strings `<<<`
- Utilities: `!`, `!!`, `alias`, `awk`, `bc`, `cat`, `cut`, `echo`, `grep`, `head`, `history`, `less`, `more`, `printf`, `sed`, `sort`, `source`, `tail`, `tee`, `tr`, `uname`, `uniq`, `wc`, `xargs`
- Editors: `vi`/`vim` and `nano`

### How it works

**The shell.** When you log in, Linux starts a program called a *shell*. The shell reads the line you type, works out what you mean (expanding `~`, `*`, and `$VARIABLES`), finds the program, and runs it. On Ubuntu and Rocky the default shell is **Bash** (`/bin/bash`). Everything in this lab is Bash.

**Paths.** Every file lives somewhere in one big tree that starts at `/` (the *root* directory). A path tells the shell where a file is:

- An **absolute** path starts at the root, so it always works no matter where you are: `/etc/hostname`, `/home/student`. The shortcut `~` means "my home directory", so `~/labs` is also absolute (the shell turns it into `/home/student/labs`).
- A **relative** path starts from your *current working directory* (where you are now). `.` means "this directory", `..` means "the parent directory", and `cd -` means "go back to the directory I was just in".

Think of an absolute path as a full postal address and a relative path as "two doors down from here".

**Variables and the environment.** The shell keeps named values called *variables*. Some of them are *environment variables*: they are copied into every program the shell starts, so programs can read them. Important ones:

| Variable | Holds | Example |
|---|---|---|
| `HOME` | Your home directory | `/home/student` |
| `USER` | Your user name | `student` |
| `SHELL` | Your login shell | `/bin/bash` |
| `PATH` | Directories searched for commands, separated by `:` | `/usr/local/bin:/usr/bin:/bin...` |
| `PS1` | The text of your prompt | `\u@\h:\w\$ ` |
| `DISPLAY` | Which X11 graphical display GUI programs should draw on | `:0` or `localhost:10.0` (empty on a server) |

When you type `ls`, the shell does not search the whole disk. It looks in each directory in `PATH`, left to right, and runs the first `ls` it finds. That is why a script in a directory that is not in `PATH` gives "command not found" until you type its path or add the directory to `PATH`.

**Startup files.** Variables you set at the prompt disappear when you log out. To make a setting permanent you put it in a *startup file* that Bash reads when it starts. Which file depends on the type of shell:

```{.diagram}
 LOGIN shell (SSH login, console login, "bash -l")
   /etc/profile
   then the FIRST one that exists of:
     ~/.bash_profile  ->  ~/.bash_login  ->  ~/.profile
                                              |
                       (Ubuntu's ~/.profile sources ~/.bashrc)

 NON-LOGIN interactive shell (typing "bash", a new terminal tab in a GUI)
   /etc/bash.bashrc
   ~/.bashrc
```

Ubuntu ships `~/.profile` and `~/.bashrc` for every new user but **no** `~/.bash_profile`. Its `~/.profile` runs `~/.bashrc`, so both kinds of shell end up reading `~/.bashrc`. The usual rule is: put **environment variables** such as `PATH` in `~/.profile` (read once at login, then inherited by every child process), and put **aliases, prompt settings, and functions** in `~/.bashrc` (read by every interactive shell, because aliases are *not* inherited). If you create `~/.bash_profile`, Bash reads it *instead of* `~/.profile`, which surprises many people. You will prove that in Task 4. The `source` command (or its short form `.`) reads a file into the *current* shell, so you can apply changes without logging out.

**Streams and redirection.** Every program starts with three open "pipes" called *streams*:

```{.diagram}
                     +-------------+  stdout (1) --> screen
 keyboard --> stdin  |   program   |
              (0)    +-------------+  stderr (2) --> screen
```

- **standard input** (stdin, number 0): where the program reads input. Normally the keyboard.
- **standard output** (stdout, number 1): normal results. Normally the screen.
- **standard error** (stderr, number 2): error messages. Also the screen, but a separate stream.

*Redirection* reconnects these streams to files: `>` sends stdout to a file (replacing it), `>>` appends, `2>` sends stderr, `<` feeds a file into stdin, `<<` (a *here doc*) feeds lines you type, and `<<<` (a *here string*) feeds one string. A *pipe* `|` connects the stdout of one program to the stdin of the next, which lets you build a "pipeline" of small tools that each do one job. That idea, small tools joined by pipes, is the heart of Unix text processing.

**Editors.** Sooner or later you will edit a config file on a server with no GUI. `nano` is simple and shows its shortcuts on screen. `vi`/`vim` is on almost every Unix system ever made, is very powerful, and is *modal*: keys mean different things in different modes. You will practise both.

    /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin

    **What just happened:** `echo` prints its arguments. A `$` in front of a name tells the shell to replace it with the variable's value *before* `echo` runs. The double quotes keep the value as one argument even if it contains spaces. `PATH` is a list of directories separated by colons. Ubuntu's `PS1` looks scary because it contains color codes and a window-title code; you will replace it with something readable in Task 4. Your `PATH` may also contain `/home/student/.local/bin` or `/home/student/bin` if those directories existed when you logged in.

2. List all environment variables and pick out a few.

    ```bash
    printenv | sort | head -n 15
    printenv HOME
    env | grep -E '^(USER|SHELL|LANG)='
    ```

    ::: explain
    **What just happened:** `printenv` (and `env` with no arguments) prints every *environment* variable as `NAME=value`. You piped the output into `sort` to alphabetize it and `head -n 15` to see only the first 15 lines. `printenv HOME` prints one variable without the `$`. `grep -E` searches using an extended regular expression; `^` means "start of line", so this matches lines that begin with exactly `USER=`, `SHELL=`, or `LANG=`.
    :::

3. Learn the difference between a shell variable and an environment variable.

    ```bash
    COLOR=blue
    echo "$COLOR"
    bash -c 'echo "child shell sees: [$COLOR]"'
    export COLOR
    bash -c 'echo "child shell sees: [$COLOR]"'
    unset COLOR
    ```

    ```{.output}
    blue
    child shell sees: []
    child shell sees: [blue]
    ```

    ::: explain
    **What just happened:** `COLOR=blue` (no spaces around `=`) creates a *shell variable* that only the current shell knows. `bash -c '...'` starts a child shell that runs one command; it saw nothing because shell variables are not passed to children. `export COLOR` marks the variable for export, turning it into an *environment variable*, so the child now sees it. You can also do both in one step: `export COLOR=blue`. `unset` deletes the variable. This is why `PATH` must be exported (it already is): programs started by your shell need it.
    :::

4. Look at `DISPLAY`. ubuntu-lab is a server with no graphical desktop.

    ```bash
    echo "DISPLAY is: [$DISPLAY]"
    ```

    ```{.output}
    DISPLAY is: []
    ```

    ::: explain
    **What just happened:** `DISPLAY` tells graphical (X11) programs where to draw their windows. The format is `host:display.screen`; `:0` means "the first display on this machine". On a server with no GUI it is empty, so a graphical program such as `xeyes` or `virt-manager` would fail with "cannot open display". The fix is *X11 forwarding*: if you connect with `ssh -X student@ubuntu-lab` from a computer that runs an X server (a Linux desktop, macOS with XQuartz, or Windows with an X server such as VcXsrv or WSLg), SSH sets `DISPLAY` to something like `localhost:10.0` and tunnels the windows back to your screen. The server needs `X11Forwarding yes` in `/etc/ssh/sshd_config` (Ubuntu's default) and the `xauth` package.
    :::

    ::: tip
    **Explore/simulate:** If your workstation has an X server, try `ssh -X student@ubuntu-lab`, then `echo $DISPLAY` (you should see `localhost:10.0`), then `sudo apt install -y x11-apps` and `xeyes`. Without an X server, just check the server side: `grep -i x11forwarding /etc/ssh/sshd_config` shows `X11Forwarding yes`. Remove `x11-apps` afterwards if you installed it.
    :::

1. Back up your startup files.

2. Change the prompt for the current shell only.

    ```bash
    PS1='[\u@\h \W]\$ '
    ```

    Your prompt becomes `[student@ubuntu-lab 1.5]$ `. Now try a two-line prompt with the time:

    ```bash
    PS1='\t \u@\h:\w\n\$ '
    ```

    ::: explain
    **What just happened:** `PS1` is the *primary prompt string*. Bash replaces special backslash codes each time it draws the prompt: `\u` user name, `\h` short host name, `\w` full current directory (with `~` for home), `\W` only the last part of the directory, `\t` time (24-hour HH:MM:SS), `\n` a new line, and `\$` shows `$` for normal users and `#` for root. Single quotes stop the shell from interpreting the backslashes when you set the variable. Because you did not save it anywhere, the change disappears when this shell exits.
    :::

3. Make a personal tools directory with a small script and try to run it.

    ```bash
    mkdir -p ~/labtools
    cat > ~/labtools/hello-lab <<'EOF'
    #!/bin/bash
    echo "Hello from $(hostname), I am running as $USER"
    EOF
    chmod +x ~/labtools/hello-lab
    hello-lab
    ```

    ```{.output}
    hello-lab: command not found
    ```

    ::: explain
    **What just happened:** You wrote a two-line script. `#!/bin/bash` (the "shebang") tells the kernel which program runs the file, and `chmod +x` makes it executable. Typing `hello-lab` fails because the shell only searches the directories in `PATH`, and `~/labtools` is not one of them. You could still run it with its full path: `~/labtools/hello-lab`.
    :::

4. Add the directory to `PATH` for this shell and test it.

    ```bash
    export PATH="$PATH:$HOME/labtools"
    hello-lab
    which hello-lab
    ```

    ```{.output}
    Hello from ubuntu-lab, I am running as student
    /home/student/labtools/hello-lab
    ```

    ::: explain
    **What just happened:** `"$PATH:$HOME/labtools"` builds a new value from the old `PATH` plus a colon and your directory, so nothing existing is lost. Putting your directory at the *end* means system commands win if names clash; putting it at the *front* (`"$HOME/labtools:$PATH"`) would let your version override a system command. Never replace `PATH` with only your directory, or commands like `ls` will stop working in that shell. `which` shows which file the shell would run.
    :::

5. Make the changes permanent. `PATH` belongs in `~/.profile`; the prompt and aliases belong in `~/.bashrc`. The `>>` operator *appends* to a file instead of overwriting it, which is critical here: a single `>` would wipe out your existing `.bashrc`.

    ```bash
    cat >> ~/.profile <<'EOF'

    # >>> lab 1.5 >>>
    export PATH="$PATH:$HOME/labtools"
    # <<< lab 1.5 <<<
    EOF
    ```

    ```bash
    cat >> ~/.bashrc <<'EOF'

    # >>> lab 1.5 >>>
    PS1='[\t] \u@\h:\w\$ '
    alias ll='ls -alF'
    alias lab='cd ~/labs/1.5'
    alias grep='grep --color=auto'
    # <<< lab 1.5 <<<
    EOF
    tail -n 8 ~/.bashrc
    ```

    ::: explain
    **What just happened:** You appended a marked block to each file. The marker comments make the block easy to find and remove later. An `alias` is a short name that the shell replaces with longer text: after this, typing `ll` runs `ls -alF`. Ubuntu's `~/.bashrc` already defines `ll`, `la`, `l`, and a colorized `grep`; defining them again is harmless, and the later definition wins. You added your lines at the *end* of `~/.bashrc` on purpose: near the top, Ubuntu's file stops early ("return") for non-interactive shells, so settings at the end only affect interactive shells, which is what you want for prompts and aliases. You could make the same edits with `nano ~/.bashrc`; the here doc just avoids typos.
    :::

6. Apply the changes without logging out by sourcing the files.

    ```bash
    source ~/.bashrc
    alias
    lab
    pwd
    ```

    ```{.output}
    ...
    alias grep='grep --color=auto'
    alias l='ls -CF'
    alias la='ls -A'
    alias lab='cd ~/labs/1.5'
    alias ll='ls -alF'
    alias ls='ls --color=auto'
    ...
    /home/student/labs/1.5
    ```

    ::: explain
    **What just happened:** `source ~/.bashrc` runs the file's commands *inside the current shell*, so the new prompt and aliases take effect right now. (Running `bash ~/.bashrc` would not work: it would apply them in a child shell that exits immediately.) `. ~/.bashrc` is the same as `source ~/.bashrc`. `alias` with no arguments lists all aliases; `alias ll` shows one; `unalias name` removes one; and `\ls` or `command ls` runs the real command, skipping any alias. Your prompt now looks like `[14:05:31] student@ubuntu-lab:~/labs/1.5$ `.
    :::

7. Tell login shells from non-login shells.

    ```bash
    echo $0
    shopt login_shell
    bash
    echo $0
    shopt login_shell
    exit
    ```

    ```{.output}
    -bash
    login_shell     on
    bash
    login_shell     off
    ```

    ::: explain
    **What just happened:** Your SSH or console session is a *login shell*. Bash shows this by putting a dash in front of its name (`-bash`) and setting the `login_shell` option. 8. Prove that `~/.bash_profile` hides `~/.profile`. Create a one-line `~/.bash_profile`, then start a login shell and look for your `lab` alias (which only reaches login shells because `~/.profile` sources `~/.bashrc`).

    ```bash
    echo 'echo "~/.bash_profile was read"' > ~/.bash_profile
    bash -l
    type lab
    exit
    ```

    ```{.output}
    ~/.bash_profile was read
    bash: type: lab: not found
    ```

    Now fix it the standard way, by making `~/.bash_profile` read `~/.profile`:

    ```bash
    echo '[ -f ~/.profile ] && . ~/.profile' >> ~/.bash_profile
    bash -l
    type lab
    exit
    rm ~/.bash_profile
    ```

    ```{.output}
    ~/.bash_profile was read
    lab is aliased to `cd ~/labs/1.5'
    ```

#### Task 5: Redirect standard input, output, and error

1. Run a command that produces both normal output and an error.

    ```bash
    cd ~/labs/1.5
    ls /etc/hostname /nope
    ```

    ```{.output}
    ls: cannot access '/nope': No such file or directory
    /etc/hostname
    ```

    Both lines appear on the screen, but they come from different streams: the error from **standard error** and the file name from **standard output**.

2. Send each stream to its own file.

    ```bash
    ls /etc/hostname /nope > out.txt
    cat out.txt
    ls /etc/hostname /nope 2> err.txt
    cat err.txt
    ```

    ```{.output}
    ls: cannot access '/nope': No such file or directory
    /etc/hostname
    /etc/hostname
    ls: cannot access '/nope': No such file or directory
    ```

    ::: explain
    **What just happened:** `>` is short for `1>`: it redirects stream 1 (stdout) to `out.txt`, so only the error still reached your screen. `2>` redirects stream 2 (stderr) to `err.txt`, so only the normal output reached the screen. A single `>` creates the file or **empties it first** if it already exists.
    :::

3. Append instead of overwrite.

    ```bash
    echo "first line" > notes.txt
    echo "second line" >> notes.txt
    echo "oops" > notes.txt
    cat notes.txt
    ```

    ```{.output}
    oops
    ```

    The third command used `>` and wiped out the first two lines. Use `>>` whenever you want to keep what is already in a file (log files, `~/.bashrc`).

    ::: tip
    `set -o noclobber` makes Bash refuse to overwrite an existing file with `>` (you then need `>|` to force it). Some admins add it to `~/.bashrc` as a safety net. Turn it off with `set +o noclobber`.
    :::

4. Send both streams to one file, and learn why order matters.

    ```bash
    ls /etc/hostname /nope > all.txt 2>&1
    cat all.txt
    ls /etc/hostname /nope &> all2.txt
    cat all2.txt
    ls /etc/hostname /nope 2>&1 > wrong.txt
    ```

    ```{.output}
    ls: cannot access '/nope': No such file or directory
    /etc/hostname
    ls: cannot access '/nope': No such file or directory
    /etc/hostname
    ls: cannot access '/nope': No such file or directory
    ```

    ::: explain
    **What just happened:** `2>&1` means "send stream 2 to wherever stream 1 is going *right now*". The shell processes redirections left to right. In the first command, stdout was already pointing to `all.txt`, so stderr followed it there. In the last command, `2>&1` came first, while stdout still pointed at the screen, so stderr went to the screen and only stdout went to `wrong.txt`. `&>` is a Bash shortcut for "both streams to this file" (`&>>` appends both).
    :::

5. Throw away output you do not want with `/dev/null`.

    ```bash
    find /etc -name "*.conf" 2> /dev/null | head -n 5
    grep -r "PermitRootLogin" /etc/ssh 2>/dev/null
    ls /nope &> /dev/null
    echo "exit status: $?"
    ```

    ::: explain
    **What just happened:** `/dev/null` is a special file that discards everything written to it (the "bit bucket"). Running `find` as a normal user produces many "Permission denied" errors; `2> /dev/null` hides them so you see only real results. The last `ls` hid all output, but you can still check whether it worked: `$?` holds the *exit status* of the previous command, `0` for success and non-zero (here `2`) for failure. Scripts use this pattern constantly: "run quietly and just tell me if it worked".
    :::

6. Feed a file to standard input with `<`, and a single string with a **here string** `<<<`.

    ```bash
    wc -l < access.log
    tr 'a-z' 'A-Z' < servers.csv | head -n 2
    wc -w <<< "one two three"
    bc <<< "2^10"
    ```

    ```{.output}
    15
    HOSTNAME,OS,RAM_GB,ROLE,SITE
    WEB01,UBUNTU,4,WEB,LONDON
    3
    1024
    ```

    ::: explain
    **What just happened:** `< access.log` connects the file to the program's standard input. `wc -l access.log` would print `15 access.log`, but `wc -l < access.log` prints just `15` because `wc` never learns the file name, which is handy in scripts. `tr` only reads standard input (it cannot take a file name), so `<` is the normal way to feed it. `<<<` passes one string, followed by a newline, as standard input: a one-line version of a here doc.
    :::

7. Pipes carry only standard output.

    ```bash
    ls /nope | wc -l
    ls /nope 2>&1 | wc -l
    ```

    ```{.output}
    ls: cannot access '/nope': No such file or directory
    0
    1
    ```

    ::: explain
    **What just happened:** The pipe `|` connects stdout of `ls` to stdin of `wc`. The error went to stderr, straight to your screen, so `wc` counted 0 lines. With `2>&1` before the pipe, stderr joins stdout and flows into `wc`. Bash also accepts `|&` as a shortcut for `2>&1 |`.
    :::

8. Use `tee` to save output *and* keep it flowing down the pipeline.

    ```bash
    grep ' 404 ' access.log | tee 404s.txt | wc -l
    cat 404s.txt
    date | tee -a run.log
    date | tee -a run.log
    cat run.log
    ```

    ```{.output}
    3

    ...
    ```

    ::: explain
    **What just happened:** `tee` is named after a T-shaped pipe fitting: it copies its standard input to a file *and* to its standard output. Here the 404 lines were saved in `404s.txt` while `wc -l` counted them. `tee -a` appends instead of overwriting.
    :::

9. Use `tee` to write a file that needs root permission.

    ```bash
    sudo echo "lab 1.5 was here" > /opt/lab15.txt
    echo "lab 1.5 was here" | sudo tee /opt/lab15.txt

    -bash: /opt/lab15.txt: Permission denied
    lab 1.5 was here
    lab 1.5 was here
    ```

    ::: explain
    **What just happened:** The first command failed even with `sudo`. The redirection `>` is performed by *your* shell, running as `student`, before `sudo` even starts; only `echo` ran as root. In the second command, `tee` itself runs as root through `sudo`, so it can write the file. This `| sudo tee file` pattern (or `| sudo tee -a file` to append) is how you write to protected files from a pipeline, and it is the pattern this book uses with here docs: `cat <<'EOF' | sudo tee /etc/...`.

6. Sort, de-duplicate, and count: the most common log analysis pipeline. Which IP address made the most requests?

    ```bash
    cut -d' ' -f1 access.log | sort | uniq -c | sort -rn
    ```

    ```{.output}
          4 203.0.113.7
          3 192.168.100.20
          3 10.0.0.22
          3 10.0.0.15
          2 198.51.100.4
    ```

    ::: explain
    **What just happened:** Read the pipeline left to right. `cut` extracts the IPs. `sort` puts identical IPs next to each other. `uniq -c` collapses adjacent identical lines into one and prefixes a count; `uniq` only compares *neighboring* lines, which is why you must `sort` first. The final `sort -rn` sorts numerically (`-n`) in reverse (`-r`), so the busiest client is on top. Lines with equal counts may appear in a different order on your system. `203.0.113.7` is the client probing for `/admin`, `/.env`, and `/phpmyadmin`: an attacker scanning for weaknesses.

#### Task 7: Transform text with awk, sed, tr, printf, bc, and xargs

1. Use `awk` to work with columns and do arithmetic.

    ```bash
    awk '{print $1, $9}' access.log | head -n 3
    awk '$9 >= 500 {print $4, $7}' access.log
    awk '{sum += $10} END {print "Total bytes:", sum}' access.log
    awk -F, 'NR > 1 {ram += $3} END {print "Total RAM:", ram, "GB"}' servers.csv
    ```

    ```{.output}
    192.168.100.20 200
    192.168.100.20 200
    10.0.0.15 200
    [10/Oct/2026:08:07:45 /reports
    [10/Oct/2026:08:15:42 /reports
    Total bytes: 50508
    Total RAM: 58 GB
    ```

    ::: explain
    **What just happened:** `awk` is a small programming language for column-based text. By default it splits each line on runs of spaces or tabs into fields `$1`, `$2`, ... (`$0` is the whole line, `NF` is the number of fields, `NR` is the current line number). A program has the form `pattern {action}`: the action runs for every line that matches the pattern. `$9 >= 500` selects server errors. `sum += $10` adds up the bytes column, and the `END` block runs once after the last line. `-F,` sets the field separator to a comma, and `NR > 1` skips the header line. Ubuntu's `awk` is `mawk`; Rocky's is `gawk`. Both run these examples.
    :::

2. Use `sed` (stream editor) to edit text on the fly.

    ```bash
    sed 's/ubuntu/Ubuntu/' servers.csv | head -n 3
    sed -n '2,4p' servers.csv
    sed '1d' servers.csv | head -n 2
    sed '/rocky/d' servers.csv
    ```

    ```{.output}
    hostname,os,ram_gb,role,site
    web01,Ubuntu,4,web,london
    web02,Ubuntu,4,web,london
    web01,ubuntu,4,web,london
    web02,ubuntu,4,web,london
    db01,rocky,16,database,paris
    web01,ubuntu,4,web,london
    web02,ubuntu,4,web,london
    hostname,os,ram_gb,role,site
    web01,ubuntu,4,web,london
    ...
    ```

    ::: explain
    **What just happened:** `sed 's/old/new/'` substitutes the first match of `old` on each line; add `g` (`s/old/new/g`) to replace every match on the line. `sed -n '2,4p'` turns off automatic printing (`-n`) and prints (`p`) only lines 2 to 4. `1d` deletes line 1. `/rocky/d` deletes every line containing `rocky`. None of these changed the file: `sed` writes to standard output unless you ask it to edit in place.

4. Translate or delete characters with `tr`.

    ```bash
    head -n 2 servers.csv | tr ',' '\t'
    echo "Hello World" | tr 'a-z' 'A-Z'

    echo "phone: 555-0142" | tr -d -c '0-9\n'

    hostname	os	ram_gb	role	site
    web01	ubuntu	4	web	london

    too many spaces
    5550142
    ```

    ::: explain
    **What just happened:** `tr set1 set2` replaces each character in set 1 with the matching character in set 2: commas become tabs (`\t`), lowercase becomes uppercase. `-s` squeezes runs of a repeated character into one. `-d` deletes characters, and `-c` complements the set, so `-d -c '0-9\n'` deletes everything that is *not* a digit or newline. `tr` works on characters, not words: `tr 'cat' 'dog'` changes every `c` to `d`, every `a` to `o`, and every `t` to `g`.

5. Format output with `printf` and compare it with `echo`.

    echo "Server: web01"

    echo -e "col1\tcol2"

In the format, `%s` is a string, `%d` an integer, `%-8s` a string left-aligned in 8 characters, and `%3d` a number right-aligned in 3 characters. 7. Turn lines into arguments with `xargs`.

#### Task 8: Reuse commands with history, !, and !!

1. Show your command history.

    ```bash
    history | tail -n 5
    history 5
    echo "$HISTSIZE $HISTFILESIZE $HISTCONTROL"
    ```

    ```{.output}
      201  ...
      205  history 5
    1000 2000 ignoreboth
    ```

    ::: explain
    **What just happened:** `history` lists previous commands with numbers. `history 5` shows the last five. Bash keeps the list in memory and writes it to `~/.bash_history` when the shell exits. Ubuntu's `~/.bashrc` sets `HISTSIZE=1000` (commands kept in memory), `HISTFILESIZE=2000` (lines kept in the file), and `HISTCONTROL=ignoreboth`, which skips duplicate commands and any command that starts with a space. That last trick is handy: start a command with a space and it is not saved in history. Your numbers will differ.

    6.8.0-45-generic

    **What just happened:** `!!` expands to the previous command. Bash prints the expanded command line first so you can see what actually ran. `sudo !!` is the classic "I forgot sudo" fix: it re-runs the last command with `sudo` in front. `/etc/shadow` holds password hashes and is readable only by root.

#### Task 9: Edit files with vim and nano

1. Create a practice file for `vim`.

    ```bash
    cd ~/labs/1.5
    cat > vim-practice.txt <<'EOF'
    The colour of the server rack is grey.
    This line has a typo: teh.
    Delete this whole line.
    The colour of the cables is blue.
    EOF
    ```

2. Open it in `vim`. On Ubuntu, `vi` also starts `vim`.

    ```bash
    vim vim-practice.txt
    ```

    ::: explain
    **What just happened:** `vim` opens in **Normal mode**, where keys are *commands*, not text. This is the part that confuses beginners. There are three modes you need:

    - **Normal mode** (the default): move around, delete, copy, paste. Press Esc to get back here from anywhere.
    - **Insert mode**: typing inserts text. Enter it with `i` (insert before the cursor), `a` (append after it), `o` (open a new line below), or `A` (append at end of line). The bottom line shows `-- INSERT --`.
    - **Command-line mode**: press `:` in Normal mode to type commands such as `:w` (write/save) and `:q` (quit).
    :::

3. Follow these steps exactly inside `vim`. Press Esc whenever you are unsure which mode you are in.

    1. Type `:set number` and press Enter. Line numbers appear.
    2. Move with the arrow keys or `h` (left), `j` (down), `k` (up), `l` (right). Press `G` to jump to the last line, `gg` for the first line, `0` for the start of the line, `$` for the end.
    3. Fix the typo: type `/teh` and press Enter to search. The cursor jumps to `teh`. Type `cw` (change word), type `the`, then press Esc.
    4. Delete line 3: type `3G` to go to line 3, then `dd` to delete the line.
    5. Undo and redo: press `u` (the line comes back), then Ctrl+R (it is deleted again).
    6. Add a line: press `G`, then `o`, type `Added in vim.`, and press Esc.
    7. Copy and paste: press `gg`, then `yy` (yank, which means copy, the line), then `p` (paste below). Press `dd` to remove the duplicate. `x` deletes a single character.
    8. Search and replace in the whole file: type `:%s/colour/color/g` and press Enter. `%` means every line, `s` substitute, `g` every match on the line. The status line reports `2 substitutions on 2 lines`.
    9. Save and quit: type `:wq` and press Enter.

    ::: explain
    **What just happened:** You used the core `vim` survival kit. The quit commands are worth memorizing: `:w` saves, `:q` quits (only if there are no unsaved changes), `:wq` or `:x` or `ZZ` saves and quits, and `:q!` quits **without** saving, throwing changes away. If you ever get stuck, press Esc twice and type `:q!`. Searching uses `/pattern` (forward), `?pattern` (backward), `n` (next), and `N` (previous). For a full interactive course, run `vimtutor` later; it takes about 30 minutes.
    :::

4. Check your edits.

    ```bash
    cat vim-practice.txt
    ```

    ```{.output}
    The color of the server rack is grey.
    This line has a typo: the.
    The color of the cables is blue.
    Added in vim.
    ```

5. Now edit a file with `nano`.

    ```bash
    nano nano-practice.txt
    ```

    `nano` opens directly in a typing mode. The bottom two lines list shortcuts: `^` means Ctrl and `M-` means Alt. Do the following:

    1. Type three lines, pressing Enter after each one: `alpha`, `beta`, `gamma`. The cursor is now on an empty fourth line.
    2. Press Ctrl+O (write Out), confirm the file name with Enter. This saves.
    3. Press Ctrl+W (Where is), type `beta`, press Enter. The cursor jumps to it.
    4. Press Ctrl+K to cut the whole `beta` line. Press Alt+/ to jump to the last (empty) line, then press Ctrl+U to paste the line there.
    5. Press Ctrl+\\ (replace), type `gamma`, press Enter, type `delta`, press Enter, then press `A` to replace all.
    6. Try undo and redo: press Alt+U (the replacement is undone), then Alt+E (it is redone).
    7. Press Ctrl+X to exit. If there are unsaved changes, `nano` asks "Save modified buffer?"; press `Y` and then Enter.

    ```bash
    cat nano-practice.txt
    ```

    ```{.output}

    delta
    beta
    ```

    ::: explain
    **What just happened:** `nano` is a *modeless* editor: you type text directly and use Ctrl and Alt combinations for commands. Ctrl+O saves, Ctrl+X exits, Ctrl+W searches, Ctrl+K and Ctrl+U cut and paste lines, and Ctrl+G shows help. Start it with `nano -l file` to show line numbers, or use Ctrl+_ (or Alt+G) to jump to a line number. If your result differs, you probably pasted on a different line; that is fine, as long as you saw cut, paste, and replace work.

Ubuntu asks which editor to use for tools like `crontab -e` and `visudo` the first time you run them, or uses the `EDITOR`/`VISUAL` variables. `export EDITOR=vim` in `~/.profile` sets your choice; `sudo update-alternatives --config editor` changes the system default. On Rocky minimal, `vi` is `vim-minimal`; install `vim-enhanced` for the full `vim`, and `nano` with `sudo dnf install -y nano`.

### Exam corner

- Absolute paths start with `/` (or `~`, which expands to `$HOME`). Relative paths start from the current directory; `.` is the current directory, `..` the parent, and `cd -` returns to the previous directory (`$OLDPWD`).
- `HOME`, `USER`, `SHELL`, `PATH`, `PS1`, and `DISPLAY` are the key variables. `export` makes a variable visible to child processes; `env`/`printenv` list environment variables.
- `PATH` is searched left to right; the current directory is not in it, so run local scripts as `./script`.
- Login shells read `/etc/profile` then the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile`. Non-login interactive shells read `~/.bashrc`. `source file` or `. file` applies changes to the current shell.
- Streams: stdin = 0, stdout = 1, stderr = 2. `>` overwrites, `>>` appends, `2>` redirects errors, `2>&1` joins stderr to stdout (order matters), `&>` sends both, `<` feeds a file to stdin, `<<` is a here doc, `<<<` is a here string, `/dev/null` discards.
- `|` passes only stdout. `tee` writes to a file and stdout at the same time; `| sudo tee file` writes a root-owned file.
- `uniq` only removes *adjacent* duplicates, so `sort | uniq -c | sort -rn` is the classic "count and rank" pipeline.
- `cut -d, -f2` for delimited fields; `awk '{print $2}'` for whitespace-separated columns; `sed 's/a/b/g'` to substitute; `sed -i` edits in place; `tr` changes or deletes single characters.
- `xargs` turns stdin lines into command arguments; `bc` does decimal math (`scale=`); `printf` formats output without an automatic newline.
- `!!` repeats the last command (`sudo !!`), `!n` runs history entry `n`, `!string` runs the latest command starting with `string`, `!$` is the last argument.
- `vim`: `i` insert, Esc normal mode, `:w` save, `:q!` quit without saving, `:wq` save and quit, `dd` delete line, `yy`/`p` copy/paste, `u` undo, `/text` search, `:%s/old/new/g` replace. `nano`: Ctrl+O save, Ctrl+X exit, Ctrl+W search.
