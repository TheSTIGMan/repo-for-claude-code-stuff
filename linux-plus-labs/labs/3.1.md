## Lab 3.1: Authentication, Authorization, and Accounting {#lab-3-1}

::: labinfo
**Objective:** 3.1 Summarize authorization, authentication, and accounting methods.\
**Domain:** 3.0 Security (18% of the exam)\
**Time:** about 120 minutes\
**VM:** ubuntu-lab (main), rocky-lab (Samba client only)\

Every Linux security question boils down to three things: who are you, what may you do, and what did you do. In this lab you will touch every piece of that puzzle: PAM and directory services (LDAP, Kerberos, SSSD) for proving identity, polkit for deciding permissions, and journald, rsyslog, logrotate, and auditd for keeping records. On the exam, objective 3.1 is a "summarize" objective, so you must recognize each tool and its job; on the job, you will configure all of them.

### What you'll practice

- Authentication through **PAM** (Pluggable Authentication Modules): reading `/etc/pam.d/` files, control flags, adding and removing a module
- Authorization with **Polkit**: `pkaction`, `pkcheck`, and a JavaScript rule in `/etc/polkit-1/rules.d/`
- Directory and network identity: **LDAP** (`slapd`, `ldapadd`, `ldapsearch`), **Kerberos** (`krb5.conf`, `kinit`), **SSSD/Winbind realm** (`realm discover`, `sssd.conf`)
- File sharing and Windows-style identity with **Samba** (`smb.conf`, `smbpasswd`, `smbclient`)
- Logging: **journalctl** filters, persistent journal, **rsyslog** rules, **logrotate**, a tour of **/var/log**
- System audit: **auditd**, `auditctl`, rules in `/etc/audit/rules.d/` compiled into **audit.rules**, `ausearch`, `aureport`

### How it works

Security people use the term **AAA**:

- **Authentication** answers "Who are you?" You prove an identity with something you know (password), have (key, token), or are (fingerprint).
- **Authorization** answers "What are you allowed to do?" File permissions, `sudo` rules, and polkit rules are all authorization.
- **Accounting** answers "What did you do?" Logs and audit records let you reconstruct events later.

Think of a hotel. The front desk checks your ID (authentication), your key card only opens your room and the gym (authorization), and the card system records every door you opened (accounting).

**PAM** is the front desk for almost every Linux program that logs people in: `login`, `sshd`, `su`, `sudo`, `passwd`. Instead of each program knowing how to check passwords, each program asks PAM, and PAM runs a stack of small modules (`pam_unix.so`, `pam_access.so`, `pam_sss.so`, ...) listed in a file under `/etc/pam.d/` named after the program. Each line has a **type** (`auth` = check identity, `account` = is this account allowed now, `password` = change a password, `session` = set things up at login) and a **control flag** that says how much that module's answer matters.

**Polkit** (formerly PolicyKit) is an authorization service for system daemons. When an unprivileged program asks `systemd` to restart a service, `systemd` asks polkit "is this user allowed to do action `org.freedesktop.systemd1.manage-units`?" Polkit checks its rules and answers yes, no, or "ask for an admin password". `sudo` grants whole commands; polkit grants specific actions inside daemons.

**Directory services** keep user accounts on a central server instead of in every machine's `/etc/passwd`:

- **LDAP** (Lightweight Directory Access Protocol, TCP 389, or 636 for LDAPS) is a database of entries arranged in a tree, like `uid=jdoe,ou=people,dc=lab,dc=local`. OpenLDAP's server is `slapd`.
- **Kerberos** (TCP/UDP 88) is a ticket-based authentication protocol. You prove your password once to the KDC (Key Distribution Center) with `kinit`, get a ticket, and then show tickets instead of passwords. Realms are written in capitals: `LAB.LOCAL`.
- **Active Directory** (Microsoft) is LDAP plus Kerberos plus DNS.
- **SSSD** (System Security Services Daemon) is the Linux client that talks to LDAP, Kerberos, AD, or FreeIPA and caches the answers, so `getent passwd jdoe` works even though jdoe is not in `/etc/passwd`. **Winbind** (part of Samba) does a similar job for AD. **realmd** (`realm` command) is a helper that discovers a domain and configures SSSD or Winbind for you.
- **Samba** implements the Windows SMB/CIFS file-sharing protocol (TCP 445) on Linux, and can even act as an AD domain controller.

**Logging** has two main systems on modern distributions:

```{.diagram}
  programs ----> journald (binary journal) ----> journalctl
     |                 |
     |   (syslog API)  +---- forwards ----> rsyslog ---> text files in /var/log
     +------------------------------------->           (syslog, auth.log, ...)
                                                             |
                                                         logrotate (rotate,
                                                         compress, delete)
```

`systemd-journald` collects everything (kernel, services, `syslog()` calls) in an indexed binary journal that you query with `journalctl`. `rsyslog` receives a copy and writes classic text files using **facility.priority** rules (for example `auth.*` or `local5.info`). `logrotate` stops text logs from filling the disk.

**auditd** is different from ordinary logging. The kernel itself generates audit records when watched files are touched or watched system calls are made, and `auditd` writes them to `/var/log/audit/audit.log`. Programs cannot avoid or fake these records, which is why auditors love them. Rules are loaded with `auditctl`, and persistent rules live in `/etc/audit/rules.d/*.rules`, which `augenrules` merges into `/etc/audit/audit.rules`.

### Tasks

#### Task 1: Read PAM stacks and understand control flags

1. Create your working directory and look at the PAM configuration directory.

    ```bash
    mkdir -p ~/labs/3.1 && cd ~/labs/3.1
    ls /etc/pam.d/
    ```

    ```{.output}
    chfn         common-password                login     runuser    sshd
    chpasswd     common-session                 newusers  runuser-l  su
    chsh         common-session-noninteractive  other     sudo       sudo-i
    common-account  common-auth                 passwd    samba      su-l
    ```

    ::: explain
    **What just happened:** each file is a PAM "service" named after the program that uses it. `sshd` is read by the SSH server, `login` by console logins, `sudo` by sudo. The `common-*` files are Ubuntu's shared building blocks that other files include. (Rocky uses `system-auth` and `password-auth` for the same job.) The `other` file is the fallback for programs with no file of their own.
    :::

2. Look at the shared authentication stack, hiding comments and blank lines.

    ```bash
    grep -Ev '^#|^$' /etc/pam.d/common-auth
    ```

    ```{.output}
    auth	[success=1 default=ignore]	pam_unix.so nullok
    auth	requisite			pam_deny.so
    auth	required			pam_permit.so
    auth	optional			pam_cap.so
    ```

    ::: explain
    **What just happened:** `grep -Ev` prints lines that do **not** match (`-v`) the extended regex (`-E`) "starts with `#`" or "is empty". Read the stack top to bottom:

    - `pam_unix.so` checks the password against `/etc/shadow`. The bracket control `[success=1 default=ignore]` means "if the password is right, **skip the next 1 line**; otherwise ignore this result and continue".
    - So on success you jump over `pam_deny.so` (which always fails) and land on `pam_permit.so` (which always succeeds). On failure you hit `pam_deny.so`, and because it is `requisite`, PAM stops immediately with failure.
    - `pam_cap.so` is `optional`: its result only matters if it is the only module.
    :::

3. Learn the four classic control flags. Read this table carefully; it is a favorite exam topic.

    | Flag | If the module succeeds | If the module fails |
    |---|---|---|
    | `required` | keep going | remember the failure, **keep going**, fail at the end |
    | `requisite` | keep going | **stop now** and fail |
    | `sufficient` | **stop now** with success (if nothing required failed earlier) | ignore, keep going |
    | `optional` | only matters if it is the only module | only matters if it is the only module |

    Two more keywords appear in the control column: `include` (pull in another file's lines of the same type) and `substack` (like include, but a `requisite` failure only ends the substack). Ubuntu also uses `@include common-auth`, which includes the whole file.

4. Now look at the SSH and console login stacks.

    ```bash
    grep -Ev '^#|^$' /etc/pam.d/sshd
    grep -n pam_access /etc/pam.d/sshd
    grep -Ev '^#|^$' /etc/pam.d/login | head -15
    ```

    ```{.output}
    @include common-auth
    account    required     pam_nologin.so
    @include common-account
    session [success=ok ignore=ignore module_unknown=ignore default=bad] pam_selinux.so close
    session    required     pam_loginuid.so
    session    optional     pam_keyinit.so force revoke
    @include common-session
    session    optional     pam_motd.so  motd=/run/motd.dynamic
    session    optional     pam_motd.so noupdate
    session    optional     pam_mail.so standard noenv
    session    required     pam_limits.so
    session    required     pam_env.so
    session    required     pam_env.so envfile=/etc/default/locale
    ...
    12:# account  required     pam_access.so
    ```

    ::: explain
    **What just happened:** `sshd` reuses `common-auth` for passwords, then adds account checks such as `pam_nologin.so` (refuse non-root logins while `/etc/nologin` exists) and session modules such as `pam_motd.so` (print the "message of the day" banner) and `pam_limits.so` (apply `/etc/security/limits.conf`). The second command shows that line 12 contains a **commented-out** `pam_access.so` line. You will enable it next. The `login` file is similar but adds console-only modules like `pam_faildelay.so`.
    :::

::: checkpoint
**Checkpoint:** you can explain why a wrong password in `common-auth` ends at `pam_deny.so`, and you know the difference between `required` and `requisite`.
:::

#### Task 2: Make a harmless PAM change, test it, and revert it

You will use `pam_access.so` to block SSH logins for one test user only. Your own `student` account is not affected, but PAM mistakes can lock you out, so follow the safety steps.

::: warning
Take a snapshot now if you have not. Keep a **second terminal** logged in as `student` (or keep the VM console open) for the whole task. If logins break, you fix the file from the session that is still open: `sudo cp /etc/pam.d/sshd.bak /etc/pam.d/sshd`.
:::

1. Create a test user and back up the file you will change.

    ```bash
    sudo useradd -m -s /bin/bash labpam
    sudo passwd labpam
    sudo cp /etc/pam.d/sshd /etc/pam.d/sshd.bak
    ```

    ::: explain
    **What just happened:** `useradd -m` creates the user and a home directory; `-s /bin/bash` sets the login shell. `passwd labpam` asks you to type a new password twice (pick something simple like `Lab3.1pass`). The `cp` makes a backup you can restore in one command.
    :::

2. Confirm that `labpam` can log in over SSH **before** you change anything.

    ```bash
    ssh labpam@localhost whoami
    ```

    ```{.output}
    labpam@localhost's password:
    labpam
    ```

    Type `yes` if asked to trust the host key. If you see `Permission denied (publickey)`, password logins are turned off in your SSH server; check `sudo sshd -T | grep passwordauthentication`, which should say `yes` for this test.

3. Enable `pam_access.so`. Open the file with `sudo nano /etc/pam.d/sshd`, find the line `# account  required     pam_access.so`, and delete the leading `# ` so it reads:

    ```text
    account  required     pam_access.so
    ```

    Save with Ctrl+O, Enter, and exit with Ctrl+X. Verify:

    ```bash
    grep -n pam_access /etc/pam.d/sshd
    ```

    ```{.output}
    12:account  required     pam_access.so
    ```

4. Add a rule to `/etc/security/access.conf`. The format is `permission:users:origins`, where `+` allows and `-` denies.

    ```bash
    echo '-:labpam:ALL' | sudo tee -a /etc/security/access.conf
    tail -1 /etc/security/access.conf
    ```

    ::: explain
    **What just happened:** `tee -a` appends (`-a`) the text to the file; you need `sudo tee` because a plain `>>` redirection would run as your normal user and fail. The rule means "deny (`-`) user `labpam` from ALL origins". Every other line in the file is a comment, so all other users are still allowed.
    :::

5. Test. PAM files are read fresh at every login, so no restart is needed.

    ```bash
    ssh labpam@localhost whoami
    sudo journalctl -u ssh -n 5 --no-pager | grep -i access
    ```

    ```{.output}
    labpam@localhost's password:
    Connection closed by 127.0.0.1 port 22
    ... sshd[2412]: pam_access(sshd:account): access denied for user `labpam'
        from `127.0.0.1'
    ```

    ::: explain
    **What just happened:** the password was correct, so the `auth` stack succeeded (authentication). Then the `account` stack ran `pam_access.so`, which said no (authorization), and SSH closed the connection. The journal entry is the accounting record. Confirm `ssh student@localhost whoami` still works.
    :::

6. Revert the change so later labs are not affected.

    ```bash
    sudo cp /etc/pam.d/sshd.bak /etc/pam.d/sshd
    sudo sed -i '/^-:labpam:ALL$/d' /etc/security/access.conf
    ssh labpam@localhost whoami
    ```

    ::: explain
    **What just happened:** `sed -i '/pattern/d'` deletes, in place (`-i`), every line matching the pattern. The last command should print `labpam` again.
    :::

::: checkpoint
**Checkpoint:** `grep -c '^account.*pam_access' /etc/pam.d/sshd` prints `0`, and `ssh labpam@localhost whoami` prints `labpam`.
:::

#### Task 3: Authorization with polkit

1. Install the polkit tools and list a few actions.

    ```bash
    sudo apt install -y polkitd pkexec
    pkaction | grep systemd1
    pkaction --action-id org.freedesktop.systemd1.manage-units --verbose
    ```

    ```{.output}
    org.freedesktop.systemd1.manage-units
    org.freedesktop.systemd1.manage-unit-files
    org.freedesktop.systemd1.reload-daemon
    ...
    org.freedesktop.systemd1.manage-units:
      description:       Manage system services or other units
      message:           Authentication is required to manage system services or ...
      vendor:            The systemd Project
      implicit any:      auth_admin
      implicit inactive: auth_admin
      implicit active:   auth_admin_keep
    ```

    ::: explain
    **What just happened:** `pkaction` lists every action ID that daemons have registered (from XML files in `/usr/share/polkit-1/actions/`). The verbose view shows the **defaults**: `auth_admin` means "ask for an administrator's password", `auth_admin_keep` means "ask, then remember for a few minutes". "Active" means a user at the local console; "any" includes SSH sessions. Other possible values are `yes`, `no`, and `auth_self` (ask for the user's own password).
    :::

2. See who counts as an "administrator". On Ubuntu, a vendor rule makes the `sudo` group the admin group.

    ```bash
    ls /usr/share/polkit-1/rules.d/ /etc/polkit-1/rules.d/
    sudo cat /usr/share/polkit-1/rules.d/40-debian-sudo.rules
    ```

    ```{.output}
    polkit.addAdminRule(function(action, subject) {
        return ["unix-group:sudo"];
    });
    ```

    ::: tip
    Polkit version 0.106 and later (Ubuntu 23.04+, Debian 12+, all RHEL 8/9) uses **JavaScript `.rules` files** in `/etc/polkit-1/rules.d/` (local admin) and `/usr/share/polkit-1/rules.d/` (packages). Older Debian/Ubuntu releases used INI-style `.pkla` files under `/etc/polkit-1/localauthority/`. You may still see `.pkla` in old documentation.
    :::

3. Create a demo service and a non-admin operator account.

    ```bash
    cat <<'EOF' | sudo tee /etc/systemd/system/labdemo.service
    [Unit]
    Description=Lab 3.1 polkit demo service

    [Service]
    ExecStart=/usr/bin/sleep infinity
    EOF
    sudo systemctl daemon-reload
    sudo systemctl start labdemo
    sudo groupadd labops
    sudo useradd -m -s /bin/bash -G labops opsuser
    sudo passwd opsuser
    ```

    ::: explain
    **What just happened:** `cat <<'EOF' ... EOF` is a **heredoc**: everything between the two `EOF` markers is fed to the command as input. Piping it to `sudo tee FILE` writes the file as root. The quotes around `'EOF'` stop the shell from expanding `$` variables inside. The unit simply runs `sleep infinity`, a process that does nothing forever. `-G labops` puts `opsuser` in the supplementary group `labops`.
    :::

4. Switch to `opsuser` and try to restart the service without sudo.

    ```bash
    su - opsuser
    systemctl restart labdemo
    ```

    ```{.output}
    ==== AUTHENTICATING FOR org.freedesktop.systemd1.manage-units ====
    Authentication is required to restart 'labdemo.service'.
    Authenticating as: student
    Password:
    ```

    ::: explain
    **What just happened:** `su -` starts a full login shell as another user (you typed opsuser's password). `systemctl` sent the request to systemd over D-Bus; systemd asked polkit; polkit answered `auth_admin`, so a text agent (`pkttyagent`) asks for the password of an admin (`student`, a member of `sudo`). Press **Ctrl+C** to cancel instead of typing it.
    :::

5. Ask polkit directly with `pkcheck`, still as `opsuser`.

    ```bash
    pkcheck --action-id org.freedesktop.systemd1.manage-units --process $$ \
      --detail unit labdemo.service --detail verb restart; echo "exit=$?"
    exit
    ```

    ```{.output}
    Authorization requires authentication but no agent is available.
    exit=2
    ```

    ::: explain
    **What just happened:** `pkcheck` asks "is the process `$$` (the PID of your current shell) authorized for this action?" The `--detail` options pass the same extra information systemd passes (which unit, which verb). Exit code `0` = authorized, `1` = not authorized, `2` = would need a password. `exit` returns you to `student`.
    :::

6. Write a rule that lets members of `labops` start, stop, and restart **only** `labdemo.service`.

    ```bash
    cat <<'EOF' | sudo tee /etc/polkit-1/rules.d/50-labops.rules
    // Let the labops group manage labdemo.service without a password
    polkit.addRule(function(action, subject) {
        if (action.id == "org.freedesktop.systemd1.manage-units" &&
            action.lookup("unit") == "labdemo.service" &&
            subject.isInGroup("labops")) {
            var verb = action.lookup("verb");
            if (verb == "start" || verb == "stop" || verb == "restart") {
                return polkit.Result.YES;
            }
        }
    });
    EOF
    sudo journalctl -u polkit -n 3 --no-pager
    ```

    ::: explain
    **What just happened:** polkit calls every `addRule` function, in file-name order, for each request. The function receives the `action` (with details from `action.lookup()`) and the `subject` (the user asking). Returning `polkit.Result.YES` grants the action; returning nothing means "no opinion, keep checking". Polkit watches the directory and reloads automatically; the journal shows a line like `Reloading rules` and `Finished loading, compiling and executing 3 rules`.
    :::

7. Test again as `opsuser`.

    ```bash
    su - opsuser
    systemctl restart labdemo && echo restarted
    systemctl restart cron
    exit
    ```

    ```{.output}
    restarted
    ==== AUTHENTICATING FOR org.freedesktop.systemd1.manage-units ====
    Authentication is required to restart 'cron.service'.
    ```

    Press Ctrl+C at the second prompt. The rule only covers `labdemo.service`.

::: checkpoint
**Checkpoint:** as `opsuser`, `systemctl restart labdemo` works with no prompt, but restarting any other unit asks for an admin password.
:::

#### Task 4: Directory services: LDAP, SSSD, Kerberos, and realm

In a company you would join an existing directory. Here you will build a tiny local LDAP server, point SSSD at it, and explore the Kerberos and realm tools.

1. Pre-answer the OpenLDAP installer questions with **debconf**, then install the server and client tools.

    ```bash
    cat <<'EOF' | sudo debconf-set-selections
    slapd slapd/no_configuration boolean false
    slapd slapd/domain string lab.local
    slapd shared/organization string Lab Org
    slapd slapd/password1 password LdapLab123
    slapd slapd/password2 password LdapLab123
    EOF
    sudo DEBIAN_FRONTEND=noninteractive apt install -y slapd ldap-utils
    ```

    ::: explain
    **What just happened:** Debian packages ask setup questions through **debconf**. `debconf-set-selections` stores answers in advance, and `DEBIAN_FRONTEND=noninteractive` tells apt not to ask. The domain `lab.local` becomes the directory's **base DN** (Distinguished Name) `dc=lab,dc=local` ("dc" = domain component), and the admin account is `cn=admin,dc=lab,dc=local` with password `LdapLab123`.
    :::

2. Query the empty directory anonymously.

    ```bash
    ldapsearch -x -H ldap://localhost -b dc=lab,dc=local
    ```

    ```{.output}
    # lab.local
    dn: dc=lab,dc=local
    objectClass: top
    objectClass: dcObject
    objectClass: organization
    o: Lab Org
    dc: lab
    # search result
    search: 2
    result: 0 Success
    ```

    ::: explain
    **What just happened:** `-x` uses simple authentication (here anonymous, since no bind DN was given) instead of SASL. `-H` is the server URI and `-b` the search base. Every entry has a `dn` and attributes; `objectClass` attributes decide which other attributes are allowed. `result: 0 Success` means the search worked.
    :::

3. Add an organizational unit and a user from an **LDIF** (LDAP Data Interchange Format) file.

    ```bash
    cat <<'EOF' > ~/labs/3.1/users.ldif
    dn: ou=people,dc=lab,dc=local
    objectClass: organizationalUnit
    ou: people

    dn: uid=jdoe,ou=people,dc=lab,dc=local
    objectClass: inetOrgPerson
    objectClass: posixAccount
    uid: jdoe
    cn: Jane Doe
    sn: Doe
    mail: jdoe@lab.local
    uidNumber: 10001
    gidNumber: 10001
    homeDirectory: /home/jdoe
    loginShell: /bin/bash
    EOF
    ldapadd -x -D cn=admin,dc=lab,dc=local -W -f ~/labs/3.1/users.ldif
    ```

    ```{.output}
    Enter LDAP Password:
    adding new entry "ou=people,dc=lab,dc=local"

    adding new entry "uid=jdoe,ou=people,dc=lab,dc=local"
    ```

    ::: explain
    **What just happened:** a blank line separates entries in LDIF. `posixAccount` adds the Unix attributes (`uidNumber`, `homeDirectory`, `loginShell`) that make the entry usable as a Linux login. `ldapadd` binds (`-D`) as the admin DN, `-W` prompts for its password (`LdapLab123`), and `-f` reads the file.
    :::

4. Search with a filter and ask for only two attributes.

    ```bash
    ldapsearch -x -H ldap://localhost -b dc=lab,dc=local '(uid=jdoe)' cn mail
    ```

    ```{.output}
    dn: uid=jdoe,ou=people,dc=lab,dc=local
    cn: Jane Doe
    mail: jdoe@lab.local
    ```

5. Install SSSD, the realm tool, and the Kerberos client. The Kerberos package also asks debconf questions, so install non-interactively.

    ```bash
    sudo DEBIAN_FRONTEND=noninteractive apt install -y sssd sssd-tools realmd krb5-user
    grep -E '^(passwd|group|shadow):' /etc/nsswitch.conf
    ```

    ```{.output}
    passwd:         files systemd sss
    group:          files systemd sss
    shadow:         files systemd sss
    ```

    ::: explain
    **What just happened:** the `libnss-sss` package (pulled in by `sssd`) added `sss` to `/etc/nsswitch.conf`, the file that tells the C library where to look up users and groups. Lookups now check local files first, then systemd, then SSSD. The `libpam-sss` package also added `pam_sss.so` to the `common-*` PAM files, so PAM can authenticate directory users.
    :::

6. Point SSSD at your LDAP server. SSSD refuses to start unless its config file is owned by root with mode `600`.

    ```bash
    cat <<'EOF' | sudo tee /etc/sssd/sssd.conf
    [sssd]
    services = nss, pam
    domains = lab.local

    [domain/lab.local]
    id_provider = ldap
    auth_provider = ldap
    ldap_uri = ldap://localhost
    ldap_search_base = dc=lab,dc=local
    cache_credentials = false
    EOF
    sudo chmod 600 /etc/sssd/sssd.conf
    sudo sssctl config-check
    sudo systemctl restart sssd
    getent passwd jdoe
    id jdoe
    ```

    ```{.output}
    Issues identified by validators: 0
    jdoe:*:10001:10001:Jane Doe:/home/jdoe:/bin/bash
    uid=10001(jdoe) gid=10001 groups=10001
    ```

    ::: explain
    **What just happened:** `id_provider = ldap` says "get user and group identities from LDAP"; `auth_provider` says where passwords are checked. `getent passwd jdoe` looked through NSS, found nothing in `/etc/passwd`, asked SSSD, and SSSD asked `slapd`. jdoe now exists on this machine as far as every program is concerned, without ever being in `/etc/passwd`. The group shows as a bare number because no group 10001 exists in LDAP. In production you must use TLS (`ldaps://` or StartTLS); SSSD will not send passwords over plain LDAP.
    :::

7. Explore the Kerberos client configuration and try to get a ticket.

    ```bash
    grep -A3 '^\[libdefaults\]' /etc/krb5.conf
    kinit jdoe@LAB.LOCAL
    klist
    ```

    ```{.output}
    [libdefaults]
    	default_realm = 
    ...
    kinit: Cannot find KDC for realm "LAB.LOCAL" while getting initial credentials
    klist: No credentials cache found (filename: /tmp/krb5cc_1000)
    ```

    ::: tip
    **Explore/simulate:** there is no Kerberos KDC in this lab, so `kinit` fails at the "find the KDC" step, which proves the client is working and looking. On a real network, `/etc/krb5.conf` would contain something like the block below, `kinit` would ask for a password and store a ticket, and `klist` would list it with an expiry time. `kdestroy` deletes your tickets.
    :::

#### Task 7: Route a custom facility with rsyslog and rotate it with logrotate

1. Check that rsyslog is running and see its default rules.

    ```bash

    ```

    ```{.output}
    active
    auth,authpriv.*			/var/log/auth.log
    *.*;auth,authpriv.none		-/var/log/syslog
    kern.*				-/var/log/kern.log
    mail.*				-/var/log/mail.log
    mail.err			/var/log/mail.err
    *.emerg				:omusrmsg:*
    ```

    ::: explain
    **What just happened:** each rule is `selector  action`. The selector is `facility.priority`: `auth,authpriv.*` means facilities auth and authpriv at any priority; `authpriv.none` excludes them. A `-` before a file name means "do not sync after every write" (faster). Facilities include `kern`, `user`, `mail`, `daemon`, `auth`, `authpriv`, `cron`, and `local0` to `local7`, which are free for your own applications.

2. Create a rule that sends facility `local5` to its own file and stops it from also going to `syslog`.

    ```bash
    cat <<'EOF' | sudo tee /etc/rsyslog.d/30-lab.conf
    # Lab 3.1: local5 messages go to their own file only
    local5.*    /var/log/lab-local5.log
    & stop
    EOF
    sudo rsyslogd -N1
    sudo systemctl restart rsyslog
    ```

    ```{.output}
    rsyslogd: version 8.2312.0, config validation run (level 1), master config
    /etc/rsyslog.conf
    rsyslogd: End of config validation run. Bye.
    ```

    ::: explain
    **What just happened:** files in `/etc/rsyslog.d/` are read in name order, so `30-lab.conf` runs before `50-default.conf`. `&` means "for the same messages as the previous line", and `stop` discards them so no later rule sees them. `rsyslogd -N1` checks the config without starting the daemon. 4. Create a logrotate policy for the new file.

    ```bash
    cat <<'EOF' | sudo tee /etc/logrotate.d/lab-local5
    /var/log/lab-local5.log {
        su root adm
        daily
        rotate 4
        compress
        delaycompress
        missingok
        notifempty
        create 0640 syslog adm
        postrotate
            /usr/lib/rsyslog/rsyslog-rotate
        endscript
    }
    EOF
    ```

    ::: explain
    **What just happened:** each directive in the block:

    - `daily` rotate once a day (`weekly`, `monthly`, or `size 10M` are alternatives); `rotate 4` keep four old copies.
    - `compress` gzip old logs; `delaycompress` wait one cycle so the newest old log (`.1`) stays plain text.
    - `missingok` no error if the file is missing; `notifempty` skip rotation if it is empty.
    - `create 0640 syslog adm` make a fresh empty file with these permissions and owner.
    - `postrotate ... endscript` commands run after rotating; Ubuntu's `rsyslog-rotate` script tells rsyslog to reopen its files, otherwise it would keep writing into the renamed file.
    - `su root adm` rotate as this user and group. It is needed because `/var/log` is group-writable, which logrotate considers insecure without it. (Ubuntu's main `/etc/logrotate.conf` sets this globally, but you are about to run this file on its own.)
    :::

    ```{.output}
    -rw-r----- 1 syslog adm 140 Oct 10 10:20 /var/log/lab-local5.log.1
    ```

    ::: explain
    **What just happened:** `-d` (debug) shows what logrotate **would** do and changes nothing. `-f` (force) rotates even if it is not due. The old content is now `lab-local5.log.1` (not compressed yet because of `delaycompress`), and the new message went to a fresh file, proving the postrotate script worked. ### Exam corner

- **AAA:** authentication = prove identity, authorization = decide what is allowed, accounting = record what happened.
- PAM files live in `/etc/pam.d/<service>`; types are `auth`, `account`, `password`, `session`.
- Control flags: `required` (fail at end), `requisite` (fail now), `sufficient` (succeed now if nothing failed), `optional`; plus `include` and `substack`.
- `pam_access.so` reads `/etc/security/access.conf`; `pam_limits.so` reads `/etc/security/limits.conf`; `pam_nologin.so` checks `/etc/nologin`.
- Polkit actions are listed by `pkaction`, tested with `pkcheck`, and run as root with `pkexec`. Local JavaScript rules go in `/etc/polkit-1/rules.d/*.rules`.
- LDAP: TCP 389, LDAPS 636; tools `ldapsearch`, `ldapadd`, `ldapmodify`; entries identified by DN such as `uid=jdoe,ou=people,dc=lab,dc=local`.
- Kerberos: port 88, KDC issues tickets; `kinit` gets a ticket, `klist` lists, `kdestroy` removes; config in `/etc/krb5.conf`; realm names are uppercase.
- SSSD (`/etc/sssd/sssd.conf`, mode 600) and Winbind connect Linux to LDAP/AD; `realm discover` and `realm join` set them up; `nsswitch.conf` needs `sss` (or `winbind`).
- Samba: config `/etc/samba/smb.conf`, check with `testparm`, users added with `smbpasswd -a`, client `smbclient`, port 445.
- `journalctl` filters: `-u unit`, `-p priority`, `-b`, `--since`, `-f`, `-k`; persistent storage needs `/var/log/journal` or `Storage=persistent`.
- rsyslog selectors are `facility.priority`; config in `/etc/rsyslog.conf` and `/etc/rsyslog.d/`; test messages with `logger`.
- logrotate: `/etc/logrotate.conf` and `/etc/logrotate.d/`; `-d` dry run, `-f` force. auditd: `auditctl -w ... -p ... -k ...`, persistent rules in `/etc/audit/rules.d/` compiled by `augenrules` into `audit.rules`; search with `ausearch -k`, report with `aureport`.
