Modern Linux admins rarely configure servers one by one. They describe the servers they want in text files, store those files in Git, and let tools build and check the servers for them. In this lab you will try the main tools the exam names: Ansible, Puppet, OpenTofu, Kickstart, cloud-init, a small CI/CD pipeline, Docker Compose, Docker Swarm, and Kubernetes. The goal is not to master each one but to touch each idea with your own hands so the exam terms make sense.

### What you'll practice

- Infrastructure as code (IaC) with **Ansible**: playbooks, inventory, modules, ad hoc commands, collections, facts, agentless design
- IaC with **Puppet**: classes, certificates, modules, facts, agent and agentless (`puppet apply`) modes
- IaC with **OpenTofu**: provider, resource, state, API
- Unattended deployment: **Kickstart** and **cloud-init**
- CI/CD: version control, shift left testing, GitOps, pipelines, DevSecOps
- Orchestration with **Kubernetes**: ConfigMaps, Secrets, Pods, Deployments, Volumes, Services, variables
- **Docker Swarm**: service, nodes, tasks, networks, scale
- **Docker/Podman Compose**: compose file, up/down, logs

### How it works

**Infrastructure as code (IaC)** means you describe your servers, networks, and services in text files instead of clicking or typing commands by hand. Think of a recipe card versus cooking from memory. With a recipe, anyone can make the same dish again, you can improve the recipe over time, and you can see exactly what changed between versions. IaC files live in **version control** (Git), so every change has an author, a date, and a reason.

Most IaC tools are **declarative**: you describe the end state ("nginx is installed and running"), not the steps. The tool compares the current state with the wanted state and only fixes the difference. Running the same code twice changes nothing the second time. This property is called **idempotence**, and it is what makes automation safe to repeat.

The tools in this lab fill different roles:

```{.diagram}
 Build the machine          Configure the OS           Run the apps
 ------------------         -----------------          ------------------
 OpenTofu (cloud APIs)      Ansible (push, SSH)        Docker Compose (1 host)
 Kickstart (RHEL install)   Puppet (pull, agent)       Docker Swarm (cluster)
 cloud-init (1st boot)                                 Kubernetes (cluster)

            ^ all of it stored in Git and tested by a CI/CD pipeline ^
```

**Ansible** is **agentless**. Nothing extra runs on the managed servers. The control node (your ubuntu-lab) connects over SSH, copies small Python programs called **modules** to the target, runs them, and deletes them. An **inventory** file lists the hosts and groups. A **playbook** is a YAML file of tasks. An **ad hoc** command runs one module from the command line without a playbook. Before running tasks, Ansible gathers **facts** (OS name, IP addresses, memory) about each host. **Collections** are bundles of extra modules you download with `ansible-galaxy`.

**Puppet** traditionally uses an **agent**. A Puppet agent service runs on every managed node and, every 30 minutes, asks the Puppet server for its configuration (a pull model). Agents and the server trust each other with TLS **certificates**: the agent sends a certificate signing request, and an admin signs it on the server. Puppet code is written in **manifests** (`.pp` files) that define **classes** (named, reusable blocks of configuration), grouped into **modules**. Puppet uses a tool called `facter` to collect **facts**. You can also run Puppet without a server (agentless) with `puppet apply`, which is what you will do.

**OpenTofu** is the open-source fork of Terraform. It builds infrastructure such as cloud VMs, DNS records, or containers. A **provider** is a plugin that knows how to talk to one platform's **API** (application programming interface: the set of web or socket calls a platform accepts). A **resource** is one thing the provider manages. OpenTofu remembers what it built in a **state** file, so next time it can compare the code, the state, and the real world.

**Kickstart** (RHEL family) and **cloud-init** (almost every cloud image, and Ubuntu autoinstall) give **unattended deployment**: a text file answers every installer or first-boot question so no human has to click.

**CI/CD** stands for continuous integration and continuous delivery/deployment. Every push to Git starts a **pipeline**: a series of automatic stages such as lint, test, security scan, and deploy. **Shift left testing** means moving tests earlier (to the left on a timeline), for example running a linter before you even commit. **DevSecOps** adds security checks (secret scanning, vulnerability scanning) into the same pipeline instead of at the end. **GitOps** goes one step further: the Git repository is the single source of truth, and an agent such as Argo CD or Flux keeps the live cluster matching what is in Git.

**Orchestration** means running and coordinating many containers across one or more hosts: starting them, restarting them when they crash, scaling them, and connecting them. **Docker Compose** runs a multi-container app on one host from a **compose file**. **Docker Swarm** clusters Docker hosts (**nodes**) and runs **services** made of **tasks** (one task = one container). **Kubernetes** is the industry standard: it runs **Pods** (one or more containers), managed by **Deployments**, reached through **Services**, configured with **ConfigMaps** and **Secrets**, and given storage through **volumes**.

#### Task 1: Set up Ansible and run ad hoc commands

1. Make a working directory for the whole lab and install Ansible on ubuntu-lab. On Ubuntu 24.04 the `ansible` package includes `ansible-core` plus a large set of community collections.

    ```{.output}
      configured module search path = ['/home/student/.ansible/plugins/modules', ...]
      ansible python module location = /usr/lib/python3/dist-packages/ansible

      executable location = /usr/bin/ansible
      python version = 3.12.3 (main, ...) [GCC 13.2.0] (/usr/bin/python3)
    ```

    ::: explain
    **What just happened:** `ansible --version` shows the core version (2.16 on Ubuntu 24.04), which Python it uses, and where it looks for collections. `config file = None` means no `ansible.cfg` was found yet. You will create one in this directory.
    :::

2. Ansible connects to managed hosts with SSH, so set up key login to rocky-lab. If you have not done Lab 3.3, create a key and copy it now. Press Enter to accept the defaults if `ssh-keygen` asks questions.

    ```bash
    test -f ~/.ssh/id_ed25519 || ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
    ssh-copy-id student@rocky-lab
    ssh student@rocky-lab hostname
    ```

    ::: explain
    **What just happened:** `test -f` checks whether the key file already exists; `||` runs `ssh-keygen` only if it does not. `-N ""` sets an empty passphrase (fine for a lab, not for production). `ssh-copy-id` appends your public key to `~/.ssh/authorized_keys` on rocky-lab. The last command must print `rocky-lab` without asking for a password. That is all Ansible needs on the target: SSH and Python. This is what **agentless** means.
    :::

3. Create the **inventory**, the list of hosts Ansible manages. You will use a heredoc to write files. A heredoc (`<<'EOF' ... EOF`) feeds every line up to `EOF` into the command. The quotes around `'EOF'` stop the shell from expanding `$` inside the text.

    ```bash
    cat > inventory.ini <<'EOF'
    [web_ubuntu]
    ubuntu-lab ansible_connection=local

    [web_rocky]
    rocky-lab ansible_user=student

    [webservers:children]
    web_ubuntu
    web_rocky
    EOF
    ```

    ::: explain
    **What just happened:** The file `inventory.ini` uses INI format. `[web_ubuntu]` and `[web_rocky]` are groups. `ansible_connection=local` tells Ansible to run tasks on ubuntu-lab directly instead of SSHing to itself. `ansible_user=student` sets the SSH login for rocky-lab. `[webservers:children]` makes a parent group that contains both groups, so you can target both VMs with one name. Every host is also in the built-in group `all`.
    :::

4. Create `ansible.cfg` in the same directory so you do not have to type `-i inventory.ini` every time, then show the inventory as a tree.

    ```bash
    cat > ansible.cfg <<'EOF'
    [defaults]
    inventory = inventory.ini
    EOF
    ansible-inventory --graph
    ```

    ```{.output}
    @all:
      |--@ungrouped:
      |--@webservers:
      |  |--@web_ubuntu:
      |  |  |--ubuntu-lab
      |  |--@web_rocky:
      |  |  |--rocky-lab
    ```

    ::: explain
    **What just happened:** Ansible reads `ansible.cfg` from the current directory first, then `~/.ansible.cfg`, then `/etc/ansible/ansible.cfg`. `ansible-inventory --graph` proves the groups were parsed the way you meant.
    :::

5. Run your first **ad hoc** command. An ad hoc command runs a single module against a host pattern: `ansible <pattern> -m <module> -a '<arguments>'`.

    ```bash

    ```

    ```{.output}
    ubuntu-lab | SUCCESS => {
        "ansible_facts": {
            "discovered_interpreter_python": "/usr/bin/python3"

        "changed": false,
        "ping": "pong"

    rocky-lab | SUCCESS => {

            "discovered_interpreter_python": "/usr/bin/python3"
    ```

    **What just happened:** The `ping` **module** is not ICMP ping. It logs in, finds Python, runs a tiny module, and returns `pong`. `ansible.builtin.ping` is the module's full name (FQCN, fully qualified collection name): collection `ansible.builtin`, module `ping`. `"changed": false` means nothing on the host was modified.

    **What just happened:** Facts are variables Ansible discovers about each host. Playbooks use them to make decisions, for example "install `httpd` if the OS family is RedHat, `nginx` if it is Debian".

7. Run a shell command on all hosts, then install a package on rocky-lab only. Installing needs root, so add `-b` (become, which uses `sudo`) and `-K` (ask for the sudo password).

    ```bash
    ansible all -m ansible.builtin.command -a 'uptime'
    ansible web_rocky -b -K -m ansible.builtin.dnf -a 'name=tree state=present'
    ansible web_rocky -b -K -m ansible.builtin.dnf -a 'name=tree state=present'
    ```

    ```{.output}
    BECOME password:
    rocky-lab | CHANGED => {
        "changed": true,
        "msg": "",
        "rc": 0,
        "results": [
            "Installed: tree-1.8.0-10.el9.x86_64"

    BECOME password:
    rocky-lab | SUCCESS => {
        "changed": false,
        "msg": "Nothing to do",
        ...
    ```

    ::: explain
    **What just happened:** The `command` module runs a program and returns its output (`CHANGED` is printed because Ansible cannot know whether an arbitrary command changed anything).     `-K` sends one password to every host. Keep the `student` password the same on both VMs for this lab. In production you would use SSH keys plus passwordless sudo for an automation account, or store secrets with `ansible-vault`.

#### Task 2: Write a playbook with variables, handlers, and a collection

1. A real project separates data from logic. Create **group variables** so each OS group gets the right package name. Ansible automatically loads `group_vars/<groupname>.yml` for hosts in that group.

    ```bash
    mkdir -p group_vars templates
    cat > group_vars/web_ubuntu.yml <<'EOF'
    web_pkg: nginx
    web_service: nginx
    web_conf: /etc/nginx/conf.d/security.conf
    web_conf_content: |
      server_tokens off;
    EOF
    cat > group_vars/web_rocky.yml <<'EOF'
    web_pkg: httpd
    web_service: httpd
    web_conf: /etc/httpd/conf.d/security.conf
    web_conf_content: |
      ServerTokens Prod
      ServerSignature Off
    EOF
    ```

    ::: explain
    **What just happened:** Each file defines **variables** (`web_pkg`, `web_service`, and so on). The `|` in YAML starts a multi-line string. Both configs hide the web server's version number from HTTP headers, a common hardening step.
    :::

2. Create a Jinja2 **template** for the home page. Text inside `{{ }}` is replaced with variable or fact values when the file is copied. The file is `templates/index.html.j2`:

    ```bash
    cat > templates/index.html.j2 <<'EOF'
    <h1>{{ site_title }}</h1>
    <p>Host {{ ansible_facts['hostname'] }} runs {{ ansible_facts['distribution'] }}
    {{ ansible_facts['distribution_version'] }}</p>
    EOF
    ```

3. Now write the **playbook** `webservers.yml`. Read every line; the explanation follows.

    ```bash
    cat > webservers.yml <<'EOF'
    ---
    - name: Configure the lab web servers
      hosts: webservers
      become: true
      vars:
        site_title: "Deployed by Ansible"

      tasks:
        - name: Install the web server package
          ansible.builtin.package:
            name: "{{ web_pkg }}"
            state: present

        - name: Hide the server version in HTTP headers
          ansible.builtin.copy:
            dest: "{{ web_conf }}"
            content: "{{ web_conf_content }}"
            owner: root
            group: root
            mode: "0644"
          notify: Restart web server

        - name: Publish the home page
          ansible.builtin.template:
            src: index.html.j2
            dest: /var/www/html/index.html
            owner: root
            group: root
            mode: "0644"

        - name: Start the web server now and at boot
          ansible.builtin.service:
            name: "{{ web_service }}"
            state: started
            enabled: true

        - name: Open HTTP in firewalld (Rocky only)
          ansible.posix.firewalld:
            service: http
            permanent: true
            immediate: true
            state: enabled
          when: ansible_facts['os_family'] == 'RedHat'

      handlers:
        - name: Restart web server
          ansible.builtin.service:
            name: "{{ web_service }}"
            state: restarted
    EOF
    ```

    ::: explain
    **What just happened:** A playbook is a list of **plays**. This play targets the `webservers` group, uses `become: true` (sudo) for every task, and defines a play variable `site_title`. Each task calls one module:

    - `package` picks apt or dnf automatically, so one task works on both OSes.
    - `copy` with `content:` writes a file. `notify:` means "if this task changed something, run the handler called *Restart web server* at the end of the play".
    - `template` renders the Jinja2 file with variables and facts.
    - `service` makes sure the service is running and enabled at boot.
    - `firewalld` comes from the `ansible.posix` collection. The `when:` condition uses a fact so the task only runs on RedHat-family hosts (Ubuntu's firewall, `ufw`, is inactive by default).

    **Handlers** run once, only when notified, after all tasks. That avoids restarting a service when nothing changed.
    :::

4. Check the syntax, then run the playbook.

    ```bash
    ansible-playbook webservers.yml --syntax-check
    ansible-playbook webservers.yml -K
    ```


    **What just happened:** Ansible ran each task on both hosts in parallel. Read the `PLAY RECAP` first: `failed=0` and `unreachable=0` mean success. `skipping` shows the `when:` condition worked.

#### Task 3: Puppet facts, classes, modules, and certificates

1. Install Puppet from the Ubuntu archive. Ubuntu 24.04 ships Puppet 8 and Facter 4. The package enables the Puppet agent service, which would keep trying to reach a server called `puppet` that does not exist, so stop and disable it.

    ```bash
    sudo apt install -y puppet
    puppet --version
    systemctl status puppet --no-pager
    sudo systemctl disable --now puppet
    ```

    ```{.output}
    8.4.0
    ...
    ```

    ::: explain
    **What just happened:** `puppet.service` is the **agent**. In agent mode it wakes up every 30 minutes, sends its facts to the Puppet server, receives a compiled catalog (the list of resources it should have), and applies it. You disabled it because this lab uses agentless `puppet apply`.
    :::

2. Look at the **facts** that Puppet's `facter` tool collects. Facts are named with dots for nested values.

    ```bash
    facter os.name os.release.full
    facter networking.hostname networking.ip
    facter memory.system.total
    ```

    ```{.output}
    os.name => Ubuntu
    os.release.full => 24.04
    networking.hostname => ubuntu-lab
    networking.ip => 192.168.100.10
    memory.system.total => 3.82 GiB
    ```

    ::: explain
    **What just happened:** Facts in Puppet play the same role as Ansible facts: they describe the node so code can adapt to it. In manifests you read them as `$facts['os']['name']`.
    :::

3. Build a Puppet **module** containing a **class**. A module is a directory with a fixed layout; the main class lives in `manifests/init.pp` and has the same name as the module.

    ```bash
    mkdir -p ~/labs/4.1/puppet/modules/labbase/manifests
    cd ~/labs/4.1/puppet
    cat > modules/labbase/manifests/init.pp <<'EOF'
    # Class labbase: baseline settings for every lab server
    class labbase (
      String $banner_text = 'Managed by Puppet',
    ) {
      package { 'figlet':
        ensure => installed,
      }

      file { '/etc/puppet-demo.txt':
        ensure  => file,
        owner   => 'root',
        group   => 'root',
        mode    => '0644',
        content => "${banner_text} on ${facts['networking']['hostname']} \
    (${facts['os']['name']} ${facts['os']['release']['full']})\n",
        require => Package['figlet'],
      }
    }
    EOF
    cat > site.pp <<'EOF'
    class { 'labbase':
      banner_text => 'Configured by the labbase class',
    }
    EOF
    puppet parser validate site.pp modules/labbase/manifests/init.pp
    ```

    ::: explain
    **What just happened:** `class labbase (...)` defines a class with one parameter and a default value. Inside are two **resources**: a `package` and a `file`. Every resource has a type, a title, and attributes. `require => Package['figlet']` sets the order. The `\` at the end of a line inside the double-quoted string joins it with the next line. `site.pp` declares (uses) the class and overrides the parameter. `puppet parser validate` checks syntax and prints nothing if all is well.
    :::

4. Preview with `--noop` (no operation, Puppet's dry run), then apply for real, then apply again.

    ```bash
    sudo puppet apply --modulepath=modules site.pp --noop
    sudo puppet apply --modulepath=modules site.pp
    cat /etc/puppet-demo.txt
    sudo puppet apply --modulepath=modules site.pp
    ```

    ```{.output}
    Notice: Compiled catalog for ubuntu-lab in environment production in 0.21 seconds
    Notice: /Stage[main]/Labbase/Package[figlet]/ensure: current_value 'purged', should
    be 'present' (noop)
    ...
    Notice: /Stage[main]/Labbase/Package[figlet]/ensure: created
    Notice: /Stage[main]/Labbase/File[/etc/puppet-demo.txt]/ensure: defined content as
    '{sha256}...'
    Notice: Applied catalog in 4.10 seconds
    Configured by the labbase class on ubuntu-lab (Ubuntu 24.04)
    Notice: Compiled catalog for ubuntu-lab in environment production in 0.20 seconds
    Notice: Applied catalog in 0.95 seconds
    ```

    **What just happened:** `puppet apply` compiled the catalog locally and enforced it, with no server and no certificates. This is agentless Puppet. #### Task 5: Build a CI/CD pipeline with shift left testing

You will build a tiny local pipeline and a Git hook that runs it before every commit, then read the GitHub Actions version.

1. Create a Git repository with one script that has a classic bug: unquoted variables. Git config here is set for this repository only (Lab 4.4 covers Git in depth).

    ```bash
    sudo apt install -y git shellcheck
    mkdir -p ~/labs/4.1/pipeline/scripts && cd ~/labs/4.1/pipeline
    git init -b main
    git config user.name "Student"
    git config user.email "student@lab.local"
    cat > scripts/cleanup-tmp.sh <<'EOF'
    #!/bin/bash
    # List files older than DAYS days in DIR (a cleanup report)
    days=$1
    target=$2
    find $target -type f -mtime +$days -print
    EOF
    chmod +x scripts/cleanup-tmp.sh
    ```

2. Write the pipeline script `ci.sh`. Each stage must pass before the next one runs.

    ```bash
    cat > ci.sh <<'EOF'
    #!/usr/bin/env bash
    # ci.sh - a tiny local CI pipeline: lint -> syntax -> secrets -> test
    set -euo pipefail

    echo "== Stage 1: lint (shellcheck) =="
    shellcheck scripts/*.sh

    echo "== Stage 2: syntax check (bash -n) =="
    for f in scripts/*.sh; do
        bash -n "$f"
    done

    echo "== Stage 3: secret scan =="
    if grep -rnE '(PASSWORD|SECRET|TOKEN)=[^$ ]+' scripts/; then
        echo "FAIL: possible hard-coded secret" >&2
        exit 1
    fi

    echo "== Stage 4: test =="
    tmpdir=$(mktemp -d)
    touch -d '10 days ago' "$tmpdir/old.log"
    touch "$tmpdir/new.log"
    result=$(scripts/cleanup-tmp.sh 7 "$tmpdir")
    rm -rf "$tmpdir"
    if [[ "$result" != *old.log ]] || [[ "$result" == *new.log* ]]; then
        echo "FAIL: expected only old.log, got: $result" >&2
        exit 1
    fi

    echo "All stages passed"
    EOF
    chmod +x ci.sh
    ```

    ::: explain
    **What just happened:** `set -euo pipefail` makes the script stop at the first failing command, so a failed stage fails the whole pipeline. Stage 1 lints with ShellCheck. Stage 2 asks Bash to parse each script without running it. Stage 3 is a **DevSecOps** check: a simple secret scanner that looks for things like `TOKEN=abc123`. Stage 4 is a real test: it makes one old file and one new file and checks that the script reports only the old one.
    :::

3. Install the pipeline as a Git **pre-commit hook**. Git runs `.git/hooks/pre-commit` before every commit and cancels the commit if the hook fails. This is **shift left testing**: problems are caught on your laptop, minutes after you write them, instead of in production.

    ```bash
    printf '#!/usr/bin/env bash\nexec ./ci.sh\n' > .git/hooks/pre-commit
    chmod +x .git/hooks/pre-commit
    git add .
    git commit -m "Add cleanup report script"
    ```

    :::

2. Write a configuration with two **providers**: `local` (manages files) and `kreuzwerker/docker` (talks to the Docker Engine **API** through `/var/run/docker.sock`). OpenTofu files use HCL and end in `.tf`. Create `~/labs/4.1/tofu/main.tf`:

    ```bash
    mkdir -p ~/labs/4.1/tofu && cd ~/labs/4.1/tofu
    cat > main.tf <<'EOF'
    terraform {
      required_providers {
        local = {
          source  = "hashicorp/local"
          version = "~> 2.5"
        }
        docker = {
          source  = "kreuzwerker/docker"
          version = "~> 3.0"
        }
      }
    }

    provider "docker" {
      host = "unix:///var/run/docker.sock"
    }

    variable "web_port" {
      type    = number
      default = 8081
    }

    resource "local_file" "notes" {
      filename = "${path.module}/deployed.txt"
      content  = "nginx is published on port ${var.web_port}\n"
    }

    resource "docker_image" "nginx" {
      name         = "nginx:alpine"
      keep_locally = true
    }

    resource "docker_container" "web" {
      name  = "tofu-web"
      image = docker_image.nginx.image_id
      ports {
        internal = 80
        external = var.web_port
      }
    }

    output "url" {
      value = "http://localhost:${var.web_port}"
    }
    EOF
    ```

    ::: explain
    **What just happened:** The `terraform {}` block (OpenTofu keeps this name for compatibility) lists required providers and version limits; `~> 3.0` means 3.x but not 4.0. Each `resource "TYPE" "NAME"` block describes one object. `docker_image.nginx.image_id` refers to an attribute of another resource, which also tells OpenTofu to create the image before the container. `variable` and `output` are inputs and printed results.

    ```{.output}
        docker swarm join --token SWMTKN-1-... 192.168.100.10:2377
    ```

    **What just happened:** A swarm is a cluster of Docker hosts called **nodes**. **Managers** keep the cluster state (using the Raft consensus algorithm) and schedule work; **workers** just run containers. The `join` command printed above would add another Docker host as a worker. `docker node ls` works only on a manager.

2. Create a **service** with three replicas. A service is the desired state ("3 copies of nginx on port 8080"); each copy is a **task**, and each task runs one container.

    ```bash
    docker service create --name web --replicas 3 \
      --publish published=8080,target=80 nginx:alpine
    docker service ls
    docker service ps web
    curl -s http://localhost:8080 | grep -i '<title>'
    ```

    ```{.output}
    ID         NAME   MODE         REPLICAS   IMAGE          PORTS
    pq1...     web    replicated   3/3        nginx:alpine   *:8080->80/tcp
    ID         NAME    IMAGE          NODE         DESIRED STATE   CURRENT STATE
    a1b...     web.1   nginx:alpine   ubuntu-lab   Running         Running 10 seconds ago
    c2d...     web.2   nginx:alpine   ubuntu-lab   Running         Running 10 seconds ago
    e3f...     web.3   nginx:alpine   ubuntu-lab   Running         Running 10 seconds ago
    <title>Welcome to nginx!</title>
    ```

    ::: explain
    **What just happened:** `docker service ps` lists the tasks. Port 8080 is published on the swarm's **routing mesh**: any node accepts the connection and forwards it to a healthy task, even one on another node.
    :::

3. **Scale** the service and watch Swarm heal itself.

    ```bash
    docker service scale web=5
    docker service ps web --filter desired-state=running
    docker rm -f $(docker ps -q --filter name=web.1)
    sleep 5
    docker service ps web
    ```

    ::: explain
    **What just happened:** `scale` changed the desired replica count; Swarm started two more tasks. When you killed a container by hand, Swarm saw that only 4 of 5 were running and started a replacement task. The old task shows as `Shutdown` / `Failed` in the history. This self-healing is the heart of orchestration. `$(...)` puts the container ID found by `docker ps -q` into the command.
    :::

4. Create an **overlay network** and attach a second service. Overlay networks span all nodes in the swarm, so services on different hosts can talk privately.

    ```bash
    docker network create --driver overlay labnet

    docker service update --network-add labnet web
    docker network ls --filter driver=overlay
    ```

    ```{.output}
    NETWORK ID     NAME      DRIVER    SCOPE
    x1y...         ingress   overlay   swarm
    z2w...         labnet    overlay   swarm
    ```

    ::: explain
    **What just happened:** `ingress` is the built-in overlay that powers the routing mesh. `labnet` is yours. `service update --network-add` performs a rolling update: Swarm replaces web's tasks one at a time so the service stays available.
    :::

5. Remove the services, the network, and the swarm.

5. Write a manifest that uses everything: a PersistentVolumeClaim for storage, and a Pod that receives the ConfigMap and Secret as environment **variables** and the ConfigMap as files in a **volume**. Create `~/labs/4.1/k8s/app.yaml`:

    ```bash
    mkdir -p ~/labs/4.1/k8s && cd ~/labs/4.1/k8s
    cat > app.yaml <<'EOF'
    apiVersion: v1
    kind: PersistentVolumeClaim
    metadata:
      name: app-data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: local-path
      resources:
        requests:
          storage: 100Mi
    ---
    apiVersion: v1
    kind: Pod
    metadata:
      name: app
      labels:
        app: demo
    spec:
      containers:
        - name: app
          image: busybox:1.36
          command: ["sh", "-c"]
          args:
            - echo "started at $(date) in $APP_MODE mode" >> /data/log.txt;
              echo "color=$APP_COLOR"; sleep 3600
          envFrom:
            - configMapRef:
                name: app-config
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: app-secret
                  key: DB_PASSWORD
          volumeMounts:
            - name: config
              mountPath: /etc/app
              readOnly: true
            - name: data
              mountPath: /data
      volumes:
        - name: config
          configMap:
            name: app-config
        - name: data
          persistentVolumeClaim:
            claimName: app-data
    EOF
    kubectl apply -f app.yaml
    kubectl get pvc,pod
    ```

    ```{.output}
    persistentvolumeclaim/app-data created
    pod/app created
    NAME                             STATUS   VOLUME        CAPACITY   ACCESS MODES ...
    persistentvolumeclaim/app-data   Bound    pvc-6c1e...   100Mi      RWO          ...
    NAME      READY   STATUS    RESTARTS   AGE
    pod/app   1/1     Running   0          12s
    ```

    ::: explain
    **What just happened:** `---` separates two objects in one file. The PVC asks for 100 MiB from k3s's built-in `local-path` storage class, which creates a directory on the node and binds it once a Pod uses the claim (if you see `Pending`, wait a few seconds). In the Pod, `envFrom` turns every ConfigMap key into an environment variable, `env.valueFrom.secretKeyRef` injects one Secret key, and `volumes` mounts the ConfigMap as files (one file per key) and the PVC at `/data`. `kubectl apply -f` is declarative: you can apply the same file again and again, which is exactly what GitOps tools do.
    :::

### Exam corner

- **IaC** = infrastructure described in version-controlled text files; declarative tools are **idempotent** (running twice changes nothing the second time).
- **Ansible**: agentless, push over SSH, needs only Python on targets; **inventory** lists hosts and groups; **playbooks** are YAML; **modules** do the work; **ad hoc** = `ansible <hosts> -m <module> -a <args>`; **facts** come from the `setup` module; **collections** install with `ansible-galaxy collection install`.
- Ansible handlers run once at the end of a play, only when notified. `--check` is a dry run, `--diff` shows changes.
- **Puppet**: agent pulls its catalog from the server every 30 minutes; trust uses TLS **certificates** signed with `puppetserver ca sign`; code is in manifests (`.pp`) with **classes** inside **modules**; facts come from `facter`; `puppet apply` runs without a server.
- **OpenTofu** (Terraform fork): **providers** call platform **APIs**; **resources** are managed objects; **state** (`terraform.tfstate`) maps code to real objects. Workflow: `init`, `plan`, `apply`, `destroy`.
- **Kickstart**: RHEL unattended install file; sample at `/root/anaconda-ks.cfg`; boot option `inst.ks=`; validate with `ksvalidator`.
- **cloud-init**: first-boot config; user-data starts with `#cloud-config`; logs in `/var/log/cloud-init.log`; check with `cloud-init status`; NoCloud seed volume label `cidata`.
- **CI/CD pipeline** stages: build, lint, test, security scan, deploy. **Shift left** = test earlier. **DevSecOps** = security inside the pipeline. **GitOps** = Git is the source of truth and an agent syncs the cluster to it.
- **Kubernetes**: Pod (smallest unit), Deployment (keeps N Pods, rolling updates), Service (stable IP/DNS, ClusterIP/NodePort/LoadBalancer), ConfigMap (settings), Secret (base64, not encrypted), volumes/PVCs (storage), env variables from ConfigMaps/Secrets.
- **Docker Swarm**: `docker swarm init`, nodes are managers or workers, a service has tasks (one container each), overlay networks span nodes, `docker service scale web=5`.
- **Compose**: `compose.yaml`, `docker compose up -d`, `ps`, `logs -f`, `down` (add `-v` to delete volumes); `podman compose` / `podman-compose` read the same file.
