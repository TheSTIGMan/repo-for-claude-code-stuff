Every program you run becomes a process, and much of a Linux administrator's day is spent watching, prioritizing, pausing, and stopping them. In this lab you will start deliberately misbehaving processes, inspect them with every tool on the exam, create each process state on purpose (including a zombie), change priorities, set resource limits, drive job control from the shell, send signals, and schedule work with `cron`, `at`, and `anacron`.

- Process ID: PPID, PID

- Scheduling: `anacron`, `at`, `crontab`

### How it works

**Programs and processes.** A *program* is a file on disk, like `/usr/bin/sleep`. A *process* is a running copy of a program: it has memory, open files, an owner, and a unique number called the **PID** (process ID). Run `sleep` three times at once and you get three processes with three PIDs.

**Parents and children.** New processes are created by existing ones. A process makes a copy of itself (*fork*), and the copy usually replaces its program with a new one (*exec*). The creator is the *parent*, and its PID is the child's **PPID** (parent process ID). When you type `ls` in Bash, Bash forks, the child execs `ls`, and Bash waits. Everything descends from PID 1, which is `systemd` on Ubuntu and Rocky, so the processes form a family tree.

```{.diagram}
 systemd (PID 1)
   +-- sshd (listener)
   |     +-- sshd (your session)
   |           +-- bash (PID 1532, PPID = sshd)
   |                 +-- yes   (PID 1601, PPID 1532)
   |                 +-- sleep (PID 1602, PPID 1532)
   +-- cron
   +-- systemd-journald
```

When a child exits, it leaves behind a tiny record holding its exit status until the parent collects it with the `wait()` system call. A child that has exited but has not been collected yet is a **zombie**. If the parent dies first, the orphaned children are adopted by PID 1 (or a nearby "subreaper"), which collects them.

**Process states.** At any instant a process is in one of a few states, shown in the `STAT` column of `ps`:

| Code | State | Meaning |
|---|---|---|
| `R` | Running | Running on a CPU, or ready and waiting for a turn |
| `S` | Sleeping | Waiting for something (a timer, keyboard input, network data); can be woken by a signal |
| `D` | Blocked (uninterruptible sleep) | Waiting inside the kernel, usually for disk or network storage I/O; ignores signals until the I/O finishes |
| `T` | Stopped | Paused by `Ctrl+Z` or a STOP signal; resumes with CONT |
| `Z` | Zombie | Finished, waiting for its parent to read the exit status |
| `I` | Idle | An idle kernel thread (you will see many) |

Extra characters may follow: `<` high priority, `N` low priority (niced), `s` session leader, `l` multi-threaded, `+` in the foreground of a terminal.

**Signals.** A *signal* is a small numbered message the kernel delivers to a process. A process can *catch* most signals and run its own handler (for example, reload its config), *ignore* them, or let the default action happen (usually exit). The exam's key three:

| Number | Name | Default action and typical use |
|---|---|---|
| 1 | `SIGHUP` (hang up) | Sent when a terminal closes. Many daemons treat it as "reload your configuration". |
| 9 | `SIGKILL` | Kills immediately. Cannot be caught, blocked, or ignored. No clean-up happens. Last resort. |
| 15 | `SIGTERM` | Polite request to exit. The default for `kill`. Lets a program save work and clean up. |

Others you will meet: 2 `SIGINT` (`Ctrl+C`), 19 `SIGSTOP` (pause, cannot be caught), 20 `SIGTSTP` (`Ctrl+Z`, can be caught), 18 `SIGCONT` (resume).

**Priority.** The scheduler shares CPUs between runnable processes. You influence it with the *nice value*, from `-20` (highest priority, "not nice to others") to `19` (lowest, "very nice"). The default is `0`. Any user can make their own processes *nicer* (raise the number), but only root can lower it below where it is.

**Jobs.** Your shell keeps its own list of the commands you started from it, called *jobs*, numbered `%1`, `%2`, and so on. One job at a time runs in the *foreground* (it owns the keyboard); others can run in the *background* or sit stopped. Job control lets you move them around.

**Limits.** The kernel enforces per-process *resource limits* (rlimits), such as the maximum number of open files or processes per user. Each limit has a *soft* value (currently enforced, and the user may raise it) and a *hard* value (the ceiling; only root can raise it). You view and change them in a shell with `ulimit`, and set them for logins in `/etc/security/limits.conf`.

**Scheduling.** `cron` runs commands repeatedly on a schedule (every night at 2:00). `at` runs a command once at a future time. `anacron` runs daily, weekly, or monthly jobs even on machines that are not always on: if the machine was off when a job was due, `anacron` runs it soon after the next boot.

#### Task 3: Look inside a process with `/proc`, `lsof`, and `strace`

1. Every process has a directory in `/proc` named after its PID. Explore your `sleep` process.

    ```bash
    SPID=$(pgrep -n sleep)
    echo $SPID
    ls /proc/$SPID
    grep -E '^(Name|State|Pid|PPid|Uid|Gid|VmRSS|Threads)' /proc/$SPID/status
    ```

    ```{.output}
    1603
    Name:	sleep
    State:	S (sleeping)
    Pid:	1603
    PPid:	1532
    Uid:	1000	1000	1000	1000
    Gid:	1000	1000	1000	1000
    VmRSS:	    1920 kB
    Threads:	1
    ```

    ::: explain
    **What just happened:** `pgrep -n` returns the newest matching PID, saved in the shell variable `SPID`. `/proc` is a virtual filesystem: nothing is stored on disk, and the kernel generates the contents when you read them. `status` is a readable summary. The four `Uid` numbers are the real, effective, saved, and filesystem UIDs. `ps`, `top`, and friends get all their information from here.
    :::

2. Read the command line, open files, environment, and working directory.

    ```bash
    tr '\0' ' ' < /proc/$SPID/cmdline; echo
    ls -l /proc/$SPID/fd
    ls -l /proc/$SPID/cwd /proc/$SPID/exe
    tr '\0' '\n' < /proc/$SPID/environ | head -5
    cat /proc/1/environ
    ```

    ```{.output}
    sleep 3000
    total 0
    lrwx------ 1 student student 64 Oct 10 11:12 0 -> /dev/pts/0
    lrwx------ 1 student student 64 Oct 10 11:12 1 -> /dev/pts/0
    lrwx------ 1 student student 64 Oct 10 11:12 2 -> /dev/pts/0
    lrwxrwxrwx 1 student student 0 Oct 10 11:12 /proc/1603/cwd -> /home/student/labs/2.3
    lrwxrwxrwx 1 student student 0 Oct 10 11:12 /proc/1603/exe -> /usr/bin/sleep
    SHELL=/bin/bash
    PWD=/home/student/labs/2.3
    LOGNAME=student
    ...
    cat: /proc/1/environ: Permission denied
    ```

    ::: explain
    **What just happened:** `cmdline` holds the arguments separated by NUL (zero) bytes, so `tr '\0' ' '` turns them into spaces. `fd/` contains one symbolic link per open file descriptor: 0, 1, and 2 point at your terminal. `cwd` is the current directory and `exe` the program file. `environ` holds the environment variables the process started with. You can read these only for your own processes; PID 1 belongs to root, so it is denied.
    :::

3. Compare with `lsof`, which reads the same data and formats it.

    ```bash
    lsof -p $SPID
    ```

    ::: explain
    **What just happened:** `lsof -p PID` lists everything the process has open: its working directory (`cwd`), program (`txt`), shared libraries (`mem`), and file descriptors. It is the same information as `/proc/PID/fd` and `/proc/PID/maps`, in one table.
    :::

#### Task 4: Create every process state on purpose

1. **Running (`R`) and sleeping (`S`):** you already have both.

    ```bash
    ps -o pid,stat,cmd -C yes,sleep
    ```

    ```{.output}
        PID STAT CMD
       1601 R    yes
       1602 R    yes
       1603 S    sleep 3000
    ```

2. **Stopped (`T`):** pause one `yes` with a signal, and watch CPU use drop.

    ```bash
    kill -STOP 1601
    ps -o pid,stat,%cpu,cmd -p 1601
    jobs
    kill -CONT 1601
    ps -o pid,stat,cmd -p 1601
    ```

    ```{.output}
        PID STAT %CPU CMD
       1601 T    82.1 yes
    [1]+  Stopped                 yes > /dev/null
    [2]   Running                 yes > /dev/null &
    [3]-  Running                 sleep 3000 &
        PID STAT CMD
       1601 R    yes
    ```

    ::: explain
    **What just happened:** Replace `1601` with your first `yes` PID. `kill -STOP` sends `SIGSTOP`, which pauses a process instantly and cannot be ignored. Its state becomes `T` and it uses no more CPU (the `%CPU` column is an average over its lifetime, so it falls slowly; `top` shows 0 immediately). `jobs` shows it as `Stopped`. `kill -CONT` resumes it. `Ctrl+Z` does the same thing to a foreground job, using `SIGTSTP`, as you will see in Task 7.
    :::

3. **Blocked (`D`):** a process waiting on disk I/O inside the kernel. It is usually too brief to see, but heavy direct reads from a disk often show it. Confirm your extra disk name with `lsblk` and substitute it (this only *reads* the disk, which is safe).

    ```bash
    lsblk -d -o NAME,SIZE,TYPE
    sudo -v
    sudo dd if=/dev/sdb of=/dev/null bs=1M count=4000 iflag=direct status=none &
    for i in 1 2 3 4 5; do ps -o pid,stat,cmd -C dd | tail -1; sleep 0.5; done
    ```

    ```{.output}
       1720 D    dd if=/dev/sdb of=/dev/null bs=1M count=4000 iflag=direct status=none
       1720 D    dd if=/dev/sdb of=/dev/null bs=1M count=4000 iflag=direct status=none
       1720 R    dd if=/dev/sdb of=/dev/null bs=1M count=4000 iflag=direct status=none
    ```

    ::: explain
    **What just happened:** `sudo -v` refreshes your cached `sudo` password first, so the background `sudo` does not get stuck waiting for a password it cannot read. `dd` reads the disk with `iflag=direct`, bypassing the cache, so it spends most of its time waiting for the (virtual) disk. While the kernel waits for the I/O, the process is in **uninterruptible sleep** (`D`, "blocked"): even `kill -9` waits until the I/O returns. A handful of `D` processes is normal; many `D` processes that never go away point to failing disks or a hung NFS server, and they raise the load average even though the CPU is idle. On a fast virtual disk you may see only `R` or `S`, and the `dd` may finish in seconds. That is fine; the point is what `D` means.
    :::

4. **Zombie (`Z`):** write a tiny Python program whose parent never collects its child. Create `~/labs/2.3/zombie.py` with this content (the heredoc writes it for you):

    ```bash
    cat > ~/labs/2.3/zombie.py <<'EOF'
    import os, time

    pid = os.fork()                  # make a copy of this process
    if pid == 0:                     # in the child
        print(f"child  {os.getpid()}: exiting now")
        os._exit(0)                  # child ends immediately
    print(f"parent {os.getpid()}: sleeping, never calling wait()")
    time.sleep(600)                  # parent ignores its dead child
    EOF
    python3 ~/labs/2.3/zombie.py &
    sleep 1
    ps -o pid,ppid,stat,cmd --ppid $(pgrep -f zombie.py)
    ```

    ```{.output}
    parent 1750: sleeping, never calling wait()
    child  1751: exiting now
        PID    PPID STAT CMD
       1751    1750 Z    [python3] <defunct>
    ```

    ::: explain
    **What just happened:** A *heredoc* (`<<'EOF' ... EOF`) feeds the lines up to `EOF` into `cat`, which writes them to the file; the quotes around `'EOF'` stop the shell from changing anything inside. `os.fork()` creates a child. The child exits at once, but the parent never calls `os.wait()`, so the kernel keeps the child's exit status: a **zombie** (`Z`, shown as `<defunct>`). `--ppid` lists children of a given PID, and `pgrep -f` matches against the full command line. A zombie uses no CPU or memory, only a process-table slot and its PID.
    :::

5. Try to kill the zombie, then fix it the right way.

    ```bash
    kill -9 1751
    ps -o pid,stat,cmd -p 1751
    kill $(pgrep -f zombie.py)
    sleep 1
    ps -o pid,stat,cmd -p 1751
    ```

    ::: explain
    **What just happened:** `kill -9` on a zombie does nothing; it is already dead. The fix is to deal with the **parent**: here you sent the parent `SIGTERM`. When the parent died, the zombie was adopted by PID 1 (`systemd`), which immediately collected it, so the last `ps` prints only the header. In production, zombies point to a bug in the parent program; restart or fix the parent. `top`'s `Tasks:` line and `ps aux | awk '$8 ~ /Z/'` are quick ways to find zombies.
    :::

#### Task 7: Drive job control: `&`, `jobs`, `fg`, `bg`, `Ctrl+C`, `Ctrl+Z`, `Ctrl+D`, `nohup`, and `exec`

1. Clean the slate, then start fresh jobs.

    ```bash

    sleep 2000 &

    ```

    ```{.output}
    [1]-  1801 Running                 sleep 1000 &
    [2]+  1802 Running                 sleep 2000 &
    ```

    ::: explain
    **What just happened:** `kill %1 %2 %3` sends `SIGTERM` to jobs 1 to 3 (the two `yes` and the old `sleep`); `%N` means "job N of this shell". `jobs` lists the shell's jobs; `-l` adds PIDs. The `+` marks the *current* job (the default for `fg` and `bg`), and `-` the previous one.

2. Bring a job to the foreground, stop it with `Ctrl+Z`, and resume it in the background.

    ```bash

    ```

    ```bash
    bg %1
    jobs
    ```

    **What just happened:** `fg %1` moved job 1 into the foreground, so it owns your keyboard. `Ctrl+Z` sends `SIGTSTP`, which stops the foreground job (state `T`) and returns your prompt. `bg %1` resumes the stopped job *in the background*, as if you had started it with `&`. 5. Keep a job alive after the terminal goes away with `nohup`. You will simulate a dropped connection by sending `SIGHUP` to a nested shell.

2. Write a script that catches signals the way a daemon does.

    ```bash
    cat > ~/labs/2.3/sigdemo.sh <<'EOF'
    #!/bin/bash
    trap 'echo "$(date +%T) HUP received: reloading configuration"' HUP
    trap 'echo "$(date +%T) TERM received: saving work and exiting"; exit 0' TERM
    echo "$(date +%T) started with PID $$"
    while true; do sleep 1; done
    EOF
    chmod +x ~/labs/2.3/sigdemo.sh
    ~/labs/2.3/sigdemo.sh > ~/labs/2.3/sig.log 2>&1 &
    ```

    ::: explain
    **What just happened:** `trap 'COMMANDS' SIGNAL` tells Bash to run the commands when that signal arrives instead of taking the default action. HUP prints a "reloading" message and keeps going, like a real daemon rereading its config file. TERM prints a message and exits cleanly. `chmod +x` makes the script executable, and the output goes to `sig.log`. Bash runs a trap after the current command (`sleep 1`) finishes, so responses take up to a second.
    :::

    **What just happened:** `at TIME` reads commands from standard input until `Ctrl+D` (shown as `<EOT>`) and runs them once at that time, using `/bin/sh`. The `atd` daemon executes them. Time formats include `now + 2 minutes`, `23:30`, `noon`, `teatime` (16:00), `tomorrow`, and `10:00 2026-12-25`. `atq` lists pending jobs (job number, time, queue letter, owner); `at -c N` prints the full script of a job, including the saved environment; `atrm N` deletes a job. After two minutes, `cat ~/labs/2.3/at.log` shows that job 1 ran and `atq` no longer lists it. Access is controlled by `/etc/at.allow` and `/etc/at.deny` (and `/etc/cron.allow` and `/etc/cron.deny` for cron).
    :::

5. Explore `anacron` and add a test job.

    ```bash
    cat /etc/anacrontab
    ls -l /var/spool/anacron/
    ```

    ```{.output}
    # /etc/anacrontab: configuration file for anacron

    # See anacron(8) and anacrontab(5) for details.

    SHELL=/bin/sh
    HOME=/root
    LOGNAME=root

    # These replace cron's entries
    1	5	cron.daily	run-parts --report /etc/cron.daily
    7	10	cron.weekly	run-parts --report /etc/cron.weekly
    @monthly	15	cron.monthly	run-parts --report /etc/cron.monthly
    ```

    Add a lab job and run it immediately:

    ```bash
    echo '1  2  lab23.daily  echo "anacron ran $(date)" >> /var/log/lab23-anacron.log' | \
      sudo tee -a /etc/anacrontab
    sudo anacron -T && echo "syntax OK"
    sudo anacron -f -n -d lab23.daily
    cat /var/log/lab23-anacron.log
    sudo cat /var/spool/anacron/lab23.daily
    ```

    ```{.output}
    syntax OK
    Anacron 2.3 started on 2026-10-10
    Will run job `lab23.daily'
    Jobs will be executed sequentially
    Job `lab23.daily' started
    Job `lab23.daily' terminated
    Normal exit (1 job run)
    anacron ran Sat Oct 10 12:01:14 UTC 2026
    20261010
    ```

    ::: explain
    **What just happened:** Each `/etc/anacrontab` line has four fields: **period** in days (or `@monthly`), **delay** in minutes to wait before starting (so jobs do not all start at boot together), a unique **job identifier**, and the **command**. `anacron` records the last run date of each job in `/var/spool/anacron/<identifier>`; if a job's period has passed since that date (for example, because the laptop was off at 06:25), it runs the job. `-T` tests the file's syntax, `-f` forces jobs regardless of their timestamps, `-n` skips the delay, and `-d` stays in the foreground and prints messages. Unlike cron, anacron's smallest unit is one day, it only runs as root, and it does not care about the exact time of day.
    :::

### Exam corner

- `ps aux` (BSD style) and `ps -ef` (UNIX style, shows PPID); `ps -eo pid,ppid,stat,ni,cmd --sort=-%cpu` for custom columns. `pstree -p` shows the parent-child tree. `pgrep -a` finds PIDs by name.
- `top` keys: `P` CPU, `M` memory, `k` kill, `r` renice, `1` per CPU, `q` quit. `htop` adds tree view (`F5`), search, and F-key actions. `atop` records history in `/var/log/atop`. `mpstat -P ALL` (per CPU) and `pidstat` (per process) come from `sysstat`.
- `/proc/<PID>/` holds `status`, `cmdline`, `environ`, `fd/`, `cwd`, and `exe`. `lsof -p PID` lists a process's open files. `strace` shows system calls; `strace -p PID` attaches (needs root on Ubuntu).
- States: `R` running, `S` sleeping (interruptible), `D` blocked (uninterruptible I/O wait), `T` stopped, `Z` zombie. Zombies cannot be killed; kill or fix the parent so PID 1 reaps them.
- Nice values run from -20 (highest priority) to 19 (lowest); default 0. `nice -n 10 cmd` starts, `renice -n 5 -p PID` changes, `renice -u user` targets a user. Only root can lower a nice value.
- `ulimit -a` shows limits; `-n` open files, `-u` processes, `-f` file size; `-S` soft, `-H` hard. Users may raise soft up to hard; only root raises hard. Permanent limits: `/etc/security/limits.conf` and `limits.d/` (`domain type item value`), applied by `pam_limits` at new logins.
- Job control: `cmd &` background; `jobs`; `fg %N`; `bg %N`; `Ctrl+Z` stop (SIGTSTP); `Ctrl+C` interrupt (SIGINT); `Ctrl+D` end of input (EOF, not a signal). `nohup cmd &` ignores SIGHUP and writes to `nohup.out`. `exec cmd` replaces the shell, keeping its PID.
- Signals: 1 `SIGHUP` (hang up, often "reload config"), 9 `SIGKILL` (cannot be caught), 15 `SIGTERM` (default for `kill`, graceful). `kill -l` lists them. `killall name` (exact name) and `pkill pattern` (`-u user`, `-f` full command line) signal by name.
- Cron fields: minute, hour, day of month, month, day of week. `crontab -e`, `-l`, `-r`. `/etc/crontab` and `/etc/cron.d/*` include a user field. `at TIME` runs once (`atq`, `atrm`, `at -c`). `anacron` runs daily/weekly/monthly jobs missed while the system was off (`/etc/anacrontab`: period, delay, identifier, command).

**Review questions**

1. A process shows `Z` in the `STAT` column and `kill -9` has no effect on it. What should the administrator do?
    A. Reboot immediately.
    B. Send `SIGKILL` again with `killall -9`.
    C. Identify its parent with `ps -o ppid` and restart or kill the parent.
    D. Run `renice -n 19` on it.
2. Which crontab entry runs `/usr/local/bin/backup.sh` at 23:45 every Sunday?
    A. `45 23 * * 0 /usr/local/bin/backup.sh`
    B. `23 45 * * 0 /usr/local/bin/backup.sh`
    C. `45 23 0 * * /usr/local/bin/backup.sh`
    D. `* 23 * * sun /usr/local/bin/backup.sh`
3. A user started a long compile in the foreground and wants it to keep running in the background so they can use the shell. Which key and command sequence does this?
4. Which signal does `kill 4321` send, and why is it preferred over `kill -9 4321`?
5. A web application logs "Too many open files." Which two things would you check or change?
6. A laptop is often powered off at night, so its daily maintenance jobs scheduled at 06:25 never run. Which tool solves this?
    A. `at`
    B. `anacron`
    C. `nohup`
    D. `renice`

::: answers
1. **C.** A zombie has already exited and cannot be killed; its parent has not collected its exit status, so fix, restart, or kill the parent and PID 1 will reap the zombie.
2. **A.** The fields are minute (45), hour (23), day of month (`*`), month (`*`), and day of week (`0` = Sunday).
3. Press `Ctrl+Z` to stop the foreground job, then run `bg` (or `bg %N`) to resume it in the background.
4. It sends signal 15, `SIGTERM`, which the program can catch to save data and exit cleanly; `SIGKILL` (9) cannot be caught, so no clean-up happens.
5. Check the current limit with `ulimit -n` (or `/proc/<PID>/limits`) and count open files with `lsof -p PID`, then raise `nofile` in `/etc/security/limits.conf` (or `LimitNOFILE=` in the systemd unit for a service).
6. **B.** `anacron` runs daily, weekly, and monthly jobs that were missed while the system was off, shortly after it starts again.
:::
