## Lab 2.2: Manage Local Accounts {#lab-2-2}

::: labinfo
**Objective:** 2.2 Given a scenario, perform local account management in a Linux environment.\
**Domain:** 2.0 Services and User Management (20% of the exam)\
**Time:** about 100 minutes\
**VM:** ubuntu-lab (Task 9 also uses rocky-lab)\
**Snapshot first:** Recommended. This lab edits `/etc/skel`, `/etc/profile.d`, and the account databases. The clean-up undoes everything, but a snapshot is a cheap safety net.

A small team is joining your company: two developers, an operations engineer, and a service that needs its own account. In this lab you onboard them, look inside the files where Linux keeps account data, lock and expire accounts, enforce password aging, see who is logged in, and finally offboard everyone cleanly. Account management is one of the most common real admin tasks, and the exam tests both the commands and the file formats behind them.

### What you'll practice

- Add: `adduser`, `groupadd`, `useradd`
- Delete: `deluser`, `groupdel`, `userdel`
- Modify: `chsh`, `groupmod`, `passwd`, `usermod`
- Lock: `chage`, `passwd`, `usermod`
- Expiration: configuration files (`/etc/login.defs`, `/etc/default/useradd`), `chage`
- List: `getent passwd`, `groups`, `id`, `last`, `lastlog`, `w`, `who`, `whoami`
- Templates: `/etc/profile`, `/etc/skel`
- Account files: `/etc/group`, `/etc/passwd`, `/etc/shadow`
- Attributes: UID, GID, EUID, EGID
- User vs system vs service accounts: UID range

### How it works

**Users are numbers.** The kernel does not know names like `alice`. It knows a **UID** (user ID), a number. Every process runs with a UID and every file is owned by a UID. Groups work the same way with a **GID** (group ID). Names exist only for humans; the system translates them using the account databases.

**The account files.** Local accounts live in three plain-text files, one line per entry, fields separated by colons:

- **`/etc/passwd`** (readable by everyone) holds the basic account info: name, a placeholder `x` for the password, UID, primary GID, a comment (the *GECOS* field, usually the full name), home directory, and login shell. Despite its name, it no longer contains passwords.
- **`/etc/shadow`** (readable only by root and the `shadow` group) holds the password *hash* and the password aging data. A *hash* is a one-way scramble of the password: the system can check a typed password by hashing it the same way, but cannot turn the hash back into the password.
- **`/etc/group`** holds groups: name, `x`, GID, and a comma-separated list of supplementary members. (`/etc/gshadow` holds group passwords, rarely used.)

```{.diagram}
 /etc/passwd   alice:x:1001:1001:Alice Ng,Dev:/home/alice:/bin/bash
                 |   |   |    |       |          |          |
               name  |  UID  GID   comment     home       shell
                     +-- "password is in /etc/shadow"

 /etc/shadow   alice:$y$j9T$...:20371:0:99999:7:::
                 |        |       |   |   |   | ||
               name     hash  lastchg min max warn inactive expire

 /etc/group    developers:x:3001:alice,bob
                   |      |  |      |
                 name     | GID  supplementary members
```

**Primary and supplementary groups.** Each user has exactly one *primary group* (the GID in `/etc/passwd`); new files get this group. A user can also belong to many *supplementary groups*, listed in `/etc/group`. Ubuntu and Rocky both create a *user private group* for each new user: a group with the same name as the user, used as the primary group.

**Real versus effective IDs.** A running process carries a **real UID** (who started it) and an **effective UID (EUID)** (whose permissions it uses right now). Usually they are the same. They differ when you run `sudo` (EUID becomes 0, root) or a *setuid* program such as `passwd`: the file is owned by root and has the setuid bit, so it runs with EUID 0 even when you start it. That is how an ordinary user can update `/etc/shadow`, but only through `passwd`'s rules. Groups have the same pair: real GID and **effective GID (EGID)**, which decides the group ownership of new files.

**Kinds of accounts and UID ranges.** The ranges come from `/etc/login.defs`:

| Account type | UID range (Ubuntu 24.04 and Rocky 9) | Examples |
|---|---|---|
| root | 0 | `root` |
| System accounts | 1 to 999 | `daemon`, `bin`, `systemd-network`, `sshd` |
| Regular (human) users | 1000 to 60000 | `student`, `alice` |
| Special | 65534 | `nobody` (owns nothing, used for least privilege) |

A **system account** is any account in the low range, created by the OS or packages. A **service account** is a system account created so one service (a web server, a database, your own app) runs under its own identity instead of root. Service accounts usually have no password, no usable shell (`/usr/sbin/nologin`), and a home directory under `/var/lib` or none at all.

**Templates and defaults.** When `useradd -m` creates a home directory, it copies everything in **`/etc/skel`** (skeleton) into it, so every new user starts with the same `.bashrc`, `.profile`, and any files you add. **`/etc/profile`** (plus the scripts in `/etc/profile.d/`) runs for *every* user at each login shell, so it is the place for system-wide environment settings and login messages. Defaults for new accounts come from **`/etc/login.defs`** (UID ranges, password aging defaults, hash method, whether to create home directories) and **`/etc/default/useradd`** (default shell, skeleton directory, account inactivity and expiration defaults).

**Ubuntu's two tools.** `useradd`, `usermod`, `userdel`, `groupadd`, `groupmod`, and `groupdel` are the low-level tools found on every distribution. They do exactly what the options say and nothing more. Ubuntu (like Debian) also ships **`adduser`** and **`deluser`**, friendlier Perl scripts that ask questions, create the home directory, set a password, and follow the policy in `/etc/adduser.conf`. On Rocky, `adduser` is simply a link to `useradd`.

#### Task 1: Explore the account files and UID ranges

1. Make a lab directory and look at your own identity.

    ```bash
    mkdir -p ~/labs/2.2 && cd ~/labs/2.2
    whoami
    id
    groups
    ```

    ```{.output}
    student
    uid=1000(student) gid=1000(student) groups=1000(student),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),101(lxd)
    student adm cdrom sudo dip plugdev lxd
    ```

    ::: explain
    **What just happened:** `whoami` prints the user name of your *effective* UID. `id` prints your UID, primary GID, and all groups, with numbers and names. `groups` prints only the group names. Membership in `sudo` is what lets `student` run admin commands on Ubuntu. Your list of groups may be slightly different.

2. Look at the first lines of `/etc/passwd` and at your own entry.

    ```bash
    head -5 /etc/passwd
    grep '^student:' /etc/passwd
    getent passwd student
    getent passwd 0
    ```

    ```{.output}
    root:x:0:0:root:/root:/bin/bash
    daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
    bin:x:2:2:bin:/bin:/usr/sbin/nologin
    sys:x:3:3:sys:/dev:/usr/sbin/nologin
    sync:x:4:65534:sync:/bin:/bin/sync
    student:x:1000:1000:student:/home/student:/bin/bash
    student:x:1000:1000:student:/home/student:/bin/bash
    root:x:0:0:root:/root:/bin/bash
    ```

    ::: explain
    **What just happened:** Each line has seven colon-separated fields: name, password placeholder (`x`), UID, GID, comment, home, and shell. `getent passwd NAME` ("get entries") asks the system's name service for the account instead of reading the file directly. The result is the same here, but `getent` also finds accounts from LDAP or Active Directory if the system is joined to a directory, so it is the correct way to look up users in scripts. It accepts a UID too (`getent passwd 0`).
    :::

3. Separate system accounts from human users with `awk`.

    ```bash
    awk -F: '$3 < 1000 {print $3, $1, $7}' /etc/passwd | head -15
    awk -F: '$3 >= 1000 && $3 < 60000 {print $3, $1, $7}' /etc/passwd
    grep -E '^(UID_MIN|UID_MAX|SYS_UID_MIN|SYS_UID_MAX|GID_MIN|GID_MAX)' /etc/login.defs
    ```

    ```{.output}
    UID_MIN			 1000
    UID_MAX			60000
    GID_MIN			 1000
    GID_MAX			60000
    ```

    ::: explain
    **What just happened:** `awk -F:` splits each line on colons, so `$1` is the name, `$3` the UID, and `$7` the shell. The first command lists accounts below 1000: system accounts, nearly all with the shell `/usr/sbin/nologin`, which refuses interactive logins. The second lists regular users (probably only `student`). `/etc/login.defs` defines the regular-user range. On Ubuntu the `SYS_UID_MIN`/`SYS_UID_MAX` lines are commented out, so the built-in defaults apply (system accounts get UIDs below 1000, allocated from 999 downward).
    :::

4. Look at groups and at the protected shadow file.

    ```bash
    grep -E '^(sudo|adm|student):' /etc/group
    getent group sudo
    ls -l /etc/passwd /etc/shadow /etc/group /etc/gshadow
    cat /etc/shadow
    sudo grep '^student:' /etc/shadow
    ```

    ```{.output}
    adm:x:4:syslog,student
    sudo:x:27:student
    student:x:1000:
    -rw-r--r-- 1 root root   1854 Oct 10 09:00 /etc/group
    -rw-r----- 1 root shadow  774 Oct 10 09:00 /etc/gshadow
    -rw-r--r-- 1 root root   1965 Oct 10 09:00 /etc/passwd
    -rw-r----- 1 root shadow 1143 Oct 10 09:00 /etc/shadow
    cat: /etc/shadow: Permission denied
    student:$y$j9T$Hk3x...long hash...:20370:0:99999:7:::
    ```

    ::: explain
    **What just happened:** In `/etc/group` the last field lists *supplementary* members. The `student` group has an empty member list because `student` is in it as a *primary* group (from `/etc/passwd`), which is never repeated here. `/etc/passwd` and `/etc/group` are world-readable (`rw-r--r--`) because many programs need to map numbers to names. `/etc/shadow` is `rw-r-----` owned by `root:shadow`, so `cat` as a normal user fails and you need `sudo`. You will dissect the shadow fields in Task 4.

#### Task 2: Prepare the templates: `/etc/skel`, `/etc/profile`, and defaults

Before anyone is created, set up what every new user should receive.

1. Look at the skeleton directory.

    ```bash
    ls -la /etc/skel
    ```

    ```{.output}
    total 20
    drwxr-xr-x   2 root root 4096 Apr 23  2024 .
    drwxr-xr-x 108 root root 4096 Oct 10 09:00 ..
    -rw-r--r--   1 root root  220 Mar 31  2024 .bash_logout
    -rw-r--r--   1 root root 3771 Mar 31  2024 .bashrc
    -rw-r--r--   1 root root  807 Mar 31  2024 .profile
    ```

    ::: explain
    **What just happened:** These three hidden files are copied into every new home directory. `.bashrc` runs for interactive Bash shells, `.profile` for login shells, and `.bash_logout` when a login shell exits.
    :::

2. Add a welcome file and a `bin` directory to the skeleton. This step uses a *heredoc*.

    ```bash
    cat <<'EOF' | sudo tee /etc/skel/WELCOME.txt
    Welcome to the company Linux server!
    - Read the acceptable use policy in /srv/policy (coming soon).
    - Put your own scripts in ~/bin.
    - Ask the ops team for help: ops@example.com
    EOF
    sudo mkdir -p /etc/skel/bin
    ls -la /etc/skel
    ```

    ::: explain
    **What just happened:** A *heredoc* (`<<'EOF' ... EOF`) feeds the lines between the markers into a command as if you had typed them. Quoting `'EOF'` stops the shell from expanding `$` variables inside. Because you cannot redirect into a root-owned file with `sudo echo ... >` (the redirection runs as you, not root), the text is piped into `sudo tee FILE`, which writes it as root and also prints it to the screen. Ubuntu's default `.profile` adds `~/bin` to `PATH` if the directory exists, so new users get a working personal script directory.
    :::

3. Add a system-wide login message through `/etc/profile`. Look at how it loads extra scripts first.

    ```bash
    grep -n -A6 'profile.d' /etc/profile
    cat <<'EOF' | sudo tee /etc/profile.d/lab-motd.sh
    # Lab 2.2: printed for every login shell
    echo "[profile] Hello $USER, you are logged in to $(hostname) at $(date +%H:%M)."
    EOF
    ```

    ```{.output}
    27:if [ -d /etc/profile.d ]; then
    28-  for i in /etc/profile.d/*.sh; do
    29-    if [ -r $i ]; then
    30-      . $i
    31-    fi
    32-  done
    33-  unset i
    ```

    ::: explain
    **What just happened:** `/etc/profile` runs for every user's *login shell* (an SSH login, a console login, or `su -`). It loops over every readable `*.sh` file in `/etc/profile.d/` and *sources* it (the `.` command runs it inside the current shell). Dropping a small file into `/etc/profile.d/` is better than editing `/etc/profile` itself, because package updates may replace `/etc/profile`. Here the quotes around `'EOF'` keep `$USER` unexpanded in the file, so it is evaluated at each login. Your line numbers may differ.
    :::

4. Check the defaults that `useradd` will apply.

    ```bash
    useradd -D
    cat /etc/default/useradd | grep -v '^#' | grep -v '^$'
    grep -E '^(PASS_MAX_DAYS|PASS_MIN_DAYS|PASS_WARN_AGE)' /etc/login.defs
    grep -E '^(ENCRYPT_METHOD|USERGROUPS_ENAB|CREATE_HOME|HOME_MODE)' /etc/login.defs
    ```

    ```{.output}
    GROUP=100
    HOME=/home
    INACTIVE=-1
    EXPIRE=
    SHELL=/bin/sh
    SKEL=/etc/skel
    CREATE_MAIL_SPOOL=no
    LOG_INIT=yes
    ...
    PASS_MAX_DAYS	99999
    PASS_MIN_DAYS	0
    PASS_WARN_AGE	7
    USERGROUPS_ENAB yes
    ENCRYPT_METHOD YESCRYPT
    HOME_MODE	0750
    ```

    ::: explain
    **What just happened:** `useradd -D` prints the defaults stored in `/etc/default/useradd` (merged with built-in values). Note two Ubuntu surprises: the default shell is `/bin/sh` (not Bash), and there is no `CREATE_HOME yes` line in `login.defs`, so **plain `useradd` does not create a home directory** unless you add `-m`. `INACTIVE=-1` and an empty `EXPIRE` mean accounts never become inactive or expire by default. From `login.defs`: passwords effectively never expire (`99999` days), can be changed any time (`0`), users are warned 7 days before expiry, each user gets a private group, new hashes use **yescrypt**, and home directories are created with mode `0750`. These aging values apply only to accounts created *after* you change them. You can change a `useradd` default with, for example, `sudo useradd -D -s /bin/bash`, but leave it as is for this lab.
    :::

**Checkpoint:** `ls -a /etc/skel` shows `WELCOME.txt` and `bin`, and `cat /etc/profile.d/lab-motd.sh` shows the `echo` line with `$USER` (not your name).

#### Task 4: Dissect `/etc/shadow` and password hashes

1. Display the shadow entries for the new users.

    ```bash
    sudo grep -E '^(alice|bob|carol|student):' /etc/shadow
    ```

    ```{.output}
    student:$y$j9T$Hk3x...:20370:0:99999:7:::
    alice:$y$j9T$3QeV2b0i8lF5d1pB/9W.r.$Kx1v...:20371:0:99999:7:::
    bob:$y$j9T$aZ0...:20371:0:99999:7:::
    carol:$y$j9T$p9L...:20371:0:99999:7:::
    ```

2. Read each field. Using Alice's line:

    | # | Field | Alice's value | Meaning |
    |---|---|---|---|
    | 1 | Login name | `alice` | Matches `/etc/passwd` |
    | 2 | Password hash | `$y$j9T$...` | `$y$` = yescrypt; `!` or `*` = no password login |
    | 3 | Last change | `20371` | Days since 1970-01-01 when the password was last changed |
    | 4 | Minimum age | `0` | Days before the user may change it again |
    | 5 | Maximum age | `99999` | Days until it must be changed |
    | 6 | Warning | `7` | Days of warning before it expires |
    | 7 | Inactive | (empty) | Days after expiry before the account is disabled |
    | 8 | Expire | (empty) | Days since 1970-01-01 when the *account* expires |
    | 9 | Reserved | (empty) | Unused |

    Convert the day number into a date:

    ```bash
    date -d "1970-01-01 +20371 days" +%F
    echo $(( $(date +%s) / 86400 ))
    ```

    ::: explain
    **What just happened:** Shadow dates are stored as a count of days since the *epoch* (1970-01-01). `date -d` converts that number into a calendar date. The second line divides the current time in seconds (`date +%s`) by 86,400 seconds per day to get today's day number. Use your own value from the shadow file.
    :::

3. Understand the hash format.

    ```{.diagram}
     $y$  j9T  $  3QeV2b0i8lF5d1pB/9W.r.  $  Kx1v...(43 chars)
      |    |           |                       |
     ID  params       salt                   hash

     $1$ MD5 (obsolete)  $5$ SHA-256  $6$ SHA-512 (Rocky 9)  $y$ yescrypt (Ubuntu 24.04)
    ```

    Try it yourself by generating a hash with the same password but a new random salt:

    ```bash
    sudo apt install -y whois
    mkpasswd -m yescrypt 'Welcome2Lab!'
    mkpasswd -m sha-512 'Welcome2Lab!'
    ```

    ::: explain
    **What just happened:** The first part between `$` signs names the algorithm. Ubuntu 24.04 uses **yescrypt** (`$y$`), set by `ENCRYPT_METHOD YESCRYPT` in `login.defs`; Rocky 9 uses SHA-512 (`$6$`). The *salt* is a random string mixed into the password before hashing, so two users with the same password (like Alice and Bob) still have completely different hashes. `mkpasswd` (in the `whois` package on Ubuntu) creates a hash; run it twice and the output changes each time because of the new salt. In the password field, a leading `!` means "locked", and `*` or `!` alone means "no password login possible".
    :::

::: checkpoint
**Checkpoint:** Alice and Bob have the same password but different hash strings in `/etc/shadow`, and both start with `$y$`.
:::

#### Task 5: Modify accounts with `usermod`, `chsh`, `groupmod`, and `passwd`

1. Update Bob's comment and move him into ops as well. First make the classic mistake.


#### Task 6: Lock, unlock, expire, and age passwords

Scenario: Bob is on leave, Carol is a contractor whose contract ends soon, and security wants passwords changed every 90 days.

1. Lock Bob's password with `passwd -l`, check, and test it.

    ```bash
    sudo passwd -l bob
    sudo passwd -S bob
    sudo grep '^bob:' /etc/shadow | cut -c1-20
    su - bob
    ```

    ```{.output}
    bob L 2026-10-10 0 99999 7 -1
    bob:!$y$j9T$aZ0...
    Password:
    su: Authentication failure
    ```

    ::: explain
    **What just happened:** `passwd -l` (lock) puts a `!` in front of the hash. No typed password can ever match a hash that starts with `!`, so password logins fail even with the correct password (type `Welcome2Lab!` at the `su` prompt to see it). `passwd -S` now shows `L`. The original hash is kept, so unlocking restores the old password.
    :::

2. Unlock with `passwd -u`, then lock and unlock again with `usermod`.

    ```bash
    sudo passwd -u bob
    sudo usermod -L bob
    sudo passwd -S bob
    sudo usermod -U bob
    sudo passwd -S bob
    ```

    ::: explain
    **What just happened:** `passwd -u` and `usermod -U` remove the `!`; `usermod -L` adds it. They are two interfaces to the same change. Bob shows `P` again at the end.
    :::

::: warning
Locking the password does **not** stop every kind of login. A user with an SSH key in `~/.ssh/authorized_keys` can still log in, because key logins never check the password hash. To fully disable an account, also expire it (next step) or set its shell to `/usr/sbin/nologin`.
:::

3. Expire Bob's account completely with `chage -E 0`.


    ```{.output}
    Password:
    Your account has expired; please contact your system administrator.
    su: Authentication failure
    ```

    ::: explain
    **What just happened:** `chage -E` sets the account *expiration* date (field 8 of shadow). `0` means day 0, 1970-01-01, which is in the past, so the account is expired immediately. This blocks all logins that go through PAM account checks, including SSH key logins. `usermod -e 1970-01-02` (or any past date) does the same thing.
    :::

### Exam corner

- `/etc/passwd`: `name:x:UID:GID:GECOS:home:shell` (world-readable). `/etc/shadow`: `name:hash:lastchg:min:max:warn:inactive:expire:reserved` (root/shadow only). `/etc/group`: `name:x:GID:members`.
- Hash prefixes: `$1$` MD5, `$5$` SHA-256, `$6$` SHA-512 (Rocky 9), `$y$` yescrypt (Ubuntu 24.04). A leading `!` means locked; `*` or `!` alone means no password.
- UID 0 = root; 1 to 999 = system and service accounts (`useradd -r`); 1000 and up = regular users (`UID_MIN`/`UID_MAX` in `/etc/login.defs`); 65534 = `nobody`.
- `useradd -m -s /bin/bash -c "comment" -G grp1,grp2 user`. Ubuntu's plain `useradd` creates no home and uses `/bin/sh`; Rocky creates the home and uses `/bin/bash`. `adduser` is interactive on Ubuntu and a link to `useradd` on Rocky.
- `usermod -aG group user` appends; `-G` alone replaces the supplementary list. `usermod -l` renames, `-s` shell, `-d -m` move home, `-L`/`-U` lock/unlock, `-e` expire date.
- `passwd user` sets a password; `-l`/`-u` lock/unlock; `-S` status; `-e` force change. `chage -l` lists; `-M` max, `-m` min, `-W` warn, `-I` inactive, `-E` account expiry (`0` = expired now, `-1` = never), `-d 0` = force change at next login.
- Defaults: `/etc/login.defs` (UID ranges, `PASS_MAX_DAYS`, `PASS_MIN_DAYS`, `PASS_WARN_AGE`, `ENCRYPT_METHOD`, `CREATE_HOME`) and `/etc/default/useradd` (shell, skel, `INACTIVE`, `EXPIRE`; view with `useradd -D`).
- `/etc/skel` is copied into new home directories only at creation. `/etc/profile` and `/etc/profile.d/*.sh` run for every login shell.
- `userdel -r` deletes the user, home, and mail spool; `deluser --remove-home` on Ubuntu. `groupdel` fails on a user's primary group. `groupmod -n` renames, `-g` changes GID.
- Listing: `whoami` (effective user), `id`, `groups`, `getent passwd`, `who` and `w` (current logins, from utmp), `last` (history, wtmp), `lastb` (failed logins), `lastlog` (last login per account).
- EUID/EGID decide permissions; they differ from the real UID/GID under `sudo` or setuid/setgid programs such as `passwd` (setuid root) and `chage` (setgid shadow).
- Service accounts: system UID, `nologin` shell, no password, home in `/var/lib` or none. `chsh` changes a shell; valid shells are in `/etc/shells`.

**Review questions**

1. A developer was added with `sudo usermod -G docker dev1` and now cannot use the `developers` shared folder. What went wrong, and what command should have been used?
2. Which field of `/etc/shadow` controls when the entire account stops working, regardless of the password?
    A. Field 3 (last change)
    B. Field 5 (maximum age)
    C. Field 7 (inactive)
    D. Field 8 (expire)
3. A new hire must set their own password the first time they log in. Which command enforces this?
    A. `chage -E 0 newhire`
    B. `chage -d 0 newhire`
    C. `passwd -l newhire`
    D. `usermod -L newhire`
4. On Ubuntu 24.04, `sudo useradd jdoe` succeeded, but `jdoe` has no home directory. Why, and how do you avoid it?
5. Which UID range would you expect for an account created with `useradd -r -s /usr/sbin/nologin metricsd`?
    A. 0
    B. 1 to 999
    C. 1000 to 60000
    D. 65534
6. While `passwd` is running for user `student`, `ps -o ruid,euid -C passwd` shows `1000 0`. Why?
    A. The user is a member of the `sudo` group.
    B. `passwd` is a setuid-root program, so its effective UID is root while its real UID is the caller's.
    C. `passwd` always runs through `sudo`.
    D. The kernel gives every process EUID 0 while it reads a password.

::: answers
1. `-G` without `-a` replaced all of the user's supplementary groups with only `docker`; the correct command is `sudo usermod -aG docker dev1` (then add `developers` back with `usermod -aG developers dev1`).
2. **D.** Field 8 is the account expiration date (set with `chage -E` or `usermod -e`); after it passes, all logins are refused.
3. **B.** `chage -d 0` sets the last-change date to day 0, so the password is already expired and must be changed at the next login.
4. Ubuntu's `login.defs` does not set `CREATE_HOME yes`, so `useradd` only creates a home with `-m`; use `useradd -m` (or `adduser`, which always creates the home).
5. **B.** `-r` creates a system account with a UID from the system range below 1000, which is typical for service accounts.
6. **B.** The setuid bit on `/usr/bin/passwd` makes it run with the owner's (root's) effective UID, while the real UID stays the caller's (1000).
:::
