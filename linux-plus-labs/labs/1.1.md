In this lab you follow a Linux system from power-on to login prompt, change a bootloader setting and a kernel parameter and watch the change take effect, and then tour the standard directory layout. - Graphical user interface (GUI): display managers, window managers, X Server, Wayland

### How it works

**The boot process.** Starting a Linux computer is a relay race. Each runner does one job and hands the baton to the next:

```{.diagram}
 Power on
    |
 Firmware (BIOS or UEFI)      tests hardware, finds a boot device
    |                         (local disk, USB, or the network = PXE)
 Bootloader (GRUB 2)          shows a menu, reads its configuration file,
    |                         loads the kernel + initrd into memory
 Kernel (vmlinuz)             starts with its parameters (the "command line"),
    |                         detects hardware, mounts the initrd
 initrd / initramfs           tiny temporary root filesystem with the drivers
    |                         needed to find and mount the real root disk
 Real root filesystem  /
    |
 systemd (PID 1)              starts services, reaches a target
    |
 Login prompt (text or graphical display manager)
```

1. **Firmware.** The BIOS (older) or UEFI (modern) firmware is built into the motherboard or the VM. It checks the hardware and picks a boot device.
2. **Bootloader.** A bootloader is a small program whose only job is to load the operating system. Linux almost always uses **GRUB 2** (GRand Unified Bootloader). GRUB reads a generated **configuration file**, `/boot/grub/grub.cfg` on Ubuntu or `/boot/grub2/grub.cfg` on Rocky. You never edit that file by hand. Instead you edit `/etc/default/grub` (the settings you choose) and run a tool that rebuilds `grub.cfg`: `update-grub` on Ubuntu, `grub2-mkconfig` on Rocky.
3. **Kernel.** The **kernel** is the core of the operating system. It talks to the hardware and shares the CPU and memory between programs. Its file is `/boot/vmlinuz-<version>`. GRUB passes it **kernel parameters**, such as `root=` (where the real root filesystem is), `ro` (mount it read-only at first), or `quiet` (show fewer messages). You can read the parameters of the running kernel in `/proc/cmdline`.
4. **initrd.** The kernel needs a driver to read the root disk, but the drivers live on that disk. The **initrd** (initial RAM disk), today called an **initramfs**, solves this chicken-and-egg problem. It is a compressed archive that GRUB loads into memory next to the kernel. It holds just enough drivers and scripts to find and mount the real root filesystem, and then it hands over control. On Ubuntu it is `/boot/initrd.img-<version>` (built by `update-initramfs`); on Rocky it is `/boot/initramfs-<version>.img` (built by `dracut`).
5. **systemd.** The first real program, process ID 1, is `systemd`. It starts all services and brings the system to a **target** (a group of services), such as `multi-user.target` (text login) or `graphical.target` (desktop login).

**PXE** (Preboot eXecution Environment, said "pixie") is booting from the network instead of a disk. The network card's firmware asks a **DHCP** server for an IP address and is told "your boot file is on this **TFTP** server." It downloads a network bootloader (for example `pxelinux.0` or `grubnetx64.efi`), which downloads its configuration, a kernel, and an initrd, and boots them. Data centers use PXE to install hundreds of servers without touching a USB stick.

**The Filesystem Hierarchy Standard (FHS)** is the agreed map of where things live on a Linux system. Think of it as the floor plan every distribution follows, so an administrator can find the logs or the configuration on any system:

| Directory | What lives there |
|---|---|
| `/` | The root of the single directory tree. Everything hangs below it. |
| `/bin` | Essential user commands (`ls`, `cp`). On modern systems a link to `/usr/bin`. |
| `/sbin` | Essential system administration commands (`fdisk`, `ip`). A link to `/usr/sbin`. |
| `/boot` | The kernel, the initrd, and GRUB files. |
| `/dev` | Device files, such as `/dev/sda` (a disk) or `/dev/null`. |
| `/etc` | System-wide configuration files (text). |
| `/home` | Personal directories for users, such as `/home/student`. |
| `/lib` | Shared libraries and kernel modules. A link to `/usr/lib`. |
| `/proc` | A virtual filesystem: live information from the kernel, not stored on disk. |
| `/tmp` | Temporary files that anyone can write. Often cleared at boot. |
| `/usr` | Installed programs, libraries, and documentation (read-mostly). |
| `/var` | Variable data that grows: logs, caches, mail, databases, print queues. |

**Architectures.** A CPU architecture is the instruction language a processor understands. A program compiled for one architecture does not run on another. **x86** is the original 32-bit Intel family. **x86_64**, also called **AMD64** (AMD invented the 64-bit extension) or `amd64` in Debian/Ubuntu package names, is the 64-bit version used by most PCs and servers. **AArch64** (also called ARM64, `arm64` in Ubuntu) is 64-bit ARM, used in phones, Apple silicon Macs, Raspberry Pi, and cloud servers such as AWS Graviton. **RISC-V** is a newer, open (royalty-free) instruction set used in embedded boards and growing in servers.

**Distribution families.** A distribution is the Linux kernel plus tools, a package format, and an installer. Two big families matter for the exam. **dpkg-based** distributions (Debian, Ubuntu, Mint) use `.deb` packages, the low-level tool `dpkg`, and the high-level tool `apt`. **RPM-based** distributions (Red Hat Enterprise Linux, Rocky, AlmaLinux, Fedora, openSUSE) use `.rpm` packages, the low-level tool `rpm`, and high-level tools such as `dnf` or `zypper`.

**The GUI stack.** A Linux desktop is built from separate layers. The **display server** draws pixels and handles the keyboard and mouse. The classic one is the **X Server** (X11, Xorg); the modern replacement is **Wayland**, a protocol where the compositor itself is the display server. A **window manager** decides where windows go and draws their borders and title bars (examples: Mutter in GNOME, KWin in KDE, Openbox, i3). A **display manager** is the graphical login screen that starts your session (GDM, SDDM, LightDM). A desktop environment (GNOME, KDE Plasma, Xfce) bundles all of this with apps. Servers usually have no GUI at all.

**Software licensing.** **Open source** means the source code is available and you may study, change, and share it under the license. **Free software** (as defined by the Free Software Foundation) means "free as in freedom": the four freedoms to run, study, change, and redistribute. In practice most open source software is also free software. **Copyleft** licenses such as the GNU GPL say "if you distribute a changed version, you must share your source under the same license." Permissive licenses (MIT, BSD, Apache) let others make closed versions. **Proprietary** software is owned and controlled by a company; you get a license to use it, usually without source code, and you may not redistribute it (examples: some NVIDIA drivers, many commercial databases).

3. List the contents of `/boot`. This is where GRUB looks for the kernel and the initrd.

    ```bash
    ls -lh /boot
    ```

    ```{.output}
    -rw-r--r-- 1 root root 287K Aug  9 config-6.8.0-45-generic
    drwx------ 3 root root 4.0K Jan  1  1970 efi
    drwxr-xr-x 5 root root 4.0K Oct 10 09:12 grub
    lrwxrwxrwx 1 root root   28 Oct 10 09:10 initrd.img -> initrd.img-6.8.0-45-generic
    -rw-r--r-- 1 root root  67M Oct 10 09:11 initrd.img-6.8.0-45-generic
    -rw------- 1 root root 8.9M Aug  9 System.map-6.8.0-45-generic
    lrwxrwxrwx 1 root root   25 Oct 10 09:10 vmlinuz -> vmlinuz-6.8.0-45-generic
    -rw------- 1 root root  15M Aug  9 vmlinuz-6.8.0-45-generic
    ```

    ::: explain
    **What just happened:** `ls -lh` shows a long listing (`-l`) with human-readable sizes (`-h`). Read it like this:

    - `vmlinuz-6.8.0-45-generic` is the compressed **kernel**. The "z" means compressed.
    - `initrd.img-6.8.0-45-generic` is the **initrd** (initramfs) for that exact kernel version. It is much larger than the kernel because it contains drivers and tools.
    - `config-...` is the list of options the kernel was compiled with, and `System.map-...` is a table of kernel symbol addresses used for debugging.
    - `vmlinuz` and `initrd.img` without a version are **symbolic links** (shortcuts, shown by `->`) that always point at the newest kernel.
    - `grub/` holds GRUB's modules and its generated configuration file. `efi/` is the EFI system partition (only on UEFI systems).

    Your version numbers will differ. You may see two kernels if updates were installed; Ubuntu keeps the previous one as a fallback.
    :::

4. Compare the file names with the kernel that is running now. `uname -r` prints the running kernel release.

    ```bash
    uname -r
    ```

    ```{.output}
    6.8.0-45-generic
    ```

#### Task 2: Read the bootloader configuration files and the kernel command line

1. Display GRUB's settings file. This is the file **you** edit.

    ```bash
    cat /etc/default/grub
    ```

    ```{.output}
    GRUB_DEFAULT=0
    GRUB_TIMEOUT_STYLE=hidden
    GRUB_TIMEOUT=0
    GRUB_DISTRIBUTOR=`( . /etc/os-release; echo ${NAME:-Ubuntu} ) 2>/dev/null || echo Ubuntu`
    GRUB_CMDLINE_LINUX_DEFAULT=""
    GRUB_CMDLINE_LINUX=""
    ```

    ::: explain
    **What just happened:** `cat` prints a file. The comment lines (starting with `#`) were left out of the sample. The important settings are:

    - `GRUB_DEFAULT=0` boots the first menu entry by default.
    - `GRUB_TIMEOUT_STYLE=hidden` and `GRUB_TIMEOUT=0` hide the menu and boot immediately. (Holding **Shift** on BIOS, or pressing **Esc** on UEFI, during boot still shows the menu.)
    - `GRUB_CMDLINE_LINUX_DEFAULT` holds kernel parameters for normal boots only. Ubuntu Desktop puts `quiet splash` here.
    - `GRUB_CMDLINE_LINUX` holds kernel parameters added to **every** boot entry, including recovery mode.
    :::

    ::: tip
    Ubuntu also reads files in `/etc/default/grub.d/` after `/etc/default/grub`, and they can override it. Cloud images often have one there. Check with `ls /etc/default/grub.d/`. If a file there sets `GRUB_TIMEOUT`, that value wins.
    :::

2. Look at the generated configuration file that GRUB actually reads at boot. It is long, so search it for the lines that load the kernel and initrd. `grep -E` searches using an extended regular expression, and `-m 4` stops after four matches.

    ```bash
    sudo grep -E -m 4 '^\s*(menuentry|linux|initrd)' /boot/grub/grub.cfg
    ```

    ```{.output}
    menuentry 'Ubuntu' --class ubuntu --class gnu-linux --class gnu --class os ... {
            linux   /vmlinuz-6.8.0-45-generic root=/dev/mapper/ubuntu--vg-ubuntu--lv ro
            initrd  /initrd.img-6.8.0-45-generic
    menuentry 'Ubuntu, with Linux 6.8.0-45-generic' --class ubuntu ...
    ```

    ::: explain
    **What just happened:** Each `menuentry` is one choice in the GRUB menu. Inside it, the `linux` line names the kernel file and its **parameters** (`root=` and `ro` here), and the `initrd` line names the initrd file. Notice the top of the real file says `DO NOT EDIT THIS FILE`: it is rebuilt from `/etc/default/grub` and the scripts in `/etc/grub.d/` every time `update-grub` runs, so manual edits would be lost.
    :::

3. Read the parameters the running kernel actually received.

    ```bash
    cat /proc/cmdline
    ```

    ```{.output}
    BOOT_IMAGE=/vmlinuz-6.8.0-45-generic root=/dev/mapper/ubuntu--vg-ubuntu--lv ro
    ```

    ::: explain
    **What just happened:** `/proc/cmdline` is not a real file on disk. `/proc` is a virtual filesystem, and reading this "file" asks the kernel to print the command line it was started with. `BOOT_IMAGE=` is added by GRUB to say which kernel file it loaded. This matches the `linux` line in `grub.cfg`, which proves which configuration was used.
    :::

::: checkpoint
**Checkpoint:** You can explain the difference between `/etc/default/grub` (you edit it), `/boot/grub/grub.cfg` (generated, GRUB reads it), and `/proc/cmdline` (what the kernel received). `cat /proc/cmdline` should show a `root=` parameter.
:::

#### Task 3: Read the story of the last boot

1. Ask systemd how long the last boot took.

    ```bash
    systemd-analyze
    ```

    ```{.output}
    Startup finished in 3.512s (firmware) + 2.104s (loader) + 2.311s (kernel)
    + 9.874s (userspace) = 17.802s
    graphical.target reached after 9.801s in userspace.
    ```

    ::: explain
    **What just happened:** `systemd-analyze` splits the boot into the stages from the diagram: **firmware** (UEFI only), **loader** (GRUB), **kernel** (kernel plus initrd), and **userspace** (systemd starting services). On a BIOS VM the firmware and loader times are not shown. Do not worry about "graphical.target" on a server; on Ubuntu Server it is an alias that adds nothing visible.
    :::

2. See which services took the longest, and the chain of units that the boot waited for. Press `q` to leave the pager if one opens.

    ```bash
    systemd-analyze blame | head -5
    systemd-analyze critical-chain
    ```

    ::: explain
    **What just happened:** `blame` lists units sorted by how long each took to start; `head -5` keeps the first five lines. `critical-chain` shows the path of units that the final target had to wait for, with times after `@` (when it started) and `+` (how long it took). Slow boots are usually explained by the top entries.
    :::

3. Read the kernel's own messages from the current boot. `journalctl` reads the systemd journal; `-b` limits it to the current boot and `-k` to kernel messages. `--no-pager` prints straight to the screen.

    ```bash
    journalctl -b -k --no-pager | head -8
    ```

    ```{.output}
    Oct 10 09:20:01 ubuntu-lab kernel: Linux version 6.8.0-45-generic ...
    Oct 10 09:20:01 ubuntu-lab kernel: Command line: BOOT_IMAGE=/vmlinuz-6.8.0-45-generic
    root=/dev/mapper/ubuntu--vg-ubuntu--lv ro
    Oct 10 09:20:01 ubuntu-lab kernel: KERNEL supported cpus:
    Oct 10 09:20:01 ubuntu-lab kernel:   Intel GenuineIntel
    Oct 10 09:20:01 ubuntu-lab kernel:   AMD AuthenticAMD
    ...
    ```

    ::: explain
    **What just happened:** The very first kernel messages show the kernel version and, again, the command line. If you run `journalctl --list-boots`, you see a numbered list of earlier boots; `journalctl -b -1` shows the previous boot. Ubuntu keeps the journal on disk in `/var/log/journal`, so these survive reboots.
    :::

4. Find the moment the initrd handed over to the real root filesystem.

    ```bash
    journalctl -b --no-pager | grep -i -m 3 -E 'initrd|switch root'
    ```

    ::: explain
    **What just happened:** You should see lines such as `Reached target initrd-switch-root.target` or `Switching root.`. That is systemd inside the initramfs finishing its job and switching to your real `/`. On some Ubuntu builds the initramfs uses shell scripts instead of systemd and the wording differs; any line mentioning initrd or switching root is fine.
    :::

#### Task 4: Change GRUB and add a kernel parameter (then revert)

::: warning
Take a snapshot of ubuntu-lab now if you have not already. A typo in `/etc/default/grub` can stop the VM from booting. You will make a backup copy first, and you should work at the VM console (not only over SSH) so you can see the GRUB menu.
:::

1. Make a backup copy of the settings file. `cp` copies a file; `sudo` is needed because only root can write in `/etc`.

    ```bash
    sudo cp /etc/default/grub /etc/default/grub.lab-backup
    ```

2. Show the GRUB menu for 10 seconds and add a harmless made-up kernel parameter, `labtest=1`. You can edit the file with `sudo nano /etc/default/grub`, or use the three `sed` commands below, which do the same edits without typos.

    ```bash
    sudo sed -i 's/^GRUB_TIMEOUT_STYLE=.*/GRUB_TIMEOUT_STYLE=menu/' /etc/default/grub
    sudo sed -i 's/^GRUB_TIMEOUT=.*/GRUB_TIMEOUT=10/' /etc/default/grub
    sudo sed -i 's/^GRUB_CMDLINE_LINUX_DEFAULT="\(.*\)"/GRUB_CMDLINE_LINUX_DEFAULT="\1 labtest=1"/' \
      /etc/default/grub
    ```

    ::: explain
    **What just happened:** `sed` is a stream editor. `-i` edits the file in place. The expression `s/OLD/NEW/` substitutes text. `^` means "start of the line" and `.*` means "anything", so `s/^GRUB_TIMEOUT=.*/GRUB_TIMEOUT=10/` replaces the whole `GRUB_TIMEOUT` line. In the third command, `\(.*\)` captures whatever was already between the quotes, and `\1` puts it back, followed by ` labtest=1`. That way any existing parameters (such as `quiet splash`) are kept.
    :::

3. Check your edits before going further.

    ```bash
    grep -E '^GRUB_(TIMEOUT|CMDLINE)' /etc/default/grub
    ```

    ```{.output}
    GRUB_TIMEOUT_STYLE=menu
    GRUB_TIMEOUT=10
    GRUB_CMDLINE_LINUX_DEFAULT=" labtest=1"
    GRUB_CMDLINE_LINUX=""
    ```

    ::: explain
    **What just happened:** The leading space inside the quotes is harmless; the kernel ignores extra spaces. If any line looks wrong, fix it with `sudo nano /etc/default/grub` before continuing.
    :::

4. Rebuild `grub.cfg` from your settings.

    ```bash

    ```

    ```{.output}
    Found initrd image: /boot/initrd.img-6.8.0-45-generic

    Check GRUB_DISABLE_OS_PROBER documentation entry.
    Adding boot menu entry for UEFI Firmware Settings ...
    ```

    ::: explain
    **What just happened:** `update-grub` is an Ubuntu/Debian shortcut for `grub-mkconfig -o /boot/grub/grub.cfg`. It reads `/etc/default/grub`, runs each script in `/etc/grub.d/` (for example `10_linux` finds kernels in `/boot`), and writes a fresh `grub.cfg`. 6. Watch the VM console. You now see the GRUB menu with a 10-second countdown. Use the arrow keys to look at the entries (including **Advanced options for Ubuntu**), but do not press `e` yet. Let it boot the default entry.

    ::: tip
    At the GRUB menu, pressing `e` opens the selected entry for a **one-time** edit. You can add or remove kernel parameters on the `linux` line and press **Ctrl+X** to boot. Nothing is saved. Administrators use this to rescue a system, for example by adding `systemd.unit=rescue.target` to boot into single-user rescue mode.

7. Log back in and check what the kernel received.

    ```bash
    cat /proc/cmdline
    sudo dmesg | grep -i labtest
    ```

    ```{.output}
    BOOT_IMAGE=/vmlinuz-6.8.0-45-generic root=/dev/mapper/ubuntu--vg-ubuntu--lv ro labtest=1
    [    0.071234] Unknown kernel command line parameters "BOOT_IMAGE=/vmlinuz-6.8.0-45-generic
    labtest=1", will be passed to user space.
    ```

    ::: explain
    **What just happened:** The parameter traveled the whole chain: `/etc/default/grub` to `grub.cfg` (via `update-grub`) to GRUB to the kernel. The kernel did not recognize `labtest=1`, so it printed a notice and passed it on to user space (programs can still read it in `/proc/cmdline`). That is why it is harmless. Real parameters work the same way, for example `nomodeset` (do not load graphics drivers), `systemd.unit=multi-user.target`, or `mitigations=off`. `dmesg` prints the kernel's message buffer; `sudo` is needed because Ubuntu restricts it to root.
    :::

8. Revert to the original settings and rebuild `grub.cfg` again.

    ```bash
    sudo cp /etc/default/grub.lab-backup /etc/default/grub
    sudo update-grub
    grep -c labtest /boot/grub/grub.cfg
    ```

    ```{.output}
    0
    ```

    ::: explain
    **What just happened:** You restored the backup and regenerated the file. `grep -c` counts matching lines; `0` proves the parameter is gone from the configuration. It disappears from `/proc/cmdline` at the next reboot. Leave the backup file for now; you delete it in Clean up.
    :::

**Checkpoint:** Before the revert, `cat /proc/cmdline` showed `labtest=1`. After the revert, `grep -c labtest /boot/grub/grub.cfg` prints `0` and `grep ^GRUB_TIMEOUT= /etc/default/grub` shows the original value.

#### Task 5: Compare GRUB tools and look inside the initrd on both systems

1. On ubuntu-lab, list what is inside the initrd. `lsinitramfs` (from the `initramfs-tools-core` package, installed by default) lists the files in an initramfs image.

    ```bash
    sudo lsinitramfs /boot/initrd.img-$(uname -r) | wc -l
    sudo lsinitramfs /boot/initrd.img-$(uname -r) | grep -E 'bin/(busybox|lvm|udevadm)$'
    ```

    ```{.output}
    3417
    usr/bin/busybox
    usr/bin/udevadm
    usr/sbin/lvm
    ```

    ::: explain
    **What just happened:** `$(uname -r)` is **command substitution**: the shell runs `uname -r` and puts its output into the file name, so the command always targets the running kernel. `wc -l` counts lines, so you see the initrd holds thousands of files. The `grep` finds three key tools: `busybox` (a small all-in-one shell and command set), `udevadm` (detects devices), and `lvm` (needed here because Ubuntu's default install puts `/` on an LVM volume). Without `lvm` in the initrd, the kernel could not find `root=/dev/mapper/ubuntu--vg-ubuntu--lv`.
    :::

2. Switch to rocky-lab (log in at its console or run `ssh student@rocky-lab`). Rocky uses the same GRUB 2, but the commands have a `2` in their names and the files are in different places.

    ```bash
    # on rocky-lab
    cat /etc/default/grub
    ls /boot
    ls /boot/loader/entries/
    ```

    ```{.output}
    GRUB_TIMEOUT=5
    GRUB_DISTRIBUTOR="$(sed 's, release .*$,,g' /etc/system-release)"
    GRUB_DEFAULT=saved
    GRUB_DISABLE_SUBMENU=true
    GRUB_TERMINAL_OUTPUT="console"
    GRUB_CMDLINE_LINUX="crashkernel=1G-4G:192M,4G-64G:256M,64G-:512M resume=/dev/mapper/rl-swap
    rd.lvm.lv=rl/root rd.lvm.lv=rl/swap"
    GRUB_DISABLE_RECOVERY="true"
    GRUB_ENABLE_BLSCFG=true
    ...
    config-5.14.0-427.13.1.el9_4.x86_64
    efi
    grub2
    initramfs-5.14.0-427.13.1.el9_4.x86_64.img
    loader
    vmlinuz-5.14.0-427.13.1.el9_4.x86_64
    ...
    a1b2c3d4e5f6-5.14.0-427.13.1.el9_4.x86_64.conf
    ```

    ::: explain
    **What just happened:** Rocky's initrd is named `initramfs-<version>.img`. `GRUB_ENABLE_BLSCFG=true` means Rocky uses the **Boot Loader Specification** (BLS): each kernel gets its own small entry file in `/boot/loader/entries/` instead of a long `menuentry` block in `grub.cfg`. The `rd.lvm.lv=` parameters tell the initramfs (`rd` means "RAM disk") which LVM volumes to activate.
    :::

3. On Rocky, the recommended tool for changing kernel parameters is `grubby`, which edits the BLS entries directly. Look at the default entry, add the test parameter, check it, and remove it again.

    ```bash
    # on rocky-lab
    sudo grubby --default-kernel
    sudo grubby --update-kernel=ALL --args="labtest=1"
    sudo grubby --info=DEFAULT | grep ^args
    sudo grubby --update-kernel=ALL --remove-args="labtest=1"
    sudo grubby --info=DEFAULT | grep ^args
    ```

#### Task 6: Explore PXE network booting

::: tip
**Explore/simulate:** A real PXE boot needs a DHCP server, a TFTP server, and a client VM with network boot enabled, and a second DHCP server on your lab network could break your other VMs. Instead, you will write the configuration files a PXE server would use, so you can recognize each piece on the exam. Nothing is installed or started.
:::

1. Here is the conversation a PXE client has when it powers on:

    ```{.diagram}
     PXE client (no OS)                    Servers on the network
     ------------------                    ----------------------
     DHCPDISCOVER  "I need an IP + boot info"  ---> DHCP server
                   <--- DHCPOFFER  IP 192.168.100.50
                        next-server 192.168.100.10  (TFTP server)
                        filename "grubnetx64.efi"   (or pxelinux.0 for BIOS)
     TFTP GET grubnetx64.efi                  ---> TFTP server
     TFTP GET grub/grub.cfg                   ---> TFTP server
     TFTP/HTTP GET vmlinuz + initrd           ---> TFTP or HTTP server
     boot kernel with parameters from the config
    ```

    ::: explain
    **What just happened:** DHCP (Dynamic Host Configuration Protocol) gives out addresses and can also say where the boot file is. TFTP (Trivial File Transfer Protocol, UDP port 69) is a tiny file transfer protocol simple enough to fit in network card firmware. After the bootloader is running, larger files are often fetched over HTTP, which is faster.
    :::

2. Write an example `dnsmasq` configuration. `dnsmasq` is a small program that can be both the DHCP and TFTP server. This lab uses a **heredoc**: everything between `<<'EOF'` and the line `EOF` is fed to `cat` as input, and `cat` writes it into the file named after `>`. The quotes around `'EOF'` stop the shell from changing anything inside.

    ```bash
    mkdir -p ~/labs/1.1/pxe/pxelinux.cfg
    cat <<'EOF' > ~/labs/1.1/pxe/dnsmasq-pxe.conf
    # Example only: DHCP + TFTP for PXE clients on the lab network
    interface=enp0s3
    dhcp-range=192.168.100.50,192.168.100.99,12h
    enable-tftp
    tftp-root=/srv/tftp
    # BIOS clients get pxelinux.0, UEFI x86_64 clients get GRUB
    dhcp-match=set:efi64,option:client-arch,7
    dhcp-boot=tag:efi64,grubnetx64.efi
    dhcp-boot=tag:!efi64,pxelinux.0
    EOF
    ```

3. Write the menu file a BIOS client would download after `pxelinux.0`. PXELINUX looks for `pxelinux.cfg/default` when no host-specific file exists.

    ```bash
    cat <<'EOF' > ~/labs/1.1/pxe/pxelinux.cfg/default
    DEFAULT install
    PROMPT 0
    TIMEOUT 50
    LABEL install
      MENU LABEL Install Ubuntu Server 24.04 over the network
      KERNEL ubuntu/vmlinuz
      APPEND initrd=ubuntu/initrd ip=dhcp url=http://192.168.100.10/ubuntu-24.04.iso
    EOF
    cat ~/labs/1.1/pxe/pxelinux.cfg/default
    ```

    ::: explain
    **What just happened:** This file has the same parts as a local GRUB entry: a **kernel** (`KERNEL`), an **initrd** (`initrd=`), and **kernel parameters** (`ip=dhcp` tells the initrd to get an address, `url=` tells the Ubuntu installer where to download the ISO). The only difference from a disk boot is that every file arrives over the network. A UEFI client would read a `grub.cfg` with `linux` and `initrd` lines instead.
    :::

::: checkpoint
**Checkpoint:** `ls -R ~/labs/1.1/pxe` shows `dnsmasq-pxe.conf` and `pxelinux.cfg/default`, and you can explain the order: DHCP, then TFTP download of the bootloader, then its configuration, then kernel and initrd.

### Exam corner

- Boot order: firmware (BIOS/UEFI) then bootloader (GRUB 2) then kernel then initrd/initramfs then systemd (PID 1) then the default target.
- Edit `/etc/default/grub`, never `grub.cfg`. Rebuild with `update-grub` or `grub-mkconfig -o /boot/grub/grub.cfg` (Debian/Ubuntu) or `grub2-mkconfig -o /boot/grub2/grub.cfg` (RHEL/Rocky). `grubby` changes kernel parameters on RHEL-family systems.
- `GRUB_CMDLINE_LINUX` applies to all entries; `GRUB_CMDLINE_LINUX_DEFAULT` to normal boots only. `GRUB_TIMEOUT` and `GRUB_DEFAULT` control the menu.
- The running kernel's parameters are in `/proc/cmdline`. Press `e` at the GRUB menu for a one-time change.
- The initrd/initramfs holds drivers needed to mount `/`. Ubuntu: `update-initramfs`, `lsinitramfs`. Rocky: `dracut`, `lsinitrd`.
- PXE = network boot: DHCP gives an address and the boot file name, TFTP delivers the bootloader, then the kernel and initrd.
- FHS: `/etc` config, `/var` variable data and logs, `/proc` virtual kernel and process info, `/dev` device files, `/boot` kernel and initrd, `/usr` installed software, `/tmp` temporary (sticky bit), `/home` user files, `/bin` and `/sbin` and `/lib` essential commands and libraries.
- x86_64 = AMD64 = `amd64` (Debian). AArch64 = ARM64 = `arm64` (Debian). RISC-V is an open instruction set. `uname -m` shows the architecture.
- dpkg-based: `.deb`, `dpkg`, `apt` (Debian, Ubuntu). RPM-based: `.rpm`, `rpm`, `dnf`/`yum`/`zypper` (RHEL, Rocky, Fedora, SUSE).
- Display manager = graphical login (GDM, SDDM, LightDM). Window manager = places and decorates windows. X Server (Xorg) and Wayland are display servers; Wayland is the modern default.
- Copyleft (GPL) requires derivative works to keep the same license. Permissive (MIT, BSD, Apache) does not. Proprietary = closed source, restricted redistribution. Free software = the four freedoms.

2. **C.** The initrd/initramfs is a temporary root filesystem in RAM that carries the drivers and tools (such as `lvm`) needed to find and mount `/`.
3. **PXE** (Preboot eXecution Environment); the bootloader is downloaded with **TFTP** after DHCP supplies the server address and file name.
4. **C.** `/proc` is a virtual filesystem whose contents are generated by the kernel on demand.
5. **B.** AArch64 is called `arm64` in Debian and Ubuntu package names; `amd64` is x86_64.
6. **B.** Copyleft requires anyone who distributes a modified version to provide the source under the same license.
