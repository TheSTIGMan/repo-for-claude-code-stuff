## Lab 4.4: Version Control with Git {#lab-4-4}

::: labinfo
**Objective:** 4.4 Given a scenario, implement version control using Git.\
**Domain:** 4.0 Automation, Orchestration, and Scripting (17% of the exam)\
**Time:** about 2.5 hours\
**VM:** ubuntu-lab and rocky-lab\
**Snapshot first:** Not required. All work happens in your home directories.

Git records every change to a set of files: who changed what, when, and why. Admins use it for scripts, configuration files, Ansible playbooks, and Kubernetes manifests, so they can review changes, undo mistakes, and work together without overwriting each other. In this lab you put a folder of admin scripts under Git, work with branches, merge (including a real conflict), squash, rebase, stash, reset, and tag. Then you host a shared repository on rocky-lab over SSH and simulate two admins pushing and pulling, exactly as you would with GitHub or GitLab.

### What you'll practice

- `git config`, `git init`, `.gitignore`
- `git add`, `git commit`, `git diff`, `git log`
- `git branch`, `git checkout` (and `git switch`)
- `git merge` (fast-forward, three-way, conflicts, and `--squash`)
- `git rebase`
- `git stash`
- `git reset` (`--soft`, `--mixed`, `--hard`) and recovery with `git reflog`
- `git tag` (lightweight and annotated)
- `git clone`, `git push`, `git fetch`, `git pull` with a remote repository

### How it works

A Git **repository** (repo) is a project folder plus a hidden `.git` directory that stores the complete history. Git is **distributed**: every clone has the full history, so you can commit, branch, and view logs with no network at all. You only need the network to exchange commits with another copy (a **remote**).

Every file you change moves through three areas:

```{.diagram}
  working directory  --git add-->  staging area (index)  --git commit-->  repository (.git)
   (files you edit)                (what the next commit                 (permanent history
                                     will contain)                         of snapshots)
        ^                                                                       |
        +--------------------------- git checkout / git switch ----------------+
```

- The **working directory** is the normal files you edit.
- The **staging area** (also called the **index**) is a draft of the next commit. `git add` copies changes into it, so you can choose exactly what goes into each commit.
- A **commit** is a snapshot of the staged files, with an author, date, message, and a pointer to its parent commit(s). Each commit is named by a 40-character SHA-1 hash, which you can shorten to the first 7 characters.

A **branch** is just a movable label that points to a commit. `main` is the usual default branch. When you commit, the current branch's label moves forward. `HEAD` is a pointer to the branch (and commit) you have checked out right now. Because branches are so cheap, admins create one for every change: `feature/new-backup`, `fix/ssh-timeout`, and so on.

**Merging** brings the commits of one branch into another. If the target branch has not moved since you branched, Git simply slides the label forward: a **fast-forward** merge. If both branches have new commits, Git makes a new **merge commit** with two parents: a **three-way merge** (it compares both tips with their common ancestor). If both branches changed the same lines, Git cannot decide and stops with a **merge conflict** for you to fix. **Rebasing** is the alternative: it replays your branch's commits on top of the other branch, producing a straight-line history instead of a merge commit. A **squash merge** combines all of a branch's commits into one new commit.

```{.diagram}
 Fast-forward:   main: A---B              after merge:  A---B---C---D  (main)
                            \
                  feature:   C---D

 Three-way:      main: A---B---E          after merge:  A---B---E---M  (main)
                            \                                \     /
                  feature:   C---D                            C---D

 Rebase:         feature C---D replayed on E:   A---B---E---C'---D'  (feature)
```

A **remote** is another copy of the repository, usually on a server. GitHub, GitLab, and Bitbucket host remotes with web interfaces, but any Linux server with SSH and Git can host a **bare** repository (one with no working directory, used only for pushing and pulling). `git push` sends your commits to the remote, `git fetch` downloads new commits without changing your files, and `git pull` is `fetch` followed by `merge` (or `rebase`). `git clone` copies a whole remote repository to a new folder.

#### Task 3: Branches and merges

1. List branches with **git branch**, create a new one with **git checkout -b**, and commit on it.

    ```bash
    git branch
    git checkout -b feature/retention
    cat >> backup.sh <<'EOF'
    # keep only the 7 newest archives
    ls -1t /var/backups/etc-*.tar.gz | tail -n +8 | xargs -r rm -f
    EOF
    git commit -am "Keep only 7 backup archives"
    git branch -v
    ```

    ```{.output}
    * main
    Switched to a new branch 'feature/retention'
    [feature/retention cb4156a] Keep only 7 backup archives
     1 file changed, 2 insertions(+)
    * feature/retention cb4156a Keep only 7 backup archives
      main              fc7035c Disable SSH password authentication
    ```

    ::: explain
    **What just happened:** `git checkout -b NAME` creates a branch at the current commit and switches to it in one step (the same as `git branch NAME` followed by `git checkout NAME`). The `*` marks the current branch. `cat >>` appended lines to the file. `git commit -a` stages every change to already-tracked files before committing, which saves a `git add` (it never adds untracked files). `git branch -v` shows the commit each branch points to.
    :::

2. Switch back to `main` and **merge** the branch. Because `main` has not moved, this is a fast-forward.

    ```bash
    git switch main
    tail -n 2 backup.sh
    git merge feature/retention
    tail -n 2 backup.sh
    git log --oneline --graph
    git branch -d feature/retention
    ```

    ```{.output}
    Switched to branch 'main'
    tar -czf "/var/backups/etc-$(date +%F).tar.gz" /etc
    Updating fc7035c..cb4156a
    Fast-forward
     backup.sh | 2 ++
     1 file changed, 2 insertions(+)
    # keep only the 7 newest archives
    ls -1t /var/backups/etc-*.tar.gz | tail -n +8 | xargs -r rm -f
    * cb4156a (HEAD -> main) Keep only 7 backup archives
    * fc7035c Disable SSH password authentication
    * 4491226 Add backup script and SSH hardening config
    Deleted branch feature/retention (was cb4156a).
    ```

    ::: explain
    **What just happened:** `git switch` (Git 2.23 and later) is a newer, clearer command just for changing branches; `git checkout main` does the same thing and is still widely used, so know both. When you switched to `main`, Git changed the files in your working directory to match: the new lines vanished, then came back after the merge. `Fast-forward` means Git just moved the `main` label forward; no merge commit was needed. `git branch -d` deletes a branch that has been merged (the commits stay in `main`).
    :::

3. Create a **three-way merge**: commit on a new branch *and* on `main`, then merge.

    ```bash
    git switch -c feature/motd
    echo 'Authorized use only. Activity is logged.' > motd.txt
    git add motd.txt
    git commit -m "Add login banner"
    git switch main
    echo 'ClientAliveInterval 300' >> sshd-hardening.conf
    git commit -am "Add SSH idle timeout"
    git merge feature/motd --no-edit
    git log --oneline --graph
    git branch -d feature/motd
    ```

    ```{.output}
    Merge made by the 'ort' strategy.
     motd.txt | 1 +
     1 file changed, 1 insertion(+)
     create mode 100644 motd.txt
    *   7046d2e (HEAD -> main) Merge branch 'feature/motd'
    |\
    | * 72e85af Add login banner
    * | 1ad82ab Add SSH idle timeout
    |/
    * cb4156a Keep only 7 backup archives
    ...
    ```

    ::: explain
    **What just happened:** `git switch -c` creates and switches, like `checkout -b`. Both branches had new commits, so Git combined them with a merge commit that has two parents; `--graph` draws the two lines of history joining. `ort` is Git's default merge strategy. `--no-edit` accepted the default message (`Merge branch 'feature/motd'`) instead of opening the editor. The branches changed different files, so there was no conflict.
    :::

4. Now cause a **merge conflict**: change the same line differently on two branches.

    ```bash
    git switch -c fix/auth-tries
    echo 'MaxAuthTries 3' >> sshd-hardening.conf
    git commit -am "Limit SSH auth tries to 3"
    git switch main
    echo 'MaxAuthTries 5' >> sshd-hardening.conf
    git commit -am "Limit SSH auth tries to 5"
    git merge fix/auth-tries
    git status
    cat sshd-hardening.conf
    ```

    ```{.output}
    Auto-merging sshd-hardening.conf
    CONFLICT (content): Merge conflict in sshd-hardening.conf
    Automatic merge failed; fix conflicts and then commit the result.
    On branch main
    You have unmerged paths.
      (fix conflicts and run "git commit")
      (use "git merge --abort" to abort the merge)

    Unmerged paths:
      (use "git add <file>..." to mark resolution)
            both modified:   sshd-hardening.conf
    PermitRootLogin no
    PasswordAuthentication no
    ClientAliveInterval 300
    <<<<<<< HEAD
    MaxAuthTries 5
    =======
    MaxAuthTries 3
    >>>>>>> fix/auth-tries
    ```

    ::: explain
    **What just happened:** Both branches added a different line at the same place, so Git stopped and wrote **conflict markers** into the file. Between `<<<<<<< HEAD` and `=======` is your current branch's version (`main`); between `=======` and `>>>>>>> fix/auth-tries` is the incoming branch's version. The merge is paused; `git merge --abort` would cancel it and put everything back.
    :::

5. Resolve the conflict. You decide the team policy is 3 tries. Edit the file so it contains the final content you want with **no markers left**: open it with `nano sshd-hardening.conf` and make it look like this, or overwrite it with the command below.

    ```bash
    printf 'PermitRootLogin no\nPasswordAuthentication no\nClientAliveInterval 300\nMaxAuthTries 3\n' \
      > sshd-hardening.conf
    git add sshd-hardening.conf
    git commit --no-edit
    git log --oneline --graph -4
    git branch -d fix/auth-tries
    ```

    ```{.output}
    [main 8ee72ad] Merge branch 'fix/auth-tries'
    *   8ee72ad (HEAD -> main) Merge branch 'fix/auth-tries'
    |\
    | * a80af20 Limit SSH auth tries to 3
    * | 51cf885 Limit SSH auth tries to 5
    |/
    ...
    ```

    ::: explain
    **What just happened:** The resolution steps are always: (1) edit each conflicted file into its final form and remove all markers, (2) `git add` each file to mark it resolved, (3) `git commit` to finish the merge. Before committing, `grep -n '<<<<<<<\|>>>>>>>' *` is a quick check that no markers were left behind; a config file with markers in it would break the service.
    :::

::: checkpoint
**Checkpoint:** `cat sshd-hardening.conf` ends with `MaxAuthTries 3`, `git status` is clean, and `git branch` lists only `main`.
:::

#### Task 4: Squash merges and rebasing

1. Make a feature branch with several messy work-in-progress commits.

    ```bash
    git switch -c feature/cleanup
    printf '#!/bin/bash\n# cleanup.sh - remove old files from /tmp\n' > cleanup.sh
    git add cleanup.sh
    git commit -m "WIP: start cleanup script"
    echo 'find /tmp -type f -mtime +7 -print' >> cleanup.sh
    git commit -am "WIP: list old files"
    sed -i 's/-print/-delete/' cleanup.sh
    git commit -am "fix typo"
    git log --oneline main..feature/cleanup
    ```

    ```{.output}
    7ea46b6 (HEAD -> feature/cleanup) fix typo
    c62bf41 WIP: list old files
    da9718e WIP: start cleanup script
    ```

    ::: explain
    **What just happened:** `main..feature/cleanup` means "commits on `feature/cleanup` that are not on `main`". Three small commits like these are normal while working, but they clutter the shared history.
    :::

2. Merge with **squash** so `main` gets one clean commit.

    ```bash
    git switch main
    git merge --squash feature/cleanup
    git status --short
    git commit -m "Add /tmp cleanup script"
    git log --oneline -3
    git branch -d feature/cleanup
    git branch -D feature/cleanup
    ```

    ```{.output}
    Updating 8ee72ad..7ea46b6
    Fast-forward
    Squash commit -- not updating HEAD
     cleanup.sh | 3 +++
     1 file changed, 3 insertions(+)
     create mode 100644 cleanup.sh
    A  cleanup.sh
    [main 563159c] Add /tmp cleanup script
     1 file changed, 3 insertions(+)
     create mode 100644 cleanup.sh
    563159c (HEAD -> main) Add /tmp cleanup script
    8ee72ad Merge branch 'fix/auth-tries'
    51cf885 Limit SSH auth tries to 5
    error: the branch 'feature/cleanup' is not fully merged.
    If you are sure you want to delete it, run 'git branch -D feature/cleanup'
    Deleted branch feature/cleanup (was 7ea46b6).
    ```

    ::: explain
    **What just happened:** `git merge --squash` applied the combined changes of all three commits to your working directory and staging area but did **not** commit (`not updating HEAD`). You then wrote one good commit message. Because the original three commits never became part of `main`, Git thinks the branch is unmerged and `-d` refuses to delete it; `-D` forces the delete. GitHub and GitLab offer the same choice as a "Squash and merge" button on pull requests.
    :::

3. Set up a situation for **rebase**: a feature branch, and a new commit on `main` made after the branch was created.

    ```bash
    git switch -c feature/report
    printf '#!/bin/bash\n# report.sh - show disk and memory usage\ndf -h /\nfree -h\n' > report.sh
    git add report.sh
    git commit -m "Add system report script"
    git switch main
    echo 'X11Forwarding no' >> sshd-hardening.conf
    git commit -am "Disable X11 forwarding"
    git log --oneline --graph --all -4
    ```

    ```{.output}
    * 1c9891c (feature/report) Add system report script
    | * f1a8daf (HEAD -> main) Disable X11 forwarding
    |/
    * 563159c Add /tmp cleanup script
    ...
    ```

4. Rebase the feature branch onto `main`, then merge it (now a fast-forward).

    ```bash
    git switch feature/report
    git rebase main
    git log --oneline --graph --all -4
    git switch main
    git merge feature/report
    git branch -d feature/report
    ```

    ```{.output}
    Successfully rebased and updated refs/heads/feature/report.
    * 6112214 (HEAD -> feature/report) Add system report script
    * f1a8daf (main) Disable X11 forwarding
    * 563159c Add /tmp cleanup script
    ...
    Updating f1a8daf..6112214
    Fast-forward
    ```

    ::: explain
    **What just happened:** `git rebase main` took the commits unique to `feature/report`, set them aside, moved the branch to the tip of `main`, and replayed them one by one. The commit got a **new hash** (`1c9891c` became `6112214`) because its parent changed. The history is now a straight line and the merge was a fast-forward. If a replayed commit conflicts, Git pauses: fix the file, `git add` it, and run `git rebase --continue` (or `git rebase --abort` to cancel).
    :::

    ::: warning
    Golden rule: **never rebase commits that you have already pushed and others may have pulled.** Rebasing rewrites history (new hashes), so other people's copies no longer match. Rebase only your own local, unshared work.
    :::

::: checkpoint
**Checkpoint:** `git log --oneline --graph -3` shows a straight line with `Add system report script` on top of `Disable X11 forwarding`.

#### Task 5: Stash, reset, and recover with reflog

1. Use **git stash** to put unfinished work aside when an urgent change comes in.

    ```bash
    echo 'uptime' >> report.sh
    git status --short
    git stash push -m "half-done uptime line"
    git status --short
    git stash list
    echo 'LoginGraceTime 30' >> sshd-hardening.conf
    git commit -am "Shorten SSH login grace time"
    git stash pop
    git status --short
    git commit -am "Show uptime in report"
    ```

    ```{.output}
     M report.sh
    Saved working directory and index state On main: half-done uptime line
    stash@{0}: On main: half-done uptime line
    [main c599ce2] Shorten SSH login grace time
     1 file changed, 1 insertion(+)
    On branch main
    Changes not staged for commit:
    ...
            modified:   report.sh
    Dropped refs/stash@{0} (00dd6ad...)
     M report.sh
    [main 1317d07] Show uptime in report
    ```

    ::: explain
    **What just happened:** `git stash` (or `git stash push`) saved your uncommitted changes on a stack and reset the working directory to the last commit, so the urgent fix went into its own clean commit. `git stash pop` reapplied the saved changes and removed them from the stack. `git stash apply` would reapply but keep the stash; `git stash drop` deletes one without applying. ` M` means modified but not staged.
    :::

2. Learn the three kinds of **git reset**. First make a commit to play with, then undo it with `--soft`.

    ```bash
    echo 'echo "Report done"' >> report.sh
    git commit -am "Print a final message"
    git log --oneline -2
    git reset --soft HEAD~1
    git status --short
    git log --oneline -1
    ```

    ```{.output}
    [main d9e417e] Print a final message
    d9e417e (HEAD -> main) Print a final message
    1317d07 Show uptime in report
    M  report.sh
    1317d07 (HEAD -> main) Show uptime in report
    ```

    ::: explain
    **What just happened:** `git reset` moves the current branch to another commit. `HEAD~1` is the commit before `HEAD`. With `--soft`, only the branch moves: the change is still staged (`M` in the first column), ready to be recommitted, for example with a better message.
    :::

3. Commit again, then undo with `--mixed` (the default) and with `--hard`.

    ```bash
    git commit -m "Print a final message"
    git reset HEAD~1
    git status --short
    git commit -am "Print a final message"
    git reset --hard HEAD~1
    git status --short
    tail -n 1 report.sh
    ```

    ```{.output}
    Unstaged changes after reset:
    M       report.sh
     M report.sh
    HEAD is now at 1317d07 Show uptime in report
    uptime
    ```

    ::: explain
    **What just happened:** The three modes differ in how much they reset:

    | Mode | Moves branch | Resets staging area | Resets working files |
    |---|---|---|---|
    | `--soft` | yes | no | no |
    | `--mixed` (default) | yes | yes | no |
    | `--hard` | yes | yes | **yes** |

    With `--mixed`, the change stayed in your file but was unstaged (`M` in the second column). With `--hard`, the change was thrown away completely; the file no longer has the `echo "Report done"` line. `git reset FILE` (no mode) is also how you unstage a single file, and `git restore --staged FILE` is the newer way to do the same.
    :::

    ::: warning
    `git reset --hard` discards uncommitted work with no confirmation and no undo. Committed work can usually be recovered (next step); changes that were never committed or stashed are gone for good.
    :::

4. Recover the "lost" commit using **reflog**, Git's diary of where `HEAD` has been.

    ```bash
    git reflog | head -n 4
    git reset --hard HEAD@{1}
    tail -n 1 report.sh
    ```

    ```{.output}
    1317d07 HEAD@{0}: reset: moving to HEAD~1
    d9e417e HEAD@{1}: commit: Print a final message
    1317d07 HEAD@{2}: reset: moving to HEAD~1
    d9e417e HEAD@{3}: commit: Print a final message
    HEAD is now at d9e417e Print a final message
    echo "Report done"
    ```

    ::: explain
    **What just happened:** Every time `HEAD` moves (commit, reset, checkout, merge, rebase), Git writes a reflog entry. `HEAD@{1}` means "where HEAD was one move ago". Resetting back to it restored the commit. The reflog is local (it is never pushed) and entries expire after about 90 days, so it is a safety net, not a backup.
    :::

::: checkpoint
**Checkpoint:** `git log --oneline -1` shows `Print a final message` and `git status` is clean.
:::

#### Task 6: Tag releases

1. Create a lightweight tag and an annotated tag with **git tag**.

    ```bash
    git tag v1.0 HEAD~1
    git tag -a v1.1 -m "Release 1.1: SSH hardening and reports"
    git tag
    git tag -n
    git cat-file -t v1.0
    git cat-file -t v1.1
    git show v1.1 | head -n 8
    ```

    ```{.output}
    v1.0
    v1.1
    v1.0            Show uptime in report
    v1.1            Release 1.1: SSH hardening and reports
    commit
    tag
    tag v1.1
    Tagger: Student Admin <student@ubuntu-lab.local>
    Date:   Sat Oct 10 10:14:34 2026 +0000

    Release 1.1: SSH hardening and reports

    commit d9e417e...
    Author: Student Admin <student@ubuntu-lab.local>
    ```

    ::: explain
    **What just happened:** A tag is a permanent name for one commit, usually a release version. Unlike a branch, it never moves. A **lightweight** tag (`git tag v1.0 COMMIT`) is just a name pointing straight at a commit (`cat-file -t` says `commit`). An **annotated** tag (`-a` with `-m`) is a full Git object with its own tagger, date, and message (`cat-file -t` says `tag`); use annotated tags for releases. With no commit given, the tag goes on `HEAD`.
    :::

2. Use a tag to look at old files without changing your branch.

    ```bash
    git diff v1.0 v1.1 --stat
    git show v1.0:report.sh
    ```

    ::: explain
    **What just happened:** Tags work anywhere a commit hash works. `git diff v1.0 v1.1` compares two releases, and `git show TAG:FILE` prints a file as it was at that tag. To get an old version of a file back into your working directory, use `git checkout v1.0 -- report.sh` (or `git restore --source v1.0 report.sh`).
    :::

::: checkpoint
**Checkpoint:** `git tag -n` lists `v1.0` and `v1.1` with their messages.

### Exam corner

- `git config --global user.name/user.email` sets your identity; levels are `--system`, `--global`, `--local`.
- `git init` creates a repo; `git init --bare` creates a server-side repo with no working directory; `git clone URL` copies a remote repo.
- Workflow: edit, `git add` (stage), `git commit -m` (snapshot). `git status` shows state; `git log` (`--oneline --graph --all`) shows history.
- `git diff` = working vs staged; `git diff --staged` = staged vs last commit; `git diff A B` = between commits.
- `.gitignore` lists patterns (`*.log`, `tmp/`) for untracked files Git should ignore; it does not remove files already committed.
- `git branch` lists/creates branches; `git checkout -b NAME` or `git switch -c NAME` creates and switches; `git branch -d` deletes a merged branch (`-D` forces).
- `git merge BRANCH`: fast-forward when possible, otherwise a merge commit. Conflicts show `<<<<<<<`, `=======`, `>>>>>>>`; fix, `git add`, `git commit`. `git merge --squash` combines a branch into one staged change you then commit.
- `git rebase main` replays your commits on top of `main` (linear history, new hashes). Never rebase published commits.
- `git stash` saves uncommitted work; `git stash pop` restores it; `git stash list` shows the stack.
- `git reset --soft` (keep staged), `--mixed` (default, keep in working dir), `--hard` (discard everything). `git reflog` finds lost commits.
- `git tag v1.0` (lightweight) vs `git tag -a v1.0 -m "msg"` (annotated); push tags with `git push --tags`.
- `git fetch` downloads without merging; `git pull` = fetch + merge (or `--rebase`); `git push` uploads and is rejected if it is not a fast-forward.
