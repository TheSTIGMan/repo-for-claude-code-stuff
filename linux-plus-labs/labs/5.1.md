### How it works

**Monitoring** means collecting data about systems over time and reacting when something looks wrong. It has three layers: *what you promise*, *what you measure*, and *how you react*.

**What you promise: SLA, SLO, SLI.** Picture a pizza shop.

- The **SLA (service level agreement)** is the contract with the customer: "Delivery in 45 minutes or the pizza is free." It is a business document with consequences (refunds, credits, penalties).
- The **SLO (service level objective)** is the internal target the shop aims for, usually stricter than the SLA so there is a safety margin: "We aim to deliver 99% of pizzas in 30 minutes."
- The **SLI (service level indicator)** is the actual measurement: "Last month, 98.7% of pizzas arrived within 30 minutes."

For a web server, a typical SLI is *availability* (the percentage of health checks that succeeded) or *latency* (the percentage of requests answered in under 300 ms). The SLO might be "99.9% available per month." The gap between 100% and the SLO is the **error budget**: 0.1% of a 30-day month is 43.2 minutes of allowed downtime. When the budget is used up, the team stops shipping risky changes.

**What you measure: data acquisition.** There are several ways to get data out of a system:

- A **health check** is a small, repeated test that asks "are you working?" For a web server, that means requesting a page and checking for HTTP status `200`. Load balancers use health checks to remove broken servers from rotation.
- An **agent** is software you install on the monitored host that collects data and exposes or sends it. Prometheus `node_exporter`, the Zabbix agent, and the Datadog agent are examples. Agents give rich, detailed data but you must install, update, and secure them on every host.
- **Agentless** monitoring uses something the host already has, usually SSH (run `uptime` remotely) or SNMP. Nothing new to install, but the data is limited to what those protocols expose, and the monitoring server needs credentials.
- **SNMP (Simple Network Management Protocol)** is the classic protocol for polling network devices and servers. A manager *polls* an SNMP agent on UDP port 161 and asks for values. Each value has an **OID (object identifier)**, a dotted number such as `1.3.6.1.2.1.1.5.0` (the host name). A **MIB (Management Information Base)** is a text file that gives names and descriptions to those numbers, so `1.3.6.1.2.1.1.5.0` can be shown as `SNMPv2-MIB::sysName.0`. A **trap** is the opposite direction: the agent sends an unrequested message to the manager on UDP port 162 when something happens (link down, disk full). SNMPv1 and v2c use a plain-text password called a **community string**; SNMPv3 adds real users with authentication and encryption.
- A **webhook** is an HTTP POST, usually with a JSON body, that one system sends to a URL on another system when an event happens. Chat tools, ticketing systems, and paging services all accept webhooks.
- **Log aggregation** means shipping logs from many hosts to one central place, so you can search them together and keep them safe if a host dies or is compromised. On Linux the simplest form is rsyslog forwarding to a central rsyslog server.

**How you react: configurations.** These words are related but not the same:

- **Logging** is recording what happened (to the journal or a log file).
- An **event** is any notable thing that happened ("nginx restarted", "check failed").
- A **threshold** is a limit that turns a measurement into a problem ("disk usage above 80%").
- An **alert** is the decision that a threshold was crossed and a human should care.
- A **notification** is how the alert reaches a human or system: email, `wall` message, chat webhook, pager.

```{.diagram}
  measure            decide              tell someone
 +---------+      +-----------+      +------------------+
 | metric  | ---> | threshold | ---> | alert            |
 | log     |      | crossed?  |      |  -> notification |
 | check   |      +-----------+      |  (wall, webhook, |
 +---------+           |             |   email, pager)  |
      |                no            +------------------+
      v                v
   logging          event only (recorded, nobody paged)
```

A common mistake is alerting on everything. When people get dozens of meaningless alerts a day they start ignoring all of them, including the important one. This is called **alert fatigue**. Good alerts are actionable (someone can do something), tied to user impact (the SLO), and tuned so they rarely fire falsely.

#### Task 1: Define an SLO and build a health check

You will run nginx on ubuntu-lab, define an SLO for it, and measure the SLI with a health check that a systemd timer runs every 15 seconds.

1. Create the lab directory and install nginx and curl.

    ```bash
    mkdir -p ~/labs/5.1 && cd ~/labs/5.1
    sudo apt update
    sudo apt install -y nginx curl
    curl -s -o /dev/null -w '%{http_code} %{time_total}\n' http://localhost/
    ```

    ```{.output}
    200 0.001412
    ```

    ::: explain
    **What just happened:** nginx installs and starts automatically on Ubuntu. The `curl` options: `-s` is silent (no progress bar), `-o /dev/null` throws away the page body, and `-w` (write-out) prints chosen variables after the transfer. `%{http_code}` is the HTTP status code and `%{time_total}` is the total time in seconds. This one line is a complete health check: the service is up (`200`) and fast (1.4 ms).
    :::

2. Write down your service levels. Create a short file so you can refer to it. A **heredoc** (`cat <<'EOF' > file` ... `EOF`) sends all the lines between the markers into the file; the quotes around `EOF` stop the shell from changing `$` signs inside.

    ```bash
    cat <<'EOF' > ~/labs/5.1/service-levels.txt
    Service: lab web site (nginx on ubuntu-lab)
    SLA (promise to customers): 99.5% monthly availability, else service credit
    SLO (internal target):      99.9% of health checks return HTTP 200
    SLI (what we measure):      successful checks / total checks, every 15 s
    Latency SLI:                checks answered in under 0.300 s
    EOF
    cat ~/labs/5.1/service-levels.txt
    ```

    ::: explain
    **What just happened:** You wrote the three levels in the order a team would. The SLO (99.9%) is stricter than the SLA (99.5%) so you get warned before you break the contract. The SLI is defined precisely enough that a script can calculate it.
    :::

3. Create the health check script. Open it with `sudo nano /usr/local/bin/web-healthcheck` or use the heredoc below. `tee` writes its input to the file; `sudo tee` lets you write to a root-owned path.

    ```bash
    cat <<'EOF' | sudo tee /usr/local/bin/web-healthcheck > /dev/null
    #!/bin/bash
    # web-healthcheck: probe the web service once and record the result
    URL="http://localhost/"
    LOG=/var/log/web-health.log
    result=$(curl -s -o /dev/null -w '%{http_code} %{time_total}' \
             --max-time 2 "$URL")
    code=${result%% *}
    secs=${result##* }
    if [ "$code" = "200" ]; then state=UP; else state=DOWN; fi
    echo "$(date -Is) $state $code $secs" >> "$LOG"
    if [ "$state" = "DOWN" ]; then
        logger -t healthcheck -p daemon.err "web check FAILED code=$code url=$URL"
    fi
    EOF
    sudo chmod 755 /usr/local/bin/web-healthcheck
    sudo /usr/local/bin/web-healthcheck
    cat /var/log/web-health.log
    ```

    ```{.output}
    2026-10-10T10:02:11+00:00 UP 200 0.001377
    ```

    ::: explain
    **What just happened:** The script runs one check and appends one line: timestamp, state, status code, response time. `--max-time 2` makes curl give up after 2 seconds, so a hung server counts as a failure instead of hanging the check. `${result%% *}` keeps the text before the first space (the code) and `${result##* }` keeps the text after the last space (the time). If nginx is down, curl prints code `000`. On failure, `logger` writes an **event** into the system log with tag `healthcheck` and priority `daemon.err` (facility `daemon`, severity `err`).
    :::

4. Run the check every 15 seconds with a systemd service and timer. The service says *what* to run; the timer says *when*.

    ```bash
    cat <<'EOF' | sudo tee /etc/systemd/system/web-healthcheck.service
    [Unit]
    Description=Health check for the lab web site

    [Service]
    Type=oneshot
    ExecStart=/usr/local/bin/web-healthcheck
    EOF
    cat <<'EOF' | sudo tee /etc/systemd/system/web-healthcheck.timer
    [Unit]
    Description=Run the web health check every 15 seconds

    [Timer]
    OnBootSec=30s
    OnUnitActiveSec=15s
    AccuracySec=1s

    [Install]
    WantedBy=timers.target
    EOF
    sudo systemctl daemon-reload
    sudo systemctl enable --now web-healthcheck.timer
    systemctl list-timers web-healthcheck.timer
    ```

    ```{.output}
    NEXT                        LEFT LAST                        PASSED UNIT
    Sat 2026-10-10 10:03:01 UTC  9s  Sat 2026-10-10 10:02:46 UTC 5s ago web-healthcheck.timer
    ```

    ::: explain
    **What just happened:** `Type=oneshot` means the service runs once and exits. In the timer, `OnUnitActiveSec=15s` starts the service 15 seconds after it last started, `OnBootSec=30s` starts the first run 30 seconds after boot, and `AccuracySec=1s` stops systemd from batching the run up to a minute late (the default accuracy). `enable --now` starts the timer immediately and at every boot.
    :::

5. Create some downtime so the SLI has something to measure. Wait about a minute, stop nginx for about one minute, then start it again.

    ```bash
    sleep 60; sudo systemctl stop nginx; sleep 60; sudo systemctl start nginx
    tail -n 8 /var/log/web-health.log
    journalctl -t healthcheck --since "10 minutes ago"
    ```

    ```{.output}
    2026-10-10T10:04:16+00:00 UP 200 0.001290
    2026-10-10T10:04:31+00:00 DOWN 000 0.000214
    2026-10-10T10:04:46+00:00 DOWN 000 0.000198
    2026-10-10T10:05:01+00:00 DOWN 000 0.000202
    2026-10-10T10:05:16+00:00 DOWN 000 0.000187
    2026-10-10T10:05:31+00:00 UP 200 0.001544
    Oct 10 10:04:31 ubuntu-lab healthcheck[2210]: web check FAILED code=000 url=http://localhost/
    ```

6. Calculate the availability SLI and the latency SLI with `awk`.

    ```bash
    awk '{ total++ } $2 == "UP" { up++ }
         END { printf "checks=%d up=%d availability=%.2f%%\n", total, up, 100*up/total }' \
         /var/log/web-health.log
    awk '{ total++ } $2 == "UP" && $4 < 0.300 { fast++ }
         END { printf "latency SLI=%.2f%% under 300 ms\n", 100*fast/total }' \
         /var/log/web-health.log
    ```

    ```{.output}
    checks=14 up=10 availability=71.43%
    latency SLI=71.43% under 300 ms
    ```

    ::: explain
    **What just happened:** `awk` reads the log line by line. Field `$2` is the state and `$4` is the response time. It counts all lines, counts the good ones, and prints the percentage at the `END`. Your numbers will differ. Over a short window, one minute of downtime destroys the SLO; over a month, that same minute would use only about 2% of a 99.9% error budget (1 of 43.2 minutes). This is why SLOs are always stated over a time window.
    :::

**Checkpoint:** `systemctl list-timers web-healthcheck.timer` shows the timer, `/var/log/web-health.log` grows by one line every 15 seconds, it contains some `DOWN` lines, and `journalctl -t healthcheck` shows the failure events.

#### Task 2: Thresholds, events, alerts, and notifications

Now build a threshold check for disk usage and load average. It records every run as an event, and only raises an alert (with a notification) when a threshold is crossed.

1. Look at the two raw numbers you will check.

    ```bash
    df --output=pcent / | tail -n 1
    cat /proc/loadavg
    nproc
    ```

    ```{.output}
     23%
    0.08 0.05 0.01 1/187 2380
    2
    ```

    ::: explain
    **What just happened:** `df --output=pcent /` prints only the "use percent" column for the root filesystem; `tail -n 1` drops the header. `/proc/loadavg` holds the 1, 5, and 15-minute load averages (the average number of processes running or waiting). A load equal to the number of CPUs (`nproc`, here 2) means the CPUs are fully busy, so `nproc` is a sensible default load threshold.
    :::

2. Create the threshold script.

    ```bash
    cat <<'EOF' | sudo tee /usr/local/bin/threshold-check > /dev/null
    #!/bin/bash
    # threshold-check: compare disk and load against limits and alert
    DISK_LIMIT=${DISK_LIMIT:-80}           # percent
    LOAD_LIMIT=${LOAD_LIMIT:-$(nproc)}     # 1-minute load average
    WEBHOOK=${WEBHOOK:-}                   # optional URL for notifications

    disk=$(df --output=pcent / | tail -n 1 | tr -dc '0-9')
    load=$(cut -d ' ' -f 1 /proc/loadavg)

    alert() {
        logger -t threshold -p user.warning "ALERT $1"
        wall "ALERT on $(hostname): $1"
        if [ -n "$WEBHOOK" ]; then
            curl -s -X POST -H 'Content-Type: application/json' \
                -d "{\"host\":\"$(hostname)\",\"severity\":\"warning\",\"message\":\"$1\"}" \
                "$WEBHOOK" > /dev/null
        fi
    }

    if [ "$disk" -ge "$DISK_LIMIT" ]; then
        alert "disk / at ${disk}% (limit ${DISK_LIMIT}%)"
    fi
    if awk -v l="$load" -v m="$LOAD_LIMIT" 'BEGIN { exit !(l > m) }'; then
        alert "load ${load} above ${LOAD_LIMIT}"
    fi
    logger -t threshold -p user.info "event: check done disk=${disk}% load=${load}"
    EOF
    sudo chmod 755 /usr/local/bin/threshold-check
    ```

    ::: explain
    **What just happened:** `${DISK_LIMIT:-80}` means "use the variable if it is set, otherwise 80", so you can change limits without editing the script. `tr -dc '0-9'` deletes every character that is not a digit, turning ` 23%` into `23`. Bash cannot compare decimals like `0.08`, so `awk` does the load comparison and sets the exit status. Every run logs an informational **event**; only a crossed threshold calls `alert`, which logs a warning and sends **notifications** with `wall` (a message to every logged-in terminal) and, if configured, a webhook.
    :::

3. Run it with normal limits, then with a deliberately tiny disk limit to force an alert.

    ```bash
    threshold-check
    DISK_LIMIT=1 threshold-check
    journalctl -t threshold --since "5 minutes ago"
    ```

    ```{.output}
    Broadcast message from student@ubuntu-lab (pts/0) (Sat Oct 10 10:12:40 2026):

    ALERT on ubuntu-lab: disk / at 23% (limit 1%)

    Oct 10 10:12:31 ubuntu-lab threshold[2401]: event: check done disk=23% load=0.02
    Oct 10 10:12:40 ubuntu-lab threshold[2412]: ALERT disk / at 23% (limit 1%)
    Oct 10 10:12:40 ubuntu-lab threshold[2415]: event: check done disk=23% load=0.02
    ```

4. Filter the journal by severity. Severity (priority) levels go from `0` (emerg) to `7` (debug); `-p warning` shows warning and anything more severe.

    ```bash
    journalctl -t threshold -p warning --since "5 minutes ago"
    ```

    ::: explain
    **What just happened:** Only the alert line appears, not the routine events. Monitoring systems work the same way: everything is logged, but only high-severity items reach people. If you set `DISK_LIMIT=1` permanently, you would get a `wall` message every run for a condition nobody needs to fix. That is how alert fatigue starts. A good threshold is high enough to be meaningful and low enough to leave time to act (for example, warn at 80%, page at 95%).
    :::

**Checkpoint:** `journalctl -t threshold -p warning` shows exactly one `ALERT` line from the forced test, and you saw the `Broadcast message` from `wall` in your terminal.

#### Task 3: Send alerts with a webhook

Real alerts usually go to a chat or paging system through a webhook. You will run a tiny webhook receiver on ubuntu-lab and point the threshold script at it. (Note: `python3 -m http.server` only answers GET requests, so it cannot receive a webhook. You need a listener that handles POST.)

1. Create a 15-line Python listener.

    ```bash
    cat <<'EOF' > ~/labs/5.1/webhook-listener.py
    #!/usr/bin/env python3
    # Minimal webhook receiver: prints the JSON body of every POST
    import json
    from http.server import BaseHTTPRequestHandler, HTTPServer

    class Hook(BaseHTTPRequestHandler):
        def do_POST(self):
            length = int(self.headers.get("Content-Length", 0))
            body = json.loads(self.rfile.read(length))
            print("WEBHOOK RECEIVED:", body, flush=True)
            self.send_response(200)
            self.end_headers()
            self.wfile.write(b"ok\n")

    HTTPServer(("127.0.0.1", 8099), Hook).serve_forever()
    EOF
    python3 ~/labs/5.1/webhook-listener.py
    ```

    ::: explain
    **What just happened:** `BaseHTTPRequestHandler` calls `do_POST` for each POST request. The handler reads exactly `Content-Length` bytes, parses the JSON, prints it, and answers `200 ok`. It listens only on `127.0.0.1` port 8099, so nothing outside the VM can reach it. Leave it running in this terminal.
    :::

2. Open a **second** SSH session to ubuntu-lab and send a test webhook by hand.

    ```bash
    curl -s -X POST -H 'Content-Type: application/json' \
        -d '{"host":"ubuntu-lab","severity":"info","message":"test"}' \
        http://127.0.0.1:8099/alert
    ```

    In the first terminal you see:

    ```{.output}
    WEBHOOK RECEIVED: {'host': 'ubuntu-lab', 'severity': 'info', 'message': 'test'}
    127.0.0.1 - - [10/Oct/2026 10:20:05] "POST /alert HTTP/1.1" 200 -
    ```

    ::: explain
    **What just happened:** `-X POST` sets the HTTP method, `-H` adds a header telling the receiver the body is JSON, and `-d` supplies the body. This is exactly what Slack, Microsoft Teams, PagerDuty, or a ticketing system would receive.
    :::

3. Trigger a real threshold alert that notifies through the webhook.


#### Task 5: Poll a host with SNMP and learn MIBs

You will make ubuntu-lab an SNMP agent and poll it from rocky-lab with SNMPv2c and SNMPv3.

1. Install the SNMP agent (`snmpd`), the client tools (`snmp`), and the MIB downloader on ubuntu-lab. `snmp-mibs-downloader` comes from the `multiverse` component, which Ubuntu 24.04 enables by default.

    ```bash
    sudo apt install -y snmpd snmp snmp-mibs-downloader
    sudo cp /etc/snmp/snmpd.conf /etc/snmp/snmpd.conf.orig
    ```

2. Replace the agent configuration. The default only listens on localhost and only shows the `system` group. Substitute your lab subnet if it is not `192.168.100.0/24`.

    The file is `/etc/snmp/snmpd.conf`:

    ```bash
    cat <<'EOF' | sudo tee /etc/snmp/snmpd.conf
    # Listen on all IPv4 addresses, UDP port 161
    agentaddress udp:161
    sysLocation  Lab rack 1
    sysContact   student <student@ubuntu-lab>
    # A view is the part of the OID tree a client may read
    view labview included .1.3.6.1.2.1.1
    view labview included .1.3.6.1.2.1.25
    view labview included .1.3.6.1.4.1.2021
    # SNMPv2c: read-only community "labcomm" from the lab subnet only
    rocommunity labcomm 192.168.100.0/24 -V labview
    rocommunity labcomm 127.0.0.1 -V labview
    # SNMPv3: read-only user that must authenticate and encrypt
    rouser labv3 priv -V labview
    EOF
    ```

    ::: explain
    **What just happened:** `agentaddress udp:161` makes snmpd listen on every interface. A `view` limits which branches of the OID tree are visible: `.1.3.6.1.2.1.1` is the `system` group (name, uptime, location), `.1.3.6.1.2.1.25` is HOST-RESOURCES (storage, processes), and `.1.3.6.1.4.1.2021` is the UCD-SNMP group (load averages, memory). `rocommunity` creates a read-only community string that only works from the listed source addresses. `rouser labv3 priv` allows the SNMPv3 user `labv3` read-only access, but only with authentication **and** privacy (encryption).
    :::

3. Create the SNMPv3 user. snmpd reads `createUser` lines from its persistent file at start-up, replaces them with hashed keys, and removes the clear-text passwords.

    ```bash
    sudo systemctl stop snmpd
    echo 'createUser labv3 SHA "AuthPass123" AES "PrivPass123"' | \
        sudo tee -a /var/lib/snmp/snmpd.conf
    sudo systemctl start snmpd
    sudo grep -c createUser /var/lib/snmp/snmpd.conf
    ss -ulnp | grep :161
    ```

    ```{.output}
    0
    UNCONN 0  0   0.0.0.0:161   0.0.0.0:*
    ```

    ::: explain
    **What just happened:** `SHA` is the authentication hash and `AES` is the encryption cipher. The count of `createUser` lines is now `0` because snmpd converted it into a `usmUser` line with localized keys. `ss -ulnp` shows snmpd listening on UDP 161 on all addresses. If `ufw` is active on your VM, also run `sudo ufw allow from 192.168.100.0/24 to any port 161 proto udp`.
    :::

    ::: tip
    The `snmpd` package also ships a helper that does the same job: with snmpd stopped, `sudo net-snmp-create-v3-user -ro -a SHA -A 'AuthPass123' -x AES -X 'PrivPass123' labv3` appends the `createUser` line to `/var/lib/snmp/snmpd.conf` and a `rouser labv3` line to `/etc/snmp/snmpd.conf`. You already wrote a `rouser` line with a view, so the manual method is used here.
    :::

4. Turn on MIB names for the Ubuntu client. Debian and Ubuntu disable MIB loading by default for licensing reasons, so you only see numbers until you comment out the `mibs :` line.

    ```bash
    snmpget -v2c -c labcomm localhost 1.3.6.1.2.1.1.5.0
    sudo sed -i 's/^mibs :/#mibs :/' /etc/snmp/snmp.conf
    snmpget -v2c -c labcomm localhost 1.3.6.1.2.1.1.5.0
    ```

    ```{.output}
    SNMPv2-MIB
    ```

    ::: explain
    **What just happened:** The first answer is just a number (`iso.3.6.1.2.1.1.5.0`). After enabling the MIBs downloaded by `snmp-mibs-downloader`, the same OID is translated to `SNMPv2-MIB::sysName.0`. The standard IETF MIBs live in `/usr/share/snmp/mibs/ietf` and `iana` (links into `/var/lib/mibs`, filled by the downloader); the Net-SNMP ones (`UCD-SNMP-MIB.txt` and others) sit directly in `/usr/share/snmp/mibs`. The MIB changed only how the *client* displays the answer; the agent sent the same data. `snmptranslate -Td SNMPv2-MIB::sysName.0` would print the MIB description of that object.

#### Task 6: Send and receive SNMP traps

Polling asks "how are you?" every few minutes. A trap lets the device shout "something happened!" immediately.

1. Install and configure the trap receiver on ubuntu-lab. The file is `/etc/snmp/snmptrapd.conf`. Ubuntu starts `snmptrapd` with `-LOw` (log only messages of priority *warning* and above), but received traps are logged at priority *info*, so out of the box traps arrive and are silently not logged. A small systemd **drop-in** (an extra file that overrides part of a unit) changes the option to `-LOi`. The empty `ExecStart=` line clears the packaged command before the new one is set.

    ```bash
    sudo apt install -y snmptrapd
    echo 'authCommunity log,execute,net labtrap' | sudo tee /etc/snmp/snmptrapd.conf
    sudo mkdir -p /etc/systemd/system/snmptrapd.service.d
    cat <<'EOF' | sudo tee /etc/systemd/system/snmptrapd.service.d/lab-logging.conf
    [Service]
    ExecStart=
    ExecStart=/usr/sbin/snmptrapd -LOi -f udp:162 udp6:162
    EOF
    sudo systemctl daemon-reload
    sudo systemctl enable --now snmptrapd.socket
    sudo systemctl restart snmptrapd.service
    sudo ss -ulnp | grep :162
    ```

    ```{.output}
    UNCONN 0  0   0.0.0.0:162   0.0.0.0:*   users:(("snmptrapd",pid=3105,fd=3),("systemd",pid=1,fd=60))
    ```

    ::: explain
    **What just happened:** On Ubuntu, `snmptrapd.socket` owns UDP port 162 (**socket activation**: systemd opens the port and hands it to the daemon), which is why `ss` shows both `systemd` and `snmptrapd`. `authCommunity log,execute,net labtrap` says: accept traps that use community `labtrap`, and allow them to be logged, passed to scripts (`execute`), and forwarded (`net`). Traps with any other community are dropped without a log line. `-LOi` sends log messages of priority `info` and above to standard output, which systemd stores in the journal.
    :::

2. Watch the receiver's log in one terminal on ubuntu-lab.

    ```bash
    sudo journalctl -u snmptrapd -f
    ```

3. Send a trap from rocky-lab. This uses an example notification defined in `NET-SNMP-EXAMPLES-MIB` with one variable attached.

    ```bash
    # on rocky-lab
    snmptrap -v2c -c labtrap ubuntu-lab '' \
        NET-SNMP-EXAMPLES-MIB::netSnmpExampleHeartbeatNotification \
        netSnmpExampleHeartbeatRate i 123456
    ```

    On ubuntu-lab you see something like:

    ```{.output}
    snmptrapd[3105]: 2026-10-10 10:48:12 rocky-lab [UDP: [192.168.100.20]:46125->[192.168.100.10]:162]:
    snmptrapd[3105]: DISMAN-EVENT-MIB::sysUpTimeInstance = Timeticks: (1234567) 3:25:45.67
      SNMPv2-MIB::snmpTrapOID.0 = OID: NET-SNMP-EXAMPLES-MIB::netSnmpExampleHeartbeatNotification
      NET-SNMP-EXAMPLES-MIB::netSnmpExampleHeartbeatRate = INTEGER: 123456
    ```

    (snmptrapd prints all the variables on one long line separated by tabs; they are wrapped here to fit the page.)

    ::: explain
    **What just happened:** The arguments are: version, community, destination, then the uptime value (`''` means "use the current uptime"), the trap OID (what kind of event this is), and then variable bindings written as *OID type value* (`i` means integer, `s` would mean string). Real devices send traps like `IF-MIB::linkDown` or vendor traps for fan failures. Stop the journal view with `Ctrl+C`.
    :::

::: tip
Traps use UDP and are fire-and-forget: if the packet is lost, the event is lost. SNMPv2c and v3 also support **informs**, which are traps the receiver must acknowledge (`snmpinform`). This is one reason monitoring systems combine traps with regular polling.
:::

::: checkpoint
**Checkpoint:** `sudo journalctl -u snmptrapd --since "10 minutes ago"` on ubuntu-lab shows the trap from rocky-lab with `netSnmpExampleHeartbeatRate = INTEGER: 123456`.

#### Task 7: Aggregate logs from rocky-lab on ubuntu-lab

You will make ubuntu-lab a central log server and forward all rocky-lab logs to it over TCP port 514.

1. On ubuntu-lab, create a directory for remote logs owned by the `syslog` user (Ubuntu's rsyslog drops root privileges to that user), then add a receiver configuration in `/etc/rsyslog.d/10-remote-in.conf`.

    ```bash
    sudo mkdir -p /var/log/remote
    sudo chown syslog:adm /var/log/remote
    cat <<'EOF' | sudo tee /etc/rsyslog.d/10-remote-in.conf
    # Receive syslog over TCP 514 and write one file per sending host
    template(name="PerHost" type="string" string="/var/log/remote/%HOSTNAME%.log")
    ruleset(name="remote") {
        action(type="omfile" dynaFile="PerHost")
    }
    module(load="imtcp")
    input(type="imtcp" port="514" ruleset="remote")
    EOF
    sudo rsyslogd -N1
    sudo systemctl restart rsyslog
    ss -tlnp | grep :514
    ```

    ```{.output}
    rsyslogd: version 8.2312.0, config validation run (level 1), master config /etc/rsyslog.conf
    rsyslogd: End of config validation run. Bye.
    LISTEN 0  25   0.0.0.0:514   0.0.0.0:*
    ```

    ::: explain
    **What just happened:** `imtcp` is the TCP input module. The `input` binds it to port 514 and sends everything it receives into the ruleset `remote`, so remote messages are kept apart from local ones (they do not end up in `/var/log/syslog`). The `template` builds a file name from the sender's host name, and `dynaFile` uses that template, so each host gets its own file. `rsyslogd -N1` checks the syntax without starting anything; always run it before a restart. If `ufw` is active, run `sudo ufw allow from 192.168.100.0/24 to any port 514 proto tcp`.
    :::

2. On rocky-lab, forward everything to ubuntu-lab. The file is `/etc/rsyslog.d/90-forward.conf`.

    ```bash
    # on rocky-lab
    sudo dnf install -y rsyslog
    cat <<'EOF' | sudo tee /etc/rsyslog.d/90-forward.conf
    # Forward all messages to the central log server over TCP
    *.* action(type="omfwd" target="ubuntu-lab" port="514" protocol="tcp"
               queue.type="linkedList" queue.size="10000"
               action.resumeRetryCount="-1")
    EOF
    sudo rsyslogd -N1
    sudo systemctl restart rsyslog
    logger -t labtest "hello from rocky-lab to the central log server"
    ```

    ::: explain
    **What just happened:** `*.*` selects every facility and every severity. `omfwd` is the forwarding module; `protocol="tcp"` is more reliable than UDP because lost packets are re-sent. The `queue` settings give the action its own memory queue, and `action.resumeRetryCount="-1"` means retry forever, so messages are held, not lost, while the server is unreachable. (In legacy syntax the same rule is `*.* @@ubuntu-lab:514`, where `@@` means TCP and a single `@` means UDP.)
    :::

3. On ubuntu-lab, check that the logs arrived.

    ```bash
    ls -l /var/log/remote/
    sudo tail -n 3 /var/log/remote/rocky-lab.log
    ```

    ```{.output}
    -rw-r----- 1 syslog adm 1873 Oct 10 11:02 rocky-lab.log
    2026-10-10T11:02:15.112345+00:00 rocky-lab systemd[1]: Started System Logging Service.
    2026-10-10T11:02:16.004211+00:00 rocky-lab labtest[4012]: hello from rocky-lab to the central log server
    ```

    ::: tip
    If nothing arrives: on rocky-lab run `journalctl -u rsyslog -n 20` (connection errors) and `sudo ausearch -m avc -ts recent` (SELinux denials). On ubuntu-lab check `journalctl -u rsyslog -n 20`, that port 514 is listening, and that `/var/log/remote` is owned by `syslog`. Test the network path with `nc -zv ubuntu-lab 514` from rocky-lab (`sudo dnf install -y nmap-ncat`). Ubuntu 24.04 also confines rsyslogd with an AppArmor profile; if `sudo journalctl -k | grep -i 'apparmor="DENIED".*rsyslogd'` shows denials for network sockets, add the rules in a local snippet that the profile includes, then restart (the rsyslog unit reloads its profile at start-up): `printf 'network inet stream,\nnetwork inet6 stream,\n' | sudo tee /etc/apparmor.d/rsyslog.d/lab-imtcp` and `sudo systemctl restart rsyslog`. Delete that file in Clean up if you created it.
    :::

4. Prove why central logs matter: search both hosts' events from one place.

    ```bash
    sudo grep -h -i "fail\|error" /var/log/remote/*.log | tail -n 5
    ```

::: explain
**What just happened:** With log aggregation, one search covers every host that forwards to the server. It also protects evidence: an attacker who gains root on rocky-lab can delete its local logs, but the copies already sent to ubuntu-lab remain. Larger shops use the same idea with tools such as the Elastic stack, Graylog, Loki, or Splunk, which add indexing, dashboards, and alerting on top of the collected logs.
:::

### Exam corner

- **SLA** = contract with customers (with penalties); **SLO** = internal target (stricter than the SLA); **SLI** = the actual measurement (for example, % of successful requests).
- Error budget = 100% minus the SLO. 99.9% per 30 days allows about 43 minutes of downtime.
- SNMP agents listen on **UDP 161**; traps go to the manager on **UDP 162**. `snmpget` reads one OID, `snmpwalk` reads a subtree, `snmptrap` sends a trap, `snmptrapd` receives traps.
- A **MIB** maps numeric **OIDs** to names and descriptions. On Ubuntu, `snmp-mibs-downloader` and commenting out `mibs :` in `/etc/snmp/snmp.conf` enable names.
- SNMPv1/v2c use clear-text **community strings**; SNMPv3 adds users with authentication (`-a SHA`) and privacy/encryption (`-x AES`), security level `authPriv`.
- **Agent** monitoring installs software on each host (node_exporter on port 9100, Zabbix agent); **agentless** uses existing protocols (SSH, SNMP, WMI).
- A **webhook** is an HTTP POST (usually JSON) sent to a URL when an event occurs.
- A **health check** is a repeated probe (for example `curl` expecting HTTP 200) used by monitors and load balancers.
- **Log aggregation**: rsyslog `imtcp`/`imudp` on the server, `omfwd` (or `@@host:514` for TCP, `@host:514` for UDP) on clients.
- Threshold crossed leads to an alert, which is delivered as a notification. Too many non-actionable alerts cause **alert fatigue**.
- `logger -t tag -p facility.severity "msg"` writes events to the log; `journalctl -t tag -p warning` filters them.

**Review questions**

1. A company promises customers 99.5% uptime with service credits if it is missed, and internally aims for 99.9%. What is the 99.9% figure?

5. An administrator is paged 40 times a day for CPU spikes that go away on their own, and starts ignoring pages. What is this called, and what is one fix?
6. What is the main trade-off of agent-based monitoring compared with agentless monitoring?

::: answers
1. **C.** The SLO is the internal target; the SLA is the 99.5% contract and the SLI is the measured value.
2. **UDP 162.** Agents are polled on UDP 161 and send traps to the manager on UDP 162.
3. **B.** The data arrived; the client just has no MIB to translate the OID into a name (on Ubuntu, install `snmp-mibs-downloader` and comment out `mibs :`).
4. **B.** `@@` means TCP; a single `@` means UDP.
5. **Alert fatigue.** Fix it by raising the threshold or requiring the condition to last several minutes, and by alerting only on user-impacting, actionable conditions.

:::
