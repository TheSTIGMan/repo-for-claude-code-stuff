## Lab 2.1: Manage Files and Directories {#lab-2-1}

::: labinfo
**Objective:** 2.1 Given a scenario, manage files and directories on a Linux system.\
**Domain:** 2.0 Services and User Management (20% of the exam)\
**Time:** about 90 minutes\
**VM:** ubuntu-lab\
**Snapshot first:** Not required. Everything happens inside `~/labs/2.1` and `/dev/shm`, and the clean-up removes it.
:::

In this lab you build a small project directory tree and then work through every file utility on the exam the way an administrator really uses them: finding files, comparing config versions, checking timestamps, and tracking down which process is holding a file open. You will also see exactly how hard links and symbolic links differ, and take a guided tour of the device files in `/dev`. These commands are the everyday tools of any Linux job, and the exam expects you to pick the right one for a scenario.

### What you'll practice

- Utilities: `cd`, `cp`, `diff`, `file`, `find`, `ln`, `locate`, `ls`, `lsof`, `mkdir`, `mv`, `pwd`, `rm`, `rmdir`, `sdiff`, `stat`, `touch`
- Links: symbolic link, hard link
- Device types in `/dev`: block devices, character devices, special character devices

### How it works

**Everything is a file.** Linux presents almost everything as a file in one big tree that starts at `/` (the *root* directory). Regular files hold data. Directories are files that hold a list of names. Links, devices, sockets, and pipes are also files with special types. The first character of `ls -l` output tells you the type:

| Character | Type |
|---|---|
| `-` | regular file |
| `d` | directory |
| `l` | symbolic link |
| `b` | block device |
| `c` | character device |
| `p` | named pipe (FIFO) |
| `s` | socket |

**Paths.** An *absolute path* starts at `/`, like `/etc/hosts`. A *relative path* starts from your *current working directory* (the directory your shell is "in"), like `project/docs`. Two special names exist in every directory: `.` means "this directory" and `..` means "the parent directory". The `~` character is shell shorthand for your home directory (`/home/student`).

**Inodes: the real identity of a file.** A file on disk has two parts. The *inode* (index node) is a small record that stores everything about the file except its name: owner, permissions, size, timestamps, and where the data blocks live. Each inode has a number that is unique inside its filesystem. The *directory entry* is just a name that points to an inode number. Think of a library: the inode is the catalog card with all the facts about a book, and a directory entry is a label on a shelf that says "card number 1311234".

```{.diagram}
 Directory entries (names)         Inode 1311234                 Data blocks
 ------------------------          ---------------------         -----------
 notes.txt       ---------+------> owner, perms, size,  ------>  "hello..."
 notes-hard.txt  ---------+        timestamps, link count = 2
   (hard link: same inode)

 notes-soft.txt  -> inode 1311240 (type l) contains the TEXT "notes.txt"
   (symbolic link: its own inode that stores a path)
```

This explains the two kinds of links:

- A **hard link** is a second directory entry that points to the *same inode*. Both names are equally "real". The inode keeps a *link count*. The data is only freed when the count drops to zero and no process has the file open. Hard links cannot cross filesystems (inode numbers are only unique inside one filesystem) and you cannot hard-link a directory.
- A **symbolic link** (symlink, soft link) is a tiny separate file whose content is a path to another file. It has its own inode. It can point anywhere, even to another filesystem or to a directory. If the target is deleted, the symlink becomes *dangling* (broken) because the path it stores no longer leads anywhere.

**Three timestamps.** Every inode records:

- **atime** (access): last time the content was read. Ubuntu mounts with `relatime`, so atime is only updated occasionally to save disk writes.
- **mtime** (modify): last time the *content* changed.
- **ctime** (change): last time the *inode* changed (content, permissions, owner, link count, or name). You cannot set ctime by hand.

Many filesystems (ext4, XFS) also record a **birth** (creation) time, which `stat` shows when available.

**Finding files: `find` versus `locate`.** `find` walks the directory tree live, every time, and can test almost anything (name, size, age, owner, permissions) and then run a command on each match. It is always accurate but can be slow on a big tree. `locate` searches a prebuilt database of file names, so it is nearly instant, but it only knows what existed the last time the database was built with `updatedb`. On Ubuntu 24.04 `locate` is provided by the `plocate` package.

**Open files and `lsof`.** When a program opens a file, the kernel gives it a *file descriptor* (a small number). `lsof` ("list open files") shows which processes have which files open. This answers classic admin questions: "Why can't I unmount this disk?" and "I deleted a huge log file, so why is the disk still full?" (Answer: a process still has the deleted file open, so the inode and data are not freed yet.)

**Device files in `/dev`.** Hardware and kernel features appear as special files in `/dev`. They contain no data on disk; reading or writing them talks to a kernel driver. Each device file carries two numbers instead of a size: the **major number** identifies the driver, and the **minor number** identifies which device that driver handles.

- **Block devices** (`b`) move data in fixed-size blocks and allow random access, so you can jump to any position. Disks and partitions are block devices: `/dev/sda`, `/dev/sda1`, `/dev/nvme0n1`.
- **Character devices** (`c`) move data as a stream of bytes, one after another. Terminals and serial ports are character devices: `/dev/tty`, `/dev/ttyS0`.
- **Special character devices** are character devices that are not real hardware at all. The kernel creates them to provide useful behavior: `/dev/null` (throws away everything written to it, returns nothing when read), `/dev/zero` (returns endless zero bytes), `/dev/random` and `/dev/urandom` (return random bytes), and `/dev/full` (always reports "disk full" when written).

#### Task 1: Navigate and build a project tree

You are setting up a working area for a small web application. You will use `pwd`, `cd`, `mkdir`, `ls`, and `touch`.

1. Create the lab directory and move into it.

    ```bash
    mkdir -p ~/labs/2.1 && cd ~/labs/2.1
    pwd
    ```

    ```{.output}
    /home/student/labs/2.1
    ```

    ::: explain
    **What just happened:** `mkdir` makes a directory. The `-p` (parents) option creates any missing parent directories along the way (`~/labs` and then `~/labs/2.1`) and does not complain if they already exist. `&&` runs the second command only if the first succeeded. `cd` (change directory) moves your shell into the new directory, and `pwd` (print working directory) shows the absolute path of where you are now.
    :::

2. Practice moving around. Run each line and watch the output of `pwd`.

    ```bash
    cd /etc
    pwd
    cd ..
    pwd
    cd -
    cd
    pwd
    cd ~/labs/2.1
    ```

    ::: explain
    **What just happened:** `cd /etc` uses an absolute path. `cd ..` moves up one level to `/`. `cd -` jumps back to the previous directory (`/etc`) and prints its name. `cd` with no argument takes you home (`/home/student`). The last line returns you to the lab directory using `~` for home.
    :::

3. Build the whole project tree in one command using *brace expansion*.

    ```bash
    mkdir -p webapp/{src,docs,config,logs,backup}
    ls
    ls webapp
    ```

    ```{.output}
    webapp
    backup  config  docs  logs  src
    ```

    ::: explain
    **What just happened:** The shell expands `webapp/{src,docs,config,logs,backup}` into five separate arguments (`webapp/src`, `webapp/docs`, and so on) before `mkdir` runs. `mkdir -p` then creates `webapp` and the five subdirectories. Brace expansion is a shell feature, so it works with any command.
    :::

4. Create some empty files with `touch`, then add content to a few.

    ```bash
    touch webapp/src/{app.py,utils.py,models.py}
    touch webapp/docs/README.md webapp/logs/app.log
    echo "print('hello')" > webapp/src/app.py
    echo "Project notes" > webapp/docs/notes.txt
    ```

    ::: explain
    **What just happened:** `touch` creates a file if it does not exist (and updates its timestamps if it does). `echo "text" > file` writes text into a file, replacing anything already there. You will learn more about `touch` and timestamps in Task 4.
    :::

5. List the tree in several useful ways.

    ```bash
    ls -l webapp
    ls -la webapp/src
    ls -lh webapp/docs
    ls -R webapp
    ls -ld webapp
    ls -lt webapp/src
    ```

    ```{.output}
    total 20
    drwxrwxr-x 2 student student 4096 Oct 10 10:02 backup
    drwxrwxr-x 2 student student 4096 Oct 10 10:02 config
    drwxrwxr-x 2 student student 4096 Oct 10 10:03 docs
    drwxrwxr-x 2 student student 4096 Oct 10 10:03 logs
    drwxrwxr-x 2 student student 4096 Oct 10 10:03 src
    ```

::: explain
**What just happened:** `ls -l` gives the *long listing*: type and permissions (`drwxrwxr-x`), link count, owner, group, size, modification time, and name. `-a` shows *all* files, including hidden ones whose names start with a dot (you will see `.` and `..`). `-h` prints sizes in human-readable units (K, M, G). `-R` lists recursively into every subdirectory. `-d` lists the directory itself instead of its contents. `-t` sorts by modification time, newest first.

#### Task 2: Copy, move, rename, and remove

Now you reorganize the project with `cp`, `mv`, `rm`, and `rmdir`.

1. Create a config file and make a backup copy of it.

    ```bash
    cd ~/labs/2.1/webapp
    printf 'port=8080\nworkers=4\ndebug=false\nlog_level=info\n' > config/app.conf
    cp config/app.conf backup/app.conf.bak
    cp -p config/app.conf backup/app.conf.preserved
    ls -l config backup
    ```

    ::: explain
    **What just happened:** `printf` writes text and turns each `\n` into a new line, so `app.conf` gets four lines. `cp SOURCE DEST` copies a file. A plain copy gets a new modification time (now). `cp -p` *preserves* the mode, ownership, and timestamps of the original, which matters for backups because you want to know when the original last changed.
    :::

2. Copy a whole directory. `cp` refuses to copy a directory unless you ask for recursion.

    ```bash
    cp src backup/
    cp -r src backup/src-copy
    cp -a docs backup/docs-archive
    ls backup
    ```

    ```{.output}
    cp: -r not specified; omitting directory 'src'
    app.conf.bak  app.conf.preserved  docs-archive  src-copy
    ```

    ::: explain
    **What just happened:** The first `cp` failed with a clear message. `-r` (recursive) copies a directory and everything inside it. `-a` (archive) is the same as `-dR --preserve=all`: recursive, keeps symlinks as symlinks, and preserves permissions, ownership, and timestamps. Use `-a` when you want an exact copy.
    :::

3. Use `mv` to rename a file and to move files into another directory.

    ```bash
    mv docs/notes.txt docs/project-notes.txt
    mv src/models.py src/utils.py backup/src-copy/
    ls docs src
    ```

    ::: explain
    **What just happened:** `mv` both renames and moves. With two names in the same directory it renames. With a directory as the last argument it moves all the earlier arguments into that directory. Inside one filesystem `mv` is instant because it only rewrites directory entries; the inode and data do not move. The original `utils.py` already existed in `backup/src-copy` from the `cp -r`, so `mv` silently replaced it. Add `-i` (interactive) to be asked before overwriting.
    :::

4. Try the safe, interactive versions. Answer `n` to each prompt.

    ```bash
    cp -i config/app.conf backup/app.conf.bak
    mv -i backup/app.conf.preserved backup/app.conf.bak
    ```

    ```{.output}
    cp: overwrite 'backup/app.conf.bak'? n
    mv: overwrite 'backup/app.conf.bak'? n
    ```

5. Remove files and directories. Start with an empty directory, then a non-empty one.

    ```bash
    mkdir -p tmp/a/b/c
    rmdir tmp/a/b/c
    rmdir -p tmp/a/b
    rmdir backup
    ```

    ```{.output}
    rmdir: failed to remove 'backup': Directory not empty
    ```

    ::: explain
    **What just happened:** `rmdir` only removes *empty* directories, which makes it a safe choice: it can never delete files by accident. `rmdir -p tmp/a/b` removes `b`, then `a`, then `tmp`, as long as each becomes empty. It refused to remove `backup` because it still has contents.
    :::

6. Use `rm` for files and non-empty directories.

    ```bash
    rm -i backup/app.conf.preserved
    rm -r backup/docs-archive
    ls backup
    ```

    ::: explain
    **What just happened:** `rm` removes files (it deletes directory entries; the data is freed when the link count reaches zero). `-i` asks for confirmation (answer `y`). `-r` removes a directory and everything under it. You will often see `rm -rf`, where `-f` (force) never prompts and ignores missing files. There is no recycle bin on the command line, so double-check paths before using `-rf`.
    :::

::: warning
`rm -rf` with a typo can destroy a system. A classic mistake is a stray space: `rm -rf / home/olduser` deletes from `/`. Modern GNU `rm` refuses to operate on `/` itself unless you add `--no-preserve-root`, but it will happily delete any other directory you name. Run `ls` on the exact path first.
:::

::: checkpoint
**Checkpoint:** `ls ~/labs/2.1/webapp/backup` shows `app.conf.bak` and `src-copy`. `ls ~/labs/2.1/webapp/src` shows only `app.py`, and `~/labs/2.1/webapp/tmp` no longer exists.
:::

#### Task 3: Identify files with `file` and inspect them with `stat`

File names in Linux do not have to have extensions, and an extension can lie. The `file` command looks inside a file to see what it really is.

1. Run `file` on several kinds of objects.

    ```bash
    cd ~/labs/2.1
    cp /usr/bin/ls ./mystery
    gzip -k webapp/config/app.conf
    file mystery webapp/config/app.conf webapp/config/app.conf.gz
    file /bin /etc /dev/sda /dev/null webapp/src/app.py
    ```

    ```{.output}
    mystery:                    ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV),
                                dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, ...
    webapp/config/app.conf:     ASCII text
    webapp/config/app.conf.gz:  gzip compressed data, was "app.conf", ...
    /bin:                       symbolic link to usr/bin
    /etc:                       directory
    /dev/sda:                   block special (8/0)
    /dev/null:                  character special (1/3)
    webapp/src/app.py:          ASCII text
    ```

    ::: explain
    **What just happened:** `file` reads the first bytes of each file and compares them to a database of known patterns called *magic numbers*. The file `mystery` has no extension, but `file` recognizes it as an ELF executable (the Linux program format). `gzip -k` compressed a copy while keeping (`-k`) the original. On Ubuntu 24.04, `/bin` is a symbolic link to `usr/bin`. For devices, `file` shows the type and the major/minor numbers. If your disk is `vda` or `nvme0n1`, `/dev/sda` will say "cannot open"; that is fine. `app.py` is reported as plain text because it has no `#!` line; with `#!/usr/bin/env python3` as its first line, `file` would call it a Python script.
    :::

2. Look at the full inode details of a file with `stat`.

    ```bash
    stat webapp/config/app.conf
    ```

    ```{.output}
      File: webapp/config/app.conf
      Size: 46        	Blocks: 8          IO Block: 4096   regular file
    Device: 252,0	Inode: 1311290     Links: 1
    Access: (0664/-rw-rw-r--)  Uid: ( 1000/ student)   Gid: ( 1000/ student)
    Access: 2026-10-10 10:05:12.418263510 +0000
    Modify: 2026-10-10 10:05:12.418263510 +0000
    Change: 2026-10-10 10:05:12.418263510 +0000
     Birth: 2026-10-10 10:05:12.418263510 +0000
    ```

    ::: explain
    **What just happened:** `stat` prints the inode contents. **Size** is in bytes; **Blocks** is the number of 512-byte units allocated. **Device** is the filesystem the file lives on (major,minor). **Inode** is the inode number and **Links** is the hard link count. **Access** shows permissions in octal (`0664`) and symbolic form, plus the owner UID and group GID. Then the three timestamps (atime, mtime, ctime) and the birth time. Your inode number and device will differ.
    :::

3. `stat` can also print just the fields you want, which is handy in scripts.

    ```bash
    stat -c '%n  inode=%i  links=%h  size=%s  mode=%a  owner=%U' webapp/config/app.conf
    stat -f /
    ```

    ::: explain
    **What just happened:** `-c` (format) prints a custom line: `%n` name, `%i` inode, `%h` hard links, `%s` size, `%a` octal permissions, `%U` owner name. `stat -f` shows information about the *filesystem* instead of a file: type (for example `ext2/ext3` for ext4), block size, and free blocks and inodes.
    :::

::: checkpoint
**Checkpoint:** `file ~/labs/2.1/mystery` reports an ELF executable, and `stat -c %h ~/labs/2.1/webapp/config/app.conf` prints `1`.
:::

#### Task 4: Control timestamps with `touch`

Backup and clean-up scripts often decide what to do based on file age. To test them you need files with old timestamps, and `touch` can create those.

1. Create a set of log files and give them different ages.

    ```bash
    cd ~/labs/2.1/webapp/logs
    touch -d "2024-01-15 09:30" old-jan.log
    touch -d "10 days ago" ten-days.log
    touch -t 202510010800 oct-first.log
    touch today.log
    ls -l --time-style=long-iso
    ```

    ```{.output}
    total 0
    -rw-rw-r-- 1 student student 0 2026-10-10 10:03 app.log
    -rw-rw-r-- 1 student student 0 2024-01-15 09:30 old-jan.log
    -rw-rw-r-- 1 student student 0 2025-10-01 08:00 oct-first.log
    -rw-rw-r-- 1 student student 0 2026-09-30 10:10 ten-days.log
    -rw-rw-r-- 1 student student 0 2026-10-10 10:10 today.log
    ```

    ::: explain
    **What just happened:** `touch -d STRING` sets the atime and mtime to a date described in almost plain English (`"10 days ago"`, `"yesterday"`, `"2024-01-15 09:30"`). `touch -t` uses the compact format `[[CC]YY]MMDDhhmm[.ss]`, so `202510010800` means 2025-10-01 08:00. `--time-style=long-iso` makes `ls` show full dates. Your dates will be relative to today.
    :::

2. Change only one timestamp, and observe that ctime cannot be faked.

    ```bash
    touch -a -d "2020-06-01" today.log
    stat today.log | grep -E 'Access: [0-9]|Modify|Change'
    ```

    ```{.output}
    Access: 2020-06-01 00:00:00.000000000 +0000
    Modify: 2026-10-10 10:10:41.120093114 +0000
    Change: 2026-10-10 10:11:02.551876020 +0000
    ```

    ::: explain
    **What just happened:** `touch -a` changes only the access time; `touch -m` changes only the modification time. Changing a timestamp is itself a change to the inode, so **ctime** jumped to *now*. There is no option to set ctime, which is why investigators trust it more than mtime.
    :::

::: checkpoint
**Checkpoint:** `ls -lt ~/labs/2.1/webapp/logs` lists `old-jan.log` last (oldest modification time).
:::

#### Task 5: Find files with `find` and `locate`

1. Find by name. `find` takes a starting directory, then tests, then an optional action.

    ```bash
    cd ~/labs/2.1
    find . -name "*.log"
    find webapp -iname "readme*"
    find webapp -type d
    find webapp -type f -name "*.py"
    ```

    ::: explain
    **What just happened:** `find .` searches from the current directory down. `-name "*.log"` matches names with a shell-style pattern; always quote the pattern so your shell does not expand `*` first. `-iname` is case-insensitive. `-type d` matches directories and `-type f` regular files (`-type l` matches symlinks). Tests placed one after another are joined with AND.
    :::

2. Find by time. Use the log files you aged in Task 4.

    ```bash
    find webapp/logs -mtime +7
    find webapp/logs -mtime -1
    find webapp -mmin -30 -type f
    ```

    ::: explain
    **What just happened:** `-mtime` counts in 24-hour days. `+7` means "modified more than 7 days ago", `-1` means "modified less than 1 day ago". `-mmin` works the same way in minutes. `-atime` and `-ctime` test the other two timestamps. This is how log clean-up jobs pick old files.
    :::

3. Find by size. Make a large file first.

    ```bash
    dd if=/dev/zero of=webapp/backup/big.img bs=1M count=50 status=none
    find . -size +10M
    find . -type f -size 0
    find . -type f -empty
    ```

    ::: explain
    **What just happened:** `dd` copied 50 blocks of 1 MiB from `/dev/zero`, making a 50 MiB file (more on `/dev/zero` in Task 8). `-size +10M` finds files bigger than 10 MiB; suffixes are `k`, `M`, and `G`. `-size 0` and `-empty` both find empty files (`-empty` also matches empty directories, but `-type f` limits it to files here).
    :::

4. Find by permissions and owner. Search system directories as well; send errors to `/dev/null`.

    ```bash
    chmod 777 webapp/config/app.conf
    find webapp -perm 777
    find webapp -perm -o=w
    find /usr/bin -perm -4000 2>/dev/null
    find /etc -user student 2>/dev/null
    find /var/log -group adm -name "*.log" 2>/dev/null | head
    ```

    ::: explain
    **What just happened:** `-perm 777` matches *exactly* mode 777. `-perm -o=w` (with a leading dash) matches files that have *at least* the "others can write" bit, which is the usual way to hunt for world-writable files. `-perm -4000` finds *setuid* programs (like `passwd`), a common security audit. `-user` and `-group` match the owner. `2>/dev/null` hides "Permission denied" errors from directories you cannot read. The `/etc -user student` search probably prints nothing, which is the expected result.
    :::

5. Act on the results with `-exec`, `-delete`, and `-ok`.

    ```bash
    find webapp -name "*.py" -exec ls -l {} \;
    find webapp -name "*.py" -exec wc -l {} +
    find webapp/logs -name "*.log" -mtime +7 -ok rm {} \;
    find webapp -perm 777 -exec chmod 644 {} \;
    find webapp/logs -mtime +7
    ```

    ::: explain
    **What just happened:** `-exec COMMAND {} \;` runs the command once per match, replacing `{}` with the file name; the `\;` (escaped semicolon) marks the end of the command. Ending with `+` instead passes many file names to a single command, which is faster. `-ok` is like `-exec` but asks `y/n` for each file (answer `y` to delete the old logs). The last line confirms that no logs older than 7 days remain. `-delete` also exists and removes every match without asking, so test the `find` without it first.
    :::

6. Install `plocate` and compare `locate` with `find`.

    ```bash
    sudo apt update
    sudo apt install -y plocate
    locate app.conf
    sudo updatedb
    locate app.conf
    locate -c "*.conf"
    locate -i readme.md | head -5
    ```

    ```{.output}
    /home/student/labs/2.1/webapp/backup/app.conf.bak
    /home/student/labs/2.1/webapp/config/app.conf
    /home/student/labs/2.1/webapp/config/app.conf.gz
    ```

    ::: explain
    **What just happened:** On Ubuntu 24.04 the `locate` command comes from the `plocate` package, which also provides `updatedb`. The first `locate app.conf` probably found nothing in your lab directory because the database was built before you created those files. `sudo updatedb` rebuilds the database (stored in `/var/lib/plocate/plocate.db`). After that, `locate` finds the files instantly. `-c` counts matches instead of listing them, and `-i` ignores case. A systemd timer (`plocate-updatedb.timer`) rebuilds the database daily. `locate` only shows you files you have permission to see.
    :::

7. Prove that `locate` can be out of date.

    ```bash
    rm webapp/config/app.conf.gz
    locate app.conf.gz
    find ~ -name app.conf.gz
    ```

    ::: explain
    **What just happened:** `locate` still lists the deleted file because the database is stale, while `find` correctly finds nothing. Rule of thumb: use `locate` for a fast "where is that file?" search, and `find` when you need accurate, current results or tests beyond the name.
    :::

::: tip
On Rocky Linux 9, `locate` comes from the `mlocate` package (`sudo dnf install -y mlocate`), and you run `sudo updatedb` the same way.
:::

**Checkpoint:** `find ~/labs/2.1 -size +10M` prints `big.img`, `find ~/labs/2.1/webapp -perm 777` prints nothing, and `locate -c app.conf.bak` prints `1`.

#### Task 6: Compare files with `diff` and `sdiff`

A colleague edited the application config, and you need to see exactly what changed.

1. Create a second version of the config file.

    ```bash
    cd ~/labs/2.1/webapp/config
    printf 'port=8080\nworkers=4\ndebug=false\nlog_level=info\n' > app.conf
    printf 'port=8443\nworkers=4\nlog_level=debug\ntls=on\n' > app.conf.new
    ```

2. Compare them with plain `diff`.

    ```bash
    diff app.conf app.conf.new
    ```

    ```{.output}
    1c1
    < port=8080
    ---
    > port=8443
    3,4c3,4
    < debug=false
    < log_level=info
    ---
    > log_level=debug
    > tls=on
    ```

    ::: explain
    **What just happened:** `diff` prints instructions for turning the first file into the second. `1c1` means "line 1 of the first file must be **c**hanged into line 1 of the second". `3,4c3,4` means lines 3 to 4 change into lines 3 to 4. Other letters are `a` (add) and `d` (delete). Lines starting with `<` come from the first file, lines with `>` from the second. If the files are identical, `diff` prints nothing and exits with status 0.
    :::

3. Use the *unified* format, which is what patches and `git` use.

    ```bash
    diff -u app.conf app.conf.new
    diff -q app.conf app.conf.new
    diff -r ../src ../backup/src-copy
    ```

    ```{.output}
    --- app.conf	2026-10-10 10:20:01.000000000 +0000
    +++ app.conf.new	2026-10-10 10:20:01.000000000 +0000
    @@ -1,4 +1,4 @@
    -port=8080
    +port=8443
     workers=4
    -debug=false
    -log_level=info
    +log_level=debug
    +tls=on
    ```

    ::: explain
    **What just happened:** `-u` shows changes with a few lines of context: `-` lines are removed, `+` lines are added, and lines starting with a space are unchanged. The `@@ -1,4 +1,4 @@` header gives the line ranges. `-q` (quiet) only reports *whether* files differ. `-r` compares two directory trees recursively and reports files that exist in only one of them ("Only in ...").
    :::

4. View the two versions side by side with `sdiff`.


    ```{.output}
    debug=false                       |	log_level=debug
    ```

    ::: explain
    **What just happened:** `sdiff` prints the first file on the left and the second on the right. The middle column marks each line: `|` means the lines differ, `<` means the line is only in the left file, `>` only in the right file, and a blank means identical. `-w 70` sets the total width in characters. `-s` suppresses identical lines so you only see differences. #### Task 7: Hard links and symbolic links

1. Create a file and one link of each type, then compare inode numbers.

    ```bash
    mkdir -p ~/labs/2.1/links && cd ~/labs/2.1/links
    echo "original content" > notes.txt
    ln notes.txt notes-hard.txt
    ln -s notes.txt notes-soft.txt
    ls -li
    ```

    ```{.output}
    total 8
    1311301 -rw-rw-r-- 2 student student 17 Oct 10 10:25 notes-hard.txt
    1311302 lrwxrwxrwx 1 student student  9 Oct 10 10:25 notes-soft.txt -> notes.txt
    1311301 -rw-rw-r-- 2 student student 17 Oct 10 10:25 notes.txt
    ```

    ::: explain
    **What just happened:** `ln TARGET LINKNAME` creates a hard link; `ln -s TARGET LINKNAME` creates a symbolic link. `ls -i` adds the inode number in the first column. `notes.txt` and `notes-hard.txt` share inode `1311301`, and the link count (third column) is `2` for both: they are two names for the same file. `notes-soft.txt` has its own inode, type `l`, permissions `rwxrwxrwx` (symlink permissions are never used; the target's permissions apply), and a size of 9, which is the length of the text `notes.txt` it stores.
    :::

2. Confirm with `stat`, and edit through each name.

    ```bash
    stat -c '%n inode=%i links=%h type=%F' notes.txt notes-hard.txt notes-soft.txt
    echo "added via hard link" >> notes-hard.txt
    echo "added via soft link" >> notes-soft.txt
    cat notes.txt
    readlink notes-soft.txt
    ```

    ```{.output}
    notes.txt inode=1311301 links=2 type=regular file
    notes-hard.txt inode=1311301 links=2 type=regular file
    notes-soft.txt inode=1311302 links=1 type=symbolic link
    original content
    added via hard link
    added via soft link
    ```

    ::: explain
    **What just happened:** Writing through either link changes the same data, so `cat notes.txt` shows both new lines. Writing through a symlink follows it to the target. `>>` appends instead of overwriting. `readlink` prints the path a symlink stores.
    :::

3. Delete the original and see what happens to each link.

    ```bash
    rm notes.txt
    ls -li
    cat notes-hard.txt
    cat notes-soft.txt
    ```

    ```{.output}
    1311301 -rw-rw-r-- 1 student student 57 Oct 10 10:26 notes-hard.txt
    1311302 lrwxrwxrwx 1 student student  9 Oct 10 10:25 notes-soft.txt -> notes.txt
    original content
    added via hard link
    added via soft link
    cat: notes-soft.txt: No such file or directory
    ```

    ::: explain
    **What just happened:** Removing `notes.txt` only removed one name. The inode's link count dropped from 2 to 1, so the data survives and `notes-hard.txt` still works. The symlink still contains the text `notes.txt`, but nothing has that name any more, so it is now *dangling* (`ls` shows it in red on a color terminal). Recreate the target and the symlink works again:
    :::

    ```bash
    echo "brand new file" > notes.txt
    cat notes-soft.txt
    find . -xtype l
    rm notes.txt
    find . -xtype l
    ```

    ::: explain
    **What just happened:** The symlink now points at the *new* `notes.txt`, a completely different inode. `find -xtype l` lists broken symlinks, a useful clean-up check (the first run prints nothing, the second prints `./notes-soft.txt`).
    :::

4. Try links to a directory and across filesystems. `/dev/shm` is a separate in-memory filesystem (tmpfs).

    ```bash
    mkdir projdir
    ln projdir projdir-hard
    ln -s ~/labs/2.1/webapp/config confdir
    ls -l confdir/
    ln notes-hard.txt /dev/shm/cross-hard.txt
    ln -s ~/labs/2.1/links/notes-hard.txt /dev/shm/cross-soft.txt
    cat /dev/shm/cross-soft.txt
    df -h . /dev/shm | awk '{print $1, $6}'
    ```

    ```{.output}
    ln: projdir: hard link not allowed for directory
    ln: failed to create hard link '/dev/shm/cross-hard.txt' => 'notes-hard.txt':
    Invalid cross-device link
    ```

    ::: explain
    **What just happened:** You cannot hard-link a directory (it could create loops in the tree). You can symlink a directory: `confdir` acts like a shortcut to the config directory. The trailing `/` in `ls -l confdir/` makes `ls` follow the link and list the contents. A hard link to `/dev/shm` fails with "Invalid cross-device link" because inode numbers only make sense inside one filesystem. A symlink across filesystems works fine because it just stores a path. `df` shows the two paths are on different filesystems.
    :::

5. Notice relative versus absolute symlinks, and how `pwd` reports a path reached through a symlink.

    ```bash
    cd confdir
    pwd
    pwd -P
    cd ~/labs/2.1/links
    ```

    ```{.output}
    /home/student/labs/2.1/links/confdir
    /home/student/labs/2.1/webapp/config
    ```

    ::: explain
    **What just happened:** `pwd` shows the *logical* path, including the symlink you walked through. `pwd -P` shows the *physical* path with all symlinks resolved. A symlink created with a relative target (like `notes.txt`) is resolved relative to the directory the link lives in, so it breaks if you move the link somewhere else. An absolute target (like `confdir`'s) keeps working wherever the link is moved.

A symbolic link has its own inode, can span filesystems and point to directories, and breaks when its target is removed. `ls -li` and `stat` show inode numbers and link counts.

#### Task 8: Find open files with `lsof`

1. Install `lsof` (it is usually already present) and look at the files your own shell has open.

    ```bash
    sudo apt install -y lsof
    lsof -p $$
    ```

    ```{.output}
    COMMAND  PID    USER   FD   TYPE DEVICE SIZE/OFF    NODE NAME
    bash    1532 student  cwd    DIR  252,0     4096 1311300 /home/student/labs/2.1/links
    bash    1532 student  rtd    DIR  252,0     4096       2 /
    bash    1532 student  txt    REG  252,0  1446024  786563 /usr/bin/bash
    bash    1532 student    0u   CHR  136,0      0t0       3 /dev/pts/0
    bash    1532 student    1u   CHR  136,0      0t0       3 /dev/pts/0
    bash    1532 student    2u   CHR  136,0      0t0       3 /dev/pts/0
    ...
    ```

    ::: explain
    **What just happened:** `$$` is a shell variable holding the PID (process ID) of your current shell, and `-p` limits `lsof` to that process. Columns: **COMMAND** and **PID** identify the process. **FD** is the file descriptor: `cwd` is the current working directory, `rtd` the root directory, `txt` the program file, and numbers like `0u`, `1u`, `2u` are standard input, output, and error (`u` means open for read and write). **TYPE** shows `DIR`, `REG` (regular file), or `CHR` (character device; your terminal `/dev/pts/0`).
    :::

2. Scenario: "I can't remove or unmount this directory because something is using it." Start a background process that sits inside a directory, then find it.

    ```bash
    (cd ~/labs/2.1/webapp/logs && sleep 600) &
    lsof +D ~/labs/2.1/webapp
    ```

    ```{.output}
    COMMAND  PID    USER  FD   TYPE DEVICE SIZE/OFF    NODE NAME
    sleep   1688 student cwd    DIR  252,0     4096 1311279 /home/student/labs/2.1/webapp/logs
    ```

    ::: explain
    **What just happened:** The parentheses run a *subshell* that changes into `logs` and then runs `sleep 600` in the background (`&`). `lsof +D DIR` searches the whole directory tree for anything open, including processes whose current directory is inside it. This is exactly how you find what is keeping a filesystem busy before `umount`. `lsof DIRNAME` without `+D` checks only that one directory.
    :::

3. Scenario: "I deleted a huge log file but the disk space did not come back." Create a 200 MB log file and hold it open with `tail -f`.

    ```bash
    cd ~/labs/2.1

    tail -f huge.log > /dev/null &
    df -h /
    rm huge.log
    df -h /
    ```

    ::: explain
    **What just happened:** `tail -f` keeps the file open, waiting for new lines. After `rm`, the name is gone, but the second `df -h /` shows the *same* used space as before, because the inode still has an open file descriptor. The kernel frees the data only when the link count is 0 **and** no process has it open.
    :::

4. Find the deleted-but-open file and release the space.

    **What just happened:** `lsof +L1` lists open files with a link count less than 1, which means files that were deleted but are still open. #### Task 9: Tour the device files in `/dev`

1. List block and character devices side by side.

    ```bash
    lsblk
    ls -l /dev/sd* /dev/vd* /dev/nvme* 2>/dev/null
    ls -l /dev/null /dev/zero /dev/random /dev/urandom /dev/full /dev/tty
    ```

    ```{.output}
    brw-rw---- 1 root disk 8,  0 Oct 10 09:01 /dev/sda
    brw-rw---- 1 root disk 8,  1 Oct 10 09:01 /dev/sda1
    brw-rw---- 1 root disk 8, 16 Oct 10 09:01 /dev/sdb
    brw-rw---- 1 root disk 8, 32 Oct 10 09:01 /dev/sdc
    crw-rw-rw- 1 root root 1, 7 Oct 10 09:01 /dev/full
    crw-rw-rw- 1 root root 1, 3 Oct 10 09:01 /dev/null
    crw-rw-rw- 1 root root 1, 8 Oct 10 09:01 /dev/random
    crw-rw-rw- 1 root tty  5, 0 Oct 10 09:01 /dev/tty
    crw-rw-rw- 1 root root 1, 9 Oct 10 09:01 /dev/urandom
    crw-rw-rw- 1 root root 1, 5 Oct 10 09:01 /dev/zero
    ```

    ::: explain
    **What just happened:** `lsblk` lists your disks so you know their names (they may be `vda` or `nvme0n1` instead of `sda`). In `ls -l`, disks start with `b` (**block device**) and are owned by group `disk`. The others start with `c` (**character device**). Where the file size normally appears you see two numbers: **major, minor**. All the SCSI/SATA disks share major `8` (the `sd` driver); the minor number picks the disk and partition (each disk gets 16 minors: `sda`=0, `sdb`=16). Major `1` is the kernel's "memory" driver, which provides the special character devices: minor `3` is null, `5` zero, `7` full, `8` random, `9` urandom.
    :::

2. See which drivers own which major numbers, and count device types.

    ```bash
    grep -A8 'Character devices' /proc/devices
    grep -A8 'Block devices' /proc/devices
    find /dev -maxdepth 1 -type b | wc -l
    find /dev -maxdepth 1 -type c | wc -l
    ```

    ::: explain
    **What just happened:** `/proc/devices` lists registered drivers and their major numbers in two sections (for example `1 mem`, `5 /dev/tty`, `136 pts`, `8 sd`). `find -type b` and `-type c` match block and character device files. Most of `/dev` is character devices.
    :::

3. Use `/dev/null`, the "black hole".

    ```bash
    echo "nobody will see this" > /dev/null
    cat /dev/null | wc -c
    ls /root 2>/dev/null; echo "exit status: $?"
    cp /dev/null ~/labs/2.1/webapp/logs/app.log
    ```

    ::: explain
    **What just happened:** Anything written to `/dev/null` is discarded, and reading it returns end-of-file immediately (0 bytes). Its main use is hiding output you do not want, like the error from `ls /root` (you still get the exit status). Copying `/dev/null` over a file empties it, a quick way to truncate a log.
    :::

4. Use `/dev/zero` and `/dev/full`.

    ```bash
    head -c 16 /dev/zero | od -An -tx1
    dd if=/dev/zero of=~/labs/2.1/zeros.bin bs=1M count=5 status=none
    ls -lh ~/labs/2.1/zeros.bin
    echo test > /dev/full
    ```

    ```{.output}
     00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
    -rw-rw-r-- 1 student student 5.0M Oct 10 10:40 /home/student/labs/2.1/zeros.bin
    -bash: echo: write error: No space left on device
    ```

    ::: explain
    **What just happened:** `/dev/zero` returns as many zero bytes as you read. `head -c 16` takes 16 bytes and `od -An -tx1` dumps them as hex. With `dd` it creates files of a known size or wipes a disk. `/dev/full` always fails writes with "No space left on device", which developers use to test how programs handle a full disk.
    :::

5. Use `/dev/urandom` and `/dev/random`.

    ```bash
    head -c 16 /dev/urandom | od -An -tx1
    head -c 12 /dev/random | base64
    tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 20; echo
    ```

    ::: explain
    **What just happened:** Both devices return random bytes from the kernel's cryptographic random generator. The last line keeps only letters and digits from the random stream and takes 20 of them, a quick random password. Historically `/dev/random` *blocked* (paused) when the kernel estimated it was low on randomness, while `/dev/urandom` never blocks. Since kernel 5.6 `/dev/random` only blocks very early at boot, before the generator is ready; on a running system both behave the same.
    :::

6. Use `/dev/tty`, which always means "the terminal of the current process".

    ```bash
    tty
    echo "hello terminal" > /dev/tty
    echo "hidden" > /dev/null; echo "shown anyway" 2>/dev/null > /dev/tty
    ```

    ```{.output}
    /dev/pts/0
    hello terminal
    shown anyway
    ```

    ::: explain
    **What just happened:** `tty` prints the device file of your terminal. Over SSH this is a *pseudo-terminal* like `/dev/pts/0` (character device, major 136). `/dev/tty` is a special alias that always points to whatever terminal the current process is attached to. Scripts write to `/dev/tty` (or read passwords from it) when they must reach the user even if normal output is redirected to a file.
    :::

::: tip
**Explore/simulate:** Physical serial ports appear as `/dev/ttyS0`, `/dev/ttyS1` (character devices, major 4) and USB serial adapters as `/dev/ttyUSB0`. Run `ls -l /dev/ttyS*` to see them even though no cable is attached. Virtual consoles (the screens you get on the VM console with `Ctrl+Alt+F1`... `F6`) are `/dev/tty1` to `/dev/tty6`.
:::

**Checkpoint:** `ls -l /dev/null` starts with `c` and shows `1, 3`. `ls -l` on your first disk starts with `b`. `stat -c '%F' /dev/zero` prints `character special file`.

### Exam corner

- `ls -l` first character: `-` file, `d` directory, `l` symlink, `b` block device, `c` character device, `p` pipe, `s` socket. `ls -i` shows inode numbers.
- `cp -r` copies directories; `cp -a` copies recursively and preserves everything; `cp -p` preserves mode, ownership, and timestamps. `mv` renames or moves. `rmdir` only removes empty directories; `rm -r` removes non-empty ones.
- `mkdir -p` creates parent directories as needed. `pwd -P` resolves symlinks. `cd -` returns to the previous directory.
- `touch` creates empty files or updates timestamps; `touch -d "date"` or `-t YYYYMMDDhhmm` sets a specific time. ctime cannot be set manually.
- `stat` shows the inode: size, blocks, inode number, link count, permissions, UID/GID, and atime/mtime/ctime/birth.
- `file` identifies content by magic numbers, not by extension.
- `find PATH TESTS ACTION`: `-name`, `-iname`, `-type`, `-size +10M`, `-mtime +7`, `-mmin -30`, `-perm -4000`, `-user`, `-group`, `-exec cmd {} \;`, `-exec cmd {} +`, `-ok`, `-delete`.
- `locate` searches a database built by `updatedb` (package `plocate` on Ubuntu 24.04, `mlocate` on Rocky 9). It is fast but can be stale.
- `diff` shows changes (`<` first file, `>` second, `c`/`a`/`d`); `diff -u` is unified format; `sdiff` shows side by side with `|`, `<`, `>`.
- Hard link: same inode, link count increases, survives deletion of the original, no directories, no cross-filesystem. Symbolic link (`ln -s`): own inode, stores a path, can cross filesystems and point to directories, breaks if the target is removed.
- `lsof +D dir` finds what is using a directory; `lsof +L1` finds deleted-but-open files; `lsof -i :port`; `lsof -u user`; `lsof -p PID`.
- Block devices (disks, partitions) use random block access; character devices (terminals, serial ports) are byte streams. Special character devices: `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/full`, `/dev/tty`. Device files show major (driver) and minor (instance) numbers.
