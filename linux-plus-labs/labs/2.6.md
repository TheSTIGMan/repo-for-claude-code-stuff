## Lab 2.6: Manage Applications in Containers {#lab-2-6}

::: labinfo

**Domain:** 2.0 Services and User Management (20% of the exam)\

Containers package an application with everything it needs and run it isolated from the rest of the server. In this lab you will install Docker and Podman, see the runtimes underneath them (containerd and runC), pull and build images, run and inspect containers, keep data in volumes, connect containers with different network types, and learn why privileged and rootful containers are risky. On rocky-lab you will meet SELinux and fix a blocked bind mount with `:Z`.

### What you'll practice

- **Runtimes**: **runC**, **Podman**, **containerd**, **Docker**
- **Image operations**: pull, build (**Dockerfile**: `ENTRYPOINT`, `CMD`, `USER`, `FROM`), pruning, tags, layers
- **Container operations**: logs, map volumes, start/stop, inspect, delete (`rm`), run, exec, pruning, tags, environment variables
- **Volumes**: create, map, prune, **SELinux context** (`:Z`), **overlay**
- **Networks**: `network create`, **port mapping**, prune; types **macvlan**, **ipvlan**, **host**, **bridge**, **overlay**, **none**
- **Privileged vs. unprivileged** containers (and rootless vs. rootful)

### How it works

**Container versus virtual machine.** A virtual machine runs a whole separate kernel on emulated hardware. A *container* is just a normal Linux process (or group of processes) that the kernel isolates with two features:

- **Namespaces** give the process its own view of the system: its own process list (PID namespace), network interfaces (network namespace), filesystem tree (mount namespace), hostname, and users.
- **Control groups (cgroups)** limit how much CPU, memory, and I/O it can use.

All containers share the host's kernel. That makes them start in milliseconds and use little memory, but it also means a kernel bug or a badly configured container can affect the host.

**Images and layers.** An *image* is a read-only template: a filesystem plus settings such as which command to run. It is built in *layers*. Each instruction in a `Dockerfile` that changes files adds a new layer on top of the previous ones. Layers are shared: ten images based on `alpine` store the alpine layer only once. An image is named `registry/repository:tag`, for example `docker.io/library/nginx:alpine`. The *tag* (after the colon) is a version label; if you leave it out, it means `latest`.

**Overlay filesystem.** When you run a container, the engine stacks the image's read-only layers and adds one thin writable layer on top, using the kernel's **OverlayFS** (Docker's storage driver is called `overlay2`):

```{.diagram}
  merged/   <- what the container sees as "/"
    |
  upperdir  <- writable layer (this container only; deleted with the container)
  ---------
  lowerdir  <- image layer 3  (read-only, shared)
  lowerdir  <- image layer 2  (read-only, shared)
  lowerdir  <- image layer 1  (read-only, shared)
```

If the container changes a file from a lower layer, OverlayFS first copies it up into the upper layer ("copy-on-write"). When you delete the container, its upper layer is deleted too. That is why data that must survive goes into a **volume**: a folder managed by the engine (named volume) or a host folder (bind mount), mounted into the container and stored outside the overlay.

**The runtime stack.** "Docker" is really several programs:

```{.diagram}
  docker (CLI) --> dockerd --> containerd --> containerd-shim --> runc --> your process
                   (API)       (image and     (keeps container    (creates namespaces
                                container      running if          and cgroups, then
                                lifecycle)     dockerd restarts)   starts the process)

  podman (CLI, no daemon) ------------------> conmon ---------> crun or runc --> process
```

**runC** is the low-level *OCI runtime*: it reads a container spec and asks the kernel to create the namespaces and cgroups. **containerd** is a daemon that manages images and container lifecycles and calls runC; Kubernetes also uses it directly. **Docker** adds a friendly CLI, image building, networking, and volumes on top. **Podman** is a Red Hat-led, Docker-compatible tool with **no central daemon**. It can run *rootless*, as a normal user, which is the default on Rocky. The OCI (Open Container Initiative) standard means images built by one tool run in the others.

**Networking.** Each container usually gets its own network namespace. Docker's network *drivers* decide how it connects:

| Driver | What it does |
|---|---|
| `bridge` | Default. A virtual switch (`docker0`) on the host with private IPs (172.17.0.0/16); reach containers from outside with **port mapping** (`-p 8080:80`). |
| `host` | No isolation: the container uses the host's network stack directly. |
| `none` | Only a loopback interface. No network at all. |
| `macvlan` | Each container gets its own MAC address and an IP on the physical LAN. |
| `ipvlan` | Like macvlan, but containers share the host NIC's MAC address. |
| `overlay` | Spans several hosts (needs Docker Swarm or another orchestrator). |

**Privileged versus unprivileged.** By default a container is *unprivileged*: even if it runs as root inside, the kernel drops most root powers (Linux *capabilities*), blocks dangerous system calls (seccomp), and applies an AppArmor or SELinux profile. `--privileged` removes nearly all of those protections and gives access to host devices. Separately, *rootful* means the engine runs as root on the host (Docker by default), while *rootless* means it runs as your normal user (Podman by default), so root inside the container maps to an unprivileged user outside.

2. Allow your user to run `docker` without `sudo`, and understand the risk.

#### Task 3: Run, inspect, and manage containers

1. Run Nginx in the background, with a port mapping and an environment variable.

    ```bash
    docker run -d --name web -p 8080:80 -e LAB_COLOR=blue nginx:alpine
    docker ps
    curl -s http://localhost:8080 | grep -o '<title>.*</title>'
    ```

    ```{.output}
    CONTAINER ID   IMAGE          COMMAND                  CREATED         STATUS         PORTS                                   NAMES
    5c1e2d7a9b01   nginx:alpine   "/docker-entrypoint.…"   3 seconds ago   Up 2 seconds   0.0.0.0:8080->80/tcp, :::8080->80/tcp   web
    <title>Welcome to nginx!</title>
    ```

    ::: explain
    **What just happened:** `docker run` creates and starts a container from an image. `-d` (detached) runs it in the background. `--name web` gives it a name to use instead of the ID. `-p 8080:80` is **port mapping**: connections to port 8080 on the host go to port 80 inside the container (format `host:container`). `-e LAB_COLOR=blue` sets an **environment variable** inside the container, the usual way to pass settings such as database passwords or modes. `docker ps` lists running containers.
    :::

2. Read the container's logs.

    ```bash
    docker logs web
    docker logs --tail 3 web
    ```

    Now follow the log live with `docker logs -f web`, open a second terminal, run `curl -s localhost:8080 > /dev/null` a few times, watch the new lines appear, and press `Ctrl+C` in the first terminal.

    ::: explain
    **What just happened:** `docker logs` shows what the container's main process wrote to standard output and standard error. That is why container images send logs to stdout instead of files. `--tail 3` shows the last 3 lines, `-f` follows new output, and `--since 10m` shows the last 10 minutes. Each `curl` produces one access-log line.
    :::

3. Run commands inside the running container with `exec`.

    ```bash
    docker exec web nginx -v
    docker exec -it web sh
    ```

    Inside the container's shell, run:

    ```bash
    echo "$LAB_COLOR"
    hostname
    ps
    cat /etc/os-release | head -2
    exit
    ```

    ::: explain
    **What just happened:** `docker exec` starts an extra process in an existing container. `-i` keeps standard input open and `-t` gives you a terminal, together `-it` for an interactive shell. Alpine has `sh`, not `bash`. Inside, `ps` shows only the container's own processes, with Nginx as PID 1, because of the PID namespace. The hostname is the container ID. `exit` leaves the shell; the container keeps running because its main process is Nginx, not your shell.
    :::

4. Inspect the container's configuration and state.

    ```bash
    docker inspect web | head -20
    docker inspect --format '{{.State.Status}} pid={{.State.Pid}}' web
    docker inspect --format '{{.NetworkSettings.IPAddress}}' web
    docker inspect --format '{{json .Config.Env}}' web
    docker port web
    ```

    ```{.output}
    running pid=5873
    172.17.0.2
    ["LAB_COLOR=blue","PATH=/usr/local/sbin:/usr/local/sbin:/usr/local/bin:...","NGINX_VERSION=1.27.2"]
    80/tcp -> 0.0.0.0:8080
    80/tcp -> [::]:8080
    ```

    ::: explain
    **What just happened:** `docker inspect` prints everything Docker knows about the container as JSON. `--format` picks out fields: its state, its host PID (the container is just a process to the host, visible in `ps -p 5873`), its IP on the default bridge, and its environment variables (yours plus those set by `ENV` in the image). `docker port` shows its port mappings.
    :::

5. Stop, start, and delete the container.

    ```bash
    docker stop web
    docker ps -a --filter name=web
    docker start web
    docker restart web
    docker rm web
    docker rm -f web
    docker ps -a --filter name=web
    ```

    ```{.output}
    CONTAINER ID   IMAGE          COMMAND                  CREATED         STATUS                     PORTS   NAMES
    5c1e2d7a9b01   nginx:alpine   "/docker-entrypoint.…"   6 minutes ago   Exited (0) 2 seconds ago           web
    Error response from daemon: cannot remove container "/web": container is running: stop the container before removing or force remove
    ```

    ::: explain
    **What just happened:** `docker stop` sends `SIGTERM`, waits 10 seconds, then sends `SIGKILL`. A stopped container still exists (`docker ps -a` shows all containers, including `Exited` ones), with its writable layer intact. `docker start` runs it again with the same settings. `docker rm` deletes a container but refuses while it is running; `rm -f` (force) stops and deletes it. Podman uses exactly the same commands (`podman ps`, `podman logs`, and so on).
    :::

::: checkpoint
**Checkpoint:** `docker ps -a` no longer lists a container named `web`.

#### Task 4: Build your own image with a Dockerfile

1. Create a small application: a shell script that greets someone.

    ```bash
    mkdir -p ~/labs/2.6/greeter && cd ~/labs/2.6/greeter
    cat <<'EOF' > greet.sh
    #!/bin/sh
    echo "Hello, $1! I am $(whoami) (uid $(id -u)) in container $(hostname)."
    echo "GREETING_STYLE is: ${GREETING_STYLE:-unset}"
    EOF
    ```

    ::: explain
    **What just happened:** This uses a *heredoc*: everything between `<<'EOF'` and the line `EOF` is written to `greet.sh`. The quotes around `EOF` stop your shell from expanding `$1` and `$(whoami)` now; they must run later, inside the container. The script prints its first argument (`$1`), the user it runs as, and an environment variable.
    :::

2. Write the `Dockerfile`. Open it with `nano Dockerfile` and type:

    ```dockerfile
    FROM alpine:3.20
    LABEL maintainer="student@ubuntu-lab"
    ENV GREETING_STYLE=friendly
    RUN adduser -D -u 10001 appuser
    COPY greet.sh /usr/local/bin/greet.sh
    RUN chmod 755 /usr/local/bin/greet.sh
    USER appuser
    ENTRYPOINT ["/usr/local/bin/greet.sh"]
    CMD ["World"]
    ```

    ::: explain
    **What just happened:** A `Dockerfile` is a recipe, read top to bottom. `FROM` names the base image every image starts from. `LABEL` adds metadata. `ENV` sets a default environment variable. `RUN` executes a command at build time (here, creating a user with `adduser -D`, no password). `COPY` copies a file from the *build context* (this folder) into the image. `USER appuser` makes everything after it, including the running container, use that non-root user, a basic security practice. `ENTRYPOINT` is the program that always runs. `CMD` supplies default *arguments* to it, which users can replace. The JSON form `["..."]` runs the program directly without a shell.
    :::

3. Build the image and give it a tag.

    ```bash
    docker build -t greeter:1.0 .
    docker image ls greeter
    docker history greeter:1.0 | head -8
    ```

    ```{.output}
    [+] Building 3.1s (9/9) FINISHED
     => [internal] load build definition from Dockerfile
     => [1/4] FROM docker.io/library/alpine:3.20
     => [2/4] RUN adduser -D -u 10001 appuser
     => [3/4] COPY greet.sh /usr/local/bin/greet.sh
     => [4/4] RUN chmod 755 /usr/local/bin/greet.sh
     => => naming to docker.io/library/greeter:1.0
    ```

    ::: explain
    **What just happened:** `docker build` reads the `Dockerfile` in the folder given as the last argument (`.` means "this folder", the build context). `-t greeter:1.0` tags the result. Each `RUN` and `COPY` step became a layer on top of alpine's layer. `docker history` shows your new layers above the alpine base.
    :::

4. Run it and see how `ENTRYPOINT` and `CMD` work together.

    ```bash
    docker run --rm greeter:1.0
    docker run --rm greeter:1.0 'Linux+ student'
    docker run --rm -e GREETING_STYLE=formal greeter:1.0 Admin
    docker run --rm --entrypoint /bin/sh greeter:1.0 -c 'id; ls -l /usr/local/bin'
    ```

    ```{.output}
    Hello, World! I am appuser (uid 10001) in container 8d1f2c0b4e77.
    GREETING_STYLE is: friendly
    Hello, Linux+ student! I am appuser (uid 10001) in container 61a9b7c3d2e0.
    GREETING_STYLE is: friendly
    Hello, Admin! I am appuser (uid 10001) in container 0c4e1a2b3f55.
    GREETING_STYLE is: formal
    uid=10001(appuser) gid=10001(appuser) groups=10001(appuser)
    -rwxr-xr-x    1 root     root           146 Oct 10 13:20 greet.sh
    ```

    ::: explain
    **What just happened:** With no arguments, Docker ran `ENTRYPOINT` + `CMD`: `greet.sh World`. Anything you type after the image name **replaces `CMD`**, so the second run greeted `Linux+ student`. `-e` overrode the `ENV` default. To replace the `ENTRYPOINT` itself, you need `--entrypoint`; here you ran a shell instead. Rule of thumb: put the fixed program in `ENTRYPOINT` and default options in `CMD`. If an image has only `CMD` (like Nginx's `nginx -g 'daemon off;'`), the arguments you type replace the whole command.
    :::

5. Change the app, rebuild, and watch the layer cache and a *dangling* image.

    ```bash
    sed -i 's/Hello/Greetings/' greet.sh
    docker build -t greeter:1.1 -t greeter:latest .
    docker run --rm greeter
    docker tag greeter:1.1 greeter:1.0
    docker image ls --filter dangling=true
    ```

    ```{.output}
     => CACHED [2/4] RUN adduser -D -u 10001 appuser
     => [3/4] COPY greet.sh /usr/local/bin/greet.sh
    ...
    Greetings, World! I am appuser (uid 10001) in container 2b8c7d1e9f03.
    REPOSITORY   TAG       IMAGE ID       CREATED          SIZE
    <none>       <none>    a7d3e5f1c2b4   10 minutes ago   7.8MB
    ```

    ::: explain
    **What just happened:** The `RUN adduser` step was `CACHED` because nothing above it changed; only the steps from the changed `COPY` onward were rebuilt. Order Dockerfile steps from least to most often changed to make builds fast. You can give several tags with several `-t` options. `docker run --rm greeter` used the tag `latest` by default. When you moved the tag `1.0` to the new image, the old image lost its last tag and became *dangling* (`<none>:<none>`). Dangling images are what `docker image prune` cleans up in Task 9.
    :::

::: checkpoint
**Checkpoint:** `docker run --rm greeter:1.0` prints a line starting with `Greetings,` and `docker image ls greeter` shows tags `1.0`, `1.1`, and `latest` with the same image ID.

#### Task 5: Keep data with volumes and bind mounts, and see the overlay filesystem

1. Create a named volume and prove that data in it survives containers.

    ```bash
    docker volume create labdata
    docker run --rm -v labdata:/data alpine:3.20 \
      sh -c 'echo "saved at $(date)" > /data/note.txt'
    docker run --rm -v labdata:/data alpine:3.20 cat /data/note.txt
    docker volume ls
    docker volume inspect labdata
    ```

    ```{.output}
    saved at Sat Oct 10 13:31:07 UTC 2026
    [
        {
            "Driver": "local",
            "Mountpoint": "/var/lib/docker/volumes/labdata/_data",
            "Name": "labdata",
            ...
        }
    ]
    ```

    ::: explain
    **What just happened:** `docker volume create` made a *named volume*, a folder Docker manages under `/var/lib/docker/volumes/`. `-v labdata:/data` **maps** that volume to `/data` inside the container (format `source:destination`). The first container wrote a file and was removed (`--rm`); the second, brand-new container still read it. Data written anywhere else in a container lives in its overlay upper layer and is lost when the container is deleted.
    :::

2. Use a *bind mount*: map a host folder into a container.

    ```bash
    mkdir -p ~/labs/2.6/site
    echo '<h1>Version 1</h1>' > ~/labs/2.6/site/index.html
    docker run -d --name site -p 8081:80 \
      -v ~/labs/2.6/site:/usr/share/nginx/html:ro nginx:alpine
    curl -s localhost:8081
    echo '<h1>Version 2</h1>' > ~/labs/2.6/site/index.html
    curl -s localhost:8081
    docker exec site touch /usr/share/nginx/html/test
    ```

    ```{.output}
    <h1>Version 1</h1>
    <h1>Version 2</h1>
    touch: /usr/share/nginx/html/test: Read-only file system
    ```

    ::: explain
    **What just happened:** When the source starts with `/` (or `~`, which the shell expands to `/home/student`), `-v` makes a *bind mount* of that host folder. Changes on the host appear in the container instantly, which is handy for configuration and development. `:ro` makes it read-only inside the container. The longer, clearer syntax is `--mount type=bind,source=/path,target=/path,readonly`. Use named volumes for application data (Docker manages them) and bind mounts when the host must own the files.
    :::

3. See the overlay filesystem of a running container.

    ```bash
    docker info --format '{{.Driver}}'
    docker exec site sh -c 'echo hi > /tmp/inside.txt'
    docker diff site
    mount | grep overlay | head -1
    docker inspect --format '{{.GraphDriver.Data.UpperDir}}' site
    sudo ls "$(docker inspect --format '{{.GraphDriver.Data.UpperDir}}' site)/tmp"
    ```

    ```{.output}
    overlay2
    C /tmp
    A /tmp/inside.txt
    C /var
    ...
    overlay on /var/lib/docker/overlay2/4c9e.../merged type overlay (rw,relatime,lowerdir=/var/lib/docker/overlay2/l/QX3K...:/var/lib/docker/overlay2/l/7HDP...,upperdir=/var/lib/docker/overlay2/4c9e.../diff,workdir=/var/lib/docker/overlay2/4c9e.../work,nouserxattr)
    /var/lib/docker/overlay2/4c9e.../diff
    inside.txt
    ```

    ::: explain
    **What just happened:** `docker diff` lists what changed in the container's writable layer: `A` added, `C` changed, `D` deleted. The `mount` line shows the real OverlayFS mount: `lowerdir=` is the colon-separated list of read-only image layers, `upperdir=` is this container's writable layer (a folder called `diff`), `workdir=` is scratch space OverlayFS needs, and `merged` is the combined view the container uses as `/`. Your new file physically lives in the upper directory on the host. Delete the container and that folder goes too.
    :::

    ::: tip
    Podman supports an *overlay volume* with `-v /host/dir:/dir:O`: the container sees the host folder but its writes go to a temporary upper layer and are thrown away when it stops, so the host folder is never changed.
    :::

::: checkpoint
**Checkpoint:** `docker run --rm -v labdata:/data alpine:3.20 cat /data/note.txt` still prints the saved line, and `curl -s localhost:8081` prints `Version 2`.

2. Show that the default bridge has no name resolution, but a user-defined bridge does.

    **What just happened:** On the default `bridge`, containers can only reach each other by IP. `docker network create labnet` made a *user-defined bridge* (driver `bridge` is the default, with its own subnet such as `172.18.0.0/16`). Containers on different networks are isolated from each other.

3. Practice port mapping options.


    ::: explain
    **What just happened:** `-p 127.0.0.1:8082:80` publishes the port only on the host's loopback address, so other machines cannot reach it. `-P` (capital) publishes every port the image `EXPOSE`s on a random high host port. `ss` shows the host side listening, often through the `docker-proxy` helper. 4. Use the `host` and `none` network types.

    ```{.output}
    <title>Welcome to nginx!</title>
    ```

    ::: explain
    **What just happened:** With `--network host`, the container shares the host's network namespace: Nginx listened directly on host port 80 with no `-p` (port mapping is ignored in this mode), and `ip addr` shows the host's real interfaces. 5. Create **macvlan** and **ipvlan** networks on your VM's NIC. First find the NIC name and your LAN details.

    ```bash

    ip route show default
    ```

    Replace the subnet and gateway below with your lab network's values. The small `--ip-range` keeps Docker away from addresses your DHCP server or other VMs use.

    ```bash
    docker network create -d macvlan \
      --subnet=192.168.100.0/24 --gateway=192.168.100.1 \
      --ip-range=192.168.100.240/29 -o parent="$NIC" labmacvlan
    ```

    ```{.output}
    macvlan parent=enp0s3
    eth0@if2         UP             192.168.100.240/24
    ```

    ::: explain
    **What just happened:** `-d macvlan` creates a network where each container gets its **own MAC address** and an IP directly on your LAN, as if it were a separate physical machine plugged into the switch. `-o parent=` names the host NIC it rides on. This suits legacy apps that must be reachable on the LAN without port mapping. Two catches: the host itself cannot talk to its own macvlan containers (by kernel design), and the switch or hypervisor must accept several MAC addresses on one port.

    ::: tip
    **Explore/simulate:** Most hypervisors drop frames from unknown MAC addresses, so a macvlan container may get an IP but fail to `ping` the gateway. To make it work, enable *promiscuous mode* (VirtualBox: "Allow All"; VMware: promiscuous mode and forged transmits; Hyper-V: MAC address spoofing) on the VM's network adapter. #### Task 7: Privileged vs. unprivileged, rootful vs. rootless

1. Try two root-only actions in a normal (unprivileged) container.

    ```bash
    docker run --rm alpine:3.20 sh -c 'id; ip link add lab0 type dummy'
    docker run --rm alpine:3.20 mount -t tmpfs none /mnt
    ```

    ```{.output}
    uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),11(floppy),20(dialout),26(tape),27(video)
    ip: RTNETLINK answers: Operation not permitted
    mount: permission denied (are you root?)
    ```

    ::: explain
    **What just happened:** The process is `root` (UID 0) inside the container, yet the kernel refuses to create a network interface or mount a filesystem. Docker drops most Linux *capabilities* (such as `CAP_NET_ADMIN` and `CAP_SYS_ADMIN`) and applies seccomp and AppArmor profiles. "Root in a container" is a limited root by default.
    :::

2. Run the same commands in a privileged container.

    ```bash
    docker run --rm --privileged alpine:3.20 \
      sh -c 'ip link add lab0 type dummy && ip -br link show lab0'
    docker run --rm --privileged alpine:3.20 sh -c 'mount -t tmpfs none /mnt && df -h /mnt'
    docker run --rm --privileged alpine:3.20 sh -c 'ls /dev | grep -E "^(sd|vd|nvme)"'
    ```

    ```{.output}
    lab0             DOWN           ...
    Filesystem                Size      Used Available Use% Mounted on
    none                      1.9G         0      1.9G   0% /mnt
    sda
    sda1
    sda2
    sdb
    ...
    ```

    ::: explain
    **What just happened:** `--privileged` gives the container all capabilities, disables the seccomp and AppArmor protections, and exposes all host devices. The last command shows it can see your real disks; it could format them. (The `lab0` interface was created in the container's own network namespace and vanished with it.) Avoid `--privileged`. If a container truly needs one power, add only that capability, for example `--cap-add NET_ADMIN`:
    :::

    ```bash
    docker run --rm --cap-add NET_ADMIN alpine:3.20 \
      sh -c 'ip link add lab0 type dummy && echo created'
    ```

3. Compare a rootful Docker container with a rootless Podman container, as seen from the host.

    ```bash
    docker run -d --name rootful alpine:3.20 sleep 600
    podman run -d --name rootless docker.io/library/alpine:3.20 sleep 600

    ps -o user,pid,cmd -C sleep
    ```

    ```{.output}
    0
    USER         PID CMD
    root        8812 sleep 600
    student     8901 sleep 600
    ```

    ::: explain
    **What just happened:** Both containers run `sleep` as root **inside** (`id -u` prints `0`). On the host, the Docker one really is `root`, because `dockerd` runs as root (*rootful*). The Podman one is just `student`: rootless Podman uses a *user namespace* that maps container UID 0 to your own UID. If someone escaped from that container, they would only have your user's rights. Use the full name `docker.io/library/alpine` with Podman so it does not have to guess which registry you mean.

4. See the user namespace mapping behind rootless Podman.

    **What just happened:** `/etc/subuid` gives `student` a private range of 65,536 extra UIDs starting at 100000. `podman unshare` runs a command inside Podman's user namespace. Each `uid_map` line reads "container UID, host UID, count": container UID 0 is host UID 1000 (`student`), and container UIDs 1 to 65536 are host UIDs 100000 and up, which belong to nobody on the host. #### Task 8: SELinux contexts and bind mounts with Podman on Rocky

Run every command in this task on rocky-lab, as `student` (rootless).

1. Install Podman and confirm SELinux is enforcing.

    ```bash
    # on rocky-lab
    sudo dnf install -y podman
    getenforce
    mkdir -p ~/labs/2.6/web
    echo '<h1>Hello from Rocky</h1>' > ~/labs/2.6/web/index.html

    ```

    ```{.output}
    Enforcing
    unconfined_u:object_r:user_home_t:s0 /home/student/labs/2.6/web/index.html
    ```

    ::: explain
    **What just happened:** `getenforce` shows SELinux mode. `ls -Z` shows a file's SELinux *context* (`user:role:type:level`). The important part is the *type*, `user_home_t`: a file in a home folder. SELinux decides access by type, on top of normal permissions.
    :::

2. Bind-mount the folder into a container without a label option.

    ```bash
    # on rocky-lab
    podman run --rm -v ~/labs/2.6/web:/data:ro \
      docker.io/library/alpine:3.20 cat /data/index.html
    sudo ausearch -m avc -ts recent | grep -o 'denied.*tclass=file' | tail -1
    ```

    ```{.output}
    cat: can't open '/data/index.html': Permission denied
    denied  { read } for  pid=4512 comm="cat" name="index.html" ... scontext=system_u:system_r:container_t:s0:c214,c870 tcontext=unconfined_u:object_r:user_home_t:s0 tclass=file
    ```

    ::: explain
    **What just happened:** The Unix permissions allow reading, but SELinux blocked it. Container processes run with the type `container_t`, and policy only lets them use files labeled `container_file_t`. The audit log entry (`ausearch -m avc` searches for *Access Vector Cache* denials) shows the source context (`container_t`) and target context (`user_home_t`). The `c214,c870` part is an MCS category pair, unique per container, which keeps containers away from each other's files too.
    :::

3. Fix it with `:Z`, and check the new label.

    ```bash
    # on rocky-lab
    podman run --rm -v ~/labs/2.6/web:/data:ro,Z \
      docker.io/library/alpine:3.20 cat /data/index.html
    ls -Z ~/labs/2.6/web/index.html
    ```

    ```{.output}
    <h1>Hello from Rocky</h1>
    system_u:object_r:container_file_t:s0:c157,c623 /home/student/labs/2.6/web/index.html
    ```

    ::: explain
    **What just happened:** `:Z` (capital) tells Podman to relabel the host folder with `container_file_t` and **this container's private** MCS categories, so only this one container can use it. `:z` (lowercase) applies `container_file_t` without categories, so **several** containers can share the folder. Options are combined with commas, as in `:ro,Z`. Docker on SELinux systems supports the same `:z` and `:Z`.
    :::

    ::: warning
    Never use `:Z` or `:z` on system folders such as `/home`, `/etc`, or `/usr`. Relabeling them would stop the host's own services from reading their files. Only relabel folders made for the container. To relabel by hand you can use `chcon -t container_file_t <dir>`, or make it permanent with `semanage fcontext` and `restorecon`.
    :::

4. Run a rootless web container on Rocky with port mapping.

### Exam corner

- Runtime stack: Docker CLI -> `dockerd` -> **containerd** -> **runC** (OCI runtime). **Podman** is daemonless, Docker-compatible, and rootless by default (uses `crun`/`runc`).
- Image commands: `pull`, `build -t name:tag .`, `tag`, `push`, `rmi`, `image ls`, `history` (layers), `image inspect`, `image prune` (dangling; `-a` for all unused).
- Dockerfile: `FROM` (base), `RUN` (build-time command, new layer), `COPY`/`ADD`, `ENV`, `USER` (non-root), `EXPOSE`, `ENTRYPOINT` (fixed program), `CMD` (default arguments; replaced by arguments after the image name). Override the entrypoint with `--entrypoint`.
- Container commands: `run -d --name -p host:container -e VAR=value -v src:dst`, `ps -a`, `logs -f`, `exec -it name sh`, `inspect --format`, `stop`, `start`, `restart`, `rm` (`-f` to force), `container prune`.
- Volumes: `volume create`, `-v name:/path` (named) vs `-v /host/path:/path` (bind), `:ro`; data outside volumes lives in the container's overlay upper layer and is lost with `rm`. `volume prune` removes anonymous volumes; `-a` includes named ones.
- Storage: `overlay2` driver; OverlayFS `lowerdir` (read-only image layers), `upperdir` (container writes), `merged` (the container's view).
- SELinux: bind mounts need `container_file_t`; `:z` = shared label, `:Z` = private label for one container; check with `ls -Z`, denials in `ausearch -m avc`.
- Networks: `network create` (user-defined bridge has DNS by container name), `bridge` (default, NAT, needs `-p`), `host` (shares host stack), `none` (loopback only), `macvlan` (own MAC on LAN, needs `-o parent=`, promiscuous mode), `ipvlan` (shares parent MAC), `overlay` (multi-host, needs Swarm). `network prune`.
- `-p 8080:80` maps host port 8080 to container port 80; `-P` maps all exposed ports to random ports; `-p 127.0.0.1:8080:80` binds only to loopback.
- Unprivileged containers lack most capabilities; `--privileged` grants all capabilities and host devices (avoid; use `--cap-add`). Rootless containers map container root to an unprivileged host UID (`/etc/subuid`).
- The `docker` group is root-equivalent.
