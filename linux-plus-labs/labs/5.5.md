## Lab 5.5: Troubleshoot Performance Issues {#lab-5-5}

::: labinfo
**Objective:** 5.5 Given a scenario, analyze and troubleshoot performance issues.\
**Domain:** 5.0 Troubleshooting (22% of the exam)\
**Time:** about 4 hours (do it over two or three sittings; each task after Task 1 stands alone)\
**VM:** ubuntu-lab (rocky-lab for Tasks 7 and 10)\
**Snapshot first:** Yes. Take a snapshot of both VMs now. This lab loads the CPU, memory, and disks on purpose, formats one extra disk, adds a service that slows down booting, and changes traffic control on a network interface.
:::

"The server is slow" is the most common and the vaguest complaint an administrator hears. In this break-and-fix lab you first record what normal looks like (a baseline), then create each slowdown yourself with load generators, traffic control, and misconfigured services, measure it with the standard Linux tools, find the root cause, fix it, and prove the fix. Exam questions for this objective describe a symptom ("high load average but the CPU is mostly idle") and ask what it means or which command to run next, so the goal is to connect each symptom to the right tool quickly.

### What you'll practice

- Building a performance baseline with `sysstat` (`sar`, `iostat`, `mpstat`, `pidstat`), `vmstat`, `free`, `top`, `iotop`, and pressure stall information, and spotting **exceeding baselines**
- **CPU bottleneck**, **high CPU usage**, and **high load average** (`uptime`, `top`, `mpstat -P ALL`, `pidstat`, `nice`/`renice`, cgroup `CPUQuota`)
- **High context switching** (`vmstat` `cs`, `pidstat -w`, `sar -w`)
- **Swapping** and **out of memory** conditions (`vmstat` `si`/`so`, `free`, `swapon --show`, `MemoryMax`, the OOM killer in `journalctl -k`)
- **High I/O wait time**, **high disk latency**, **blocked processes**, and **low throughput** from storage (`iostat -x`, `vmstat` `wa` and `b`, process state `D`, `fio`, `iotop`)
- **System unresponsiveness** and **sluggish terminal behavior** (pressure stall information, cgroups, `nice`)
- **Slow startup** (`systemd-analyze blame`, `critical-chain`)
- **High failed log-in attempts** (`journalctl -u ssh`, `/var/log/auth.log`, `lastb`, `fail2ban`)
- Network performance: **high latency**, **jitter**, **packet drops**, **random timeouts**, **random disconnects**, **low throughput**, **slow response times**, and **slow application response** (`ping`, `mtr`, `curl -w`, `iperf3`, `tc` with `netem` and `tbf`)
- **Slow remote storage response** over NFS (`nfsiostat`, `mountstats`, `nfsstat`)
- **Hardware errors** (`journalctl -k -p err`, `dmesg`, `rasdaemon`/`ras-mc-ctl`, `smartctl`)

### How it works

**Use the same method as Lab 5.2.** Lab 5.2 introduced the troubleshooting loop: identify the symptoms, gather data, form a hypothesis, test it, fix, verify, document. Performance problems follow the same loop. The difference is that nothing is "broken" with an error message. Instead, something is *slower than normal*, so you need numbers, and you need to know what normal numbers look like. Every scenario below uses the same parts as Lab 5.2: **Break it**, **Symptom**, **Investigate**, **Root cause**, **Fix**, **Verify**, and **Prevent**.

**The four resources.** Almost every slowdown comes from one of four resources running out: **CPU**, **memory**, **storage I/O**, or the **network**. For each resource, ask three questions (this is called the **USE method**):

- **Utilization**: how busy is it? (CPU 100% busy, disk `%util` 100%)
- **Saturation**: is work waiting in a queue? (run queue longer than the number of CPUs, disk queue growing, memory pushed to swap)
- **Errors**: is anything failing? (dropped packets, I/O errors, hardware errors in the kernel log)

```{.diagram}
 Resource   Utilization            Saturation (queue)            Errors
 --------   -------------------    --------------------------    ------------------
 CPU        top %us+%sy, mpstat    vmstat r > CPUs, load avg     (rare) MCE in dmesg
 Memory     free "used"            vmstat si/so, swap used, OOM  OOM killer messages
 Disk       iostat %util           iostat aqu-sz, await, vmstat b I/O error in dmesg
 Network    sar -n DEV, iperf3     ping latency, tc backlog      ip -s link drops/errs
```

**Load average.** `uptime` prints three numbers, for example `load average: 3.80, 2.10, 0.95`. They are the average number of tasks that were *runnable* (running or waiting for a CPU) or in *uninterruptible sleep* (usually waiting for disk I/O) over the last 1, 5, and 15 minutes. Compare them with the number of CPUs (`nproc`). On a 2-CPU VM, a load of 2.0 means both CPUs are fully used with nobody waiting; 4.0 means that on average two tasks are waiting all the time. Because Linux also counts tasks waiting for disks, a high load average with an idle CPU points at storage, not CPU. The order of the three numbers tells you the trend: a 1-minute value much higher than the 15-minute value means the problem just started.

**Baselines.** A number is only "high" compared with something. A **baseline** is a record of normal values (CPU, memory, disk, network, load) captured when the system is healthy. When users complain, you compare current values with the baseline and look for the metric that changed. The `sysstat` package collects this automatically every few minutes, and `sar` reads the history back.

**Controlling who gets resources.** Two mechanisms decide how resources are shared:

- **nice values** (from `-20`, most favored, to `19`, least favored) tell the CPU scheduler how to share CPU time between processes. `nice -n 19 command` starts a command politely; `renice` changes a running process.
- **cgroups** (control groups) put processes in boxes with limits. systemd puts every service in its own cgroup, so you can say "this service may use at most half a CPU (`CPUQuota=50%`) and 400 MB of memory (`MemoryMax=400M`)". `systemd-run` starts any command in a new temporary cgroup with such limits. This is how you run a test or a batch job without hurting `sshd` and other important services.

**Practice safely.** You will create load with `stress-ng` (a load generator with a timeout) and `fio` (a storage benchmark), always with time limits, in cgroups where possible. Network problems are created inside network namespaces with veth pairs, the same pattern as Lab 5.3, so your real network interface and your SSH session are never touched (except in Task 10, which delays only NFS traffic). You will never use a fork bomb or anything without an off switch.

2. Turn on sysstat data collection. On Ubuntu 24.04 the package installs with collection **disabled** (`ENABLED="false"` in `/etc/default/sysstat`, and the systemd units are disabled to match).

    ```bash
    sudo sed -i 's/^ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
    sudo systemctl enable --now sysstat sysstat-collect.timer sysstat-summary.timer
    systemctl list-timers 'sysstat*'

    ```{.output}
    NEXT                        LEFT     LAST PASSED UNIT                   ACTIVATES
    Sat 2026-10-10 10:10:00 UTC 4min 1s  -    -      sysstat-collect.timer  sysstat-collect.service
    Sun 2026-10-11 00:07:00 UTC 13h left -    -      sysstat-summary.timer  sysstat-summary.service

    ::: explain
    **What just happened:** `sed -i` edits the file in place and changes the setting to `true`, so a later `dpkg-reconfigure sysstat` or package upgrade keeps collection on. `systemctl enable --now` enables the units at boot and starts them now. `sysstat.service` writes a "restart" marker at boot, `sysstat-collect.timer` runs `/usr/lib/sysstat/sa1` every 10 minutes to append a sample to `/var/log/sysstat/saDD` (DD is the day of the month), and `sysstat-summary.timer` writes a daily report shortly after midnight. 3. Ten minutes between samples is fine for production but slow for a lab. Add a systemd **drop-in** (a small file that overrides part of a unit) to sample every 2 minutes. A **heredoc** sends the lines between `<<'EOF'` and `EOF` into a command; the quotes around `EOF` stop the shell from changing `$` signs.

    ```bash
    sudo mkdir -p /etc/systemd/system/sysstat-collect.timer.d
    cat <<'EOF' | sudo tee /etc/systemd/system/sysstat-collect.timer.d/lab.conf
    [Timer]
    OnCalendar=
    OnCalendar=*:00/2
    EOF
    sudo systemctl daemon-reload
    sudo systemctl restart sysstat-collect.timer
    systemctl list-timers sysstat-collect.timer
    ```

    ::: explain
    **What just happened:** The empty `OnCalendar=` clears the original schedule, and `*:00/2` means "every hour, starting at minute 0, every 2 minutes". `daemon-reload` makes systemd reread unit files. The `NEXT` column now shows a time less than 2 minutes away. You will remove this drop-in in the clean-up.
    :::

    ```bash
    vmstat 2 5

    ```{.output}
    procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
     r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
     0  0      0 2961204  48212 612044    0    0    52    31  118  205  1  1 98  0  0  0

    ::: explain
    **What just happened:** `vmstat 2 5` prints 5 lines, 2 seconds apart. **The first line is an average since boot; ignore it and read the others.** Columns: `r` = runnable tasks (running or waiting for CPU), `b` = **blocked processes** (uninterruptible sleep, usually waiting for I/O), `swpd` = swap in use (KB), `free`/`buff`/`cache` = memory (KB), `si`/`so` = swap in/out per second (any steady non-zero value means **swapping**), `bi`/`bo` = blocks read/written per second, `in` = interrupts, `cs` = **context switches** per second, and CPU percentages `us` (user programs), `sy` (kernel), `id` (idle), `wa` (**I/O wait**: idle while waiting for disk), `st` (steal: time the hypervisor gave your vCPU to another VM), and `gu` (time running guest VMs).

    free -h
    swapon --show
    ```

    ```{.output}
                   total        used        free      shared  buff/cache   available
    Mem:           3.8Gi       382Mi       2.8Gi       1.1Mi       791Mi       3.4Gi

    **What just happened:** `mpstat -P ALL 2 1` shows one 2-second sample for all CPUs together (`all`) and for each CPU, so you can see whether one CPU is maxed out while the other is idle. `iostat -d` shows devices only, `-x` extended columns, `-z` hides idle devices, and `-y` skips the since-boot report. 8. Look at the interactive views. Run `top`, press `1` to show each CPU, `M` to sort by memory, `P` to sort by CPU, and `q` to quit. Then enable delay accounting (needed for the `IO>` column of `iotop`) and run `iotop` in batch mode.

    ```bash
    top
    sudo sysctl -w kernel.task_delayacct=1
    sudo iotop -o -b -n 2 -d 2
    ```

    ::: explain
    **What just happened:** `top` refreshes every 3 seconds; its header shows the load average, task counts by state, and the same `us sy ni id wa hi si st` CPU split as `vmstat`. `kernel.task_delayacct=1` turns on per-task delay accounting until the next reboot; without it `iotop` warns and cannot show how much time each process waits for I/O. `iotop -o` shows only processes doing I/O, `-b` is batch (non-interactive) mode, `-n 2` takes two samples, and `-d 2` waits 2 seconds between them. On an idle system it shows only the totals lines.
    :::

#### Task 2: CPU bottleneck, high CPU usage, high load average, and high context switching

**Scenario A: CPU-bound jobs**

1. **Break it.** Start four CPU-hungry workers on your 2-CPU VM. They stop by themselves after 5 minutes.

    ```bash
    cd ~/labs/5.5
    stress-ng --cpu 4 --timeout 300s > /dev/null 2>&1 &
    ```

    ::: explain
    **What just happened:** `stress-ng --cpu 4` starts four workers that do nothing but math, and `--timeout 300s` stops them after 300 seconds. `> /dev/null 2>&1` discards its messages and `&` runs it in the background so you keep your prompt. Four workers on two CPUs means two of them are always waiting for a CPU.
    :::

2. **Symptom.** Wait about a minute, then run the probe and check the load.

    ```bash
    ~/labs/5.5/probe.sh
    uptime
    ```

    ```{.output}
    probe: 1.31 seconds
     10:21:40 up 40 min,  1 user,  load average: 3.12, 1.20, 0.47
    ```

    The "application" takes about three times longer than the baseline, and the 1-minute load average is well above the CPU count (2) and still climbing toward 4.

4. Identify the processes precisely with `pidstat`, which also shows how much each one *waits* for a CPU.

    ```bash
    pidstat -u 2 1 | grep -E 'Average|stress'
    ```

    ```{.output}
    Average:      UID       PID    %usr %system  %guest   %wait    %CPU   CPU  Command
    Average:     1000      2301   49.75    0.00    0.00   49.75   49.75     -  stress-ng-cpu
    Average:     1000      2302   50.25    0.00    0.00   49.25   50.25     -  stress-ng-cpu
    ```

    ::: explain
    **What just happened:** `%wait` is the percentage of time the task was ready to run but waiting for a CPU. Values near 50% mean each worker spends half its life in the queue. On a real server this column tells you that a process is slow not because it is inefficient but because it is starved of CPU.
    :::

5. **Root cause.** More CPU-bound work than CPUs: four always-runnable processes on two CPUs. In real life this is a runaway process, a batch job started at the wrong time, too many worker processes for the hardware, or a VM with too few vCPUs.

6. **Fix, option 1: lower the priority.** Make the workers "nice" so that everything else wins when it competes with them.

    ```bash
    renice -n 19 -p $(pgrep -d ' ' stress-ng-cpu)
    ps -o pid,ni,pcpu,comm -C stress-ng-cpu
    ~/labs/5.5/probe.sh
    uptime
    ```

    ```{.output}
    2301 (process ID) old priority 0, new priority 19
    2302 (process ID) old priority 0, new priority 19
    ...
        PID  NI %CPU COMMAND
       2301  19 49.6 stress-ng-cpu
    ...
    probe: 0.47 seconds
     10:24:02 up 42 min,  1 user,  load average: 4.02, 2.31, 0.98
    ```

    ::: explain
    **What just happened:** `pgrep -d ' ' stress-ng-cpu` prints the matching PIDs separated by spaces, and `renice -n 19 -p` sets their nice value to 19, the lowest priority. A normal user can only make their own processes *nicer* (higher numbers); lowering the value needs `sudo`. The probe is fast again because the scheduler now prefers it. Notice that the **load average stays high**: the workers are still runnable, they just yield. Load average measures demand, not user pain, which is why you always check it together with the other tools.
    :::

#### Task 3: Swapping and out of memory

**Swap** is disk space used as overflow for RAM. Moving rarely used pages to swap is fine. **Swapping** as a *problem* means pages are moved out and back in constantly (also called thrashing), and because a disk is thousands of times slower than RAM, everything waits. When memory and swap run out completely, the kernel's **OOM killer** (out of memory killer) kills a process to free memory.

You will create both conditions inside a cgroup with a memory limit, so only the test process suffers and the rest of the VM keeps working.

1. Make sure swap exists. If `swapon --show` printed a line in Task 1, skip to step 2. If it printed nothing, create a temporary 2 GB swap file.

    ```bash
    sudo fallocate -l 2G /swap-lab.img
    sudo chmod 600 /swap-lab.img
    sudo mkswap /swap-lab.img
    sudo swapon /swap-lab.img
    swapon --show
    ```

    ::: explain
    **What just happened:** `fallocate -l 2G` reserves a 2 GB file, `chmod 600` makes it readable only by root (required for swap), `mkswap` writes a swap signature, and `swapon` activates it. The clean-up removes it.
    :::

**Part A: swapping**

2. **Break it.** Run a memory worker that needs 800 MB in a cgroup limited to 400 MB of RAM. The kernel must keep half of the worker's memory in swap, and because the worker touches all of it constantly, pages go out and come back in all the time.

        stress-ng --vm 1 --vm-bytes 800M --vm-keep --timeout 180s
    ```

    ::: explain
    **What just happened:** `--vm 1` starts one worker that allocates memory, `--vm-bytes 800M` sets the amount, and `--vm-keep` keeps rewriting the same memory instead of freeing it. `-p MemoryMax=400M` is the hard RAM limit for the cgroup. Swap is still allowed for this cgroup, so instead of being killed the worker is forced to swap. The limit stands in for "a server with too little RAM for its workload".
    :::

#### Task 5: System unresponsiveness and sluggish terminal behavior

**Sluggish terminal behavior** is what a user feels first: characters appear a moment after you type them, `ls` takes a second, tab completion hangs. Every keystroke over SSH needs `sshd` and your shell to get CPU time and memory; when other tasks hog both, the terminal lags. In the worst case the system becomes **unresponsive**: SSH logins time out and even the console is slow.

1. **Break it.** Start CPU and memory pressure together, in your own login session, with a time limit.

    ```bash

    ```

    ::: explain
    **What just happened:** Eight CPU workers on two CPUs create a long run queue, and two memory workers keep 2 GB of RAM constantly busy. The 120-second timeout is your safety net. Never test this with a fork bomb (a function that copies itself endlessly): it has no off switch and usually needs a hard reset.
    :::

    10  0      0  736120  50300 792040    0    0     0     0 1302 1987 93  7  0  0  0  0
    ```

    ::: explain
    **What just happened:** `cpu some avg10=78.12` means that during the last 10 seconds, some task was waiting for a CPU 78% of the time; your shell and `sshd` are among those tasks. Memory pressure is starting too, and `free` memory is low. The load average of about 10 and `r` = 10 on 2 CPUs confirm the run queue. If memory pressure grew further, swapping would begin and `wa` would rise; that combination is what turns "sluggish" into "unresponsive".
    :::

4. **Root cause.** A heavy job runs at the same priority, in the same cgroup, as your interactive session, so it competes equally for CPU and memory.

5. **Fix.** Stop it, then run the same job the right way: in its own cgroup with a low CPU weight, a CPU cap, a memory cap, and a nice value.

    ```bash
    pkill stress-ng
    sudo systemd-run --unit=batchjob --nice=19 -p CPUWeight=20 -p CPUQuota=100% \
        -p MemoryMax=2500M stress-ng --cpu 8 --vm 2 --vm-bytes 1G --vm-keep --timeout 120s
    sleep 15
    ~/labs/5.5/probe.sh
    grep some /proc/pressure/cpu
    ```

    ```{.output}
    probe: 0.51 seconds
    some avg10=6.20 avg60=20.15 avg300=9.88 total=55120330
    ```

    ::: explain
    **What just happened:** `--nice=19` starts the job with the lowest CPU priority. `CPUWeight=20` gives its cgroup a fifth of the default weight (100) when CPUs are contended. `CPUQuota=100%` caps it at one full CPU out of two, so one CPU always stays free for everything else, and `MemoryMax=2500M` stops it from taking all the RAM. The job still runs, but the probe is close to normal and pressure falls. `avg60` is still high because it includes the earlier minute.
    :::

6. See how systemd protects the important services. Each service lives in its own cgroup under `system.slice`; your login lives under `user.slice`.

    ```bash
    systemctl status ssh --no-pager | grep -A2 CGroup
    systemd-cgls --no-pager -u user.slice | head -6
    sudo systemd-cgtop -b -n 1 --depth=2 | head -10
    cat /proc/$(pgrep -o sshd)/oom_score_adj
    ```

    ::: explain
    **What just happened:** `sshd` runs in `/system.slice/ssh.service` and your session in `user.slice/user-1000.slice/session-N.scope`. When CPUs are busy, slices share CPU by weight, so a job boxed in its own unit cannot take everything. `systemd-cgtop` is a `top` for cgroups. An `oom_score_adj` of `-1000` would mean the OOM killer never chooses that process. `TasksMax=` in a unit (or `ulimit -u` per user) caps the number of processes, the real defense against fork bombs.
    :::

7. **Verify** and stop the job.

    ```bash
    sudo systemctl stop batchjob
    ~/labs/5.5/probe.sh
    ```

8. **Prevent.** Run heavy jobs as systemd units or with `systemd-run` and resource limits, use `nice`, leave headroom (do not size a server to 100% of its CPU and RAM), and when a terminal is sluggish, check `uptime`, `vmstat`, and `/proc/pressure/*` first: they tell you in seconds whether CPU, memory, or I/O is the bottleneck. If a system is too unresponsive to log in, use the console, or (if enabled) the magic SysRq key described in Lab 5.2.

1. Write the build and tear-down scripts.

    ```bash
    cat <<'EOF' > ~/labs/5.5/labnet-up.sh
    #!/bin/bash
    # labnet-up.sh: client <-> router <-> server practice network
    set -e
    for ns in client router server; do ip netns add "$ns"; done
    ip link add veth-c type veth peer name veth-rc
    ip link add veth-s type veth peer name veth-rs
    ip link set veth-c netns client
    ip link set veth-rc netns router
    ip link set veth-rs netns router
    ip link set veth-s netns server
    ip -n client addr add 10.10.1.10/24 dev veth-c
    ip -n router addr add 10.10.1.1/24 dev veth-rc
    ip -n router addr add 10.10.2.1/24 dev veth-rs
    ip -n server addr add 10.10.2.20/24 dev veth-s
    for ns in client router server; do ip -n "$ns" link set lo up; done
    ip -n client link set veth-c up
    ip -n router link set veth-rc up
    ip -n router link set veth-rs up
    ip -n server link set veth-s up
    ip -n client route add default via 10.10.1.1
    ip -n server route add default via 10.10.2.1
    ip netns exec router sysctl -qw net.ipv4.ip_forward=1
    echo "lab network is up"

    #!/bin/bash
    # labnet-down.sh: stop everything in the namespaces and delete them

        ip netns del "$ns" 2>/dev/null

    EOF

    ::: explain
    **What just happened:** `labnet-up.sh` creates three namespaces, connects them with two veth pairs (virtual cables), assigns addresses, and turns on forwarding in the router namespace only. `labnet-down.sh` uses `ip netns pids` to find every process running inside each namespace (the test servers you start below), kills them with `xargs -r kill` (`-r` means do nothing if there are none), and deletes the namespaces; the veth pairs disappear with them.

#### Task 11: Hardware errors and exceeding baselines

**Part A: hardware errors**

Failing hardware often shows up first as a performance problem: a disk with bad sectors retries each read for seconds, a NIC with a bad cable drops packets, ECC memory corrects errors, and a CPU throttles when it overheats. The evidence is in the kernel log.

1. Search the kernel log for errors from this boot.

    ```bash
    journalctl -k -p err -b --no-pager | tail -10
    sudo dmesg -T --level=err,warn | tail -10
    journalctl -k -b --no-pager | grep -i -E 'mce|machine check|edac|hardware error|i/o error|thermal|throttl'
    ```

    ::: explain
    **What just happened:** `journalctl -k -p err -b` shows kernel messages of priority `err` and more severe, from the current boot. `dmesg -T --level=err,warn` shows the kernel ring buffer with readable times, errors and warnings only. The `grep` looks for the usual signs of **hardware errors**: `mce` and `machine check` (the CPU reported a hardware fault in itself, its cache, or memory), `EDAC` (error detection and correction: memory controller errors), `I/O error` (disk or controller problems), and thermal throttling. A healthy VM usually prints few or no lines here.
    :::

2. Install and query `rasdaemon`, the RAS (reliability, availability, serviceability) daemon that records hardware error events in a database.

    ```bash
    sudo apt install -y rasdaemon smartmontools
    sudo systemctl enable --now rasdaemon
    sudo ras-mc-ctl --status
    sudo ras-mc-ctl --summary
    sudo ras-mc-ctl --errors

    ```{.output}
    ras-mc-ctl: drivers not loaded.
    No Memory errors.

    No PCIe AER errors.

    No MCE errors.

    ::: explain
    **What just happened:** `rasdaemon` listens for kernel hardware error events (memory, PCIe AER, MCE, disk) and stores them in `/var/lib/rasdaemon/`. `ras-mc-ctl --status` reports whether EDAC memory controller drivers are loaded; in a VM there is no real memory controller, so they are not. `--summary` counts errors by type and `--errors` lists each event. On a physical server, a growing count of corrected memory errors on one DIMM means "replace that DIMM soon", before it starts causing crashes. The older `mcelog` tool does a similar job on some distributions.

3. Check disk health with SMART.

    ```bash
    lsblk -d -o NAME,MODEL,SIZE
    sudo smartctl -i /dev/sda
    sudo smartctl -H /dev/sda
    ```

    ```{.output}
    Device Model:     VBOX HARDDISK
    ...
    SMART support is: Unavailable - device lacks SMART capability.
    ```

    ::: explain
    **What just happened:** `smartctl -i` shows the disk identity and whether it supports SMART (Self-Monitoring, Analysis and Reporting Technology), and `-H` asks for the overall health verdict. Virtual disks usually do not support SMART (a `virtio` disk like `/dev/vda` may even report "Unable to detect device type"). On a physical disk, `sudo smartctl -a /dev/sda` shows attributes such as `Reallocated_Sector_Ct`, `Current_Pending_Sector`, and `UDMA_CRC_Error_Count`; any non-zero, growing value means the disk or its cable is failing. Lab 5.2 covers device failures in more depth.

4. **Explore/simulate** an I/O error and see what it looks like in the log and to a user.

    ::: tip
    **Explore/simulate:** A VM cannot grow real bad sectors, so you build a small fake disk with a device-mapper `error` target in the middle (the same technique Lab 5.2 uses), read through it, and look at the evidence. The loop file lives in your lab directory and is deleted afterwards.
    :::

    ```bash
    cd ~/labs/5.5
    truncate -s 20M hw.img
    LOOP=$(sudo losetup --find --show hw.img)
    printf '0 20480 linear %s 0\n20480 2048 error\n22528 18432 linear %s 22528\n' \
        "$LOOP" "$LOOP" | sudo dmsetup create badlab
    sudo dd if=/dev/mapper/badlab of=/dev/null bs=1M
    journalctl -k --since "2 min ago" --no-pager | grep -i error | tail -3
    ```

    ```{.output}
    dd: error reading '/dev/mapper/badlab': Input/output error
    10+0 records in
    10+0 records out
    10485760 bytes (10 MB, 10 MiB) copied, 0.0213 s, 492 MB/s
    Oct 10 13:40:12 ubuntu-lab kernel: Buffer I/O error on dev dm-0, logical block 2560, async page read
    ```

    ::: explain
    **What just happened:** `losetup --find --show` attaches the 20 MB file as a loop device, and the `dmsetup` table (in 512-byte sectors) maps it normally except for 1 MB in the middle (sectors 20480 to 22527), which returns errors. `dd` stops at exactly 10 MiB with `Input/output error`, and the kernel logs a `Buffer I/O error`. A real failing disk also logs `ata` or `nvme` resets and retries, and each retry can take seconds, so a dying disk often looks like extreme disk latency before it fails outright.
    :::

7. Look at the other resources and narrow the time window.

    ```bash
    LC_ALL=C sar -r | tail -4
    LC_ALL=C sar -W -s 10:30:00 -e 11:00:00
    LC_ALL=C sar -b | tail -4
    LC_ALL=C sar -d -p | grep -E 'DEV|sdb' | head -6
    LC_ALL=C sar -n DEV | grep -E 'IFACE|enp' | tail -3
    LC_ALL=C sar -w | tail -3
    ls /var/log/sysstat/
    LC_ALL=C sar -q -f /var/log/sysstat/sa$(date +%d) | tail -3
    ```

    ::: explain
    **What just happened:** `-r` is memory, `-W` swap paging, `-b` overall I/O, `-d -p` per-disk statistics with readable names (`await`, `aqu-sz`, `%util`), `-n DEV` per-interface traffic (`-n EDEV` for errors and drops), and `-w` process creations and context switches. `-s`/`-e` limit the time window, and `-f` reads another day's file (for example `sa09`); Ubuntu keeps 7 days (`HISTORY` in `/etc/sysstat/sysstat`). The practice network does not appear in `sar -n DEV` because sysstat sees only the main network namespace.
    :::

8. Find the moments when the system was **exceeding baselines**: here, when the 1-minute load was higher than the number of CPUs, and when the CPU was less than 20% idle.

    ```bash

    **What just happened:** `awk` reads each line as columns. ### Exam corner

- Work resource by resource (CPU, memory, disk, network): utilization, saturation, errors. "High" means higher than the **baseline**.
- **Load average** = runnable + uninterruptible (`D`) tasks over 1, 5, 15 minutes; compare with `nproc`. High load with busy CPUs = **CPU bottleneck**; high load with idle CPUs and high `wa` = storage.
- `vmstat`: `r` run queue, `b` **blocked processes**, `si`/`so` **swapping**, `cs` **context switches**, `wa` **I/O wait**, `st` steal. Ignore the first line.
- `iostat -x`: `r_await`/`w_await` = **disk latency** (ms), `aqu-sz` = queue, `%util` near 100 = saturated. A `D`-state process cannot be killed until its I/O completes.
- **Out of memory**: "Killed process" in `journalctl -k`/`dmesg`, exit code 137; control with `MemoryMax=` and `oom_score_adj`/`OOMScoreAdjust=`.
- `nice`/`renice` range -20 (favored) to 19; only root can lower the value. Cgroup limits: `CPUQuota=`, `CPUWeight=`, `MemoryMax=`, `IOWriteIOPSMax=` via unit files, `systemd-run`, or `systemctl set-property`.
- **Slow startup**: `systemd-analyze`, `systemd-analyze blame`, `systemd-analyze critical-chain`.
- **Failed log-in attempts**: `journalctl -u ssh` (Rocky `sshd`), `/var/log/auth.log` (Rocky `/var/log/secure`), `lastb`; fix with `fail2ban` and key-only SSH.
- Network: **latency** = RTT, **jitter** = `mdev`/`StDev`, **packet drops** = loss, `ip -s link`, `tc -s qdisc`; **low throughput** = `iperf3`. `netem` emulates delay/jitter/loss, `tbf` limits rate.
- `curl -w`: slow `time_connect` = network (**slow response times**); fast connect, slow `time_starttransfer` = **slow application response**.
- **Random timeouts/disconnects** come in bursts (flapping links, IP conflicts, firewall or NAT idle timeouts). **Slow remote storage**: `nfsiostat` (RTT vs exe), `mountstats`, `nfsstat`.
- **Hardware errors**: `journalctl -k -p err`, MCE/EDAC/I/O errors in `dmesg`, `ras-mc-ctl --summary`, `smartctl -a`. **Sluggish terminal behavior**/**unresponsive** system: `uptime`, `vmstat`, `/proc/pressure/*`.

| Symptom | First tools to reach for |
|---|---|
| CPU bottleneck, high CPU usage, high load average | `uptime`, `top`, `mpstat -P ALL`, `pidstat -u`, `vmstat` (`r`) |
| High context switching | `vmstat` (`cs`), `pidstat -w`, `sar -w` |
| Swapping, out of memory | `free -h`, `swapon --show`, `vmstat` (`si`/`so`), `sar -W`, `journalctl -k \| grep -i oom` |
| High I/O wait, high disk latency, blocked processes | `vmstat` (`wa`, `b`), `iostat -x`, `iotop`, `pidstat -d`, `ps` state `D` |
| Slow startup | `systemd-analyze blame`, `systemd-analyze critical-chain` |
| High failed log-in attempts | `journalctl -u ssh`, `/var/log/auth.log`, `lastb`, `fail2ban-client status` |
| High latency, jitter, packet drops | `ping`, `mtr`, `ip -s link`, `tc -s qdisc`, `nstat` |
| Low throughput | `iperf3`, `ethtool`, `tc -s qdisc`, `iostat` (for disk) |
| Slow response times, slow application response | `curl -w`, `ss`, application logs, `strace` |
| Random timeouts, random disconnects | `ping -O`, `journalctl -k`, `ip -s link`, firewall/NAT logs |
| Slow remote storage response | `nfsiostat`, `mountstats`, `nfsstat` |
| Hardware errors | `journalctl -k -p err`, `dmesg`, `ras-mc-ctl`, `smartctl` |
| System unresponsiveness, sluggish terminal behavior | `uptime`, `vmstat`, `/proc/pressure/*`, `systemd-cgtop` |
| Exceeding baselines | `sar -u/-q/-r/-b/-d/-n DEV -f /var/log/sysstat/saDD` (Rocky: `/var/log/sa/`) |

**Review questions**

1. A 4-CPU server shows `load average: 12.4, 11.9, 10.2`, but `top` shows the CPUs 85% `wa` and only 5% `us`. What is the most likely cause?

    A. A CPU bottleneck caused by too many processes\
    B. Processes blocked waiting for slow storage\
    C. A memory leak causing the OOM killer to run\
    D. High context switching

2. `vmstat 2` shows `si` and `so` values in the thousands on every line, and users say the application is slow. Which statement is correct?

    A. The system is swapping because the workload needs more RAM than is available\
    B. The disk is full\
    C. The CPU is overheating\
    D. The network is dropping packets

3. An application process disappears without writing an error to its own log, and its parent reports exit code 137. Which command most quickly confirms the cause?

    A. `systemd-analyze blame`\
    B. `journalctl -k | grep -i 'killed process'`\
    C. `iostat -x 2`\
    D. `lastb`

4. Users report that a web application is slow. `curl -w '%{time_connect} %{time_starttransfer}\n'` prints `0.001 3.204`. Where should you look next?

    A. The network path, because the connection is slow\
    B. The DNS server\
    C. The application or its back end (database, API), because the server takes 3 seconds to answer\
    D. The client's network card

5. After adding a new service, a server takes 45 seconds longer to boot. Which command shows whether that service is on the chain of units the boot waited for?

    A. `systemd-analyze critical-chain`\
    B. `systemctl list-timers`\
    C. `sar -q`\
    D. `journalctl -k -p err`

6. NFS clients complain that file saves are very slow. `ping` to the NFS server is fast, the server's CPU and disks are idle, and `nfsiostat` shows `avg RTT` of 95 ms with `avg exe` of 96 ms. What does this tell you?

    A. The client is queuing requests internally; increase the number of client threads\
    B. The NFS server's disk is failing\
    C. Requests take about 95 ms on the network path, and something on the path treats NFS traffic differently than ping\
    D. The mount is read-only

::: answers
1. **B.** Linux counts tasks in uninterruptible sleep (`D`, waiting for I/O) in the load average, so high load with high `wa` and idle CPU means blocked processes waiting for storage; confirm with `iostat -x` and `vmstat` (`b` column).
2. **A.** Continuous swap-in and swap-out (`si`/`so`) means pages are being moved between RAM and swap all the time: the working set does not fit in memory.
3. **B.** Exit code 137 is 128 + 9 (`SIGKILL`), the signature of the OOM killer, which always logs "Killed process" in the kernel log.
4. **C.** The TCP connection took 1 ms, so the network is fine; the 3 seconds until the first byte are spent inside the server application or the systems it waits on.
5. **A.** `systemd-analyze critical-chain` shows the units the default target actually waited for, with their start time and duration; `blame` alone does not show whether a slow unit delayed boot.
6. **C.** RTT (network plus server time) is high while exe is almost the same, so the client is not queuing; with an idle server and a fast `ping`, the delay is on the network path for NFS traffic only (for example QoS, a firewall, or traffic shaping).
:::
