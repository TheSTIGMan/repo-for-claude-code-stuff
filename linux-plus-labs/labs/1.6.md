## Lab 1.6: Back Up and Restore a Linux Server {#lab-1-6}

::: labinfo
**Objective:** 1.6 Given a scenario, perform backup and restore operations for a Linux server.\
**Domain:** 1.0 System Management (23% of the exam)\

A backup you have never restored is only a hope. In this lab you back up `/etc` and a sample data directory with `tar` and `cpio`, take full and incremental backups, restore them to a scratch location and prove they match the original, compare the main compression tools, read compressed log files without unpacking them, copy data locally and to rocky-lab with `rsync`, and image a disk with `dd` and `ddrescue`. These are the exact tools the exam names, and the same tools you will use when a server breaks for real.

### What you'll practice

- Archiving: `cpio`, `tar` (create, extract, list, `z`/`j`/`J` compression, `--exclude`, preserving permissions, incremental backups)
- Compression: 7-Zip (`7z`), `bzip2`, `gzip`, `unzip` (and `zip`), `xz`
- Other: `dd`, `ddrescue`, `rsync`, `zcat`, `zgrep`, `zless`
- Restore testing and the 3-2-1 backup rule

### How it works

**Archiving versus compression.** These are two different jobs, and Linux keeps them separate:

- An **archiver** bundles many files and directories into *one* file, recording names, permissions, owners, and timestamps. `tar` (tape archive) and `cpio` (copy in/out) are archivers. They do not make data smaller.
- A **compressor** makes *one* stream of data smaller. `gzip`, `bzip2`, and `xz` are compressors. They work on single files, not directories.

So the classic Linux backup file `etc.tar.gz` is a tar archive that was then run through gzip, like putting papers in a box (`tar`) and then vacuum-sealing the box (`gzip`). `tar` can call the compressor for you with one letter: `z` for gzip, `j` for bzip2, `J` for xz. Tools from the Windows world, `zip` and 7-Zip (`7z`), do both jobs at once.

| Tool | Extension | Speed | Size | Notes |
|---|---|---|---|---|
| `gzip` | `.gz` | fastest | largest | Universal default; used for rotated logs |
| `bzip2` | `.bz2` | medium | smaller | Older; mostly replaced by xz |
| `xz` | `.xz` | slow | very small | Used for kernel and package archives |
| 7-Zip | `.7z` | slow | very small | LZMA2, like xz; package `7zip` on Ubuntu 24.04 |
| `zip` | `.zip` | fast | like gzip | Archive + compress; best for sharing with Windows users |

**Copying and syncing.** `rsync` copies files and, on later runs, sends only what changed. That makes it ideal for keeping a mirror of a directory on another disk or another server over SSH. It is not an archive format; the copy is just normal files.

**Block-level imaging.** `tar`, `cpio`, and `rsync` work with *files*. `dd` works with *raw blocks*: it copies bytes from one place to another without caring what they mean. You use it to copy a whole disk or partition, back up the boot sector, or create a blank disk image file. `ddrescue` does the same job for *failing* disks: it copies the good areas first, keeps a *mapfile* (a log of which areas were copied and which failed), and can resume or retry the bad spots later.

```{.diagram}
  FILE level                         BLOCK level
  tar / cpio / rsync                 dd / ddrescue
  +---------+                        +------------------------------+
  | /etc    | -- names, perms -->    | sector 0 | sector 1 | ...    |
  | /home   |    owners, data        |  (copies every byte, used or |
  +---------+                        |   empty, without reading the |
  small, selective, portable         |   file system)               |
                                     +------------------------------+
                                     exact clone, includes boot code
```

**Types of backup.** A *full* backup copies everything. An *incremental* backup copies only what changed since the last backup of any kind; it is small and fast, but a restore needs the full backup plus *every* incremental in order. A *differential* backup copies everything changed since the last full backup; a restore needs only the full plus the latest differential. GNU `tar` makes incrementals with `--listed-incremental`, using a *snapshot file* that remembers what it saw last time.

**The 3-2-1 rule.** A widely used guideline for backups that survive real disasters:

- **3** copies of your data (the original plus two backups),
- on **2** different types of storage (for example the server disk and a NAS or tape),
- with **1** copy off-site (another building, another region, or the cloud).

Many teams add "1 copy offline or immutable" (ransomware cannot encrypt what it cannot reach) and "0 errors after a restore test". A backup is only proven when you have restored it and checked the result, which is what you will do in this lab every time.

**Safety with dd.** `dd` does exactly what you tell it, instantly, with no "Are you sure?". Swapping `if=` (input file) and `of=` (output file) overwrites the disk you meant to save. People joke that `dd` stands for "disk destroyer". Always run `lsblk` first, read the command twice, and take a VM snapshot.

#### Task 2: Create full backups with tar

1. Back up all of `/etc` into a gzip-compressed archive. You need `sudo` because some files in `/etc` (such as `/etc/shadow`) are readable only by root.

    ```bash
    sudo tar -czpf backups/etc-full.tar.gz /etc
    ls -lh backups/etc-full.tar.gz
    ```

    ```{.output}
    tar: Removing leading `/' from member names
    -rw-r--r-- 1 root root 1.3M Oct 10 10:02 backups/etc-full.tar.gz
    ```

    ::: explain
    **What just happened:** `tar` options are single letters that can be grouped: `-c` create a new archive, `-z` compress it with gzip, `-p` preserve permissions, and `-f` names the archive file, so `f` must come last, right before the file name. The message about the leading `/` is normal and protective: tar stores `etc/hostname` instead of `/etc/hostname`, so a later extract goes into the *current* directory instead of overwriting the live `/etc`. Your size will differ.
    :::

2. This archive contains password hashes and private keys from `/etc`. Protect it like the original.

    ```bash
    sudo chmod 600 backups/etc-full.tar.gz
    ```

    ::: warning
    Backups are a favorite target for attackers because they hold everything in one file. Restrict permissions, and encrypt backups that leave the server (for example with `gpg --symmetric` or an encrypting backup tool).
    :::

3. List the contents without extracting.

    ```bash
    sudo tar -tzf backups/etc-full.tar.gz | head -n 5
    sudo tar -tzvf backups/etc-full.tar.gz etc/shadow etc/hostname
    ```

    ```{.output}
    etc/
    etc/fstab
    etc/crypttab
    etc/hostname
    etc/ssh/
    -rw-r----- root/shadow    1024 2026-10-10 09:12 etc/shadow
    -rw-r--r-- root/root        11 2026-10-10 08:40 etc/hostname
    ```

    ::: explain
    **What just happened:** `-t` lists the table of contents. Adding `-v` (verbose) shows permissions, owner/group, size, and date, so you can confirm tar recorded `/etc/shadow` with mode `640` and group `shadow`. Naming specific members after the archive limits the listing to those paths. Listing an archive is a quick health check: a damaged archive fails with an error.
    :::

4. Back up the data directory, leaving out the cache, and try all three compressors.

    ```bash
    tar -czvf backups/data.tar.gz --exclude='data/cache' data
    tar -cjf backups/data.tar.bz2 --exclude='data/cache' data
    tar -cJf backups/data.tar.xz --exclude='data/cache' data
    ls -l backups/data.tar.*
    ```

    ```{.output}
    data/
    data/docs/
    data/docs/numbers.txt
    data/docs/report.txt
    data/docs/secret.txt
    data/scripts/
    data/scripts/nightly.sh
    -rw-rw-r-- 1 student student  6374 Oct 10 10:03 backups/data.tar.bz2
    -rw-rw-r-- 1 student student 11609 Oct 10 10:03 backups/data.tar.gz
    -rw-rw-r-- 1 student student  2228 Oct 10 10:03 backups/data.tar.xz
    ```

    ::: explain
    **What just happened:** `-v` printed each file as it was added. `--exclude='data/cache'` skipped the cache directory; patterns can also use wildcards, such as `--exclude='*.tmp'`. The only difference between the three commands is the compression letter: `z` (gzip, `.tar.gz` or `.tgz`), `j` (bzip2, `.tar.bz2`), and `J` (xz, `.tar.xz`). When extracting, modern GNU tar detects the compression automatically, so `tar -xf file.tar.xz` works too. Here xz produced by far the smallest file, because `numbers.txt` is very repetitive text, which LZMA handles especially well. The exact byte counts on your system will be slightly different.
    :::

::: tip
Put the date in backup names so they sort and never overwrite each other: `tar -czf backups/etc-$(date +%F).tar.gz /etc`. `$(date +%F)` is *command substitution*: the shell runs `date +%F` and inserts its output, such as `2026-10-10`.
:::

::: checkpoint
**Checkpoint:** `ls backups` shows `etc-full.tar.gz` plus three `data.tar` files, and `tar -tf backups/data.tar.xz | grep -c cache` prints `0`.
:::

#### Task 3: Restore to a scratch location and prove it matches

Never test a restore by extracting over the live system. Extract into an empty directory, compare, and only then copy what you need back.

1. Extract the `/etc` backup into `restore/`.

    ```bash
    sudo tar -xzpf backups/etc-full.tar.gz -C restore
    ls restore
    sudo ls -l restore/etc/shadow /etc/shadow
    ```

    ```{.output}
    etc
    -rw-r----- 1 root shadow 1024 Oct 10 09:12 /etc/shadow
    -rw-r----- 1 root shadow 1024 Oct 10 09:12 restore/etc/shadow
    ```

    ::: explain
    **What just happened:** `-x` extracts, and `-C restore` changes into the `restore` directory first, so the files land in `restore/etc/...`. Because you ran tar as root, it restored the original owners (`root:shadow`), permissions (`-p`), and timestamps. Run as a normal user, tar would make you the owner of every file and apply your umask unless you add `-p`; only root can restore other users' ownership.
    :::

2. Compare the restored copy with the original.

    ```bash
    sudo diff -r --no-dereference /etc restore/etc && echo "RESTORE MATCHES"
    ```

    ```{.output}
    RESTORE MATCHES
    ```

    ::: explain
    **What just happened:** `diff -r` compares two directory trees recursively and prints any file that differs or exists in only one place. `--no-dereference` compares symbolic links as links instead of following them (some links in `/etc` point outside it, such as `/etc/resolv.conf`). No output means the trees are identical, so `&&` printed the message. If something in `/etc` changed after the backup (for example a package update), `diff` lists it, which is also useful: it shows exactly what changed.
    :::

3. Restore a single file, the most common real-world request ("I deleted my config, can you get it back?").

    ```bash
    mkdir -p restore-one
    sudo tar -xzf backups/etc-full.tar.gz -C restore-one etc/hostname
    cat restore-one/etc/hostname
    ```

    ```{.output}
    ubuntu-lab
    ```

    ::: explain
    **What just happened:** After the archive name you can list member paths to extract only those. The path must match what `tar -t` shows (`etc/hostname`, without a leading `/`). Use `--wildcards 'etc/ssh/*'` to extract a pattern.
    :::

4. Restore the data backup as a normal user and check the permissions survived.

    ```bash
    mkdir -p restore-data
    tar -xJf backups/data.tar.xz -C restore-data
    ls -l restore-data/data/docs/secret.txt restore-data/data/scripts/nightly.sh
    diff -r --exclude=cache data restore-data/data && echo "DATA MATCHES"
    ```

    ```{.output}
    -rw------- 1 student student 21 Oct 10 10:00 restore-data/data/docs/secret.txt
    -rwxr-x--- 1 student student 35 Oct 10 10:00 restore-data/data/scripts/nightly.sh
    DATA MATCHES
    ```

::: explain
**What just happened:** You restored the xz archive as `student` without `sudo`, and the modes `600` and `750` survived, because the files already belonged to you. `--exclude=cache` told `diff` to ignore the cache directory, which you deliberately left out of the backup. This is a complete restore test: extract to a scratch location, compare with the original, and check permissions. Doing it regularly is what turns a backup into a *proven* backup.
:::

::: checkpoint
**Checkpoint:** Both `diff` commands printed their "MATCHES" message, and `restore-data/data/docs/secret.txt` still has mode `-rw-------`.
:::

#### Task 4: Take incremental backups with tar

1. Take a level-0 (full) backup that also records a snapshot file.

    ```bash
    tar -czvf backups/data-level0.tar.gz --exclude='data/cache' \
        --listed-incremental=backups/data.snar data
    ```

    ```{.output}
    tar: data: Directory is new
    tar: data/docs: Directory is new
    tar: data/scripts: Directory is new
    data/
    data/docs/
    data/scripts/
    data/docs/numbers.txt
    data/docs/report.txt
    data/docs/secret.txt
    data/scripts/nightly.sh
    ```

    ::: explain
    **What just happened:** `--listed-incremental=backups/data.snar` tells GNU tar to keep a *snapshot file* (`.snar`). Because the file did not exist, tar made a full backup and wrote down every directory and file it saw, with timestamps. "Directory is new" just means "not in the snapshot yet". The backslash `\` at the end of the first line continues the command on the next line.
    :::

2. Simulate a day of changes: add a file, delete a file, and modify a file.

    ```bash
    echo "new customer list" > data/docs/new.txt
    rm data/docs/report.txt
    echo 5001 >> data/docs/numbers.txt
    ```

3. Take a level-1 (incremental) backup using the same snapshot file.

    ```bash
    tar -czvf backups/data-level1.tar.gz --exclude='data/cache' \
        --listed-incremental=backups/data.snar data
    ls -l backups/data-level*.tar.gz
    ```

    ```{.output}
    data/
    data/docs/
    data/scripts/
    data/docs/new.txt
    data/docs/numbers.txt
    -rw-rw-r-- 1 student student 11781 Oct 10 10:06 backups/data-level0.tar.gz
    -rw-rw-r-- 1 student student 11540 Oct 10 10:07 backups/data-level1.tar.gz
    ```

    ::: explain
    **What just happened:** tar compared the files with the snapshot and stored only the new and changed files (`new.txt` and `numbers.txt`), plus the directory entries. It also recorded that `report.txt` is gone. The snapshot file was updated, so the next run would be level 2, containing only changes since now. Here the two archives are similar in size only because `numbers.txt` is most of the data; on a real server the incremental is usually far smaller. To make more level-1 backups against the same full backup (a differential style), copy the level-0 `.snar` file before each run and use the copy.
    :::

4. Restore the chain in order into an empty directory.

    ```bash
    mkdir -p restore-incr
    tar -xzvf backups/data-level0.tar.gz --listed-incremental=/dev/null -C restore-incr
    ls restore-incr/data/docs
    tar -xzvf backups/data-level1.tar.gz --listed-incremental=/dev/null -C restore-incr
    ls restore-incr/data/docs
    diff -r --exclude=cache data restore-incr/data && echo "INCREMENTAL RESTORE MATCHES"
    ```

    ```{.output}
    ...
    numbers.txt  report.txt  secret.txt
    data/
    data/docs/
    tar: Deleting 'data/docs/report.txt'
    data/scripts/
    data/docs/new.txt
    data/docs/numbers.txt
    new.txt  numbers.txt  secret.txt
    INCREMENTAL RESTORE MATCHES
    ```

    ::: explain
    **What just happened:** You restored the full backup first, then the incremental on top of it. `--listed-incremental=/dev/null` tells tar "this is an incremental archive, apply its directory information" without needing the snapshot file. Notice `Deleting 'data/docs/report.txt'`: tar removed the file that had been deleted between the backups, so the result matches the live directory exactly. Restoring incrementals out of order, or skipping one, gives the wrong result.
    :::

::: checkpoint
**Checkpoint:** `ls restore-incr/data/docs` shows `new.txt numbers.txt secret.txt` (no `report.txt`), and the final `diff` printed its success message.
:::

#### Task 5: Archive with cpio

`cpio` is older than tar and works differently: it does not search directories itself. It reads a list of file names on standard input, usually from `find`. You meet it in the real world inside initramfs images and RPM packages.

1. Create a cpio archive of the data directory.

    ```bash
    find data | cpio -ov -H newc > backups/data.cpio
    ```

    ```{.output}
    data
    data/cache
    data/cache/blob.tmp
    data/scripts
    data/scripts/nightly.sh
    data/docs
    data/docs/new.txt
    data/docs/secret.txt
    data/docs/numbers.txt
    1074 blocks
    ```

    ::: explain
    **What just happened:** `find data` prints every path under `data`, one per line, and the pipe feeds that list to `cpio`. `-o` is *copy-out* mode (create an archive), `-v` lists each file, and `-H newc` chooses the modern "new ASCII" format (the one initramfs uses), which handles large files and inode numbers well. cpio writes the archive to standard output, so you redirected it into a file with `>`. The block count is the archive size in 512-byte blocks. To leave out the cache you would filter the list, for example `find data -path data/cache -prune -o -print`.
    :::

2. List the archive and extract it into an empty directory.

    ```bash
    cpio -itv < backups/data.cpio
    mkdir -p restore-cpio && cd restore-cpio
    cpio -idmv < ../backups/data.cpio
    cd ..
    diff -r data restore-cpio/data && echo "CPIO MATCHES"
    ```

    ```{.output}
    drwxrwxr-x   5 student  student         0 Oct 10 10:00 data
    ...
    -rw-------   1 student  student        21 Oct 10 10:00 data/docs/secret.txt
    ...
    CPIO MATCHES
    ```

    ::: explain
    **What just happened:** `-i` is *copy-in* mode (extract or list), and `-t` with it means "only list the table of contents". cpio reads the archive from standard input, hence `<`. For the extract, `-d` creates directories as needed and `-m` keeps the original modification times. Unlike tar, cpio has no `-C` option, so you `cd` into the target directory first.
    :::

3. Use pass-through mode to copy files that match a pattern into another directory tree.

    ```bash
    mkdir -p copy-scripts
    find data -name '*.sh' | cpio -pdmv copy-scripts
    ls -l copy-scripts/data/scripts
    ```

    ```{.output}
    copy-scripts/data/scripts/nightly.sh
    1 block
    -rwxr-x--- 1 student student 35 Oct 10 10:00 nightly.sh
    ```

    ::: explain
    **What just happened:** `-p` (pass-through) copies the listed files straight into a directory, keeping their relative paths and attributes, without creating an archive. Combined with `find`'s power (by name, age, owner, size), this is a precise way to copy a selection of files.
    :::

::: tip
You can look inside Ubuntu's initramfs, which is built from cpio archives, with `lsinitramfs /boot/initrd.img-$(uname -r) | head`.
:::

::: checkpoint
**Checkpoint:** `cpio -it < backups/data.cpio | wc -l` prints `9`, and `restore-cpio/data` matches `data`.
:::

#### Task 6: Compare gzip, bzip2, xz, 7-Zip, and zip

1. Build a realistic test file: a tar archive of Python's standard library (thousands of text files, present on every Ubuntu 24.04 system).

    ```bash
    cd ~/labs/1.6
    mkdir -p compress && cd compress
    tar -cf sample.tar --exclude=__pycache__ /usr/lib/python3.12 2>/dev/null
    ls -lh sample.tar
    ```

    ```{.output}
    -rw-rw-r-- 1 student student 41M Oct 10 10:10 sample.tar
    ```

    Your size may be somewhat different; that does not matter.

2. Compress it with each tool and time each one. The `-k` option keeps the original file so the next tool can use it.

    ```bash
    time gzip -k sample.tar
    time bzip2 -k sample.tar
    time xz -k sample.tar
    time 7z a sample.tar.7z sample.tar
    time zip sample.zip sample.tar
    ls -l sample.*
    ```

    ```{.output}
    real    0m1.770s
    ...
    real    0m3.948s
    ...
    real    0m20.745s
    ...
    real    0m10.467s
    ...
      adding: sample.tar (deflated 74%)
    real    0m1.908s
    ...
    -rw-rw-r-- 1 student student 42854400 Oct 10 10:10 sample.tar
    -rw-rw-r-- 1 student student  6888671 Oct 10 10:12 sample.tar.7z
    -rw-rw-r-- 1 student student  9716209 Oct 10 10:11 sample.tar.bz2
    -rw-rw-r-- 1 student student 11172117 Oct 10 10:11 sample.tar.gz
    -rw-rw-r-- 1 student student  7563380 Oct 10 10:11 sample.tar.xz
    -rw-rw-r-- 1 student student 11172258 Oct 10 10:12 sample.zip
    ```

    ::: explain
    **What just happened:** `time` runs a command and reports how long it took; `real` is wall-clock time. Fill in your own numbers, but the pattern is typical: gzip and zip are fastest with the biggest output (they use the same "deflate" algorithm, which is why their sizes are almost identical), bzip2 is in the middle, and xz and 7-Zip (both based on LZMA) produce the smallest files but take the longest. 7-Zip was faster than xz here because it uses several CPU threads by default; `xz -T0` also uses all cores. All of them are *lossless*: decompressing gives back the exact original bytes. Each tool accepts a level from `-1` (fastest) to `-9` (smallest); the default is `-6` for gzip and xz and `-9` for bzip2.
    :::

3. Inspect the compressed files without decompressing.

    ```bash
    gzip -l sample.tar.gz
    xz -l sample.tar.xz
    unzip -l sample.zip
    7z l sample.tar.7z | tail -n 3
    ```

    ```{.output}
             compressed        uncompressed  ratio uncompressed_name
               11172117            42854400  73.9% sample.tar
    Strms  Blocks   Compressed Uncompressed  Ratio  Check   Filename
        1       1   7386.1 KiB     40.9 MiB  0.176  CRC64   sample.tar.xz
    Archive:  sample.zip
      Length      Date    Time    Name
    ---------  ---------- -----   ----
     42854400  2026-10-10 10:10   sample.tar
    ---------                     -------
     42854400                     1 file
    ------------------- ----- ------------ ------------  ------------------------
    2026-10-10 10:10:38           42854400      6888541  1 files
    ```

    ::: explain
    **What just happened:** `gzip -l` shows the space saved (73.9% smaller). `xz -l` shows the ratio as a fraction (0.176 means the file is 17.6% of the original). `unzip -l` and `7z l` list archive contents. Listing is a quick way to see what an archive holds before you extract it.
    :::

4. Decompress and verify the files are identical to the original.

    ```bash
    mkdir -p out
    gunzip -c sample.tar.gz > out/from-gz.tar
    bzip2 -dc sample.tar.bz2 > out/from-bz2.tar
    xz -dc sample.tar.xz > out/from-xz.tar
    7z x sample.tar.7z -oout/7z > /dev/null
    unzip -q sample.zip -d out/zip
    sha256sum sample.tar out/from-*.tar out/7z/sample.tar out/zip/sample.tar
    ```

    **What just happened:** `zip -r` recurses into directories, and `-x` excludes matching paths. `7z a` adds files to an archive, `-xr'!cache'` recursively excludes anything named `cache`, and `7z t` tests the archive's integrity. #### Task 7: Read compressed logs with zcat, zgrep, and zless

`logrotate` compresses old logs with gzip to save space, so on a real server yesterday's evidence is usually in a `.gz` file. The `z` tools let you read those files without unpacking them.

1. Look for rotated, compressed logs on your system.

    ```bash
    ls -l /var/log/*.gz /var/log/*/*.gz 2>/dev/null | head
    ```

    A VM that has been running for a while shows files such as `/var/log/syslog.2.gz` or `/var/log/apt/history.log.1.gz`. A brand-new VM may show nothing yet, which is why you will also build your own.

2. Create a practice set of rotated logs, named the way `logrotate` names them.

    ```bash
    mkdir -p ~/labs/1.6/logs && cd ~/labs/1.6/logs
    printf '%s\n' "10:01 INFO  service started" "10:05 ERROR disk /dev/sdb not found" \
        "10:09 INFO  backup completed" > app.log
    printf '%s\n' "09:01 INFO  service started" "09:30 WARN  disk 85% full" > app.log.1
    printf '%s\n' "08:00 INFO  service started" "08:12 ERROR backup failed: disk full" \
        "08:15 ERROR backup failed: disk full" > app.log.2
    printf '%s\n' "07:00 INFO  service started" "07:44 ERROR login failed for root" > app.log.3
    gzip app.log.2 app.log.3
    ls -l
    ```

    ```{.output}
    -rw-rw-r-- 1 student student 93 Oct 10 10:20 app.log
    -rw-rw-r-- 1 student student 54 Oct 10 10:20 app.log.1
    -rw-rw-r-- 1 student student 99 Oct 10 10:20 app.log.2.gz
    -rw-rw-r-- 1 student student 92 Oct 10 10:20 app.log.3.gz
    ```

    ::: explain
    **What just happened:** `printf '%s\n'` prints each argument on its own line, a tidy way to write several lines at once. `gzip` replaced each file with a compressed `.gz` version (it deletes the original unless you add `-k`). This matches the default rotation on Ubuntu: the current log, `.1` uncompressed (because of the `delaycompress` setting), and older ones compressed.
    :::

3. Read, search, and page through the compressed logs.

    ```bash
    cat app.log.2.gz | head -c 40; echo
    zcat app.log.2.gz
    zgrep ERROR app.log*
    zgrep -c ERROR app.log.*.gz
    zless app.log.3.gz
    ```

    ```{.output}
    ...binary garbage...
    08:00 INFO  service started
    08:12 ERROR backup failed: disk full
    08:15 ERROR backup failed: disk full
    app.log:10:05 ERROR disk /dev/sdb not found
    app.log.2.gz:08:12 ERROR backup failed: disk full
    app.log.2.gz:08:15 ERROR backup failed: disk full
    app.log.3.gz:07:44 ERROR login failed for root
    app.log.2.gz:2
    app.log.3.gz:1
    ```

    Press `q` to leave `zless`.

    ::: explain
    **What just happened:** `cat` on a `.gz` file prints compressed bytes, which is unreadable. `zcat` decompresses to standard output (like `gunzip -c`) and leaves the file untouched. `zgrep` takes the same options as `grep` (`-i`, `-c`, `-v`, `-E`) and works on both compressed and plain files, so `app.log*` searched all four at once. `zless` opens a compressed file in `less`, with the same keys (`/` to search, `q` to quit). The same family exists for other formats: `bzcat`/`bzgrep`/`bzless` for `.bz2` and `xzcat`/`xzgrep`/`xzless` for `.xz`.
    :::

4. If step 1 found real rotated logs, try the tools on them. For example:

    ```bash

    sudo zcat /var/log/syslog.2.gz | tail -n 5
    ```

    `-h` hides the file name prefix. Adjust the file names to match what `ls` showed.

#### Task 8: Synchronize data with rsync, locally and to rocky-lab

1. Make a local mirror and learn the trailing-slash rule.

    ```bash
    cd ~/labs/1.6
    rsync -av data mirror1/
    rsync -av data/ mirror2/
    ls mirror1 mirror2
    ```

    ```{.output}
    sending incremental file list
    created directory mirror1
    data/
    data/cache/
    ...
    mirror1:
    data

    mirror2:
    cache  docs  scripts
    ```

    ::: explain
    **What just happened:** `-a` (archive) is shorthand for `-rlptgoD`: recurse, copy symlinks as symlinks, and keep permissions, times, group, owner (owner only when run as root), and device files. `-v` lists what is copied. Now the important rule. Without a trailing slash on the *source* (`data`), rsync copies the directory itself, so you get `mirror1/data/...`. With a trailing slash (`data/`), rsync copies the directory's *contents*, so you get `mirror2/docs/...`. Think of `data/` as "everything inside data". A slash on the destination makes no difference. Getting this wrong is the most common rsync mistake, and with `--delete` it can be expensive.
    :::

2. Run the same sync again, then change a few files and preview the next run.

    ```bash
    rsync -av data/ mirror2/
    rm data/docs/new.txt
    echo "draft" > data/docs/plan.txt
    rsync -av --delete --dry-run data/ mirror2/
    ```

    ```{.output}
    sending incremental file list

    sent 261 bytes  received 15 bytes  552.00 bytes/sec
    total size is 548,246  speedup is 1,986.40
    sending incremental file list
    deleting docs/new.txt
    docs/
    docs/plan.txt

    sent 287 bytes  received 44 bytes  662.00 bytes/sec
    total size is 548,242  speedup is 1,656.32 (DRY RUN)
    ```

    ::: explain
    **What just happened:** The second identical run copied nothing: rsync compares size and modification time and skips files that have not changed, which is why it is so fast for repeated backups. `--delete` removes files from the destination that no longer exist in the source, making an exact mirror. `--dry-run` (`-n`) shows what *would* happen, marked `(DRY RUN)`, without changing anything. Always dry-run a `--delete` command first.
    :::

3. Apply the changes for real and verify.

    ```bash
    rsync -av --delete data/ mirror2/
    diff -r data mirror2 && echo "MIRROR MATCHES"
    ```

    ::: warning
    `--delete` mirrors *deletions* too. If someone deletes a file by mistake (or ransomware encrypts everything), the next sync faithfully copies that damage. A mirror is not a backup on its own; keep versioned copies as well (for example dated tar archives, or `rsync --backup --backup-dir=...`).
    :::

4. Copy the data to rocky-lab over SSH. First make sure `rsync` is installed there, because rsync must run on **both** ends.

#### Task 9: Image disks with dd and ddrescue

::: warning
Take a snapshot of ubuntu-lab now. This task writes directly to the extra disk. Run `lsblk` and make sure the disk you use is an **empty 5 GB lab disk** with no mount points. This book uses `/dev/sdb`; if your extra disks are named differently (`/dev/vdb`, `/dev/nvme0n2`), substitute your name in **every** command. Writing to the wrong device destroys its data instantly.
:::

1. Identify the disk, then create a small partition with a file system and a file on it.

    ```bash
    lsblk
    sudo parted -s /dev/sdb mklabel msdos mkpart primary ext4 1MiB 201MiB
    sudo mkfs.ext4 -q -L labdata /dev/sdb1
    sudo mkdir -p /mnt/lab16
    sudo mount /dev/sdb1 /mnt/lab16
    echo "important data" | sudo tee /mnt/lab16/important.txt
    sudo umount /mnt/lab16
    lsblk /dev/sdb
    ```

    ```{.output}
    important data
    NAME   MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
    sdb      8:16   0    5G  0 disk
    └─sdb1   8:17   0  200M  0 part
    ```

    ::: explain
    **What just happened:** `parted -s` (script mode, no questions) wrote an MBR (`msdos`) partition table and one 200 MiB partition starting at 1 MiB. `mkfs.ext4 -q -L labdata` formatted it as ext4 with the label `labdata`. You mounted it, wrote a test file, and unmounted it. Unmounting matters: imaging a mounted, changing file system can give an inconsistent copy. (Lab 1.3 covers partitioning in depth.)
    :::

2. Back up the MBR, the first 512-byte sector of the disk.

    ```bash
    cd ~/labs/1.6
    sudo dd if=/dev/sdb of=backups/sdb-mbr.bin bs=512 count=1
    file backups/sdb-mbr.bin
    od -A d -t x1 -j 510 -N 2 backups/sdb-mbr.bin
    ```

    ```{.output}
    1+0 records in
    1+0 records out
    512 bytes copied, 0.0003 s, 1.6 MB/s
    backups/sdb-mbr.bin: DOS/MBR boot sector; partition 1 : ID=0x83, ... startsector 2048, 409600 sectors
    0000510 55 aa
    0000512
    ```

    ::: explain
    **What just happened:** `dd` copies data in blocks. `if=` is the input file (here the whole disk), `of=` is the output file, `bs=512` sets the block size to 512 bytes, and `count=1` copies just one block. The MBR holds 446 bytes of boot code, a 64-byte partition table (four entries), and the 2-byte signature `55 aa`. `file` recognized it, and `od` (octal dump) showed the two bytes at offset 510 in hexadecimal. `dd` reports records in and out when it finishes. GPT disks keep their partition table in the first 34 sectors and a backup copy at the end of the disk, so for GPT you would back up more (or use `sgdisk --backup`); for any disk, `sudo sfdisk -d /dev/sdb > table.txt` saves the partition layout as text.
    :::

3. Image the partition to a file, both raw and compressed, and record a checksum.

    ```bash
    sudo dd if=/dev/sdb1 of=backups/sdb1.img bs=4M status=progress
    sudo dd if=/dev/sdb1 bs=4M status=none | gzip > backups/sdb1.img.gz
    ls -lh backups/sdb1.img*
    sudo sha256sum /dev/sdb1 backups/sdb1.img
    ```

    ```{.output}
    50+0 records in
    50+0 records out
    209715200 bytes (210 MB, 200 MiB) copied, 0.61 s, 344 MB/s
    -rw-r--r-- 1 root    root    200M Oct 10 10:40 backups/sdb1.img
    -rw-rw-r-- 1 student student 212K Oct 10 10:40 backups/sdb1.img.gz
    3b7e...c1d0  /dev/sdb1
    3b7e...c1d0  backups/sdb1.img
    ```

    ::: explain
    **What just happened:** The first `dd` copied every byte of the partition into `sdb1.img`. `bs=4M` reads 4 MiB at a time, which is much faster than the default of 512 bytes, and `status=progress` shows live progress. The second `dd` has no `of=`, so it wrote to standard output; the pipe sent the bytes through `gzip`. Because most of the partition is empty (zeros), the compressed image is tiny. The matching checksums prove the image is exact. The raw image is owned by root because `sudo dd` created it; the `.gz` file is yours because your shell created it through the redirection.
    :::

4. Create a blank disk image file and use it like a disk.

    ```bash
    dd if=/dev/zero of=backups/blank.img bs=1M count=64 status=progress
    mkfs.ext4 -q backups/blank.img
    sudo mount -o loop backups/blank.img /mnt/lab16
    df -h /mnt/lab16
    sudo umount /mnt/lab16
    ```

    ```{.output}
    64+0 records in
    64+0 records out
    67108864 bytes (67 MB, 64 MiB) copied, 0.05 s, 1.3 GB/s
    Filesystem      Size  Used Avail Use% Mounted on
    /dev/loop8       56M   14K   51M   1% /mnt/lab16
    ```

    ::: explain
    **What just happened:** `/dev/zero` produces endless zero bytes, so this `dd` created a 64 MiB file full of zeros. You formatted the *file* with ext4 and mounted it with `-o loop`, which makes the kernel present the file as a block device (a *loop device* such as `/dev/loop8`; the number varies, because snap packages already use the first few). Virtual machine disks, ISO images, and swap files are created this same way. (`fallocate -l 64M file` or `truncate -s 64M file` create such files faster.)
    :::

5. Disaster 1: destroy the partition table, then restore it from your MBR backup.

    ```bash
    sudo wipefs -a /dev/sdb
    lsblk /dev/sdb
    ```

    ```{.output}
    /dev/sdb: 2 bytes were erased at offset 0x000001fe (dos): 55 aa
    /dev/sdb: calling ioctl to re-read partition table: Success
    NAME MAJ:MIN RM SIZE RO TYPE MOUNTPOINTS
    sdb    8:16   0   5G  0 disk
    ```

    The partition is gone. Restore the MBR and ask the kernel to re-read it:

    ```bash
    sudo dd if=backups/sdb-mbr.bin of=/dev/sdb bs=512 count=1
    sudo partprobe /dev/sdb
    lsblk /dev/sdb
    sudo mount /dev/sdb1 /mnt/lab16 && cat /mnt/lab16/important.txt
    sudo umount /mnt/lab16
    ```

    ```{.output}
    1+0 records in
    1+0 records out
    512 bytes copied, 0.0004 s, 1.3 MB/s
    NAME   MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
    sdb      8:16   0    5G  0 disk
    └─sdb1   8:17   0  200M  0 part
    important data
    ```

    ::: explain
    **What just happened:** `wipefs -a` erased the MBR signature, so the kernel no longer saw a partition table. Note the direction of the restore: now the *image* is `if=` and the *disk* is `of=`. `partprobe` tells the kernel to re-read the partition table, and `sdb1` came back with its data intact, because only the table was damaged, not the file system.
    :::

6. Disaster 2: destroy the file system, then restore the partition image.

    ```bash
    sudo wipefs -a /dev/sdb1
    sudo mount /dev/sdb1 /mnt/lab16
    ```

    ```{.output}
    /dev/sdb1: 2 bytes were erased at offset 0x00000438 (ext4): 53 ef
    mount: /mnt/lab16: wrong fs type, bad option, bad superblock on /dev/sdb1, missing
    codepage or helper program, or other error.
    ```

    Restore from the compressed image, then mount and check:

    ```bash
    zcat backups/sdb1.img.gz | sudo dd of=/dev/sdb1 bs=4M status=progress
    sudo mount /dev/sdb1 /mnt/lab16 && cat /mnt/lab16/important.txt
    ```

    ```{.output}
    0+3200 records out
    209715200 bytes (210 MB, 200 MiB) copied, 0.9 s, 233 MB/s

    ```

    ::: explain
    **What just happened:** `wipefs` erased the ext4 "magic number", so `mount` could not recognize the file system. `zcat` decompressed the image to standard output, and `sudo dd of=/dev/sdb1` wrote that stream onto the partition. `0+3200 records` means dd received only partial blocks from the pipe (a pipe delivers data in small pieces), which is normal; your numbers may differ. 7. Image the partition with `ddrescue`, the tool you would use on a failing disk.

    ```bash
    sudo ddrescue /dev/sdb1 backups/sdb1-rescue.img backups/sdb1.map

    ```

    ```{.output}
    GNU ddrescue 1.27
    Press Ctrl-C to interrupt
         ipos:  209649 kB, non-trimmed:        0 B,  current rate:    209 MB/s
         opos:  209649 kB, non-scraped:        0 B,  average rate:    209 MB/s
    ```

    ::: explain
    **What just happened:** The arguments are input, output, and *mapfile*. ddrescue copied everything and wrote the mapfile, which records each area of the disk and its status: `+` means rescued, `-` bad sector, `?` not tried yet, `*` and `/` partly processed. ### Exam corner

- `tar` modes: `-c` create, `-x` extract, `-t` list; `-f file` names the archive; `-v` verbose; `-C dir` extracts into `dir`; `-p` preserves permissions; `--exclude=PATTERN` skips files.
- `tar` compression: `-z` gzip (`.tar.gz`/`.tgz`), `-j` bzip2 (`.tar.bz2`), `-J` xz (`.tar.xz`). GNU tar strips the leading `/` so restores go into the current directory.
- Incremental tar: `--listed-incremental=file.snar`; restore the full archive first, then each incremental in order (with `--listed-incremental=/dev/null`).
- `cpio` reads file names from stdin: `find dir | cpio -ov > a.cpio` (copy-out), `cpio -idv < a.cpio` (copy-in, extract), `cpio -it < a.cpio` (list), `cpio -pdm dest` (pass-through copy). initramfs images are cpio archives.
- Compression speed versus size: `gzip` (fastest, largest) < `bzip2` < `xz` (slowest, smallest). Decompress with `gunzip`/`gzip -d`, `bunzip2`/`bzip2 -d`, `unxz`/`xz -d`; `-k` keeps the original, `-c` writes to stdout, `-1` to `-9` set the level.
- 7-Zip: `7z a` add, `7z l` list, `7z x` extract (`-oDIR`), `7z t` test; Ubuntu 24.04 package `7zip`. `zip -r` and `unzip` (`-l` list, `-d DIR` destination) for Windows-friendly archives.
- `zcat`, `zgrep`, `zless` read gzip files without decompressing them on disk; `bzcat`/`xzcat` are the bzip2/xz equivalents.
- `rsync -av src/ dest/`: `-a` keeps permissions, times, links, ownership; a trailing slash on the source copies its *contents*; `--delete` mirrors deletions; `--dry-run`/`-n` previews; `-z` compresses; `user@host:path` uses SSH.
- `dd if=INPUT of=OUTPUT bs=SIZE count=N status=progress`: block-level copy. MBR = first 512 bytes (`bs=512 count=1`). Swapping `if` and `of` destroys data.
- `ddrescue INPUT OUTPUT MAPFILE` images failing disks, skips bad areas first, and resumes using the mapfile; package `gddrescue` on Ubuntu.
- 3-2-1 rule: 3 copies, 2 media types, 1 off-site. A backup is not proven until a restore has been tested.

**Review questions**

1. Which command creates a bzip2-compressed archive of `/home` named `home.tar.bz2`?
    - A. `tar -czf home.tar.bz2 /home`
    - B. `tar -cjf home.tar.bz2 /home`
    - C. `tar -cJf home.tar.bz2 /home`
    - D. `tar -xjf home.tar.bz2 /home`
2. You run `rsync -a /srv/web /backup/` and find your files in `/backup/web/`, but you wanted them directly in `/backup/`. What should you change?
3. An administrator needs to search last week's compressed log `/var/log/auth.log.2.gz` for "Failed password" without decompressing it. Which command should be used?
    - A. `grep "Failed password" /var/log/auth.log.2.gz`
    - B. `zcat -l /var/log/auth.log.2.gz`
    - C. `zgrep "Failed password" /var/log/auth.log.2.gz`
    - D. `gunzip /var/log/auth.log.2.gz`
4. Which command backs up only the master boot record of `/dev/sda` to a file?
    - A. `dd if=mbr.bin of=/dev/sda bs=512 count=1`
    - B. `dd if=/dev/sda of=mbr.bin bs=512 count=1`
    - C. `dd if=/dev/sda of=mbr.bin bs=1M`
    - D. `cpio -o /dev/sda > mbr.bin`
5. A disk is failing with read errors. Why is `ddrescue` with a mapfile a better choice than plain `dd` for imaging it?
6. Which tool combination creates a cpio archive of the `/data` directory?
    - A. `cpio -i /data > data.cpio`
    - B. `tar -c /data | cpio -o > data.cpio`
    - C. `find /data | cpio -o > data.cpio`
    - D. `cpio -t /data > data.cpio`

::: answers
1. **B.** `-j` selects bzip2; `-z` is gzip, `-J` is xz, and `-x` extracts instead of creating.
2. Add a trailing slash to the source (`rsync -a /srv/web/ /backup/`) so rsync copies the directory's contents rather than the directory itself.
3. **C.** `zgrep` searches inside gzip-compressed files directly; plain `grep` sees only compressed bytes, and `gunzip` would decompress the file on disk.
4. **B.** The input (`if`) is the disk and the output (`of`) is the file, copying one 512-byte block; option A does the reverse and overwrites the MBR.
5. `ddrescue` copies the good areas first, skips and later retries bad areas, and records progress in the mapfile so it can resume and retry without re-reading what it already rescued; `dd` stops at errors or blindly pads them.
6. **C.** `cpio` in copy-out mode (`-o`) reads the list of file names from standard input, which `find` provides.
:::
