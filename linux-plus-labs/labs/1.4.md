## Lab 1.4: Manage Network Services and Configurations {#lab-1-4}

::: labinfo
**Objective:** 1.4 Given a scenario, manage network services and configurations on a Linux server.\
**Domain:** 1.0 System Management (23% of the exam)\
**Time:** about 100 minutes\
**VM:** ubuntu-lab and rocky-lab (both running)\
**Snapshot first:** Yes. This lab changes network settings on both VMs; a mistake can cut off your network connection.
:::

Almost every Linux problem ticket eventually becomes a network question: "Is the address right? Can it reach the gateway? Does the name resolve? Is the port open?" In this lab you configure addresses with Netplan on Ubuntu and NetworkManager on Rocky, trace how a host name becomes an IP address, and then use every network tool on the exam against your two VMs and the internet.

### What you'll practice

- Name resolution files: `/etc/hosts`, `/etc/resolv.conf`, `/etc/nsswitch.conf`
- NetworkManager: `nmcli`, `nmconnect` (connection profiles) and `nmtui`
- Netplan: `netplan apply`, `netplan status`, `netplan try`; `/etc/netplan`
- Common tools: `arp`, `curl`, `dig`, `ethtool`, `hostname`, `ip` (`ip address`, `ip link`, `ip route`), `iperf3`, `mtr`, `nc`, `nmap`, `nslookup`, `ping`/`ping6`, `ss`, `tcpdump`, `tracepath`, `traceroute`

### How it works

**The basics of a network connection.** For a Linux server to talk on a network it needs four things:

1. A working **link**: the network interface (for example `enp0s3`) must exist and be "up." Interface names describe where the card sits: `en` = Ethernet, `p0s3` = PCI bus 0, slot 3. VMware VMs often have `ens33`, KVM VMs `enp1s0`.
2. An **IP address** with a prefix length, such as `192.168.100.10/24`. The `/24` means the first 24 bits are the network part, so every `192.168.100.x` address is on the same local network.
3. A **default route** (default gateway): the router that receives traffic for every network that is not local.
4. **DNS servers** that translate names such as `rockylinux.org` into IP addresses.

On the local network, computers actually deliver frames by **MAC address** (the hardware address of a network card). **ARP** (Address Resolution Protocol) asks "who has 192.168.100.20?" and caches the answer in the **neighbor table**.

**Who configures the network?** The `ip` command changes the running kernel settings immediately, but those changes are lost at reboot. Permanent settings come from a network configuration service:

```{.diagram}
 Ubuntu Server 24.04                     Rocky Linux 9
 -------------------                     -------------
 /etc/netplan/*.yaml   (you edit)        nmcli / nmtui   (you run)
        |                                       |
   netplan generate / apply             /etc/NetworkManager/system-connections/
        |                                  *.nmconnection  (connection profiles)
 systemd-networkd  (renderer)                   |
        |                               NetworkManager  (service)
        +--------------> Linux kernel <---------+
                    (addresses, links, routes)
```

**Netplan** is Ubuntu's configuration layer. You describe the network in YAML files in `/etc/netplan/`, and Netplan hands the settings to a "renderer": `systemd-networkd` on servers or NetworkManager on desktops. `netplan try` applies a change and automatically rolls it back after a timeout unless you confirm it; `netplan apply` applies it right away; `netplan status` shows the current state.

**NetworkManager** is the standard on Red Hat-family systems (and Ubuntu Desktop). It works with **connection profiles**: named sets of settings (addresses, DNS, gateway) that are applied to a **device** (an interface). On Rocky 9 each profile is stored as a keyfile ending in `.nmconnection`. The exam's wording "nmconnect" refers to this NetworkManager connection management. You manage profiles with `nmcli` (command line) or `nmtui` (a text menu).

**Name resolution.** When a program looks up a name, the C library reads `/etc/nsswitch.conf` to decide where to look and in what order:

```{.diagram}
 ping rocky-lab
      |
 /etc/nsswitch.conf    "hosts: files dns"
      |                     |
   files  -------->  /etc/hosts        found? use it, stop
      |
   dns    -------->  /etc/resolv.conf  "nameserver 127.0.0.53"
                            |
              Ubuntu: systemd-resolved stub (127.0.0.53)
                            |  forwards to the real DNS servers
              Rocky:  the real DNS server listed directly
```

- `/etc/hosts` is a simple local table of IP address and names. It is checked first, so it can override DNS.
- `/etc/resolv.conf` lists the DNS servers (`nameserver`) and the search domains (`search`). On Ubuntu it points to `127.0.0.53`, a local stub run by **systemd-resolved**, which forwards to the real servers (see them with `resolvectl status`). On Rocky, NetworkManager writes the real servers into it.
- Important: `dig` and `nslookup` are DNS tools. They talk to DNS servers directly and never read `/etc/hosts` or `nsswitch.conf`. `getent hosts NAME` follows the same path as normal programs.

**The toolbox:**

| Tool | Question it answers |
|---|---|
| `ip address`, `ip link`, `ip route` | What addresses, interfaces, and routes do I have? |
| `hostname` | What is this machine called? |
| `ping`, `ping6` | Can I reach that host (IPv4/IPv6)? |
| `arp`, `ip neigh` | Which MAC address belongs to that local IP? |
| `traceroute`, `tracepath`, `mtr` | Which routers are on the path, and where does it break? |
| `dig`, `nslookup` | What does DNS say about this name? |
| `curl` | Does the web service answer, and what does it return? |
| `ss` | Which ports are listening, and which connections are open? |
| `nc` | Can I open a TCP/UDP connection to that port? Send raw data. |
| `nmap` | Which ports are open on that host? |
| `iperf3` | How fast is the network between two hosts? |
| `ethtool` | What speed, duplex, and driver does the network card use? |
| `tcpdump` | What packets are actually on the wire? |

#### Task 1: Inspect the network with hostname and ip

1. On ubuntu-lab, create the lab directory and check the host name.

    ```bash
    mkdir -p ~/labs/1.4 && cd ~/labs/1.4
    hostname
    hostname -I
    hostnamectl
    ```

    ```{.output}
    ubuntu-lab
    192.168.100.10
     Static hostname: ubuntu-lab
           Icon name: computer-vm
             Chassis: vm
    Operating System: Ubuntu 24.04.1 LTS
              Kernel: Linux 6.8.0-45-generic
        Architecture: x86-64
    ```

    ::: explain
    **What just happened:** `hostname` prints the system's name, and `hostname -I` prints all its IP addresses (IPv4 and IPv6) on one line. `hostnamectl` shows the name plus system details; the permanent name is stored in `/etc/hostname` and you change it with `sudo hostnamectl set-hostname NEWNAME`.
    :::

2. List the network interfaces (links).

    ```bash
    ip link
    ```

    ```{.output}
    1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN mode DEFAULT group ...
        link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode ...
        link/ether 08:00:27:4e:66:a1 brd ff:ff:ff:ff:ff:ff
    ```

    ::: explain
    **What just happened:** `ip link` (short for `ip link show`) lists every interface. `lo` is the **loopback** interface, which the computer uses to talk to itself (`127.0.0.1`). `enp0s3` is the network card. `UP` means it is enabled, `LOWER_UP` means a cable (virtual, here) is connected, `mtu 1500` is the largest packet size in bytes, and `link/ether` is the MAC address. Write down your interface name: this lab uses `enp0s3`, so replace it with yours everywhere.
    :::

3. Show the IP addresses, in long and brief form.

    ```bash
    ip address show enp0s3
    ip -br address
    ```

    ```{.output}
    2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group ...
        link/ether 08:00:27:4e:66:a1 brd ff:ff:ff:ff:ff:ff
        inet 192.168.100.10/24 metric 100 brd 192.168.100.255 scope global dynamic enp0s3
           valid_lft 85912sec preferred_lft 85912sec
        inet6 fe80::a00:27ff:fe4e:66a1/64 scope link
           valid_lft forever preferred_lft forever
    lo               UNKNOWN        127.0.0.1/8 ::1/128
    enp0s3           UP             192.168.100.10/24 fe80::a00:27ff:fe4e:66a1/64
    ```

    ::: explain
    **What just happened:** `ip address` (you can abbreviate it to `ip a` or `ip addr`) shows addresses. `inet` is IPv4, `inet6` is IPv6. `dynamic` means it came from DHCP and `valid_lft` is how long the lease has left; a static address shows `forever`. The `fe80::` address is an IPv6 **link-local** address that every interface gives itself automatically. `-br` (brief) prints one line per interface, which is the quickest overview.
    :::

4. Show the routing table and ask which route a packet would take.

    ```bash
    ip route
    ip route get 1.1.1.1
    ```

    ```{.output}
    default via 192.168.100.1 dev enp0s3 proto dhcp src 192.168.100.10 metric 100
    192.168.100.0/24 dev enp0s3 proto kernel scope link src 192.168.100.10 metric 100
    192.168.100.1 dev enp0s3 proto dhcp scope link src 192.168.100.10 metric 100
    1.1.1.1 via 192.168.100.1 dev enp0s3 src 192.168.100.10 uid 1000
        cache
    ```

    ::: explain
    **What just happened:** `ip route` lists routes. `default via 192.168.100.1` is the default gateway: anything not matched by a more specific route goes there. The `192.168.100.0/24 ... scope link` line says the local network is reached directly, without a router. `ip route get` shows the decision for one destination, which is the fastest way to answer "which interface and gateway would this use?"
    :::

5. Practice runtime changes safely on a dummy interface (the fake interface type from Lab 1.2). These changes affect only the running system and vanish at reboot.

    ```bash
    sudo ip link add lab0 type dummy
    sudo ip link set lab0 up
    sudo ip address add 10.50.0.1/24 dev lab0
    sudo ip route add 10.60.0.0/24 via 10.50.0.2 dev lab0
    ip -br address show lab0
    ip route get 10.60.0.9
    sudo ip link delete lab0
    ```

    ```{.output}
    lab0             UNKNOWN        10.50.0.1/24 fe80::d4b1:2cff:fe9a:13e7/64
    10.60.0.9 via 10.50.0.2 dev lab0 src 10.50.0.1 uid 1000
        cache
    ```

    ::: explain
    **What just happened:** `ip link add ... type dummy` created an interface, `ip link set ... up` enabled it (`down` would disable it), `ip address add` gave it an address, and `ip route add NETWORK via GATEWAY` added a static route. `ip route get` confirms traffic for `10.60.0.9` would go out through `lab0` to `10.50.0.2`. Deleting the link removed its address and route too. This is how you test settings quickly; then you make them permanent with Netplan or NetworkManager. On the exam, remember that old `ifconfig` and `route` (package `net-tools`) are replaced by `ip address` and `ip route`.
    :::

::: checkpoint
**Checkpoint:** You know your interface name, IP address, prefix, and default gateway, and `ip link show lab0` reports that the device does not exist (it was deleted).
:::

#### Task 2: Follow name resolution through hosts, nsswitch, and resolv.conf

1. Look at the three name resolution files on ubuntu-lab.

    ```bash
    cat /etc/hosts
    grep '^hosts' /etc/nsswitch.conf
    ls -l /etc/resolv.conf
    grep -v '^#' /etc/resolv.conf
    ```

    ```{.output}
    127.0.0.1 localhost
    127.0.1.1 ubuntu-lab
    192.168.100.10 ubuntu-lab
    192.168.100.20 rocky-lab
    ::1     ip6-localhost ip6-loopback
    hosts:          files dns
    lrwxrwxrwx 1 root root 39 Apr 22 13:10 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
    nameserver 127.0.0.53
    options edns0 trust-ad
    search .
    ```

    ::: explain
    **What just happened:** `/etc/hosts` lines are `IP NAME [ALIASES...]`; your Lab 0 entries for both VMs are there. The `hosts:` line in `/etc/nsswitch.conf` says "check `files` (`/etc/hosts`) first, then `dns`." `/etc/resolv.conf` is a symbolic link managed by systemd-resolved and points to the local stub at `127.0.0.53`. Do not edit it by hand on Ubuntu; your changes would be overwritten. `grep -v '^#'` hides the comment lines.
    :::

2. Find the real DNS servers behind the stub.

    ```bash
    resolvectl status enp0s3
    ```

    ```{.output}
    Link 2 (enp0s3)
        Current Scopes: DNS
             Protocols: +DefaultRoute -LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
    Current DNS Server: 192.168.100.1
           DNS Servers: 192.168.100.1
    ```

    ::: explain
    **What just happened:** `resolvectl` talks to systemd-resolved. The DNS server for `enp0s3` came from DHCP (often your virtual router or host). systemd-resolved receives every query on `127.0.0.53`, caches answers, and forwards misses to this server.
    :::

3. Add a test name to `/etc/hosts` and resolve it with three different tools. You can use `sudo nano /etc/hosts`, or append the line with `tee -a`. The first command makes sure `dig` is installed (it comes in the `bind9-dnsutils` package; apt just says "already the newest version" if you have it).

    ```bash
    sudo apt install -y bind9-dnsutils
    echo "192.168.100.20 fileserver.lab fileserver" | sudo tee -a /etc/hosts
    getent hosts fileserver
    ping -c 2 fileserver
    dig +short @1.1.1.1 fileserver.lab
    ```

    ```{.output}
    192.168.100.20 fileserver.lab fileserver
    192.168.100.20  fileserver.lab fileserver
    PING fileserver.lab (192.168.100.20) 56(84) bytes of data.
    64 bytes from rocky-lab (192.168.100.20): icmp_seq=1 ttl=64 time=0.412 ms
    64 bytes from rocky-lab (192.168.100.20): icmp_seq=2 ttl=64 time=0.398 ms
    ```

    ::: explain
    **What just happened:** `getent hosts` and `ping` follow `nsswitch.conf`, find the name in `/etc/hosts`, and get `192.168.100.20`. `dig @1.1.1.1` asked a public DNS server directly, which has never heard of `fileserver.lab`, so `+short` printed nothing. This is the key troubleshooting lesson: **if `ping NAME` works but `dig NAME` fails (or the reverse), the name is coming from `/etc/hosts`**, not DNS. (On Ubuntu, plain `dig fileserver.lab` would succeed because the systemd-resolved stub also reads `/etc/hosts`. On Rocky, which has no stub, it would fail.)
    :::

4. Look at the same files on rocky-lab, where NetworkManager writes `resolv.conf`.

    ```bash
    # on rocky-lab
    grep '^hosts' /etc/nsswitch.conf
    ls -l /etc/resolv.conf
    cat /etc/resolv.conf
    ```

    ```{.output}
    hosts:      files dns myhostname
    -rw-r--r--. 1 root root 72 Oct 10 09:21 /etc/resolv.conf
    # Generated by NetworkManager
    search localdomain
    nameserver 192.168.100.1
    ```

    ::: explain
    **What just happened:** On Rocky, `/etc/resolv.conf` is a regular file written by NetworkManager, and it lists the real DNS server. `myhostname` in `nsswitch.conf` is a systemd module that always resolves the machine's own name. To change DNS on Rocky you change the NetworkManager connection (Task 4), not this file directly, because NetworkManager rewrites it.
    :::

::: checkpoint
**Checkpoint:** On ubuntu-lab, `getent hosts fileserver` returns `192.168.100.20`, and you can explain why `dig @1.1.1.1 fileserver.lab` returns nothing.
:::

#### Task 3: Configure a second IP address with Netplan

::: warning
Do this task at the ubuntu-lab **console**, not over SSH. A wrong Netplan file can disconnect the network. `netplan try` protects you by rolling back automatically, but only if you can still see the prompt. Take a snapshot now if you have not.
:::

1. Look at the existing Netplan configuration. The files are readable only by root.

    ```bash
    ls -l /etc/netplan/
    sudo cat /etc/netplan/*.yaml
    ```

    ```{.output}
    -rw------- 1 root root 104 Oct 10 09:10 50-cloud-init.yaml
    network:
      version: 2
      ethernets:
        enp0s3:
          dhcp4: true
    ```

    ::: explain
    **What just happened:** The installer wrote `50-cloud-init.yaml`. YAML uses **indentation with spaces** (never tabs) to show structure: `network` contains `ethernets`, which contains the interface `enp0s3`, which has `dhcp4: true` (get an IPv4 address from DHCP). Your file name may differ (for example `00-installer-config.yaml`). Netplan reads every `.yaml` file in `/etc/netplan/` in alphabetical order and merges them.
    :::

2. Check the current state with `netplan status`.

    ```bash
    sudo netplan status
    ```

    ```{.output}
         Online state: online
        DNS Addresses: 127.0.0.53 (stub)
           DNS Search: .

    ●  2: enp0s3 ethernet UP (networkd: enp0s3)
          MAC Address: 08:00:27:4e:66:a1 (Intel Corporation)
            Addresses: 192.168.100.10/24 (dhcp)
                       fe80::a00:27ff:fe4e:66a1/64 (link)
        DNS Addresses: 192.168.100.1
               Routes: default via 192.168.100.1 from 192.168.100.10 metric 100 (dhcp)
                       192.168.100.0/24 from 192.168.100.10 metric 100 (link)
    ```

    ::: explain
    **What just happened:** `netplan status` summarizes each interface: which backend manages it (`networkd: enp0s3`), its addresses and where they came from (`dhcp`, `link`), DNS servers, and routes. Interfaces Netplan does not manage are listed at the end as "inactive or unmanaged."
    :::

3. Create a new file that adds a second, static address to the same interface. Choose an unused address on your lab network; this lab uses `192.168.100.110`. The heredoc below writes the file: everything between `<<'EOF'` and the closing `EOF` goes into `tee`, which saves it with root rights. Replace `enp0s3` if your interface has another name.

    ```bash
    cat <<'EOF' | sudo tee /etc/netplan/60-lab.yaml
    network:
      version: 2
      ethernets:
        enp0s3:
          addresses:
            - 192.168.100.110/24
    EOF
    sudo chmod 600 /etc/netplan/60-lab.yaml
    ```

    ::: explain
    **What just happened:** Because Netplan merges files, this file adds an `addresses` list to `enp0s3` while `dhcp4: true` from the first file stays in effect. Using a separate file makes it easy to undo: delete it and apply. `chmod 600` limits the file to root; Netplan warns about files that others can read, because they may contain Wi-Fi passwords.
    :::

4. Apply it with `netplan try`. Press **Enter** when asked to keep the settings.

    ```bash
    sudo netplan try
    ```

    ```{.output}
    Do you want to keep these settings?

    Press ENTER before the timeout to accept the new configuration

    Changes will revert in 118 seconds
    Configuration accepted.
    ```

    ::: explain
    **What just happened:** `netplan try` checked the YAML, applied it, and started a countdown (120 seconds by default; change it with `--timeout`). If the change had broken your connection, you would not be able to press Enter (or would not be able to reach the prompt over SSH), and Netplan would restore the previous configuration by itself. Pressing Enter made it permanent.
    :::

5. Verify the new address, and test it from rocky-lab.

    ```bash
    ip -br address show enp0s3
    ```

    ```{.output}
    enp0s3           UP             192.168.100.110/24 192.168.100.10/24 fe80::a00:27ff:fe4e:66a1/64
    ```

    ```bash
    # on rocky-lab
    ping -c 2 192.168.100.110
    ```

6. Watch the automatic rollback. Remove the extra address from the configuration, run `netplan try` with a short timeout, and this time do **not** press Enter.

    ```bash
    sudo mv /etc/netplan/60-lab.yaml ~/labs/1.4/60-lab.yaml.disabled
    sudo netplan try --timeout 20
    ip -br address show enp0s3
    ```

    ```{.output}
    Do you want to keep these settings?

    Press ENTER before the timeout to accept the new configuration

    Changes will revert in  1 seconds
    Reverting.
    enp0s3           UP             192.168.100.110/24 192.168.100.10/24 fe80::a00:27ff:fe4e:66a1/64
    ```

    ::: explain
    **What just happened:** `netplan try` applied the configuration without the extra address, waited 20 seconds, received no confirmation, and reverted to the configuration that was active before, so `192.168.100.110` is still there. Because it saved a backup of `/etc/netplan` before trying, it even put `60-lab.yaml` back. Check with `ls /etc/netplan/`. This is your safety net for remote changes.
    :::

7. Now remove the change for real with `netplan apply`, which applies immediately with no rollback.

    ```bash
    ls /etc/netplan/
    sudo rm -f /etc/netplan/60-lab.yaml
    sudo netplan apply
    ip -br address show enp0s3
    ```

    ```{.output}
    50-cloud-init.yaml  60-lab.yaml
    enp0s3           UP             192.168.100.10/24 fe80::a00:27ff:fe4e:66a1/64
    ```

    ::: explain
    **What just happened:** `netplan apply` generated the backend configuration (for systemd-networkd, files under `/run/systemd/network/`) and reloaded the network. Only the DHCP address remains. If the extra address is still listed, run `sudo ip address del 192.168.100.110/24 dev enp0s3` once to remove the leftover runtime address.
    :::

8. For reference, this is what a fully static configuration looks like. Save it as a file in your lab folder; do **not** copy it into `/etc/netplan/`.

    ```bash
    cat <<'EOF' > ~/labs/1.4/static-example.yaml
    network:
      version: 2
      renderer: networkd
      ethernets:
        enp0s3:
          dhcp4: false
          addresses:
            - 192.168.100.10/24
          routes:
            - to: default
              via: 192.168.100.1
          nameservers:
            addresses: [1.1.1.1, 9.9.9.9]
            search: [lab.local]
    EOF
    ```

    ::: explain
    **What just happened:** A static setup lists the address, a default route (`to: default` with `via:` the gateway; the older `gateway4:` key is deprecated), and DNS servers under `nameservers`. `renderer: networkd` is the server default; Ubuntu Desktop uses `renderer: NetworkManager`. `sudo netplan generate` would turn YAML into backend files without applying them, which is a handy syntax check.
    :::

::: checkpoint
**Checkpoint:** `ls /etc/netplan/` shows only the original file, `ip -br address show enp0s3` shows only the DHCP address, and `sudo netplan status` reports `Online state: online`.
:::

#### Task 4: Manage connections with NetworkManager (nmcli and nmtui) on rocky-lab

::: warning
Work at the rocky-lab console for this task. The commands use `nmcli device reapply`, which applies changes without taking the link down, but a typo in an address can still interrupt SSH.
:::

1. Look at NetworkManager's view of the system: overall status, devices, and connection profiles.

    ```bash
    # on rocky-lab
    nmcli general status
    nmcli device status
    nmcli connection show
    ```

    ```{.output}
    STATE      CONNECTIVITY  WIFI-HW  WIFI     WWAN-HW  WWAN
    connected  full          missing  enabled  missing  enabled
    DEVICE  TYPE      STATE                   CONNECTION
    enp0s3  ethernet  connected               enp0s3
    lo      loopback  connected (externally)  lo
    NAME    UUID                                  TYPE      DEVICE
    enp0s3  a3f9c1d2-5b6e-4f70-8a91-b2c3d4e5f607  ethernet  enp0s3
    lo      0c1d2e3f-4a5b-4c6d-8e7f-a0b1c2d3e4f5  loopback  lo
    ```

    ::: explain
    **What just happened:** A **device** is a network interface; a **connection** is a profile of settings applied to a device. Here the profile is named `enp0s3`, like its device, but it could be called `Wired connection 1` or `System eth0`. In the commands below, replace `enp0s3` with your **connection NAME** where the command says `connection`, and with your **DEVICE** where it says `device`.
    :::

2. Find the profile file. This is NetworkManager's "nmconnect" storage: one keyfile per connection.

    ```bash
    # on rocky-lab
    sudo ls /etc/NetworkManager/system-connections/
    sudo cat /etc/NetworkManager/system-connections/enp0s3.nmconnection
    ```

    ```{.output}
    enp0s3.nmconnection
    [connection]
    id=enp0s3
    uuid=a3f9c1d2-5b6e-4f70-8a91-b2c3d4e5f607
    type=ethernet
    interface-name=enp0s3

    [ipv4]
    method=auto

    [ipv6]
    addr-gen-mode=eui64
    method=auto
    ```

    ::: explain
    **What just happened:** Rocky 9 stores connection profiles as INI-style keyfiles ending in `.nmconnection`. `method=auto` means DHCP. You can edit these files, but then you must run `sudo nmcli connection reload`; using `nmcli` is safer because it validates every value. (Older systems, and Rocky 9 machines upgraded from 8, may still use `/etc/sysconfig/network-scripts/ifcfg-*` files instead.)
    :::

3. Show the IPv4 settings of the profile, then add a secondary address. The `+` in `+ipv4.addresses` means "add to the list" instead of replacing it.

    ```bash
    # on rocky-lab
    nmcli -f ipv4.method,ipv4.addresses,ipv4.dns connection show enp0s3
    sudo nmcli connection modify enp0s3 +ipv4.addresses 192.168.100.120/24
    sudo nmcli device reapply enp0s3
    ip -br address show enp0s3
    ```

    ```{.output}
    ipv4.method:                            auto
    ipv4.addresses:                         --
    ipv4.dns:                               --
    Connection successfully reapplied to device 'enp0s3'.
    ```

### Exam corner

- `ip address` (addresses), `ip link` (interfaces, `set dev X up/down`), `ip route` (routes, `ip route add NET via GW`). `ip` changes are not persistent.
- Netplan: YAML in `/etc/netplan/`, spaces not tabs. `netplan try` applies with automatic rollback (default 120 s), `netplan apply` applies immediately, `netplan status` shows state, `netplan generate` builds backend files. Renderer is `networkd` (server) or `NetworkManager` (desktop).
- NetworkManager: `nmcli general status`, `nmcli device status`, `nmcli connection show|add|modify|up|down|delete`, `nmcli device reapply`. Profiles are `.nmconnection` keyfiles in `/etc/NetworkManager/system-connections/` ("nmconnect"). `nmtui` is the text menu.
- Name lookup order comes from the `hosts:` line in `/etc/nsswitch.conf` (`files dns`); `/etc/hosts` is checked first. `/etc/resolv.conf` lists `nameserver` and `search`; on Ubuntu it points to the systemd-resolved stub `127.0.0.53` (`resolvectl status` shows real servers).
- `dig` and `nslookup` query DNS directly and ignore `/etc/hosts`; `getent hosts` follows nsswitch. `dig @SERVER NAME TYPE`, `dig +short`, `dig -x IP` for reverse.
- `ping`/`ping6` test reachability; `arp -n` / `ip neigh` show IP-to-MAC mappings; `traceroute`, `tracepath` (no root, shows PMTU), and `mtr` (continuous) show the path.
- `ss -tulpn` lists listening TCP/UDP ports with processes (replaces `netstat`). `nc -l PORT` listens, `nc -zv HOST PORT` tests a port. `nmap HOST` scans ports: open, closed, filtered.
- `curl -I URL` shows HTTP headers and status code; `-L` follows redirects, `-o` saves output.
- `iperf3 -s` (server) and `iperf3 -c HOST` (client) measure throughput, default TCP port 5201.
- `ethtool IFACE` shows speed, duplex, link; `-i` driver; `-S` statistics; `-s` changes settings.
- `tcpdump -i IFACE -n FILTER`, `-c N` count, `-w file.pcap` write, `-r file.pcap` read.
- `hostname` shows the name, `hostname -I` the addresses; `hostnamectl set-hostname` changes it permanently.

**Review questions**

1. An administrator must change the IP address of a remote Ubuntu server over SSH and wants the change undone automatically if the connection is lost. Which command should be used?

    A. `netplan apply`\
    B. `netplan try`\
    C. `netplan generate`\
    D. `ip address add`

2. `ping app01` works, but `dig app01` returns NXDOMAIN on a Rocky server. What is the most likely explanation?
3. Which command adds the DNS server `10.0.0.53` to the NetworkManager connection `ens192` so it survives reboots?

    A. `echo "nameserver 10.0.0.53" >> /etc/resolv.conf`\
    B. `nmcli connection modify ens192 ipv4.dns 10.0.0.53`\
    C. `ip route add dns 10.0.0.53`\
    D. `resolvectl dns 10.0.0.53`

4. A web application cannot reach a database on port 5432. Which command, run on the database server, confirms that something is listening on that port and shows which process it is?

    A. `ss -tulpn`\
    B. `arp -n`\
    C. `tracepath db01`\
    D. `ethtool -S eth0`

5. `nc -zv db01 5432` returns "Connection refused." What does this tell you?
6. Which tool would you use to measure the maximum TCP throughput between two Linux servers?

    A. `mtr`\
    B. `iperf3`\
    C. `nmap`\
    D. `curl`

::: answers
1. **B.** `netplan try` applies the configuration and reverts it automatically unless you confirm within the timeout, protecting remote sessions.
2. **The name is defined in `/etc/hosts`, not in DNS.** `ping` follows `/etc/nsswitch.conf` (files first), while `dig` queries DNS servers directly and ignores `/etc/hosts`.
3. **B.** `nmcli connection modify` saves the setting in the connection profile, and NetworkManager writes it into `/etc/resolv.conf`; manual edits to `resolv.conf` are overwritten.
4. **A.** `ss -tulpn` lists listening TCP and UDP sockets with numeric ports and the owning process.
5. **The host is reachable but nothing is listening on port 5432** (or the service is bound only to another address such as `127.0.0.1`); a firewall would usually cause a timeout or "No route to host" instead.
6. **B.** `iperf3` runs a client and server pair to measure network throughput.
:::
