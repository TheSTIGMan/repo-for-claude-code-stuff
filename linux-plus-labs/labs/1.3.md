Storage is where most real administration happens: a database runs out of space, a new disk is added, a disk in a mirror dies, or a team needs a shared folder. In this lab you use the four blank 5 GB disks to practice every storage skill on the exam: partitioning, LVM, filesystems and their repair tools, mount options, RAID, network shares, automounting, and inodes.

### How it works

**Disks, partitions, and filesystems.** A new disk is like an empty warehouse. **Partitioning** puts up walls to divide it into rooms (partitions). **Formatting** (`mkfs`, "make filesystem") puts shelves and a catalog into a room so files can be stored and found. **Mounting** attaches a formatted room to a folder in the directory tree, called the **mount point**, so you can reach it with a path like `/mnt/data`.

There are two partition table formats. **MBR** (Master Boot Record, also called DOS) is the old one: at most 4 primary partitions and disks up to 2 TiB. **GPT** (GUID Partition Table) is the modern one: 128 partitions, huge disks, and a backup copy of the table at the end of the disk. `fdisk` handles both (it started with MBR), `gdisk` is a GPT-focused clone of fdisk, and `parted` handles both and can be scripted. `lsblk` shows disks and partitions as a tree, and `blkid` shows each one's filesystem type and **UUID** (a unique ID that never changes, unlike `/dev/sdb`, which can change if disks are added).

**Filesystems you need to know:**

| Filesystem | Key facts |
|---|---|
| `ext4` | Debian/Ubuntu default. Journaling. Can grow online, shrink only offline. Tools: `mkfs.ext4`, `resize2fs`, `e2fsck` (via `fsck`). |
| `xfs` | RHEL/Rocky default. Fast with large files. Can grow online, **cannot shrink**. Tools: `mkfs.xfs`, `xfs_growfs`, `xfs_repair`. |
| `btrfs` | Copy-on-write with built-in snapshots, subvolumes, checksums, and multi-disk support. Default on openSUSE and Fedora desktops. |
| `tmpfs` | Lives in RAM (and swap). Very fast, gone at reboot. Used for `/run` and often `/tmp`. |

**Inodes.** Every file has an **inode** (index node): a small record that stores the file's owner, permissions, size, timestamps, and where its data blocks are. The file **name** is not in the inode; it lives in the directory, which maps names to inode numbers. ext4 creates a fixed number of inodes when you format, so a disk can run out of inodes (lots of tiny files) while still having free space. `df -i` shows inode use; `ls -i` shows inode numbers.

**LVM.** The Logical Volume Manager adds a flexible layer between disks and filesystems. Picture pouring several jugs of water (disks) into one tank (a volume group), then filling bottles of any size from the tank (logical volumes). Later you can pour in another jug and make a bottle bigger without touching its contents.

```{.diagram}
 Disks          /dev/sdb          /dev/sdc
                   |                  |
 PVs            [ PV ]             [ PV ]        pvcreate   (pvs, pvdisplay)
                   \______    _______/
 VG                   [   labvg    ]             vgcreate   (vgs, vgdisplay)
                     /              \
 LVs           [ data ]          [ logs ]        lvcreate   (lvs, lvdisplay)
                  |                  |
 Filesystems    ext4               xfs            mkfs
                  |                  |
 Mount points  /mnt/data          /mnt/logs       mount
```

- A **physical volume (PV)** is a disk or partition prepared for LVM with `pvcreate`.
- A **volume group (VG)** is a pool made of one or more PVs, created with `vgcreate`. Space in it is divided into **extents** (4 MiB chunks by default).
- A **logical volume (LV)** is a slice of the VG that acts like a partition. It appears as `/dev/VGNAME/LVNAME` (and `/dev/mapper/VGNAME-LVNAME`).

**RAID** combines disks for speed or safety. **RAID 0** stripes data across disks (fast, no protection). **RAID 1** mirrors two disks (either can die). **RAID 5** stripes with parity (needs 3+ disks, survives one failure). **RAID 6** has double parity (4+ disks, survives two). **RAID 10** is mirrors that are striped. Linux software RAID is managed with `mdadm` and creates devices like `/dev/md0`; its live status is in `/proc/mdstat`.

**Mounting.** `mount DEVICE DIR` attaches a filesystem and `umount DIR` detaches it. Mounts listed in **`/etc/fstab`** are mounted at boot. Each fstab line has six fields: device, mount point, type, options, dump flag, and fsck order. The kernel's live list of mounts is **`/proc/mounts`**; **`/etc/mtab`** used to be a separate file but is now a link to it. **Mount options** change behavior: `ro`/`rw` (read-only/read-write), `noexec` (programs cannot run from here), `nosuid` (setuid bits are ignored), `nodev` (device files do not work), `noatime`/`nodiratime` (do not update access times), `nofail` (do not stop the boot if the device is missing), and `remount` (change options on a mounted filesystem).

**Network mounts.** **NFS** (Network File System) is the Unix/Linux way to share a directory over the network: the server lists shares in `/etc/exports`. **SMB** (Server Message Block, also called CIFS) is the Windows way; **Samba** is the Linux server for it, and `mount -t cifs` is the client. **autofs** mounts shares automatically when someone opens the folder and unmounts them after they have been idle.

#### Task 2: Partition a disk with fdisk (MBR) and parted

1. Open `/dev/sdd` in `fdisk`. It is interactive: you type one-letter commands and nothing is written until you press `w`.

    ```bash
    sudo fdisk /dev/sdd
    ```

2. Type these answers, one per line, pressing **Enter** after each. Lines in parentheses describe what fdisk asks.

    ```text
    o          (create a new empty DOS/MBR partition table)
    n          (new partition)
    p          (primary)
    1          (partition number 1)
    <Enter>    (first sector: accept the default 2048)
    +1G        (last sector: make it 1 GiB)
    n          (new partition)
    p          (primary)
    2          (partition number 2)
    <Enter>    (first sector: default)
    +512M      (size 512 MiB)
    t          (change a partition type)
    2          (partition 2)
    82         (Linux swap)
    p          (print the table)
    w          (write and exit)
    ```

    ```{.output}
    Disk /dev/sdd: 5 GiB, 5368709120 bytes, 10485760 sectors
    Disk model: VBOX HARDDISK
    Units: sectors of 1 * 512 = 512 bytes
    Disklabel type: dos
    Disk identifier: 0x5b1c2d3e

    Device     Boot   Start     End Sectors  Size Id Type
    /dev/sdd1          2048 2099199 2097152    1G 83 Linux
    /dev/sdd2       2099200 3147775 1048576  512M 82 Linux swap / Solaris

    Command (m for help): w
    The partition table has been altered.
    Calling ioctl() to re-read partition table.
    Syncing disks.
    ```

    ::: explain
    **What just happened:** `o` wrote a new, empty MBR table (in memory only). `n` created partitions; the first one starts at sector 2048 (1 MiB) so it lines up with the physical blocks of modern disks. `t` changed partition 2's **type ID** from `83` (Linux) to `82` (Linux swap). Type IDs are only labels; they tell tools what is meant to be there. `w` wrote the table to disk and told the kernel to re-read it. If you make a mistake before `w`, press `q` to quit without saving.
    :::

3. Look at the result with `lsblk` and with `parted`.

    ```bash
    lsblk /dev/sdd
    sudo parted /dev/sdd print
    ```

    ```{.output}
    NAME   MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
    sdd      8:48   0    5G  0 disk
    ├─sdd1   8:49   0    1G  0 part
    └─sdd2   8:50   0  512M  0 part
    Model: ATA VBOX HARDDISK (scsi)
    Disk /dev/sdd: 5369MB
    Sector size (logical/physical): 512B/512B
    Partition Table: msdos
    Disk Flags:

    Number  Start   End     Size    Type     File system  Flags
     1      1049kB  1075MB  1074MB  primary
     2      1075MB  1612MB  537MB   primary
    ```

    ::: explain
    **What just happened:** `parted` calls an MBR table `msdos`. By default it shows sizes in decimal megabytes (MB = 1,000,000 bytes), while fdisk's `1G` meant 1 GiB (1,073,741,824 bytes), which is why the numbers look different. The "File system" column is empty because you have not formatted anything yet.
    :::

4. `parted` can also do everything in one non-interactive command, which is handy in scripts. Replace the MBR table with a GPT table and create one partition. `-s` (script mode) means "do not ask questions."

    ```bash
    sudo parted -s /dev/sdd mklabel gpt mkpart labpart ext4 1MiB 1GiB
    sudo parted /dev/sdd unit MiB print free
    ```

    ```{.output}
    Partition Table: gpt
    Number  Start    End      Size     File system  Name     Flags
            0.02MiB  1.00MiB  0.98MiB  Free Space
     1      1.00MiB  1024MiB  1023MiB               labpart
            1024MiB  5120MiB  4096MiB  Free Space
    ```

    ::: explain
    **What just happened:** `mklabel gpt` replaced the whole partition table (the old partitions are gone), and `mkpart NAME FSTYPE START END` created a partition. The `ext4` word is only a hint; parted does not format. `unit MiB` displays sizes in MiB and `print free` also shows unused space. Unlike fdisk, parted writes each change **immediately**, with no `w` step, so be careful with it.
    :::

5. Erase the disk again so it is blank for later tasks.

    ```bash
    sudo wipefs -a /dev/sdd
    ```

    ```{.output}
    /dev/sdd: 8 bytes were erased at offset 0x00000200 (gpt): 45 46 49 20 50 41 52 54
    /dev/sdd: 8 bytes were erased at offset 0x13ffffe00 (gpt): 45 46 49 20 50 41 52 54
    /dev/sdd: 2 bytes were erased at offset 0x000001fe (PMBR): 55 aa
    ```

    ::: explain
    **What just happened:** `wipefs -a` erases all signatures it finds: here the primary GPT header, the backup GPT header at the end of the disk, and the "protective MBR" that GPT keeps at the start so old tools do not think the disk is empty.
    :::

**Checkpoint:** `lsblk /dev/sdd` shows a disk with no partitions. You can say which tool needs `w` to save (`fdisk`, `gdisk`) and which writes immediately (`parted`).

3. Show the identifiers with `blkid`.

    ```bash
    sudo blkid /dev/sde1
    ```


    **What just happened:** `blkid` prints the filesystem **UUID** and **LABEL** (stored inside the filesystem) and the GPT **PARTUUID** and **PARTLABEL** (stored in the partition table). You use the UUID in `/etc/fstab` later because it stays the same even if the disk becomes `/dev/sdf` one day.

4. Now imagine this is a cloud server whose disk was just enlarged in the provider's console: the partition must grow to fill the disk. `growpart DISK PARTNUMBER` grows a partition into the free space after it, even while it is mounted. Note the space between the disk and the number.

    ```bash
    sudo growpart /dev/sde 1
    lsblk /dev/sde
    ```

    ```{.output}
    CHANGED: partition=1 start=2048 old: size=2097152 end=2099199 new: size=10483679 end=10485726

    └─sde1   8:65   0   5G  0 part /mnt/part
    ```

5. The partition is bigger, but the filesystem inside it is not. Grow the ext4 filesystem with `resize2fs`, online.

    ```bash
    df -h /mnt/part
    sudo resize2fs /dev/sde1
    df -h /mnt/part
    ```

    ```{.output}
    Filesystem      Size  Used Avail Use% Mounted on
    /dev/sde1       974M   24K  907M   1% /mnt/part
    ```

#### Task 4: Build LVM storage

1. Turn `/dev/sdb` and `/dev/sdc` into physical volumes, then list them.

    ```bash
    sudo pvcreate /dev/sdb /dev/sdc
    sudo pvs
    sudo pvdisplay /dev/sdb
    ```

    ```{.output}
      Physical volume "/dev/sdb" successfully created.
      Physical volume "/dev/sdc" successfully created.
      PV         VG        Fmt  Attr PSize   PFree
      /dev/sda3  ubuntu-vg lvm2 a--  <23.00g 11.50g
      /dev/sdb             lvm2 ---    5.00g  5.00g
      /dev/sdc             lvm2 ---    5.00g  5.00g
      "/dev/sdb" is a new physical volume of "5.00 GiB"
      --- NEW Physical volume ---
      PV Name               /dev/sdb
      VG Name
      PV Size               5.00 GiB
      Allocatable           NO
      PE Size               0
      Total PE              0
      Free PE               0
      Allocated PE          0
      PV UUID               Xb3k2L-....
    ```

    ::: explain
    **What just happened:** `pvcreate` wrote an LVM label on each disk. You can use whole disks (as here) or partitions of type `8e00`/`8e`. `pvs` is the short, one-line-per-PV summary; `pvdisplay` is the long, detailed view. The new PVs have no **VG** yet, and **PE** (physical extent) counts are 0 until they join a group. `/dev/sda3` is Ubuntu's own PV.
    :::

2. Create a volume group named `labvg` from `/dev/sdb` only. You add `/dev/sdc` later to practice growing.

    ```bash
    sudo vgcreate labvg /dev/sdb
    sudo vgs
    sudo vgdisplay labvg | grep -E 'VG Name|VG Size|PE Size|Total PE|Free  PE'
    ```

    ```{.output}
      Volume group "labvg" successfully created
      VG        #PV #LV #SN Attr   VSize   VFree
      labvg       1   0   0 wz--n-  <5.00g <5.00g
      ubuntu-vg   1   1   0 wz--n- <23.00g 11.50g
      VG Name               labvg
      VG Size               <5.00 GiB
      PE Size               4.00 MiB
      Total PE              1279
      Free  PE / Size       1279 / <5.00 GiB
    ```

    ::: explain
    **What just happened:** `vgs` shows the number of PVs, LVs, and snapshots (`#SN`) in each group, its size (**VSize**), and free space (**VFree**). In **Attr**, `w` means writable, `z` resizable, and `n` the normal allocation policy. `vgdisplay` shows the extent size (4 MiB) and how many extents exist. `<5.00g` means "slightly less than 5 GiB"; LVM metadata uses a little space.
    :::

3. Create two logical volumes. `-n` names the LV, `-L` gives its size, and the last argument is the VG.

    ```bash
    sudo lvcreate -n data -L 1G labvg
    sudo lvcreate -n logs -L 1G labvg
    sudo lvs labvg
    sudo lvdisplay labvg/data | grep -E 'LV Path|LV Size|LV Status'
    ```

    ```{.output}
      Logical volume "data" created.
      Logical volume "logs" created.
      LV   VG    Attr       LSize Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
      data labvg -wi-a----- 1.00g
      logs labvg -wi-a----- 1.00g
      LV Path                /dev/labvg/data
      LV Status              available
      LV Size                1.00 GiB
    ```

    ::: explain
    **What just happened:** Each LV is now a block device at `/dev/labvg/data` and `/dev/labvg/logs`. In the `lvs` **Attr** column, `w` means writable, `i` inherited allocation, and `a` **active** (usable). When an LV is mounted, a sixth letter `o` (open) appears. You could also size by extents (`-l 100`) or by percent (`-l 50%FREE`).
    :::

4. Put an ext4 filesystem on `data` and an XFS filesystem on `logs`, mount them, and save a test file on each.

    ```bash
    sudo mkfs.ext4 -q /dev/labvg/data
    sudo mkfs.xfs -q /dev/labvg/logs
    sudo mount /dev/labvg/data /mnt/data
    sudo mount /dev/labvg/logs /mnt/logs
    echo "LVM test data" | sudo tee /mnt/data/hello.txt /mnt/logs/hello.txt
    df -hT /mnt/data /mnt/logs
    ```

    ```{.output}
    LVM test data
    Filesystem             Type  Size  Used Avail Use% Mounted on
    /dev/mapper/labvg-data ext4  974M   28K  907M   1% /mnt/data
    /dev/mapper/labvg-logs xfs   960M   51M  909M   6% /mnt/logs
    ```

    ::: explain
    **What just happened:** `-q` (quiet) hides the long `mkfs` output. `tee` can write to several files at once. `df -hT` adds the filesystem **Type** column. Notice the device name: `/dev/labvg/data` is a link to `/dev/mapper/labvg-data`, the device-mapper name the kernel uses. Both names work everywhere.
    :::

::: checkpoint
**Checkpoint:** `sudo lvs labvg` shows `data` and `logs`, both with `o` (open) in their attributes, and `cat /mnt/data/hello.txt /mnt/logs/hello.txt` prints the test line twice.

    ```bash
    done

    df -i /mnt/tiny
    ```

    ```{.output}

    Failed at file 100
    Filesystem      Size  Used Avail Use% Mounted on

    Filesystem     Inodes IUsed IFree IUse% Mounted on
    tmpfs             100   100     0  100% /mnt/tiny
    ```

    ::: explain
    **What just happened:** The `for` loop runs `touch` for `f1` through `f200`. `||` runs the block in braces only if `touch` fails, and `break` stops the loop. The error says **No space left on device**, yet `df -h` shows 0% used. The real cause is in `df -i`: 100% of inodes are used (the root folder took one, so file 100 failed).     ::: explain
    **What just happened:** `-x TYPE` hides filesystem types you do not care about. `du -s` gives one summary total, and `--max-depth=1` gives one total per subfolder; `sort -h` sorts human-readable sizes so the biggest folders come last. 1. Test `noexec`. Create a tiny script on `/mnt/data`, run it, then remount with `noexec` and run it again. `-o remount,OPTION` changes options without unmounting.

    ```bash
    printf '#!/bin/bash\necho "script ran"\n' | sudo tee /mnt/data/hi.sh
    sudo chmod +x /mnt/data/hi.sh
    /mnt/data/hi.sh
    sudo mount -o remount,noexec /mnt/data
    /mnt/data/hi.sh
    sudo mount -o remount,exec /mnt/data
    ```

    ```{.output}
    script ran
    -bash: /mnt/data/hi.sh: Permission denied
    ```

    ::: explain
    **What just happened:** `printf` writes the text with `\n` turned into new lines. With `noexec`, the kernel refuses to run any program stored on that filesystem, even though the file has execute permission. Administrators mount `/tmp`, `/var/tmp`, and `/dev/shm` with `noexec` so that malware downloaded there cannot be run directly. (`bash /mnt/data/hi.sh` still works, because then `bash` is the program and it lives elsewhere.)

2. Test `ro` and `rw`.

    ```bash
    sudo mount -o remount,ro /mnt/data
    sudo touch /mnt/data/newfile
    sudo mount -o remount,rw /mnt/data
    sudo touch /mnt/data/newfile && echo "write OK"
    ```

    ```{.output}
    touch: cannot touch '/mnt/data/newfile': Read-only file system
    write OK
    ```

    ::: explain
    **What just happened:** Even root cannot write to a filesystem mounted `ro`. The kernel also switches a filesystem to read-only by itself when it detects errors, which is why "Read-only file system" in a log often means "run fsck." `mount -o remount,rw /` is a common step in rescue mode.
    :::

3. Test `nosuid`. A **setuid** program runs as its owner instead of as the person who started it. Copy `whoami` (which prints the effective user), make the copy setuid root, and compare.

    ```bash
    sudo cp /usr/bin/whoami /mnt/data/whoami-suid
    sudo chmod u+s /mnt/data/whoami-suid
    /mnt/data/whoami-suid
    sudo mount -o remount,nosuid /mnt/data
    /mnt/data/whoami-suid
    sudo rm /mnt/data/whoami-suid
    ```

    ```{.output}
    root
    student
    ```

    ::: explain
    **What just happened:** `chmod u+s` set the setuid bit, so the copy ran as its owner, `root`, even though you are `student`. That is dangerous on a removable disk or shared folder: anyone could bring their own setuid-root program. With `nosuid`, the kernel ignores the bit and the program runs as `student`. You deleted the copy right away because a setuid-root binary is a security risk.
    :::

4. Test `nodev`. Create a device file that points to the same kernel device as `/dev/null` (character device, major 1, minor 3) and write to it.

    ```bash
    sudo mknod /mnt/data/mynull c 1 3
    sudo chmod 666 /mnt/data/mynull
    echo test > /mnt/data/mynull && echo "device works"
    sudo mount -o remount,nodev /mnt/data
    echo test > /mnt/data/mynull
    sudo rm /mnt/data/mynull
    ```

    ```{.output}
    device works
    -bash: /mnt/data/mynull: Permission denied
    ```

    ::: explain
    **What just happened:** `mknod NAME c MAJOR MINOR` creates a character device file. Without `nodev`, a device file anywhere gives access to that device, so someone could put a copy of `/dev/sda` on a USB stick and read your disk. `nodev` blocks device files on that filesystem. Use `nodev`, `nosuid`, and `noexec` together on removable media, `/tmp`, and home directories.
    :::

5. Test `noatime`. Every read normally updates a file's **access time** (atime). Ubuntu mounts with `relatime` by default, which updates it only if it is older than the last modification or more than a day old. Set an old access time, read the file, and compare.

    ```bash
    sudo touch -a -d '2 days ago' /mnt/data/hello.txt
    stat -c 'atime: %x' /mnt/data/hello.txt
    cat /mnt/data/hello.txt > /dev/null
    stat -c 'atime: %x' /mnt/data/hello.txt
    sudo mount -o remount,noatime /mnt/data
    sudo touch -a -d '2 days ago' /mnt/data/hello.txt
    cat /mnt/data/hello.txt > /dev/null
    stat -c 'atime: %x' /mnt/data/hello.txt
    ```

    ```{.output}
    atime: 2026-10-08 11:30:12.000000000 +0000
    atime: 2026-10-10 11:30:15.123456789 +0000
    atime: 2026-10-08 11:30:20.000000000 +0000
    ```

    ::: explain
    **What just happened:** `touch -a -d` set only the access time to two days ago. With `relatime`, reading the file updated the atime to now. With `noatime`, the read did not change it. Skipping these updates saves disk writes on busy servers. `nodiratime` does the same for directories only; `noatime` already includes it.
    :::


    ```{.output}
    lrwxrwxrwx 1 root root 19 Apr 22 13:08 /etc/mtab -> ../proc/self/mounts
    /dev/mapper/labvg-logs /mnt/logs xfs rw,relatime,attr2,inode64,logbufs=8,... 0 0
    /dev/mapper/labvg-data /mnt/data ext4 rw,relatime 0 0
    ```

    ::: explain
    **What just happened:** `/proc/mounts` is the kernel's live list of mounted filesystems, in the same six-field format as fstab. `/etc/mtab` was once a file that `mount` updated by hand (and could get out of sync); today it is a symbolic link to the kernel's list, so both always agree. `/etc/fstab` is different: it is what **should** be mounted at boot.
    :::

    ::: warning
    The next steps edit `/etc/fstab`. A mistake in this file can stop the VM from booting normally. Make sure you took the snapshot at the start of the lab, keep the backup copy you make below, and use `tee -a` (append), never `tee` alone, which would replace the whole file.
    :::

8. Make the LV mounts permanent in `/etc/fstab`. Back up the file first. The commands use `blkid -s UUID -o value` to print only the UUID, so you do not have to copy it by hand.

    ```bash
    sudo cp /etc/fstab /etc/fstab.lab-backup
    DATA_UUID=$(sudo blkid -s UUID -o value /dev/labvg/data)
    LOGS_UUID=$(sudo blkid -s UUID -o value /dev/labvg/logs)
    echo "UUID=$DATA_UUID /mnt/data ext4 defaults,noatime,nofail 0 2" | sudo tee -a /etc/fstab
    echo "UUID=$LOGS_UUID /mnt/logs xfs  defaults,nofail 0 0" | sudo tee -a /etc/fstab
    ```

    ```{.output}
    UUID=4c1e6a2f-... /mnt/data ext4 defaults,noatime,nofail 0 2
    UUID=8d2b7f3a-... /mnt/logs xfs  defaults,nofail 0 0
    ```

    ::: explain
    **What just happened:** The six fields are: **device** (`UUID=...`), **mount point**, **type**, **options** (`defaults` means `rw,suid,dev,exec,auto,nouser,async`, then `noatime` and `nofail` change some of those), **dump** (`0`, legacy backup flag), and **fsck pass** (`1` for `/`, `2` for other ext4 filesystems checked at boot, `0` to skip; XFS always uses `0`). Shell variables like `DATA_UUID` hold the UUIDs; `$DATA_UUID` inserts the value. `tee -a` appends instead of overwriting, which matters a lot here.
    :::

9. Test the new lines without rebooting. A broken fstab line can drop the system into emergency mode at boot, so always test.

    ```bash
    sudo umount /mnt/data /mnt/logs
    sudo systemctl daemon-reload
    sudo findmnt --verify
    sudo mount -a
    findmnt /mnt/data /mnt/logs
    ```

    ```{.output}
    Success, no errors or warnings detected
    TARGET    SOURCE                 FSTYPE OPTIONS
    /mnt/data /dev/mapper/labvg-data ext4   rw,noatime
    /mnt/logs /dev/mapper/labvg-logs xfs    rw,relatime,attr2,inode64,logbufs=8,...
    ```

    ::: explain
    **What just happened:** `systemctl daemon-reload` makes systemd re-read fstab (systemd turns each line into a `.mount` unit). `findmnt --verify` checks the file for errors. `mount -a` mounts everything in fstab that is not mounted yet; if it prints nothing, every line worked. `findmnt` with mount points shows they came back with the fstab options (`noatime` on `/mnt/data`).
    :::

10. See what `nofail` does. Add a line for a disk that does not exist, with `nofail`.

    ```bash
    sudo mkdir -p /mnt/missing
    echo "UUID=00000000-1111-2222-3333-444444444444 /mnt/missing ext4 defaults,nofail 0 0" \
      | sudo tee -a /etc/fstab
    sudo systemctl daemon-reload
    sudo mount -a && echo "mount -a finished without errors"
    sudo sed -i '/\/mnt\/missing/d' /etc/fstab
    sudo systemctl daemon-reload
    ```

    ::: explain
    **What just happened:** `mount -a` quietly skipped the missing device because of `nofail`. Without `nofail`, `mount -a` would print an error, and at boot systemd would wait about 90 seconds for the device and then drop to emergency mode, which is a disaster on a remote server. Use `nofail` for removable, network, and non-essential disks. The `sed` command deleted every line containing `/mnt/missing` (the slashes are escaped with `\` because `/` is sed's separator).
    :::

::: checkpoint
**Checkpoint:** `grep -c labvg /proc/mounts` prints `2`, `grep -c missing /etc/fstab` prints `0`, and `sudo findmnt --verify` reports no errors.
:::

#### Task 8: Build and break a RAID 1 mirror with mdadm

1. Create a RAID 1 array named `/dev/md0` from `/dev/sdd` and `/dev/sde`. When mdadm warns that the array may not be suitable as a boot device and asks `Continue creating array?`, type `y`.

    ```bash
    sudo mdadm --create /dev/md0 --level=1 --raid-devices=2 /dev/sdd /dev/sde
    ```

    ```{.output}
    mdadm: Note: this array has metadata at the start and
        may not be suitable as a boot device.  If you plan to
        store '/boot' on this device please ensure that
        your boot-loader understands md/v1.x metadata, or use
        --metadata=0.90
    mdadm: size set to 5237760K
    Continue creating array? y
    mdadm: Defaulting to version 1.2 metadata
    mdadm: array /dev/md0 started.
    ```

2. Watch the two disks synchronize. `/proc/mdstat` is the kernel's live RAID status. `watch -n 1` reruns a command every second; press **Ctrl+C** when the progress bar is gone.

    ```bash
    watch -n 1 cat /proc/mdstat
    ```

    ```{.output}
    Personalities : [raid1] [linear] [raid0] [raid6] [raid5] [raid4] [raid10]
    md0 : active raid1 sde[1] sdd[0]
          5237760 blocks super 1.2 [2/2] [UU]
          [=======>.............]  resync = 38.4% (2011648/5237760) finish=0.3min speed=168000K/sec
    ```

    ::: explain
    **What just happened:** `md0 : active raid1` names the array and level, followed by its members with their slot numbers. `[2/2]` means 2 devices wanted, 2 working, and `[UU]` shows each member's state (`U` = up, `_` = missing or failed). The resync copies one disk onto the other so they start identical. You can use the array during the resync.
    :::

3. Format the array, mount it, and save a file.

    ```bash
    sudo mkfs.ext4 -q /dev/md0
    sudo mount /dev/md0 /mnt/raid
    echo "mirrored data" | sudo tee /mnt/raid/important.txt
    sudo mdadm --detail /dev/md0 | grep -E 'Raid Level|State :|Active Devices|/dev/sd'
    ```

    ```{.output}
    mirrored data
            Raid Level : raid1
                 State : clean
        Active Devices : 2
           0       8       48        0      active sync   /dev/sdd
           1       8       64        1      active sync   /dev/sde
    ```

4. Simulate a disk failure: mark `/dev/sde` as failed, check the status, and prove the data is still readable.

    ```bash
    sudo mdadm /dev/md0 --fail /dev/sde
    cat /proc/mdstat
    cat /mnt/raid/important.txt
    ```

    ```{.output}
    mdadm: set /dev/sde faulty in /dev/md0
    md0 : active raid1 sde[1](F) sdd[0]
          5237760 blocks super 1.2 [2/1] [U_]
    mirrored data
    ```

    ::: explain
    **What just happened:** `(F)` marks the failed member, `[2/1]` means only one of two devices works, and `[U_]` shows the second slot is down. The array is **degraded** but your file is still there, served from `/dev/sdd`. On a real server, `mdadm --monitor` (the `mdmonitor` service) would email you now.
    :::

5. Replace the disk: remove the failed member and add it back (on real hardware you would add the new disk). Watch it rebuild.

    ```bash
    sudo mdadm /dev/md0 --remove /dev/sde
    sudo mdadm /dev/md0 --add /dev/sde
    watch -n 1 cat /proc/mdstat
    ```

    ```{.output}
    mdadm: hot removed /dev/sde from md0
    mdadm: added /dev/sde
    md0 : active raid1 sde[2] sdd[0]
          5237760 blocks super 1.2 [2/1] [U_]
          [====>................]  recovery = 22.0% (1152000/5237760) finish=0.4min
    ```

    ::: explain
    **What just happened:** `--remove` takes the failed disk out of the array, and `--add` adds a disk as a spare, which immediately starts **recovery** (rebuilding the mirror). When it finishes, `/proc/mdstat` shows `[2/2] [UU]` again. To make an array start automatically at boot you would save its definition with `sudo mdadm --detail --scan | sudo tee -a /etc/mdadm/mdadm.conf` and run `sudo update-initramfs -u`; this lab skips that because you remove the array in Clean up.
    :::

::: checkpoint
**Checkpoint:** After recovery finishes, `cat /proc/mdstat` shows `[2/2] [UU]`, and `cat /mnt/raid/important.txt` prints `mirrored data`.
:::

#### Task 9: Share storage over the network with NFS, Samba, and autofs

1. Create an NFS share. You will export it to ubuntu-lab itself (`127.0.0.1`) and to the lab network. Back up `/etc/exports`, create the folder, and give it to `student`.

    ```bash
    sudo cp /etc/exports /etc/exports.lab-backup
    sudo mkdir -p /srv/nfs/share
    sudo chown student:student /srv/nfs/share
    OPTS="rw,sync,no_subtree_check"
    echo "/srv/nfs/share 127.0.0.1($OPTS) 192.168.100.0/24($OPTS)" | sudo tee -a /etc/exports
    sudo exportfs -ra
    sudo exportfs -v
    ```

    ```{.output}
    /srv/nfs/share  127.0.0.1(sync,wdelay,hide,no_subtree_check,sec=sys,rw,secure,root_squash,...)
    /srv/nfs/share  192.168.100.0/24(sync,wdelay,hide,no_subtree_check,sec=sys,rw,secure,...)
    ```

    ::: explain
    **What just happened:** `OPTS` is a shell variable that holds the option list so the line stays short; `$OPTS` inserts it. Each `/etc/exports` line is `DIRECTORY CLIENT(OPTIONS) CLIENT(OPTIONS)...`. **There must be no space between a client and its parentheses**; a space would export to everyone with default options. `rw` allows writing, `sync` makes the server save data to disk before replying, and `no_subtree_check` avoids a slow and unreliable check. `exportfs -ra` re-reads the file and applies it, and `exportfs -v` shows the active exports with all default options, including `root_squash`. Change `192.168.100.0/24` to your lab network if it differs.
    :::

2. Mount the NFS share as a client and test it.

    ```bash
    showmount -e 127.0.0.1
    sudo mount -t nfs 127.0.0.1:/srv/nfs/share /mnt/nfs
    findmnt /mnt/nfs
    touch /mnt/nfs/from-student.txt && ls -l /mnt/nfs
    sudo touch /mnt/nfs/from-root.txt
    ```

    ```{.output}
    Export list for 127.0.0.1:
    /srv/nfs/share 192.168.100.0/24,127.0.0.1
    TARGET   SOURCE                   FSTYPE OPTIONS
    /mnt/nfs 127.0.0.1:/srv/nfs/share nfs4   rw,relatime,vers=4.2,rsize=524288,...
    -rw-rw-r-- 1 student student 0 Oct 10 11:45 from-student.txt
    touch: cannot touch '/mnt/nfs/from-root.txt': Permission denied
    ```

    ::: explain
    **What just happened:** `showmount -e` asks the server what it exports. The NFS source is written `SERVER:/path`. The client negotiated NFS version 4.2 (type `nfs4`). `student` could write because the folder belongs to `student` (NFS checks user ID numbers, so UIDs should match on client and server). **root** could not write: with `root_squash` (the default), root on the client is mapped to the powerless user `nobody` on the server, so a client's root cannot take over the server's files. An fstab line for this share would be `ubuntu-lab:/srv/nfs/share /mnt/nfs nfs defaults,_netdev,nofail 0 0`.
    :::

    ::: tip
    Optional, from rocky-lab: `sudo dnf install -y nfs-utils`, then `sudo mount -t nfs ubuntu-lab:/srv/nfs/share /mnt` and `ls /mnt`. Unmount with `sudo umount /mnt` when done. Ubuntu's firewall (`ufw`) is inactive by default, so no port needs opening; on a server with a firewall you would allow NFS (TCP port 2049).
    :::

3. Create an SMB share with Samba. Back up the configuration, create the folder, and add a share definition at the end of `/etc/samba/smb.conf`.

    ```bash
    sudo cp /etc/samba/smb.conf /etc/samba/smb.conf.lab-backup

       valid users = student

    testparm -s 2>/dev/null | grep -A4 '\[labshare\]'
    ```

    ::: explain
    **What just happened:** This uses a **heredoc**: the lines between `<<'EOF'` and `EOF` are sent to `sudo tee -a`, which appends them to the file with root rights. A Samba share is a section in brackets (the share name) followed by settings. `testparm` checks `smb.conf` for errors and prints the result; `-s` skips the "press Enter" prompt.
    :::

6. Set up **autofs** to mount the NFS share on demand. First unmount the manual NFS mount. Then create an **indirect map**: a master entry that says "manage folder `/auto` using map file `/etc/auto.lab`," and a map that says "the key `nfs` under it is this NFS share."

    ::: explain
    **What just happened:** The `grep` confirmed that the main file `/etc/auto.master` includes every `*.autofs` file in `/etc/auto.master.d/`. (If it prints nothing, add the line `/auto /etc/auto.lab --timeout=30` to `/etc/auto.master` instead.) In the map file, each line is `KEY OPTIONS LOCATION`. `--timeout=30` unmounts the share after 30 idle seconds. ### Exam corner

- LVM order: `pvcreate` then `vgcreate` then `lvcreate` then `mkfs` then `mount`. Removal is the reverse: `umount`, `lvremove`, `vgremove`, `pvremove`.
- Summaries: `pvs`, `vgs`, `lvs`. Details: `pvdisplay`, `vgdisplay`, `lvdisplay`. Discovery: `pvscan`, `vgscan`.
- Grow: `vgextend` adds a PV; `lvextend`/`lvresize -L +SIZE`; then `resize2fs` (ext4) or `xfs_growfs MOUNTPOINT` (XFS), or use `-r` to do both. XFS cannot shrink.
- `pvmove` migrates extents off a PV online; then `vgreduce` and `pvremove`. `pvresize` after the disk grows. Move a VG between hosts: `vgchange -an`, `vgexport`, then `vgimport`, `vgchange -ay`. `lvchange -an/-ay` deactivates/activates one LV.
- MBR: 4 primary partitions, 2 TiB limit. GPT: 128 partitions, backup table. `fdisk` and `gdisk` save with `w`; `parted` writes immediately. `growpart DISK N` grows a partition (cloud disks).
- `blkid` shows UUID and TYPE; use `UUID=` in `/etc/fstab`. Fields: device, mount point, type, options, dump, fsck pass. Test with `mount -a` and `findmnt --verify`.
- Options: `noexec`, `nosuid`, `nodev` (harden `/tmp` and removable media), `ro`/`rw`, `remount`, `noatime`/`nodiratime`, `nofail` (do not block boot), `_netdev` (network mounts).
- `/proc/mounts` is the kernel's live list; `/etc/mtab` links to it.
- `fsck` (ext family) and `xfs_repair` (XFS) only on unmounted filesystems. `df -h` space, `df -i` inodes, `du -sh` folder size, `fio` benchmarks I/O.
- "No space left on device" with free space = inode exhaustion; check `df -i`.
- RAID 0 stripe, 1 mirror, 5 parity (3+ disks), 6 double parity (4+), 10 striped mirrors. `mdadm --create`, `--detail`, `--fail`, `--remove`, `--add`; status in `/proc/mdstat` (`[UU]` healthy, `[U_]` degraded).
- NFS: `/etc/exports`, `exportfs -ra`, `showmount -e`, `mount -t nfs host:/path`; `root_squash` is the default. SMB: Samba `smb.conf`, `smbpasswd -a`, `mount -t cifs //host/share`. autofs: `/etc/auto.master` plus map files, mounts on access.
