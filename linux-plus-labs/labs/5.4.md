## Lab 5.4: Troubleshoot Security Issues {#lab-5-4}

::: labinfo
**Objective:** 5.4 Given a scenario, analyze and troubleshoot security issues on a Linux system.\
**Domain:** 5.0 Troubleshooting (22% of the exam)\
**Time:** about 3.5 hours\
**VM:** rocky-lab (SELinux, faillock, repositories) and ubuntu-lab (everything else)\
**Snapshot first:** Yes. Take a snapshot of both VMs now. This lab changes SSH, PAM, firewall, and repository settings, and a mistake there can lock you out.
:::

Security problems show up in two ways: something legitimate is blocked ("403 Forbidden", "Permission denied (publickey)", "certificate has expired") or something dangerous is allowed (a database open to the network, TLS 1.0 still enabled, months of missing patches). In this break-and-fix lab you create both kinds, find the evidence in the logs, and fix them the right way, not by turning security off.

### What you'll practice

- SELinux issues: file **context** (`ls -Z`, `restorecon`), **booleans** (`getsebool`, `setsebool -P`), and **policy** (port labels with `semanage port`); reading AVC denials with `ausearch` and `sealert`
- File and directory permission issues: missing execute on directories, **ACL** mask problems (`getfacl`, `setfacl`), and **attributes** (`lsattr`, `chattr`)
- Account access: locked, expired, and `nologin` accounts (`passwd -S`, `chage -l`, `usermod`), and `faillock` lockouts
- Remote access issues: `AllowUsers`, wrong `~/.ssh` permissions, reading `ssh -v` and sshd logs
- Unpatched vulnerable systems: pending security updates, held packages, unattended-upgrades, `dnf updateinfo`, reboot-required checks
- Exposed or misconfigured services: a database listening on all interfaces, found with `ss` and `nmap`
- Certificate issues: untrusted, missing intermediate, hostname mismatch, and expired certificates (`openssl s_client`, `openssl x509`, `curl -v`)
- Misconfigured package repository: bad URLs and wrong signing keys (`NO_PUBKEY`) with apt and dnf
- Use of obsolete or insecure protocols and ciphers, and cipher negotiation issues (TLS and SSH, `nmap ssl-enum-ciphers`, `update-crypto-policies`)

### How it works

**The same method, with a security twist.** You still identify symptoms, gather data, form a hypothesis, test, fix, verify, and document (Lab 5.2). Security adds one rule: **the fix must not weaken security**. "Disable SELinux", "chmod 777", "PermitRootLogin yes", and "skip certificate checks" make the symptom go away while creating a bigger problem. The right fix corrects the label, permission, key, or configuration that was actually wrong.

**Where security evidence lives.**

| What | Ubuntu | Rocky |
|---|---|---|
| Logins, sudo, SSH | `/var/log/auth.log`, `journalctl -u ssh` | `/var/log/secure`, `journalctl -u sshd` |
| SELinux / AppArmor denials | `journalctl -k | grep apparmor` | `/var/log/audit/audit.log` (`ausearch -m avc`) |
| Web server errors | `/var/log/nginx/error.log` | `/var/log/httpd/error_log` |
| Package updates | `/var/log/apt/history.log`, `/var/log/unattended-upgrades/` | `dnf history` |

**SELinux in one page.** SELinux (Security-Enhanced Linux, enforcing by default on Rocky) labels every process and file with a **context** like `system_u:system_r:httpd_t:s0`. The third part is the **type**. The **policy** is a large set of rules saying which process types may do what to which object types: for example `httpd_t` may read files of type `httpd_sys_content_t` and bind to ports of type `http_port_t`. Anything not allowed is denied and logged as an **AVC** (access vector cache) denial, *even for root and even if normal file permissions allow it*. **Booleans** are on/off switches built into the policy for common optional behavior (for example `httpd_can_network_connect`). So an SELinux problem is always one of three things:

```{.diagram}
  denied!  ->  is the FILE/PORT labeled wrong?    -> restorecon / semanage fcontext
           ->  is an optional feature switched off? -> setsebool -P <boolean> on
           ->  is it truly not in the policy?       -> semanage port, or (last resort)
                                                       audit2allow -M local module
```

Ubuntu uses **AppArmor** instead, which confines programs by file path rather than labels. Its denials appear in the kernel log as `apparmor="DENIED"`; `sudo aa-status` lists confined programs.

**Permissions are layered.** Access must pass *every* layer: directory execute permission on every parent directory, the file's mode bits, any **ACL** (access control list) entries limited by the ACL **mask**, file **attributes** such as immutable (`i`) or append-only (`a`), and finally SELinux or AppArmor. Check them in that order.

**TLS certificates in one paragraph.** A server certificate binds a name (in the Subject Alternative Name, **SAN**) to a public key, is valid between two dates, and is signed by a CA (certificate authority), usually through an **intermediate** CA. A client trusts it only if it can build a chain from the server certificate, through intermediates *the server sends*, up to a root CA in its own trust store, and the name it connected to is in the SAN, and today's date is within the validity period.

#### Task 2: Scenario 1: "403 Forbidden" after moving a file (SELinux context)

1. **Break it.** On rocky-lab, create a page in your home directory and *move* it into the web root, as many admins do.

    ```bash
    # on rocky-lab
    echo "<h1>Quarterly report</h1>" > ~/report.html
    sudo mv ~/report.html /var/www/html/
    ```

2. **Symptom.**

    ```bash
    # on rocky-lab
    curl -s -o /dev/null -w '%{http_code}\n' http://localhost/report.html
    ```

    ```{.output}
    403
    ```

3. **Investigate the normal layers first:** file permissions and the web server's own log.

    ```bash
    # on rocky-lab
    ls -l /var/www/html/
    sudo tail -n 1 /var/log/httpd/error_log
    ```

    ```{.output}
    -rw-r--r--. 1 root    root    21 Oct 10 14:02 index.html
    -rw-rw-r--. 1 student student 26 Oct 10 14:05 report.html
    [core:error] [pid 2345:tid 2401] (13)Permission denied: [client ::1:54322] AH00132: file permissions deny server access: /var/www/html/report.html
    ```

    ::: explain
    **What just happened:** The mode bits allow everyone to read (`r--` for others), yet Apache reports "Permission denied". The `.` after the permissions means the file has an SELinux context. When normal permissions look fine but access is denied, suspect SELinux.
    :::

4. **Investigate SELinux.** Compare the labels and look for AVC denials.

    ```bash
    # on rocky-lab
    ls -Z /var/www/html/
    sudo ausearch -m avc -ts recent
    ```

    ```{.output}
    system_u:object_r:httpd_sys_content_t:s0 index.html
    unconfined_u:object_r:user_home_t:s0 report.html
    ----
    time->Sat Oct 10 14:05:31 2026
    type=AVC msg=audit(1791641131.512:412): avc:  denied  { read } for  pid=2345 comm="httpd" name="report.html" dev="dm-0" ino=17112 scontext=system_u:system_r:httpd_t:s0 tcontext=unconfined_u:object_r:user_home_t:s0 tclass=file permissive=0
    ```

    ::: explain
    **What just happened:** `ls -Z` shows contexts: `index.html` has the web content type `httpd_sys_content_t`, but `report.html` kept `user_home_t` from your home directory, because `mv` keeps a file's label (while `cp` creates a new file that gets the destination directory's label). `ausearch -m avc -ts recent` searches the audit log for AVC messages from the last 10 minutes. Read it as: process `httpd` with context `scontext` (`httpd_t`) was denied `read` on a `file` with context `tcontext` (`user_home_t`). `permissive=0` means it was really blocked.
    :::

5. **Test the hypothesis** with the plain-English explanation and the expected label.

    ```bash
    # on rocky-lab
    sudo sealert -a /var/log/audit/audit.log | grep -A6 "SELinux is preventing" | head -n 8
    matchpathcon /var/www/html/report.html
    ```

    ```{.output}
    SELinux is preventing /usr/sbin/httpd from read access on the file report.html.

    *****  Plugin restorecon (99.5 confidence) suggests   ************************

    If you want to fix the label.
    /var/www/html/report.html default label should be httpd_sys_content_t.
    Then you can run restorecon.
    /var/www/html/report.html	system_u:object_r:httpd_sys_content_t:s0
    ```

6. **Root cause.** Wrong SELinux file context (`user_home_t` instead of `httpd_sys_content_t`).

7. **Fix.** Reset the label to what the policy says it should be.

    ```bash
    # on rocky-lab
    sudo restorecon -v /var/www/html/report.html
    ```

    ```{.output}
    Relabeled /var/www/html/report.html from unconfined_u:object_r:user_home_t:s0 to unconfined_u:object_r:httpd_sys_content_t:s0
    ```

    ::: explain
    **What just happened:** `restorecon` sets files back to the default context defined by the policy's file-context rules (`-v` shows what changed, `-R` would recurse into directories). If you serve content from a non-standard directory such as `/srv/site`, first teach the policy the right label with `sudo semanage fcontext -a -t httpd_sys_content_t "/srv/site(/.*)?"`, then run `sudo restorecon -Rv /srv/site`. Using `chcon` also changes a label, but only until the next relabel.
    :::

8. **Verify.** The `curl` from step 2 now prints `200`.

9. **Prevent.** Use `cp` (or `mv` followed by `restorecon`) when placing web content, and never "fix" SELinux with `setenforce 0`. Switching to permissive mode is only acceptable for a few seconds as a *test* to confirm SELinux is involved.

::: checkpoint
**Checkpoint:** `ls -Z /var/www/html/report.html` shows `httpd_sys_content_t` and the page returns `200`.
:::

#### Task 3: Scenario 2: "503 Service Unavailable" from a reverse proxy (SELinux boolean)

1. **Break it.** Start a small back-end application on port 5000 and make Apache a reverse proxy for it.

    ```bash
    # on rocky-lab
    mkdir -p /tmp/backend && echo "backend app says hi" > /tmp/backend/index.html
    python3 -m http.server 5000 --bind 127.0.0.1 --directory /tmp/backend > /dev/null 2>&1 &
    curl -s http://127.0.0.1:5000/
    cat <<'EOF' | sudo tee /etc/httpd/conf.d/lab-proxy.conf
    # Forward /app/ to the back-end application
    ProxyPass        "/app/" "http://127.0.0.1:5000/" retry=0
    ProxyPassReverse "/app/" "http://127.0.0.1:5000/"
    EOF
    sudo systemctl reload httpd
    ```

    ::: explain
    **What just happened:** The back end answers directly on `127.0.0.1:5000`. `ProxyPass` makes Apache forward requests for `/app/` to it, and `retry=0` makes Apache retry a failed back end immediately instead of waiting 60 seconds (handy while troubleshooting). A **heredoc** (`cat <<'EOF' | sudo tee file`) writes all lines up to `EOF` into the file.
    :::

2. **Symptom.**

    ```bash
    # on rocky-lab
    curl -s -o /dev/null -w '%{http_code}\n' http://localhost/app/
    sudo tail -n 2 /var/log/httpd/error_log
    ```

    ```{.output}
    503
    [proxy:error] [pid 2412:tid 2460] (13)Permission denied: AH00957: http: attempt to connect to 127.0.0.1:5000 (127.0.0.1:5000) failed
    [proxy_http:error] [pid 2412:tid 2460] [client ::1:41236] AH01114: HTTP: failed to make connection to backend: 127.0.0.1
    ```

3. **Investigate.** The back end works when you call it directly, and Apache gets "Permission denied" when *connecting*. Look for the AVC.

    ```bash
    # on rocky-lab
    sudo ausearch -m avc -ts recent | grep name_connect | tail -n 1
    sudo ausearch -m avc -ts recent | audit2why | tail -n 6
    ```

    ```{.output}
    type=AVC msg=audit(1791641402.218:431): avc:  denied  { name_connect } for  pid=2412 comm="httpd" dest=5000 scontext=system_u:system_r:httpd_t:s0 tcontext=system_u:object_r:commplex_main_port_t:s0 tclass=tcp_socket permissive=0

            Was caused by:
            One of the following booleans was set incorrectly.
            Description:
            Allow httpd to can network connect

            Allow access by executing:
            # setsebool -P httpd_can_network_connect 1
    ```

    ::: explain
    **What just happened:** `name_connect` on a `tcp_socket` means httpd tried to open an outgoing TCP connection to port 5000 (whose type here is `commplex_main_port_t`), and the policy does not allow that by default, so that a hacked web server cannot easily attack other services. `audit2why` reads AVC messages and explains why each was denied; here it names the boolean that controls this behavior.
    :::

4. **Look at the boolean.**

    ```bash
    # on rocky-lab
    getsebool httpd_can_network_connect
    sudo semanage boolean -l | grep -E "^httpd_can_network_connect "
    getsebool -a | grep -c httpd
    ```

    ```{.output}
    httpd_can_network_connect --> off
    httpd_can_network_connect      (off  ,  off)  Allow httpd to can network connect
    48
    ```

    ::: explain
    **What just happened:** `getsebool` shows the current value. `semanage boolean -l` shows the current and the default (saved) value plus a description. There are dozens of httpd booleans alone, such as `httpd_enable_homedirs` (serve `~/public_html`), `httpd_can_network_connect_db` (connect to databases), and `httpd_can_sendmail`.
    :::

5. **Root cause and fix.** The optional "web server may make network connections" feature is off. Turn it on **permanently** with `-P`.

    ```bash
    # on rocky-lab
    sudo setsebool -P httpd_can_network_connect on
    getsebool httpd_can_network_connect
    ```

    ::: explain
    **What just happened:** `setsebool` changes a boolean immediately; `-P` also writes it to the policy on disk so it survives a reboot (it takes a few seconds). Without `-P` the fix silently disappears at the next boot, a classic "it broke again after maintenance" problem.
    :::

6. **Verify.** `curl -s http://localhost/app/` prints `backend app says hi`.

7. **Prevent.** Enable only the booleans you need and document why. Before writing custom policy, always check whether a boolean already covers the case (`audit2why` or `sealert` will say so).

::: checkpoint
**Checkpoint:** `getsebool httpd_can_network_connect` shows `on` and `/app/` returns the back end's page.
:::

#### Task 4: Scenario 3: Apache will not start on a new port (SELinux policy)

1. **Break it.** Ask Apache to also listen on port 8090.

    ```bash
    # on rocky-lab
    echo "Listen 8090" | sudo tee /etc/httpd/conf.d/lab-port.conf
    sudo systemctl restart httpd
    ```

    ```{.output}
    Job for httpd.service failed because the control process exited with error code.
    See "systemctl status httpd.service" and "journalctl -xeu httpd.service" for details.
    ```

2. **Symptom and investigation.**

    ```bash
    # on rocky-lab
    sudo journalctl -u httpd -n 5 --no-pager
    sudo ausearch -m avc -ts recent | grep name_bind | tail -n 1
    sudo semanage port -l | grep -w 8090; echo "exit: $?"
    sudo semanage port -l | grep ^http_port_t
    ```

    ```{.output}
    httpd[2601]: (13)Permission denied: AH00072: make_sock: could not bind to address [::]:8090
    httpd[2601]: (13)Permission denied: AH00072: make_sock: could not bind to address 0.0.0.0:8090
    httpd[2601]: no listening sockets available, shutting down
    systemd[1]: httpd.service: Main process exited, code=exited, status=1/FAILURE
    type=AVC msg=audit(1791641620.004:447): avc:  denied  { name_bind } for  pid=2601 comm="httpd" src=8090 scontext=system_u:system_r:httpd_t:s0 tcontext=system_u:object_r:unreserved_port_t:s0 tclass=tcp_socket permissive=0
    exit: 1
    http_port_t                    tcp      80, 81, 443, 488, 8008, 8009, 8443, 9000
    ```

    ::: explain
    **What just happened:** Apache, running as root, still got "Permission denied" when binding (`name_bind`) to port 8090. SELinux labels ports too: 8090 has the generic `unreserved_port_t` type, and the policy only lets `httpd_t` bind to ports labeled `http_port_t`, which lists 80, 443, 8443 and a few others.
    :::

3. **Root cause.** The policy has no rule allowing the web server on this port, because the port is not labeled as a web port.

4. **Fix.** Add the port to the `http_port_t` type, then start Apache.

    ```bash
    # on rocky-lab
    sudo semanage port -a -t http_port_t -p tcp 8090
    sudo semanage port -l | grep ^http_port_t
    sudo systemctl restart httpd
    curl -s http://localhost:8090/
    ```

    ```{.output}
    http_port_t                    tcp      8090, 80, 81, 443, 488, 8008, 8009, 8443, 9000
    hello from rocky-lab
    ```

    ::: explain
    **What just happened:** `semanage port -a` (add) labels TCP port 8090 as `http_port_t`; the change is permanent. If a port already has another type, `-a` fails with "already defined" and you use `-m` (modify) instead. For remote clients you would also open the port in the firewall (`sudo firewall-cmd --permanent --add-port=8090/tcp`, `sudo firewall-cmd --reload`): SELinux and the firewall are separate layers.
    :::

5. **Last resort: a custom policy module.** When no label or boolean fits, you can turn denials into a small local policy module. Look at what it *would* allow before installing anything:

    ```bash
    # on rocky-lab
    sudo ausearch -m avc -ts today | audit2allow | head -n 8
    ```

    ::: explain
    **What just happened:** `audit2allow` turns AVC denials into `allow` rules. `audit2allow -M mymodule` would create `mymodule.pp`, which `sudo semodule -i mymodule.pp` installs. Review the rules carefully: blindly allowing every denial (for example letting `httpd_t` read `user_home_t`) can open real holes when the right fix was a label or boolean. In this lab, the right fixes already exist, so do not install a module.
    :::

6. **Prevent.** When you change a service's port or directories, update SELinux in the same change (`semanage port`, `semanage fcontext`), and check `sudo ausearch -m avc -ts recent` whenever a confined service fails mysteriously.

::: checkpoint
**Checkpoint:** `sudo semanage port -l | grep ^http_port_t` includes `8090`, and `curl http://localhost:8090/` returns the page.
:::

#### Task 5: Scenario 4: "Permission denied" on shared files (permissions, ACLs, attributes)

1. **Break it.** On ubuntu-lab, create a shared finance directory where `bob` should be able to read and edit the budget, then make three "small" changes that each break something.

    ```bash
    sudo mkdir -p /srv/finance
    echo "Q4 budget: 100" | sudo tee /srv/finance/budget.txt > /dev/null
    echo "2026-10-01 audit started" | sudo tee /srv/finance/audit.log > /dev/null
    sudo setfacl -m u:bob:rw /srv/finance/budget.txt
    sudo -u bob cat /srv/finance/budget.txt
    sudo chmod o-x /srv/finance
    sudo chmod 644 /srv/finance/budget.txt
    sudo chattr +a /srv/finance/audit.log
    ```

    ::: explain
    **What just happened:** `setfacl -m u:bob:rw` adds an ACL entry giving bob read and write on the budget, and the `cat` proves he can read it. Then: `chmod o-x` removes "execute" for others on the directory, `chmod 644` is a routine-looking permission reset on the budget, and `chattr +a` makes the audit log append-only.
    :::

2. **Symptom 1: bob cannot reach any file.**

    ```bash
    sudo -u bob cat /srv/finance/budget.txt
    sudo -u bob ls -l /srv/finance
    ```

    ```{.output}
    cat: /srv/finance/budget.txt: Permission denied
    ls: cannot access '/srv/finance/audit.log': Permission denied
    ls: cannot access '/srv/finance/budget.txt': Permission denied
    total 0
    -????????? ? ? ? ?            ? audit.log
    -????????? ? ? ? ?            ? budget.txt
    ```

3. **Investigate.**

    ```bash
    namei -l /srv/finance/budget.txt
    ```

    ```{.output}
    f: /srv/finance/budget.txt
    drwxr-xr-x root root /
    drwxr-xr-x root root srv
    drwxr-xr-- root root finance
    -rw-r--r-- root root budget.txt
    ```

    ::: explain
    **What just happened:** On a **directory**, `r` lets you list names, `w` lets you create and delete entries, and `x` lets you *enter* it and reach anything inside. `finance` is `drwxr-xr--`: others (bob) have `r` but not `x`, so `ls` can read the names but not look at the files (hence the `?` marks), and `cat` cannot reach the file at all. `namei -l` shows each directory on the path so you can spot the one that blocks.
    :::

4. **Fix 1.** Give others execute on the directory again, then test.

    ```bash
    sudo chmod o+x /srv/finance
    sudo -u bob cat /srv/finance/budget.txt
    ```

5. **Symptom 2: bob can read but no longer edit the budget, even though his ACL says `rw`.**

    ```bash
    sudo -u bob sh -c 'echo "Q4 budget: 120" >> /srv/finance/budget.txt'
    ls -l /srv/finance/budget.txt
    getfacl /srv/finance/budget.txt
    ```

    ```{.output}
    sh: 1: cannot create /srv/finance/budget.txt: Permission denied
    -rw-r--r--+ 1 root root 15 Oct 10 15:01 /srv/finance/budget.txt
    # file: srv/finance/budget.txt
    # owner: root
    # group: root
    user::rw-
    user:bob:rw-                    #effective:r--
    group::r--
    mask::r--
    other::r--
    ```

    ::: explain
    **What just happened:** The `+` after the mode means the file has an ACL. `getfacl` shows bob's entry is `rw-` but **effective** `r--`. The **mask** is the maximum permission any named user, named group, or the owning group can get; it is `r--`. On a file with an ACL, the "group" bits shown by `ls -l` *are* the mask, so `chmod 644` (group `r--`) silently lowered the mask and took bob's write access away.
    :::

6. **Fix 2.** Raise the mask (or use `chmod g+w`, which does the same thing here).

    ```bash
    sudo setfacl -m m::rw /srv/finance/budget.txt
    getfacl /srv/finance/budget.txt | grep -E "bob|mask"
    sudo -u bob sh -c 'echo "Q4 budget: 120" >> /srv/finance/budget.txt' && echo "bob can write"
    ```

7. **Symptom 3: log rotation fails, even for root.**

    ```bash
    sudo sh -c 'echo "2026-10-02 new entry" >> /srv/finance/audit.log' && echo "append works"
    sudo sh -c ': > /srv/finance/audit.log'
    sudo rm /srv/finance/audit.log
    lsattr /srv/finance/audit.log
    ```

    ```{.output}
    append works
    sh: 1: cannot create /srv/finance/audit.log: Operation not permitted
    rm: cannot remove '/srv/finance/audit.log': Operation not permitted
    -----a--------e------- /srv/finance/audit.log
    ```

    ::: explain
    **What just happened:** Appending works, but truncating or deleting fails with "Operation not permitted" even as root. `lsattr` shows the `a` (append-only) **attribute**: the file can only grow. It is a deliberate protection for audit logs, but it breaks log rotation. The immutable attribute `i` is even stricter (no changes at all). Only root can change these attributes, with `chattr`.
    :::

8. **Fix 3.** If rotation is legitimately needed, remove the attribute, rotate, and decide whether to set it again.

    ```bash
    sudo chattr -a /srv/finance/audit.log
    lsattr /srv/finance/audit.log
    ```

9. **Prevent.** Prefer ACLs plus `setfacl -m d:u:bob:rw` (a *default* ACL on the directory, inherited by new files) over repeated `chmod` on files with ACLs, remember that `chmod` on the group bits changes the mask, and document every `chattr` use.

::: checkpoint
**Checkpoint:** bob can read and append to `budget.txt`, `getfacl` shows `mask::rw-`, and `lsattr /srv/finance/audit.log` no longer shows `a`.
:::

#### Task 6: Scenario 5: "carol can't log in" (account access)

Many different account settings produce "I can't log in". You will create four on purpose, using SSH to `localhost` on ubuntu-lab, and identify each from its evidence.

1. **Confirm carol works first.** Answer `yes` to the host key question the first time, then type carol's password (`Lab54-Pass!`).

    ```bash
    ssh carol@localhost whoami
    ```

    ```{.output}
    carol@localhost's password:
    carol
    ```

2. **Break 1: locked password.**

    ```bash
    sudo passwd -l carol
    ssh carol@localhost whoami
    ```

    ```{.output}
    passwd: password changed.
    carol@localhost's password:
    Permission denied, please try again.
    ```

    Press `Ctrl+C`, then investigate:

    ```bash
    sudo passwd -S carol
    sudo grep carol /etc/shadow | cut -d: -f1,2 | cut -c1-20
    sudo journalctl -u ssh -n 5 --no-pager | grep carol
    ```

    ```{.output}
    carol L 2026-10-10 0 99999 7 -1
    carol:!$y$j9T$xQ
    sshd[3302]: Failed password for carol from 127.0.0.1 port 49826 ssh2
    ```

    ::: explain
    **What just happened:** `passwd -S` prints the status: `L` = locked (`P` = usable password, `NP` = no password), followed by the last change date and aging fields. Locking puts a `!` in front of the password hash in `/etc/shadow`, so no typed password can ever match. The log just says "Failed password", which looks like a typo; only `passwd -S` reveals the lock. Note: a locked *password* does not block SSH *key* logins. To block an account completely, also expire it (`chage -E 0`) or set a `nologin` shell.
    :::

    Fix: `sudo passwd -u carol` and confirm with `sudo passwd -S carol` (`P`).

3. **Break 2: expired account.**

    ```bash
    sudo chage -E 0 carol
    ssh carol@localhost whoami
    ```

    ```{.output}
    carol@localhost's password:
    Your account has expired; please contact your system administrator.
    Connection closed by 127.0.0.1 port 22
    ```

    Investigate:

    ```bash
    sudo chage -l carol
    sudo journalctl -u ssh -n 5 --no-pager | grep -i -E "expired|denied"
    ```

    ```{.output}
    Last password change                                    : Oct 10, 2026
    Password expires                                        : never
    Password inactive                                       : never
    Account expires                                         : Jan 01, 1970
    Minimum number of days between password change          : 0
    Maximum number of days between password change          : 99999
    Number of days of warning before password expires       : 7
    sshd[3330]: pam_unix(sshd:account): account carol has expired (account expired)
    sshd[3330]: fatal: Access denied for user carol by PAM account configuration [preauth]
    ```

    ::: explain
    **What just happened:** The password was correct (authentication passed), but the PAM **account** check failed. `chage -l` lists password aging and account expiry; `-E 0` set the account expiry to day 0 (January 1, 1970), so it is expired. Contractors' accounts are often set to expire this way. Do not confuse *account* expiry with *password* expiry: an expired password forces a password change at login instead.
    :::

    Fix: `sudo chage -E -1 carol` (`-1` means never expires), then check `sudo chage -l carol | grep "Account expires"`.

4. **Break 3: no login shell.**

    ```bash
    sudo usermod -s /usr/sbin/nologin carol
    ssh carol@localhost
    ```

    ```{.output}
    carol@localhost's password:
    This account is currently not available.
    Connection to localhost closed.
    ```

    Investigate and fix:

    ```bash
    getent passwd carol
    sudo usermod -s /bin/bash carol
    ```

    ::: explain
    **What just happened:** The last field of the `passwd` entry is the login shell. `/usr/sbin/nologin` prints "This account is currently not available." and exits, which is correct for service accounts (`www-data`, `mysql`) and wrong for people. `/bin/false` does the same silently.
    :::

5. **Break 4: too many failed logins (faillock, on rocky-lab).** **pam_faillock** locks an account temporarily after repeated failed logins, a defense against password guessing. Rocky enables it through `authselect`.

    ```bash
    # on rocky-lab
    sudo authselect current
    sudo authselect enable-feature with-faillock
    grep -E "^#? ?(deny|unlock_time) =" /etc/security/faillock.conf
    sudo useradd -m carol
    echo 'carol:Lab54-Pass!' | sudo chpasswd
    ```

    ```{.output}
    Profile ID: sssd
    Enabled features: None
    # deny = 3
    # unlock_time = 600
    ```

    ::: explain
    **What just happened:** `authselect` manages the PAM files on RHEL-family systems; `enable-feature with-faillock` adds `pam_faillock` to them. The commented defaults in `/etc/security/faillock.conf` apply: lock after 3 failures (`deny`) for 600 seconds (`unlock_time`). If `authselect current` says no configuration is present, skip this step; your VM's PAM is managed differently.
    :::

    From ubuntu-lab, log in as carol to rocky-lab and type a **wrong** password three times, then try once more with the **right** password:

    ```bash
    ssh carol@rocky-lab
    ssh carol@rocky-lab
    ```

    ```{.output}
    carol@rocky-lab's password:
    Permission denied, please try again.
    carol@rocky-lab's password:
    Permission denied, please try again.
    carol@rocky-lab's password:
    carol@rocky-lab: Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
    carol@rocky-lab's password:
    Permission denied, please try again.
    ```

    Investigate on rocky-lab:

    ```bash
    # on rocky-lab
    sudo faillock --user carol
    sudo grep carol /var/log/secure | tail -n 3
    ```

    ```{.output}
    carol:
    When                Type  Source                                           Valid
    2026-10-10 15:31:02 RHOST 192.168.100.10                                       V
    2026-10-10 15:31:06 RHOST 192.168.100.10                                       V
    2026-10-10 15:31:09 RHOST 192.168.100.10                                       V
    sshd[4021]: pam_faillock(sshd:auth): Consecutive login failures for user carol account temporarily locked
    sshd[4021]: Failed password for carol from 192.168.100.10 port 50122 ssh2
    ```

    ::: explain
    **What just happened:** `faillock --user carol` lists the recorded failures and where they came from. With three valid (`V`) failures inside the interval, the account is locked, so even the correct password is rejected. The log line "account temporarily locked" is the giveaway; without it, this looks exactly like a wrong password. Many failures from one source address is also a sign of a brute-force attack (Lab 5.5 covers that).
    :::

    Fix: `sudo faillock --user carol --reset` on rocky-lab, then `ssh carol@rocky-lab whoami` from ubuntu-lab works.

6. **Prevent.** When someone cannot log in, check in this order: `passwd -S` (locked?), `chage -l` (expired?), `getent passwd` (shell?), `faillock --user` (locked out?), and the auth log for the exact message. Document account expiry dates and lockout policies so the help desk knows them.

::: checkpoint
**Checkpoint:** carol can log in to ubuntu-lab (`ssh carol@localhost whoami`) and to rocky-lab after `faillock --reset`, and you can name the command that reveals each of the four causes.
:::

#### Task 7: Scenario 6: "Permission denied (publickey)" (remote access issues)

1. **Set up key login for carol.** Create a key pair as student and install the public key in carol's account (enter carol's password once).

    ```bash
    ssh-keygen -t ed25519 -N "" -f ~/.ssh/lab54_key
    ssh-copy-id -i ~/.ssh/lab54_key.pub carol@localhost
    ssh -i ~/.ssh/lab54_key -o IdentitiesOnly=yes -o BatchMode=yes carol@localhost whoami
    ```

    ```{.output}
    carol
    ```

    ::: explain
    **What just happened:** `ssh-keygen -t ed25519 -N ""` makes a key pair with no passphrase (fine for a lab), `ssh-copy-id` appends the public key to `/home/carol/.ssh/authorized_keys`, and the test uses only that key (`IdentitiesOnly=yes`) and never prompts for a password (`BatchMode=yes`), so it proves key login works.
    :::

2. **Break 1: wrong permissions.** Someone "helpfully" makes carol's `authorized_keys` writable by everyone.

    ```bash
    sudo chmod 666 /home/carol/.ssh/authorized_keys
    ssh -i ~/.ssh/lab54_key -o IdentitiesOnly=yes -o BatchMode=yes carol@localhost whoami
    ```

    ```{.output}
    carol@localhost: Permission denied (publickey,password).
    ```

3. **Investigate both sides.** The client's verbose output shows what was tried; the server's log shows why it was refused.

    ```bash
    ssh -v -i ~/.ssh/lab54_key -o IdentitiesOnly=yes -o BatchMode=yes carol@localhost true 2>&1 | \
        grep -E "Offering|Authentications that can continue" | head -n 3
    sudo journalctl -u ssh -n 10 --no-pager | grep -i -E "refused|bad ownership"
    ls -la /home/carol/.ssh/
    ```

    ```{.output}
    debug1: Authentications that can continue: publickey,password
    debug1: Offering public key: /home/student/.ssh/lab54_key ED25519 SHA256:3bX... explicit
    debug1: Authentications that can continue: publickey,password
    sshd[3411]: Authentication refused: bad ownership or modes for file /home/carol/.ssh/authorized_keys
    drwx------ 2 carol carol 4096 Oct 10 15:40 .
    -rw-rw-rw- 1 carol carol   99 Oct 10 15:40 authorized_keys
    ```

    ::: explain
    **What just happened:** The client offered the key and the server simply moved on ("Authentications that can continue" again). The server log gives the reason: sshd's `StrictModes yes` (the default) refuses to use an `authorized_keys` file, `.ssh` directory, or home directory that other users could write to, because anyone could add their own key. The required modes: home directory not group/world-writable, `~/.ssh` `700`, `authorized_keys` `600`, all owned by the user.
    :::

4. **Fix and verify.**

    ```bash
    sudo chmod 600 /home/carol/.ssh/authorized_keys
    ssh -i ~/.ssh/lab54_key -o IdentitiesOnly=yes -o BatchMode=yes carol@localhost whoami
    ```

5. **Break 2: AllowUsers.** A hardening change restricts SSH to the admin account. Keep your current session open while you do this.

    ::: warning
    A mistake in `AllowUsers` can lock you out of SSH. Keep this session open, include `student` in the list, and test with `sudo sshd -t` before restarting.
    :::

    ```bash
    echo "AllowUsers student" | sudo tee /etc/ssh/sshd_config.d/50-lab-allowusers.conf
    sudo sshd -t && sudo systemctl restart ssh
    ssh -i ~/.ssh/lab54_key -o IdentitiesOnly=yes -o BatchMode=yes carol@localhost whoami
    ```

    ```{.output}
    carol@localhost: Permission denied (publickey,password).
    ```

6. **Investigate.**

    ```bash
    sudo journalctl -u ssh -n 10 --no-pager | grep -i "not allowed"
    sudo sshd -T | grep -i -E "^allowusers|^allowgroups|^denyusers|^denygroups"
    ```

    ```{.output}
    sshd[3502]: User carol from 127.0.0.1 not allowed because not listed in AllowUsers
    allowusers student
    ```

    ::: explain
    **What just happened:** The log names the exact rule. `sshd -T` prints the *effective* configuration after reading `sshd_config` and every file in `sshd_config.d/`, which is the quickest way to find which file set what. `AllowUsers`, `AllowGroups`, `DenyUsers`, and `DenyGroups` are checked before any password or key, so the user gets the same generic "Permission denied" either way.
    :::

7. **Fix.** Add carol (or better, use a group such as `AllowGroups sshusers` and add people to the group), test the syntax, and restart.

    ```bash
    echo "AllowUsers student carol" | sudo tee /etc/ssh/sshd_config.d/50-lab-allowusers.conf
    sudo sshd -t && sudo systemctl restart ssh
    ssh -i ~/.ssh/lab54_key -o IdentitiesOnly=yes -o BatchMode=yes carol@localhost whoami
    ```

8. **Other remote access problems and their tell-tale messages:**

    | Message | Cause | Fix |
    |---|---|---|
    | `Connection refused` / `timed out` | sshd down, firewall, network (Lab 5.3) | `ss -tlnp`, firewall rules |
    | `REMOTE HOST IDENTIFICATION HAS CHANGED!` | Server reinstalled or a man-in-the-middle | Verify the new key out of band, then `ssh-keygen -R host` |
    | `Permission denied (publickey)` only | `PasswordAuthentication no` and no valid key | Install the key, check modes |
    | Root cannot log in | `PermitRootLogin prohibit-password` or `no` | Log in as a user and use `sudo` |
    | `no matching cipher` / `key exchange` | Algorithm mismatch (Task 12) | Update the old client or device |

9. **Prevent.** Always run `sudo sshd -t` before restarting sshd, keep a second session open while changing SSH or PAM, manage access with groups, and check modes with `ls -la ~/.ssh` when keys stop working.

::: checkpoint
**Checkpoint:** Key login for carol works again, and you saw both "bad ownership or modes" and "not listed in AllowUsers" in the sshd log.

#### Task 8: Scenario 7: "Are we patched?" (unpatched vulnerable systems)

An unpatched system is the most common way attackers get in. The symptoms are quiet: security updates waiting, automatic updates switched off, packages held back, or updates installed but the old vulnerable code still running because nothing was restarted.

1. **Check what is pending on ubuntu-lab.**

    ```bash
    sudo apt update
    apt list --upgradable 2>/dev/null | head -n 5
    apt list --upgradable 2>/dev/null | grep -c -- -security
    pro security-status | head -n 12
    ```

    ```{.output}
    Listing...
    libssl3t64/noble-updates,noble-security 3.0.13-0ubuntu3.6 amd64 [upgradable from: 3.0.13-0ubuntu3.4]
    openssl/noble-updates,noble-security 3.0.13-0ubuntu3.6 amd64 [upgradable from: 3.0.13-0ubuntu3.4]
    ...
    7
    ```

    ::: explain
    **What just happened:** `apt list --upgradable` lists packages with a newer version available; the part after `/` shows which pockets offer it, and `-security` means it fixes a vulnerability. `pro security-status` (the Ubuntu Pro client, installed by default) summarizes how many installed packages get security coverage. Your counts will differ; a freshly updated VM may show `0`.
    :::

2. **Break 1: automatic updates switched off.** Ubuntu installs security updates automatically with `unattended-upgrades`. Simulate someone disabling it.

    ```bash
    cat /etc/apt/apt.conf.d/20auto-upgrades
    sudo cp /etc/apt/apt.conf.d/20auto-upgrades ~/labs/5.4/20auto-upgrades.bak
    sudo sed -i 's/Unattended-Upgrade "1"/Unattended-Upgrade "0"/' /etc/apt/apt.conf.d/20auto-upgrades
    ```

    ```{.output}
    APT::Periodic::Update-Package-Lists "1";
    APT::Periodic::Unattended-Upgrade "1";
    ```

3. **Investigate** the way you would on an unfamiliar server.

    ```bash
    apt-config dump | grep -E "Periodic::(Update-Package-Lists|Unattended-Upgrade)"
    systemctl list-timers 'apt-daily*' --no-pager
    sudo tail -n 3 /var/log/unattended-upgrades/unattended-upgrades.log
    grep " upgrade " /var/log/dpkg.log | tail -n 3
    ```

    ```{.output}
    APT::Periodic::Update-Package-Lists "1";
    APT::Periodic::Unattended-Upgrade "0";
    NEXT                        LEFT     LAST                        PASSED  UNIT
    Sun 2026-10-11 06:21:44 UTC 14h left Sat 2026-10-10 06:40:01 UTC 9h ago  apt-daily-upgrade.timer
    ...
    ```

    ::: explain
    **What just happened:** `apt-config dump` shows the effective APT settings from every file in `/etc/apt/apt.conf.d/`. `Unattended-Upgrade "0"` means the daily job runs but installs nothing. The timers still fire, so a quick glance at `systemctl` looks healthy; the log in `/var/log/unattended-upgrades/` and `/var/log/dpkg.log` show when packages were last actually upgraded.
    :::

4. **Fix and test** with a dry run (shows what would be installed, changes nothing).

    ```bash
    sudo cp ~/labs/5.4/20auto-upgrades.bak /etc/apt/apt.conf.d/20auto-upgrades
    apt-config dump | grep "Periodic::Unattended-Upgrade"
    sudo unattended-upgrade --dry-run -v 2>&1 | tail -n 5
    ```

5. **Break 2: a held package.** Holding stops a package from being upgraded, often done "temporarily" and forgotten.

    ```bash
    sudo apt-mark hold openssh-server
    apt-mark showhold
    sudo apt-get -s upgrade | grep -A2 "kept back"
    ```

    ```{.output}
    openssh-server set on hold.
    openssh-server
    The following packages have been kept back:
      openssh-server
    ```

    ::: explain
    **What just happened:** `apt-mark showhold` lists held packages. `apt-get -s upgrade` is a simulation (`-s` changes nothing). If an update exists for the held package, it appears under "kept back"; if your VM is fully updated, nothing is listed, but the hold is still there waiting to block the next security fix. unattended-upgrades also skips held packages. On Rocky the equivalent is the `versionlock` plugin (`dnf versionlock list`) or `exclude=` lines in `/etc/dnf/dnf.conf`.
    :::

    Fix: `sudo apt-mark unhold openssh-server`.

6. **Updated but still vulnerable: restarts.** A library update does not fix programs that already loaded the old library, and a kernel update needs a reboot.

    ```bash
    ls /var/run/reboot-required* 2>/dev/null && cat /var/run/reboot-required.pkgs
    uname -r; ls /boot/vmlinuz-*
    sudo needrestart -r l
    ```

    ::: explain
    **What just happened:** Ubuntu creates `/var/run/reboot-required` (and lists the reason in `.pkgs`) when an update needs a reboot. If the newest `vmlinuz` in `/boot` is newer than `uname -r`, you are running an old kernel. `needrestart -r l` (list mode) shows services still using outdated libraries and whether the kernel is outdated.
    :::

7. **Check rocky-lab the RHEL way.**

    ```bash
    # on rocky-lab
    sudo dnf install -y dnf-plugins-core
    sudo dnf updateinfo summary
    sudo dnf updateinfo list --security | head -n 5
    sudo dnf needs-restarting -r; echo "exit: $?"
    rpm -q --changelog openssl | grep -m 3 CVE
    ```

    ```{.output}
    Updates Information Summary: available
        5 Security notice(s)
            2 Important Security notice(s)
            3 Moderate Security notice(s)
    RLSA-2026:1234 Important/Sec.  openssl-1:3.2.2-6.el9_5.1.x86_64
    ...
    Core libraries or services have been updated since boot-up:
      * kernel
    Reboot is required to fully utilize these updates.
    exit: 1
    ```

    ::: explain
    **What just happened:** `dnf updateinfo` reads the security advisories (RLSA for Rocky, RHSA for Red Hat) published with updates. `sudo dnf upgrade --security` would install only security updates. `dnf needs-restarting -r` exits with `1` and explains when a reboot is needed (`0` means not needed). `rpm -q --changelog` shows which CVEs a package version fixed, which answers "are we patched against CVE-X?".
    :::

8. **Prevent.** Keep automatic security updates on (Ubuntu `unattended-upgrades`, Rocky `dnf-automatic`), review holds monthly, schedule reboots after kernel updates, and track patch status in monitoring.

::: checkpoint
**Checkpoint:** `apt-config dump | grep Unattended-Upgrade` shows `"1"`, `apt-mark showhold` prints nothing, and you know how to list security updates on both distributions.
:::
