## Lab 5.4: Troubleshoot Security Issues {#lab-5-4}

::: labinfo
**Objective:** 5.4 Given a scenario, analyze and troubleshoot security issues on a Linux system.\
**Domain:** 5.0 Troubleshooting (22% of the exam)\
**Time:** about 3.5 hours\
**VM:** rocky-lab (SELinux, faillock, repositories) and ubuntu-lab (everything else)\
**Snapshot first:** Yes. Take a snapshot of both VMs now. This lab changes SSH, PAM, firewall, and repository settings, and a mistake there can lock you out.
:::

Security problems show up in two ways: something legitimate is blocked ("403 Forbidden", "Permission denied (publickey)", "certificate has expired") or something dangerous is allowed (a database open to the network, TLS 1.0 still enabled, months of missing patches). In this break-and-fix lab you create both kinds, find the evidence in the logs, and fix them the right way, not by turning security off.

### What you'll practice

- SELinux issues: file **context** (`ls -Z`, `restorecon`), **booleans** (`getsebool`, `setsebool -P`), and **policy** (port labels with `semanage port`); reading AVC denials with `ausearch` and `sealert`
- File and directory permission issues: missing execute on directories, **ACL** mask problems (`getfacl`, `setfacl`), and **attributes** (`lsattr`, `chattr`)
- Account access: locked, expired, and `nologin` accounts (`passwd -S`, `chage -l`, `usermod`), and `faillock` lockouts
- Remote access issues: `AllowUsers`, wrong `~/.ssh` permissions, reading `ssh -v` and sshd logs
- Unpatched vulnerable systems: pending security updates, held packages, unattended-upgrades, `dnf updateinfo`, reboot-required checks
- Exposed or misconfigured services: a database listening on all interfaces, found with `ss` and `nmap`
- Certificate issues: untrusted, missing intermediate, hostname mismatch, and expired certificates (`openssl s_client`, `openssl x509`, `curl -v`)
- Misconfigured package repository: bad URLs and wrong signing keys (`NO_PUBKEY`) with apt and dnf
- Use of obsolete or insecure protocols and ciphers, and cipher negotiation issues (TLS and SSH, `nmap ssl-enum-ciphers`, `update-crypto-policies`)

### How it works

**The same method, with a security twist.** You still identify symptoms, gather data, form a hypothesis, test, fix, verify, and document (Lab 5.2). Security adds one rule: **the fix must not weaken security**. "Disable SELinux", "chmod 777", "PermitRootLogin yes", and "skip certificate checks" make the symptom go away while creating a bigger problem. The right fix corrects the label, permission, key, or configuration that was actually wrong.

**Where security evidence lives.**

| What | Ubuntu | Rocky |
|---|---|---|
| Logins, sudo, SSH | `/var/log/auth.log`, `journalctl -u ssh` | `/var/log/secure`, `journalctl -u sshd` |
| SELinux / AppArmor denials | `journalctl -k | grep apparmor` | `/var/log/audit/audit.log` (`ausearch -m avc`) |
| Web server errors | `/var/log/nginx/error.log` | `/var/log/httpd/error_log` |
| Package updates | `/var/log/apt/history.log`, `/var/log/unattended-upgrades/` | `dnf history` |

**SELinux in one page.** SELinux (Security-Enhanced Linux, enforcing by default on Rocky) labels every process and file with a **context** like `system_u:system_r:httpd_t:s0`. The third part is the **type**. The **policy** is a large set of rules saying which process types may do what to which object types: for example `httpd_t` may read files of type `httpd_sys_content_t` and bind to ports of type `http_port_t`. Anything not allowed is denied and logged as an **AVC** (access vector cache) denial, *even for root and even if normal file permissions allow it*. **Booleans** are on/off switches built into the policy for common optional behavior (for example `httpd_can_network_connect`). So an SELinux problem is always one of three things:

```{.diagram}
  denied!  ->  is the FILE/PORT labeled wrong?    -> restorecon / semanage fcontext
           ->  is an optional feature switched off? -> setsebool -P <boolean> on
           ->  is it truly not in the policy?       -> semanage port, or (last resort)
                                                       audit2allow -M local module
```

Ubuntu uses **AppArmor** instead, which confines programs by file path rather than labels. Its denials appear in the kernel log as `apparmor="DENIED"`; `sudo aa-status` lists confined programs.

**Permissions are layered.** Access must pass *every* layer: directory execute permission on every parent directory, the file's mode bits, any **ACL** (access control list) entries limited by the ACL **mask**, file **attributes** such as immutable (`i`) or append-only (`a`), and finally SELinux or AppArmor. Check them in that order.

**TLS certificates in one paragraph.** A server certificate binds a name (in the Subject Alternative Name, **SAN**) to a public key, is valid between two dates, and is signed by a CA (certificate authority), usually through an **intermediate** CA. A client trusts it only if it can build a chain from the server certificate, through intermediates *the server sends*, up to a root CA in its own trust store, and the name it connected to is in the SAN, and today's date is within the validity period.

#### Task 2: Scenario 1: "403 Forbidden" after moving a file (SELinux context)

1. **Break it.** On rocky-lab, create a page in your home directory and *move* it into the web root, as many admins do.

    ```bash
    # on rocky-lab
    echo "<h1>Quarterly report</h1>" > ~/report.html
    sudo mv ~/report.html /var/www/html/
    ```

2. **Symptom.**

    ```bash
    # on rocky-lab
    curl -s -o /dev/null -w '%{http_code}\n' http://localhost/report.html
    ```

    ```{.output}
    403
    ```

3. **Investigate the normal layers first:** file permissions and the web server's own log.

    ```bash
    # on rocky-lab
    ls -l /var/www/html/
    sudo tail -n 1 /var/log/httpd/error_log
    ```

    ```{.output}
    -rw-r--r--. 1 root    root    21 Oct 10 14:02 index.html
    -rw-rw-r--. 1 student student 26 Oct 10 14:05 report.html
    [core:error] [pid 2345:tid 2401] (13)Permission denied: [client ::1:54322] AH00132: file permissions deny server access: /var/www/html/report.html
    ```

    ::: explain
    **What just happened:** The mode bits allow everyone to read (`r--` for others), yet Apache reports "Permission denied". The `.` after the permissions means the file has an SELinux context. When normal permissions look fine but access is denied, suspect SELinux.
    :::

4. **Investigate SELinux.** Compare the labels and look for AVC denials.

    ```bash
    # on rocky-lab
    ls -Z /var/www/html/
    sudo ausearch -m avc -ts recent
    ```

    ```{.output}
    system_u:object_r:httpd_sys_content_t:s0 index.html
    unconfined_u:object_r:user_home_t:s0 report.html
    ----
    time->Sat Oct 10 14:05:31 2026
    type=AVC msg=audit(1791641131.512:412): avc:  denied  { read } for  pid=2345 comm="httpd" name="report.html" dev="dm-0" ino=17112 scontext=system_u:system_r:httpd_t:s0 tcontext=unconfined_u:object_r:user_home_t:s0 tclass=file permissive=0
    ```

    ::: explain
    **What just happened:** `ls -Z` shows contexts: `index.html` has the web content type `httpd_sys_content_t`, but `report.html` kept `user_home_t` from your home directory, because `mv` keeps a file's label (while `cp` creates a new file that gets the destination directory's label). `ausearch -m avc -ts recent` searches the audit log for AVC messages from the last 10 minutes. Read it as: process `httpd` with context `scontext` (`httpd_t`) was denied `read` on a `file` with context `tcontext` (`user_home_t`). `permissive=0` means it was really blocked.
    :::

5. **Test the hypothesis** with the plain-English explanation and the expected label.

    ```bash
    # on rocky-lab
    sudo sealert -a /var/log/audit/audit.log | grep -A6 "SELinux is preventing" | head -n 8
    matchpathcon /var/www/html/report.html
    ```

    ```{.output}
    SELinux is preventing /usr/sbin/httpd from read access on the file report.html.

    *****  Plugin restorecon (99.5 confidence) suggests   ************************

    If you want to fix the label.
    /var/www/html/report.html default label should be httpd_sys_content_t.
    Then you can run restorecon.
    /var/www/html/report.html	system_u:object_r:httpd_sys_content_t:s0
    ```

6. **Root cause.** Wrong SELinux file context (`user_home_t` instead of `httpd_sys_content_t`).

7. **Fix.** Reset the label to what the policy says it should be.

    ```bash
    # on rocky-lab
    sudo restorecon -v /var/www/html/report.html
    ```

    ```{.output}
    Relabeled /var/www/html/report.html from unconfined_u:object_r:user_home_t:s0 to unconfined_u:object_r:httpd_sys_content_t:s0
    ```

    ::: explain
    **What just happened:** `restorecon` sets files back to the default context defined by the policy's file-context rules (`-v` shows what changed, `-R` would recurse into directories). If you serve content from a non-standard directory such as `/srv/site`, first teach the policy the right label with `sudo semanage fcontext -a -t httpd_sys_content_t "/srv/site(/.*)?"`, then run `sudo restorecon -Rv /srv/site`. Using `chcon` also changes a label, but only until the next relabel.
    :::

8. **Verify.** The `curl` from step 2 now prints `200`.

9. **Prevent.** Use `cp` (or `mv` followed by `restorecon`) when placing web content, and never "fix" SELinux with `setenforce 0`. Switching to permissive mode is only acceptable for a few seconds as a *test* to confirm SELinux is involved.

::: checkpoint
**Checkpoint:** `ls -Z /var/www/html/report.html` shows `httpd_sys_content_t` and the page returns `200`.
:::

#### Task 3: Scenario 2: "503 Service Unavailable" from a reverse proxy (SELinux boolean)

1. **Break it.** Start a small back-end application on port 5000 and make Apache a reverse proxy for it.

    ```bash
    # on rocky-lab
    mkdir -p /tmp/backend && echo "backend app says hi" > /tmp/backend/index.html
    python3 -m http.server 5000 --bind 127.0.0.1 --directory /tmp/backend > /dev/null 2>&1 &
    curl -s http://127.0.0.1:5000/
    cat <<'EOF' | sudo tee /etc/httpd/conf.d/lab-proxy.conf
    # Forward /app/ to the back-end application
    ProxyPass        "/app/" "http://127.0.0.1:5000/" retry=0
    ProxyPassReverse "/app/" "http://127.0.0.1:5000/"
    EOF
    sudo systemctl reload httpd
    ```

    ::: explain
    **What just happened:** The back end answers directly on `127.0.0.1:5000`. `ProxyPass` makes Apache forward requests for `/app/` to it, and `retry=0` makes Apache retry a failed back end immediately instead of waiting 60 seconds (handy while troubleshooting). A **heredoc** (`cat <<'EOF' | sudo tee file`) writes all lines up to `EOF` into the file.
    :::

2. **Symptom.**

    ```bash
    # on rocky-lab
    curl -s -o /dev/null -w '%{http_code}\n' http://localhost/app/
    sudo tail -n 2 /var/log/httpd/error_log
    ```

    ```{.output}
    503
    [proxy:error] [pid 2412:tid 2460] (13)Permission denied: AH00957: http: attempt to connect to 127.0.0.1:5000 (127.0.0.1:5000) failed
    [proxy_http:error] [pid 2412:tid 2460] [client ::1:41236] AH01114: HTTP: failed to make connection to backend: 127.0.0.1
    ```

3. **Investigate.** The back end works when you call it directly, and Apache gets "Permission denied" when *connecting*. Look for the AVC.

    ```bash
    # on rocky-lab
    sudo ausearch -m avc -ts recent | grep name_connect | tail -n 1
    sudo ausearch -m avc -ts recent | audit2why | tail -n 6
    ```

    ```{.output}
    type=AVC msg=audit(1791641402.218:431): avc:  denied  { name_connect } for  pid=2412 comm="httpd" dest=5000 scontext=system_u:system_r:httpd_t:s0 tcontext=system_u:object_r:commplex_main_port_t:s0 tclass=tcp_socket permissive=0

            Was caused by:
            One of the following booleans was set incorrectly.
            Description:
            Allow httpd to can network connect

            Allow access by executing:
            # setsebool -P httpd_can_network_connect 1
    ```

    ::: explain
    **What just happened:** `name_connect` on a `tcp_socket` means httpd tried to open an outgoing TCP connection to port 5000 (whose type here is `commplex_main_port_t`), and the policy does not allow that by default, so that a hacked web server cannot easily attack other services. `audit2why` reads AVC messages and explains why each was denied; here it names the boolean that controls this behavior.
    :::

4. **Look at the boolean.**

    ```bash
    # on rocky-lab
    getsebool httpd_can_network_connect
    sudo semanage boolean -l | grep -E "^httpd_can_network_connect "
    getsebool -a | grep -c httpd
    ```

    ```{.output}
    httpd_can_network_connect --> off
    httpd_can_network_connect      (off  ,  off)  Allow httpd to can network connect
    48
    ```

    ::: explain
    **What just happened:** `getsebool` shows the current value. `semanage boolean -l` shows the current and the default (saved) value plus a description. There are dozens of httpd booleans alone, such as `httpd_enable_homedirs` (serve `~/public_html`), `httpd_can_network_connect_db` (connect to databases), and `httpd_can_sendmail`.
    :::

5. **Root cause and fix.** The optional "web server may make network connections" feature is off. Turn it on **permanently** with `-P`.

    ```bash
    # on rocky-lab
    sudo setsebool -P httpd_can_network_connect on
    getsebool httpd_can_network_connect
    ```

    ::: explain
    **What just happened:** `setsebool` changes a boolean immediately; `-P` also writes it to the policy on disk so it survives a reboot (it takes a few seconds). Without `-P` the fix silently disappears at the next boot, a classic "it broke again after maintenance" problem.
    :::

6. **Verify.** `curl -s http://localhost/app/` prints `backend app says hi`.

7. **Prevent.** Enable only the booleans you need and document why. Before writing custom policy, always check whether a boolean already covers the case (`audit2why` or `sealert` will say so).

::: checkpoint
**Checkpoint:** `getsebool httpd_can_network_connect` shows `on` and `/app/` returns the back end's page.
:::

#### Task 4: Scenario 3: Apache will not start on a new port (SELinux policy)

1. **Break it.** Ask Apache to also listen on port 8090.

    ```bash
    # on rocky-lab
    echo "Listen 8090" | sudo tee /etc/httpd/conf.d/lab-port.conf
    sudo systemctl restart httpd
    ```

    ```{.output}
    Job for httpd.service failed because the control process exited with error code.
    See "systemctl status httpd.service" and "journalctl -xeu httpd.service" for details.
    ```

2. **Symptom and investigation.**

    ```bash
    # on rocky-lab
    sudo journalctl -u httpd -n 5 --no-pager
    sudo ausearch -m avc -ts recent | grep name_bind | tail -n 1
    sudo semanage port -l | grep -w 8090; echo "exit: $?"
    sudo semanage port -l | grep ^http_port_t
    ```

    ```{.output}
    httpd[2601]: (13)Permission denied: AH00072: make_sock: could not bind to address [::]:8090
    httpd[2601]: (13)Permission denied: AH00072: make_sock: could not bind to address 0.0.0.0:8090
    httpd[2601]: no listening sockets available, shutting down
    systemd[1]: httpd.service: Main process exited, code=exited, status=1/FAILURE
    type=AVC msg=audit(1791641620.004:447): avc:  denied  { name_bind } for  pid=2601 comm="httpd" src=8090 scontext=system_u:system_r:httpd_t:s0 tcontext=system_u:object_r:unreserved_port_t:s0 tclass=tcp_socket permissive=0
    exit: 1
    http_port_t                    tcp      80, 81, 443, 488, 8008, 8009, 8443, 9000
    ```

    ::: explain
    **What just happened:** Apache, running as root, still got "Permission denied" when binding (`name_bind`) to port 8090. SELinux labels ports too: 8090 has the generic `unreserved_port_t` type, and the policy only lets `httpd_t` bind to ports labeled `http_port_t`, which lists 80, 443, 8443 and a few others.
    :::

3. **Root cause.** The policy has no rule allowing the web server on this port, because the port is not labeled as a web port.

4. **Fix.** Add the port to the `http_port_t` type, then start Apache.

    ```bash
    # on rocky-lab
    sudo semanage port -a -t http_port_t -p tcp 8090
    sudo semanage port -l | grep ^http_port_t
    sudo systemctl restart httpd
    curl -s http://localhost:8090/
    ```

    ```{.output}
    http_port_t                    tcp      8090, 80, 81, 443, 488, 8008, 8009, 8443, 9000
    hello from rocky-lab
    ```

    ::: explain
    **What just happened:** `semanage port -a` (add) labels TCP port 8090 as `http_port_t`; the change is permanent. If a port already has another type, `-a` fails with "already defined" and you use `-m` (modify) instead. For remote clients you would also open the port in the firewall (`sudo firewall-cmd --permanent --add-port=8090/tcp`, `sudo firewall-cmd --reload`): SELinux and the firewall are separate layers.
    :::

5. **Last resort: a custom policy module.** When no label or boolean fits, you can turn denials into a small local policy module. Look at what it *would* allow before installing anything:

    ```bash
    # on rocky-lab
    sudo ausearch -m avc -ts today | audit2allow | head -n 8
    ```

    ::: explain
    **What just happened:** `audit2allow` turns AVC denials into `allow` rules. `audit2allow -M mymodule` would create `mymodule.pp`, which `sudo semodule -i mymodule.pp` installs. Review the rules carefully: blindly allowing every denial (for example letting `httpd_t` read `user_home_t`) can open real holes when the right fix was a label or boolean. In this lab, the right fixes already exist, so do not install a module.
    :::

6. **Prevent.** When you change a service's port or directories, update SELinux in the same change (`semanage port`, `semanage fcontext`), and check `sudo ausearch -m avc -ts recent` whenever a confined service fails mysteriously.

::: checkpoint
**Checkpoint:** `sudo semanage port -l | grep ^http_port_t` includes `8090`, and `curl http://localhost:8090/` returns the page.
:::

#### Task 5: Scenario 4: "Permission denied" on shared files (permissions, ACLs, attributes)

1. **Break it.** On ubuntu-lab, create a shared finance directory where `bob` should be able to read and edit the budget, then make three "small" changes that each break something.

    ```bash
    sudo mkdir -p /srv/finance
    echo "Q4 budget: 100" | sudo tee /srv/finance/budget.txt > /dev/null
    echo "2026-10-01 audit started" | sudo tee /srv/finance/audit.log > /dev/null
    sudo setfacl -m u:bob:rw /srv/finance/budget.txt
    sudo -u bob cat /srv/finance/budget.txt
    sudo chmod o-x /srv/finance
    sudo chmod 644 /srv/finance/budget.txt
    sudo chattr +a /srv/finance/audit.log
    ```

    ::: explain
    **What just happened:** `setfacl -m u:bob:rw` adds an ACL entry giving bob read and write on the budget, and the `cat` proves he can read it. Then: `chmod o-x` removes "execute" for others on the directory, `chmod 644` is a routine-looking permission reset on the budget, and `chattr +a` makes the audit log append-only.
    :::

2. **Symptom 1: bob cannot reach any file.**

    ```bash
    sudo -u bob cat /srv/finance/budget.txt
    sudo -u bob ls -l /srv/finance
    ```

    ```{.output}
    cat: /srv/finance/budget.txt: Permission denied
    ls: cannot access '/srv/finance/audit.log': Permission denied
    ls: cannot access '/srv/finance/budget.txt': Permission denied
    total 0
    -????????? ? ? ? ?            ? audit.log
    -????????? ? ? ? ?            ? budget.txt
    ```

3. **Investigate.**

    ```bash
    namei -l /srv/finance/budget.txt
    ```

    ```{.output}
    f: /srv/finance/budget.txt
    drwxr-xr-x root root /
    drwxr-xr-x root root srv
    drwxr-xr-- root root finance
    -rw-r--r-- root root budget.txt
    ```

    ::: explain
    **What just happened:** On a **directory**, `r` lets you list names, `w` lets you create and delete entries, and `x` lets you *enter* it and reach anything inside. `finance` is `drwxr-xr--`: others (bob) have `r` but not `x`, so `ls` can read the names but not look at the files (hence the `?` marks), and `cat` cannot reach the file at all. `namei -l` shows each directory on the path so you can spot the one that blocks.
    :::

4. **Fix 1.** Give others execute on the directory again, then test.

    ```bash
    sudo chmod o+x /srv/finance
    sudo -u bob cat /srv/finance/budget.txt
    ```

5. **Symptom 2: bob can read but no longer edit the budget, even though his ACL says `rw`.**

    ```bash
    sudo -u bob sh -c 'echo "Q4 budget: 120" >> /srv/finance/budget.txt'
    ls -l /srv/finance/budget.txt
    getfacl /srv/finance/budget.txt
    ```

    ```{.output}
    sh: 1: cannot create /srv/finance/budget.txt: Permission denied
    -rw-r--r--+ 1 root root 15 Oct 10 15:01 /srv/finance/budget.txt
    # file: srv/finance/budget.txt
    # owner: root
    # group: root
    user::rw-
    user:bob:rw-                    #effective:r--
    group::r--
    mask::r--
    other::r--
    ```

    ::: explain
    **What just happened:** The `+` after the mode means the file has an ACL. `getfacl` shows bob's entry is `rw-` but **effective** `r--`. The **mask** is the maximum permission any named user, named group, or the owning group can get; it is `r--`. On a file with an ACL, the "group" bits shown by `ls -l` *are* the mask, so `chmod 644` (group `r--`) silently lowered the mask and took bob's write access away.
    :::

6. **Fix 2.** Raise the mask (or use `chmod g+w`, which does the same thing here).

    ```bash
    sudo setfacl -m m::rw /srv/finance/budget.txt
    getfacl /srv/finance/budget.txt | grep -E "bob|mask"
    sudo -u bob sh -c 'echo "Q4 budget: 120" >> /srv/finance/budget.txt' && echo "bob can write"
    ```

7. **Symptom 3: log rotation fails, even for root.**

    ```bash
    sudo sh -c 'echo "2026-10-02 new entry" >> /srv/finance/audit.log' && echo "append works"
    sudo sh -c ': > /srv/finance/audit.log'
    sudo rm /srv/finance/audit.log
    lsattr /srv/finance/audit.log
    ```

    ```{.output}
    append works
    sh: 1: cannot create /srv/finance/audit.log: Operation not permitted
    rm: cannot remove '/srv/finance/audit.log': Operation not permitted
    -----a--------e------- /srv/finance/audit.log
    ```

    ::: explain
    **What just happened:** Appending works, but truncating or deleting fails with "Operation not permitted" even as root. `lsattr` shows the `a` (append-only) **attribute**: the file can only grow. It is a deliberate protection for audit logs, but it breaks log rotation. The immutable attribute `i` is even stricter (no changes at all). Only root can change these attributes, with `chattr`.
    :::

8. **Fix 3.** If rotation is legitimately needed, remove the attribute, rotate, and decide whether to set it again.

    ```bash
    sudo chattr -a /srv/finance/audit.log
    lsattr /srv/finance/audit.log
    ```

9. **Prevent.** Prefer ACLs plus `setfacl -m d:u:bob:rw` (a *default* ACL on the directory, inherited by new files) over repeated `chmod` on files with ACLs, remember that `chmod` on the group bits changes the mask, and document every `chattr` use.

::: checkpoint

#### Task 6: Scenario 5: "carol can't log in" (account access)

Many different account settings produce "I can't log in". You will create four on purpose, using SSH to `localhost` on ubuntu-lab, and identify each from its evidence.

1. **Confirm carol works first.** Answer `yes` to the host key question the first time, then type carol's password (`Lab54-Pass!`).

    ```bash

    ```

    ```{.output}
    carol@localhost's password:
    carol
    ```

2. **Break 1: locked password.**

    ```bash
    sudo passwd -l carol
    ssh carol@localhost whoami
    ```

    ```{.output}
    passwd: password changed.
    carol@localhost's password:
    Permission denied, please try again.
    ```

    Press `Ctrl+C`, then investigate:

2. **Break 1: wrong permissions.** Someone "helpfully" makes carol's `authorized_keys` writable by everyone.

    **What just happened:** The log names the exact rule. `sshd -T` prints the *effective* configuration after reading `sshd_config` and every file in `sshd_config.d/`, which is the quickest way to find which file set what. `AllowUsers`, `AllowGroups`, `DenyUsers`, and `DenyGroups` are checked before any password or key, so the user gets the same generic "Permission denied" either way.

#### Task 8: Scenario 7: "Are we patched?" (unpatched vulnerable systems)

An unpatched system is the most common way attackers get in. The symptoms are quiet: security updates waiting, automatic updates switched off, packages held back, or updates installed but the old vulnerable code still running because nothing was restarted.

1. **Check what is pending on ubuntu-lab.**

#### Task 9: Scenario 8: "Why is our cache server on the network?" (exposed or misconfigured service)

An **exposed service** is a program that listens on a network interface where it should not, usually because someone changed a setting "just to make it work". Redis, a fast in-memory database often used as a cache, is a classic example: by default it listens only on the local machine, but one edited line makes it reachable from anywhere. In this task you play the administrator who audits **their own server**. Everything happens on ubuntu-lab; you never connect to the service from another machine.

1. **Install Redis and look at the safe defaults.**

    ```bash
    sudo apt install -y redis-server
    systemctl is-active redis-server
    sudo grep -E "^(bind|protected-mode|port) " /etc/redis/redis.conf
    ```

    ```{.output}
    active
    bind 127.0.0.1 -::1
    protected-mode yes
    port 6379
    ```

    ::: explain
    **What just happened:** The package installs and starts the `redis-server` service. `bind 127.0.0.1 -::1` means "listen only on the IPv4 and IPv6 loopback addresses" (the `-` in front of `::1` means "skip it without an error if IPv6 is not available"). **Protected mode** is Redis's safety net: when it is `yes` and no password is set, Redis refuses clients that do not come from loopback. Port `6379` is the Redis default.
    :::

2. **Break it.** A developer wants an application on another host to use the cache, so they open Redis to every interface and switch the safety net off. First keep a copy of the original file.

    ```bash
    sudo cp /etc/redis/redis.conf ~/labs/5.4/redis.conf.bak
    sudo sed -i 's/^bind 127.0.0.1 -::1/bind 0.0.0.0/' /etc/redis/redis.conf
    sudo sed -i 's/^protected-mode yes/protected-mode no/' /etc/redis/redis.conf
    sudo systemctl restart redis-server
    ```

    ::: explain
    **What just happened:** `sed -i 's/old/new/'` edits the file in place, replacing the first match on each line. `bind 0.0.0.0` means "every IPv4 address this machine has", and `protected-mode no` removes the safety net. Redis also has no password by default, so now anyone who can reach port 6379 can read, change, or delete every key, and with some tricks even write files on the server. Real attackers scan the internet for exactly this.
    :::

3. **Symptom.** There is no error message. Exposed services are silent; you only find them by auditing. Start with the listening sockets.

    ```bash
    sudo ss -tlnp
    ```

    ```{.output}
    State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
    LISTEN 0      4096   127.0.0.53%lo:53         0.0.0.0:*     users:(("systemd-resolve",pid=612,fd=15))
    LISTEN 0      4096      127.0.0.54:53         0.0.0.0:*     users:(("systemd-resolve",pid=612,fd=17))
    LISTEN 0      511          0.0.0.0:80         0.0.0.0:*     users:(("nginx",pid=1820,fd=5))
    LISTEN 0      511          0.0.0.0:6379       0.0.0.0:*     users:(("redis-server",pid=5120,fd=6))
    LISTEN 0      4096               *:22               *:*     users:(("sshd",pid=1105,fd=3),("systemd",pid=1,fd=108))
    LISTEN 0      511             [::]:80            [::]:*     users:(("nginx",pid=1820,fd=5))
    ```

    ::: explain
    **What just happened:** `ss` lists sockets: `-t` TCP only, `-l` listening sockets only, `-n` numbers instead of names, `-p` the process that owns each socket (needs `sudo`). Read the **Local Address** column: `127.0.0.1` or `127.0.0.53` means "this machine only"; `0.0.0.0` (IPv4), `[::]` (IPv6), or `*` (both) means "every interface", which is reachable from the network unless a firewall blocks it. `0.0.0.0:6379` owned by `redis-server` is the finding. SSH and nginx are meant to be reachable; a cache database is not.
    :::

4. **See what a scanner sees.** **nmap** is a port scanner. Scan your own server, first through loopback and then through its network address. Replace `192.168.100.10` with ubuntu-lab's real IP (`ip -4 addr` shows it).

    ```bash
    sudo apt install -y nmap
    sudo nmap -sT -p- localhost
    sudo nmap -sT -p 22,80,6379 192.168.100.10
    ```

    ```{.output}
    Nmap scan report for localhost (127.0.0.1)
    Not shown: 65532 closed tcp ports (conn-refused)
    PORT     STATE SERVICE
    22/tcp   open  ssh
    80/tcp   open  http
    6379/tcp open  redis

    Nmap scan report for ubuntu-lab (192.168.100.10)
    PORT     STATE SERVICE
    22/tcp   open  ssh
    80/tcp   open  http
    6379/tcp open  redis
    ```

    ::: explain
    **What just happened:** `-sT` is a TCP connect scan (it completes the normal TCP handshake for each port and then closes it), and `-p-` means all 65,535 ports instead of nmap's default top 1,000. The first scan shows everything listening on loopback. The second scan targets the server's LAN address: Redis answers there too, which proves it is bound to the network interface, not just loopback. Only scan systems you own or are authorized to test. Note that a scan of your own IP travels over the loopback interface inside the kernel, so it shows what is *bound*, not what a host firewall would let through from outside; you check the firewall separately with `ufw status`.
    :::

5. **Investigate the configuration and the firewall.**

    ```bash
    sudo grep -E "^(bind|protected-mode|requirepass|port) " /etc/redis/redis.conf
    sudo ufw status verbose
    ```

    ```{.output}
    bind 0.0.0.0
    protected-mode no
    port 6379
    Status: inactive
    ```

6. **Root cause.** Three layers failed together: Redis binds to all interfaces (`bind 0.0.0.0`), the protected-mode safety net is off, there is no password (`requirepass` is missing), and no host firewall filters incoming connections (ufw is inactive, the Ubuntu default). Any one of these layers would have limited the damage.

7. **Fix the service.** Restore loopback-only listening, turn protected mode back on, and require a password. Open the file with `sudo nano /etc/redis/redis.conf` and make sure these three lines read exactly like this (`requirepass` is commented out near the "SECURITY" section; add the line if it is not there):

    ```text
    bind 127.0.0.1 -::1
    protected-mode yes
    requirepass S3cure-Lab54-Redis!
    ```

    Then restart and verify.

    ```bash
    sudo systemctl restart redis-server
    sudo ss -tlnp | grep 6379
    redis-cli ping
    REDISCLI_AUTH='S3cure-Lab54-Redis!' redis-cli ping
    ```

    ```{.output}
    LISTEN 0      511        127.0.0.1:6379       0.0.0.0:*     users:(("redis-server",pid=5301,fd=6))
    LISTEN 0      511            [::1]:6379          [::]:*     users:(("redis-server",pid=5301,fd=7))

    ::: explain
    **What just happened:** `ss` now shows Redis on `127.0.0.1` and `[::1]` only. `redis-cli ping` (run locally, on the server itself) is refused with `NOAUTH`, and the same command with the password in the `REDISCLI_AUTH` environment variable gets `PONG`, which proves the password is enforced. In production, prefer Redis **ACLs** (named users with limited commands, configured with `user` lines or an `aclfile`) over one shared password, and use a long random password. If an application on another host truly needs Redis, the safe design is to bind to one private interface, require authentication with TLS, and allow only that application server's IP in the firewall.
    :::

8. **Defense in depth: turn on the host firewall.** A host firewall would have blocked the exposure even with the bad Redis config. Allow SSH **first**, then set the default to deny incoming, then enable.

    ::: warning
    If you are connected to ubuntu-lab over SSH, run `sudo ufw allow OpenSSH` before `sudo ufw enable`, or you will cut off your own session. If that happens, use the VM console.
    :::

    ```bash
    sudo ufw allow OpenSSH
    sudo ufw default deny incoming
    sudo ufw default allow outgoing
    sudo ufw enable
    sudo ufw status verbose
    ```

    ```{.output}

    (be sure to update your rules accordingly)

    (be sure to update your rules accordingly)

    **What just happened:** `ufw allow OpenSSH` uses an application profile (port 22/tcp). `default deny incoming` drops every new incoming connection that no rule allows, and `default allow outgoing` lets the server start connections (updates, DNS). `ufw enable` activates the rules now and at every boot. #### Task 10: Scenario 9: "Your connection is not private" (certificate issues)

Certificate problems are some of the most common tickets an administrator sees. In this task you build a small private **PKI** (public key infrastructure: a root CA, an intermediate CA, and server certificates), serve the certificates with nginx on ubuntu-lab, and create and diagnose the four classic failures: untrusted, missing intermediate, hostname mismatch, and expired.

```{.diagram}
  Lab54 Root CA  (self-signed, in the client's trust store)
       |  signs
  Lab54 Intermediate CA  (the server must SEND this one)
       |  signs
  ubuntu-lab server certificate  (SAN: DNS:ubuntu-lab, valid from..to)
```

1. **Build the CA chain.** Install the tools (they are probably there from Task 1) and work in a dedicated directory.

    ```bash
    sudo apt install -y openssl nginx faketime
    mkdir -p ~/labs/5.4/pki && cd ~/labs/5.4/pki
    openssl req -x509 -newkey rsa:2048 -nodes -days 3650 \
        -keyout rootCA.key -out rootCA.crt -subj "/CN=Lab54 Root CA"
    ```

    ::: explain
    **What just happened:** `openssl req` creates certificate requests; with `-x509` it creates a **self-signed certificate** instead (the issuer and subject are the same). `-newkey rsa:2048` makes a new 2048-bit RSA private key, `-nodes` ("no DES") leaves the key unencrypted so services can read it without a passphrase (protect it with file permissions instead), `-days 3650` makes it valid for ten years, and `-subj` sets the name without prompting. OpenSSL's default config marks it as a CA (`CA:TRUE`). This is your **root CA**.
    :::

2. **Create the intermediate CA.** Real CAs keep the root offline and sign server certificates with an intermediate. First write a small file of **extensions** (extra fields in the certificate) that make it a CA.

    ```bash
    cat > ca-int.ext <<'EOF'
    basicConstraints = critical, CA:TRUE, pathlen:0
    keyUsage = critical, keyCertSign, cRLSign
    subjectKeyIdentifier = hash
    authorityKeyIdentifier = keyid
    EOF
    openssl req -new -newkey rsa:2048 -nodes \
        -keyout intCA.key -out intCA.csr -subj "/CN=Lab54 Intermediate CA"
    openssl x509 -req -in intCA.csr -CA rootCA.crt -CAkey rootCA.key \
        -CAcreateserial -days 1825 -extfile ca-int.ext -out intCA.crt
    ```

    ```{.output}
    Certificate request self-signature ok
    subject=CN = Lab54 Intermediate CA
    ```

    ::: explain
    **What just happened:** `openssl req -new` creates a **CSR** (certificate signing request: the public key plus the requested name). `openssl x509 -req` signs a CSR: `-CA` and `-CAkey` are the signer's certificate and key, `-CAcreateserial` creates a serial-number file (`rootCA.srl`) so each certificate gets a unique serial, and `-extfile` adds the extensions. `CA:TRUE, pathlen:0` means "may sign server certificates but not further CAs"; `keyCertSign` allows signing certificates.
    :::

3. **Create the server certificate**, signed by the intermediate, valid for the name `ubuntu-lab` only.

    ```bash
    cat > server.ext <<'EOF'
    basicConstraints = CA:FALSE
    keyUsage = critical, digitalSignature, keyEncipherment
    extendedKeyUsage = serverAuth
    subjectAltName = DNS:ubuntu-lab
    EOF
    openssl req -new -newkey rsa:2048 -nodes \
        -keyout server.key -out server.csr -subj "/CN=ubuntu-lab"
    openssl x509 -req -in server.csr -CA intCA.crt -CAkey intCA.key \
        -CAcreateserial -days 365 -extfile server.ext -out server.crt
    openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
    ```

    ```{.output}
    subject=CN = ubuntu-lab
    issuer=CN = Lab54 Intermediate CA
    notBefore=Oct 10 16:20:11 2026 GMT
    notAfter=Oct 10 16:20:11 2027 GMT
    X509v3 Subject Alternative Name:
        DNS:ubuntu-lab
    ```

    ::: explain
    **What just happened:** `openssl x509 -noout` reads a certificate without printing its encoded form; `-subject` and `-issuer` show who it is for and who signed it, `-dates` shows the validity window (`notBefore` and `notAfter`), and `-ext subjectAltName` shows the names it is valid for. Modern clients check **only the SAN** for the hostname; the CN (common name) in the subject is ignored. You will use this exact command in every scenario below.
    :::

4. **Set up an HTTPS site in nginx.** The site always serves `/etc/nginx/lab54/site.crt` and `site.key`, so each scenario only swaps those two files. Write the site file with a heredoc:

    ```bash
    sudo mkdir -p /etc/nginx/lab54
    cat <<'EOF' | sudo tee /etc/nginx/sites-available/lab54-tls
    server {
        listen 443 ssl;
        server_name ubuntu-lab;
        ssl_certificate     /etc/nginx/lab54/site.crt;
        ssl_certificate_key /etc/nginx/lab54/site.key;
        root /var/www/html;
    }
    EOF
    sudo ln -s /etc/nginx/sites-available/lab54-tls /etc/nginx/sites-enabled/
    ```

5. **Scenario (a): untrusted self-signed certificate.** Someone "quickly" made a self-signed certificate for the server.

    ```bash
    openssl req -x509 -newkey rsa:2048 -nodes -days 30 \
        -keyout selfsigned.key -out selfsigned.crt -subj "/CN=ubuntu-lab" \
        -addext "subjectAltName=DNS:ubuntu-lab"
    sudo cp selfsigned.crt /etc/nginx/lab54/site.crt
    sudo cp selfsigned.key /etc/nginx/lab54/site.key
    sudo nginx -t && sudo systemctl reload nginx
    curl -sS https://ubuntu-lab/ -o /dev/null
    ```

    ```{.output}
    nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
    nginx: configuration file /etc/nginx/nginx.conf test is successful
    curl: (60) SSL certificate problem: self-signed certificate
    ```

    Investigate what the server sends:

    ```bash
    openssl s_client -connect ubuntu-lab:443 -servername ubuntu-lab </dev/null 2>/dev/null | \
        grep -E "^depth|verify error|Verify return code"
    openssl s_client -connect ubuntu-lab:443 -servername ubuntu-lab </dev/null 2>/dev/null | \
        openssl x509 -noout -subject -issuer
    ```

    ```{.output}
    depth=0 CN = ubuntu-lab
    verify error:num=18:self-signed certificate
    Verify return code: 18 (self-signed certificate)
    subject=CN = ubuntu-lab
    issuer=CN = ubuntu-lab
    ```

    ::: explain
    **What just happened:** `openssl s_client` is a TLS test client. `-connect host:port` opens the connection, `-servername` sends the **SNI** (Server Name Indication: the hostname the client wants, so a server with many sites picks the right certificate), and `</dev/null` closes the connection right after the handshake. `depth=0` is the server certificate itself; error 18 means it is self-signed. Piping the output to `openssl x509` extracts the first certificate the server sent: subject and issuer are identical, so no CA vouches for it. Browsers show "Your connection is not private" for the same reason.
    :::

    **Root cause and fix.** Nobody the client trusts signed the certificate. Serve a CA-issued certificate, and make clients trust your private root CA by adding it to the system trust store.

    ```bash
    sudo cp server.crt /etc/nginx/lab54/site.crt
    sudo cp server.key /etc/nginx/lab54/site.key
    sudo nginx -t && sudo systemctl reload nginx
    sudo cp rootCA.crt /usr/local/share/ca-certificates/lab54-root.crt
    sudo update-ca-certificates
    ```

    ```{.output}
    Updating certificates in /etc/ssl/certs...
    1 added, 0 removed; done.
    ```

    ::: explain
    **What just happened:** On Ubuntu, `.crt` files placed in `/usr/local/share/ca-certificates/` are added to the system bundle `/etc/ssl/certs/ca-certificates.crt` by `update-ca-certificates`; curl, wget, apt, and most programs use that bundle. (Rocky: copy to `/etc/pki/ca-trust/source/anchors/` and run `sudo update-ca-trust`.) The other fix, `curl -k` or "ignore certificate errors", turns off the protection TLS exists to provide, so never make it permanent.
    :::

6. **Scenario (b): missing intermediate.** The server now has a properly issued certificate and the client trusts the root, yet:

    ```bash
    curl -sS https://ubuntu-lab/ -o /dev/null
    curl -sS --cacert rootCA.crt https://ubuntu-lab/ -o /dev/null
    ```

    ```{.output}
    curl: (60) SSL certificate problem: unable to get local issuer certificate
    curl: (60) SSL certificate problem: unable to get local issuer certificate
    ```

    Investigate: look at the whole chain the server sends with `-showcerts`, and test the chain offline with `openssl verify`.

    ```bash
    openssl s_client -connect ubuntu-lab:443 -servername ubuntu-lab -showcerts \
        -CAfile rootCA.crt </dev/null 2>/dev/null | grep -E "^ *[0-9] s:|i:|Verify return"
    openssl verify -CAfile rootCA.crt server.crt
    openssl verify -CAfile rootCA.crt -untrusted intCA.crt server.crt
    ```

    ```{.output}
     0 s:CN = ubuntu-lab
       i:CN = Lab54 Intermediate CA
    Verify return code: 21 (unable to verify the first certificate)
    CN = ubuntu-lab
    error 20 at 0 depth lookup: unable to get local issuer certificate
    error server.crt: verification failed
    server.crt: OK
    ```

    ::: explain
    **What just happened:** `-showcerts` prints every certificate the server sends, numbered from `0`; `s:` is the subject and `i:` the issuer. The server sends only certificate `0`, issued by "Lab54 Intermediate CA", but the client only has the root, so it cannot connect the two: there is a missing link. `-CAfile` tells `s_client` which roots to trust. `openssl verify -CAfile root` fails the same way (error 20), and adding the intermediate with `-untrusted` (meaning "an intermediate you may use to build the chain, but not trust as a root") makes it `OK`. That proves the certificate is fine and only the **served chain** is incomplete. Browsers sometimes hide this problem because they cache intermediates from other sites, which is why "it works in my browser but not in curl or the app" is the classic symptom.
    :::

    **Root cause and fix.** nginx must send the server certificate followed by the intermediate in one file (a **full chain**). Order matters: server first, then the intermediate. The root is not needed.

    ```bash
    cat server.crt intCA.crt > fullchain.crt
    sudo cp fullchain.crt /etc/nginx/lab54/site.crt
    sudo nginx -t && sudo systemctl reload nginx
    curl -sS https://ubuntu-lab/ -o /dev/null -w '%{http_code}\n'
    ```

    ```{.output}
    200
    ```

    (Apache uses the same idea: a full-chain file in `SSLCertificateFile`.) Running the `-showcerts` command again now lists certificates `0` and `1` and `Verify return code: 0 (ok)`.

7. **Scenario (c): hostname mismatch.** A user connects by a different name than the certificate covers.

    ```bash
    curl -sS https://localhost/ -o /dev/null
    openssl s_client -connect localhost:443 -servername localhost \
        -verify_hostname localhost </dev/null 2>/dev/null | grep "Verify return"
    openssl x509 -in /etc/nginx/lab54/site.crt -noout -ext subjectAltName
    ```

    ```{.output}
    curl: (60) SSL: no alternative certificate subject name matches target host name 'localhost'
    Verify return code: 62 (hostname mismatch)
        DNS:ubuntu-lab
    ```

    ::: explain
    **What just happened:** The chain is valid, but the certificate's SAN lists only `ubuntu-lab`, and the client asked for `localhost`. `openssl s_client` checks the chain but **not the hostname** unless you add `-verify_hostname`, so without it a mismatch can look like `Verify return code: 0 (ok)`. `openssl x509 -in file` reads the first certificate in the full-chain file, which is the server's. The same error appears when users browse to a server by IP address or by a short name that is not in the SAN.
    :::

    **Root cause and fix.** The certificate does not include every name clients use. Reissue it with all of them in the SAN (do not tell users to ignore the warning).

    ```bash
    sed -i 's/^subjectAltName.*/subjectAltName = DNS:ubuntu-lab, DNS:localhost, IP:127.0.0.1/' \
        server.ext
    openssl x509 -req -in server.csr -CA intCA.crt -CAkey intCA.key \
        -CAcreateserial -days 365 -extfile server.ext -out server.crt
    cat server.crt intCA.crt > fullchain.crt
    sudo cp fullchain.crt /etc/nginx/lab54/site.crt
    sudo systemctl reload nginx
    curl -sS https://localhost/ -o /dev/null -w '%{http_code}\n'
    ```

    ```{.output}
    Certificate request self-signature ok
    subject=CN = ubuntu-lab
    200
    ```

8. **Scenario (d): expired certificate.** To create a certificate that is already expired, you need it to be valid in the past. On Ubuntu 24.04 (OpenSSL 3.0) `openssl x509` has no option for a start date, so use the `faketime` package, which makes a single command believe it is a different date.

    ```bash
    faketime '2023-01-01' openssl x509 -req -in server.csr -CA intCA.crt -CAkey intCA.key \
        -CAcreateserial -days 30 -extfile server.ext -out expired.crt
    cat expired.crt intCA.crt > expired-chain.crt
    sudo cp expired-chain.crt /etc/nginx/lab54/site.crt
    sudo systemctl reload nginx
    curl -sS https://ubuntu-lab/ -o /dev/null
    ```

    ```{.output}
    Certificate request self-signature ok
    subject=CN = ubuntu-lab
    curl: (60) SSL certificate problem: certificate has expired
    ```

    ::: explain
    **What just happened:** `faketime '2023-01-01' command` runs one command with a fake clock (it preloads a small library that changes the time functions programs call). OpenSSL therefore stamped the certificate as valid from January 1, 2023 for 30 days. The system clock is not changed. Expired certificates are the most common certificate outage in real life: someone forgot to renew.
    :::

    Investigate the dates of what the server is actually serving:

    ```bash
    openssl s_client -connect ubuntu-lab:443 -servername ubuntu-lab </dev/null 2>/dev/null | \
        openssl x509 -noout -subject -issuer -dates -ext subjectAltName
    curl -v https://ubuntu-lab/ -o /dev/null 2>&1 | grep -E "expire|problem"
    date -u
    ```

    ```{.output}
    subject=CN = ubuntu-lab
    issuer=CN = Lab54 Intermediate CA
    notBefore=Jan  1 00:00:00 2023 GMT
    notAfter=Jan 31 00:00:00 2023 GMT
    X509v3 Subject Alternative Name:
        DNS:ubuntu-lab, DNS:localhost, IP Address:127.0.0.1
    * TLSv1.3 (OUT), TLS alert, certificate expired (557):
    * SSL certificate problem: certificate has expired
    Sat Oct 10 16:41:02 UTC 2026
    ```

    ::: explain
    **What just happened:** `notAfter` is in the past compared with `date -u`, so the certificate is expired. `curl -v` (verbose) prints the TLS handshake steps and the certificate details when it succeeds, and the exact reason when it fails. Always check the client's clock too: a client whose clock is years off reports valid certificates as expired or "not yet valid". On Rocky, `timedatectl` and `chronyc tracking` show whether the clock is synchronized.
    :::

    **Root cause and fix.** The certificate's validity period ended. Install a current certificate (here, the one from scenario (c)) and reload.

    ```bash
    sudo cp fullchain.crt /etc/nginx/lab54/site.crt
    sudo systemctl reload nginx
    curl -sS https://ubuntu-lab/ -o /dev/null -w '%{http_code}\n'
    openssl x509 -in fullchain.crt -noout -checkend 2592000 && echo "OK for 30+ days"
    ```

    ```{.output}
    200
    Certificate will not expire
    OK for 30+ days
    ```

    ::: explain
    **What just happened:** `-checkend 2592000` asks "will this certificate still be valid in 2,592,000 seconds (30 days)?" and exits `0` if yes, `1` if no, which makes it perfect for a monitoring script or cron job.
    :::

9. **Prevent.** Automate renewal (for public sites, an ACME client such as `certbot` renews Let's Encrypt certificates automatically), monitor expiry with `openssl x509 -checkend`, always deploy the full chain, put every name and IP clients use in the SAN, and test with `openssl s_client -verify_hostname` and `curl` (not only a browser) after every certificate change.

::: checkpoint
**Checkpoint:** `curl -sS https://ubuntu-lab/ -o /dev/null -w '%{http_code}\n'` prints `200` without `-k`, and you can name the error text for each of the four scenarios: "self-signed certificate", "unable to get local issuer certificate", "no alternative certificate subject name matches", and "certificate has expired".
:::

#### Task 11: Scenario 10: "apt update fails" (misconfigured package repository)

A **repository** is a server that holds packages plus signed index files. The package manager downloads the index, checks its digital signature against a trusted key, and only then believes the package list. Two things go wrong constantly: the URL is wrong, or the key is wrong. Both block updates, which quietly turns into an unpatched system (Task 8).

1. **Break 1 on ubuntu-lab: a typo in the URL.** Ubuntu 24.04 uses **deb822** source files: `/etc/apt/sources.list.d/*.sources`, with one `Field: value` per line. Create one with a typo (`ubuntuu`):

    ```bash
    cat <<'EOF' | sudo tee /etc/apt/sources.list.d/lab54-typo.sources
    Types: deb
    URIs: http://archive.ubuntu.com/ubuntuu
    Suites: noble
    Components: main
    Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
    EOF
    ```

    ::: explain
    **What just happened:** `Types: deb` means binary packages, `URIs` is the repository's base URL, `Suites` is the release (`noble` is the codename for 24.04), `Components` lists sections, and `Signed-By` names the only keyring whose keys may sign this repository. Compare it with the real file, `/etc/apt/sources.list.d/ubuntu.sources`.
    :::

2. **Break 2: the wrong signing key.** Add Ubuntu's debug-symbol repository (`ddebs.ubuntu.com`, a real repository signed with a different key) but point `Signed-By` at the normal archive keyring.

    ```bash
    cat <<'EOF' | sudo tee /etc/apt/sources.list.d/lab54-ddebs.sources
    Types: deb
    URIs: http://ddebs.ubuntu.com
    Suites: noble
    Components: main
    Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
    EOF
    ```

3. **Symptom.**

    ```bash
    sudo apt update
    ```

    ```{.output}
    Ign:5 http://archive.ubuntu.com/ubuntuu noble InRelease
    Err:6 http://ddebs.ubuntu.com noble InRelease
      The following signatures couldn't be verified because the public key is not available: NO_PUBKEY C8CAB6595FDFF622
    Err:7 http://archive.ubuntu.com/ubuntuu noble Release
      404  Not Found [IP: 91.189.91.83 80]
    Reading package lists... Done
    W: GPG error: http://ddebs.ubuntu.com noble InRelease: The following signatures couldn't be verified because the public key is not available: NO_PUBKEY C8CAB6595FDFF622
    E: The repository 'http://ddebs.ubuntu.com noble InRelease' is not signed.
    E: The repository 'http://archive.ubuntu.com/ubuntuu noble Release' does not have a Release file.
    N: Updating from such a repository can't be done securely, and is therefore disabled by default.
    ```

    ::: explain
    **What just happened:** Read every `Err:` and `E:` line; each names the repository URL. **"404 Not Found" plus "does not have a Release file"** means apt reached the server but the path does not exist: a typo, a wrong suite name (for example `jammy` content on a `noble` system, or a release the vendor never published), or a repository that moved. **"NO_PUBKEY C8CAB6595FDFF622" plus "is not signed"** means the index was signed by a key that is not in the keyring named by `Signed-By`. apt then refuses the repository instead of trusting unsigned data, which is exactly the right behavior.
    :::

4. **Investigate.** Find which files define the failing repositories, check what apt actually uses, and compare the key IDs.

    ```bash
    grep -rl -e ubuntuu -e ddebs /etc/apt/sources.list /etc/apt/sources.list.d/
    apt-cache policy | grep -E "ddebs|ubuntuu"; echo "exit: $?"
    curl -sI http://archive.ubuntu.com/ubuntuu/dists/noble/Release | head -n 1
    curl -sI http://archive.ubuntu.com/ubuntu/dists/noble/Release | head -n 1
    gpg --show-keys /usr/share/keyrings/ubuntu-archive-keyring.gpg | grep -E "^ +[0-9A-F]{40}"
    ```

    ```{.output}
    /etc/apt/sources.list.d/lab54-ddebs.sources
    /etc/apt/sources.list.d/lab54-typo.sources
    exit: 1
    HTTP/1.1 404 Not Found
    HTTP/1.1 200 OK
    790BC7277767219C42C86F933B4FE6ACC0B21F32
    843938DF228D22F7B3742BC0D94AA3F0EFE21092
    F6ECB3762474EDA9D21B7022871920D1991BC93C
    ```

    ::: explain
    **What just happened:** `grep -rl` lists the files that contain the bad names. `apt-cache policy` shows every repository apt is actually using, with its priority; the two broken ones are absent (exit `1` from `grep`), so their packages are invisible. `curl -sI` fetches only the HTTP headers: the typo'd path returns `404` while the correct path returns `200`, which confirms the URL error. `gpg --show-keys` lists the fingerprints in a keyring without importing anything; the last 16 hex digits of a fingerprint are its key ID. `C8CAB6595FDFF622` is not among them, so the wrong keyring is named.
    :::

5. **Root cause and fix.** The first file has a wrong URL; the second names the wrong keyring. Fix the URL, and install the correct keyring package for the debug repository and point `Signed-By` at it.

    ```bash
    sudo sed -i 's#/ubuntuu$#/ubuntu#' /etc/apt/sources.list.d/lab54-typo.sources
    sudo apt install -y ubuntu-dbgsym-keyring
    sudo sed -i 's#ubuntu-archive-keyring.gpg#ubuntu-dbgsym-keyring.gpg#' \
        /etc/apt/sources.list.d/lab54-ddebs.sources
    sudo apt update 2>&1 | grep -E "^(Err|E:|W:)"
    apt-cache policy | grep -A1 ddebs | head -n 2
    ```

    ```{.output}
    W: Target Packages (main/binary-amd64/Packages) is configured multiple times in /etc/apt/sources.list.d/lab54-typo.sources:1 and /etc/apt/sources.list.d/ubuntu.sources:1
    W: Target Packages (main/binary-all/Packages) is configured multiple times in /etc/apt/sources.list.d/lab54-typo.sources:1 and /etc/apt/sources.list.d/ubuntu.sources:1
    ...
     500 http://ddebs.ubuntu.com noble/main amd64 Packages
         release o=Ubuntu,a=noble,n=noble,l=Ubuntu,c=main,b=amd64
    ```

    ::: explain
    **What just happened:** `sed` with `#` as the separator avoids escaping the slashes in the URL. The `ubuntu-dbgsym-keyring` package puts the right public key in `/usr/share/keyrings/ubuntu-dbgsym-keyring.gpg`, so the `Err` and `E:` lines are gone and `apt-cache policy` now lists the debug repository with the default priority `500`. #### Task 12: Scenario 11: Old protocols and "no matching cipher" (obsolete and insecure protocols and ciphers)

**Obsolete** protocols such as SSLv3, TLS 1.0, and TLS 1.1 and **insecure** ciphers such as RC4, 3DES, CBC-mode SSH ciphers, and SHA-1-based key exchange have known weaknesses. Leaving them enabled is a security finding (and fails compliance standards such as PCI DSS). Removing them can then cause **cipher negotiation** failures with old clients. You handle both sides here.

**How negotiation works:** the client sends its list of supported protocol versions and algorithms; the server picks the best one that appears in *both* lists. If there is no overlap, the handshake fails before any login. So "no matching cipher" is never fixed by guessing; you compare the two lists.

1. **Break it on ubuntu-lab: enable TLS 1.0 and 1.1.** An admin wants an ancient monitoring tool to connect, so they add old protocols to the Task 10 site. On Ubuntu 24.04 OpenSSL's default **security level** (2) already refuses TLS 1.0/1.1 even if nginx lists them, so the "make it work" change also lowers the security level. Open the site file with `sudo nano /etc/nginx/sites-available/lab54-tls` and add these two lines inside the `server { }` block, under `ssl_certificate_key`:

    ```text
        ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3;
        ssl_ciphers DEFAULT:@SECLEVEL=0;
    ```

    Then test and reload:

    ```bash
    sudo nginx -t && sudo systemctl reload nginx
    ```

    ::: explain
    **What just happened:** `ssl_protocols` lists the TLS versions nginx accepts. `ssl_ciphers` sets the OpenSSL cipher string; `DEFAULT` is OpenSSL's default list, and `@SECLEVEL=0` drops the security level to 0, which allows old protocols, SHA-1, and small keys. Note that Ubuntu's main `/etc/nginx/nginx.conf` itself contains `ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3;` in its `http` block; a server-level `ssl_protocols` overrides it. Check with `grep -rn ssl_protocols /etc/nginx/`.
    :::

2. **Detect it the way an auditor would.** nmap's `ssl-enum-ciphers` script performs a handshake for every protocol version and cipher it knows and lists what the server accepts.

    ```bash

3. **Try it with OpenSSL, and understand the client-side refusal.**

    ```bash

    **What just happened:** `-tls1` forces TLS 1.0. Do not mistake that for proof that the server is safe. Lowering the client's level with `-cipher 'DEFAULT:@SECLEVEL=0'` lets the client try, and the server accepts: `Protocol : TLSv1`. 5. **SSH cipher negotiation: break it from the client side.** Simulate an old SSH client (or a script written for an old device) that insists on algorithms modern OpenSSH no longer offers.

7. **Decide on the right fix.**

        ```text

            HostName 192.168.100.50
            KexAlgorithms +diffie-hellman-group14-sha1
            HostKeyAlgorithms +ssh-rsa
        ```

        The `+` adds an algorithm to the default list instead of replacing it. Never add old algorithms globally in `/etc/ssh/sshd_config` "just in case".

    ```bash

- Security fixes must not weaken security: fix the label, boolean, permission, key, or config; never "disable SELinux", `chmod 777`, `curl -k`, or `gpgcheck=0`.
- **SELinux**: wrong **context** = `ls -Z`, `restorecon -Rv` (persistent custom paths: `semanage fcontext -a`); optional feature off = **boolean** (`getsebool`, `setsebool -P`); port not allowed = **policy** (`semanage port -a -t http_port_t -p tcp 8090`). Evidence: `ausearch -m avc -ts recent`, `audit2why`, `sealert -a`. `mv` keeps labels, `cp` does not.
- **Permissions**: directories need `x` to be entered (`namei -l`); on a file with an **ACL**, `chmod` group bits change the **mask** (`getfacl` shows `#effective:`); **attributes** `i` (immutable) and `a` (append-only) block even root (`lsattr`, `chattr`).
- **Account access**: `passwd -S` (L = locked), `chage -l` / `chage -E` (account expiry), `getent passwd` (`nologin` shell), `faillock --user X --reset` (pam_faillock lockout).
- **Remote access**: `ssh -v` on the client plus `journalctl -u ssh` / `/var/log/secure` on the server; `StrictModes` needs `~/.ssh` `700` and `authorized_keys` `600`; `AllowUsers`/`AllowGroups`; test with `sshd -t`, view effective config with `sshd -T`.
- **Unpatched** systems: `apt list --upgradable`, `unattended-upgrades`, `apt-mark showhold`, `/var/run/reboot-required`, `needrestart`; Rocky `dnf updateinfo list --security`, `dnf upgrade --security`, `dnf needs-restarting -r`.
- **Exposed** service: `ss -tlnp` shows `0.0.0.0`, `[::]`, or `*` for all interfaces versus `127.0.0.1` for local only; confirm with `nmap -sT -p-`; fix by binding to loopback, requiring authentication, and a default-deny firewall (`ufw default deny incoming` after `ufw allow OpenSSH`).
- **Certificate** errors: "self-signed certificate" (untrusted; add the CA to the trust store with `update-ca-certificates` / `update-ca-trust`), "unable to get local issuer certificate" (missing intermediate; serve the full chain), "no alternative certificate subject name matches" (fix the SAN), "certificate has expired" (renew; check `notAfter` and the clock).
- Certificate tools: `openssl s_client -connect host:443 -servername host -showcerts`, `openssl x509 -noout -subject -issuer -dates -ext subjectAltName`, `openssl verify -CAfile root -untrusted intermediate cert`, `curl -v --cacert`, `openssl x509 -checkend`.
- **Repository** errors: apt "404 Not Found" / "does not have a Release file" = wrong URL or suite; "NO_PUBKEY" / "is not signed" = wrong or missing key in `Signed-By`. dnf: "Cannot download repomd.xml" = wrong `baseurl`; "GPG check FAILED" = wrong `gpgkey`. Check with `apt-cache policy`, `dnf repolist -v`, `dnf makecache`.
- **Obsolete/insecure** protocols: SSLv3, TLS 1.0, TLS 1.1, RC4, 3DES, CBC SSH ciphers, `diffie-hellman-group1-sha1`. Detect with `nmap --script ssl-enum-ciphers -p 443 host`; nginx `ssl_protocols TLSv1.2 TLSv1.3;`.
- **Cipher** negotiation: "no matching cipher found" / "no matching key exchange method found. Their offer: ..." means the lists do not overlap; diagnose with `ssh -vv`, `ssh -Q cipher`, `sshd -T`; fix the old client. Rocky: `update-crypto-policies --show` (DEFAULT, LEGACY, FUTURE, FIPS).

**Review questions**

1. A web page copied with `mv` from a home directory into `/var/www/html` returns "403 Forbidden" on Rocky Linux, although the file mode is `644`. Which command fixes it the right way?

    A. `setenforce 0`\
    B. `chmod 777 /var/www/html/page.html`\
    C. `restorecon -v /var/www/html/page.html`\
    D. `setsebool -P httpd_enable_homedirs on`

2. A security audit runs `ss -tlnp` on a server and sees `0.0.0.0:6379` owned by `redis-server`. What does this mean?

    A. Redis is listening only on the loopback interface\
    B. Redis is listening on every IPv4 interface and may be reachable from the network\
    C. Redis is not running\
    D. Redis is blocked by the firewall

3. `curl https://app.example.lan/` fails with "SSL certificate problem: unable to get local issuer certificate", but the site works in a browser. `openssl s_client -showcerts` shows only certificate `0`. What is the best fix?

    A. Add `-k` to every curl command\
    B. Configure the server to send the server certificate followed by the intermediate certificate\
    C. Add the server certificate's SAN to `/etc/hosts`\
    D. Set the client's clock back

4. `sudo apt update` prints "The following signatures couldn't be verified because the public key is not available: NO_PUBKEY 1234ABCD5678EF90" for a third-party repository. What should the administrator do?

    A. Add `trusted=yes` to the source entry\
    B. Delete `/var/lib/apt/lists/` and retry\
    C. Obtain the vendor's correct key from an official source, verify its fingerprint, and reference it with `Signed-By`\
    D. Change `http` to `https` in the URL

5. A user's script fails with "Unable to negotiate with 10.0.0.5 port 22: no matching key exchange method found. Their offer: curve25519-sha256,...". The script uses `-oKexAlgorithms=diffie-hellman-group1-sha1`. What is the best fix?

    A. Add `diffie-hellman-group1-sha1` to the server's `KexAlgorithms`\
    B. Remove the forced old algorithm from the script (or upgrade the client) so a modern key exchange is negotiated\
    C. Set the crypto policy to LEGACY on the server\
    D. Restart sshd

6. Which command lists the TLS protocol versions and ciphers a web server accepts?

    A. `nmap --script ssl-enum-ciphers -p 443 server`\
    B. `ss -tlnp`\
    C. `openssl x509 -noout -dates`\
    D. `update-ca-certificates`

::: answers
1. **C.** `mv` kept the `user_home_t` label; `restorecon` resets the file to the policy's default type `httpd_sys_content_t` without weakening SELinux.
2. **B.** `0.0.0.0` means all IPv4 addresses, so Redis is reachable from other hosts unless a firewall blocks it; it should bind to `127.0.0.1`.
3. **B.** The served chain is missing the intermediate (browsers often cache it); serving a full chain lets every client build the path to the trusted root.
4. **C.** The index was signed by a key apt does not have; the fix is the correct, verified key, never disabling signature checks.
5. **B.** The server correctly refuses an obsolete key exchange; the client should use modern algorithms instead of weakening the server.
6. **A.** The `ssl-enum-ciphers` NSE script handshakes with each protocol version and cipher and lists what the server accepts.
:::
